# Katelya Blog 长期内容策略设计（A 方案）

日期：2026-08-17

## 目标

将博客从偏 AI Coding 资讯聚合，调整为更有个人辨识度的“技术实验记录 + 深度技术分享”型数字花园。核心要求不是追逐热点数量，而是持续沉淀可复现、可验证、能体现工程判断的内容。

博客叙事主体应始终是技术问题、实验过程、系统架构、踩坑经验与个人思考。LINUX DO、NodeLoc 等社区可以作为素材雷达，但不应频繁成为文章开场、标题或主叙事来源。

## 内容比例

采用 A 方案：

- 70%：真实项目、真实环境、真实折腾形成的实战记录。
- 20%：前沿技术深挖、学习型实验与新方向探索。
- 10%：真正值得记录的重大科技动态。

这里的比例按一段时间内的文章池理解，不要求逐周机械凑数。

## 70%：实战记录主线

优先从已经实际使用、部署、排障或长期维护过的技术栈中选题，包括：

- VPS / Linux：Oracle ARM、Ubuntu、磁盘扩容、内存分析、systemd、日志、性能调优、备份与故障恢复。
- 网络与边缘基础设施：Cloudflare、DNS、CDN、Pages、Workers、Tunnel、Zero Trust、HTTP/3、QUIC、IPv6、反向代理、缓存策略。
- 自托管与个人云实验室：Docker、1Panel、对象存储、图床、Telegram Storage、监控、服务编排、自动备份。
- DevOps：GitHub Actions、CI/CD、自动 PR、发布流水线、Cloudflare Pages、CDN 刷新、Secrets、分支策略、回滚与验证。
- Web / Serverless：Astro、Cloudflare Workers、API、数据库、缓存、PWA、小程序及其后端工程。
- AI 工程：Codex、Claude Code、Kimi CLI、MCP、Skills、Agent Harness、模型路由、API 中转、上下文管理、测试与验证。
- 桌面与开发环境：Windows 深度定制、Windhawk、PowerShell、WSL、终端、文件管理器、自动化工具链。

这类文章优先使用“问题 → 原因 → 实验 → 配置/代码 → 验证 → 取舍 → 最终方案”的结构，而不是教程命令堆砌。

## 20%：前沿技术深挖与学习型实验

这一部分用于扩宽技术面，可以写尚未成为长期主力栈、但值得学习和实验的方向。

### 嵌入式 / 单片机新增主线

将嵌入式、MCU、IoT 正式加入选题池，优先覆盖：

- ESP32 / ESP32-S3：Wi-Fi、BLE、GPIO、ADC、PWM、I2C、SPI、UART。
- STM32：寄存器、HAL、CubeMX、定时器、中断、DMA、ADC、串口与基础 RTOS。
- RP2040 / Raspberry Pi Pico：PIO、MicroPython、C/C++ SDK。
- MQTT、Home Assistant、Node-RED、传感器与边缘采集。
- FreeRTOS：任务、队列、信号量、调度与实时系统基础。
- TinyML / Edge AI：MCU 端推理、量化、传感器数据分类、边缘 AI。
- PCB / 硬件基础：原理图阅读、供电、GPIO 电平、常用通信总线、调试工具。
- 调试工具：串口、逻辑分析仪、示波器、JTAG/SWD 的入门与实战。

嵌入式内容必须保持真实性。尚未亲自完成的内容，不包装成“我已经长期实战过”，而使用以下叙事形式：

- 学习笔记；
- 原理拆解；
- 从零实验计划；
- 仿真或最小可复现实验；
- 官方开发板 / 模拟器验证；
- “准备入坑前先搞懂什么”系列。

一旦真正完成板卡、传感器、MQTT 或边缘 AI 项目，相应内容可以转入 70% 实战主线。

### 其他前沿方向

- eBPF、WASM、WebAssembly Runtime。
- Tailscale / WireGuard / Overlay Network。
- Service Mesh、边缘计算、分布式缓存。
- 本地 AI、量化、推理加速与端侧模型。
- 新型数据库、向量数据库、流式数据系统。
- 浏览器新能力、WebGPU、WebRTC。
- 安全工程、供应链安全、SBOM、Passkey。

## 10%：重大科技动态

只有当一条新闻至少满足以下条件之一时，才值得单独成文：

- 明显改变开发者工作流；
- 引入新的网络、云、AI 或硬件范式；
- 会直接影响现有项目选型；
- 有足够技术细节可做原理和工程分析；
- 可以结合真实环境做测试或验证。

单纯“某模型发布”“某产品更新几个参数”“社区很火”不再作为独立成文的充分理由。

## 文章含金量门槛

正式发布的技术文章至少满足下列 3 项：

1. 有明确的问题或技术命题。
2. 有原理解释，而不只是操作步骤。
3. 有可复现命令、配置、代码、架构图或实验方法。
4. 有实际验证结果或来源可靠的一手数据。
5. 有踩坑、失败路径或边界条件。
6. 有性能、成本、安全、复杂度等取舍分析。
7. 有作者自己的结论，而不是重新排列别人的观点。

如果只能做到“新闻摘要 + 参数表 + 泛泛评论”，则不发布。

## 推荐文章形态

长期轮换以下几种类型，避免页面被同一种标题和结构占满：

- 《我为什么这样搭》：拆真实系统架构与技术选型。
- 《踩坑记录》：从异常现象一路追到根因。
- 《从 0 到可用》：完整构建一个小型工具或服务。
- 《原理拆解》：讲清协议、系统机制或硬件原理。
- 《实测》：比较性能、成本、延迟、资源占用或稳定性。
- 《学习实验室》：用于嵌入式、单片机、网络协议等新领域。
- 《重构复盘》：记录项目架构从旧方案迁移到新方案的原因。
- 《一个周末的技术实验》：短周期但真实可复现的小项目。

## 来源策略

信息来源优先级：

1. 官方文档、RFC、标准、源码、Release Notes、技术论文。
2. 项目仓库 Issue / Discussion / Changelog。
3. 作者或维护者的一手技术文章。
4. 高质量社区讨论，用于发现问题和不同观点。
5. 二手媒体仅用于发现线索，不作为复杂技术结论的唯一依据。

社区素材可以触发选题，但文章尽量不写成“我在某论坛看到一个帖子，于是……”的转载式叙事。

## 真实性与个人风格

文章可以有明显的 Katelya 个人风格和第一人称判断，但需要区分三类事实：

- “我实际做过”：必须确实有项目、命令、截图、配置、日志或实验支撑。
- “我正在学 / 准备试”：可以写学习路径、原理和最小实验，不伪造长期经验。
- “我推测 / 我认为”：明确标注这是工程判断或趋势推断。

这样可以让博客技术面快速扩宽，同时维持长期可信度。

## 选题决策规则

每次准备发文前先回答：

- 这篇东西六个月后还有没有参考价值？
- 它是否能帮读者少踩一个坑、理解一个机制，或复现一个系统？
- 是否与最近三篇文章过于相似？
- 是否能体现个人技术栈或正在扩展的能力边界？
- 是否有足够一手资料验证？

如果前三个问题中有两个回答为否，则换题。

## 近期内容方向建议

接下来优先降低连续 AI Coding 文章密度，穿插网络、VPS、Cloudflare、自托管和嵌入式内容。比较适合作为下一阶段的主题包括：

- Cloudflare Pages + DogeCloud CDN 双层发布链路到底发生了什么。
- Oracle ARM VPS 内存到底被谁吃掉了：Linux 内存统计的正确读法。
- 从 DNS 到 TLS：访问一个自建站点时数据包到底经历了什么。
- GitHub Actions 为什么“CI 全绿”仍然不代表生产已经上线。
- ESP32 入坑第一课：GPIO、UART、I2C 到底是什么，为什么单片机总在和外设“说话”。
- 用 Wokwi 做第一个无需购买开发板的 ESP32 可复现实验。
- MQTT 为什么特别适合 IoT：从 Publish/Subscribe 到 QoS。
- Cloudflare Tunnel、FRP、Tailscale 三种“把内网服务带出去”的思路有什么本质区别。
- Docker 容器显示占用很小，为什么 VPS 内存还是越来越高。
- 从 Telegram Storage 到对象存储：个人图床真正应该怎么选。

## 成功标准

经过一段时间后，首页不应让访问者产生“这是一个 AI 模型资讯站”的印象，而应该自然形成以下认知：

> 这是 Katelya 的个人技术实验室：会折腾服务器、网络、云服务、Web、自动化和 AI，也正在逐渐深入嵌入式与边缘计算；每篇文章尽量留下真实的问题、实验和工程判断。
