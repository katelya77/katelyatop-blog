很多团队把“包已经能安装”当作 SDK 发布完成，把“GitHub 上有一个 Release”当作版本事实的最终证明。但软件交付不是一个布尔值：npm 上出现包，说明某个发布动作完成；Git 标签存在，说明仓库有一个可定位的版本对象；Release 页面可读，说明维护者为人类读者建立了入口；而 SDK 实际捆绑的 CLI、源码提交和构建产物是否彼此对应，仍然需要单独验证。

Qwen Code 的 TypeScript SDK v0.1.29 Release 提供了一个很典型的公开样本。其说明明确写道：这是一次回填发布，原因是原始工作流在 npm publish 成功之后，于推送 release 分支步骤失败；同一页面还列出了不同的 Bundled CLI Version，包括 0.26.9、0.26.8、0.26.6、0.26.4、0.26.3 和 0.26.2。这个事实不等于 SDK 一定不可用，却说明“发布成功”与“发布记录完整”不是同一个状态。另一个对照样本是 OpenAI Codex 的 rust-v0.169.0-alpha.5：它以 alpha 标签发布，并指向明确的 Git 提交，同时页面显示有两个资产。它适合提醒我们：预发布标签、提交对象和资产列表，也都只是证据链中的不同节点。

## 先把“发布完成”拆成多个状态

一个可审计的 SDK 发布，至少应拆成五个状态：源码可定位、包已生成、包已上传、发布记录已建立、依赖关系已解释。它们可以由同一条 CI 工作流触发，但不应被当作一个不可分割的事务。

第一层是源码定位。版本号应能落到一个 Git tag、一个提交或一个明确的构建引用。没有这个定位，后续即使下载到了包，也很难回答“这个包由哪一次源码构建而来”。第二层是包生成。构建结果需要包含预期的入口、类型声明和运行时文件，而不是只凭文件名判断。第三层是上传。npm publish 成功只能证明注册表接受了某次上传，不会自动证明 GitHub Release 已经创建，也不会证明 Release 说明中的版本信息完整。

第四层是发布记录。Release 是给维护者、使用者和自动化系统共同消费的索引；回填 Release 并不天然是错误，但它意味着流程曾经在中间状态停下。第五层是关系解释：SDK 捆绑哪个 CLI、使用哪个提交、是否包含预发布组件，都需要在发布记录中保持一致。若一个页面同时出现多个 Bundled CLI Version，读者就必须知道它们分别对应什么版本或历史条目，否则“SDK v0.1.29”这个标签的解释成本会转嫁给使用者。

因此，发布状态不应只有 `success`。更实用的模型是：`source_resolved`、`artifact_built`、`registry_published`、`release_indexed`、`metadata_consistent`。只有最后一个状态也为真，才适合把版本推荐给下游项目。

## 回填发布暴露了什么故障边界

S4 中最值得关注的不是“回填”两个字，而是故障发生在 npm publish 之后。它证明发布流水线可能已经产生不可逆的外部副作用，随后才在仓库分支或 Release 元数据步骤失败。此时重跑整条流水线并不安全：如果再次执行上传动作，可能遇到不可覆盖的版本、重复的资产，或者让消费者看到两个看似相同但来源不同的构建结果。

这类流程应该把不可逆步骤放在明确的边界之后，并为每一步设计幂等处理。一个简化的发布流程可以是：

```text
准备版本 -> 构建并检查包 -> 记录源码提交 -> 上传注册表 -> 创建或回填 Release -> 校验所有元数据
```

其中“上传注册表”之后必须进入恢复流程，而不是简单地从头重跑。恢复流程至少要回答三个问题：注册表中是否已经存在目标版本；现有包的内容是否与本次构建一致；Release 是否缺失、部分创建，还是已经存在但内容错误。

检查动作可以从这些命令开始：

```bash
npm view <package-name>@<version> version dist.tarball
npm pack <package-name>@<version> --dry-run
npm view <package-name>@<version> dist.integrity

git ls-remote --tags origin 'refs/tags/<tag>'
git rev-list -n 1 <tag>
sha256sum <downloaded-tarball>
```

这些命令不能单独证明“发布完全正确”，但能把注册表版本、包内容、完整性字段和 Git 引用分别拉出来。重要的是不要把 `npm view` 的成功当作源码对应关系已经成立；它只能回答注册表当前看到了什么。

## 捆绑版本为什么需要结构化记录

SDK 与 CLI 的关系比普通依赖更容易造成误解。用户安装的是 SDK，却可能实际启动一个随 SDK 打包的 CLI；于是 SDK 版本和 CLI 版本构成一个二维版本关系。发布页如果只写“bundled CLI”，但没有明确它对应的构建输入、兼容范围或变更原因，下游就无法判断升级风险。

Qwen Code 的公开 Release 文本列出多个 CLI 版本，这至少说明发布记录不是一个简单的单值字段，或者页面内容包含了多个历史条目。无论原因是回填脚本重复写入、模板未清理，还是多个构建结果被合并展示，工程上都不应让读者猜测。更可靠的做法是把关系结构化，例如：

```json
{
  "sdk": "0.1.29",
  "cli": "0.26.9",
  "sourceCommit": "<commit>",
  "artifact": "<sha256>",
  "releaseKind": "stable"
}
```

这里的关键不是 JSON 本身，而是每个字段都只能有一个明确语义。若确实存在多个兼容的 CLI 构建，应分别列出平台、入口和校验值，而不是连续追加多个“Bundled CLI Version”标题。发布说明服务于人类阅读，机器可验证的关系则应放入包元数据、构建清单或自动生成的附件中。

同样的原则适用于 Codex 的 alpha Release。`rust-v0.169.0-alpha.5` 已经通过标签表达了预发布性质，页面还指向提交并列出资产。这里不能推导出它适合生产，也不能因为有 Release 就忽略 alpha 风险。标签、提交、资产分别回答“它是什么”“由什么源码定位”“用户能拿到什么”，不能互相替代。

## 一套适合 CI 的验收清单

发布前，先验证版本唯一性：包管理器、Git tag、Release 标题和包内版本字段必须一致。若项目允许 SDK 与 CLI 分开版本，必须明确二者的对应关系，而不是依赖读者从时间顺序推断。

发布后，验证四类结果：

1. 注册表查询返回目标版本，下载地址可访问，包内入口和类型声明存在。
2. Git tag 能解析到预期提交，Release 的标签与提交没有漂移。
3. 发布说明中的捆绑组件版本与包内实际文件一致，不能只检查文字。
4. 失败重试不会再次执行已经完成的不可逆动作，回填路径有明确日志和人工介入条件。

对于预发布版本，再增加三项门禁：标签是否包含 alpha、beta 或 rc 等稳定性信号；安装命令是否被文档明确标为试用路径；升级测试是否覆盖从上一个稳定版本到当前版本的回退。预发布版本可以进入测试仓库或内部渠道，但不能仅凭 Release 页面存在就改变生产依赖策略。

## 什么时候应该停止升级

如果版本号存在但源码提交无法定位，应停止升级；如果 npm 包存在但 Release 缺失，可以先把它视为“注册表已发布、索引未完成”，而不是直接宣布完整交付；如果 Release 中出现互相矛盾的捆绑版本，应暂停自动升级，直到维护者澄清元数据；如果只能确认“下载成功”，却无法确认包内容和来源一致，则最多把它用于隔离环境验证。

这套边界的价值在于避免两种相反错误。一种是看到回填就断言发布失败，忽略包可能已经成功可用；另一种是看到 npm 安装成功就断言整个交付完成，掩盖后续索引和来源问题。工程判断应当描述事实所在的阶段，而不是给整个事件贴一个过于粗糙的成功或失败标签。

## 结论：发布系统要交付证据，不只是交付文件

SDK 发布的核心产物不只有 tarball，还包括一组能相互指向的证据：源码提交、版本标签、注册表包、完整性信息、Release 说明以及捆绑组件关系。Qwen Code v0.1.29 的回填说明揭示了外部副作用之后的工作流失败边界；Codex 的 alpha Release 则展示了预发布标签、提交和资产如何共同构成定位信息。

原创的工程结论是：发布流水线不应追求“所有步骤看起来像一次成功”，而应允许部分完成，并把每个完成状态持久化、可查询、可恢复。只有这样，失败时才能准确回填，升级时才能判断风险，审计时也才能区分“包存在”“版本可定位”和“交付证据完整”。对 SDK 消费者而言，最稳妥的升级动作不是盯着最新版本号，而是先验证这条证据链是否闭合。
