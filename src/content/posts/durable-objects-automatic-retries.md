## 这次变化解决的不是“所有失败”

Cloudflare 在 2026 年 11 月 5 日的官方 Changelog 中宣布：Workers 或另一个 Durable Object 调用 Durable Object 时，如果调用在到达目标对象前遇到可重试错误，运行时会自动再次发起调用。过去，应用通常需要在业务代码中包一层重试循环；现在，短暂的网络中断可以由运行时处理。

这个描述有两个容易被忽略的限定。第一，重试针对的是“可重试错误”，不是所有异常。Durable Object 方法自身抛出的错误不会触发这套机制；标记了 `overloaded` 的错误也不会触发。第二，自动重试只覆盖调用链上的一部分失败，并不能证明业务操作已经安全完成。调用者仍然要回答一个问题：如果网络在服务端已经收到请求之后断开，客户端还能不能再次发送？

因此，这项能力更适合被理解为调用传输层的可靠性增强，而不是业务事务的自动恢复。它降低了网络抖动对调用方的可见性，却没有替应用决定库存扣减、余额变更或消息追加是否允许重复执行。

## 先画清调用模型：失败发生在哪里

一次 Durable Object 调用至少可以拆成四个阶段：调用方创建 stub，运行时建立连接，请求抵达目标对象，目标对象执行方法并写入存储。自动重试主要处理前两个阶段以及请求抵达前后无法明确判断状态的异常。

最简单的成功路径是：调用方发送请求，目标对象收到请求，方法完成，响应返回。若连接在发送前断开，重新发送通常不会产生业务副作用，因为目标对象尚未执行方法。若连接在目标对象收到请求后断开，调用方却无法判断方法是否已经完成，运行时仍可能重试。这就是分布式系统中典型的“结果未知”状态：网络层不知道服务端究竟执行到了哪一步。

官方说明给出的保护是：当连接中断且运行时无法判断 Durable Object 是否已经收到调用时，运行时会继续尝试；如果第一次调用已经抵达，Durable Object 会拒绝这次重试。这样做的目标是避免同一个普通方法因为运行时重试而执行两次。这里的关键不是“网络永远不会重复投递”，而是普通方法默认受到运行时语义保护。

不过，官方也提供了 `retryable()` 标记，用来声明某个方法可以在重试中再次运行。这个 API 把决定权交给开发者：只有确认方法具有幂等性，或者已经设计了去重机制，才应当允许它被再次执行。把所有方法都标记为可重试，会把网络恢复问题转化为业务重复执行问题。

## `retryable()` 的真正含义是业务承诺

下面的例子中，`setQuantity` 是幂等操作。无论同一个参数被执行一次还是多次，最终数量都被设置为同一个值；`addOne` 则是累加操作，重复运行会多加一次，因此不能直接标记为可重试。

```ts
import { DurableObject } from "cloudflare:workers";
import { retryable } from "cloudflare:durable-objects";

export class Cart extends DurableObject {
  static {
    retryable(this.prototype.setQuantity);
  }

  async setQuantity(itemId: string, quantity: number): Promise<void> {
    await this.ctx.storage.put(itemId, quantity);
  }

  async addOne(itemId: string): Promise<void> {
    const quantity = (await this.ctx.storage.get<number>(itemId)) ?? 0;
    await this.ctx.storage.put(itemId, quantity + 1);
  }
}
```

这里的“幂等”不能只看函数名。`setQuantity` 的写入值由参数直接决定，重复执行通常仍然收敛到同一结果；但如果方法同时发送邮件、扣除外部账户、写入另一个系统，单一 Durable Object 存储中的幂等性就不够了。工程上应把副作用拆开，或者为外部操作引入请求 ID、去重表和可查询的处理状态。

对累加类操作，不能因为“加一”很短就放开重试。更稳妥的方案是把业务请求变成带唯一键的命令：目标对象先记录请求 ID，再决定是否应用变更。若同一个请求再次到达，读取到已完成记录后直接返回原结果。这样保护的是业务语义，而不是依赖网络层恰好只投递一次。

## 默认策略与局部配置：不要把数字当成可靠性保证

官方变更说明给出的默认行为是：运行时最多重试四次，并且从初次调用开始计算，不会在超过十秒后再启动新的重试。调用者也可以在 `get()` 或 `getByName()` 时为单个 stub 指定 `retry` 选项：`maxRetries` 可设为 0 到 10，`timeoutMs` 可设为 500 到 60000 毫秒。

```ts
const stub = env.CART.getByName("user-123", {
  retry: {
    maxRetries: 1,
    timeoutMs: 2000,
  },
});
```

这两个参数表达的是调用策略，不是业务成功率。把 `maxRetries` 从 1 调到 10，可能提高短暂网络故障下的完成概率，也会增加等待时间、请求压力和故障恢复期间的资源占用。对用户交互请求，较短的超时和较少的重试可能比长时间等待更合理；对后台任务，则可以把重试交给队列或调度器，并在业务层记录最终失败。

如果应用已经在外层实现了重试循环，每一次应用层尝试都会包含运行时自己的重试。假设外层循环执行三次、stub 默认最多重试四次，最坏情况下的实际调用次数并不是三次，而是多个层级叠加后的结果。官方建议降低应用层尝试次数，或者对已经自行管理重试的 stub 设置 `maxRetries: 0`。这不是微优化，而是防止延迟和请求量失控的必要配置。

使用 `retryable()` 和 `retry` 选项前，还需要把 Wrangler 更新到 4.158.0 或更高版本。版本检查应纳入项目升级流程，而不是只在本地安装最新 CLI 后直接提交代码：部署环境、锁文件和 CI 中的 Wrangler 版本都应保持一致。

## 可复现的验收清单：验证“重试了什么”

这类功能不能只用一次成功请求验收，因为正常路径无法证明重试策略生效。可以按下面的顺序建立最小检查集：

1. **确认工具链版本。** 执行 `npx wrangler --version`，确认实际使用版本满足 `4.158.0` 或更高要求；同时检查 `package.json` 与锁文件，避免本地和 CI 使用不同版本。
2. **盘点调用入口。** 搜索 `getByName(`、`get(`、Durable Object stub 的 `fetch` 与 RPC 调用，列出每个入口的默认重试、局部重试和应用层重试，先找出叠加的地方。
3. **给方法分类。** 将方法分为只读、设置型写入、追加型写入和外部副作用四类。只有能证明重复执行安全的方法，才考虑 `retryable()`；追加型和外部副作用默认按不可重复处理。
4. **构造网络失败场景。** 在测试环境模拟调用建立阶段或返回阶段的短暂中断，观察调用是否在官方描述的重试范围内恢复。测试重点不是“最终返回成功”，而是记录目标对象收到请求的次数以及存储变化次数。
5. **验证未知结果。** 让目标对象完成一次写入后再制造响应链路中断，检查普通方法是否按预期避免重复执行；对显式标记为可重试的方法，则验证业务去重是否能把多次投递收敛为一次结果。
6. **验证上限与关闭策略。** 分别测试 `maxRetries: 0`、较小的 `maxRetries` 和自定义 `timeoutMs`，确认已经由应用层重试的调用不会同时承受两套循环。
7. **记录可观测字段。** 日志至少应包含请求 ID、对象名称、方法名、应用层尝试次数和业务结果。没有请求 ID，就很难区分运行时重试、客户端重试和用户重复点击。

测试结果应形成一张按调用入口维护的表，而不是只保留一条“接口返回 200”的记录。需要明确：故障注入发生在哪个阶段、目标对象执行了几次、存储最终状态是什么、调用方等待了多久，以及失败是否被正确暴露。

## 失败边界：哪些问题自动重试不了

第一类边界是业务异常。方法内部主动抛出的错误不会因为这项能力自动重试；这意味着参数校验失败、权限拒绝、状态冲突等错误不应被当成网络问题处理。若业务确实需要补偿，应由业务代码根据错误类型决定，而不是无差别再次调用。

第二类边界是过载保护。错误带有 `overloaded` 标记时不会触发运行时重试。这个设计避免在目标对象已经承压时继续放大流量。调用方应把过载视为容量或限流信号，采用退避、排队、降级或向用户返回可理解的失败，而不是把 `maxRetries` 调到最大。

第三类边界是外部一致性。Durable Object 的存储写入可以在对象内部组织，但外部支付、邮件、第三方 API 或消息系统不一定理解运行时的重试语义。只要一个方法包含不可回滚的外部副作用，就不能仅凭 `retryable()` 解决重复问题。

第四类边界是延迟预算。自动重试可能让原本快速失败的调用等待更久。对于页面请求、同步 RPC 和边缘链路，应该把 `timeoutMs`、上游超时和用户可接受等待时间放在同一张预算表里；不能让每一层都独立配置一个“看起来合理”的超时。

## 工程取舍：把重试放在离故障最近的地方

运行时重试的优点是统一、透明，并且能够处理应用代码难以准确识别的短暂连接故障；缺点是业务代码对重试次数和投递时机的直接控制减少了。应用层重试则可以结合订单状态、请求优先级和业务退避，但更容易出现重复循环、错误分类和实现不一致。

一个实用的分层方式是：让 Durable Objects 运行时负责短暂传输故障，让业务代码负责幂等、去重和状态机，让更长时间的失败交给队列或任务调度器。三层各自处理不同问题，不要把所有可靠性都压到同一个重试参数上。

最终验收标准也不应是“故障时一定成功”，而应是：可重试的短暂故障能够在预算内恢复；不可重试的业务错误能够快速暴露；重复投递不会破坏业务不变量；过载时不会形成重试风暴；外层重试与运行时重试的总次数可计算、可观测、可限制。

自动重试把网络的不确定性藏得更深，因此更需要显式建模。真正成熟的实现不是给每个方法加上 `retryable()`，而是先证明重复执行的后果，再选择运行时重试、业务去重或异步补偿。可靠性来自边界清晰的组合，而不是更大的重试次数。
