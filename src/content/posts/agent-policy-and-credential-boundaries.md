## 先看问题：Agent 不是只有一个“允许”开关

AI Agent 的安全边界经常被压缩成一个问题：这个工具能不能执行？但从工程角度看，至少存在两道不同的闸门。

第一道闸门决定“这次行为是否应当被允许”。它关注请求上下文、策略、实验开关、模型网关以及平台是否能够完成判断。第二道闸门决定“即使允许，凭什么身份执行”。它关注令牌的作用域、有效期、来源地址和具体策略块。

Claude Code v2.1.319 的发布说明提供了一个很典型的例子：当自动模式关闭遥测或功能标志，或者运行在 LLM Gateway 后面时，无法由服务器检查的调用会被询问或拒绝，不再回退到内置分类器；同时，Bedrock、Vertex 和 Foundry 有单独的行为说明。发布说明还增加了 `CLAUDE_CODE_AUTO_MODE_SERVER=0` 这一兼容控制，并说明在网关场景下可以用 `CLAUDE_CODE_AUTO_MODE_SERVER=1` 打开服务端检查。

Cloudflare 在同一天发布的更新处理的是另一层问题：用户 API Token 的创建界面被重新设计，加入更清晰的策略块编辑、过期时间预设和客户端 IP 过滤。它明确保留了用户作用域语义：令牌仍然代表创建它的用户，而不是因为界面更像 Account API Token 就自动获得账户级身份。

这两条官方材料的共同价值，不在于“又多了几个开关”，而在于它们把决策控制面和身份控制面分开了。Agent 运行时的策略判断不能替代凭据最小权限；一个限制完善的 Token，也不能替代对高风险工具调用的逐次判断。

## 第一层：把服务端策略检查看成决策平面

自动模式的关键不是“自动”两个字，而是决策在哪里完成，以及失败时是否会悄悄换一套逻辑。

可以把一次 Agent 工具调用抽象成四步：

1. Agent 生成工具调用意图；
2. 客户端或网关判断当前调用是否可交给服务端检查；
3. 服务端根据策略、遥测或功能标志返回允许、询问或拒绝；
4. 只有获得明确结论后，调用才进入执行阶段。

v2.1.319 的变化值得注意的是第三步失败时的语义。发布说明不是简单地说“服务端检查更快”，而是明确指出：服务器无法检查的调用会被询问或拒绝，并且不再回退到内置分类器。这里的工程含义是，策略检查不可达不应被当成普通网络抖动，更不能自动降级成一条未经组织治理的本地路径。

对于位于 LLM Gateway 后面的部署，还要额外检查两个环境变量的组合。一个是 `CLAUDE_CODE_AUTO_MODE_SERVER`，另一个是 `CLAUDE_CODE_DISABLE_EXPERIMENTAL_BETAS`。官方说明指出，设置前者为 `1` 可以在网关环境中启用服务端检查，即使设置了后者；如果托管设置强制关闭实验 Beta，也必须同时显式设置前者。这意味着配置不是单变量开关，而是一个有优先级和约束关系的策略矩阵。

可以先做静态配置检查：

```bash
printf 'server=%s\n' "${CLAUDE_CODE_AUTO_MODE_SERVER:-unset}"
printf 'disable_betas=%s\n' "${CLAUDE_CODE_DISABLE_EXPERIMENTAL_BETAS:-unset}"
```

这条命令不能证明服务端真的返回了正确决策，它只能确认运行时看到的环境。真正的验收至少需要覆盖三类输入：服务端可检查的调用、服务端不可检查的调用，以及位于 LLM Gateway 后且启用了托管设置的调用。验收结果应记录为“允许”“询问”或“拒绝”，而不是只记录进程是否退出。

## 第二层：MCP 任务的异步化不是权限放宽

同一版本还增加了终端中的 MCP tasks 支持：当 MCP 服务器把工具调用作为任务运行时，Claude Code 会立即将其移到后台，并在任务完成后把结果告知 Claude；同时提供 `CLAUDE_CODE_DISABLE_MCP_TASK_BACKGROUND`，用于让 Claude Code 在工具调用内部等待 MCP 任务完成。

这里容易产生一个错误推论：后台运行代表平台更信任任务。实际上，异步化改变的是时间模型，不是授权模型。

同步调用的控制流大致是“发起—等待—返回结果”；后台任务则变成“发起—得到任务状态—继续处理—接收完成结果”。后者会引入新的状态边界：任务已经提交但结果尚未到达时，Agent 是否允许继续调用其他工具？任务失败时，失败信息是否会回到同一个上下文？任务超时、重复提交和结果延迟是否会影响后续判断？仅凭“任务在后台运行”这个事实，无法回答这些问题。

因此，使用 MCP tasks 时应把任务 ID、发起时间、当前状态、最终结果和错误信息视为一组可审计数据。若某类操作必须在结果确认后才能继续，可以使用 `CLAUDE_CODE_DISABLE_MCP_TASK_BACKGROUND` 让调用保持等待语义；若任务适合长时间运行，则应在工作流层明确“提交成功”与“业务完成”不是同一个状态。

一个实用的验收清单是：

- 工具调用返回后，Agent 是否明确知道任务处于后台状态；
- MCP 任务完成后，结果是否回到原始会话，而不是只停留在服务器日志；
- 任务失败时，是否有可区分的失败信息，而非空结果；
- 关闭后台模式后，同一个任务是否恢复为调用内等待；
- 重复触发同一任务时，系统是否有幂等策略或人工确认点。

这些检查验证的是异步执行语义，不是权限。权限仍然需要由工具策略和执行身份共同约束。

## 第三层：Token 的限制必须落到凭据本身

Cloudflare 的用户 API Token 更新把另一个边界讲得很清楚。新的创建流程提供更一致的创建与审核界面，策略块可以直接添加、编辑和删除，过期预设与客户端 IP 过滤也被放进创建流程中。这样做的价值不是界面更漂亮，而是减少“创建完成后才发现限制没有配置”的遗漏。

令牌创建时至少应检查四个维度：

1. **身份语义**：确认这是用户作用域 Token，还是账户级 Token。界面相似不代表权限语义相同。
2. **策略范围**：逐块核对允许的资源和操作，避免用过宽的通配范围代替实际需求。
3. **时间边界**：为临时自动化设置明确过期时间，避免把一次性任务变成永久凭据。
4. **网络边界**：如果运行环境出口稳定，配置客户端 IP 过滤；如果出口会变化，则应先确认网络架构，否则可能得到“安全但不可用”的令牌。

创建后的检查也不能只看 Token 是否生成成功。应重新审阅策略块、过期时间和 IP 限制，并用一个最小权限请求验证“应该成功”的操作，再用一个超出范围的操作验证“应该失败”的边界。这里的失败不是异常，而是验收结果的一部分。

尤其需要保留 Cloudflare 更新中关于用户作用域的提醒：用户 API Token 仍代表创建它的用户。把它交给 Agent 后，Agent 获得的是这枚 Token 已有的身份能力，而不是一个抽象的“机器人身份”。因此，令牌持有人、令牌用途、运行环境和撤销责任都应被记录。

## 把两道闸门组合成一条验证链

一个可落地的 Agent 工作流，可以按下面顺序验证：

```text
意图生成
  -> 服务端策略检查
  -> 工具调用授权
  -> Token 权限校验
  -> 同步或后台执行
  -> 结果回传与审计
```

其中任何一步失败，都不应被包装成成功。服务端策略无法检查时，按官方发布说明应进入询问或拒绝路径；Token 权限不足时，应保留明确的授权失败；后台任务尚未完成时，应区分“已提交”和“已完成”。

部署或升级前，可以使用以下检查表：

- 记录 Claude Code 版本，并确认环境变量的实际值；
- 在没有网关、经过网关、以及托管设置生效三种条件下分别验证自动模式；
- 对 MCP 任务分别验证后台模式和等待模式；
- 为每个自动化任务建立独立 Token，而不是复用个人长期凭据；
- 记录 Token 的作用域、策略块、过期时间和客户端 IP 条件；
- 用允许和拒绝各一条的最小请求验证权限边界；
- 将任务提交、任务完成、Token 授权失败和服务端拒绝分开记录。

## 工程取舍：安全边界越多，不代表系统越简单

服务端检查会增加对网关、遥测和策略服务可达性的依赖。它的优点是组织可以集中治理，缺点是“检查不可用”会直接影响自动模式。后台任务可以改善交互体验，缺点是状态机更复杂，结果与后续操作可能发生时间错位。Token 的过期时间和 IP 过滤可以缩小泄漏后的影响面，缺点是轮换和网络变更会增加运维工作。

因此，正确目标不是把所有操作都改成拒绝，也不是让所有流程都自动放行，而是让每一种降级都有明确语义：策略服务不可达时停在哪里，任务未完成时哪些动作仍可继续，令牌失效时由谁轮换，权限拒绝时如何定位是策略问题还是身份问题。

## 结论：不要用一个控制面替代另一个控制面

Claude Code v2.1.319 展示的是 Agent 执行过程中的策略决策与异步状态管理；Cloudflare 用户 API Token 的新创建体验展示的是凭据自身的身份、范围和生命周期。两者共同说明：可靠的 Agent 系统至少要同时回答“这次调用能不能做”和“它凭什么身份去做”。

把服务端策略检查当成第一道闸门，把 Token 限制当成第二道闸门，再把后台任务的状态回传纳入验收，才能避免最常见的错觉：策略通过就等于安全，令牌有效就等于可治理，任务提交成功就等于业务完成。
