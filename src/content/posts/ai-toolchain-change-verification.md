## 为什么这两条 Release 值得放在一起看

AI 工具链的版本更新，往往同时发生在两个相距很远的层面：一端是面向开发者的 Agent 工作流，另一端是模型推理内核。前者决定工具调用、记忆、界面和会话是否连贯；后者决定注意力计算如何读取缓存、如何组织稀疏选择。它们看起来一个属于产品层，一个属于底层运行时，但共同指向同一个工程问题：一次局部变更，究竟会不会破坏原有的状态边界。

材料中的两个版本都不是稳定版。Qwen Code 发布的是 `v0.26.3-preview.0`，GitHub 明确标为 Pre-release；llama.cpp 的 `b11936` 同样标为 Pre-release。因此，本文把它们作为官方预发布变更样本，而不是“已经成熟可升级”的结论。能从 Release 页面确认的是变更描述和版本身份，不能仅凭标题确认性能提升、兼容性或生产稳定性。

Qwen Code 的变更集中在 Agent 的状态和工具链：记忆提取改为在一次无操作运行后按选择启用的节奏执行；核心层修复带引号调用内容的外层 XML 调用恢复；工具结果会根据自动压缩前剩余的上下文空间进行收缩；ACP 守护进程客户端传递 rewind identity；web-shell 在同页导航中保留 Generated UI 实例。llama.cpp 的变更则指出，稀疏选择不再依赖 `kq_mask` 的形状，缓存单元按索引选择，并在进入注意力计算前再拆分为 K 视图的流。

这两组描述的共同价值，不是“功能更多”，而是把原本耦合在一起的状态或布局拆开：工具结果与上下文预算分离，稀疏选择与 dense mask 布局分离。拆耦合通常能扩大兼容范围，但也会把验证责任从一个简单路径扩散到多个边界。

## Qwen Code：从工具调用恢复到上下文预算

先看工具调用。Release 提到，核心层修复了“带引号的调用内容”导致的外层 XML 调用恢复问题。这里可以抽象出一条解析链：模型或工具层产生带结构标记的调用内容，外层负责恢复调用，再把内容交给执行器。只要调用内容中的引号改变了解析边界，恢复器就可能把完整调用误判为截断、嵌套或无效内容。

工程上不能只验证普通参数。至少要覆盖三类输入：不含引号的简单调用、包含单引号和双引号的字符串、引号与 XML 特殊字符同时出现的内容。验证目标也不应只是“命令被执行”，还要检查调用名、参数原文、错误位置和重试次数是否保持一致。若系统存在自动修复或重试，修复成功但多执行一次同样属于失败，因为 Agent 工具调用可能具有副作用。

另一个核心变更是工具结果收缩。Release 的表述是：根据自动压缩前剩余的 headroom 缩小工具结果。这里的关键不是简单截断字符串，而是把工具输出纳入上下文预算管理。工具结果过长时，系统需要在“保留足够信息”和“为后续推理留下空间”之间做取舍。

可复现的检查可以从版本和差异开始：

```bash
git clone https://github.com/QwenLM/qwen-code.git
cd qwen-code
git fetch --tags origin
git show --stat v0.26.3-preview.0
git diff v0.26.2..v0.26.3-preview.0 --stat
git log --oneline v0.26.2..v0.26.3-preview.0
```

这些命令只能确认标签、提交范围和变更规模，不能替代行为测试。行为验证应记录至少四个量：原始工具结果长度、压缩后的长度、压缩前剩余上下文空间、下一轮模型调用是否成功。测试数据还要包含短结果、接近预算的结果和明显超过预算的结果。特别要检查压缩是否破坏 JSON、XML、代码块或错误堆栈的关键边界。

Qwen Code 的记忆提取变更也属于状态机问题。Release 使用了“opt-in extraction cadence after a no-op run”的描述，至少可以确认它与无操作运行和选择启用有关，但材料没有给出默认配置名称、存储格式或触发周期。因此，工程验证应避免猜测配置项，而是围绕可观察行为设计：一次无操作运行是否产生记忆候选；未选择启用时是否保持不提取；选择启用后是否只在约定节奏触发；重复运行是否产生重复记忆。

web-shell 保留 Generated UI 实例，以及 ACP 守护进程客户端传递 rewind identity，则共同说明“导航”和“回退”不只是界面操作。前者需要验证同页导航前后实例身份、状态和事件监听是否延续；后者需要验证回退到某个身份后，客户端、守护进程和会话状态是否仍然指向同一条历史。不能因为页面仍显示内容，就断定实例没有被重新创建。

## llama.cpp：把稀疏选择从 mask 布局中解耦

llama.cpp 的 `b11936` 描述了更底层的结构调整。对于 `qwen4exp (QSA)` 和 `glm5-next`，QSA 可以理解为一种需要按缓存单元索引进行选择的稀疏注意力路径。Release 指出，这些路径不再读取 `kq_mask` 的值，却仍然让选择形状服从 dense mask；新实现把选择构造成 `[n_kv, n_tokens]`，表示缓存单元与当前 token 的关系，然后在进入注意力计算前，再拆分为 K view 的流。

这个变化的核心是“选择语义”和“布局语义”分离。旧的耦合方式要求稀疏层理解 dense mask 的形状；一旦 dense mask 改成按序列排列的行列表，稀疏层就必须同步修改。新的边界把稀疏层关心的对象限定为缓存单元索引，把具体视图拆分推迟到注意力入口。这样做的潜在收益是减少布局变化对稀疏层的影响，但它并不自动证明计算结果、内存访问或性能一定更好。

可以先固定版本并检查提交说明：

```bash
git clone https://github.com/ggml-org/llama.cpp.git
cd llama.cpp
git fetch --tags origin
git show --stat b11936
git show --format=fuller --no-ext-diff b11936 --
git log --oneline -n 5 b11936
```

如果仓库提供针对相关模型和后端的测试，应在同一硬件、同一编译选项、同一输入下比较变更前后的结果。最低验证矩阵包括：单序列与多序列、短上下文与长上下文、dense mask 布局与稀疏选择路径、不同 batch 或 token 数量。输出层面要比较 token 序列、停止原因和错误日志；运行层面要记录峰值内存、首 token 延迟、持续生成速度以及是否出现越界或非法索引。

最容易被忽略的是形状检查。新描述明确给出 `[n_kv, n_tokens]`，因此测试不能只用方阵输入。应覆盖 `n_kv` 大于、等于、小于 `n_tokens` 的情况，并覆盖空选择、全选择和重复索引。若某个后端把维度顺序误读为 `[n_tokens, n_kv]`，小规模方阵可能仍然通过，只有非方阵用例才能暴露问题。

## 一套不依赖“感觉可用”的升级流程

第一步是确认版本身份。记录仓库地址、标签、提交哈希、是否为预发布，并把 Release 页面中的事实与自己的推断分开。预发布版本可以用于定位问题或验证新架构，但不能直接等价于稳定升级建议。

第二步是建立变更假设。Qwen Code 的假设包括：带引号调用能够恢复且不重复执行；工具结果收缩受上下文 headroom 约束；同页导航不会意外丢失 Generated UI 实例；rewind identity 能穿过 ACP 守护进程边界。llama.cpp 的假设包括：稀疏选择不依赖 dense mask 的具体布局；非方阵和多序列输入仍能正确映射缓存单元；拆分 K view 不改变可观察输出。

第三步是设计失败注入。不要只跑成功样例：给工具调用加入引号和特殊字符；把工具输出扩大到预算边界；在同页导航期间触发 UI 状态变化；让回退发生在守护进程仍有未完成状态时；为稀疏选择提供空索引、重复索引和非方阵尺寸。失败注入的目标不是证明版本“很脆弱”，而是确认错误是否可定位、是否会静默产生错误结果。

第四步是保存可比较证据。每次测试至少保留版本信息、输入摘要、配置、输出摘要、错误日志和资源指标。对于上下文压缩，保存压缩前后的结构校验结果；对于工具调用，保存调用次数和副作用记录；对于注意力路径，保存维度、索引数量和最终 token 输出。没有这些证据，所谓“升级后正常”通常只是一段不可复查的主观判断。

## 工程取舍：解耦不是免费收益

解耦带来的第一项成本是适配层增多。Qwen Code 把工具结果压缩放进上下文预算后，执行器、压缩器和模型调用之间需要共享更明确的预算语义；llama.cpp 把选择和布局分离后，索引构造、视图拆分和后端实现之间需要严格约定维度。

第二项成本是回归测试从单路径变成组合矩阵。工具调用格式、上下文剩余空间、会话导航和回退身份可以组合；注意力路径的序列数、token 数、缓存大小和后端也可以组合。工程上不可能穷举所有组合，因此应优先覆盖边界形状、状态切换和有副作用的路径，而不是只追求测试数量。

第三项成本是性能结论不能从结构描述直接推出。稀疏选择可能减少不必要的布局耦合，但实际收益仍取决于索引构造、缓存访问和后端实现；工具结果收缩可能为后续推理留下更多空间，但也可能丢失调试上下文。任何性能或质量结论，都应绑定输入、硬件、编译选项和版本。

## 结论：把 Release 当作假设清单

这两个预发布版本给出的启示，不是“看到新版本就升级”，而是：高质量的 AI 工具链需要把状态、预算、索引和布局都变成可观察、可验证的边界。Qwen Code 的变更提醒我们，Agent 的可靠性不仅在于模型是否调用工具，还在于调用内容、上下文预算和会话身份是否跨层保持一致。llama.cpp 的变更则说明，推理内核的可维护性来自把稀疏语义与具体张量布局拆开。

因此，Release Notes 最适合作为测试假设的入口，而不是验收报告。先确认标签，再提取变更，再为每个变更写出正常路径、边界输入和失败注入，最后用可比较的输出与资源证据收口。对于明确标为 Preview 或 Pre-release 的版本，最稳妥的结论应当是“值得验证的架构变化”，而不是“已经可以无条件采用”。
