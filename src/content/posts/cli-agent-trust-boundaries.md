## 先区分两种“能运行”

CLI Agent 的安全边界，往往不是在模型回答错误时才出现。更常见的情况是：工具确实启动了，命令也确实执行了，但用户并不知道哪些行为来自当前目录，哪些行为来自托管配置，哪些状态来自远程服务。此时“能运行”并不等于“可接受”。

Claude Code v2.1.329 的官方发布说明集中增加了几类与信任和可见性有关的能力：当项目目录声明 hooks 时显示信任对话框；当托管设置中的 hooks 无法加载时，在会话、Claude Desktop 及其他非交互宿主中发出警告；在 `/tasks` 中展示当前会话的定时任务、循环唤醒、目标和会话分叉；在 `/mcp` 的服务器页面显示拒绝连接的远程 HTTP MCP 服务器返回的 JSON-RPC 错误；在 `/status` 中说明哪些托管 marketplace 不会自动更新以及原因。

这些变化的共同点不是“再增加几个命令”，而是把原本隐藏在执行链里的状态变成用户可审计的状态。工程上，这比单纯增加一个新模型或一个新工具更值得关注。

## Hooks：目录不是无害的上下文

Agent 通常需要读取项目文件、运行检查、调用外部工具。hooks 会把这些行为进一步自动化：某个目录可以声明在特定阶段触发的脚本或处理逻辑。问题在于，用户打开一个陌生目录时，目录本身就可能携带影响 Agent 行为的配置。

因此，信任判断至少要回答三个问题：

1. hooks 是在哪个目录声明的？
2. 它们由谁维护，是否随仓库一起进入工作区？
3. 当前宿主是否真的加载了这些 hooks？

v2.1.329 新增的信任对话框，明确提示 hooks 声明所在的位置。这个设计把“脚本存在”提升为“用户需要作出判断的事实”。它没有替用户决定目录可信，也没有把 hooks 静默视为普通项目配置，而是让来源出现在授权时刻。

这类提示的价值在于缩小误判范围。用户不一定能立刻理解每个 hook 的代码，但至少可以知道审查对象在哪里。对于团队仓库，建议把 hooks 当成代码审查范围的一部分，而不是只审查应用源代码。拉取请求检查清单可以加入：hooks 是否新增、触发时机是否变化、是否访问网络或凭据、失败时是否阻断任务。

边界也很明显：提示只解决“用户是否看到来源”，不等于脚本本身安全。一个来源明确的 hook 仍可能执行高风险操作。因此信任对话框应被视为授权前置条件，而不是安全扫描器。

## 托管设置失败：静默降级比显式失败更危险

另一项变化针对 managed settings 中 hooks 加载失败的情况。官方说明强调，警告会出现在会话、Claude Desktop 和其他非交互宿主中。

这里有一个容易被忽略的工程问题：配置失败可能产生两种完全不同的结果。

第一种是显式失败。系统告诉用户某项配置没有加载，用户知道当前环境与预期不同，可以暂停、修复或切换策略。第二种是静默降级。系统继续工作，但用户误以为组织级 hooks、审计逻辑或安全限制仍然生效。

第二种情况通常更危险，因为它制造了“策略已经存在”的错觉。比如团队以为某个 hook 会在执行前做检查，实际却因为托管设置加载失败而没有运行。Agent 随后完成任务，界面也没有明显报错，审计记录却缺失。

验收时不要只检查配置文件是否存在，而应检查三层状态：

```text
配置文件存在
→ 配置被宿主加载
→ 预期 hook 在目标宿主中实际触发
```

对于交互式 CLI、桌面应用和非交互宿主，这三层不能互相替代。发布说明特意列出多个宿主，说明同一配置路径在不同运行入口下可能有不同的失败表现。工程上应为每个宿主保留最小验证用例：使用无副作用的测试 hook，记录触发时间、输入摘要和退出状态，然后确认失败时是否能在界面或日志中被发现。

不要用“任务最后成功”作为配置加载成功的证据。任务成功只能证明最终结果出现，不能证明中间的治理策略执行过。

## `/tasks`：后台工作首先是状态问题

定时任务、循环唤醒、目标和会话分叉都属于容易被用户遗忘的状态。它们不一定正在执行，但会影响下一次 Agent 行为。把这些内容加入 `/tasks`，意味着任务管理从“我记得自己启动过什么”转向“系统给出当前可见清单”。

可以把 Agent 的工作拆成四个状态：

- 已声明：用户或会话创建了任务。
- 已调度：任务具备下一次唤醒或执行条件。
- 执行中：宿主正在处理任务。
- 已终止或失效：任务不再会继续产生动作。

如果界面只显示执行中任务，用户很容易忽略已调度但尚未运行的工作；如果只显示任务名称，又无法判断它属于当前会话、循环机制还是会话分叉。发布说明将这些对象放在同一处，解决的是发现问题，而不是自动替用户做生命周期决策。

实际检查可以从一个干净会话开始：

```text
1. 启动 CLI Agent，确认初始 /tasks 清单。
2. 创建一个最短周期、无副作用的定时任务。
3. 再创建一个循环唤醒或会话分叉。
4. 重新查看 /tasks，记录每项的归属和状态。
5. 终止会话后再次查看，确认哪些状态仍然存在。
```

这里的关键不是验证某个具体时间间隔，而是确认“创建了什么、由谁拥有、什么时候还会发生”。生产环境中，后台任务还应配套幂等键、最大执行次数和明确的撤销路径。若产品只提供可见清单，却没有可靠的取消或失效语义，清单只能降低遗忘风险，不能替代任务治理。

## `/mcp`：连接失败是协议事实，不是模糊提示

远程 HTTP MCP 服务器拒绝连接时，新增的 server message 行会显示 JSON-RPC 错误消息。这是一个重要的诊断粒度变化。

“连接失败”至少可能代表网络不可达、认证失败、协议协商失败、服务主动拒绝，或者服务端处理请求时返回错误。若界面只显示一个统一错误，用户通常会重复重试，甚至错误地修改本地网络配置。JSON-RPC 错误消息虽然不能自动修复问题，却能把排查入口从猜测变成证据。

建议将 MCP 验收分为四步：

```text
连通性：客户端是否能够到达远程 HTTP 端点？
身份：服务端是否接受当前认证信息？
协议：双方是否完成预期的 JSON-RPC 交互？
能力：连接成功后，工具列表和调用结果是否符合约定？
```

每一步都应保留不同的失败证据。连通性失败不能归因于工具实现；认证失败不能通过不断重试解决；协议错误需要检查客户端和服务端版本或消息结构；能力不匹配则属于契约问题。

这里也存在安全边界：错误消息适合用于诊断，但不应把访问令牌、完整请求头或敏感上下文直接展示给普通用户。可见性提升必须与脱敏策略同时设计。一个详细但泄露凭据的错误面板，并不是更好的可观测性。

## `/status`：自动更新需要解释“为什么没有更新”

发布说明还增加了 `/status` 中关于 marketplace 自动更新的行，说明哪些托管 marketplace 不会自动更新以及原因。

版本治理最容易犯的错误，是只记录“当前版本号”。版本号告诉我们结果，却不告诉我们路径：它是自动更新得到的、管理员固定的、策略禁止的，还是因为网络或权限问题没有更新。对于 Agent 的扩展市场，这些路径会直接影响工具行为和安全修复是否及时生效。

一个可用的状态检查至少要回答：

- 当前扩展或 marketplace 的版本是什么？
- 它是否允许自动更新？
- 如果不允许，阻断原因是什么？
- 当前状态由用户设置、托管策略还是运行时错误造成？
- 变更后如何证明新版本已经加载？

这也是为什么“显示版本号”不够。真正可审计的状态应同时包含版本、更新策略和阻断原因。对于团队环境，管理员还应把固定版本当作有意的变更控制，而不是把未更新简单标记为异常。

## 预发布版本不能用同一把尺子验收

同一批公开材料里，OpenAI Codex 的 `0.173.0-alpha.1` 被标为 Pre-release，页面显示该版本包含 23 次主分支提交并提供 196 个资产。这个证据只能说明一个预发布构建已经公开，不能推出它适合生产，也不能据此推断具体功能稳定。

因此，稳定版本和 alpha 版本的验收标准必须分开：稳定版本重点检查兼容性、回归和升级路径；预发布版本还必须检查变更范围、资产是否匹配平台、失败是否可回退，以及是否存在明确的试验环境隔离。发布页上的标签、提交数量和资产数量是发布证据，不是质量结论。

这条原则同样适用于 Agent 的 hooks、MCP 和后台任务：看到功能入口，不代表它已经覆盖所有宿主；看到错误消息，不代表错误已经被正确处理；看到版本更新，不代表托管策略已经生效。

## 一套最小验收清单

将上述边界压缩成一次发布后的检查，可以使用下面的顺序：

```text
[ ] 打开陌生项目时，能看到 hooks 的声明来源
[ ] hooks 加载失败时，交互式和非交互式宿主都会留下警告
[ ] /tasks 能列出当前会话相关的调度、循环和分叉状态
[ ] 任务终止后，状态不会制造虚假的继续执行暗示
[ ] /mcp 能区分网络、认证、协议和远程拒绝
[ ] JSON-RPC 错误可诊断，但不会泄露敏感信息
[ ] /status 能解释托管 marketplace 未自动更新的原因
[ ] 预发布版本与稳定版本使用不同的上线门槛
```

这份清单的核心不是多测几个命令，而是检查系统有没有把“隐藏状态”变成“可解释状态”。

## 原创结论：Agent 的下一条安全边界是可解释的状态机

CLI Agent 的安全问题，不能只靠权限列表解决。权限回答“允许做什么”，但 hooks、MCP、后台任务和自动更新还涉及“谁声明了什么、何时生效、失败后变成什么状态”。如果这些状态不可见，用户就会把默认行为误认为治理行为。

因此，Agent 工程的关键指标不应只是工具调用成功率，还应包括：配置加载可见性、后台任务可发现性、远程错误可诊断性和版本策略可解释性。一个成熟的 Agent 不一定永远成功，但必须让失败、未加载、待执行和未更新这些状态被准确发现。

从这个角度看，CLI 的 `/tasks`、`/mcp`、`/status` 与 hooks 信任提示并不是零散功能。它们共同构成一层状态机界面：把自动化系统中原本不可见的转移暴露出来，让用户能够判断下一步是继续执行、暂停审查、修复配置，还是回滚版本。对 Agent 来说，这种可解释性不是附加体验，而是从“会调用工具”走向“可被工程治理”的必要条件。
