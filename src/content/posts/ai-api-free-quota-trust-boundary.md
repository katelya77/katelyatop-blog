## 先把“免费”拆成三种完全不同的承诺

在 AI API 社区里，“免费”不是一个技术属性，而是一组商业和信任条件的简写。至少要区分三类情况：平台赠送调用额度、平台允许使用免费后缀模型、以及第三方中转站提供的低价或免费访问。

S1 的帖子声称注册后可领取 5000 万 Token，并列出多个带 Free 后缀的模型，同时提醒可能存在每分钟请求限制，服务也可能随时停止。S2 则声称每月提供 1 亿 Token、持续一年，并支持多个模型，但同样给出了 Rate limit exceeded 和 Billing verification failed 等失败情况。两条材料都只能证明社区中出现了相应的额度宣传，不能证明额度一定到账、模型一定可用，也不能证明服务具有稳定的 SLA。

第三类风险更高：用户先把钱交给一个中转站，再由中转站代为访问模型服务。S5 记录了一起宣传后跑路的案例，并提到单个用户损失 130 元；S8 也记录了“刚充值完，中转就当天跑路”的情况。这里的关键变化是：免费额度失败时，通常损失的是时间、注册信息或未使用额度；充值中转失败时，损失直接变成不可逆的资金，而且用户往往无法验证上游账户、余额和真实成本。

因此，不能把“免费额度”和“中转充值”放在同一张价格表里比较。前者主要是可用性问题，后者是托管资金和第三方履约问题。

## 真正的架构：你买到的不是模型，而是一条代理链

一次看似简单的 API 调用，至少可能经过四个边界：客户端、第三方网关、上游模型平台，以及负责身份和计费的账户系统。用户发送的请求内容、模型名称、Token 用量、错误信息和返回结果，都可能在网关处被记录或处理。中转站为了兼容不同模型，通常还要做协议转换、限流、重试、余额扣减和密钥管理。

这意味着“接口兼容”不能推出“服务可信”。一个网关可以返回 OpenAI 风格的 JSON，却仍然无法向用户证明以下问题：

- 请求是否真的转发到了帖子宣称的模型；
- 账单中的 Token 是否由上游真实产生；
- 余额扣减是否有可审计的流水；
- 网关是否保存提示词、响应和密钥；
- 上游账户被封禁或额度耗尽时，谁承担损失；
- 服务停止后，未消费余额是否可以取回。

免费额度服务也存在类似链路，只是资金风险可能被额度赠送掩盖。S1 的提示已经说明每分钟请求限制和随时停止的可能性；S2 的错误示例则表明“宣称支持某模型”与“当前能够稳定调用”之间存在差距。对工程使用者来说，最重要的不是帖子的额度数字，而是失败时是否有明确、可验证的状态转换：额度是否扣除、请求是否重试、错误是否可区分、剩余余额能否导出。

可以把第三方 AI 服务抽象成一个状态机：注册成功不等于认证成功，认证成功不等于额度到账，额度到账不等于模型可用，模型可用不等于高峰期可用，调用成功也不等于账单可信。每个状态都应当有独立证据，而不是用一次成功响应覆盖全部风险。

## 一套不依赖宣传文案的核验流程

### 1. 先核验身份，再核验价格

不要从“每月多少 Token”开始。先记录服务主体、域名、运营方公开联系方式、条款页面、退款规则和密钥处理说明。若只存在一个群聊、一个收款码和一张额度截图，应把它视为低证据等级的社区线索，而不是正式服务说明。

S5 中社区提出对非认证商家和非公益免费中转站收取押金，并在跑路时作为先行赔偿款。这说明社区治理正在试图把“口头信任”转换成“可追索的担保机制”。但押金制度只能降低部分交易风险，不能证明上游模型授权、数据处理方式或技术稳定性。它解决的是“跑了以后谁先赔”的问题，不解决“运行时谁能看到请求”的问题。

### 2. 用最小请求确认真实能力

注册后不要立即导入生产密钥，也不要把真实业务提示词发给陌生网关。使用不包含个人信息和商业秘密的测试文本，逐项确认：模型名是否被原样返回、上下文长度是否符合说明、流式响应是否稳定、错误码是否可区分、请求 ID 和用量信息是否存在。

可以使用类似下面的最小化检查命令。变量只放在本地环境中，不要把密钥写进 Shell 历史、仓库或截图：

```bash
export AI_BASE_URL='https://example.invalid/v1'
export AI_API_KEY='只在本地临时设置'

curl --fail-with-body --silent --show-error \\
  "$AI_BASE_URL/models" \\
  -H "Authorization: Bearer $AI_API_KEY" \\
  -o /tmp/models.json

curl --fail-with-body --silent --show-error \\
  "$AI_BASE_URL/chat/completions" \\
  -H 'Content-Type: application/json' \\
  -H "Authorization: Bearer $AI_API_KEY" \\
  --data '{
    "model": "服务方明确列出的模型名",
    "messages": [{"role": "user", "content": "只返回 OK"}],
    "max_tokens": 8,
    "temperature": 0
  }' \\
  -o /tmp/response.json

jq '{id, model, usage, error}' /tmp/response.json
```

这段命令不能证明服务长期可靠，只能建立一份初始证据：接口是否可达、返回模型是否一致、是否存在 usage 字段、失败时是否返回结构化错误。若服务声称支持免费模型，却要求绑定付款方式，或者模型列表和宣传名称不一致，应暂停继续测试。

### 3. 给额度和余额建立本地账本

每次测试至少记录时间、请求模型、输入输出 Token、HTTP 状态码、响应中的 usage、平台显示的剩余额度和实际扣减值。不要只截图一次余额，因为截图无法解释并发请求、重试和延迟扣费。

可以用 CSV 保存最小账本：

```text
time,model,http_status,input_tokens,output_tokens,reported_balance,error
2026-09-10T12:00:00+08:00,free-model,200,18,2,49999980,
```

如果平台没有用量明细，或者账面余额只显示一个无法导出的数字，就不能把它当作可审计的配额。S2 提到可以查看用量明细，这类功能的价值不在于界面更漂亮，而在于用户能把“承诺额度”与“实际扣减”进行比对。

## 哪些失败边界必须提前写进工程方案

第一类是限流。S1 已明确提示可能存在每分钟请求限制，S2 也出现 Rate limit exceeded。应用不应把所有 429 都无限重试，否则会放大拥塞、重复扣费或触发更严格的封禁。应设置有限次数、指数退避和总等待上限，并把“免费额度耗尽”“瞬时限流”“账户验证失败”分开处理。

第二类是认证和支付校验。Billing verification failed 不一定表示代码错误，也不能简单通过更换密钥解决。它可能是账户状态、付款验证或平台风控问题。工程上应把认证失败当作不可自动恢复的状态，暂停任务并保留原始错误，避免 Agent 或后台队列不断重复请求。

第三类是服务突然停止。社区材料多次提醒免费服务可能停止，S5 和 S8 则展示了中转跑路后的资金损失。因此生产系统不能把免费网关当作唯一上游。至少应支持切换到已知的备用端点，缓存不含敏感数据的中间结果，并设置单个供应商的预算、并发和每日请求上限。

第四类是数据边界。即使没有证据证明某个具体服务一定会保存提示词，也不能反过来假设它不会保存。没有清晰数据处理说明的第三方网关，只适合处理经过脱敏、降级和最小化后的请求。涉及个人资料、源代码、访问令牌、客户数据的请求，应直接排除在测试范围之外。

## 平台治理能解决什么，不能解决什么

S11 是 App Store 上的官方应用页面，页面列出了 NodeLoc 的社区、搜索、消息、通知、举报和屏蔽功能，也显示开发者声明的隐私数据类别；同时页面明确提示隐私信息未经过 Apple 验证。这个材料提供了一个重要的治理边界：平台可以提供举报、屏蔽和审核流程，也可以展示开发者提交的隐私声明，但平台展示不等于对所有运营承诺进行技术审计。

把这个边界映射到 AI API 社区，可以得到两个结论。第一，社区认证、押金、举报和先行赔付，主要解决发现问题后的追责与止损；第二，真正的技术信任仍然需要调用日志、账单流水、数据处理说明、密钥隔离和可迁移性来支撑。没有任何一个徽章或帖子热度能够替代这些证据。

## 原创结论：把“便宜”改写成可撤销的实验

AI API 福利最合理的工程用法，不是把它当作生产依赖，而是把它当作有预算、有边界、可撤销的实验资源。预算可以是零，也可以是一个明确的极小金额；边界包括测试模型、脱敏输入、限流策略和禁止上传的数据类型；可撤销则意味着随时可以删除密钥、停止任务、切换供应商，并且不会因为预充值而被锁死。

判断一个服务是否值得继续使用，可以采用三条门槛：没有可验证的额度或余额记录，不进入自动化流水线；没有明确的数据处理边界，不处理敏感输入；没有退出和退款路径，不进行大额充值。即使某个免费服务真的提供了很高的额度，也只能提高实验价值，不能自动提高信任等级。

社区帖子适合发现线索，官方文档和可重复的调用记录适合建立证据，账单与退出机制才决定它能否进入工程系统。把这三者分开，才能避免用一张“免费额度”海报，替代对身份、数据、计费和故障责任的完整判断。
