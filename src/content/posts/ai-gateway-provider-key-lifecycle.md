## 先区分两个问题：密钥可用，不等于密钥仍然合理

在 AI 网关中，Provider Key 通常处在应用与模型供应商之间。应用把请求交给网关，网关再使用已经保存的供应商凭据完成调用。只要请求还能成功，传统监控就很容易给出一个过于乐观的结论：密钥健康、系统正常、无需处理。

但“可用”只回答了连通性问题，没有回答密钥是否仍被业务需要，也没有回答它是否已经超出组织的保留周期。一个长期没有调用记录的密钥，可能是废弃环境遗留物，也可能仍被某条低频任务、应急脚本或夜间批处理依赖。两者在网络请求层面都表现为“暂时没有错误”，在治理层面却完全不同。

Cloudflare 在 2026 年 11 月 6 日公布的 AI Gateway 更新，把 Provider Key 页面从静态凭据清单推进到活动审查界面：密钥按供应商分组，展示掩码预览、别名、最近使用时间和最近更新时间；Key security 区域会突出显示已有活动记录且超过 90 天的密钥。官方说明还指出，使用追踪从 2026 年 11 月开始。这意味着新数据并不是对历史所有调用的完整回放，而是一个有明确起算点的运营信号。

这类变化的价值不在于多了一个日期字段，而在于它把密钥生命周期拆成了三个可验证问题：它是什么、最近是否被使用、删除或轮换之后谁会受到影响。

## 活动记录实际上是一种轻量级依赖图

密钥列表通常只描述对象本身：供应商、别名、掩码、创建或更新时间。活动记录则增加了时间维度，但它仍然不是完整的调用链。仅凭“最近使用时间为空”不能推导出“绝对没有依赖”，因为追踪可能刚启用，或者相关任务尚未运行。

因此，Provider Key 活动应该被看作依赖图的一个观测点，而不是依赖图本身。

可以把一次调用抽象为：

```text
业务任务 -> AI 网关路由 -> 供应商分组 -> Provider Key -> 供应商 API
```

其中，活动时间只能证明某条路径在某个时间窗口内被观测到。它不能单独证明所有路径都已被覆盖，也不能证明某个低频任务不会在下周再次使用该密钥。工程上更稳妥的做法，是把活动记录与配置、任务调度、部署清单和变更记录交叉验证。

例如，一个“超过 90 天未活动”的密钥至少需要经过以下判断：

1. 90 天是从什么时候开始计算的；
2. 最近使用时间是否来自真实调用，而不是更新时间；
3. 是否存在未运行的定时任务、灾备流程或人工应急脚本；
4. 是否有其他密钥已经接替它，但旧配置尚未清理；
5. 删除后是否能够恢复，恢复动作由谁负责。

这也是为什么活动记录更适合作为候选筛选器，而不是自动删除条件。它降低了人工盘点范围，却不能替代依赖确认。

## 90 天阈值应当触发审查，而不是触发删除

官方更新将“已有活动且活动时间超过 90 天”的密钥放入安全审查区域。这个阈值适合被理解为一个治理信号：它告诉运营人员哪些凭据值得优先检查，而不是宣告这些凭据已经无效。

在不同系统中，90 天可能对应不同风险。一个每天运行的摘要任务，超过 90 天没有活动，通常值得高度怀疑；一个季度运行的财务报表任务，90 天可能恰好落在正常周期边界；一个灾备密钥可能平时永远没有调用，但它的价值正是留在故障场景中。

因此可以采用分层处理：

- **高频业务密钥**：未活动超过一个业务周期后进入复核，超过 90 天优先轮换或停用。
- **低频任务密钥**：把调度周期纳入判断，不能直接使用通用阈值。
- **灾备或应急密钥**：保留明确的责任人、用途和演练记录，不能因为平时没有活动就删除。
- **未知用途密钥**：先标记为待认领，冻结新增使用，再进行依赖查找。

这里的关键不是把 90 天改成 30 天或 180 天，而是让阈值与业务频率、恢复目标和责任归属发生关系。没有这些上下文，阈值只是一个漂亮的数字。

## 一套可复现的审查清单

即使供应商提供了管理界面，团队也应该把审查过程固定成可重复的记录，而不是依赖某个人浏览页面后的记忆。可以使用下面的最小字段集维护内部台账：

```text
provider
key_alias
masked_preview
last_used_at
last_updated_at
tracking_start_at
owner
known_dependencies
risk_class
decision
next_review_at
```

其中 `tracking_start_at` 特别重要。Cloudflare 的说明明确表示，使用追踪从 2026 年 11 月开始。对于早于该时间的历史密钥，空白活动信息不能被解释成“从未使用”。

如果团队把页面信息导出为 JSON，可以先用一个只读检查筛选审查对象：

```bash
jq '
  .keys[]
  | select(.last_used_at != null)
  | select((.last_used_at | fromdateiso8601) < (now - 90*24*60*60))
  | {provider, key_alias, last_used_at, last_updated_at}
' provider-keys.json
```

这段命令只是本地台账的示例，不应被当作 Cloudflare API 的接口承诺。它的工程意义在于：筛选、人工确认和执行删除必须分成不同步骤，不能把查询结果直接管道传给破坏性命令。

删除前至少应完成一次反向搜索：在部署配置、CI 变量、定时任务、脚本和应急文档中查找别名、供应商和密钥引用。密钥值本身不应写入搜索日志，也不应为了确认依赖而打印完整凭据。能够公开记录的应是别名、掩码预览和责任人，而不是秘密材料。

## 轮换与删除是两个不同的操作

轮换的目标是替换秘密，同时尽量保持服务连续；删除的目标是移除不再需要的对象。两者不能混为一谈。

更安全的轮换流程通常是：先创建或保存新密钥，更新网关配置，执行一组代表性调用，观察错误和活动记录，再撤销旧密钥。旧密钥在观察窗口内保留，并且必须有明确的最晚撤销时间。这样做的代价是短时间内存在两把有效密钥，但换来了回滚能力。

删除流程则应从“确认不再需要”开始，而不是从“活动时间很久”开始。删除前记录当前别名、供应商、最后活动时间、依赖确认人和回滚方式；删除后检查应用错误、网关调用状态和相关任务结果。对于关键路径，还应安排一次受控恢复演练，确认团队知道如何重新配置供应商凭据。

Provider Key 页面提供掩码预览、别名、最近使用和最近更新时间，这些信息足以支持审查排序，却不等于完整的审计日志。它们不能回答每一次调用来自哪个用户、哪条业务请求或哪次部署。若业务需要逐请求归因，还应在应用或网关侧维护不包含秘密值的请求标识、服务身份和变更记录。

## 隐私与后量子讨论都指向同一个工程结论

Cloudflare 的另一篇官方文章把讨论延伸到后量子时代的 Web 隐私。材料本身不足以支持对具体算法、协议或性能的进一步断言，但它至少提醒我们：密码学风险会随着时间和威胁模型变化，不能把“今天没有泄漏”当作长期安全证明。

对 AI 网关而言，这个结论并不要求立即引入复杂密码学方案，而是要求把凭据当作有生命周期的对象管理。密钥的供应商、用途、责任人、最近活动和轮换窗口都应可见；没有活动追踪或追踪刚启用时，应明确标记证据缺口；自动化可以筛选候选对象，却不应在缺少依赖信息时擅自删除。

这也解释了为什么“密钥安全”不应只靠一次性扫描。扫描擅长发现已经存在的风险，活动记录擅长发现长期未被触碰的对象，配置审查负责确认依赖，轮换演练负责验证恢复能力。四者组合起来，才形成可操作的控制闭环。

## 原创结论：最重要的字段不是最后使用时间，而是证据起点

很多治理面板把 `last_used_at` 放在最显眼的位置，因为它容易排序，也容易形成“活跃/不活跃”的二元判断。但在使用追踪刚开始启用的系统里，真正决定结论可信度的是 `tracking_start_at`：我们从什么时候开始拥有这份证据。

如果没有证据起点，空值可能代表未使用、未追踪、数据丢失或展示限制；如果有证据起点，团队才能把“在观察窗口内未见活动”与“历史上从未使用”区分开。前者可以进入审查，后者通常无法直接证明。

因此，AI 网关的密钥治理不应追求一个自动清理按钮，而应追求一条可解释的决策链：系统发现候选密钥，工程人员确认业务依赖，配置变更完成验证，旧凭据在可回滚窗口后撤销，最终留下不含秘密值的处理记录。活动视图的真正价值，是让这条链条拥有一个稳定、可复核的起点。
