## 先把它看成一个受策略约束的文件状态机

NodeLoc 上有人分享了一个临时网盘入口，页面公开信息显示，它支持多文件上传、电脑端拖拽、单文件最大 50 MB、默认保存 7 天，并能生成分享外链。用户还可以设置永久有效、1 天、3 天、7 天、30 天或自定义保存期限，也可以限制访问次数，包含 1 次阅后即焚、5 次、10 次、50 次和自定义次数等选项。页面还提供提取密码、关闭外链、文件预览、下载和直链代码生成等能力。

如果只把它理解成一个“上传文件并返回 URL”的小工具，很容易遗漏真正的工程问题。文件从上传到消失，至少经历了待上传、上传中、已保存、已分享、已过期、已达到访问上限和主动关闭外链等状态。访问者看到的页面、直链、Markdown 引用代码和 HTML 引用代码，也不一定拥有相同的行为边界。

因此，临时网盘的核心不是上传接口，而是一个由时间、次数和访问策略共同驱动的状态机。可以用下面的抽象表示单个文件的生命周期：

```text
未创建
  └─上传成功→ 可访问
                ├─到期时间到达→ 已过期
                ├─访问次数耗尽→ 已耗尽
                ├─上传者关闭外链→ 已关闭
                └─上传者删除文件→ 已删除
```

这张图的价值在于，它迫使实现者区分“文件还存在”和“文件还能被分享”两个事实。一个文件可能仍然保留在后台存储中，但外链已经关闭；也可能外链仍在，但访问次数已达到上限。若把这些状态压缩为一个布尔值，后台清理、下载鉴权和管理页面就会互相矛盾。

## 从公开页面反推最小架构

公开页面没有给出后端实现、数据库类型或存储厂商，因此不能把某种具体架构写成既定事实。但从功能边界可以推导出一个足够小、同时能支撑这些能力的系统模型。

第一层是上传控制面。它负责检查文件大小、接收文件元数据、创建文件记录，并把上传结果交给存储层。单文件 50 MB 是页面明确展示的限制，不能简单理解为所有请求都可以无限接近这个数值。工程上还要考虑反向代理请求体限制、内存缓冲、超时和并发上传数。若前端支持多文件批量上传，单文件限制并不等于单次请求的总大小限制；二者应当分别配置和验证。

第二层是文件元数据。至少需要保存文件标识、原始文件名、实际存储位置、文件大小、创建时间、过期时间、访问次数上限、当前访问次数、提取密码状态、外链状态和上传者标识。页面列出了文件名称、大小、修改时间、访问次数以及外链和访问控制，这说明这些字段不是装饰性信息，而是用户理解文件生命周期的主要依据。

第三层是分享控制面。分享 URL 不应直接等同于存储对象地址。更稳妥的做法是让 URL 指向一个下载控制器，由控制器依次判断文件是否存在、外链是否开启、是否超过有效期、是否超过访问次数，以及是否需要密码。所有条件通过后，再返回文件流或一个短时有效的内部地址。

第四层是后台清理。有效期只是访问规则，不自动意味着对象会在同一秒从存储中删除。系统至少需要一个清理任务，定期寻找已过期、已关闭或已删除的对象，并处理数据库记录、实际文件和临时下载凭证之间的残留。清理任务失败时，用户可能已经无法访问文件，但存储费用仍然继续产生。

第五层是管理配置。页面公开了网站标题、单文件最大限制、游客上传数、默认外链有效天数、游客浏览公共目录、游客上传、游客新建目录、游客配置提取码与次数、游客上传私有隔离等开关。它们说明管理员配置会改变产品的安全模型，而不是单纯改变界面文案。

## 一次分享请求应该如何被验证

一个可复查的验证流程，比“能打开链接”更有价值。下面的检查不依赖具体实现语言，可以用于评估公开服务，也可以作为自建服务的验收清单。

### 1. 上传边界

准备一个明显小于 50 MB 的文件、一个接近 50 MB 的文件和一个超过限制的文件。分别记录服务返回的状态、错误信息和文件列表变化。重点不是只看前端是否阻止选择，而是确认服务端是否也拒绝超限请求。前端限制可以被绕过，服务端限制才是实际边界。

如果产品支持多文件批量上传，还应验证“单文件限制”和“单次批量限制”是否被明确区分。一个批次中只要有一个文件失败，系统是全部回滚、部分成功，还是返回混合结果，都应在页面和接口中表达清楚。否则用户可能复制了一个只包含部分文件的分享链接，却误以为所有文件都已上传。

### 2. 时间边界

分别创建默认有效期、短期有效期和自定义有效期的分享。记录创建时间、页面显示的修改时间和到期时间。验证到期前能够访问，到期后不能访问；同时检查过期文件是否仍出现在上传者自己的列表中，以及管理端是否还能删除它。

时间判断还要注意时区。页面面向用户显示的是日期和时间，但服务端通常应使用统一时间基准保存时间戳。若创建、展示和清理分别使用不同的时区，最容易出现“页面显示还没过期，下载却已失败”或“已经过期，后台仍长期保留”的边界错误。

### 3. 次数边界

选择 1 次访问限制，使用不同浏览器或不同网络请求访问同一个链接，观察计数在什么时候增加。需要明确计数对象是成功下载、打开预览、请求文件头，还是任何一次到达控制器的请求。页面同时提供预览和下载，因此“访问次数”的语义不能默认等于“完整下载次数”。

阅后即焚尤其需要防止并发竞争。两个请求同时到达时，如果系统先读取次数、再分别写回结果，两个请求都可能看到剩余 1 次并成功下载。可靠实现需要原子递增或带条件更新，让“最后一次可用访问”只被一个请求消费。

### 4. 密码与外链边界

为文件设置提取密码，验证没有密码、错误密码和正确密码三种结果。密码不应出现在 URL、页面源码或生成的 Markdown 代码中。若生成的是长期外链，密码校验应当在每次访问时执行，而不是只在第一次打开页面时执行。

关闭外链后，原来的直链、Markdown 代码和 HTML 代码都应失效。否则“关闭外链”只关闭了管理页面入口，却没有关闭真正的分享能力，用户会得到错误的安全预期。

## 轻量产品的几个失败边界

最常见的失败边界是文件名处理。页面支持直链、Markdown 和 HTML 引用，文件名可能进入响应头、HTML 属性或日志。如果没有统一的文件名编码和输出转义，包含特殊字符的文件可能在下载时出现乱码，甚至污染页面上下文。存储路径也不应直接使用用户提交的原始文件名，文件名和内部对象标识应当分离。

第二个边界是 MIME 类型和浏览器预览。页面提供文件预览，但材料没有说明支持哪些文件格式，也没有说明预览是服务端转换还是浏览器直接打开。因此不能把“可预览”扩大解释成任意文件都安全预览。工程上应建立允许的内容类型清单；对不信任的 HTML、SVG 或带脚本内容，优先使用下载响应或隔离域名，避免把用户上传内容放在主站安全上下文中。

第三个边界是访问计数与缓存。若下载响应被 CDN、浏览器或代理缓存，后续请求可能没有到达计数控制器，导致次数限制失真。反过来，如果响应完全禁止缓存，重复下载大文件会持续占用源站带宽。访问计数严格程度、缓存策略和成本之间需要明确取舍，不能只在页面上放一个“次数限制”选项。

第四个边界是游客隔离。页面提供“游客上传私有隔离”开关，说明默认行为可能由管理员选择，而不是天然固定。对临时文件服务而言，目录列表和文件分享是两条不同路径：关闭目录公开访问，并不代表猜到文件标识的访问者无法打开文件；启用游客隔离，也不代表外链自动变成私有。目录权限、文件权限和分享凭证需要分别验证。

第五个边界是配额与滥用。页面显示游客上传数和基础配额配置，但公开信息没有给出具体配额值、限流算法或恶意文件处理策略。实际部署时至少应同时限制单文件大小、单用户文件数量、总存储空间、请求频率和并发上传数，并对过期对象设置回收策略。只限制文件大小，无法阻止大量小文件长期占满空间。

## 自建或选型时的工程取舍

如果目标只是短期中转，最小系统可以采用本地磁盘、关系型元数据表和定时清理任务。优点是部署简单，缺点是单机磁盘、备份、扩容和故障恢复都需要自行负责。若采用对象存储，则可以把大文件交给存储服务，但仍然需要保留自己的访问控制层，否则预签名地址的有效期、访问次数和主动关闭外链会变得难以统一管理。

“永久有效”选项也值得谨慎。它会把临时工具变成长期文件托管服务，带来更高的存储成本、投诉处理和数据生命周期责任。若产品定位是中转站，可以默认短期有效，并把永久保存设置为明确的例外；若必须支持永久有效，应至少展示文件占用、最后访问时间和手动删除入口。

对于分享链接，随机标识应足够长，且不要从自增 ID 直接推导。链接本身不应承担全部认证职责：提取密码、过期时间、关闭状态和访问次数都必须在服务端再次判断。管理员页面中的“VIP 登录账号与密码”也应使用强哈希保存，页面已明确说明用户 ID 和密码采用高强度哈希持久化；除此之外，还应限制登录尝试并避免在日志中记录明文凭据。

## 一份可落地的验收清单

部署或接入此类服务前，可以按以下顺序验收：

1. 上传小文件、接近限制的文件和超限文件，确认服务端边界一致。
2. 验证批量上传的部分成功、失败回滚和结果展示。
3. 验证默认期限、自定义期限和过期后的下载行为。
4. 验证 1 次、固定次数和无限次数的计数语义。
5. 验证预览是否消耗次数，以及并发访问是否发生超额消费。
6. 验证提取密码不会出现在 URL、源码和日志中。
7. 验证关闭外链后，旧直链、Markdown 和 HTML 引用全部失效。
8. 验证游客之间不能通过目录列表或可预测标识看到彼此文件。
9. 验证特殊文件名、特殊 MIME 类型和不可信内容不会污染页面。
10. 验证过期清理同时处理数据库记录、存储对象和缓存凭证。

临时网盘的价值，不在于它能否把一个文件放到云端，而在于它能否准确表达“谁可以在什么时间、以什么方式、访问多少次”。公开页面展示的功能已经覆盖了文件生命周期中最关键的几个控制点：大小、时间、次数、密码、外链和游客隔离。真正决定可靠性的，则是这些选项能否在服务端形成一致的状态转换，并在失败、并发、缓存和清理场景下保持同样的语义。

这也是轻量文件工具最容易被低估的地方：页面越简单，用户越会把一个链接当成明确承诺。工程实现必须让这个承诺可验证、可撤销、可过期，并且在每一次边界请求中保持一致。
