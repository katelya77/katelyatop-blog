## 先看变化：代理不再只是一次性命令

AI 编程代理早期最容易被观察到的指标，是模型名称、上下文长度或一次回答的代码质量。但当代理进入真实仓库，最难处理的往往不是“能不能生成代码”，而是一次长任务中断后能否继续、网络异常时能否定位、权限设置是否会在恢复线程后继续生效，以及它是否会把一个看似正常的请求送到不应访问的上游。

材料中的两个官方 Release 恰好覆盖了这条链路。OpenAI Codex 0.166.0 增加了 `codex doctor --network-only`，用于聚焦配置、连接性和 WebSocket 诊断；同时增加 `codex queue --resume`，可以在消息排队后恢复已卸载的线程。Claude Code v2.1.314 则把策略约束推进到多个边界：`permissions.blockWritesOutsideWorkingDirectories` 在每种权限模式下拒绝工作目录之外的写入；Claude apps gateway 上游支持按 IdP 群组筛选开发者，并且故障转移时仍执行筛选；Bedrock 上游增加 `guardrail_trace`，记录触发了哪个护栏过滤器，但不记录匹配文本；另外，VS Code 与 Claude Desktop 的 Code tab 增加了空闲压缩机制。

这些不是同一种功能的简单堆叠。它们分别解决了“怎么知道坏在哪里”“如何从中断处继续”“允许代理做什么”“请求实际经过了哪条安全路径”和“上下文如何保持可用”五个问题。代理产品的核心，正在从一次调用的智能程度转向一个可恢复、可约束、可观察的运行时。

## 第一层：把故障诊断从全量检查变成窄路径

网络问题是代理最容易被误判的一类故障。请求失败可能来自本地配置、连接建立、WebSocket 通道，或者服务端本身。如果诊断命令把所有因素混在一起，用户只能得到“失败了”，很难判断下一步应该改配置、查网络，还是等待服务恢复。

Codex 0.166.0 增加的 `--network-only` 值得注意的地方，不是命令名称本身，而是它把诊断范围明确收窄到配置、连接性与 WebSocket。对于工程排障，这相当于把“代理不可用”拆成一个可执行的最小检查面：

```bash
codex doctor --network-only
```

这条命令适合放在故障复现的第一步，而不是等到所有配置都被改过之后才运行。检查记录至少应保存以下信息：执行时间、当前版本、命令原始输出、是否能建立连接、是否涉及 WebSocket，以及随后采取的唯一变更。这样才能避免把多个变量同时修改，最后只知道“好像恢复了”。

这里有一个重要边界：官方材料只说明该命令用于聚焦配置、连接性和 WebSocket 诊断，并没有证明它能覆盖模型服务错误、权限拒绝或代码执行失败。因此，`doctor --network-only` 通过，不能推出代理整体可用；它最多证明网络相关的窄路径没有暴露出问题。验证流程应把结果分层记录：网络诊断、身份与权限、模型请求、工具调用分别判定，不能用一个绿色结果替代全部健康检查。

## 第二层：恢复能力要恢复状态，而不是重新开始

长任务中断后，最昂贵的损失通常不是几秒钟的等待，而是已经积累的上下文、排队意图和人工确认。Codex 新增的 `codex queue --resume` 说明其恢复对象不是简单重放最后一条命令，而是“已卸载的线程”。这一区分很关键：重新启动一个新线程，可能丢掉原来的讨论状态；恢复线程，则要求系统保留足够的任务身份与历史关联。

可以用一个最小检查清单验证恢复链路：

```bash
codex queue --resume
```

1. 先记录排队消息对应的线程标识或终端输出。
2. 在不改变仓库内容的前提下，让线程进入卸载或等待恢复状态。
3. 执行恢复命令，确认恢复的是原线程，而不是新建会话。
4. 检查恢复后是否仍能看到原任务的上下文、待处理消息与权限选择。
5. 对恢复前后执行的工具调用分别留痕，避免把重复执行误当成成功恢复。

材料明确支持“恢复排队消息后已卸载的线程”这一能力，但没有给出持久化时长、跨机器恢复、进程崩溃后的所有场景。因此，工程上不能把它宣传成无限可靠的任务续接。特别是涉及写文件、迁移数据库或发布操作时，恢复机制必须与幂等设计配合：恢复后先检查工作区和外部系统状态，再决定是否重试。否则，同一条排队消息可能在业务层产生两次副作用。

恢复能力还有一个容易被忽视的测试点：权限状态是否随线程一起保留。官方 Release 同时提到 Codex 修复了恢复或分叉线程时，已确认的审批与权限设置能够保留。由此可以建立更严格的验收条件：不仅要验证“线程回来了”，还要验证“线程回来后仍按原来的授权边界工作”。

## 第三层：把写入边界放到所有权限模式之上

Claude Code v2.1.314 新增的 `permissions.blockWritesOutsideWorkingDirectories`，解决的是代理工具最危险的默认歧义之一：权限模式可能允许某些操作，但工作目录之外的写入是否仍然被允许？Release 明确说明，启用该设置后，Write、Edit 和 NotebookEdit 会在每一种权限模式下拒绝工作目录之外的路径。

它的工程价值在于提供了一条跨模式的不变量。普通权限控制回答的是“这次操作是否需要批准”；工作目录写入边界回答的是“即使操作被允许，目标位置是否仍在任务的空间内”。两者不能互相替代。一个代理可以拥有较宽松的交互权限，但仍不应因为路径解析、脚本生成或工具参数错误而改写无关目录。

配置验证不应只检查配置文件是否存在，而应做正反两组测试：

```text
permissions.blockWritesOutsideWorkingDirectories = true
```

在工作目录内创建一个明确的测试文件，确认正常写入；再请求写入工作目录外的临时路径，确认 Write、Edit、NotebookEdit 三类操作都被拒绝。测试时要记录实际解析后的目标路径，因为相对路径、父目录跳转和符号链接都可能让“看起来在目录内”的输入指向别处。材料没有提供符号链接处理规则，因此不能假设该设置自动覆盖所有路径绕过方式；这部分应作为部署前的额外边界测试，而不是写成已被官方保证的行为。

这个设计也带来取舍。强制目录边界能够降低误写风险，却可能阻碍需要修改生成目录、缓存目录或单独工作树的任务。与其关闭保护，不如显式调整工作目录范围，并为例外目录建立单独的审计记录。安全策略的目标不是让代理永远不能写，而是让写入范围可解释、可复查、可回滚。

## 第四层：身份路由、故障转移与护栏必须使用同一策略

Claude apps gateway 的两个变化揭示了企业代理接入中的另一条链路。上游可以配置可选的 IdP 群组列表，只有属于指定群组的开发者才会被发送到该上游；而且发生故障转移时，这个群组筛选仍然生效。这意味着身份策略不能只挂在主路由上，否则主上游故障时，备用上游可能成为绕过组织边界的隐蔽通道。

验证这类配置时，应准备至少两个身份样本和两个上游：一个满足群组条件，一个不满足；然后分别验证主路径与故障转移路径。检查重点不是“请求最终成功”，而是“不满足条件的身份在两条路径上都不会被发送”。如果系统只返回统一的拒绝结果，还需要结合网关审计记录确认路由目标，不能把客户端看见的错误码当成完整证据。

Bedrock 上游新增的 `guardrail_trace` 则补上了安全可观察性。它记录哪个 Amazon Bedrock guardrail 过滤器触发，同时不记录匹配文本。这个设计体现了一个现实取舍：运维需要知道哪条护栏生效，排查误拦截需要可定位性；但日志不应把用户输入中的敏感匹配内容再次扩散。

因此，日志验收应分成两项：一是触发事件能够关联到具体过滤器；二是日志中不存在匹配文本。不能为了调试方便而把原始请求全文写入同一日志，也不能因为隐私要求而完全关闭触发线索。更稳妥的做法是让“策略标识”和“内容数据”分离保存，并限制后者的访问范围；材料只证明了 `guardrail_trace` 的记录语义，具体保留周期、权限模型和导出格式仍需以实际产品文档为准。

## 第五层：上下文压缩不是删除历史，而是延长可用状态

Claude Code v2.1.314 还为 VS Code 与 Claude Desktop 的 Code tab 增加了 idle compaction：当一个超过 200K token 的对话空闲时，会被总结；下一条消息在提示缓存过期后使用该摘要。这里的关键条件有三个：对象是长对话，触发条件包括空闲与超过 200K token，摘要的使用时机与提示缓存是否过期有关。

这不是简单的“上下文太长就截断”。压缩后的系统仍需要保留任务目标、已确认的约束、关键文件变更和未完成事项，否则代理虽然恢复了可用窗口，却失去了工程语义。验证时可以构造一个长对话，停止操作并等待触发，再发送下一条消息，检查摘要是否被使用；同时比较缓存未过期与已过期两种情况。不要把“界面还能继续输入”当成压缩成功的证据，因为那只能说明前端没有崩溃。

材料没有说明摘要算法、摘要大小、是否保留全部工具输出，也没有说明压缩对每种模型的影响。因此，不能据此推导准确的 token 节省比例或质量提升。部署决策应关注失败边界：如果任务依赖某个精确的编译错误、补丁片段或路径列表，摘要可能不足以替代原始记录。关键操作应沉淀到仓库中的状态文件、变更记录或外部工单，而不是只依赖聊天历史。

## 一套可落地的验收顺序

把上述能力组合起来，可以得到一条比“升级后能不能聊天”更可靠的验收链：

1. **先验网络**：运行 `codex doctor --network-only`，保存原始输出，确认配置、连接性和 WebSocket 检查结果。
2. **再验恢复**：对排队线程执行 `codex queue --resume`，确认线程身份、上下文、待处理消息和权限状态没有被替换或丢失。
3. **再验写入**：启用 `permissions.blockWritesOutsideWorkingDirectories`，分别测试目录内成功与目录外拒绝，并覆盖 Write、Edit、NotebookEdit。
4. **再验路由**：用不同 IdP 群组身份测试主上游与故障转移，确认备用路径不绕过群组约束。
5. **再验护栏日志**：触发已配置的 Bedrock 护栏，检查能够识别过滤器，同时确认日志不含匹配文本。
6. **最后验压缩**：构造超过 200K token 且空闲的 Code tab 对话，分别观察提示缓存状态变化后的后续消息行为。

这套顺序体现了一个工程原则：先确认控制面，再确认数据面；先确认“能否连接和恢复”，再确认“能做什么”；最后验证长时间运行时的上下文退化。每一步都应保留输入条件、版本、输出和结论，形成可重放的发布记录。

## 原创结论：代理的可靠性是策略闭环，不是功能清单

从这两份官方 Release 可以得出一个比“又增加了几个命令”更重要的结论：AI 编程代理正在形成策略闭环。诊断能力负责暴露连接与配置问题，恢复能力负责把中断任务带回正确状态，目录边界限制工具的副作用，身份群组限制请求的路由范围，护栏追踪解释安全拦截，空闲压缩则维持长任务的上下文可用性。

这些能力也不能孤立验收。一个能恢复线程却丢失权限状态的代理，会把可靠性变成风险；一个有群组路由却在故障转移时放宽条件的网关，会让主路径的治理形同虚设；一个能压缩上下文却没有外部变更记录的工作台，会让摘要成为新的单点故障。

因此，评估下一代代理时，建议把问题从“模型更强了吗”改成四个可验证的问题：失败后能否定位，任务能否恢复，权限边界能否保持，关键决策能否留下不泄露内容的证据。只有当这四项同时成立，代理才从一次性智能工具走向可以进入真实工程流程的运行时。
