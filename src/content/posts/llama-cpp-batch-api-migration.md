升级推理运行时，最容易被低估的不是模型文件，而是应用与运行库之间那层调用契约。llama.cpp v1.1.0 的发布说明将旧的 `llama_batch` API 标记为弃用，并推荐转向 `llama_batch_ext` 与 `llama_process`。这是一条明确的迁移信号，却不等于“把函数名替换掉就完成升级”：发布摘要没有给出完整的调用语义、兼容周期或逐项迁移代码，应用仍需以目标版本的头文件和实现为准。

本文聚焦一个实际问题：当底层 API 从旧入口转向新入口时，怎样既不把弃用当成紧急故障，也不把“当前还能编译”误认为迁移已经完成？

## 弃用说明告诉我们什么，又没有告诉我们什么

v1.1.0 的发布说明把 `llama_batch` 的弃用，以及 `llama_batch_ext`、`llama_process` 的引入，列在 API 变更中。这足以支持几个谨慎的结论：旧入口不再是新代码的优先选择；维护者正在调整批处理相关的接口；依赖旧入口的应用应当开始盘点和规划迁移。

但仅凭这段说明，不能推出旧 API 已被删除，不能断言新旧入口行为完全等价，也不能推断应用只需要改一个符号。摘要没有说明参数如何映射、调用的状态边界如何变化，或不同后端是否有相同表现。此时若写出未经核对的替换代码，反而会把猜测伪装成迁移指南。

更可靠的理解方式是把“弃用”视作生命周期信息，而不是运行时错误。它提示团队把升级成本纳入计划：先定位使用点，再对照目标版本的定义和示例，最后用应用自己的行为测试确认结果。若项目当前版本仍可正常构建，是否立即升级还要看维护期限、后续依赖和验证预算；但把迁移拖到旧入口消失后再做，通常会让诊断和回退更困难。

## 批处理接口不是一个孤立的函数名

批处理 API 位于应用与推理运行时的边界。应用准备输入、组织一次或多次处理，再消费输出；调用方式的调整可能影响的不只是编译器能否找到符号，还可能涉及数据如何表达、调用何时完成、错误如何传递，以及上层如何判断一次请求已经结束。这些是迁移时需要检查的维度，并非发布摘要对新 API 行为的逐项承诺。

因此，不宜把 `llama_batch`、`llama_batch_ext` 和 `llama_process` 简化成三个名字相近的函数。新接口名称中包含“扩展”或“处理”，本身不足以说明它们的参数、生命周期或性能属性。正确的依据应是目标 tag 下的公开头文件、项目示例、测试以及实际调用路径。尤其在封装层、异步任务或多请求服务中，还要确认应用拥有的数据在调用期间是否仍然有效，失败时是否会留下半完成状态，以及重试是否会重复处理。

这也解释了为什么“能编译”是必要条件，却不是充分条件。头文件证明接口形状，编译证明代码与该形状相容；只有针对应用行为的测试，才能进一步检验输入、输出和错误处理是否仍符合预期。不同证据回答不同问题，不应相互替代。

## 先盘点，再改代码：可复核的迁移起点

可以先在官方仓库检出目标版本，查找批处理相关定义和使用位置：

```sh
git clone https://github.com/ggml-org/llama.cpp.git
cd llama.cpp
git checkout v1.1.0
git grep -n -E 'llama_batch|llama_process' -- '*.h' '*.hpp' '*.c' '*.cc' '*.cpp'
```

这组命令的用途是建立源码位置清单，不是自动生成迁移方案。还应阅读命中的声明、相邻注释、示例及测试；若项目调整了目录结构，按检出的源码实际路径补充搜索范围。之后在自己的仓库中进行相同盘点：

```sh
git grep -n -E 'llama_batch|llama_batch_ext|llama_process' -- '*.h' '*.hpp' '*.c' '*.cc' '*.cpp'
```

检查结果至少分成三类：直接调用旧 API 的代码；封装了旧 API、但调用点看不出底层依赖的适配层；文档、测试或构建配置中对特定版本的假设。只搜函数名容易漏掉封装和间接依赖，所以还要沿调用链向上追到请求入口、向下追到输出消费处。对每一处记录使用场景、输入形状、错误路径和对应测试，才能判断一项改动是否影响多个上层功能。

盘点之后再对照 v1.1.0 的实际声明和官方示例，逐项确认旧调用能否迁移、需要怎样组织数据、调用后的状态由谁负责。遇到发布摘要没有回答的问题，标为待核实，而不是根据名称推测。若新旧入口无法一一对应，应将差异体现在适配层中，并把适配约束写进测试，避免让多个调用点各自做出不同假设。

## 验收应覆盖行为，而不只是构建

迁移验证可以分成由窄到宽的几层。第一层是静态检查：旧入口是否还有未评估的使用点，适配层是否遗漏分支。第二层是编译：在项目实际支持的构建配置下，应用是否能使用目标版本的公开接口。第三层是行为回归：对固定输入检查输出结构、结束条件、错误返回和资源清理是否符合应用原有契约。第四层是在真实部署配置中确认后端、模型和并发方式与生产使用场景一致。

测试样本不必一开始就很大，但应能区分正常路径和边界路径。至少保留一个普通请求、一个较长或多段输入的请求，以及一个会触发错误处理的场景；若服务会并行处理多个请求，也要覆盖并发调用与取消或失败后的清理。对输出的验证应使用应用真正依赖的指标，而不是只比较日志文本。比如应用关心结构化结果，就检查结构；应用关心结束条件，就验证是否按预期停止。不要仅凭一次成功响应便宣称所有后端和负载都已兼容。

升级前后的结果也要有可比较的基线：固定模型、输入、运行配置和测试版本，记录输出差异及失败情况。若生成内容具有非确定性，测试应比较稳定的契约，而不是要求逐字一致；具体可比较什么，取决于应用的使用方式。回归失败时，应区分接口调用问题、运行配置变化和模型输出波动，避免把所有差异都归因于 API 改动。

## 版本证据不能跨项目互相代替

同一批发布材料还显示，Ollama 的 `v0.40.19-rc0` 是一个候选版本，说明中只提到更新了 `llama-server`。这条记录不能证明它采用了 llama.cpp v1.1.0，也不能证明两者的 API 或行为兼容。名称上的关联和时间上的接近，不构成依赖关系的证据；候选版本也不能直接代表正式发布状态。

这对集成层尤其重要：上游 API 的迁移信号、下游运行时的版本更新、应用实际链接或调用的组件，是三个不同层次。团队应从锁定文件、构建配置、镜像或二进制来源中确认实际版本，再针对该组合做验证。若只记录“升级了 llama.cpp”或“升级了服务”，却没有明确组件版本和测试环境，之后就很难复现问题。

一个实用的升级记录至少应包含：目标版本及其稳定性；应用实际使用的 API；构建配置和后端；覆盖的测试场景；已知未覆盖项；失败时回退到哪个已验证版本。这里的回退版本不是发布说明替你选择的答案，而是团队自身的兼容性记录。对候选版本，先限定在隔离环境或可回滚的发布阶段，也比直接把预发布状态当作正式承诺更稳妥。

## 工程取舍：不要过早迁移，也不要等到最后一刻

面对弃用，常见的两个极端都不理想：一看到提示就大范围重写，可能扩大变更面、引入不必要风险；把弃用当作无关紧要的噪声，则会让旧调用继续扩散，最终在必须升级时集中付出代价。更好的做法是先收敛使用点，把直接调用集中在边界清晰的适配层；明确目标版本与验收条件；再以小步提交迁移，并保留可回退的旧版本构建路径，直到新路径通过所需验证。

是否现在迁移，取决于旧接口的实际使用范围、应用的升级窗口和可用测试。若调用点少、目标版本已在计划内，尽早完成盘点和验证通常成本较低；若当前版本被稳定性要求锁定，可以先建立迁移任务和回归基线，而不是为了追新版本制造无必要的运行变更。重要的是把“暂缓”变成有记录的决定，而不是默认遗忘。

从 v1.1.0 这条变更能得到的工程结论，并不是某个新函数必然更快或更好，而是 API 弃用会把兼容性责任推回到集成者：查明真实依赖，读懂目标版本的契约，用应用行为验证迁移，并区分上游事实与下游猜测。版本号只指出从哪里开始调查；真正的完成标准，是团队能说明迁了什么、验证了什么，以及哪些边界仍未覆盖。
