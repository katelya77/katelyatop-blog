## 先把“发布”拆成几种不同事实

在 AI 工具链里，“某版本已经发布”经常被误读成“它已经适合升级”。实际上，发布页至少包含四种不同事实：项目维护者创建了一个标签；自动化流程生成了构建资产；项目方写下了本次变更；用户能够下载并运行某个产物。这四件事相互有关，却不能互相替代。

llama.cpp 的 b12211 发布页明确标记为 Pre-release，页面显示该标签对应提交 `7d7f028`，并列出一次 `mtmd` 重构：移除 `clip.h`，把相关代码整合到 `mtmd` 中。页面同时列出多种平台构建，包括 macOS Apple Silicon、macOS Intel、iOS XCFramework、Linux CPU、Vulkan、CUDA、ROCm、OpenVINO、SYCL，以及面向 Snapdragon 的 CPU、Adreno GPU 和 Hexagon NPU 构建。这里能证明的是：该标签存在、某个提交与它关联、发布流程声明了这些构建目标。它不能单独证明每一个目标都能在你的机器上正常工作。

OpenAI Codex 的 `0.169.0-alpha.3` 同样被标记为 Pre-release。官方页面显示它在 2026 年 11 月 7 日发布，关联提交为 `737775c`，页面列出 196 个 Assets，并注明该版本之后主分支已有 14 个提交。这里的证据重点不同：它能说明这是一个带有大量平台产物的 Alpha 版本，但不能从“196 个资产”推导出 196 种独立功能，也不能把“主分支继续前进”解释为该 Alpha 已经被替代或已经稳定。

因此，预发布验收的第一原则是：先写清楚你正在验证哪一个命题，而不是先执行升级命令。

## 从发布元数据建立最小证据链

一个可审计的升级记录，至少应该保存四类信息：版本标签、提交身份、发布状态和资产清单。不要只截取网页标题，也不要只保存下载链接。网页内容可能变化，而标签、提交和资产是可以被命令行再次查询的结构化对象。

如果使用 GitHub CLI，可以先读取两个发布对象：

```bash
gh api repos/ggml-org/llama.cpp/releases/tags/b12211 \
  --jq '{tag_name,name,prerelease,target_commitish,created_at,assets:[.assets[].name]}'

gh api repos/openai/codex/releases/tags/rust-v0.169.0-alpha.3 \
  --jq '{tag_name,name,prerelease,target_commitish,created_at,assets:[.assets[].name]}'
```

这一步的验收点不是“命令返回 200”这么简单，而是检查结果是否符合预期：`prerelease` 是否为真；标签是否与批准的版本完全一致；资产是否包含目标操作系统和架构；下载名称是否落在允许的范围内。对生产环境而言，预发布标签应当默认进入候选环境，而不是直接覆盖稳定版本。

随后保存标签与提交的关系：

```bash
gh api repos/ggml-org/llama.cpp/git/ref/tags/b12211 \
  --jq '.object | {type,sha,url}'

gh api repos/openai/codex/git/ref/tags/rust-v0.169.0-alpha.3 \
  --jq '.object | {type,sha,url}'
```

如果返回的是 annotated tag，标签对象与最终提交可能不是同一个 SHA，需要继续解析 tag 对象；如果返回的是 commit，则可直接与发布页中的提交标识进行比对。工程记录中应保留最终可构建提交，而不是只保留一个容易被误抄的短 SHA。

## 构建矩阵不是兼容性承诺

llama.cpp b12211 的构建矩阵很长，这对使用者有两个启发。第一，平台名称本身是范围声明，不是测试报告。Linux x64 CUDA、Linux x64 Vulkan 和 Linux arm64 CPU 代表不同的编译条件、驱动条件与运行时路径；同一个重构可能在 CPU 路径通过，却在某个 GPU 后端暴露接口或链接问题。第二，矩阵越长，越需要把“下载验证”和“运行验证”分开。

下载验证可以确认资产存在、文件完整、架构匹配。例如在 Linux 上，至少应检查文件类型和动态依赖：

```bash
file ./artifact
uname -m
ldd ./artifact || true
```

`file` 用于发现明显的架构错配，`uname -m` 提供当前主机架构，`ldd` 则帮助识别缺失的共享库。它们只能证明产物具备被当前系统加载的基本条件，不能证明模型推理结果正确，也不能证明某个后端真正被启用。

运行验证需要针对变更触达的路径设计最小场景。b12211 的发布说明只明确指出 `mtmd` 代码组织发生重构，并没有在材料中给出性能提升、模型兼容范围或行为变化。因此，不能把“移除 `clip.h`”写成性能优化，也不能据此断言多模态能力增加。合理的验证对象应是：相关目标是否仍能编译；依赖 `mtmd` 的最小程序是否能启动；原有输入在重构前后是否产生一致的成功或失败结果；异常输入是否仍能得到可识别的错误。

若项目提供测试命令，应优先运行项目自身的目标测试；若没有针对该变更的公开测试说明，则记录构建命令、运行输入、退出码和日志摘要，而不是用一次成功启动替代完整结论。

## Alpha 版本要单独处理“变更未知”

Codex `0.169.0-alpha.3` 的官方页面提供了版本状态、发布日期、提交和资产数量，但材料没有列出具体功能变更。这是一个重要的负面证据：没有变更说明，不等于没有变化；它只意味着当前材料不足以支持功能层面的结论。

这类版本的检查流程应更保守。先在隔离目录解压或安装，避免覆盖已有二进制；再记录版本输出、帮助文本和关键退出码：

```bash
mkdir -p /tmp/codex-alpha-check
cp ./codex /tmp/codex-alpha-check/codex
/tmp/codex-alpha-check/codex --version
/tmp/codex-alpha-check/codex --help > /tmp/codex-alpha-check/help.txt
```

如果工具会读取配置、访问网络或调用外部程序，还应使用最小权限环境，并明确禁用不必要的凭据与生产目录。Alpha 版本的验证重点不是“所有功能都试一遍”，而是确认升级不会破坏现有工作流：启动、版本回退、配置解析、非交互退出、日志输出和失败返回值都应有记录。

尤其要注意“主分支已有 14 个提交”这一事实的边界。它说明发布之后开发仍在继续，但不能说明这些提交修复了 Alpha 的问题，也不能说明下一个版本必然包含某项修复。把时间线信息当作质量结论，是发布审查中常见的推断越界。

## 失败边界：哪些结果不能被包装成通过

第一种失败是资产缺失。发布页存在，但目标平台没有对应文件，此时只能判定“版本可见”，不能判定“目标平台可升级”。

第二种失败是标签与运行版本不一致。下载文件名可能相似，二进制内部版本也可能来自不同构建；如果 `--version`、标签和记录中的 SHA 无法对应，应停止继续验证。

第三种失败是构建成功但后端未生效。尤其是 GPU 相关构建，编译器和链接器通过不代表运行时找到了正确驱动。应把“可执行文件启动”“目标后端被加载”“实际任务完成”作为三个独立检查点。

第四种失败是行为变化没有证据。对于 b12211，材料只支持 `mtmd` 代码重构这一发布事实；对于 Codex Alpha，材料支持预发布状态和资产信息。任何性能提升、兼容性扩大、安全修复或 API 变化，都需要额外的一手文档、测试或变更记录支持。没有证据时，结论应写成“尚未验证”，而不是“应该没问题”。

第五种失败是回滚不可用。预发布升级前必须保存旧版本、配置和可重复的启动方式。回滚检查不是把旧文件复制回来，而是确认旧版本能够在相同数据目录或明确的迁移后目录中启动，并且不会被新版本生成的不可逆状态阻塞。

## 一套适合预发布工具链的验收清单

可以把一次升级分成四道门：

1. **身份门**：标签、发布状态、最终提交和资产名称全部匹配；
2. **环境门**：操作系统、CPU 架构、GPU 后端、驱动和动态库满足目标构建条件；
3. **行为门**：最小启动、关键命令、代表性输入和失败路径均有可复现记录；
4. **回退门**：旧版本、配置备份和回滚命令经过演练，升级失败不会扩大影响范围。

四道门的顺序也有工程含义。身份门不通过，后续运行结果没有归属；环境门不通过，行为门的失败可能只是部署错误；行为门不通过，不能因为发布页是官方页面就放行；回退门不通过，即使前三道门通过，也不适合进入不可逆的生产变更窗口。

## 结论：发布页是起点，不是质量证明

llama.cpp b12211 和 Codex `0.169.0-alpha.3` 展示了两种常见的预发布证据形态：前者给出具体重构说明和广泛构建矩阵，后者突出 Alpha 状态、提交身份与大量资产。它们都很有价值，但都没有替使用者完成环境兼容、行为正确性和回滚安全的验收。

真正可靠的升级判断，应当把“官方发布事实”“本地环境事实”和“运行行为事实”分别保存，并让每个结论都能回到对应证据。预发布版本并不是不能用，而是不能用一个绿色标签替代一条完整证据链。
