## 先把证据等级说清楚

这篇文章讨论的是两个预发布信号：llama.cpp 的 b12444，以及 Ollama 的 v0.40.17-rc1。它们都来自项目官方 GitHub Release，因此属于一手发布材料；但它们不是稳定版承诺，也不能直接证明某个模型、某张显卡或某种工作负载已经获得可感知的加速。

b12444 的发布说明只明确写出一项变化：`HIP/CUDA: enable GDN mma kernel on CDNA`。同一页面还列出了多个构建目标，包括 Ubuntu x64 CPU、Vulkan、CUDA 12、CUDA 13、ROCm 等。Ollama 的 v0.40.17-rc1 则列出了 Vulkan 集成显卡使用 mmap、MLX 并发生成，以及 llama.cpp 版本更新等变化。这里能确认的是“代码路径或构建关系发生了变化”，不能确认的是“所有 GPU 都变快了”“所有模型都受益”或“不同发行版的二进制都具备相同能力”。

这一区分很重要。预发布说明描述的是变更意图和交付内容，性能结论还需要把硬件、后端、模型、上下文长度、并发度和编译选项绑定在一起验证。

## 内核优化为什么有明确适用域

GPU 推理并不是一个单一的“GPU 开关”。一次生成请求至少经过模型算子、张量布局、内存分配、调度器和后端内核等多个层次。某个内核被启用，只说明满足条件的算子可以走新的实现；如果模型没有调用该算子，或者运行时最终选择了另一条路径，优化就不会自动转化为端到端收益。

b12444 把 GDN mma kernel 的启用范围写在 `HIP/CUDA` 和 `CDNA` 两个限定条件中。工程上应把它理解为一个二维门槛：第一层是后端，第二层是硬件架构。使用 Vulkan、CPU 或其他 GPU 架构时，不能从这条发布说明推导出同样的效果。即使是 CDNA 设备，也还要确认实际二进制是否包含对应后端、模型执行是否触发相关算子，以及运行时有没有因为显存、数据类型或算子不匹配而回退。

这也是为什么“支持 CUDA”不是完整的验收条件。CUDA 版本、GPU 架构、编译目标和运行时库共同决定可执行路径；“支持 ROCm”同样不等于每个 AMD 架构都能使用同一组内核。发布页中并列出现多种构建产物，恰恰说明后端不是一个可以互相替代的标签。

Ollama 的发布说明提供了另一个例子。v0.40.17-rc1 同时提到 Vulkan 集成 GPU 的 mmap 改进、MLX 并发生成和 llama.cpp 版本更新。它们分别涉及内存映射、并发执行和底层推理库，不能合并成一个笼统的“推理性能提升”。不同变化的受益对象、瓶颈位置和失败方式可能完全不同。

## 用发布材料建立可复现的检查起点

第一步不是跑 benchmark，而是固定候选版本和来源。下面的命令可以从官方仓库读取发布元数据，避免把搜索结果、镜像页面或第三方打包版本当成同一个构建：

```bash
gh release view b12444 --repo ggml-org/llama.cpp

gh release view v0.40.17-rc1 --repo ollama/ollama
```

如果需要保存审计记录，可以把输出写入带版本号的文件，但不要只保存网页截图。至少记录 tag、是否为 prerelease、发布时间、发布提交、资产名称和校验信息。对二进制进行验证时，建议把下载、校验和运行分成三个独立步骤：

```bash
sha256sum ./llama-cli
./llama-cli --version
./llama-cli --help | sed -n '1,120p'
```

这里的关键不是某个命令一定输出什么，而是确认“拿到的文件是什么”。版本字符串、编译后端、目标架构和实际运行路径应进入测试记录。若使用发行版包、容器镜像或上层封装，还要额外记录它们包含的底层 llama.cpp 版本，不能仅凭上层工具的版本号推断底层行为。

第二步是记录硬件与后端，而不是只记录显卡商品名。测试表至少包含：GPU 型号与架构、驱动版本、运行时版本、模型文件、量化类型、上下文长度、提示词长度、生成 token 数、并发请求数、是否启用 mmap，以及最终选择的后端。对于 b12444 的目标路径，尤其要确认测试设备确实属于 CDNA 范围，并且使用的是 HIP/CUDA 路径；否则测试结果无法回答这次发布改动是否生效。

## 性能验证要测“路径”，不只测“速度”

一个可用的预发布基线应至少包含三组对照：候选版本、上一版本、以及禁用目标后端或使用替代后端的结果。每组都使用相同模型和输入，先进行一次预热，再重复多轮，分别记录首 token 延迟、生成吞吐、总延迟、峰值显存和失败率。

只看 tokens/s 很容易误判。内核优化可能改善生成阶段，却不影响提示词处理；mmap 变化可能降低内存压力，却不会在短请求中体现为吞吐提升；并发生成优化可能提高总吞吐，却增加单请求延迟。应把指标按阶段拆开，至少区分：

1. 模型加载时间与首次请求时间；
2. 提示词处理速度；
3. 生成阶段吞吐；
4. 并发请求下的排队与尾延迟；
5. 显存占用、主机内存占用和进程异常退出。

重复次数也不能随意。短输入、短输出会放大启动噪声，单次长输出又可能掩盖加载成本。更稳妥的做法是准备短上下文和长上下文两类样本，再准备单请求和多请求两类负载。若目标是验证某个内核是否被调用，性能数据还不够，应结合运行日志、后端诊断信息或构建信息确认实际路径；没有路径证据时，只能说“观察到结果变化”，不能说“证明新内核生效”。

## 失败边界要提前写进验收表

第一类边界是硬件不匹配。发布说明明确限定 CDNA，测试机若不属于该架构，结果只能用于验证兼容性或回归，不能用于评价该内核的收益。第二类边界是后端不匹配。Vulkan、CPU、HIP 和 CUDA 不是同一执行路径，切换后端后应重新建立基线。

第三类边界是算子覆盖不足。模型可能只在部分层或部分形状上触发目标实现，因此“某个模型没有加速”不必然说明发布失败；反过来，“某个小样本变快”也不代表所有模型都受益。应记录模型结构、量化格式和输入形状，把结论限定在实际覆盖范围内。

第四类边界是回退。预发布版本可能在初始化阶段成功，却在长上下文、并发、显存接近上限或特定输入形状下回退或失败。验收不能只跑一条短提示词。至少应加入长上下文、连续请求、并发请求和接近显存上限的安全压力样本，并明确失败后的处置：保留日志、降级到上一版本、切换已知稳定后端，或者暂缓扩大流量。

第五类边界是上层封装。Ollama 的发布说明涉及底层库版本更新，但用户调用的是上层服务。上层参数、模型缓存、并发调度和默认后端选择都可能改变结果。因此，不能把 llama.cpp 独立二进制的测试结论直接复制给 Ollama，也不能用 Ollama 的吞吐结果反推某个底层内核一定被使用。

## 面向生产的最小验收清单

可以把一次预发布 GPU 变更压缩成以下顺序：

- 固定官方 tag、提交、资产和校验值，并标注 prerelease；
- 记录硬件架构、驱动、运行时、编译后端和上层封装版本；
- 选定至少一个上一版本作为回归基线；
- 用同一模型、量化、上下文和输入生成可重复样本；
- 分别测加载、提示处理、生成吞吐、尾延迟、显存和失败率；
- 用日志或诊断信息确认目标后端与目标路径，而不是只看速度；
- 覆盖短请求、长上下文、连续请求和并发请求；
- 写明不适用的硬件、后端、模型和输入形状；
- 设定回退条件，例如错误率上升、尾延迟恶化、显存异常或结果一致性失败；
- 将候选版本限制在灰度环境，直到证据覆盖真实负载。

## 结论：把“优化”改写成一个有条件的命题

b12444 的价值不在于给出一个可以套用到所有设备的加速百分比，而在于它把优化边界写得足够具体：HIP/CUDA、CDNA、GDN mma kernel。Ollama v0.40.17-rc1 的变化也提醒我们，同一个发布版本可能同时包含内存、并发和底层库更新，必须逐项验证，不能用一个总指标替代分析。

因此，预发布 GPU 优化的正确表述应是：在指定硬件、指定后端、指定模型和指定负载下，某条执行路径出现了可重复的改进，并且没有突破预先定义的稳定性边界。只有当路径证据、性能证据和失败处置证据同时成立，发布说明中的“启用内核”才真正变成可以交付的工程结论。
