## 先把“模型能力”还原成工作台问题

社区里介绍 AI 视觉服务时，最容易被放大的通常是模型名称、分辨率或“免费体验”。但真正决定一个服务能否被使用的，往往不是模型列表，而是用户能否稳定完成一次任务：输入什么，系统如何校验，消耗如何计算，任务是否可追踪，结果能否复用，失败后又能否判断责任边界。

AXAI Studio 的页面给出了一个相对完整的产品样本。它同时展示文生图、参考图引导、文生视频、首帧与尾帧、主体一致性参考图、视频时长、清晰度和画幅等控件；页面还显示点数消耗、浏览器本地历史，以及“通过标准 API 接口或授权令牌调用”的产品说明。AXAI API 的入口则返回“AXAI API Gateway is running”与 `status: true`。这两类证据可以证明入口与工作台页面存在，但不能直接证明后台采用了哪一种队列、模型服务或存储系统。

因此，本文不把页面文案当作内部实现说明，而是把它当作产品契约的可观察部分：哪些输入被公开承诺，哪些状态能够被用户看到，哪些能力仍然需要进一步验证。

## 从控件反推输入层：视觉任务不是一个 prompt 字符串

普通文本模型的调用经常被抽象成“提交一段 prompt，等待一段文本”。视觉生成工作台明显不同。AXAI Studio 把一次生图任务拆成至少四组输入：文本提示词、参考图、输出比例和质量等级。参考图最多可上传 5 张，页面说明它们可用于引导构图、人物或画风；如果不上传，则退化为纯文本生成。这个设计说明工作台需要在提交前区分“没有图片”和“图片上传失败”两种状态，不能把二者都静默当成普通文生图。

视频任务的输入维度更复杂。页面列出了运镜提示词、起始首帧、结束尾帧、主体一致性参考图，以及由大模型扩写镜头动态细节的选项。首帧和尾帧并不是普通参考图的同义词：首帧约束视频开始时的画面，尾帧约束结束时的画面，而主体一致性参考图承担的是跨镜头保持对象特征的作用。产品界面把它们分开，至少在交互层面承认了这三类约束的语义不同。

工程上，这意味着请求对象不应设计成一个不断追加字段的“大而全参数包”。更可靠的做法是先按任务类型建立输入契约，再对每类任务做独立校验。例如：

```json
{
  "task": "image",
  "prompt": "一座雨后的未来城市",
  "referenceImages": [],
  "aspectRatio": "16:9",
  "quality": "1080p"
}
```

视频请求则应明确区分时长、清晰度、比例、首帧、尾帧和主体参考图。即使后端最终把它们转换成某个模型的统一格式，前端也不应在用户未选择时伪造默认图片或默认的时序约束。输入越丰富，越需要在提交前给出可解释的错误：超过图片数量、时长不在页面列出的范围、首尾帧格式不兼容，均应成为明确失败，而不是进入队列后返回一个含糊的“生成失败”。

## 点数不是展示文案，而是一次任务的账本

页面同时展示了不同生成方式的点数消耗：生图区域出现按张计费和高清输出的消耗提示，视频区域则按照秒数与版本区分成本，并给出 5 秒、10 秒、15 秒乃至更长时长的选项。无论这些数值最终如何调整，产品结构已经表明：视觉任务的成本不是固定的请求费用，而是由任务类型、时长、质量和可能的模型档位共同决定。

这会带来一个容易被忽略的账本问题。用户点击“生成”时，系统究竟何时扣点？如果请求在排队前失败，是否扣除？如果任务进入渲染后超时，点数是否退回？如果用户重复点击按钮，是否产生两笔任务？页面材料没有给出这些规则，因此不能替平台宣称答案，但工程设计必须先把问题写出来。

一个可验证的最小账本至少要记录四个事件：任务创建、额度预扣、渲染成功或失败、最终结算。额度预扣可以防止任务进入队列后余额不足；最终结算则允许平台在失败时回滚，或在实际消耗与预估消耗不同的情况下补扣差额。每个事件都需要任务 ID、用户或会话标识、点数变化、原因和时间戳。这样，用户看到“消耗 5 点”时，后台才能回答这 5 点对应哪次任务，而不是只在页面上减少一个数字。

还需要把幂等性放在提交入口。客户端重试、网络抖动和用户连续点击都会产生重复请求。可以让客户端生成幂等键，也可以由服务端根据用户、输入摘要和短时间窗口建立去重策略；两者都比单纯禁用按钮可靠。禁用按钮只能改善正常操作，无法解决浏览器重发、代理重试或移动网络切换造成的重复提交。

## 异步渲染的核心是状态，而不是“等待十几秒”

页面文案给出了约 10 到 15 秒的图像渲染体验描述，并展示“正在渲染”“解析意图与构图权重”等过程提示。但这类提示不能直接证明后端已经提供了真实进度。工程上必须区分“状态事件”和“装饰性文案”：如果系统没有可计算的阶段进度，就不应把旋转动画包装成百分比。

视觉生成更适合使用明确的任务状态机，例如：`created`、`validated`、`queued`、`running`、`succeeded`、`failed`、`expired`。客户端提交后拿到任务 ID，随后通过轮询、服务器推送或其他明确机制读取状态。每次状态变更都应携带可供排障的信息：失败类型、是否可重试、结果地址是否已经生成，以及最终计费状态。

最小验证可以从命令行开始。材料只证明 AXAI API 的根入口返回运行状态，因此可以先检查入口，而不能据此推断某个模型接口可用：

```bash
curl -i https://api.vicub.com/v1
```

预期只能验证 HTTP 响应和页面材料中出现的 JSON 字段，例如 `message` 与 `status`。下一步若要验证实际 API 契约，应在拥有合法授权令牌的前提下，依据官方接口文档发送一个最小请求，并记录 HTTP 状态码、响应结构、任务 ID、错误码和耗时。不能把社区帖子中未公开的凭据、隐藏接口或点赞后可见内容当作稳定的测试依据。

验证视频任务时，应分别测试纯文本、仅首帧、首尾帧同时存在、主体参考图达到上限，以及非法时长。每个用例都要检查三件事：请求是否在入口被拒绝，额度是否发生变化，任务是否留下可查询的终态。只有比较这些结果，才能判断验证失败来自输入校验、额度系统、队列、模型服务还是结果分发。

## 本地历史与云端结果：不要混成一个存储层

AXAI Studio 页面明确展示“工作台历史作品保存在本地浏览器”，并提供清空历史、复制提示词、复制链接和下载原图等操作。这个设计的直接好处是减少服务端对作品历史的承诺：浏览器可以保存用户用于回顾的索引或结果信息，用户也可以主动清理本地记录。但它同时制造了一个边界：本地历史不是云端备份。

工程实现应明确区分三类数据。第一类是任务输入，例如提示词、参数和参考图；第二类是任务状态，例如任务 ID、状态与错误信息；第三类是生成结果，例如图片或视频地址、过期时间和下载权限。若浏览器只保存第三类的临时链接，用户清空站点数据后可能无法恢复；若保存了参考图或生成结果，则需要向用户说明数据所在位置和清理方式。页面能够证明“本地浏览器历史”的产品意图，但不能证明浏览器保存了哪些具体字段，因此这部分仍应通过隐私说明或源码进一步核验。

复制链接也不等于永久分享。一个工程上更安全的默认值是短期、只读、可撤销的结果链接；如果结果需要长期访问，则应明确对象归属、过期策略和删除入口。下载原图则应校验任务所有权，避免仅凭一个可猜测的结果 ID 获取他人作品。

## API 入口与网页工作台必须分开验收

页面宣传“兼容 OpenAI 格式，可在 NextChat、LobeChat 等客户端接入”，API 根入口则显示网关正在运行。这足以说明产品试图同时覆盖网页工作台和程序化调用，但不能自动推出“所有视觉模型都支持同一套 OpenAI 请求格式”。文本对话、图片生成和视频生成在输入结构、同步方式、结果格式上都可能不同。

因此，接入方应建立一份自己的契约检查表：

1. 根入口是否返回稳定的健康检查结果；
2. 授权失败是否返回明确状态码，而不是伪装成模型错误；
3. 模型列表是否与实际可调用能力一致；
4. 图片任务是否返回可追踪的任务标识或明确结果；
5. 视频任务是否支持异步查询，超时后如何继续获取结果；
6. 额度不足、参数非法和上游失败是否能区分；
7. 结果链接是否有过期、权限和删除规则；
8. 重试同一个请求是否会重复扣费。

这份清单的价值在于把“入口在线”与“能力可用”分开。`status: true` 只能作为第一层可达性信号，不能替代授权验证、参数验证、任务验证和结果验证。

## 结论：视觉工作台的竞争力来自可解释的失败

从 AXAI Studio 的公开页面可以看到，一套视觉生成产品已经不再只是一个 prompt 输入框，而是把图像参考、视频时序、主体一致性、画幅、质量、点数和历史操作组合在一起。真正复杂的地方也随之从“调用哪个模型”转移到“如何把多维输入变成可验证任务”。

本文能够确认的是：AXAI API 入口公开返回运行状态，AXAI Studio 公开展示了多种视觉任务输入、点数提示、浏览器本地历史和 API 接入方向。本文不能据此确认其内部队列、计费落账、数据保留周期、具体模型接口或失败退款规则。对使用者而言，这种证据边界本身就是结论：在没有官方契约和授权测试之前，不要把页面上的能力清单当成生产 SLA。

一个值得复用的判断标准是：好的视觉工作台不是让所有选项都能点击，而是让每一次拒绝都可解释、每一次扣费都可追踪、每一个结果都能验证。只要这三点没有建立，再多模型名称和更大的并发宣传，也只是把不确定性从界面移动到了用户的账单与排障过程里。
