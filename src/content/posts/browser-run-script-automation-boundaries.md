浏览器自动化最容易被误解成“把一段 Playwright 代码发过去，然后拿回结果”。这种理解只覆盖了最短路径，却忽略了真正决定系统可靠性的几个问题：脚本在哪个执行环境中运行，浏览器会话是否持续，后续请求如何定位页面，脚本结束后资源是否释放，以及失败时究竟应该重试哪一层。

Cloudflare 在 2026 年 11 月 20 日发布的 Browser Run 更新，为这类问题提供了一个值得研究的接口模型：新增 `/script` 端点，可以在一次 API 请求中提交 JavaScript 函数，并使用 Playwright、Puppeteer 或原始 Chrome DevTools Protocol 连接浏览器执行。官方描述显示，脚本会在一个隔离的 Worker 中运行，Worker 连接到浏览器会话，因此调用方不需要另外部署 Worker。这是本文唯一采用的产品事实来源；社区帖子只能帮助我们发现“浏览器自动化是否值得关注”，不能替代官方 API 证据。

## 一次请求背后并不是一次性浏览器

最基本的调用可以写成下面这样：

```bash
curl -i -X POST \
  "https://api.cloudflare.com/client/v4/accounts/<accountId>/browser-run/script" \
  -H "Authorization: Bearer <apiToken>" \
  -H "Content-Type: application/json" \
  -d '{
    "code": "async ({ page }) => { await page.goto(\"https://example.com\"); return { title: await page.title() }; }",
    "library": "playwright"
  }'
```

请求体里的 `code` 是一个异步 JavaScript 函数，示例中通过 `page.goto` 打开网页，再返回页面标题。接口成功时返回一个包含 `success` 与 `result` 的对象。这个返回结构的重要性不在于字段数量，而在于它把“浏览器动作”和“业务结果”分离了：浏览器只是执行载体，真正应该进入流水线的是结构化结果，而不是整页 HTML 或一段无法解析的日志。

同时，响应头会返回 `cf-browser-session-id` 和 `cf-browser-target-id`，分别代表浏览器会话和当前页面目标。这里已经暴露出一个关键架构事实：脚本执行完成，并不代表浏览器会话已经结束。官方说明明确指出，`/script` 或 `/devtools/browser` 创建的会话不会在脚本运行后自动关闭，而是持续到空闲超时，或者由调用方显式关闭。

因此，正确的抽象不是：

```text
HTTP 请求 -> 打开浏览器 -> 执行脚本 -> 浏览器消失
```

而更接近：

```text
HTTP 请求
  -> 获取或连接浏览器会话
  -> 在指定页面目标上运行函数
  -> 返回业务结果与会话定位信息
  -> 由调用方决定复用、扩展或关闭会话
```

这一区别直接影响成本、并发和故障恢复。一个只读取标题的短脚本，可以把会话看成一次任务的临时资源；一个需要登录、跳转、截图或多页面协作的流程，则应该把会话 ID 当成受控状态，并为它设计过期、关闭和重试策略。

## 会话、目标与脚本不是同一个层次

Browser Run 的接口模型至少包含三个层次。

第一层是脚本。脚本描述本次要执行的浏览器动作，例如打开 URL、读取标题、填写表单或返回页面中的结构化字段。脚本结束后，结果可以被上游任务继续处理。

第二层是会话。会话代表浏览器运行上下文。官方更新说明支持在脚本请求的查询字符串中传递 `keep_alive`、`recording` 和 `lab` 等会话启动选项。这里不应把它们理解成普通业务参数，而应视作“如何创建浏览器运行环境”的控制面配置。会话是否保持、是否录制以及是否使用实验能力，都会改变验收方式。

第三层是页面目标。一个浏览器会话可以包含不止一个页面，后续脚本可以通过 `targetId` 指定要操作的页面，也可以创建额外页面，以便在同一会话中并发执行。于是，“浏览器已经打开”并不能证明“脚本操作了正确页面”。当流程包含新窗口、弹窗或多标签页时，必须把目标 ID 记录到任务状态中，而不能依赖当前页面的隐式顺序。

可以用以下方式组织一个最小的任务状态：

```json
{
  "sessionId": "<session-id>",
  "targetId": "<target-id>",
  "step": "read-title",
  "result": {
    "title": "Example Domain"
  },
  "expiresAt": "<application-managed-deadline>"
}
```

其中 `expiresAt` 不是 Browser Run 返回的固定字段，而是调用方自己的治理字段。这样做的目的，是防止会话 ID 在队列、数据库或日志中无限存留。若业务只需要一次结果，就应在拿到结果后关闭会话；若业务需要连续步骤，就应限制会话的最大生命周期，并在每一步验证目标仍然存在。

## 从单步调用开始做可复现验收

验证浏览器自动化，不能只检查 HTTP 状态码。一个成功的 API 响应可能只代表脚本被执行，并不代表脚本读到了正确页面，更不代表会话已被正确回收。

第一步，验证返回结构。最小验收应检查：

```bash
curl -sS -D /tmp/browser-run.headers \
  -o /tmp/browser-run.body \
  -X POST \
  "https://api.cloudflare.com/client/v4/accounts/<accountId>/browser-run/script" \
  -H "Authorization: Bearer <apiToken>" \
  -H "Content-Type: application/json" \
  -d '{"code":"async ({ page }) => ({ title: await page.title() })","library":"playwright"}'

cat /tmp/browser-run.headers
cat /tmp/browser-run.body
```

验收时应同时确认三件事：响应成功标志为真；`result` 中包含预期的业务字段；响应头中存在会话和目标定位信息。若只解析 JSON 而丢弃响应头，后续会话复用就失去了必要的控制信息。

第二步，验证结果来源。一个更稳妥的脚本不应只返回标题，而可以返回页面 URL、标题和一个明确的页面标记：

```javascript
async ({ page }) => {
  await page.goto("https://example.com");
  return {
    url: page.url(),
    title: await page.title(),
    marker: await page.locator("h1").textContent()
  };
}
```

这样能区分“请求成功但页面未按预期加载”和“页面加载正确但业务字段为空”。如果页面内容是动态生成的，还要为等待条件设定明确规则，避免把网络连接建立成功误判为页面业务就绪。

第三步，验证清理。官方说明给出了关闭会话的路径：可以调用 `DELETE /devtools/browser/<sessionId>`，也可以在 Worker 的浏览器绑定中调用 `browser.close()`。如果没有主动关闭，会话会继续存在，直到达到空闲超时。对于批处理、定时任务和失败重试，关闭动作应该进入 finally 语义，而不是只写在成功分支：

```text
创建会话
  -> 执行脚本
  -> 保存结构化结果
  -> 无论成功或失败，都尝试关闭会话
```

这不是为了追求“每个请求只用一个连接”，而是为了明确资源所有权。谁创建会话，谁负责决定会话何时结束；如果会话被交给另一个异步任务，则必须把所有权转移记录下来。

## 后续脚本与并发页面的取舍

当一个流程包含多个步骤时，重新创建浏览器会话通常会丢失上下文；但无条件复用会话，也会让状态污染和并发冲突变得难以排查。官方接口允许对已有会话调用 `/script/<sessionId>` 执行后续脚本，并且可以传入 `targetId` 连接到特定页面。

适合复用会话的场景，是步骤之间确实共享浏览器状态，例如前一步打开页面，后一步读取同一页面中的结果。此时应把每一步写成可验证的转换：

```text
target A: 已打开入口页
  -> 脚本 1: 跳转并返回 URL
  -> 验证 URL
  -> 脚本 2: 读取业务字段
  -> 验证字段存在
  -> 关闭会话
```

不适合复用的场景，是两个互不相关的任务共用一个长期会话。这样做会把 Cookie、页面目标、导航历史和失败状态混在一起，最终即使脚本代码没有变化，任务结果也会不稳定。工程上更安全的默认值是：不同业务任务使用不同会话；同一任务内部才复用会话。

同一会话中的多页面并发也有边界。官方说明提到可以创建额外页面，并在一个会话中并发运行脚本。这解决的是浏览器资源共享问题，不等于业务操作天然线程安全。两个脚本如果同时修改同一个页面、依赖同一个弹窗，或者竞争同一个目标 ID，结果仍然可能互相影响。因此并发设计应至少明确页面粒度：一个页面一个责任，跨页面共享的数据通过脚本返回值或外部任务状态传递，而不是依赖隐式的当前页。

## Worker、控制台与 API 是三种入口

同一能力存在三种调用入口：外部 API、Worker 浏览器绑定和 Cloudflare 控制台中的 Script Studio。API 适合纳入已有的任务系统和 CI 流程；Worker 绑定适合把脚本调用放在 Cloudflare 运行环境中，并且官方说明中不需要 API token；Script Studio 则适合人工编写和运行脚本。

三者不应被当作完全等价的部署方式。API 调用需要处理令牌保护、请求超时、响应头保存和会话关闭；Worker 调用需要处理绑定配置以及 Worker 本身的错误传播；控制台操作更适合探索和调试，不应自动等同于可重复的生产流程。一个脚本在 Script Studio 中能运行，只能证明脚本逻辑具有探索价值，不能证明它已经具备版本控制、权限隔离、审计和回滚能力。

令牌也不应出现在脚本源码、前端页面或普通调试输出中。上面的 curl 只使用占位符 `<apiToken>`，实际接入时应由运行环境注入，并限制令牌可以访问的账户范围。浏览器脚本本身还可能接触登录态、个人数据或业务后台，因此“脚本能打开网页”与“脚本被允许读取该网页”是两个独立的授权问题。

## 失败边界：哪些现象不能靠重试解决

第一类是脚本级失败。例如选择器不存在、页面结构变化、跳转后 URL 不符合预期。这类错误应返回可诊断的业务失败信息，并优先修正脚本或页面契约，而不是盲目重复请求。

第二类是目标级失败。会话仍然存在，但目标页面已经关闭、目标 ID 错误或脚本连接到了错误页面。此时重试同一个 `targetId` 可能永远失败，正确动作是重新获取当前会话中的页面信息，必要时创建新页面。

第三类是会话级失败。会话可能因为空闲超时而结束，或者被显式关闭。后续脚本不能假设旧的会话 ID 永久有效，应把“会话不可用”视为需要重新建立上下文的状态，而不是把它伪装成一次普通页面错误。

第四类是入口差异。官方说明指出，脚本和页面信息会通过响应头返回，但 Kitesurf 运行方式是例外。也就是说，不能编写一个完全不区分浏览器模式的响应解析器，然后把缺少这些头部一律判断为 API 损坏。验收代码应该先识别运行模式，再按该模式的契约检查返回值。

第五类是资源未关闭。脚本已经返回成功，但浏览器仍然保持运行，这不是业务成功的充分条件。监控中至少要区分“脚本结果成功”和“会话已回收”两个事件，否则会把资源泄漏隐藏在绿色任务状态之后。

## 一份可落地的验收清单

在把 `/script` 接入自动化平台前，可以按以下顺序验收：

1. 使用一个公开、稳定、无登录要求的页面验证最小脚本，确认 `success`、`result`、会话 ID 和目标 ID 的处理方式。
2. 让脚本返回 URL、标题和页面标记，确认结果确实来自目标页面，而不是只确认 HTTP 成功。
3. 保存响应头中的会话和目标信息，使用已有会话执行第二个脚本，确认状态复用符合预期。
4. 在同一会话中创建额外页面时，验证每个页面都有明确的目标定位，不依赖当前页面顺序。
5. 分别测试脚本失败、目标失效、会话关闭和空闲超时，并为每种情况定义不同的恢复动作。
6. 验证成功和失败路径都会执行会话清理，确认没有把浏览器关闭只放在成功分支。
7. 检查 API 令牌不出现在源码、前端或普通日志中，并限制调用方权限。
8. 对脚本版本、库选择、会话选项和业务结果建立可追踪记录，确保一次失败可以还原当时执行的契约。

## 结论：浏览器自动化的核心是状态治理

`/script` 的价值不只是省去部署一个 Worker。更重要的变化，是把浏览器动作包装成了可被服务端调用、返回结构化结果并继续复用会话的执行单元。但它同时把状态治理责任交给了调用方：会话需要生命周期，页面需要目标定位，脚本需要结果契约，失败需要分层恢复，资源需要显式关闭。

因此，最小可用方案可以是一条 curl 命令；可靠的工程方案则至少需要一份任务状态、一套响应头解析、一个 finally 级别的清理流程，以及针对脚本、目标和会话的不同验收标准。浏览器自动化真正难的地方，从来不是把鼠标点击搬到 API 中，而是证明每一步操作发生在正确的会话、正确的页面和正确的生命周期里。
