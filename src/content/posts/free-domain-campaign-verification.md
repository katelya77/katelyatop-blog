## 先把“免费”拆成几个不同命题

“免费域名”看起来像一个简单结论，实际上至少包含五个不同问题：活动是否真实存在、注册是否真的免首年费用、域名是否登记在自己的账户下、域名是否能够被自己控制 DNS，以及第二年是否仍然可以低成本续费。社区帖子通常只解决第一个问题，甚至只是提供一个待核验的线索。

本批材料中的 S3 是 NodeLoc 社区帖子，描述了 my.id、biz.id 和 web.id 三种后缀、每个账户一个、第一年免费、支持 Cloudflare，以及一个活动截止时间。它的证据等级是社区发现，不足以单独证明服务商的完整条款。S4 则指向 IDwebhost 的活动页面，页面内容包括登录入口、域名搜索、注册入口和服务条款提示，但材料没有展示具体结算结果、注册成功页面、域名控制台或 DNS 委派结果。因此，较稳妥的结论不是“现在一定能免费拿到域名”，而是“存在一个应当在截止时间前核验的活动入口”。

这一区分很重要。把宣传文案当成资产事实，容易把“可申请”误写成“已注册”，把“首年免费”误写成“永久免费”，把“支持 Cloudflare”误写成“已经接入 Cloudflare”。技术编辑应当把这些命题拆开，逐项寻找证据。

## 活动链路其实是一条状态机

可以把一次域名活动抽象成下面的状态流：

```text
发现线索
  -> 打开官方入口
  -> 账户登录或注册
  -> 搜索域名
  -> 输入优惠码或满足积分条件
  -> 进入结算
  -> 完成注册
  -> 在控制台看到域名
  -> 修改名称服务器
  -> 在权威 DNS 平台确认委派
  -> 等待解析生效
  -> 记录续费价格和到期时间
```

每一步的成功，都不能替代下一步的成功。

例如，优惠码被接受，只能说明促销规则在当前页面被识别；结算金额显示为零，也不能说明域名已经写入注册局；控制台显示域名，才初步说明账户与域名之间建立了关系；DNS 平台显示已接入，才说明名称服务器配置至少完成了一部分；从公共 DNS 查询到预期记录，才接近“可用”。

这也是免费资源最容易被误判的地方：用户往往只截取最容易展示的一张截图。截图适合证明页面当时显示了什么，不适合证明域名归属、委派状态和未来续费义务。一个可靠记录应当包含时间、账户状态、订单编号或域名列表、当前到期日，以及 DNS 查询结果。

## 先验证入口，再验证结算

打开活动页面时，第一步不是立即注册，而是确认入口是否与社区帖子指向同一个服务商。S4 的页面标题和内容显示为 IDwebhost 的 Domain Gratis 页面，并提供登录、Google 登录、域名搜索和服务条款入口。这个材料能支持“官方活动页面存在”的判断，但不能替页面没有展示的条款背书。

实际操作可以按以下顺序进行：

```bash
# 记录最终跳转地址，避免只保存短链
curl -I -L 'https://t.co/eE6vLjJNBj'

# 查询目标域名的基础注册状态，实际域名替换为自己的候选名称
whois example.my.id

# 保存当前 DNS 委派信息
 dig +short NS example.my.id
```

如果环境中没有 `dig`，可以使用公共 DNS 查询服务，但应记录查询时间和查询服务器。命令本身不是“官方证明”，它们的作用是把网页上不可复核的说法转化为可重复检查的结果。

结算页面至少需要核对四项：域名后缀是否符合活动范围、优惠码是否实际被接受、价格减免发生在注册费还是其他项目、订单是否存在自动续费或附加服务。尤其要区分“首年注册费为零”和“订单总额为零”。域名保护、邮箱、托管、税费或其他产品可能具有单独的价格；材料没有给出这些项目的具体规则，因此不能替活动做更强的价格承诺。

## “支持 Cloudflare”不等于 DNS 已经托管

S3 使用了“支持 Cloudflare”的表述，但这至少有三种可能含义：服务商允许把名称服务器改为 Cloudflare；Cloudflare 能够识别该域名后缀；或者活动页面提供了某种接入指引。它们不是同一个技术事实。

域名接入 Cloudflare 的核心不是在 Cloudflare 面板里添加站点，而是最终让注册商侧的名称服务器与 Cloudflare 分配的名称服务器一致。一个最小验证流程如下：

```bash
# 查看父域和目标域的 NS 记录
 dig NS example.my.id +short
 dig NS example.my.id @1.1.1.1 +short
 dig NS example.my.id @8.8.8.8 +short

# 查看网站记录，确认解析结果是否符合预期
 dig A example.my.id +short
 dig AAAA example.my.id +short
 dig CNAME www.example.my.id +short
```

如果不同递归解析器返回的结果不一致，可能处于缓存更新阶段，也可能是委派配置本身不完整。不要因为 Cloudflare 控制台显示“已添加”就直接发布业务；还需要确认注册商控制台中的名称服务器已经保存，并且公共 DNS 查询能够看到一致结果。

对 DNS 记录还要做反向检查。若目标是将站点指向某台服务器，应确认 A 或 AAAA 记录是否指向预期地址；若使用 CNAME，应确认目标名称和代理模式是否符合应用需求。域名“能解析”只说明 DNS 层有响应，不代表 TLS 证书、HTTP 服务、邮件收发和应用访问都已经完成。

## 账号、积分和优惠码是不同的信任边界

S1 与 S3 都体现了社区活动常见的交付方式：点赞后查看内容、通过链接获得积分或使用优惠码。这里至少存在三类风险边界。

第一是账号边界。活动可能要求注册服务商账户，也可能要求社区账户满足某种条件。不要把社区帖子中的登录信息、代注册承诺或共享账号当成自己的资产。S2 中“免费账号”的材料尤其说明了共享凭据存在已被使用的情况，但它与域名活动不是同一服务，也不能作为活动成功率或安全性的证据。

第二是优惠码边界。优惠码可能有适用后缀、账户限制、时间限制和使用次数限制。服务商页面接受代码，只说明代码格式或规则匹配，不说明域名一定可注册。真正的结果应以订单明细和账户中的域名状态为准。

第三是积分边界。社区积分不是注册商余额，也不是域名所有权。即使通过活动链接获得积分，也要确认积分最终进入哪个账户、是否有过期时间、是否能抵扣注册费，以及是否会要求额外验证。没有这些一手条款，就只能把积分视为促销流程中的临时条件。

工程上，最安全的做法是使用自己的邮箱和独立密码，不复用主邮箱密码，不把验证码交给第三方，不下载所谓“自动领取”程序。若活动要求授权第三方账户，应先检查授权范围，完成后撤销不再使用的授权。免费并不意味着可以降低凭据保护等级。

## 到期日比首年价格更值得记录

域名活动最容易掩盖的成本是第二年。首年价格为零，不能推导出续费价格；社区帖子也没有提供完整的续费条款。因此，在注册完成后，应立即建立一个最小资产记录：

```text
域名：example.my.id
注册账户：自己的服务商账户
注册日期：YYYY-MM-DD
到期日期：YYYY-MM-DD
注册商：页面显示的服务商名称
当前名称服务器：ns1.example / ns2.example
DNS 托管：Cloudflare 或其他平台
首年订单：订单号、金额、优惠码
续费信息：以控制台和官方条款为准
提醒时间：到期前 30 天、7 天
```

如果控制台没有显示到期日，或者域名列表中没有出现该名称，就不要把结算页面截图当成完成证明。若到期日已经出现，还要检查自动续费开关和付款方式。没有明确续费意愿时，避免把生产业务、邮件地址、登录回调或长期品牌绑定到活动域名上。

对于测试项目，可以把域名放在低风险环境中，设置独立的监控和迁移方案。对于生产服务，应该先确认转移政策、DNS 修改权限、到期宽限期和续费价格，再决定是否依赖该域名。材料没有提供这些规则时，文章只能提出检查项，不能替服务商作保证。

## 一份可审计的验收清单

完成活动核验后，可以用下面的清单判断证据是否闭环：

1. 官方入口可打开，且最终域名与服务商身份一致。
2. 候选后缀、活动时间和适用条件被页面或官方条款确认。
3. 优惠码或积分在自己的账户中使用，结算明细显示实际减免项目。
4. 订单或注册结果可在自己的控制台重复查看。
5. 域名到期日期、注册商和名称服务器已经记录。
6. 注册商侧的 DNS 委派与预期平台一致。
7. 至少使用两个递归 DNS 解析器检查 NS 和业务记录。
8. 网站、证书、邮件等上层功能分别验证，不把 DNS 成功当成服务成功。
9. 续费价格、自动续费和提醒时间已经明确；未知项必须标记为未知。
10. 所有截图、订单号和查询结果带有时间，便于后续复核。

这份清单的价值不在于让所有活动都变得可靠，而在于明确什么时候应该停止投入。若活动只能证明“有人发过帖子”，却无法证明账户、订单和控制台状态，那么它仍然只是线索；若域名已经注册但 DNS 权限和续费条件不明，那么它是一个短期测试资源，而不是稳定资产。

## 原创结论：免费域名真正卖的是验证成本

从 S3 的社区活动描述到 S4 的官方入口，可以确认的是：存在一个值得核验的限时域名活动线索，以及一个对应的服务商页面。不能从现有材料直接推出注册成功率、完整价格、续费金额、Cloudflare 委派结果或长期可用性。

因此，这类活动的核心工程问题不是“如何更快领取”，而是“如何用最少的成本确认自己到底获得了什么”。把活动看成状态机，把网页、订单、控制台和 DNS 查询分成不同证据层，再为到期和迁移保留退路，才能避免免费资源变成隐性运维负担。

对个人实验项目而言，零成本域名可以是短期入口；对正式服务而言，真正需要购买的往往不是注册费，而是可预测的续费、清晰的控制权、可迁移的 DNS 和可审计的账户记录。只要其中一项仍停留在社区截图或口头承诺层面，就不应把它写进生产架构的前提条件。
