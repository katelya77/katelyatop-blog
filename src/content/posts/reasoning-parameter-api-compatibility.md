## 先把证据等级说清楚

这篇文章讨论的不是某个参数“应该如何工作”，而是如何处理一个已经出现的兼容性信号。官方 llama.cpp b12431 发布页记录了一条服务端问题：模板拒绝 `reasoning_effort` 等级，并返回 HTTP 400。这个证据足以证明存在一条具体的失败路径，但不足以证明所有模型、所有模板、所有构建方式都会复现相同结果。

因此，本文把结论分成三层：第一层是发布页明确记录的事实；第二层是根据 HTTP 请求链路建立的工程推理；第三层是需要在目标构建、目标模型和目标模板上自行验证的假设。另一个官方发布页 vLLM v0.34.0 只能说明该项目存在一个对应版本发布，不能被用来推导 llama.cpp 的参数行为，也不能作为“所有 OpenAI 兼容服务都支持该参数”的证据。

这一区分很重要。AI 推理服务通常会模仿相同的请求格式，但“字段名称相同”与“字段语义、允许值、处理阶段相同”是两件事。

## 一个请求为什么会在模板阶段失败

把一次聊天请求简化，可以看成四个连续阶段：

```text
客户端构造 JSON
        |
        v
HTTP 服务解析请求体
        |
        v
服务端校验参数与模型能力
        |
        v
模板把消息和控制参数转换为模型输入
        |
        v
推理运行时生成结果
```

很多兼容性排查只观察第一步：客户端成功把 `reasoning_effort` 放进 JSON，或者 HTTP 客户端没有报连接错误，于是认为参数已生效。实际上，400 表示请求在进入正常推理结果之前就被拒绝了。拒绝点可能是请求 schema、参数枚举、模型模板，或者模板所依赖的运行时变量。

`reasoning_effort` 这个名字尤其容易制造错觉。它看起来像一个抽象层参数，仿佛服务端只需把它转换成“思考更多”或“思考更少”。但对本地推理服务而言，参数最终可能影响提示词结构、特殊标记、停止条件、采样策略或模型特定的控制 token。若当前模板没有定义对应变量，或者只接受某些等级，服务端就不能安全地把它继续传给后续阶段。

这也是为什么“兼容 OpenAI API”不能直接等价于“兼容 OpenAI 的全部参数”。兼容通常分为三层：路径和方法兼容、字段形状兼容、字段语义兼容。第一层解决能不能发出去，第二层解决能不能被解析，第三层才解决服务是否按预期使用了它。b12431 页面记录的 400 错误，恰好提醒我们：即使前两层看起来相似，第三层仍可能失败。

## 用最小请求把失败固定下来

排查时不要一开始就带上完整业务提示词、工具定义、长上下文和流式选项。先建立一个最小请求，减少变量数量。下面的地址、模型名和端口只是占位符，应替换成自己的测试服务：

```bash
export BASE_URL=http://127.0.0.1:8080
export MODEL_ID=test-model

curl -sS -D /tmp/headers.txt \
  -H 'Content-Type: application/json' \
  "$BASE_URL/v1/chat/completions" \
  -d "$(cat <<JSON
{
  "model": "$MODEL_ID",
  "messages": [{"role": "user", "content": "用一句话回答：1+1 等于多少？"}],
  "reasoning_effort": "low",
  "stream": false
}
JSON
)" \
  -o /tmp/body.json

printf '%s\n' '--- headers ---'
cat /tmp/headers.txt
printf '%s\n' '--- body ---'
cat /tmp/body.json
```

这个命令的目的不是证明 `low` 是合法值，而是把它作为一个待验证输入。第一项检查是 HTTP 状态码；第二项检查是错误正文是否明确指出字段、等级或模板；第三项检查是服务日志中是否出现对应请求。不要只看客户端 SDK 抛出的异常，因为 SDK 经常会把服务端返回的具体原因压缩成一个通用错误。

随后进行对照实验：只删除该字段，其余内容保持一致。

```bash
jq 'del(.reasoning_effort)' /tmp/request.json > /tmp/request-without-reasoning.json
curl -sS -w '\nstatus=%{http_code}\n' \
  -H 'Content-Type: application/json' \
  "$BASE_URL/v1/chat/completions" \
  --data-binary @/tmp/request-without-reasoning.json
```

如果带字段的请求返回 400，而删除字段后请求能够进入正常响应，这只能证明该字段与失败路径相关，不能证明字段一定是唯一原因。还应分别测试不同等级、不同模型和不同模板。若所有等级都失败，问题更可能位于字段未被当前接口或模板支持；若只有某些等级失败，则应记录实际允许集合，而不是把失败等级简单改成另一个值后继续上线。

## 把“支持”拆成可验收的契约

建议为每个可选参数建立一张小型契约表，但不要把它当成静态参数表。真正需要记录的是验证结果：

| 项目 | 要回答的问题 | 证据形式 |
| --- | --- | --- |
| 字段位置 | 参数位于顶层、消息内，还是模板变量中？ | 原始 JSON 与服务日志 |
| 值域 | 接受字符串、整数，还是有限枚举？ | 正常请求与非法值请求 |
| 作用阶段 | 影响请求校验、模板渲染，还是采样？ | 状态码、日志、输出差异 |
| 适用范围 | 所有模型都可用，还是依赖模板？ | 多模型或多模板矩阵 |
| 失败形式 | 返回 400、忽略字段，还是降级？ | 原始响应正文 |
| 版本范围 | 哪个构建首次或当前确认支持？ | 固定版本与构建信息 |

其中“忽略字段”是最危险的一种结果。返回 200 并不代表参数生效；服务可能只是丢弃了未知字段。要验证语义，至少需要一个可观察的行为差异，或者服务端明确返回已采用的配置。对于推理强度这类可能影响延迟、输出结构和成本的参数，静默忽略比明确返回 400 更难发现，也更容易造成错误结论。

实际验收可以采用三组测试：

1. **正向测试**：发送文档或实现明确允许的值，确认请求成功，并记录响应与日志。
2. **边界测试**：发送空字符串、未知等级、错误类型和大小写变体，确认服务不会把非法输入当成合法配置。
3. **缺省测试**：删除参数，确认默认行为稳定，并明确客户端是否把“未提供”与“低等级”混为一谈。

测试结果应与模型名称、模板名称、服务构建标识、启动参数和请求体一起保存。只保存“返回 200”没有复现价值，因为同一服务更换模型文件或模板后，参数处理路径可能已经不同。

## 客户端降级不能伪装成参数生效

面对 400，最简单的做法是在客户端捕获错误后删除 `reasoning_effort` 再重试。这种策略有时有价值，但必须明确它的语义：重试成功只说明“无该参数的请求可用”，不说明服务执行了客户端要求的推理等级。

更可靠的降级策略应满足三个条件。第一，只有在错误明确指向未知字段、非法枚举或模板不接受该字段时才降级；网络超时、鉴权失败、模型不存在和服务过载不应被伪装成参数不支持。第二，降级必须写入结构化日志，例如记录 `requested_reasoning_effort=low`、`applied_reasoning_effort=default` 和 `fallback_reason=unsupported_by_template`。第三，调用方必须能选择“严格模式”：严格模式遇到不支持就失败，兼容模式才允许删除字段重试。

可以把策略写成如下伪代码：

```text
发送带 reasoning_effort 的请求
如果成功：记录 requested 与 applied 的确认信息
如果 400 且错误明确指向该字段：
    严格模式：返回不支持错误
    兼容模式：删除字段后重试一次，并记录降级
否则：
    原样返回错误，不进行参数降级
```

重试次数也应限定为一次。无边界重试会放大请求量，尤其是在服务端对某个参数稳定返回 400 的情况下。若业务依赖该参数来控制质量、延迟或成本，就不应默认降级，而应把不支持视为部署配置错误。

## 版本升级要验证行为，不要只验证标签

b12431 的官方发布页记录了问题，但发布标签本身不是完整的兼容性合同。升级前后都应运行同一组请求，至少比较：状态码、错误正文、首 token 延迟、总耗时、输出是否出现异常控制标记，以及服务日志中的模板路径。若只是把镜像或二进制替换为新版本，却没有锁定模型和模板，测试结果无法归因。

一个可重复的升级检查清单如下：

```text
[ ] 记录旧版本构建标识
[ ] 记录模型文件与模板来源
[ ] 记录启动参数和 API 路径
[ ] 保存带 reasoning_effort 的原始请求
[ ] 保存不带该字段的对照请求
[ ] 测试合法、非法和缺省三类输入
[ ] 检查 HTTP 状态码与完整响应正文
[ ] 检查服务日志中的拒绝或忽略信息
[ ] 对比升级前后的结果与延迟
[ ] 明确是否允许客户端降级
[ ] 为失败设置回退版本或停用条件
```

这里的“停用条件”比“升级成功”更重要。例如，只要严格模式下仍然返回 400，或者服务返回 200 但日志表明字段被忽略，就不能把升级标记为“推理参数已支持”。发布说明可以作为起点，最终结论必须来自目标运行组合上的行为证据。

## 失败边界决定架构边界

这类问题的核心不是某一个参数名称，而是控制面和模型执行面的边界。客户端拥有意图，服务端拥有实际能力，模板决定意图能否被翻译成模型可理解的输入。三者之间若没有明确的能力发现或确认机制，客户端就只能依赖版本猜测，或者在失败后盲目降级。

工程上可以采取三种取舍。第一，**严格契约**：客户端只发送经过能力清单确认的字段，适合对质量和成本敏感的生产调用。第二，**显式适配器**：按服务和模板维护参数映射，适合需要同时接入多种本地推理后端的系统，但维护成本更高。第三，**兼容降级**：优先发送高级参数，遇到明确的不支持错误后去掉字段，适合交互式工具，但必须把“降级成功”与“参数生效”区分开。

我的结论是：推理服务的 API 兼容性，应以“可证明的语义”而不是“可发送的字段”作为验收单位。一个 400 错误虽然让请求失败，却比静默忽略更容易治理。对发布者而言，错误应说明字段、允许值和适用条件；对调用者而言，必须保存原始请求、原始响应和最终采用的配置。只有把这三份证据放在一起，版本升级和多后端接入才不会变成猜谜。
