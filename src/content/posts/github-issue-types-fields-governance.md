## 先区分“记录问题”和“管理问题”

很多团队已经在使用 Issue，却仍然依赖标题、标签和描述文本表达项目状态。一个标题可能写成“登录页偶发 500”，标签再补上 `bug`、`urgent`，描述中继续写“预计本周处理”。这种方式短期内足够灵活，但它把不同性质的信息混在了同一个文本容器里：Issue 是什么、优先级如何、何时开始、何时完成，往往只能靠人工阅读理解。

GitHub 在 2026 年 11 月 11 日宣布，Issue types 和 Issue fields 已经面向个人账户正式可用。官方说明中，个人账户可以在 Planning 下自定义 Issue 类型，最多创建 25 个类型；默认类型包括 Bug、Task 和 Feature。Issue fields 同样最多 25 个，默认字段包括 Priority、Effort、Start date 和 Target date，并支持文本、数字、日期、单选和多选字段。

这项变化的关键不在于“多了几个输入框”，而在于 Issue 从一段半结构化文本，变成了可以被项目视图、批量更新和程序接口共同消费的数据对象。它适合解决的是组织和排序问题，而不是替代需求分析、代码审查或发布验收。

## 类型、字段和标签分别承担什么职责

一个可维护的 Issue 模型，至少要把三类信息拆开。

第一类是对象类型。Bug、Task、Feature 不是优先级，也不是状态。它们回答的是“这条工作项属于哪一种工作”。类型应该保持稳定，因为类型一旦承担了过多含义，后续统计就会失真。例如把“紧急 Bug”单独设成一个类型，会把对象分类和处理优先级耦合在一起；更合理的模型是类型为 Bug，Priority 字段为 High。

第二类是可排序属性。Priority、Effort、Start date 和 Target date 都属于这一类。它们允许团队按照同一种规则比较不同 Issue。优先级通常用于决定先做什么，Effort 用于估算投入，日期用于表达计划窗口。字段的价值来自一致性：如果同一个团队有人把 Effort 填“3”，有人填“中等”，它就不能稳定支持筛选和汇总。

第三类是协作上下文。标签、里程碑和描述仍然有价值。标签适合表达跨类型的主题，例如 `frontend`、`docs` 或 `good-first-issue`；里程碑适合聚合交付目标；描述则保留背景、复现步骤、决策记录和验收条件。结构化字段不是要消灭这些内容，而是把适合机器比较的信息从长文本中抽出来。

官方公告还说明，字段可以固定到特定 Issue 类型，也可以让所有 Issue 使用。这个选择直接影响治理成本：只有 Bug 才需要“复现环境”的团队，可以把相关字段绑定到 Bug；所有工作项都需要 Priority 的团队，则应让它成为通用字段。字段越多不等于管理越精细，真正重要的是每个字段是否有明确的填写者、取值范围和使用场景。

## 一套可复现的配置检查清单

这项能力面向个人账户正式开放后，可以按下面的顺序建立最小模型。这里不假设任何自动迁移结果，也不把界面中的默认值当成适合所有项目的最终方案。

### 1. 先定义工作分类

进入个人账户设置中的 Planning 区域，检查 Issue types 页面。先保留 Bug、Task、Feature 这三个默认类型，再确认项目是否确实需要增加类型。只有当新类型能改变筛选、分工或统计时，才值得创建。

推荐先回答三个问题：

- 这个类型是否与其他类型有不同的生命周期或验收方式？
- 它是否会被项目视图单独筛选？
- 新类型消失后，团队是否会把它误填为另一个类型？

如果三个问题都无法给出明确答案，就不要增加类型。最多 25 个类型是平台能力边界，不是团队必须达到的配置目标。

### 2. 再定义字段语义

进入 Issue fields 页面，逐个核对字段名称、数据类型和适用范围。Priority 适合单选，Effort 可以使用数字或有限的单选集合，Start date 和 Target date 应使用日期类型。自由文本字段只有在内容确实无法枚举或数值化时才使用。

为每个字段写出一句内部定义，例如“Priority 表示当前交付排序，不表示严重性”。这句话看似简单，却能避免把 Priority、Severity、Impact 和 Effort 混成一个“重要程度”字段。

### 3. 决定字段绑定方式

对于只适用于某类工作的问题，把字段固定到对应 Issue type；对于跨类型的共同约束，让字段出现在所有相关 Issue 上。绑定关系应当服务于填写体验和数据质量，而不是追求模型复杂度。

### 4. 选择项目视图

官方说明指出，类型和字段可以在 Projects 中用于创建自定义视图和批量更新。验证时不要只检查某个 Issue 是否显示字段，而应创建一个按类型或字段筛选的视图，确认它能回答实际问题，例如“所有高优先级 Bug”或“目标日期在近期的 Feature”。

### 5. 建立空值和非法值检查

最后抽查一批旧 Issue 和新建 Issue：是否存在没有类型的对象，是否有字段被填入不符合定义的值，日期是否表达同一种含义，批量更新后是否影响了不该修改的工作项。结构化数据最常见的失败不是字段不存在，而是字段存在却没人相信它。

## 验证重点：查询结果能否支持决策

验证 Issue fields 不应停留在“页面上看到了一个下拉框”。至少要做四层检查。

第一层是覆盖率。随机抽取不同来源、不同阶段的 Issue，确认类型和关键字段是否都能填写。只验证新建 Issue，会遗漏历史数据和从其他入口进入的工作项。

第二层是语义一致性。让不同成员独立判断同一条 Issue 应该使用什么类型和字段值，再比较结果。如果分歧来自字段定义不清，继续增加选项只会放大问题。

第三层是视图有效性。用项目视图执行筛选和批量更新，检查结果是否与人工预期一致。一个字段只有在筛选结果能直接支持排期、分派或复盘时，才真正产生治理价值。

第四层是自动化可用性。官方公告明确提到，Issue types 和 fields 可以通过 REST API、GraphQL API 与 webhooks 进行程序化管理。验证自动化时，应先确定需要读取、写入还是监听事件，再为每个动作保留输入、输出和失败记录。不要因为接口可用，就把所有字段同步到外部系统；先证明同步后的数据仍然能追溯到原始 Issue。

## 和指标视图相似，但不是同一种治理

Cloudflare 在同一天发布的 API Shield 更新提供了一个有价值的对照：Web Assets 的 Operations 页面增加了面向流量、错误、延迟、响应大小和安全的指标视图，并支持服务端排序，用于在大型资产清单中优先处理操作。

Issue 字段和指标视图看起来属于不同产品，但它们解决了相似的控制面问题：当对象数量变多时，单纯展示对象列表已经不够，系统必须提供稳定的维度来排序和筛选。GitHub 的维度来自人为定义的类型、优先级和日期；Cloudflare 的维度来自运行指标。前者描述“应该如何管理工作”，后者描述“系统正在发生什么”。

这个区别决定了验证方法。Issue 字段需要验证输入规则、覆盖率和语义一致性；指标视图需要验证指标来源、排序行为和大规模清单中的定位效果。不能把一个项目的人工分类直接当成另一个系统的运行事实，也不能因为某项指标排序靠前，就自动推导出对应 Issue 的优先级。

更稳妥的工程做法是保留两个方向的证据：工作项记录为什么要处理，运行指标说明现在发生了什么。两者可以通过自动化建立关联，但关联本身不应覆盖原始证据。

## 失败边界：结构化不等于真实和完整

第一种失败是字段过度设计。团队先创建大量字段，再试图要求每个人填写，结果是字段空置、随意填值和绕过流程。字段数量应由可执行的决策需求驱动，而不是由平台上限驱动。

第二种失败是把字段当成状态机。Priority、Effort 和日期可以帮助排序，但它们不自动代表开发、审核、发布或回滚状态。状态变化仍需要清晰的流程和责任人，不能仅凭一个日期字段推断工作已经完成。

第三种失败是历史数据假完整。新模型上线后，旧 Issue 可能缺少类型和字段。把空值批量填成默认值，会制造一种虚假的数据覆盖率。更可靠的策略是区分“未知”“不适用”和“尚未补录”，并在项目视图中专门暴露这些缺口。

第四种失败是自动化越权。REST、GraphQL 和 webhooks 让系统可以管理这些数据，但并不意味着外部机器人应该拥有全部写权限。自动化应限定可修改的字段、触发条件和回滚方式，同时保留失败事件。尤其在批量更新时，先用小范围对象验证，再扩大范围。

第五种失败是把排序结果当成结论。无论是人工填写的 Priority，还是运行时的错误、延迟指标，它们都只是决策输入。真正的工程结论还需要结合影响范围、时间窗口、依赖关系和验收条件。

## 结论：先建立可验证的维度，再谈自动化治理

GitHub Issue types 和 fields 的意义，不是让个人项目看起来更像企业项目，而是提供了一种更清晰的工作数据边界：类型负责分类，字段负责比较，标签和描述负责上下文，项目视图负责把数据转成可执行的队列。

Cloudflare API Shield 的指标视图则提醒我们，结构化管理不能只依赖人工分类；当系统进入运行阶段，还需要用流量、错误、延迟、响应大小和安全等维度观察真实行为。两者结合时，最有价值的不是把所有数据汇总到一个大表，而是让每一条排序结果都能回答两个问题：它依据什么事实产生？下一步由谁验证？

因此，采用 Issue 字段的最小成功标准不是“所有 Issue 都填满了字段”，而是团队可以稳定地筛出一组工作项，解释为什么它们排在前面，并在处理完成后用新的证据更新判断。做到这一点，结构化元数据才从表单装饰变成了工程控制面。
