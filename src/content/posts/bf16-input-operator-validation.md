一条发布说明写着“支持 BF16”，很容易被压缩成一句产品结论：这个后端现在支持 BF16，甚至因此更快。实际工程里，这句话缺少了至少四个限定条件：哪个算子、哪个输入、哪个后端、哪些布局。llama.cpp b12780 的变化恰好适合说明这种差异：它明确增加 `MUL_MAT` 和 `MUL_MAT_ID` 对 BF16 `src1` 的支持，范围标为 CPU、CUDA；同一批变更还提到 strided BF16 输入测试、CUDA MMVF 的类型处理，以及一个特定的 MUSA 规则。它描述的是若干明确路径，不是对所有模型和设备的一张通行证。

## 从“支持 BF16”还原成算子契约

BF16 是一种数值格式；算子支持则是一份更具体的契约。对于矩阵乘法，至少要问：两个操作数分别是什么类型？数据是否连续？算子实际走哪条实现路径？目标设备是否有对应内核？把这些问题合并成“模型能不能用 BF16”，会把完全不同的失败原因混在一起。

b12780 的关键措辞是 `src1`。它不是笼统宣布所有输入都能使用 BF16，而是指明了操作数位置；`MUL_MAT` 与 `MUL_MAT_ID` 也分别代表不同的运算路径，不能因为前者通过就推定后者也通过。发布说明将新增支持限定在 CPU 与 CUDA，因此不能据此声称其他后端同样具备能力。更不能把算子可运行解释为吞吐提升：发布材料证明的是支持范围与相关修复，没有提供可推广到具体模型、显卡或批量大小的性能数据。

布局同样属于契约的一部分。发布说明特别提到 strided BF16 `src1` 测试，说明验证不能只覆盖最简单的连续内存样例。一个只在紧密排列输入上通过的实现，仍可能在步长、偏移或批次组合下出现错误。矩阵维度和类型正确，不等于索引计算就必然正确。

## CPU、CUDA 与特殊路径不能互相代证

同一份发布记录还涉及 CUDA MMVF：通过模板参数读取 BF16 `src1`，覆盖 BF16 和 FP8 权重；并提到 CUDA 路径通过 `ggml_cuda_cast` 处理 `src1` 配对。这些细节说明“CUDA 支持”内部也有分派和类型门槛。它们不能被扩写为任意权重类型、任意算子或任意输入格式的支持承诺。

发布说明还提到显式的 MUSA Q2_K 规则，以及 MMVF expert offset overflow 修复。这两项是重要的边界信号：同一批改动里既有类型能力扩展，也有后端规则和索引修正，但它们并不自动组成一套跨后端统一保证。尤其是 offset 溢出问题，提醒验收不能只看输出类型或是否成功启动；带专家索引的路径还需要验证选择和偏移是否正确。

另一个项目的发布节奏也说明了集成边界：Ollama v0.40.19-rc0 的说明包含 `bump llama-server`，且该版本标为预发布。这只能说明该候选版本更新了所用的 llama-server，不能证明它包含 llama.cpp b12780，也不能证明其中的 BF16 路径已集成或可用。不同项目的版本号、发布时间相近，不构成依赖关系证据。要判断某个上层运行时是否带有某项底层能力，必须核对其实际依赖版本和构建产物。

## 固定版本：先让结果可追溯

以下命令用于在独立副本中固定到 b12780 并记录实际检出的提交。它们只建立版本证据，不代表编译或测试已经通过：

```sh
git clone https://github.com/ggml-org/llama.cpp.git llama.cpp-bf16-check
cd llama.cpp-bf16-check
git fetch --tags origin
git checkout --detach b12780
git rev-parse --short HEAD
git status --short
```

验收记录应保存提交标识、编译配置、设备与驱动信息、模型文件摘要、测试输入形状和结果。若要检查上层运行时，不要只记录它的产品版本；还要记录实际捆绑或调用的 llama-server 版本。候选版、正式版和本地修改版要分开标注，否则即使复现出差异，也很难判断差异来自代码、构建选项还是依赖更新。

## 一份可执行的分层验收清单

对这类变更，可以按下面顺序组织测试；这是一份验收设计，不是声称发布仓库采用了某个特定测试命令或阈值。

1. **范围矩阵**：分别记录 `MUL_MAT`、`MUL_MAT_ID`；CPU、CUDA；BF16 `src1`；以及实际涉及的权重类型。只对发布说明明确覆盖的组合写“有证据支持”，其他组合记为待验证。
2. **布局矩阵**：同一组维度至少覆盖连续输入和带步长输入；如路径使用批次或偏移，再加入对应组合。检查结果、越界和崩溃，不要只用一个最小形状代表所有情况。
3. **数值对照**：对每个组合用相同输入与可信参考结果比较，按项目已有的数值容差规则判定。BF16 与 FP32 的结果不应被要求逐位相同；容差必须来自既有测试标准或明确的应用要求，不能为了让新实现过关临时放宽。
4. **路径确认**：确认测试实际运行在目标后端，而非回退到 CPU 或其他实现。仅有“程序成功返回”不能证明 CUDA 内核被调用；记录设备、后端日志或项目提供的路径诊断信息。
5. **回归与性能分开**：正确性通过后，再以固定模型、输入形状、批量和运行环境比较性能。性能测试单独记录预热、重复次数和统计口径；没有这组证据时，只能说算子路径得到支持，不能说推理更快。
6. **上层集成**：如果从 Ollama 或其他服务入口调用，单独核对其实际 server 依赖、模型加载路径和请求配置，再重复关键正确性用例。底层仓库通过测试，不等于上层产品已经交付该能力。

## 失败时先缩小边界，而不是扩大结论

如果连续布局通过、strided 布局失败，优先把问题定位到步长与寻址；如果 CPU 通过而 CUDA 失败，检查设备分派和 CUDA 构建路径；如果 `MUL_MAT` 通过而 `MUL_MAT_ID` 失败，则应把它当作不同算子路径处理，而不是推翻或泛化整个 BF16 支持结论。若结果正确但速度没有提升，也不矛盾：能力支持和性能收益是两种不同的验收目标。

反过来，单次请求成功也不够。它可能走了回退路径，只覆盖了连续输入，或者根本没有触发特定专家索引。最小测试负责快速发现问题，边界矩阵负责证明覆盖面；两者不可互相替代。

工程上更有用的表述不是“某版本支持 BF16”，而是“某提交在指定后端、指定算子、指定输入位置和布局下通过了哪些验证”。llama.cpp b12780 的发布说明提供了比一句类型标签更细的范围线索；验收的任务，是把这些线索转成可复现的组合和明确的未覆盖项。这样既能正确使用新增能力，也能避免把局部实现进展误报成全局加速或上层产品承诺。
