## 先看变化：两个看似无关的状态

截至 2026 年 11 月 13 日，材料中有两个值得放在一起观察的预发布信号。vLLM 的 `v0.34.0rc2` 发布说明标题指出，在大多数可扩展场景中停止设置 `gpu_memory_utilization`；llama.cpp 的 `b12321` 发布说明则指出，SYCL 后端会让 oneDNN FA cache 具备线程安全能力，并记忆运行时失败。

这两条信息的共同点，不是“某个参数被删了”或“缓存变快了”，而是推理服务开始重新划分隐藏状态的责任边界：显存预算究竟由谁决定，失败结果是否会影响后续调用，多个请求能否同时触碰同一份后端状态。前者属于资源策略，后者属于运行时状态。它们都可能让服务在单请求测试中表现正常，却在扩展、并发或异常路径中出现难以解释的差异。

证据等级需要先说清楚：S11 是 vLLM 官方 GitHub Release 的候选发布版本，S9 是 llama.cpp 官方 GitHub Release 的预发布版本。材料只证明了发布说明中的变化，不证明它们已经成为稳定版默认行为，也不证明所有模型、硬件和后端都适用。因此，本文把它们作为架构变更样本，给出验证方法和工程推论，不把候选版本写成普遍可用的正式承诺。

## 显存预算不是一个越大越好的数字

`gpu_memory_utilization` 这类配置最容易被误用成“启动成功率旋钮”：启动失败就调高，运行中 OOM 就调低。但在可扩展推理服务中，服务本身、扩展模块、模型加载器和后端运行时可能都需要参与资源规划。若顶层服务强行替所有组件预留同一块显存，参数的含义就不再是“服务的预算”，而变成“对整个运行时的猜测”。猜测越强，扩展越难拥有自己的资源策略。

因此，S11 暗示的方向可以抽象为：在可扩展场景中，顶层配置不应默认替所有下层组件做显存承诺。这里的关键不是删除一个配置项，而是明确预算的拥有者。至少要区分三层：模型权重所需的固定空间、运行时缓存所需的动态空间，以及扩展或插件可能申请的额外空间。只有知道每一层的生命周期和分配入口，才知道某个比例参数是否仍然有准确含义。

一个可复现的检查可以从配置快照开始。下面是通用示例，变量名只代表待确认的实际启动参数，不应直接视为 vLLM 的完整命令行接口：

```bash
# 记录候选版本、模型标识和硬件信息
python -V
nvidia-smi --query-gpu=name,memory.total,memory.free --format=csv,noheader
python -m pip show vllm | sed -n '1,8p'

# 保存最终启动配置，避免只记录部署脚本中的模板
env | grep -E 'MODEL|GPU|MEMORY|VLLM' | sort
```

接着建立至少三组实验：显式设置旧预算、移除该预算、启用目标扩展但不覆盖其资源配置。每组都要固定模型、序列长度、并发数、输入输出比例和 GPU 数量。不要只比较“能否启动”，还要记录权重加载完成时间、首个请求延迟、连续请求中的显存曲线、并发上升时的失败类型，以及扩展初始化是否完成。

```bash
set -o pipefail
for case in explicit removed extension; do
  echo "=== $case ==="
  date -Is
  # 这里调用项目实际启动命令；每个 case 使用独立配置文件
  ./run-inference --config "configs/${case}.yaml" 2>&1 | tee "logs/${case}.log"
done
```

如果移除预算后服务仍然启动，并不代表参数没有影响；如果启动失败，也不能立即得出“必须恢复旧参数”的结论。失败可能来自模型权重、扩展初始化、驱动、可用显存碎片或并发压力。验收应把错误分成配置解析失败、资源不足、后端初始化失败和请求阶段失败四类。只有当失败类别在多次重复中稳定出现，且改变单一变量后能够恢复，才可以把它归因于资源策略。

## 运行时缓存需要记住什么，又必须忘掉什么

S9 提到的 oneDNN FA cache 变化包含两个关键词：线程安全，以及对运行时失败进行记忆。它们解决的是不同问题。线程安全关注多个执行路径同时访问缓存时，状态是否会被破坏；失败记忆关注某种运行时条件已经失败后，后续请求是否还会反复尝试相同路径。

缓存的正确性不能只用命中率衡量。一个缓存可能在单线程下命中率很高，却在并发初始化时产生竞态；也可能因为记住失败而减少重复开销，却把暂时性故障错误地延长为持续不可用。工程上必须先定义失败的性质：输入必然不支持、硬件能力不满足、资源暂时不足，还是初始化时序导致的偶发异常。只有前两类通常适合长期记忆，后两类更需要重试、过期或人工清理机制。

在无法从发布摘要确认具体失效策略时，不能臆测缓存的键、生命周期或清理 API。可以做的是设计黑盒验证。准备相同形状的并发请求、一个已知会触发后端选择的请求，以及一个应该走备用路径的请求，依次执行以下检查：

1. 单线程重复调用，确认成功路径是否稳定。
2. 多线程或多请求并发首次调用，观察是否出现初始化竞态。
3. 注入一次可控的后端失败，再重复相同请求，比较是否仍然反复触发昂贵初始化。
4. 更换输入形状或设备后重试，确认失败状态没有错误地污染不相干的缓存键。
5. 重启进程后重复测试，区分进程内状态与持久化状态。

可以用请求编号和进程编号把结果串起来：

```bash
for i in $(seq 1 20); do
  curl -fsS -X POST http://127.0.0.1:8000/generate \
    -H 'content-type: application/json' \
    -d '{"prompt":"cache-check","max_tokens":8}' \
    -w " request=$i code=%{http_code} time=%{time_total}\n" \
    -o /tmp/response-$i.json || echo "request=$i failed"
done
```

这段命令只能验证外部行为，不能证明内部缓存一定线程安全。要证明并发安全，仍需要项目提供的测试、日志或可观测指标；若材料没有给出指标名称，就不应擅自编造字段。外部验收可以记录错误次数、响应时间分布、进程退出情况和后端是否回退，但应把“观察到行为稳定”与“证明实现无竞态”分开写。

## 把升级验收拆成资源、状态和回退

对于候选版本，最小验收矩阵应包含三个维度。第一是资源：空闲显存、权重加载峰值、稳定运行后的显存、并发增加时的增长趋势。第二是状态：同一请求重复执行、不同请求交错执行、异常后恢复、进程重启后恢复。第三是回退：扩展不可用、后端初始化失败、显存不足、单个请求超时分别如何表现。

每个实验都要保留版本标识和配置快照。S11 的版本是 `v0.34.0rc2`，S9 的版本是 `b12321`；这类标识必须进入日志，而不是只写在文章或部署记录里。候选版本还应与当前稳定版本进行对照，至少使用相同模型和相同请求脚本。对照的目的不是追求单一吞吐数字，而是判断变化是否只影响目标边界：显存策略调整不应被误判为模型质量变化，缓存失败记忆也不应被误判为所有请求都获得了加速。

失败处理同样需要写成明确规则。例如：启动阶段资源不足时停止发布，不自动无限调高预算；请求阶段后端失败时记录请求形状、设备和后端选择，不把所有错误归结为 OOM；候选版本出现只在并发下复现的错误时，保留现场并回退到对照版本，而不是用增加重试次数掩盖问题。回退条件必须能够由日志或指标触发，不能依赖“感觉变慢了”。

## 我的结论：先治理状态所有权，再谈性能

这两个 Release 给出的工程启发是，推理优化越来越像状态治理，而不只是参数调优。显存比例、扩展初始化、后端缓存和失败记忆都属于服务的隐含状态；隐含状态越多，单次成功请求越不能代表系统正确。

更可靠的升级方式是先问三个问题：谁拥有这份状态，状态何时建立，失败后谁负责清理或重试。对于可扩展配置，先确认资源预算的所有权，再决定是否保留顶层比例参数；对于运行时缓存，先区分永久性失败和暂时性失败，再决定是否记忆失败；对于候选版本，先建立可对照的实验和回退条件，再讨论吞吐或延迟是否改善。

换句话说，真正可交付的不是“新版本能启动”，而是能够解释资源从哪里来、缓存为什么命中或失败、并发异常如何被发现，以及回退后是否恢复到可接受状态。S11 和 S9 都只是候选版本的官方发布信号，最终结论必须由同一硬件、同一模型、同一请求矩阵下的证据来完成。
