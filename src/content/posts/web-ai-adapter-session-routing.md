# 网页 AI 适配器的隐形成本：从号池与 IP 池拆解会话路由、并发背压与封禁边界

社区里经常出现一种看似简单的需求：把某个网页 AI 的能力包装成兼容 API，再通过一个地址供内部工具调用。NodeLoc 的相关帖子把这种需求描述为“网页反代”“2API”或“高并发出图”，并指向了几个公开仓库。这里需要先划清证据边界：S1 是社区讨论，只能说明真实使用场景；S2、S3、S4 是公开 GitHub 仓库，能够证明项目作者公开声明了哪些组件和目标，但不能证明其性能数字、长期可用性或对上游服务的合规性。

从 S2 的目录和项目描述看，GPT-Codex-image-2api 并不是一个单纯的 HTTP 转发器：它明确提到号池管理、IP 池管理、Codex 与 GPT 网页逆向出图，以及面向生产环境的并发能力。S3 的项目描述还涉及自动注册、邮箱、人机挑战和账号导出。S4 则把“多平台 2API、服务器部署、高并发”作为项目定位。把这些材料放在一起，真正值得讨论的不是如何绕过限制，而是：为什么一个网页适配器一旦进入并发场景，就会迅速变成身份路由、会话管理、排队和风险控制系统。

## 一、请求链路不是一条代理，而是四个状态机

一个合规的网页 AI 适配器，可以抽象成下面这条链路：

```text
客户端请求
  -> 协议校验与任务入队
  -> 选择可用的上游会话
  -> 浏览器或网页协议执行
  -> 结果标准化、审计与返回
```

每一段都有自己的状态，而不是简单的“收到请求后转发”。客户端请求至少包含模型、输入、超时和幂等标识；任务入队后，需要记录等待、执行、成功、失败和取消；上游会话则可能处于空闲、占用、冷却、失效或人工复核状态；结果阶段还要区分完整输出、部分输出、超时和上游拒绝。

因此，号池并不等于一个字符串数组。它至少需要保存：

- 会话标识与创建时间；
- 当前占用任务和最后一次活动时间；
- 最近错误类型，而不是只有一个失败计数；
- 是否需要重新登录或人工处理；
- 允许承担的任务类型和并发上限。

IP 池也不应被理解成“失败后换一个地址”的随机列表。网络出口、账号会话、浏览器指纹、请求节奏和业务行为之间存在关联。把其中某一个维度单独轮换，不能推导出稳定性，更不能推导出合法性。工程上更稳妥的做法，是把网络出口视为资源属性，用于地域、可达性和容量管理，而不是设计规避平台控制的机制。

## 二、真正的瓶颈通常在会话，而不是带宽

网页 AI 调用与无状态 API 的关键差异，是请求往往依赖浏览器上下文：Cookie、页面状态、上传任务、异步生成结果以及前后端协议顺序。一个会话在处理任务时，不能被另一个任务随意复用。即使服务器有足够 CPU 和带宽，上游会话仍可能只有有限的串行处理能力。

可以用一个简单模型估算容量。假设可用会话数为 `N`，每个会话允许的并发为 `c`，单任务平均占用时间为 `T` 秒，那么理想吞吐量约为：

```text
throughput ≈ N × c / T
```

这只是上限，不包含登录失效、页面加载、上传、重试、冷却和排队开销。若任务平均耗时 30 秒，10 个会话且每个会话只允许一个任务，理论上限也只有约 0.33 个任务/秒；增加客户端连接数不会改变这个事实，只会把压力转移到队列和超时。

因此，适配器必须有显式背压。最小实现可以包括：

```yaml
queue:
  max_pending: 200
  max_wait_seconds: 120
worker:
  session_concurrency: 1
  task_timeout_seconds: 180
retry:
  max_attempts: 2
  retryable_errors: [timeout, upstream_5xx]
```

这段配置是工程示例，不是上述仓库的官方配置格式。它表达的是三个原则：队列必须有上限；单会话并发必须由事实测量决定；重试必须按错误类型区分。认证失败、权限拒绝、内容政策拒绝和会话失效，不应该被当成普通网络超时无限重试。

## 三、把“高并发”拆成可验证的指标

S2 和 S4 的项目描述都强调高并发或高性能，但公开描述本身没有提供完整的压测环境、任务大小、上游响应时间、成功率和错误分布。于是，“一分钟万次任务”只能作为项目作者的声明，不能直接当作可迁移的容量结论。

验证一个适配器时，至少要记录以下指标：

1. **排队延迟**：请求进入系统到获得会话的时间。它能揭示号池是否已经耗尽。
2. **上游执行时间**：从浏览器动作开始到收到结果的时间。它能区分网页慢和本地排队慢。
3. **成功率与错误分类**：不能只看 HTTP 200，还要区分空结果、任务失败、会话失效和上游拒绝。
4. **会话周转率**：一个会话完成多少任务后进入冷却或失效状态。
5. **重试放大倍数**：客户端请求数与上游实际尝试数的比例。这个数字过高时，系统可能正在用重试制造拥塞。
6. **资源水位**：浏览器进程数、内存、文件描述符、队列长度和出口连接数。

一个安全的验证流程应先使用模拟上游或自有测试页面，固定输入大小和任务时长，再逐步增加并发。命令可以从本地健康检查开始：

```bash
curl -fsS http://127.0.0.1:8080/healthz
curl -fsS http://127.0.0.1:8080/metrics | sed -n '1,80p'
```

如果项目没有 `/healthz` 或 `/metrics`，不要为了“看起来完整”伪造结果，而应直接检查其日志、测试目录和任务状态接口。压测时应保存请求数、成功数、超时数和每个阶段的延迟分位数；只报告峰值吞吐而不报告成功率，结论没有工程意义。

## 四、失败边界：账号、出口和浏览器不是可无限替换的零件

S1 描述了自动注册账号短时间被封的情况，S3 的仓库描述也明确涉及自动注册、人机挑战和账号密码设置。这里不能把社区经验写成平台规则，更不能把自动注册或挑战处理当成可复制的部署步骤。它只能说明一个事实：身份资源存在明显的生命周期和失效边界，批量创建并不等于获得稳定容量。

对适配器而言，常见失败模式至少有四种：

- **身份失效**：账号登录失败、需要重新验证或被限制。继续重试会把故障放大。
- **会话失效**：Cookie 仍在，但页面上下文已过期；此时返回“认证成功”会误导调用方。
- **网络失效**：出口可连接，但到具体上游的 TLS、DNS 或长连接不稳定。
- **协议漂移**：网页前端改动后，原有请求顺序、字段或响应解析失效。

状态机应为每种失败设置不同动作。例如身份失效进入隔离区并触发人工核验；协议解析失败停止自动重试并报警；普通超时才允许有限重试；客户端取消则尽快释放会话。最忌讳的是一个统一的 `except Exception: retry()`，它会把认证错误、业务拒绝和程序缺陷全部伪装成暂时性网络问题。

## 五、从“资源池”转向“可撤销的能力边界”

很多项目首先想到的是增加账号、增加 IP、增加浏览器实例。但更重要的问题是：调用方能否知道自己消耗了哪类资源，以及管理员能否在异常时立即停止某一类任务。

建议把权限和资源边界做成显式配置：

```yaml
policy:
  allowed_models: [internal-test-model]
  max_input_bytes: 1048576
  max_tasks_per_client_per_minute: 20
  allow_file_upload: false
  audit_payload_hash: true
  emergency_stop: true
```

这里的重点不是具体数值，而是“默认收紧、可审计、可撤销”。文件上传、长时间任务和批量并发都应单独授权；日志不应无条件保存完整敏感输入，可以保存请求摘要、哈希、大小、耗时和结果状态；紧急停止应能按客户端、模型、会话池和任务类型生效。

此外，适配器不应把上游网页凭据暴露给下游用户。凭据应由服务端托管，权限按用途分离，日志和错误响应中要清理 Cookie、授权头和页面中的敏感字段。对于公开仓库，还应在部署前检查 `.env.example`、默认密钥、调试接口、管理端口和容器权限，而不是因为项目“能启动”就认为可以直接上线。

## 六、一份上线前检查清单

在接入任何网页 AI 适配器前，可以按以下顺序检查：

- 是否明确获得上游服务和账号的使用授权？
- 项目声明的性能是否有测试脚本、环境和成功率支撑？
- 任务是否具备队列上限、超时、取消和幂等机制？
- 会话、账号和网络出口是否有独立状态，而不是失败后随机替换？
- 认证失败、业务拒绝、协议变化和网络超时是否分开处理？
- 是否能够隔离失效会话，并阻止重试风暴？
- 是否有健康检查、指标、结构化日志和告警？
- 凭据是否不会进入日志、错误响应、导出文件或前端？
- 是否能一键停止高风险任务，而不必关闭整台服务器？
- 是否准备了自有测试上游，避免用第三方生产服务做压测？

## 结语：适配器的核心产品不是“另一个 API 地址”

从 S2、S3、S4 可以看到，网页 AI 适配器的复杂度来自多个状态系统的叠加：身份会过期，浏览器会漂移，网络出口有容量，任务有长尾，协议会变化。S1 中关于账号快速失效的社区样本，则提醒我们不要把资源池误读成无限供给。

因此，一个可维护的实现，目标不应是宣称“多少任务一分​​钟”，而应回答四个问题：当前有多少可用会话？请求正在等待什么资源？失败属于哪一种边界？管理员能否在风险扩大前撤销能力？

如果这些问题没有答案，那么所谓高并发只是把不确定性隐藏在更多账号、更多代理和更多浏览器进程后面。真正可靠的网页适配器，首先是一套有背压、有审计、有停止开关的任务系统；协议转换只是它最容易被看见的那一层。
