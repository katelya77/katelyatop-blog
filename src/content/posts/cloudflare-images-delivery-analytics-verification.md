图片服务最容易被误判为“只要返回 200 就正常”。实际上，图片交付链路至少包含源图、变体、转换规则、客户端请求、边缘响应和来源流量几个层次。某个页面能打开，只能证明一次请求成功；它不能说明哪个源图最热门、哪个变体被大量使用、错误是否集中在某类客户端，也不能说明突发流量来自正常页面还是异常引用。

Cloudflare 在 2026 年 11 月 20 日的官方 Changelog 中宣布，Cloudflare Images 的 Hosted images 新增 Analytics 能力。官方描述显示，该能力提供最多 30 天的交付数据，并可在控制台查看请求趋势、国家、ASN、Referrer、响应状态码、浏览器、操作系统，以及源图和变体的使用情况；同时，部分数据可以通过 `cf sql query` 查询。这个证据等级是官方产品变更记录，而不是社区猜测，但它仍然意味着一个明确边界：这是交付分析能力的新增，不等同于完整的 APM、实时告警或长期数据仓库。

## 先把图片交付拆成几个可观察对象

一个典型的托管图片请求，可以抽象为：客户端请求某个图片 URL，平台根据 URL、预定义 Variant 或内联配置，找到源图并执行或复用转换，最后返回某种输出格式。分析系统如果只统计 URL 访问量，无法回答“请求打到了哪张源图”和“转换配置是否导致了额外负担”。

因此，至少要区分四类对象：

1. **请求**：某段时间内发生了多少交付请求，返回了什么状态码。
2. **来源**：请求来自哪些国家、ASN、Referrer，以及流量是否突然改变。
3. **资产**：哪些 source image 被请求最多，是否存在少数大图承担了主要流量。
4. **转换**：请求使用了哪种预定义 Variant 或 inline configuration，是否有某类配置持续占用请求量。

Cloudflare 的官方记录明确提到，Hosted images Analytics 可以查看请求量随时间变化，按国家、ASN 或 Referrer 筛选；还可以按响应状态码、浏览器和操作系统拆分。对于资产和变体，它提供最常请求的源图，以及预定义变体和内联配置之间的使用对比。这种维度划分很重要：它把“流量异常”和“资源配置异常”从同一个总数中分离出来。

不过，这些维度不能互相替代。一个 Referrer 流量很高，不代表它对应的图片转换成本最高；一个源图请求很多，也不代表它的响应全部成功。工程上应把它们视为不同的切片，而不是寻找一个万能指标。

## 从控制台到命令行：先做低风险的总量核对

官方变更记录给出的 SQL API 示例，是按 HTTP 状态码统计请求量：

```bash
cf sql query \\
  'SELECT httpStatus, COUNT(*) AS requests \\
   FROM events.imagesHostedRequests \\
   GROUP BY httpStatus \\
   ORDER BY requests DESC \\
   LIMIT 20' \\
  --scope-account "<ACCOUNT_TAG>" \\
  --time-since "<START_TIME>"
```

这条查询适合做第一轮核对，因为它不依赖具体图片名称，也不需要先假设某个变体一定有问题。执行时至少要替换两个占位项：账户标识和起始时间。不要把示例中的占位符原样复制到自动化任务中，也不要在没有明确时间窗口时把查询扩大到无限历史范围；官方能力本身只承诺最多 30 天的交付数据可见性。

查询结果首先用于回答三个问题：

- 成功响应是否占据预期的主要部分；
- 非成功状态码是否集中在某个时间段；
- 是否存在少量状态码异常放大、值得进一步按来源或资产切分的情况。

这里有一个容易被忽略的取舍：状态码总量适合发现问题，不适合直接定位根因。若某个错误状态码增加，下一步应回到控制台按时间、来源、客户端或资产筛选，而不是仅凭总数判断是源图缺失、URL 配置错误、客户端兼容性还是外部引用增长。查询应该形成逐层缩小范围的流程，而不是堆叠越来越复杂的 SQL。

## 用转换数据检查“同一张图被怎样使用”

官方记录还给出了转换数据的查询示例：

```bash
cf sql query \\
  'SELECT isBindingRequest, scriptName, originHost, COUNT(*) AS transformations \\
   FROM events.imagesTransformations \\
   GROUP BY isBindingRequest, scriptName, originHost \\
   ORDER BY transformations DESC \\
   LIMIT 5' \\
  --scope-account "<ACCOUNT_TAG>" \\
  --time-since "<START_TIME>"
```

这条查询观察的是 transformation 维度，而不是简单的图片交付量。`isBindingRequest`、`scriptName` 和 `originHost` 被组合起来，可以帮助判断转换请求是否集中在某种绑定请求、某个脚本或某个来源主机上。这里最有价值的不是“排名第一”这个结果，而是发现配置结构与访问结构之间的不一致。

例如，一个站点可能以为自己主要使用少数预定义变体，但转换统计却显示大量请求来自 inline configuration。这并不能自动证明 inline configuration 错误，却提示团队检查：是否存在组件各自拼接参数、是否出现尺寸参数碎片化、是否难以建立缓存复用、是否有旧页面继续使用不同配置。相反，如果请求集中在少量预定义变体，维护者更容易建立命名、尺寸和格式的治理规则。

查询结果也不能直接等价为“性能成本”。官方材料说明它可以查看转换数据和绑定请求，但没有在给定材料中承诺完整的计费解释、缓存命中率、端到端延迟或每次转换的资源消耗。因此，文章和运维结论都不应把 transformations 数量直接写成 CPU 成本或用户体验分数。它更适合作为配置使用的证据，配合其他性能工具继续验证。

## 一套可复现的验收清单

把 Analytics 接入日常流程时，可以按以下顺序验收，而不是只打开面板看一眼：

### 1. 能否在明确窗口内得到数据

选择一个已知存在请求的时间窗口，确认 Hosted images Analytics 能显示交付趋势，并确认查询命令接受账户范围和起始时间参数。窗口应尽量短，方便把一次页面发布、营销活动或故障时间与数据对应起来。

### 2. 状态码是否能形成异常入口

执行按 `httpStatus` 分组的查询，保存查询时间、账户范围和结果。不要只记录“有数据”，还要记录是否出现非预期状态码，以及它们占比是否随时间变化。若结果只有总量，没有时间上下文，后续很难判断异常是否已经恢复。

### 3. 来源维度能否解释流量变化

在控制台按国家、ASN 和 Referrer 逐一筛选同一时间窗口。若总请求量升高，但主要来源仍是预期站点，可能是内容访问增长；若出现陌生 Referrer 或异常 ASN，则应进一步检查外部引用、热链或机器人流量。这里的“可能”必须保留，因为仅凭来源统计不足以确认攻击或滥用。

### 4. 资产和变体是否符合设计

查看最常请求的源图，确认热门资产是否符合业务预期；再比较预定义 Variants 与 inline configurations 的使用情况。如果一个已经废弃的源图或旧变体仍然排名靠前，问题可能在页面缓存、旧客户端或未清理的引用链路，而不是图片平台本身。

### 5. 客户端输出是否出现集中差异

按浏览器和操作系统观察请求分布，检查是否存在某类客户端大量触发错误或使用不同输出格式。不要因为某个浏览器请求量少就忽略错误；应结合状态码和资产维度判断它是否影响关键用户群。

## 失败边界：哪些结论不能从 Analytics 单独推出

第一，**不能把“可见数据最多 30 天”当作长期审计日志**。如果团队需要季度趋势、版本前后对比或成本归因，应在可用窗口内建立合规的数据导出或记录机制；给定材料没有说明更长期的保留方式，因此不应假设平台会永久保存这些明细。

第二，**不能把请求量当作唯一性能指标**。请求数量可以说明负载和使用结构，却不能直接回答首字节时间、下载耗时、缓存命中、图片体积或页面转化率。图片交付分析解决的是“发生了什么请求”，不是完整的用户体验测量。

第三，**不能把异常来源自动判定为恶意行为**。国家、ASN、Referrer 和 User-Agent 是调查线索，不是安全结论。误配置的代理、RSS 阅读器、搜索爬虫和真实用户都可能造成非典型分布。安全处置仍需结合访问控制、速率限制和其他日志证据。

第四，**不能只看源图排名就删除低频资产**。低频图片可能属于错误页、合规页面、邮件模板或季节性活动。删除前至少要确认引用关系、业务所有权和回滚方式；Analytics 只能提供使用证据，不能替代资产生命周期管理。

## 工程取舍：面板、SQL 与长期监控如何分工

控制台适合探索：通过筛选器快速查看趋势、来源、状态码和客户端差异，适合故障初判和发布后观察。SQL 适合重复核对：把固定查询放进运行手册，在同样的时间窗口内生成可比较结果。长期监控则需要另一个系统负责告警、历史保存、权限和报表，不能因为有 SQL 查询就假设这些能力已经自动存在。

更稳妥的做法是建立三层信号：第一层用总请求量和状态码发现异常；第二层用来源、资产和变体定位范围；第三层再把具体 URL、发布记录、应用日志和用户体验指标串起来。这样可以避免“看见一个高峰就立刻封禁”，也避免“所有请求都是 200，所以系统没问题”的两种极端。

Cloudflare Images Analytics 的真正价值，不是增加一个更漂亮的图表，而是让图片交付从黑盒请求变成可按对象拆解的证据链：请求告诉你异常是否存在，来源告诉你异常从哪里来，资产告诉你影响了什么，转换数据告诉你配置如何参与其中。最终的工程结论应当是：图片系统的验收不再止于“图片能打开”，而要验证交付结果、流量来源和转换配置是否同时符合预期；但任何单一分析维度，都不能替代完整的性能、安全和业务验证。
