## 先把证据等级说清楚

llama.cpp b12608 是一份带有 GitHub verified signature 的正式预发布说明，而不是社区转述。Release 页面明确标记为 Pre-release，并给出提交 93cb37e，以及一个可核验的 attestation 链接。它说明的问题是：`ggml-cpu` 中 tinyBLAS_Q0_PPC 的矩阵乘法分块要求 `nc` 是 8 的倍数；修复前的特殊逻辑会允许 `n == 4` 时把 `nc_aligned` 设成 4，于是走 tiled 路径的参数违反了内核约束，已观察到 Flint Q4_K_M 和 Gemma 3 27B Instruct 出现乱码推理输出。

需要区分“已经修复”和“此版本已经适用于所有平台”。前者由固定提交中的回归修复支持，后者不能据此得出。PPC 的正确性并不代表 x86、ARM 或 Apple 平台同样需要更新，也不代表该修复已在所有模型、量化格式和编译配置上完成验证。b12608 只是一个证据起点：提交身份、问题机制、受影响代码路径和可复现边界都有了，完整结论仍取决于目标机器上的回归矩阵。

与之类似，Release 页本身的标签也需要分级。OpenAI Codex 的 `rust-v0.173.0-alpha.4` 是 alpha；Qwen Code v0.28.3 则明确标记为 Latest，但同时声明没有已知破坏性变更。标签不能替代兼容性证明，Release 列表的说明只能证明维护者发布了哪些内容，不能证明某个应用已经在真实配置中通过验证。

## 为什么 nc 对齐会直接影响模型输出

这里不应把 b12608 理解成一次常规的内存性能优化。问题发生在张量并行计算内部：Q0 矩阵乘法被拆成 tiled 路径，而 tiled 路径对块宽度有固定约束。若它收到的列分块 `nc` 不满足其设计宽度，数据会进入错误的内部布局。硬件并不一定崩溃，反而可能静默地产生错误结果，因此最明显的外部症状不是进程退出，而是文本乱码。

修复前的逻辑在 `n == 4` 时允许额外特殊对齐，测试到的受影响实例正好说明了为什么 `nc = 4` 的特殊分支非常危险：原本只检查数值是否能被 8 整除的分块约束，遇到小的特殊情况后被绕过。修复后的约束可以概括为：进入 tinyBLAS_Q0_PPC 的 tiled 路径之前，确保有效列块宽度始终符合后端要求。

更容易忽略的是，后端正确性和量化文件正确性是两个独立问题。Flint Q4_K_M 或 Gemma 3 27B Instruct 内容异常，不能仅凭模型权重文件损坏或提示词问题下结论。必须同时确认模型文件 SHA256、加载日志、线程和后端选择相同，然后只替换内核修复前后的可执行版本。只有这样，`nc` 对齐才成为最可疑变量。

## 复现前应锁定哪些变量

最低限度应固定以下变量：PPC64 架构、操作系统和工具链；llama.cpp 提交；模型文件及 SHA256；量化格式；提示词和采样参数；线程数；后端选择；以及是否启用了同一组编译选项。若只是更换镜像标签，而继续沿用宿主缓存、旧模型、旧 CMake 构建产物或动态库，就无法判断回归来自代码修复还是环境变化。

构建核验可以从一个干净目录开始：

```bash
git clone https://github.com/ggml-org/llama.cpp.git
cd llama.cpp
git fetch --tags
git switch --detach b12608

git rev-parse HEAD
git show -s --format='%H %G? %GS %GD' HEAD

git show --stat --oneline 93cb37e

git show --stat --oneline 93cb37e -- ggml
```

其中最后一条用于确认提交确实涉及计算后端，而不是只修改文档或版本元数据。实际产物应使用提交对应的二进制版本，不要让系统同时加载旧的 `libggml*`。构建后记录完整路径和系统解析到的动态库：

```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build --parallel

find build -type f -perm -111 -print
ldd ./build/bin/llama-cli 2>/dev/null | sort
```

二进制名可能随项目构建配置变化，应以构建目录中的实际产物为准。核验时不要只运行一次。至少准备一个纯文本 UTF-8 提示词、一个要求较长输出的提示词，以及一组确定性参数。对比目标提交与修复前提交时，采样参数也应保持完全一致；否则乱码与随机采样无法区分。

## 针对 Q0 PPC 的回归矩阵

一个工程上合理的验收矩阵不是所有后端一次跑完，而是先缩小变量：

1. 固定同一台 PPC 主机和同一份操作系统环境。
2. 固定 Flint Q4_K_M 的权重 SHA256，分别构建修复前和修复后提交。
3. 固定 Gemma 3 27B Instruct 的权重 SHA256，重复相同步骤。
4. 固定提示词、输出长度、线程数和随机种子。
5. 分别记录正常文本、异常文本、退出码和进程日志。
6. 重复至少三轮，排除偶发内存状态或系统负载造成的差异。
7. 再切换到至少一种不受该量化分块影响的模型，确认故障没有迁移到模型加载或提示词处理。

可以用一个简单脚本核对输出是否包含明显的替代字符或非预期控制字符：

```bash
python3 - <<'PY'
from pathlib import Path

for name in ('before.txt', 'after.txt'):
    data = Path(name).read_bytes()
    text = data.decode('utf-8', errors='replace')
    replacement_count = text.count('\ufffd')
    control_count = sum(ord(c) < 32 and c not in '\n\r\t' for c in text)
    print(f'{name}: replacement={replacement_count}, control={control_count}')
PY
```

这个脚本只能作为乱码筛选器，不能证明模型内容正确。因为语义错误、替换字符较少的 UTF-8 串和合理文本都可能通过初步统计。因此，除机器检查外，还应保留对照输出并人工校验关键片段。

更直接的结构核验是检查源码中的分块条件。不要只搜索字符串后停止，应确认两个条件同时成立：tiled 分支使用的宽度被计算为合适值；特殊分支不再把宽度降到违反 8 的倍数约束的值。一个最小不变量可以写成：

```bash
python3 - <<'PY'
nc = 4
n = 4
TILE_WIDTH = 8

# 当 n 的特殊分支进入 tiled 路径时，nc 必须仍满足后端约束。
if n == 4:
    nc = max(nc, TILE_WIDTH)

if nc % TILE_WIDTH != 0:
    raise SystemExit(f'invalid nc={nc}')
print(f'valid nc={nc}')
PY
```

它不是项目源码的替代测试，而是把修复前的断言编码成可读规则。真正通过验收前，需要由目标后端自己的测试和真实模型推理共同确认该约束。

## 验收报告应该包含什么证据

一次合格报告至少应记录提交哈希、构建产物哈希、目标平台、模型哈希、测试提示词、参数、重复次数和最终结论。只写“PPC 已修复”“版本可用”是不够的；应写成可审计的陈述，例如：在提交 93cb37e 的发布产物上，固定 Flint Q4_K_M 模型，使用同一台 PPC64 环境连续运行相同提示词三次，未再观察到乱码；而其他量化格式或扩展后端仍未覆盖。

通过与失败的边界也应分开。以下情况应视为不通过：修复前后都出现相同乱码；修复后在部分线程数下通过、在其他线程数下失败；构建时使用了缓存中的旧库；模型哈希未固定；只跑一次；只检查进程退出码却不检查文本；或只在短提示词中通过，却不覆盖发布说明提到的两个模型形态。

相反，以下情况可以成立有限结论：特定提交、特定模型、特定量化格式、特定编译配置下不再出现此前的乱码；或者特定环境下乱码消失，但性能没有改善，甚至出现轻微回退。正确性修复和性能回归是不同指标，不能互相替代。

## 工程取舍：是否立即升级

升级应由可观察风险决定，而不是由版本号决定。对于会直接在 PPC 上运行大模型的环境，b12608 的修复描述使升级理由具体且强：已知 Q0 后端可能被错误的分块宽度带入 tiled 路径，并出现静默错误，而静默错误比崩溃更难排查。此时可以先在候选实例中运行回归模型，再推广到全部节点。

对于不运行 PPC、使用完全不同量化后端，或者当前工作负载未触及受影响路径，升级收益主要来自软件栈一致性，而不是已被证明的直接故障修复。此时应把升级视为普通依赖变更，优先验证启动、加载、最小推理和回滚能力，而不是假定每个平台都会获得相同收益。

同时应保留回滚版本。回滚不仅是恢复镜像，还包括恢复与之匹配的模型、动态库和构建缓存。只替换可执行文件，而保留系统中另一个旧版 llama.cpp 库，可能让验收结果失去意义。

## 原创结论：对齐修复的真正可复用模式

这个案例最值得学习的不是“矩阵乘法要对齐”，而是静默错误必须用证据链来关闭。提交说明证明了一个具体逻辑缺陷；模型乱码证明了外部症状；目标架构和量化格式限定了影响面；只有固定版本、固定权重、固定参数的重复测试才能证明修复有效。

因此，发布工程应始终保留四层证据：源码提交的签名或可核验身份；构建产物的提交哈希和内容哈希；目标平台上的最小功能与回归测试；模型和文本输出的人工验收。缺少其中一层时，最多能得到“发布声明存在”，不能得到“所有环境均已修复”。

对于模型推理后端，尤其不能把绿色测试等同于全局可用。PPC 上修复了 `nc` 对齐，可能解决 Flint 和 Gemma 路径中的乱码，但它不会自动证明另一个量化格式、另一个硬件后端或更高并发下没有同类分块问题。最稳妥的结论是：b12608 为 PPC Q0 tiled 路径提供了明确、可验证的修复方向，但升级后的最终结论仍属于目标环境的验收产物。
