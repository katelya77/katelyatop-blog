## 先换一个问题：它不是“更大的聊天窗口”

很多 AI 产品的展示方式仍然是输入框、模型选择器和一段回答。但科研任务的交付物通常不是回答本身，而是一组可以继续检查的东西：论文或数据集来源、处理步骤、分析脚本、图表、统计表，以及别人能否沿着同样的输入重新得到相近结果。

从公开产品页看，Codar 把自己定位为科研工作台，而不是单纯的对话入口。它提供文献库、专业插件、生信模式、项目文件、本地生成物和定时任务；页面还展示了从 GSE96583 数据出发，完成解析、质控、细胞类型注释、ISG 评分、伪 bulk 差异表达并生成报告与脚本的任务链。这里最值得关注的不是某个模型名称，而是产品把“上下文”从聊天记录扩展成了一个带有文件、工具和过程状态的项目空间。

这也带来一个更严格的判断标准：一个科研 AI 工作台是否有价值，不应只看它能否生成一段专业术语密集的文字，而要看它能否回答四个问题：输入从哪里来，工具以什么权限运行，中间产物是否留下，结果如何被复查。

## 三层架构：材料、能力与执行面

可以把公开信息抽象为三层，而不必假设产品内部采用了某种未公开的具体实现。

第一层是材料层。文献库支持 PDF、DOI、arXiv、BibTeX、RIS 和 Zotero 导入，并提供文件夹、标签和全文检索。项目文件则可能包括论文、数据集、笔记、脚本、图片和报告。材料层的价值是让任务拥有稳定的输入边界：用户可以指出某一篇文献、某一批本地数据或某个项目目录，而不是把所有内容压缩进一次聊天请求。

第二层是能力层。产品页将插件描述为 Skills 和 MCP 工具的组合，并按基础科研、计算机、经济学、生物医学、数学建模等方向组织。生信模式进一步细分转录组、单细胞、空间组学、基因组、表观组、蛋白质组和代谢组。由此可以推断，系统试图把“该怎么做”从模型自由发挥，转化为按任务启用的工具能力；但公开材料并没有证明每个插件的实现、版本锁定方式或权限模型，因此不能把这种产品描述直接等同于完整的可复现执行环境。

第三层是执行层。公开页面明确写到，Codar 可在电脑上读写本地项目文件、操作用户授权的浏览器标签页、执行定时任务，并可从微信、钉钉、飞书等消息平台发起任务。这个层次决定了风险边界：读本地文件、访问浏览器、调用外部服务和生成代码，都是不同权限，不应该因为它们出现在同一个工作台里，就被视作同一种操作。

因此，一个更稳妥的架构图不是“模型调用工具”，而是：材料层提供可定位输入，能力层提供受控方法，执行层落实授权与产物落盘，模型负责规划、解释和连接这些环节。模型能力越强，越需要把执行面拆开，而不是把所有权限都交给一个对话进程。

## 为什么生信模式比普通聊天更需要过程状态

生物信息学任务天然是多阶段流水线。以产品页展示的单细胞分析为例，任务至少涉及数据读取、质量控制、聚类、细胞类型注释、Marker 验证、差异表达和报告生成。每一步的输入输出都可能影响下一步，任何一个环节被省略，最终结论就很难复查。

产品页展示的另一个案例是 GSE96583 的 IFN-β 刺激后 PBMC 分析：页面给出 8 名供体配对伪 bulk 分析、CD14+ 单核细胞响应更强，以及多个细胞类型中共同上调的基因集合。这些内容可以作为产品展示的结果样本，但不能仅凭页面结论判断分析是否严格复现。真正有工程价值的是它同时声称会保留任务原文、操作步骤、结果图和统计表，并生成分析报告与可复现脚本。

这里存在一个关键区别：报告是解释层，脚本是执行层，原始数据和参数才是输入层。三者缺一不可。只有报告，没有脚本，读者无法判断结论如何产生；只有脚本，没有固定输入和环境，别人可能无法重现；只有输出图，没有中间统计表，则很难定位异常。

因此，在使用这类工具时，建议把每次任务的交付物最低要求固定为：

- 输入清单：数据集标识、文件路径、文献 DOI 或下载地址；
- 方法清单：使用的插件、分析方法、关键参数和过滤条件；
- 过程产物：日志、临时表、图表源数据和中间结果；
- 最终产物：报告、脚本、环境说明和失败步骤；
- 复核入口：能够重新运行、替换参数或单独检查某一步的方式。

这份清单比“回答是否专业”更能区分科研助手与普通聊天机器人。

## 一套可复现的验收流程

下面的流程不假设存在公开 API，也不把宣传页当作执行证明，适合在获得软件后进行本地验收。

### 1. 先建立隔离项目

为每个研究问题创建独立目录，至少分出输入、脚本、结果和日志：

```text
project/
  inputs/
  scripts/
  results/
  logs/
  README.md
```

在 README 中记录任务原文、数据来源、开始时间、软件版本和预期输出。不要一开始就授予整个用户目录的读写权限；优先选择这个项目目录，并在任务完成后检查是否有文件被写到目录之外。

Windows 用户可以先用 PowerShell 记录目录与文件清单：

```powershell
Get-ChildItem .\project -Recurse -File |
  Select-Object FullName, Length, LastWriteTime
```

如果需要检查某个应用配置是否存在，先只读取路径和文件属性，不要把令牌、Cookie 或完整配置内容复制到日志、工单或公开帖子中。社区材料曾提到 Codar 用户目录下存在明文 config.json，这属于社区发现而非官方安全声明，足以说明本地凭据检查必须成为验收步骤，但不足以推断所有版本都采用相同存储方式。

### 2. 用小数据验证链路，而不是直接跑完整项目

先准备一个规模可控、结果容易人工检查的任务。例如使用公开的 PBMC 示例数据，只要求完成读取、基础质控和一个简单统计表。验证每一步是否产生预期文件，再扩大到聚类、注释和差异分析。

检查重点不是“模型是否说完成”，而是：脚本是否真的存在；脚本是否引用了实际输入；结果文件的时间戳是否对应本次任务；日志是否包含失败信息；报告中的数字能否在统计表或脚本输出中找到。

可以用哈希记录输入和关键产物：

```powershell
Get-FileHash .\project\inputs\* -Algorithm SHA256
Get-FileHash .\project\results\* -Algorithm SHA256
```

哈希不能证明科学结论正确，但能帮助区分“同一输入重新运行”和“文件已经被悄悄替换”。对于大文件，还应记录下载地址、数据集版本或发布日期；材料没有提供某个数据集的固定镜像时，不要擅自声称结果可以永久复现。

### 3. 单独验收外部连接器

浏览器连接器和消息平台是便利功能，也是边界最容易扩张的地方。先在没有敏感标签页、未登录高价值账户的浏览器配置中授权，观察它能访问哪些页面、是否会读取其他标签、任务结束后能否撤销权限。

如果任务通过消息平台发起，至少验证三件事：消息中是否包含敏感数据，回复是否带出本地文件内容，远程触发是否可以执行写文件或外部命令。定时任务则应记录触发时间、执行主体、输出目录和失败通知。一个“能从手机发起任务”的功能，不等于它具备适合无人值守生产运行的审计能力。

## 失败边界：免费、快速和可复现不是同一件事

社区材料中对某次免费模型活动做了较详细的观察：测试者报告了约 2.8 秒级别的短请求首字延迟、并发达到一定规模后出现 429、响应中包含计费字段，并指出免费窗口与登录令牌存在时间边界。这些内容的证据等级是社区实测记录，不是 Codar 官方性能承诺，也不能外推到所有账号、模型和时间段。

但它仍然揭示了几个通用工程事实。

第一，低价格或零费用不等于稳定吞吐。队列、并发上限、重试延迟和活动期限都会改变真实可用性。科研流水线不能把免费模型当作永远在线的基础设施，关键任务应保存中间结果，并允许更换模型或稍后续跑。

第二，模型目录名不一定等于实际执行模型。社区观察曾指出，相近模型标识可能路由到相同或不同的后端，甚至出现活动模型与付费模型命名相似的情况。对于任何按量计费或有免费窗口的入口，必须以响应中的实际模型、计费字段和账户账单交叉验证，不能只看下拉菜单。

第三，前缀缓存能降低部分计算成本，却不必然消除固定网关延迟。社区测试中，长提示词命中缓存后，首字延迟下降幅度有限。这说明系统优化不能只围绕 token 数量，还要关注排队、调度、连接建立和后端批处理。没有连续时间序列和明确测试条件时，不应把单次延迟数字写成稳定 SLA。

## 安全边界：本地优先仍然需要凭据治理

“运行在你的电脑上”主要说明部分文件处理和任务执行发生在本地，并不自动说明所有内容都不会离开设备。文献检索、模型调用、浏览器连接器、消息平台和远程下载都可能形成外部数据流。验收时要分别记录：哪些文件被读取，哪些内容被发送，哪些凭据被使用，哪些结果被写回本地。

最低限度的检查包括：

1. 搜索项目目录和应用配置目录中的 token、API key、Cookie、JWT 等敏感字段；
2. 检查生成脚本是否把凭据硬编码进命令或配置；
3. 检查日志和报告是否包含完整路径、邮箱、研究对象身份信息；
4. 使用最小目录权限，任务结束后撤销浏览器和消息平台连接；
5. 对外分享前删除配置文件、缓存、临时文件和带个人信息的截图。

这些检查不能替代厂商的隐私政策、权限说明或安全审计。公开产品页明确提到浏览器授权可以撤销，这是一个可验证的控制点；至于数据是否默认上传、插件是否隔离、凭据是否加密，则必须以对应版本的官方文档或实际网络与文件行为为准。

## 原创结论：科研 AI 的护城河是“可回到现场”

科研工作台最重要的指标，不是一次回答有多像专家，而是用户能否从结论回到输入、从图表回到脚本、从脚本回到参数、从失败回到日志。Codar 的公开设计至少把这些对象放进了同一产品叙事：文献库负责材料，插件和 MCP 工具负责能力，项目文件与报告脚本负责产物，浏览器连接器和定时任务负责外部执行。

但这套结构只有在权限、版本、输入和中间结果都被记录时，才会从“功能集合”变成工程系统。社区测试展示的延迟、并发、计费和令牌边界也提醒我们：AI 工作台的可用性不是一个静态参数，而是模型、账户、活动窗口、队列和本地执行环境共同决定的状态。

所以，选择科研 AI 工具时最有价值的问题不是“它支持多少模型”，而是：任务失败后能否续跑，结果错误时能否定位，权限扩大时能否撤销，活动结束后能否迁移。能回到现场，才是真正可复查；能在边界处停下来，才是真正可治理。
