## 先把变化说清楚：摘要发生在索引期，不在每次查询期

Cloudflare 在 2026 年 11 月 17 日的官方更新中，为 AI Search 增加了文件摘要能力。它的关键位置不是查询接口，而是 ingestion，也就是文件被索引的阶段：当一个文本文件至少产生三个 chunk 时，系统可以调用大语言模型生成 summary、topics 和 keywords。summary 与 keywords 会写入条目的 context metadata，topics 则会加入该文件各个 chunk 的 context header。

这看起来像是一个小开关，实际改变的是检索系统的数据流。传统流程通常可以抽象为：读取文件、切分、生成向量、写入索引、查询时召回。启用摘要后，流程变成：读取文件、切分、判断是否达到条件、调用模型生成摘要和主题信息、把结构化结果附着到条目及 chunk、再完成索引。摘要不是页面展示层的附属字段，而是会参与后续检索上下文构造的索引产物。

因此，最容易犯的错误是把它理解成“搜索时自动总结结果”。这项能力首先解决的是文档在进入检索系统时的语义补充问题；它并没有在官方材料中承诺某个固定的召回率、问答准确率或延迟提升。摘要生成成功，只能证明预处理步骤完成，不能直接证明用户问题会得到更好的答案。

## 三层数据结构：条目上下文、chunk 头部与原文内容

理解这项能力，应该先区分三种信息。

第一层是原文内容。文件仍然需要被解析并切分成多个 chunk，原始文本是检索系统能够返回证据的基础。摘要不能替代原文，也不能因为摘要存在，就删除原始 chunk。对于技术文档、配置说明和代码片段，细节往往只存在于原文中。

第二层是 item context，也就是文件条目的上下文元数据。官方说明显示，summary 和 keywords 会存储在这里；如果用户此前已经设置了 context，已有值会被保留。这意味着摘要功能并不是简单覆盖自定义上下文，而是要和已有的描述、标签或业务元数据共存。工程上应把它当作一个合并后的数据结构，而不是一个可以随意重写的字符串。

第三层是 chunk 的 context header。topics 会加入文件 chunk 的上下文头部，使每个片段在参与检索时拥有更明确的主题线索。它与条目级 summary 的作用域不同：summary 更像整篇文件的压缩说明，topics 更接近供片段定位使用的主题标记。两者同时存在，才能兼顾文档级语义和片段级语义。

这也解释了为什么“把摘要保存下来”不等于“把摘要拼到每个 chunk 前面”这么简单。如果应用层自行复制摘要，可能增加上下文长度，也可能让每个片段重复携带同一段文本；而由索引服务处理时，summary、keywords 和 topics 分别进入不同元数据位置，作用域和生命周期更明确。除非有明确的查询模板与评估数据，否则不应在应用层再次复制这些字段。

## 开关背后的运维动作：全量重建不是免费刷新

官方更新明确指出，文件摘要默认关闭。开启方式有两类：在控制台启用，或者在创建、更新实例时，把 `indexing_options.file_summary` 设置为 `true`。这里最重要的不是字段名称，而是启用后的副作用：修改该设置会触发完整重新索引。

全量重建意味着改变一个 indexing option 不能被视为普通配置热更新。它会重新处理已有文件，而不是只影响未来上传的文件。对于文件数量较多、内容频繁变化或有严格费用预算的实例，变更前至少要回答四个问题：当前有多少文件会被重建？哪些文件满足至少三个 chunk 的条件？模型调用费用由谁承担？重建期间，应用是否允许索引结果处于新旧混合状态？

还有一个容易被忽略的配置语义：`indexing_options` 在每次更新时是整体替换，而不是逐字段合并。没有在请求中保留的选项会回到默认值。也就是说，不能只发送一个 `file_summary` 字段，就假设其他索引选项会自动保持原状。安全的更新流程应当先读取当前配置，形成完整的目标配置，再提交更新；提交后再次读取并核对所有选项。

一个通用的变更检查可以写成下面这样：

```bash
# 1. 保存当前实例配置，作为变更前快照
curl -sS -H "Authorization: Bearer $CF_API_TOKEN" \
  "https://api.cloudflare.com/client/v4/accounts/$ACCOUNT_ID/ai-search/instances/$INSTANCE_ID" \
  > before-indexing-options.json

# 2. 从快照整理完整 indexing_options 后再提交更新
curl -sS -X PUT \
  -H "Authorization: Bearer $CF_API_TOKEN" \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer $CF_API_TOKEN" \
  "https://api.cloudflare.com/client/v4/accounts/$ACCOUNT_ID/ai-search/instances/$INSTANCE_ID" \
  --data @target-instance.json

# 3. 保存更新后的配置，确认没有意外回退其他选项
curl -sS -H "Authorization: Bearer $CF_API_TOKEN" \
  "https://api.cloudflare.com/client/v4/accounts/$ACCOUNT_ID/ai-search/instances/$INSTANCE_ID" \
  > after-indexing-options.json
```

上面的命令只表达配置核对的工程模式，具体 API 路径、认证权限和请求字段仍应以当前 API 文档为准。真正重要的是保留 before 与 after 快照，并对完整 `indexing_options` 做差异检查，而不是只检查 `file_summary` 是否为 `true`。

## 成本模型：文件数量、修改频率与模型调用次数

摘要能力带来的费用并不等于一次固定的功能费。官方说明指出，调用摘要模型的费用会计入账户，使用的是适合摘要任务的 Workers AI 模型，并通过该实例配置的 AI Gateway 调用；如果没有配置，则使用默认网关。这些调用按 Workers AI 使用量计费，且摘要不计入 AI Search ingestion allotment。

还需要注意调用发生的时机。每个新文件或被修改的文件只生成一次摘要。这个设计比“每次查询都重新总结”更适合稳定检索，因为查询请求不会直接触发摘要模型调用；但它把成本与内容变更绑定起来。一个每天被自动同步、实际内容却没有变化的文件，如果上游仍然以修改事件覆盖写入，就可能造成不必要的重新处理风险。

因此成本治理不能只看文件总量，还要看三个乘数：一是符合至少三个 chunk 条件的文件比例，二是文件修改频率，三是每次索引产生的摘要模型调用量。工程上可以建立一张简单的预算表：

```text
预计摘要调用量
= 首次启用时需要重建的符合条件文件数
+ 评估周期内新增文件数
+ 评估周期内被修改的符合条件文件数
```

这不是账单计算公式，而是变更评估的上界近似。实际费用仍受文件长度、模型用量和平台计费规则影响。它的价值在于提醒团队：开启摘要后，内容同步系统的“修改”语义变得重要。若同步器无法区分内容未变和内容已变，就应先治理同步事件，再扩大摘要功能范围。

## 如何验证：把索引成功与检索收益分成两条证据链

验证这项能力至少需要两层。

第一层是索引完整性。选取一组已知文件，确认摘要选项已生效、重建确实完成，并检查条目上下文是否包含 summary 与 keywords，chunk 上下文是否出现 topics。对于少于三个 chunk 的短文件，应明确记录它们不满足官方描述的生成条件，不能把“没有摘要”直接判定为失败。

第二层是检索质量。准备一组固定问题，每个问题绑定期望命中的文件和关键片段，分别在关闭摘要与开启摘要的索引上运行。至少比较：目标文件是否进入召回结果、关键 chunk 的排名变化、无关文件是否增加、最终上下文长度是否变化。若只观察最终回答，很难区分是召回变好了，还是模型生成阶段偶然说得更流畅。

一个最小的评估表可以包含以下字段：

```text
query_id
query
expected_file
expected_chunk
baseline_rank
summary_rank
baseline_hit
summary_hit
irrelevant_hits
notes
```

这里的重点不是追求一个漂亮的百分比，而是捕捉失败模式。摘要可能帮助宽泛问题找到正确文档，却不一定帮助精确问题找到包含参数、命令或异常码的 chunk；topics 可能改善主题识别，也可能让相似主题的文档更容易一起进入候选集合。只有把结果拆成文档命中、片段命中和噪声变化，才能判断它究竟改善了哪一层。

## 失败边界：哪些结论不能从“已启用”推出

第一，不能把摘要当作事实校验。摘要由 LLM 生成，官方材料只说明它会生成 summary、topics 和 keywords，并未承诺摘要永远准确。涉及版本号、命令参数、权限规则或安全配置时，原文 chunk 仍应作为最终证据。

第二，不能把默认关闭理解成默认无价值。关闭可能是为了让团队先控制成本、评估数据质量，再决定是否承担全量重建和模型调用费用。是否开启应由固定问题集和成本预算决定，而不是由功能开关本身决定。

第三，不能把索引成功当作端到端成功。摘要生成完成、元数据写入成功、查询返回结果，分别属于不同阶段。任何一个阶段通过，都不能替代对最终召回和回答的验证。

第四，不能把 AI Search 的摘要索引和 Agent 的模型编排混为一谈。同期的 GitHub Copilot Fusion 更新展示了另一类能力：系统可以在不同 Copilot 表面提供模型选择，并由 Fusion 根据任务协调模型；这属于运行时代理与模型编排问题，而文件摘要属于索引期预处理问题。前者关注任务执行和模型选择，后者关注文档进入检索系统前的语义准备。两者都使用模型，但验收指标、失败回退和成本边界完全不同。

## 工程取舍：什么时候值得开启

如果知识库包含大量较长、主题分散、用户提问方式差异明显的文档，摘要、主题和关键词可能提供有价值的语义入口。特别是用户常用概念描述问题，却不熟悉文档原始标题时，文档级 summary 和 chunk 级 topics 有机会缩短从问题到目标内容的距离。

如果知识库主要由短配置片段、单页 API 条目或高度结构化记录组成，摘要收益可能有限，因为很多文件本来就不会达到至少三个 chunk，或者原文中的精确字段比自然语言总结更重要。此时优先优化切分策略、元数据质量和问题评估集，通常比直接打开摘要更稳妥。

我的判断是：文件摘要应被视为一个有成本的索引变换，而不是一个无风险的搜索增强按钮。正确的上线顺序应是：保存现有配置，建立代表性问题集，估算符合条件的文件规模，明确完整配置更新方式，在可控范围内开启并完成重建，然后分别验证元数据完整性与检索质量。只有当收益能够解释额外的模型调用成本，并且原文证据仍然可追溯时，摘要才真正成为 RAG 架构的一部分，而不是又一层不可见的 AI 魔法。
