实时音视频系统里，一个看似普通的“加入会议链接”，实际上承载了身份识别、授权、时效控制和资源计费四个问题。令牌如果有效期过长，链接被转发后就可能在原定课程、面试或会议结束很久以后继续尝试使用；如果系统只提供整场会议级别的关闭开关，又很难处理单个参与者被移除、账号被吊销或临时访客失效的场景。

Cloudflare 在 2026 年 11 月 12 日的 RealtimeKit 更新中，把参与者令牌从默认的固定有效期扩展为可选的时间窗口，并增加单令牌撤销能力。这是官方 Changelog 已确认的正式能力，不是社区传闻或预览功能。真正值得讨论的并不是“多了两个字段”，而是令牌生命周期、会议状态和实时阻断之间出现了更清晰的边界。

## 先还原加入链路：令牌不是会议本身的权限

RealtimeKit 的参与者加入流程可以拆成三步：业务后端把参与者加入某个会议；服务端返回一个供参与者应用使用的认证令牌；参与者应用携带该令牌尝试进入会议。这个结构意味着，业务系统掌握的是“谁可以在什么时间尝试加入”，而会议服务负责验证令牌并决定是否允许进入。

这一区分很重要。令牌不是会议的永久成员资格，也不是把会议状态复制到客户端的静态密码。它更接近一张带有时间条件的入场凭证：凭证本身可以被签发、拒绝、撤销或等待生效，而会议仍然是独立的运行对象。

更新前，官方材料说明每个令牌从签发时起有效 100 天。这个默认值对快速集成很方便，却不适合“只在某个时间段开放”的业务。课程、面试、远程值班或临时访客都更适合使用明确的起止时间，而不是让令牌在活动结束后继续存在数月。

新的 token 对象支持两个可选字段：not_before 表示令牌开始生效的时间，expires_on 表示令牌失效的时间。两个字段都可选，因此旧集成仍会获得原有的 100 天令牌；但一旦业务要求“只允许在预约窗口内进入”，后端就应主动传入时间边界，而不是依赖默认值。

## 时间窗口的核心不是格式，而是授权语义

一个可操作的窗口通常需要三层时间：业务预约时间、服务端签发时间和令牌有效时间。业务预约时间决定活动何时发生，签发时间决定何时把凭证交给参与者，令牌窗口则决定服务端何时接受这张凭证。三者不应混为一个字段。

例如，一场预约在 UTC 时间 15:00 开始、17:00 结束，可以在添加参与者时传入：

```bash
curl "https://api.cloudflare.com/client/v4/accounts/$ACCOUNT_ID/realtime/kit/$APP_ID/meetings/$MEETING_ID/participants" \
  --request POST \
  --header "Authorization: Bearer $CLOUDFLARE_API_TOKEN" \
  --json '{
    "name": "Mary Sue",
    "preset_name": "<preset_name>",
    "custom_participant_id": "<uuid_of_the_user_in_your_system>",
    "token": {
      "not_before": "2026-12-01T15:00:00Z",
      "expires_on": "2026-12-01T17:00:00Z"
    }
  }'
```

这里有几个工程约束。

第一，时间带必须明确。示例使用 Z 表示 UTC，业务系统应统一把本地时间转换为带时区的时间戳，再写入审计记录。不要让浏览器、应用服务器和数据库各自用默认时区解释同一个预约时间。

第二，窗口应描述“允许服务端接受令牌的范围”，而不是客户端 UI 的展示范围。客户端可以提前展示倒计时，但真正的准入判断仍然发生在 RealtimeKit 的令牌校验环节。

第三，不能把过期时间当成会议结束动作。expires_on 控制的是令牌的有效性；它不会自动替代业务侧的会议收尾、录制处理、参与者状态同步或数据保留策略。

第四，权限本身也必须纳入发布检查。官方材料要求调用添加参与者 API 的令牌至少拥有 Realtime Admin 或 Realtime 权限。时间窗口写对了，不代表调用凭据就具备执行该操作的权限。

## 过期、尚未生效和撤销：三个不同的失败边界

有效窗口至少包含两种时间失败：令牌尚未到 not_before，或者已经超过 expires_on。官方说明 RealtimeKit 会在参与者进入会议前拒绝这两类令牌。对系统设计来说，这意味着可以把“太早访问”和“太晚访问”都视为准入失败，而不是让客户端先加入、再由业务逻辑踢出。

这还带来一个实际收益：官方材料明确指出，被拒绝的过期或尚未生效令牌不会产生参与者进入会议后的计费。也就是说，时间窗口不仅是访问控制字段，也能把明显无效的尝试挡在会议参与状态之前。这里不能推导出完整的价格模型，但可以确认：准入前拒绝与已经进入会议后再处理，在资源和计费语义上并不等价。

撤销则是第三种状态。它不是自然到期，也不是尚未到生效时间，而是业务主动改变某个已签发令牌的状态。例如，访客被取消资格、用户账号被风控系统冻结，或者一张链接已经被怀疑泄露，都可能触发撤销。

但撤销并不等于全球瞬时阻断。官方更新明确说明，单个令牌撤销后，最多可能需要 60 秒才能在所有地方停止工作。如果要求立即阻止当前参与者，官方建议删除参与者，而不是只依赖撤销令牌。这个差异应该直接写进威胁模型：撤销适合收回凭证，删除参与者才是更强的当前会话处置动作。

因此，安全策略可以分成两档：低紧急度事件使用撤销，接受传播延迟；高紧急度事件执行删除参与者，并把撤销作为后续凭证清理。不要用“撤销接口调用成功”替代“参与者已经无法继续停留”的结论。

## 一套可复现的后端验证清单

在接入真实业务前，可以围绕四类状态设计验证，而不是只检查 HTTP 请求是否返回成功。

### 1. 窗口配置检查

记录每次签发请求中的 not_before、expires_on、会议 ID、业务用户 ID 和自定义参与者 ID。检查时间是否带时区、结束时间是否晚于开始时间、窗口是否符合业务预约。自定义参与者 ID 应与业务系统中的稳定用户标识对应，避免同一个人因重复请求生成无法追踪的记录。

### 2. 准入行为检查

至少验证三种时刻：早于 not_before 尝试加入、窗口内尝试加入、晚于 expires_on 尝试加入。预期分别是拒绝、允许、拒绝。验证时应使用独立测试参与者和测试会议，避免把失败请求混入真实会议的运营数据。

### 3. 撤销传播检查

撤销单个令牌后，不要立即断言所有边缘位置都已同步。把 60 秒作为官方给出的最坏等待边界，并记录撤销发起时间、客户端重试时间和实际观察到的结果。如果需求是立即阻断，验证删除参与者路径，而不是把撤销路径当作替代品。

### 4. 兼容性检查

先确认旧集成不传 token 时间字段时仍使用原有行为，再为新业务逐步开启窗口。检查客户端是否能处理“令牌尚未生效”“令牌已过期”“令牌已撤销”这些准入失败，不要只在前端显示一个笼统的“加入失败”。

这些检查的重点是状态和时间，而不是只看添加参与者 API 的返回体。一个成功返回只能证明服务端接受了请求，不能证明客户端在正确的时间进入，也不能证明撤销已经完成全球传播。

## 设计取舍：固定默认值、短窗口与即时处置

继续使用 100 天默认令牌的优点是改动最小，适合不关心时间边界的旧应用；缺点是泄露后的暴露面长，业务也无法把一次活动和一次授权清晰绑定。显式设置时间窗口会增加后端的时间处理和测试成本，但能把“预约开放”表达为服务端可验证的规则。

窗口也不宜机械地压缩到极短。过短会放大客户端时钟偏差、网络延迟和用户提前进入的影响。更合理的做法是先定义业务容忍度，再决定是否为进入前准备预留缓冲，同时保留会议内的身份和参与者管理逻辑。缓冲不是绕过过期控制，而是对真实网络条件的工程让步。

撤销和删除也不应二选一。撤销解决“这张凭证以后还能不能使用”，删除解决“当前参与者是否继续留在会议里”。两者针对的对象不同，组合使用才能覆盖凭证泄露和实时事件处置。

## 原创结论：把令牌生命周期当成状态机，而不是字符串字段

RealtimeKit 这次更新最值得借鉴的地方，不是给 token 增加了两个时间属性，而是把参与者授权从“签发一次、长期有效”推进为可观察的状态机：未生效、有效、过期、撤销，以及当前会议中的参与者状态。

工程上应至少分开记录三条证据链：令牌何时签发，服务端何时认为它有效，参与者何时真正进入或被移除。只有把这三条时间线分开，才能解释“令牌已撤销但短时间仍可用”“令牌有效但用户尚未进入”“令牌过期且没有产生参与者计费”这类看似矛盾的现象。

最终的验收标准也应从“能否拿到令牌”升级为四个问题：它是否只在正确的时间生效，窗口外是否在进入前被拒绝，撤销是否按官方延迟边界验证，紧急事件是否有删除参与者的即时处置路径。对实时系统而言，安全不是把失效时间写进 JSON，而是让每一种失败都对应明确的系统动作和可核验证据。
