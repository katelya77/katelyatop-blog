## 先把公告读成一次变更事件

GitHub Changelog 公告显示，GitHub Copilot 将在 2026 年 12 月 14 日退役 Claude Fable 5、Claude Haiku 4.5、Gemini 3.8 Flash、Gemini 4 Argon、Grok 4.6 和 Kimi K3。公告覆盖 Copilot Chat、内联编辑、ask 模式、agent 模式以及代码补全等体验，并为其中多数模型列出了建议替代项：Claude Fable 5 对应 Claude Fable 5.2，Claude Haiku 4.5 对应 Claude Haiku 5.5，Gemini 3.8 Flash 对应 Gemini 4 Hydrogen，Gemini 4 Argon 对应 Gemini 4 Carbon，Grok 4.6 对应 Grok 4.7；Kimi K3 的替代项当时尚未公布。

这不是一条简单的“版本升级提示”。它至少包含四种不同变化：旧模型可能彻底不可选，替代模型的能力和输出风格未必相同，覆盖的 Copilot 入口不止聊天窗口，企业策略是否允许新模型还取决于组织配置。公告还说明，在默认模型启用机制下，替代模型会自动为 Copilot Enterprise 和 Copilot Business 客户启用，前提是管理员没有关闭全局默认或明确禁用该模型；如果组织关闭了全局默认，则需要在 Copilot 设置中的模型策略里手动启用。

因此，迁移目标不应写成“把 A 改成 B”，而应写成：在退役日期之后，受影响工作流仍能选择可用模型，组织策略与个人体验一致，关键任务的结果质量处于可接受范围，并且找不到替代模型时能够显式失败，而不是悄悄落到未知模型。

## 模型名称只是最外层依赖

一个团队通常会在多个位置使用模型：开发者在 Chat 中手动选择，编辑器通过默认模型完成代码补全，自动化流程使用 agent 模式，内部规范或脚本则可能记录推荐模型。公告同时覆盖这些体验，意味着只搜索配置文件中的模型字符串是不够的。

可以先建立一份“模型使用面清单”，把每一项依赖拆成五列：入口、使用目的、当前模型、策略来源、退役后的预期行为。

```text
入口                 目的             当前模型          策略来源          预期行为
Chat                 问答             Claude Fable 5    用户/组织         切换到 5.2
Inline edits         局部修改         Gemini 3.8 Flash   默认策略          切换到 Hydrogen
Ask mode             代码解释         Grok 4.6          用户选择          切换到 Grok 4.7
Agent mode           多步任务         Kimi K3            组织策略          等待官方替代项
Completions          补全             受影响模型         默认策略          验证是否仍可用
```

这张表的价值在于把“谁在使用模型”与“模型由谁控制”分开。管理员关闭全局默认时，用户侧看到的选择器可能与组织允许列表不同；个人订阅的特殊规则也不能直接推导到企业用户。公告特别注明，Claude Haiku 4.5 对个人 Copilot 年付订阅者仍可用，这说明同一个模型的退役语义可能包含用户类型条件，不能只按模型名称做全局替换。

工程上可以把扫描分为两步。第一步是静态搜索：检查仓库、团队文档、脚本、提示词模板和测试用例中的旧模型名称。第二步是运行时盘点：在每个 Copilot 入口确认当前可选模型、默认模型和组织策略。静态搜索找不到的手动选择仍然可能影响交付；运行时没有验证的配置，也不能证明自动化流程已经迁移。

## 替代模型需要行为验收

替代模型是产品方建议的迁移方向，不等于对所有任务完全等价。公告给出了替代关系，但没有承诺输出格式、响应速度、工具使用倾向、代码修改范围或上下文处理方式完全不变。因此，验收重点应放在工作流契约，而不是模型名称是否更新。

可以为每类入口准备一组固定任务，任务本身不应依赖某个具体模型的偶然回答，而应检查可观察结果：

1. **代码理解**：给定一个包含多个模块的小型变更，要求模型指出调用链、风险点和需要修改的文件，检查是否遗漏关键依赖。
2. **代码编辑**：要求只修改指定文件，检查是否越界写入、是否保留类型约束、是否能通过既有测试。
3. **工具或代理任务**：提供一个需要读取、修改、验证的多步任务，检查模型是否在每一步报告状态，失败后是否停止并说明原因。
4. **补全体验**：使用相同的短函数、类型定义和注释上下文，记录建议是否符合项目风格，不能只比较单次延迟。
5. **安全边界**：构造包含敏感字段、危险命令或越权要求的任务，确认替代模型仍遵守团队的拒答和确认规则。

验证记录至少应包含日期、入口、组织策略、模型名称、任务版本、结果摘要和人工判定。不要把“能生成答案”作为通过条件；真正需要确认的是任务完成率、修改范围、测试结果和失败可解释性。

如果团队没有统一的评测平台，也可以用仓库内的固定样例建立最小回归集：每个入口准备 5 到 10 个代表性任务，结果用人工评分加命令检查。对于代码编辑场景，模型输出只是候选变更，最终门槛仍是格式化、静态检查、单元测试和人工审查。

## 策略迁移要验证三个层面

第一层是**可见性**。管理员是否启用了替代模型？公告说明，企业客户在默认模型启用时可能自动获得替代模型，但关闭全局默认或显式禁用模型会改变结果。迁移检查不能只看个人账户中的模型选择器，还要确认组织级策略。

第二层是**入口一致性**。模型在 Copilot Chat 中可用，不代表它在内联编辑、代码补全或 agent 模式中具有相同表现。公告明确把多个 Copilot 体验纳入退役范围，因此应逐入口验证，而不是选一个界面截图作为全局证据。

第三层是**日期切换**。在退役日前测试通过，只能证明候选配置当前可用。还需要验证退役日之后的预期行为：旧模型不应继续被脚本硬编码调用；新模型应能被策略识别；没有替代项的模型应进入待定或阻断状态。

可将迁移门禁写成简单的配置检查：

```yaml
migration:
  effective_date: "2026-12-14"
  deprecated:
    - "Claude Fable 5"
    - "Claude Haiku 4.5"
    - "Gemini 3.8 Flash"
    - "Gemini 4 Argon"
    - "Grok 4.6"
    - "Kimi K3"
  replacements:
    "Claude Fable 5": "Claude Fable 5.2"
    "Claude Haiku 4.5": "Claude Haiku 5.5"
    "Gemini 3.8 Flash": "Gemini 4 Hydrogen"
    "Gemini 4 Argon": "Gemini 4 Carbon"
    "Grok 4.6": "Grok 4.7"
  unresolved:
    - "Kimi K3"
```

这不是 GitHub 官方配置格式，而是团队内部的变更清单示例。关键规则是：未公布替代项时保留 unresolved，不要填入猜测名称；配置检查发现 unresolved 时应提示人工决策或阻止发布，而不是自动选择一个“看起来接近”的模型。

## 失败边界比成功路径更重要

最危险的情况不是模型明确报错，而是旧模型被移除后，系统静默切换到另一个未评估模型。这样表面上流程仍然成功，实际却可能改变代码修改范围、回答风格或安全策略。对于需要稳定输出的团队，宁可让任务进入人工确认，也不应把未知回退伪装成成功。

另一种边界是策略不同步。管理员启用了替代模型，但用户客户端或文档仍保留旧推荐；或者用户可以在 Chat 中选择新模型，自动化 agent 却仍依赖旧模型。此时“账号能用”不等于“工作流已迁移”。

还要区分稳定发布与预发布信号。研究材料中的 Qwen Code `v0.27.2-nightly.20261113.6f754be654` 明确标为 Pre-release，属于项目发布页上的夜间版本。它可以说明软件项目会通过预发布渠道快速迭代，但不能作为 GitHub Copilot 模型退役或替代关系的证据，更不能据此推断某个模型已经正式上线。编辑和工程团队都应把这种材料标为预发布证据，避免把“看到了版本”写成“生产可用”。

## 一份可执行的迁移验收清单

在 2026 年 12 月 14 日之前，可以按以下顺序完成检查：

- 统计所有受影响模型在 Chat、内联编辑、ask、agent 和补全中的使用位置。
- 确认每个组织的全局默认、模型策略和显式禁用项。
- 对已有替代关系逐项建立固定任务回归集。
- 对个人订阅、Business、Enterprise 等不同用户类型分别验证，不把特殊例外扩展为普遍规则。
- 对 Kimi K3 这类尚未公布替代项的模型建立阻断或人工确认流程。
- 在退役日期前后分别保留模型可见性、策略状态和任务结果证据。
- 检查旧名称是否仍出现在脚本、文档、自动化任务和培训材料中。
- 只有在结果、权限和失败行为都通过后，才删除旧模型的兼容分支。

原创地说，模型退役的核心不是“换一个更大的模型”，而是把模型当作会过期的外部依赖管理。版本公告提供的是时间窗口和建议映射，团队仍需补齐使用面盘点、策略核对、行为回归和失败门禁四条证据链。只有这样，迁移完成才意味着工程系统在退役之后仍然可解释、可验证，而不是某个选择器恰好显示了一个新名字。
