一项技能出现在 Agent 的菜单里，不代表它已经获得执行命令的许可；一个钩子能够拒绝命令，也不代表整个技能都被审查过。Claude Code v2.1.332 的发布说明把这两个容易混淆的边界放在了同一版本里：MCP 服务器提供的技能可以出现在 `/` 菜单，新增的 `PreSkillShellCommand` 钩子则可在技能或命令加载时拒绝其中的内联 shell 命令。

这不是一套完整的权限模型，也不是“接入 MCP 就安全”的承诺。它更像是把技能发现与特定命令的加载门禁，显式放进可观察、可验收的流程中。真正的工程问题是：团队能否确认技能来自哪里、何时会触发门禁，以及拒绝之后系统究竟还会做什么。

## 两项变化，两个不同阶段

按照 v2.1.332 的发布说明，来自 MCP 服务器的技能会以 `server:skill` 的形式出现在 `/` 菜单中；其他技能仍保留原来的名称。这个命名差异提供了来源线索，至少让用户在选择技能时可以区分服务器提供的条目与其他技能。它解决的是“发现与辨认”，不是“授权与执行”。

同一版本新增 `PreSkillShellCommand` hook event。发布说明给出的能力边界是：在技能或命令加载时，拒绝它所包含的内联 shell 命令。关键词是“加载时”和“内联 shell 命令”。这既不同于等命令执行后再记录，也不能直接扩大解释成对所有终端操作、工具调用或外部副作用的拦截。

可以把两者放进一个简化流程理解：MCP 服务器暴露技能，Claude Code 将技能呈现在菜单中；用户或 Agent 选择后，加载过程可能遇到内联 shell 命令；门禁决定是否拒绝这类命令。这个流程图是根据发布说明所作的工程化归纳，不等于官方给出了完整的内部执行顺序。尤其是技能内容如何被解析、hook 在何种上下文运行、拒绝后是否中止整个技能，材料都没有说明，不能把推断当成产品保证。

## 来源标记不是可信度证明

`server:skill` 是有用的来源标识，但标识只回答“它看起来来自哪个服务器”，不能单独回答服务器是否可信、技能是否经过审核、内容是否发生变化。若团队把 MCP 服务器当作技能分发渠道，仍需要单独治理服务器身份与变更：谁批准接入、技能更新如何被发现、使用者如何确认本次加载对应的版本。

这是从命名行为推导出的工程建议，不是发布说明宣称的新能力。S8 只明确说 MCP 技能会显示在菜单里，并采用 `server:skill` 形式；它没有声称提供签名校验、版本锁定、内容审计或服务器信任评分。因此，不能因为菜单里出现了一个带服务器前缀的名称，就把它当作可信供应链证明。

同样，`PreSkillShellCommand` 的名字容易让人以为它会覆盖所有 shell 执行。发布说明支持的说法更窄：它可以在加载时拒绝技能或命令包含的内联 shell 命令。至于脚本是否由其他工具调用、命令是否从外部文件读取、是否存在不同的执行路径，都应作为待验证问题，而非假定已被保护的范围。

## 用隔离工作区验收，而不是凭菜单判断

下面是一份不依赖臆造配置字段的验收清单。先准备一个无敏感数据、无生产凭据的临时工作区，以及一个可控的 MCP 测试服务器；具体服务器配置和 hook 配置应依照对应版本的官方文档填写。现有材料没有提供配置语法，因此不应复制未经核对的 JSON 示例。

1. **确认版本与基线。** 记录被测客户端的准确版本，并保存当前技能菜单的结果。测试目标应为 v2.1.332；另选一个较早版本做兼容性对照。不要只记录“更新了”，要能复核实际运行版本。
2. **验证技能发现。** 让测试服务器提供一个无副作用的测试技能，检查它是否出现在 `/` 菜单中，以及名称是否体现 `server:skill`。同时确认非 MCP 技能仍按发布说明所述保留原名称。菜单显示只验证发现路径，不验证技能内容的安全性。
3. **构造最小拒绝用例。** 在隔离环境中准备一个包含可辨识、无破坏性内联 shell 命令的技能或命令，并按该版本官方文档配置 `PreSkillShellCommand`。验证加载时是否发生拒绝，并确认该命令没有被执行。不要用删除文件、改写真实配置或访问生产服务作为测试动作。
4. **分别测试拒绝范围。** 对技能与命令两种入口分别验收；检查拒绝的是内联命令、整个技能加载，还是其他范围。发布说明没有明确拒绝后的交互、日志和后续行为，测试记录应如实写结果，不要把一次拒绝自动推广为所有入口都受保护。
5. **检查兼容边界。** 发布说明特别提醒：在 v2.1.331 及更早版本中，设置文件若写入这个事件名，启动时会弹出对话框。分别在旧版本的隔离配置中验证该提示，并避免把新事件配置直接推广到旧版本用户。
6. **留下可追踪证据。** 保存版本号、测试技能标识、预期动作、实际提示与命令是否运行的结果。日志或截图应移除令牌、个人路径和其他敏感信息。用同一组测试在升级前后对照，才能区分版本变化与配置差异。

这套检查清单验证的是已知行为及其边界，不是完整安全认证。若官方文档没有明确事件参数、拒绝语义或审计输出，就把它列为待补证项；不要为了让验收表“全绿”而自行假设默认行为。

## 旧版本提示意味着配置也有生命周期

v2.1.332 的发布说明还有一个容易被忽略的兼容细节：v2.1.331 及更早版本若在设置文件中写入 `PreSkillShellCommand`，启动时会弹出对话框。它说明事件名并非对所有版本都无感知，配置迁移要考虑使用者仍运行旧版本的情况。

发布说明并没有提供完整的旧版本解析规则，也没有说明提示框的按钮、处理结果或自动化运行时的具体表现。因此，稳妥做法不是推测“旧版会忽略”或“旧版会失败”，而是在推广前用目标版本验证：新版本配置能否正常工作，旧版本是否出现预期提示，以及提示是否会阻断团队的启动流程。若无法保证客户端版本一致，就应把配置分发和版本升级作为同一变更来管理。

另外，S1 记录了 Codex `0.174.0-alpha.6` 的预发布条目，但给出的材料只有版本与预发布状态，没有可用于比较的功能说明。它能支持的结论仅限于“存在这条 alpha 发布记录”，不能拿来推导其他工具的技能治理方式。版本材料的证据等级不同，比较时也应限制结论范围。

## 工程取舍：门禁要可拒绝，也要可诊断

加载期拒绝的价值，在于能把某些命令挡在执行之前；代价则是，拒绝本身会改变技能是否可用。若 hook 配置错误、规则过宽或版本不兼容，用户可能遇到技能无法加载。反过来，若团队只追求“不要打断使用”，却没有验证拒绝确实生效，门禁也可能只存在于配置文件里，而没有形成有效控制。

因此，门禁设计至少要同时回答三个问题：什么范围会被检查、拒绝后用户能看到什么、如何判断命令没有执行。发布说明只明确了拒绝能力发生的阶段和对象范围的一部分；其余问题需要借助对应版本的官方文档与隔离测试补齐。在证据不足时，限制使用场景比虚构一套更强的保障承诺可靠。

更实用的团队规则是把技能治理拆开：来源治理负责批准 MCP 服务器及其更新；加载门禁负责检查已知的内联 shell 命令；运行验收负责确认拒绝效果与兼容性；使用者仍需判断技能请求是否符合当前任务。任何一个环节通过，都不能替代其他环节。

## 结论：把“能看见”与“能执行”分开

Claude Code v2.1.332 的两项变化，分别改善了 MCP 技能的可发现性和加载阶段的命令拒绝能力。它们值得关注，但没有证据表明 `server:skill` 就是可信证明，也没有证据表明 `PreSkillShellCommand` 覆盖所有执行路径。

更可靠的落地方式，是用来源标记提高辨认度，用窄范围、可复现的测试确认拒绝行为，再用版本对照管理旧配置的兼容风险。Agent 工具链的安全边界，不在菜单里多了一个名称，也不在配置文件里多了一个事件名；边界要靠明确的适用范围、可观察的失败结果和可重复的验收共同建立。
