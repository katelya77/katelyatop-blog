## 一个崩溃修复，暴露了 CLI 的真实边界

llama.cpp 的 b12177 发布页明确列出一项修复：CLI 在 prompt 或文件中遇到非法 UTF-8 时可能崩溃。该版本同时被标记为 Pre-release，发布页还展示了多个平台和后端构建目标。这里有两个容易被忽略的信号。

第一，问题发生在模型推理之前。用户提供的 prompt、文件内容和命令行参数，必须先经过操作系统、文件读取、字符串转换和 CLI 参数处理，之后才可能进入 tokenizer 或推理循环。只要输入边界上的字节处理不稳定，模型本身即使完全正常，程序仍然可能在“准备推理”阶段退出。

第二，“修复了崩溃”并不等于“所有文本输入都正确”。非法 UTF-8 可以出现在 prompt、文件末尾、截断的多字节字符、管道输入或不同平台生成的文件中。一个版本能够处理单个复现样例，不代表它已经覆盖了输入来源、错误策略和后续输出的全部组合。

因此，这类发布不能只看版本号，也不能只执行一次正常 prompt。更合理的判断对象是：程序面对不合法输入时，是否保持可预测的进程行为；面对合法输入时，是否没有因为修复错误处理而改变既有语义。

## 从字节到推理：问题发生在哪里

UTF-8 是一种变长编码。ASCII 字符占用一个字节，而部分非 ASCII 字符由多个字节组成。一个合法字符要求首字节与后续字节满足特定结构；如果文件被截断、字节被替换，或者外部系统把二进制内容误当成文本，就可能得到无法解码的序列。

CLI 通常会遇到三种不同输入路径：

1. 直接参数，例如 `--prompt` 后面的文本；
2. 文件参数，例如从文件加载 system prompt 或上下文；
3. 标准输入或管道，例如脚本把动态内容传给交互式程序。

这三条路径看起来都在传递“字符串”，但它们的失败条件并不相同。直接参数往往先经过 shell 和进程参数编码；文件输入保留原始字节，可能包含零字节、截断字符或混合编码；标准输入还叠加了流式读取、EOF 时机和分块边界。

工程上最危险的假设是：只要输入来自文本文件，就一定是合法文本。文件扩展名不能证明编码，编辑器界面也不能证明所有字节都经过一致处理。更稳妥的设计是把输入分成两个阶段：先读取字节，再明确执行解码策略；解码失败时记录可诊断的错误并结束当前操作，而不是让异常穿过字符串、tokenizer 或 UI 层，最终演变成未处理崩溃。

这也是为什么非法 UTF-8 修复值得单独验收。它测试的不只是某个 `if` 分支，而是输入边界与整个调用链之间的契约：错误输入应该被拒绝、替换、跳过还是原样传递？不同策略会影响 prompt 内容、token 数量、日志可读性和自动化脚本的判断。发布说明只告诉我们修复目标，不能替我们决定这些行为是否符合业务需求。

## 一套不依赖模型质量的复现检查

验证这类修复时，先把模型因素排除出去。使用极短的 prompt、最小模型或只验证程序启动和退出行为，可以避免把下载、显存、上下文长度等问题误判为编码问题。下面的检查重点是输入和进程，而不是输出内容的智能程度。

先准备一个包含非法字节的文件。不要在编辑器里复制粘贴，因为编辑器可能自动替换或清理内容：

```bash
printf 'ascii-prefix\377ascii-suffix\n' > invalid-utf8.txt
printf '\342\202\n' > truncated-utf8.txt
printf '正常文本\n' > valid-utf8.txt
```

第一个文件包含一个不符合 UTF-8 规则的字节，第二个文件模拟多字节字符在文件末尾被截断，第三个文件用于回归合法中文输入。检查文件类型和原始字节时，应以十六进制输出为准：

```bash
xxd -g 1 invalid-utf8.txt
xxd -g 1 truncated-utf8.txt
file --mime invalid-utf8.txt truncated-utf8.txt valid-utf8.txt
```

随后分别通过文件参数、标准输入和直接 prompt 运行同一个构建。具体选项名称应以当前构建的 `--help` 输出为准，不要把某个版本的参数名硬编码到所有脚本中：

```bash
./build/bin/llama-cli --help
./build/bin/llama-cli --version
./build/bin/llama-cli <当前文件参数> invalid-utf8.txt
cat invalid-utf8.txt | ./build/bin/llama-cli <当前标准输入参数>
./build/bin/llama-cli <当前 prompt 参数> "ASCII smoke test"
```

每次运行至少记录四项结果：退出码、是否产生崩溃信号、标准错误中的诊断信息、进程是否留下异常临时文件或僵尸进程。可以用 shell 保存退出码，但不要用“命令失败就继续”的写法掩盖问题：

```bash
set +e
./build/bin/llama-cli <当前文件参数> invalid-utf8.txt >out.txt 2>err.txt
status=$?
set -e
printf 'exit=%s\n' "$status"
sed -n '1,80p' err.txt
```

这里不应预设某个固定退出码。不同 CLI 可能选择替换非法字节、报告输入错误后正常退出，或者拒绝请求并返回非零状态。真正不能接受的是段错误、无诊断退出、无穷重试，或同一个文件在不同输入路径上出现无法解释的行为差异。

## 把预发布版本放进证据分层

b12177 是预发布版本，因此它适合验证修复方向，不适合直接推导“生产环境已经安全”。预发布构建的证据至少分为四层。

第一层是发布证据：仓库发布页是否明确列出修复项，版本是否确实对应被测试的提交或构建产物。第二层是构建证据：目标平台是否成功生成二进制，依赖探测是否选择了预期后端，构建过程中是否出现降级。第三层是行为证据：非法 UTF-8、合法 UTF-8、空文件、超大文件和管道输入是否都得到可解释结果。第四层是回归证据：正常 prompt、文件上下文、交互式输入和脚本调用没有因为错误处理变化而退化。

这四层不能相互替代。发布页有修复说明，不代表本地构建使用了对应代码；构建成功，不代表运行时走到了相关路径；单个非法文件不崩溃，不代表流式输入的分块边界安全；正常 prompt 成功，也不能证明异常输入处理正确。

可以把验收结果写成一张最小矩阵：

| 输入来源 | 合法文本 | 非法字节 | 截断多字节字符 | 关注点 |
| --- | --- | --- | --- | --- |
| 直接参数 | 语义未变 | 不崩溃 | 能诊断 | shell 与参数边界 |
| 文件 | 正常加载 | 可预测拒绝或替换 | EOF 行为明确 | 字节读取与解码 |
| 标准输入 | 正常结束 | 不崩溃 | 分块不改变结果 | 流式状态机 |

矩阵的价值不在于制造大量测试，而在于防止团队只验证最顺手的路径。尤其是修复由“文件中的非法 UTF-8”触发时，不能只测文件参数后就宣布完成；标准输入与直接参数可能经过完全不同的代码。

## 失败边界与工程取舍

处理非法文本有三种常见取舍。严格拒绝最容易保持数据完整性：程序明确指出输入不可解码，不会静默改变 prompt。但它可能影响自动化任务，需要调用方修复数据。替换非法序列可以提高可用性，让任务继续执行，但模型看到的内容已经不是原始输入，日志和审计必须记录替换发生。跳过非法字节看似简单，却可能把两个原本分离的文本片段拼接起来，导致语义变化，通常不适合没有明确契约的通用 CLI。

无论选择哪种策略，都要定义三个边界：错误是否可观测、退出状态是否稳定、重复运行是否得到一致结果。对交互式程序，友好的错误提示很重要；对 CI 或代理调用，稳定的非零退出状态和机器可解析的错误类别更重要。不要用“返回空 prompt”这种成功形状的降级，因为上层很可能把它误认为用户确实提供了空输入。

还要注意日志中的隐私问题。非法文件可能来自用户代码、配置或敏感数据，诊断信息不应直接打印整个 prompt。记录输入来源、字节偏移、错误类型和处理策略，通常比输出原始内容更适合自动化和审计。

## 结论：修复输入崩溃，验收的是契约而不是演示

llama.cpp b12177 的非法 UTF-8 修复提醒我们：推理工具的稳定性不只取决于模型、GPU 和吞吐量，也取决于最靠近用户的一小段输入处理代码。CLI 是一个边界系统，它同时连接 shell、文件系统、编码、tokenizer、推理循环和自动化编排；任何一层把“字节”未经定义地当成“文本”，都可能把普通数据错误变成进程崩溃。

对预发布版本，最可靠的做法不是等待更多宣传材料，而是建立小而明确的验证闭环：锁定版本和构建产物，准备原始字节样本，覆盖文件、管道和直接参数三条路径，记录退出行为与诊断，再用合法输入做回归。只有当异常输入不再以崩溃结束、合法输入保持原有语义、失败结果能够被上层准确识别时，这项修复才从发布说明中的一句话，变成可以纳入工程流程的可靠契约。
