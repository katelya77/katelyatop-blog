## 这不是“请求变快了”，而是连接生命周期被修正

llama.cpp 的 b12404 发布说明中包含一项明确的服务器修复：`Fix connection reuse after streamed responses`。这句话的信息密度很高，但也很克制。它没有声称所有请求延迟下降，也没有承诺吞吐量提升，更没有把它描述成新的推理能力。它指出的是一个更底层的问题：一次流式响应结束之后，下一次请求是否还能安全地使用同一条连接。

流式输出通常意味着服务端不会一次性生成完整响应再返回，而是边生成、边发送多个数据片段。客户端因此需要同时处理两个状态：业务数据是否已经收完，以及 HTTP 消息是否已经在传输层正确结束。前者是应用语义，后者是协议语义。只要两者没有对齐，连接池就可能把一条仍处于不确定状态的连接交给下一个请求。

这类问题很容易被误判为“偶发超时”。第一次请求往往成功，单次命令行调用也看不出异常；故障通常在第二次或第三次请求复用连接时出现。表现可能是读取到残留字节、等待一个永远不会到来的结束标记、连接被服务端关闭后重新建立，或者代理认为响应仍未完成而继续缓存。因而，修复的核心不是让流式响应更快，而是让响应结束后的连接重新回到可预测状态。

## 从字节流到连接池：问题发生在哪里

可以把一次请求拆成四层，而不要只看“HTTP 200”。

第一层是生成器。模型推理产生增量结果，服务端把这些结果包装成连续的数据片段。这里的片段边界是应用层选择，不等于 TCP 数据包边界；一次 `read` 可能拿到半个片段，也可能同时拿到多个片段。

第二层是 HTTP 消息 framing，也就是客户端如何判断响应何时结束。它可能依赖固定长度，也可能依赖分块传输的结束标记，或者依赖连接关闭。流式响应尤其不能把“暂时没有新数据”当成“响应已经完成”。正确的客户端必须等待协议层明确的结束条件。

第三层是连接状态。只有在响应体已被完整消费、协议尾部已处理、连接没有被标记为不可复用时，连接池才可以把它放回空闲集合。若客户端提前停止读取，或者服务端结束响应时留下未消费的数据，复用就会把上一个请求的尾部与下一个请求混在同一条字节流里。

第四层是中间代理。反向代理、TLS 终止层和负载均衡器可能对流式响应做缓冲、超时或连接管理。直连时通过，不代表经过代理后仍然能复用；相反，直连失败也可能被代理的强制关闭行为掩盖。因此验收时必须区分“服务端连接状态正确”和“整个链路看起来能用”。

b12404 的官方发布材料只确认了修复目标，并没有给出适用于所有部署方式的性能数字。工程上更稳妥的结论是：先把它当作连接生命周期正确性修复，再用自己的客户端、并发度和代理配置测量收益，而不是直接把版本升级宣传成吞吐优化。

## 可复现的最小验证：先证明第二个请求真的复用了连接

验证不需要一开始就接入完整业务。应先构造一个能返回流式数据的测试端点，并把端口、路径和请求体替换为实际服务的配置。下面的命令只展示测试方法，不假定某个项目的具体 API：

```bash
export URL='http://127.0.0.1:PORT/your-stream-endpoint'
export BODY='{"prompt":"return a short response"}'

curl --http1.1 --no-buffer -sS \
  -H 'Content-Type: application/json' \
  -d "$BODY" "$URL" > /tmp/stream-1.out

curl --http1.1 --no-buffer -sS \
  -H 'Content-Type: application/json' \
  -d "$BODY" "$URL" > /tmp/stream-2.out

wc -c /tmp/stream-1.out /tmp/stream-2.out
```

这一步只能证明两个独立命令都能完成，不能证明连接被复用。要观察连接行为，应使用一个长期运行的客户端连接池，而不是每次都启动新的进程。以 Python 标准库为例，下面的骨架将多个请求放进同一个 `HTTPConnection`。真实环境中应根据响应头和接口协议解析完整响应体；示例重点是“完整读取后再发下一个请求”：

```python
import http.client
import json
import os

host = os.environ["HOST"]
port = int(os.environ.get("PORT", "80"))
path = os.environ["PATH"]
body = json.dumps({"prompt": "return a short response"})

conn = http.client.HTTPConnection(host, port, timeout=30)
for index in range(10):
    conn.request(
        "POST", path, body=body,
        headers={"Content-Type": "application/json"},
    )
    response = conn.getresponse()
    payload = response.read()
    print(index, response.status, len(payload))
conn.close()
```

如果服务端支持流式响应，`response.read()` 的意义不是把流式能力关闭，而是确保客户端在发起下一个请求前消费完本次响应。实际客户端应逐段处理数据，同时在检测到协议规定的结束条件后确认读取完成。若为了提前返回而中断读取，连接就不应无条件放回连接池；可以选择显式关闭它，牺牲一次复用换取状态确定性。

验证时记录至少四项结果：每次请求的状态码、完整响应长度、请求间隔和连接是否被关闭。不要只记录总耗时，因为自动重连可能把连接错误隐藏在一次成功请求里。若能开启服务端访问日志，还应比较请求是否来自同一个连接标识；若无法获得连接标识，至少观察重复请求时是否出现额外 TCP/TLS 建连。

## 验收矩阵：正常结束、提前取消和代理链路不能混为一谈

第一组是正常结束。连续发送几十到几百次短流式请求，每次都完整消费响应体，检查是否出现随机空响应、协议解析错误或第二个请求等待超时。这组测试回答的是最基本的问题：一次正常完成的流式响应能否把连接还给连接池。

第二组是长响应。短响应可能恰好在一个缓冲区内完成，掩盖 framing 问题。应让服务端产生更长的输出，并在读取过程中记录片段到达时间。重点不是追求某个固定吞吐数字，而是确认最后一个片段之后，客户端能明确识别响应结束，并能立即发起下一次请求。

第三组是客户端取消。用户关闭页面、任务超时或上游 Agent 放弃结果时，客户端可能只读了一部分响应。此时不能把“服务端最终会结束”当作连接可复用的充分条件。应分别测试：读取到一半后关闭响应、发送连接关闭、超时后释放连接。验收标准是下一次请求不会继承上一次的残留数据；如果连接被主动丢弃，至少不能伪装成健康的空闲连接。

第四组是并发连接池。单连接串行测试通过后，再使用固定大小的池发送并发请求。观察连接池是否耗尽、是否出现队头阻塞、是否频繁新建连接。这里要区分两类现象：服务端确实不能复用连接，和客户端为了隔离流式任务而主动限制复用。前者是正确性问题，后者可能是明确的资源策略。

第五组是代理路径。把同一测试分别放在直连、反向代理和 TLS 终止之后运行。检查代理是否启用响应缓冲、是否设置过短的读取超时、是否在流式响应结束时复用上游连接。代理链路的成功不能替代直连验证，因为代理可能通过关闭连接来规避复用错误；直连成功也不能证明真实生产路径没有额外边界。

## 失败边界：连接复用不是越多越好

连接复用的价值来自减少握手、减少连接建立和降低连接管理开销，但它不是无条件优化。流式请求持续时间长，连接池中的连接可能长期被占用；如果池大小与并发模型不匹配，复用反而会增加等待。长连接还会放大空闲超时、负载均衡连接迁移和 NAT 状态失效等问题。

因此，不能把“所有响应都复用”作为策略。至少需要以下判断：响应体是否已经完整消费；服务端是否明确允许保持连接；中间代理是否允许该连接继续存活；客户端是否在取消路径上正确清理；连接是否超过空闲或使用次数上限。任何一项不确定，都应关闭连接或交给库的标准连接管理逻辑，而不是手工强行复用。

还要警惕测试工具制造的假象。`curl` 每次单独执行通常不会覆盖连接池复用；只测非流式接口无法暴露流式结束问题；只测第一个请求无法覆盖复用路径；只看成功率则可能漏掉大量隐式重连。真正有效的测试必须让“同一连接上的下一个请求”成为断言的一部分。

## 如何看待 b12404：修复项应进入升级验收，而不是直接进入性能宣传

官方材料把 b12404 标为预发布版本，并列出服务器连接复用修复。另一个材料中的 vLLM v0.34.0rc4 同样是候选版本，说明在推理服务生态里，发布标签本身并不等于生产适配结论。候选版或预发布版可以提供重要修复线索，但最终是否适合升级，仍需要把二进制、客户端、代理和部署参数放在同一条验证链上。

对使用 llama.cpp 服务的团队，较稳妥的升级顺序是：先固定旧版本基线，保存流式请求的成功率、取消率、重连次数和连接建立次数；再在隔离环境升级 b12404，重复同一组串行、长响应、取消、并发和代理测试；最后只把确认过的收益写入发布说明。若只观察首个请求延迟，无法证明这项修复已经被验证。

我的原创结论是：流式推理服务的性能边界，往往不在“每秒生成多少 token”，而在“生成结束后连接是否仍然可预测”。一次请求的尾部处理决定了下一次请求的起点；连接池、代理和取消逻辑任何一个环节含糊，所谓复用就可能变成隐蔽的重连或更难定位的协议错误。把连接复用当作可验证的状态转换，而不是一个开关，才是这类版本修复真正值得带回工程现场的地方。
