很多推理框架的性能讨论，习惯从算子、量化格式、批处理大小或显存占用开始。但在真正的异构执行路径中，另一个更底层的问题同样可能决定结果是否可信：数据有没有被正确搬到应该到达的位置。

llama.cpp 的 b12030 预发布说明提供了一个很典型的样本。项目明确记录了一项 Hexagon DMA 修复：在 v75 及更新版本上，2D DMA 描述符中的 row_size 和 stride 只有 24 位；当源数据步长达到 16 MB 或更大时，原有路径可能把过大的 stride 交给 fallback_2d，而该路径只拆分行数，没有正确处理步长，最终导致地址被截断。修复方案是在这种情况下退回到逐行传输，并新增了两个源 stride 超过 16 MB 的 CONT 测试。

这不是一条只影响驱动开发者的冷知识。它说明了推理系统里一个重要的工程边界：模型输出不正确时，不能只检查权重、提示词和采样参数，还要检查数据布局、搬运描述符以及异常尺寸下的降级路径。

## 先把问题还原成一条地址计算链

二维 DMA 的直觉模型并不复杂。假设源缓冲区的首地址是 base，每一行有效数据长度是 row_size，行与行之间的实际间隔是 stride，那么第 n 行的起始位置通常可以抽象为：

    address(n) = base + n × stride

这里的 stride 不一定等于 row_size。对于连续矩阵，两者可能接近；对于带有 padding、切片、拼接或更复杂布局的张量，两者可以明显不同。传输引擎需要知道每行搬多少字节，也需要知道从当前行跳到下一行应该跨过多少字节。

b12030 的发布说明指出，Hexagon v75+ 的 2D DMA 描述符把 row_size 和 stride 存在 24 位字段中。24 位能够表达的最大无符号值是 2^24 - 1，也就是 16 MiB - 1。于是，16 MB 这个边界不是一个随意挑出的压力测试数字，而是描述符可表达范围与实际缓冲区布局发生冲突的位置。

如果上层直接把超出范围的 stride 交给硬件路径，风险并不是“传输变慢”这么简单。字段被截断后，硬件看到的可能是另一个更小的步长，下一行数据就会从错误的位置开始读取。对推理而言，这可能表现为某些输入下输出异常、特定长度才复现的乱码、偶发的精度下降，甚至是难以定位的非确定性错误。

因此，正确性问题的根源不在模型层，而在一条跨层链路上：张量布局产生大步长，DMA 描述符无法完整表达，fallback 路径又错误地假设只有 nrows 需要拆分，最后错误地址进入后续计算。

## fallback 不是天然安全的后备方案

工程上常见的误区是：主路径不支持某种尺寸时，进入 fallback 就代表系统已经安全处理。实际上，fallback 也有自己的输入假设和边界条件。

从 b12030 的说明来看，旧的 fallback_2d 会拆分 nrows，但没有解决 oversized stride。也就是说，它改变了“传多少行”，却没有改变“每一行从哪里开始”。如果 stride 本身已经无法被原始描述符准确表示，仅仅把传输任务切成更多批次，并不会修复地址计算。

修复后的策略是：当 stride 超出可用范围时，退回到每行一次传输。逐行传输牺牲了二维 DMA 能够提供的批量描述能力，却把复杂的跨行跳转变成一组更简单的单行操作。每次传输只需要处理当前行的起始地址和长度，不再依赖一个无法容纳完整 stride 的二维字段。

这个选择体现了正确性优先的降级原则：

第一，降级条件必须对应真正的硬件约束，而不是笼统地捕获所有异常。只有 stride 超过描述符可表达范围时，才需要绕开二维路径。

第二，降级后的操作语义必须等价。逐行搬运不应改变每行的有效数据，只改变任务拆分方式。

第三，降级路径必须被测试覆盖。否则它只是代码作者认为“应该可行”的备用分支，无法证明在边界输入上真的有效。

这里也存在明确的性能取舍。逐行传输通常意味着更多的提交动作、更多的调度开销，以及更低的批量利用率。材料只证明 b12030 修复了超大 stride 下的地址正确性，并没有提供性能收益或损失数据，因此不能把这项改动描述成性能优化。更准确的说法是：它用可能的吞吐损失，换取了超出二维描述符能力时的地址正确性。

## 为什么 CONT 测试比“能跑通”更有价值

发布说明特别提到新增了两个源 stride 超过 16 MB 的 CONT 测试。这一细节非常关键，因为普通测试很容易避开问题：

- 连续内存的 stride 可能与 row_size 相同，天然小于边界；
- 小尺寸矩阵不会触发 24 位字段上限；
- 只检查进程是否结束，无法确认每一行是否来自正确地址；
- 只覆盖主 DMA 路径，无法触发 fallback；
- 只使用单一布局，无法发现 padding 或大间隔带来的错误。

高质量边界测试至少要同时控制三个变量：行数、每行有效长度和行间 stride。测试不应只把整块数据扩大，而应构造“有效数据不一定很大，但行间距足够大”的布局。这样才能确认错误来自 stride 表达能力，而不是单纯来自总缓冲区大小。

验证结果也不能只看程序返回码。更可靠的检查方式是为每一行填入可识别的模式，例如让第 n 行包含与 n 相关的标记，再执行搬运或后续计算，最后逐行比较目标缓冲区。若 stride 被截断，错误通常会表现为某些行重叠、跳过或读取到其他行的数据。

在不依赖特定开发板的前提下，可以先对发布变更做静态核验：

    git clone https://github.com/ggml-org/llama.cpp.git
    cd llama.cpp
    git fetch --tags origin
    git show --stat b12030
    git show b12030 --grep='DMA\|stride\|CONT' --oneline

这些命令只能确认版本标签、提交内容和测试线索，不能替代硬件验证。若要继续构造回归测试，应把测试输入、目标硬件、编译选项、运行日志和逐行校验结果一起保存。特别是预发布版本，不能因为标签存在就默认所有后端和平台都已经获得同等验证。

## 预发布版本的证据等级必须写清楚

b12030 在材料中被明确标记为 Pre-release。因此，本文可以把它作为一个已经出现在官方发布说明中的修复样本，但不能把它当作稳定版承诺，也不能据此推导所有 Hexagon 平台都具有相同表现。

同一批材料中的 vLLM v0.33.0rc3 也属于候选发布版本，其发布内容显示了一项 CI 修复：把 ColUltraVBERT 测试 checkpoint 固定到某个 revision。这个案例与 DMA 问题位于不同层次，却共享一个验证原则：测试输入本身必须稳定。

DMA 案例要求控制内存布局和边界尺寸，checkpoint 固定则要求控制模型测试资产的具体版本。前者避免“地址错了却没人发现”，后者避免“模型变了却误判为代码回归”。二者共同说明，AI 基础设施的验证对象不只是源代码，还包括硬件能力、数据布局、模型资产和测试选择器。

因此，在评估预发布推理框架时，至少应区分三种证据：

一是发布说明中的变更事实，例如 b12030 明确列出的 24 位 stride 限制、fallback 调整和新增 CONT 测试。这类信息可以用于解释修复目标。

二是仓库中的提交和测试代码。它们能进一步确认测试到底构造了什么输入、比较了什么结果，但需要实际查看对应提交，不能只凭标题推断覆盖范围。

三是目标硬件上的运行结果。只有这一层才能回答特定设备、编译配置和驱动组合是否真正通过验证。没有这层证据时，文章或升级报告应明确写成“代码层面的发布说明已给出修复”，而不是“所有设备已经验证无误”。

## 一份面向升级的检查清单

如果团队准备把包含底层后端修复的预发布版本放入测试环境，可以把检查拆成四组。

第一组是版本身份。记录精确 tag、commit、构建时间和编译选项。不要只记录“使用了最新版本”，因为预发布标签可能继续移动，或者同一分支包含多个不同构建。

第二组是边界输入。明确列出 row_size、stride、nrows 和总缓冲区大小。至少覆盖小于 16 MB、接近 16 MB、等于或超过 16 MB 的 stride，并确认测试真正使用了非连续布局。

第三组是结果校验。对每一行或每个切片使用可追踪模式，比较源与目标的有效字节，检查是否出现重叠、错位、丢行或越界。只检查最终模型文本是不够的，因为后续算子可能掩盖部分搬运错误。

第四组是性能与降级观测。记录主二维路径和逐行 fallback 的触发条件、执行时间、提交次数以及错误日志。不能把 fallback 的存在直接判定为失败；应先确认它是否只在必要边界触发，再评估它对真实工作负载的影响。

## 原创结论：推理优化的最小单位不是算子，而是可证明的路径

从 b12030 这个具体修复可以得到一个比“修了一个 DMA bug”更有用的结论：推理系统的最小验证单位，不应只是某个算子或某个模型，而应是一条可证明的数据路径。

这条路径至少包含输入布局、地址计算、传输描述符、异常分支、后续计算和最终校验。任何一个环节有隐含上限，系统就可能在普通样例上表现正常，却在特定尺寸和布局下产生错误。越是追求异构加速，越不能把底层搬运当成透明黑盒。

对使用者而言，b12030 的价值首先是修复了一个明确的边界正确性问题，而不是带来了可以直接宣传的性能数字。对维护者而言，逐行 fallback 和大 stride CONT 测试提供了更重要的示范：当硬件描述符存在表达上限时，先把边界写成可执行测试，再决定是否接受性能代价。对升级决策而言，预发布版本可以进入隔离验证，但不应跳过硬件、布局和测试资产三者的联合核验。

真正可靠的推理优化，不是让数据更快地抵达错误地址，而是先证明它抵达了正确地址，再讨论怎样让这条正确路径更快。
