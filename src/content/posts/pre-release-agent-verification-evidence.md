预发布版本的发布页常常同时给出醒目的功能条目、修复说明和构建产物，很容易让人把“已经发布”理解成“已经成熟”。但发布动作只证明一个版本快照被标记并提供出来，不等于它通过了某个团队的兼容性、安全性或生产验收。

2026 年 11 月 28 日的 Qwen Code v0.29.0-preview.0 发布页明确标注为 Pre-release，列出 Managed Agent 恢复、Harness 池和跨会话提示处理等变更。OpenAI Codex 的 0.174.0-alpha.9 同样标注为 Pre-release；页面还显示发布后 main 有 19 次提交。它们都是有用的工程信号，但信号的含义需要分层：版本身份、代码变化、功能行为和运行环境适配，不应混成一句“新版本可用了”。

## 先把证据等级说清楚

这里讨论的是两个项目发布页公开的预发布信息，不是项目的稳定版承诺，也不是一次独立的功能验证。Qwen 页面把 v0.29.0-preview.0 标为 Pre-release，Codex 页面把 0.174.0-alpha.9 标为 Pre-release。alpha、preview 这些标签适合提醒读者降低默认信任，但不能单独推出具体的缺陷率、兼容性范围或上线时间；材料没有给出这些结论。

发布说明中的条目也有不同证据强度。比如 Qwen 的条目分别提到“Broker failover 后恢复 Managed Turns”“Harness 替换时恢复 Action parking”以及“在外部 Workspace 创建时接纳 session skills”。这些是变更摘要，说明维护者把对应内容纳入该发布快照，却没有给出完整设计、所有前置条件或可量化的恢复保证。严谨的验收表述应是“该预览版本包含与恢复相关的变更”，而不是“故障恢复已经可靠”。

Codex 页面提供了另一个容易忽视的信号：发布后 main 又前进了 19 个提交。它不能证明 alpha.9 有问题，也不能说明后续提交一定修复了什么；它只意味着“当前主分支”与“这个 alpha 发布快照”不是同一个对象。若测试使用了主分支代码，却把结论归给 alpha.9，证据链就断了。

## 固定你要验收的快照

第一步是读取发布元数据，而不是只看搜索摘要或聊天转述。对这两个材料，可用 GitHub CLI 查询发布页字段：

```sh
gh release view v0.29.0-preview.0 \
  --repo QwenLM/qwen-code \
  --json tagName,isPrerelease,publishedAt,url

gh release view rust-v0.174.0-alpha.9 \
  --repo openai/codex \
  --json tagName,isPrerelease,publishedAt,url
```

检查返回的 tag、预发布标记、发布时间和 URL，并将这些信息与团队记录的测试对象对应起来。这里的命令读取发布元数据，不会验证安装包是否适配某台机器，也不会运行功能测试。发布页中出现构建产物，也不等同于产物已在你的目标操作系统、权限配置或网络条件下验证。

如果需要比较代码变化，先在各自仓库中获取标签，再明确写出基线和目标：

```sh
git fetch --tags
git show --no-patch --format=fuller v0.29.0-preview.0
# 将 BASE 替换为团队实际采用的基线标签
git log --oneline BASE..v0.29.0-preview.0
```

这段示例只适用于 Qwen 仓库；Codex 仓库应使用其标签 `rust-v0.174.0-alpha.9`。`git show` 可帮助确认标签解析到的提交信息，`git log` 可列出基线之后的提交，但二者都不是行为测试。不要拿某个项目的标签去另一个仓库执行，也不要在尚未确定基线时把“版本间差异”写成已核实结论。

## 把变更摘要拆成可证伪的问题

验收不是复述发布说明，而是把每条摘要转成能失败的检查。以 Qwen 发布页中的条目为例，可以围绕“跨会话提示处理”提出问题：请求是否确实由目标会话执行？执行上下文是否与预期会话对应？普通单会话流程是否仍保持原行为？这只是测试设计，不是对该功能实际协议的断言；协议字段、预期响应和调用入口必须从项目文档或代码中另行确认，不能从摘要标题臆测。

对“Broker failover 后恢复 Managed Turns”这样的条目，测试应区分正常恢复和边界状态：恢复前任务是否处于可恢复状态；切换后是否重复执行副作用；任务结果是否可追踪；恢复失败时是否有可识别的错误，而不是看起来成功但缺少结果。是否支持这些状态、如何模拟故障，都要以项目明确提供的机制为依据。若没有可靠的故障注入方式，就把这一项标为未验证，而不是用一次正常运行替代故障恢复验收。

对“两个成员的 Hosted Harness pool”也应先核对项目定义的行为，再测池成员选择、成员不可用时的结果，以及并发请求是否出现串线。不能仅凭条目中的 two-member 就推导出负载均衡算法、故障转移保证或容量上限；发布摘要没有提供这些事实。好的测试问题会指出需要观察什么，同时不提前假设内部实现。

## 建一张最小验证矩阵

可以把验证拆成四层，记录版本、输入、观察结果和证据链接。第一层是身份：确认运行对象确实是目标标签对应的版本，而不是系统中已有的全局安装或另一个通道。第二层是基本行为：按项目文档运行一个最小、可重复的工作流，记录输入、退出状态和结果。第三层是变更相关行为：针对发布条目分别设计成功路径、边界输入和预期失败路径。第四层是回归与环境：检查原有工作流、目标操作系统、权限、网络和配置是否与部署条件一致。

每个检查项都应有明确状态，例如“通过”“失败”“未覆盖”或“无法验证”。尤其要避免把“未覆盖”折叠成“通过”：预览版的验收重点往往不是证明它没有问题，而是让团队知道已验证到哪里、尚有哪些未知。记录中至少保留标签、运行平台、关键配置、复现步骤和结果摘要；涉及日志时，先清理令牌、路径、仓库私有信息和用户输入等敏感内容。

发布后主分支继续变化时，矩阵还应记录测试对象是否仍是原标签。如果测试过程中改用较新的提交，结果需要归属于新的提交，不应沿用 alpha.9 的结论。否则即使测试通过，也无法回答用户真正关心的问题：这个被部署或试用的确切版本到底表现如何？

## 预发布环境的取舍与停止条件

预发布版本的价值在于较早试用变更、发现集成问题，并向维护者提供具体反馈；相应代价是团队需要自己承担更严格的回归、版本固定和回退准备。是否适合试用，应由风险和可恢复性决定，而不是由功能标题吸引力决定。对会改写文件、调用外部服务或触发自动化动作的工具，优先使用隔离工作区、低权限凭据和可丢弃数据；先确认其副作用范围，再扩大使用场景。

以下情况应视作停止条件：无法确认运行的是哪个构建；关键工作流的失败结果不能区分于成功；验证必须依赖未经确认的配置猜测；或者回退步骤和数据恢复方式不清楚。停止并不意味着版本一定有缺陷，而是当前证据还不足以支撑更高风险的使用。对可控的试验环境，可以把未知项明确列出后继续；对不可逆或影响真实用户的流程，则应等待更多证据。

## 结论：发布是起点，不是验收章

两个发布页共同说明了一件事：项目可以在预发布阶段发布具体的变更快照，而这些快照仍然需要使用者按自己的环境验证。发布标签回答“这是什么版本”，变更摘要回答“维护者声称改了什么”，只有固定版本并执行可复现的检查，才开始回答“它在我的场景是否可用”。

因此，团队的验收结论最好带上范围：例如“在指定平台、指定标签和列出的工作流中通过”，并同时列出未测试项。这样的结论比“新版已验证”更窄，却更可靠；它可以被复现、反驳和更新，也不会把预览或 alpha 的发布事实误写成稳定性承诺。
