## 先区分两件事：调用工具，还是编排工具

Claude Code v2.1.323 的发布说明把 Code Mode 定义为一种实验性、需要显式选择加入的模式：Claude 可以编写 JavaScript 来调用工具。这个描述的重要性不在于“工具调用终于支持 JavaScript”，而在于执行控制面发生了变化。

传统的工具调用通常是一次请求对应一次工具：模型提出结构化参数，宿主执行工具，再把结果返回给模型。宿主可以在每一步检查工具名称、参数和权限。JavaScript 编排则可能把多个工具调用、条件判断、结果转换放进同一段脚本中。模型获得的不是一张更长的工具清单，而是一层可以组织调用顺序的控制逻辑。

这带来三个直接变化。第一，审计对象从单次调用扩展为脚本及其运行结果。第二，失败可能发生在工具调用之前、脚本执行过程中，或脚本已经产生部分副作用之后。第三，优化空间和风险同时增加：脚本可以减少来回往返，也可能让一次看似简单的请求包含更多隐含步骤。

因此，Code Mode 不应被当作普通功能开关处理。它更接近一个实验性的执行层。启用前需要明确：哪些工具允许被脚本调用，脚本是否可以组合具有副作用的操作，以及失败后能否准确判断哪些步骤已经完成。

## 实验性能力的正确启用方式

发布说明明确要求通过 Code Mode 文档进行开启或关闭，并将其标记为 experimental opt-in。这里至少包含两个工程信号：默认状态不能假设为开启，能力本身也不应被视为稳定接口。

在团队环境中，建议把启用动作与版本固定、范围限制和回滚方案放在同一份变更记录中，而不是只在个人配置里打开。一个最小的变更记录可以包含：

```text
CLI 版本：v2.1.323
能力：Code Mode
状态：显式开启 / 显式关闭
适用范围：开发环境或指定组织
允许工具：只列出已审核工具
回滚：恢复原配置并固定到上一已验证版本
验证日期：YYYY-MM-DD
```

如果需要把这项能力纳入自动化验收，可以先固定待测版本，再分别验证关闭和开启两条路径。关闭路径要确认原有工具调用仍然可用；开启路径要确认脚本只能使用预期工具，并且错误信息能回到调用者，而不是被包装成成功结果。

最小检查命令可以从插件验证开始：

```bash
claude plugin validate ./plugins/example
claude plugin validate ./plugins/example --strict
```

发布说明指出，插件中的 TypeScript hooks 模块现在会进行类型检查；普通校验将发现报告为警告，而 `--strict` 会让这些问题导致失败。因此，非严格模式适合开发期快速发现问题，严格模式才更适合作为合并门禁。两者不能混为一谈：一次普通校验通过，不代表插件满足发布条件。

## 插件兼容性从“能加载”变成“版本契约”

同一版本发布还增加了 `plugin.json` 中的 `engines["claude-code"]`。插件如果不在声明的 Claude Code 版本范围内，将不会被安装、更新或加载；安装和更新会选择满足范围的最新版本。

这改变了插件升级的判断方式。过去，“当前版本能不能加载”可能是最主要的问题；现在还必须检查插件声明的兼容范围是否覆盖目标 CLI。一个插件即使代码在本地看起来没有变化，也可能因为引擎范围不匹配而无法进入运行态。

工程上应把兼容性拆成三层：

1. **声明层**：`plugin.json` 是否存在明确的 `engines["claude-code"]` 约束，范围是否覆盖目标版本。
2. **安装层**：安装或更新时实际解析出的插件版本，是否是团队批准的版本，而不是仅仅“最新可用版本”。
3. **运行层**：插件是否成功加载，TypeScript hooks 是否通过严格校验，运行时暴露的能力是否仍符合预期。

这三层分别回答“允许什么”“拿到了什么”和“实际运行什么”。只看安装成功信息，会漏掉声明不完整、版本解析变化和 Hook 类型问题。

可以在提交检查中加入简单的静态门禁，避免兼容性声明被意外删除：

```bash
test -f ./plugins/example/plugin.json
jq -e '.engines["claude-code"]' ./plugins/example/plugin.json
claude plugin validate ./plugins/example --strict
git diff --check
```

这里的关键不是 `jq` 本身，而是把版本契约当成可检查的输入。若项目没有使用 `jq`，也可以用现有 JSON 校验工具实现同样的检查，但不能用“插件目录存在”替代引擎范围验证。

## Hook 校验解决什么，解决不了什么

TypeScript Hook 类型检查能够发现一类明确的问题：模块结构、类型不匹配以及 Hook 接口使用错误。它可以在插件进入更深的运行阶段之前，提前阻断一部分错误。

但类型正确不等于行为安全。一个类型合法的 Hook 仍可能调用不应调用的工具、产生不符合预期的副作用，或在异常路径中返回让上层误判为成功的数据。因此，严格校验应当被视为必要条件，而不是完整测试。

发布说明还提到，`claude plugin validate` 会检查某个模块的 `engine.create` Hook 增加、保留或替换的 `$` nouns。这个变化说明插件校验不只关注 TypeScript 语法，还开始检查插件对执行模型中可见能力的修改。

这里的工程含义是：插件并非被动提供几个函数，它可以影响代理能够理解和使用的能力集合。能力集合发生变化时，审查重点就不能只放在代码文件，还要比较变更前后的工具或语义暴露面。

可以为每个插件维护一份能力快照：

```text
插件名称：example
目标 CLI：v2.1.323
允许能力：read_file, search, test
新增能力：无
移除能力：无
替换能力：无
副作用工具：单独列出并需要人工批准
```

当 `engine.create` 的行为发生变化时，先更新快照，再决定是否允许合并。若无法解释某个新增、保留或替换项，就不应把严格校验通过直接当作批准依据。

## Code Mode 的失败边界要提前定义

JavaScript 编排最容易被忽略的是部分成功。假设脚本依次执行读取、修改和测试：读取成功，修改成功，测试失败。此时“任务失败”并不意味着工作区没有变化；相反，工作区可能已经处于中间状态。

因此，验收不能只看最终自然语言回答。至少要记录以下事实：

- 脚本是否开始执行；
- 实际调用了哪些工具；
- 哪一步返回错误；
- 错误发生前是否已经产生外部副作用；
- 重试是否会再次执行不可幂等操作；
- 最终状态能否通过独立检查复核。

对于只读工具，失败通常可以重试；对于写文件、提交变更、发布资源等操作，则需要更严格的边界。稳妥的顺序是先读取和分析，再生成变更计划，最后执行具有副作用的步骤，并在每个阶段留下可验证结果。不要让一个脚本把检查、修改和发布压缩成不可分辨的一次调用。

一个最低限度的测试矩阵可以这样设计：

| 场景 | 预期结果 | 重点观察 |
| --- | --- | --- |
| Code Mode 关闭 | 原有工具路径可用 | 是否出现隐式依赖 |
| 只读工具失败 | 明确失败并可重试 | 错误是否被吞掉 |
| 中间步骤失败 | 标记部分完成 | 是否误报全部成功 |
| 插件版本不匹配 | 不安装、不更新或不加载 | 是否有清晰提示 |
| Hook 类型错误 | 普通校验警告，严格校验失败 | 门禁是否接入 CI |
| 能力集合变化 | 需要人工审查 | 是否能解释差异 |

## 把实验功能纳入发布门禁

Code Mode 的合理使用方式不是“看到新能力就全局打开”，而是将它当成一项有边界的实验。建议采用分层策略：个人开发环境先验证，团队测试环境再验证，生产或高权限环境保持关闭，直到工具范围、失败恢复和审计信息都满足要求。

发布前可以执行一条短流程：

```bash
# 1. 确认当前工作区没有未预期变更
git diff --check

# 2. 校验插件元数据与引擎范围
test -f ./plugins/example/plugin.json
jq -e '.engines["claude-code"]' ./plugins/example/plugin.json

# 3. 执行严格插件校验
claude plugin validate ./plugins/example --strict

# 4. 运行只读工具场景，再运行失败场景
./scripts/test-agent-readonly.sh
./scripts/test-agent-failure-path.sh
```

脚本名称应替换为项目已有的测试入口；重点是把只读路径和失败路径分开。若当前项目没有自动化测试，也应至少保存一次工具调用记录、插件验证输出和工作区差异，避免只凭代理最后一句话判断结果。

## 结论：能力越强，越要缩小可解释范围

Claude Code v2.1.323 的 Code Mode 展示了代理工具链的一个方向：从“模型选择工具”走向“模型编写调用逻辑”。这会提高组合能力，但也会扩大执行路径和失败面。与此同时，插件引擎版本范围、TypeScript Hook 严格校验以及能力集合检查，说明插件系统正在从松散扩展转向更明确的兼容性契约。

原创的工程判断是：Code Mode 的核心验收指标不应是“能否完成更多任务”，而应是“能否解释每一次任务如何完成，以及失败后留下了什么状态”。只要脚本、插件版本和能力集合仍然不可追踪，新增的自动化就只是把复杂度藏起来。真正可交付的代理能力，必须同时具备显式启用、版本约束、严格校验、部分成功识别和可回滚路径。
