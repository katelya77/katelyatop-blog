## 先把“免费 API”拆成三个不同问题

在 NodeLoc 的一条帖子里，BT-API 被描述为“国产模型限时免费体验”，并宣称提供统一接口、多个模型和抽奖额度。帖子还给出了站点地址、模型名称与一张第三方检测报告截图。这些内容足以说明它是一个值得观察的真实样本，却不足以证明服务的长期稳定性、模型来源、数据处理方式或账号安全性。

官方站点本身提供的标题是“BT-API - AI API Gateway”。这至少能确认站点把自己定位成 API 网关，而不是某个基础模型的官方接口。网关的含义很关键：客户端通常只需要把请求发给一个地址，但请求之后可能还要经过路由、鉴权、计费、模型适配、重试和日志系统。调用者看到的是兼容格式，真正承担信任成本的却是中间层。

因此，“能不能用”不能只回答一个是或否，而要拆成三个问题：接口是否真的可用，模型结果是否满足业务要求，发送给网关的数据是否值得托付。第一问可以通过命令验证，第二问需要建立可重复的模型测试，第三问则不能靠一次成功响应来证明。

## OpenAI 兼容只是协议外观，不是安全承诺

所谓 OpenAI-compatible，通常只表示请求和响应采用相近的路径、字段或消息结构。例如客户端可能通过 `POST /v1/chat/completions` 发送 `model`、`messages` 和 `temperature`，网关再把它们转换到后端实际供应商。这个兼容层降低了迁移成本，却没有自动带来以下保证：

- 网关是否保存请求正文、系统提示词和响应内容；
- API Key 是否只用于鉴权，还是同时关联账户、额度和行为日志；
- `model` 字段是否真的映射到用户以为的模型；
- 失败重试是否把同一段敏感内容发送给多个后端；
- 服务方是否会修改系统提示词、工具参数或响应内容；
- 免费额度是否有明确的有效期、限速和撤销规则。

这些问题不能从“接口长得像官方 SDK”推导出来。更不能因为页面列出了很多模型，就推导出网关拥有这些模型的官方授权。社区帖子中关于模型数量、价格和“限时免费”的说法，应当被标记为运营者或用户提供的待核验信息，而不是稳定的产品事实。

这也是为什么第三方检测报告不能替代安全审计。S7 页面明确说明，报告只描述某一凭证在某一时刻的检测结果，不构成安全认证；`inconclusive` 也不等于干净。这个限制不是免责声明里的小字，而是理解报告的核心：检测结果是一个时间点、一个凭证、一个测试集合下的观测值，不能外推到所有账号、所有接口和未来状态。

## 先用无敏感数据验证接口行为

如果只是判断一个网关是否遵循基本的兼容协议，可以从最小请求开始。不要一上来就把代码仓库、生产日志、客户资料或长期系统提示词发给未知服务。下面的命令使用占位符，模型名称必须以站点实际公开列表为准，不应照抄社区帖子中的价格或型号：

```bash
export BASE_URL='https://example.invalid/v1'
export API_KEY='replace-with-a-short-lived-test-key'
export MODEL='replace-with-a-published-model-id'

curl --fail-with-body --silent --show-error \
  "$BASE_URL/chat/completions" \
  -H "Authorization: Bearer $API_KEY" \
  -H 'Content-Type: application/json' \
  --data-binary @- <<'JSON'
{
  "model": "replace-with-a-published-model-id",
  "messages": [
    {"role": "user", "content": "只回复协议测试成功，不要输出其他内容。"}
  ],
  "temperature": 0,
  "max_tokens": 32
}
JSON
```

实际使用时需要把 JSON 中的模型值替换为环境变量，避免命令示例造成误解：

```bash
curl --fail-with-body --silent --show-error \
  "$BASE_URL/chat/completions" \
  -H "Authorization: Bearer $API_KEY" \
  -H 'Content-Type: application/json' \
  --data-binary "$(printf '%s' '{"model":"'"$MODEL"'","messages":[{"role":"user","content":"protocol-check"}],"temperature":0,"max_tokens":8}')"
```

检查时不要只看 HTTP 200。至少记录以下字段：状态码、响应是否为合法 JSON、`model` 是否被改写、是否存在 `choices`、是否返回用量字段、错误信息是否泄露后端供应商或内部路径、同一请求重复发送时结果是否符合预期。流式模式还要检查连接中断、事件顺序和结束标记，不能因为非流式请求成功就认为流式实现可靠。

测试内容应当是无意义的固定字符串，例如 `protocol-check-2026-09-05`。不要使用真实用户文本来“顺便测试”。如果服务要求注册或充值，测试账号也应使用专门邮箱和专门凭证，并限制余额、权限与有效期。

## 把模型验证和网关验证分开

中转服务最容易制造的错觉是：回答流畅，所以模型、计费和路由都没有问题。实际上，网关验证和模型验证是两套实验。

网关验证关注协议层。可以固定一条短提示，连续执行若干次，比较响应结构、延迟、错误码和连接行为；再分别测试普通请求、最大输出限制、无效模型、无效凭证和超时。每次测试只改变一个变量，并保存时间、请求参数摘要和响应元数据，不保存敏感正文。

模型验证关注能力层。对于同一模型标识，准备一组不包含机密的固定样例，覆盖结构化输出、长文本截断、工具调用或 JSON 格式等业务真正依赖的能力。不同网关之间不要只比较一句问答的观感，要比较可解析性、错误率和边界行为。如果模型名称相同而输出能力差异明显，应把“模型身份未充分验证”记录为风险，而不是自行认定服务在造假。

还要单独验证计费和限额。社区帖子中出现的单次请求价格、混池折扣和抽奖额度属于活动信息，不能当作合同条款。正式接入前应确认额度单位、失败请求是否计费、重试是否重复计费、免费期结束后的默认行为，以及余额不足时是否会自动扣款。没有明确答案，就不要把它接入无人值守任务。

## 凭证和数据的最小暴露原则

未知网关最危险的地方往往不是一次错误答案，而是调用者把它当成了官方供应商，进而交出长期凭证和完整上下文。工程上可以采取几条简单但有效的边界：

第一，使用独立测试账号和短期 Key。不要复用官方模型供应商的密钥，不要把个人主账号 Token 放进第三方客户端，也不要把密钥写进 shell 历史、公开仓库或截图。测试结束后立即撤销凭证。

第二，在本地增加脱敏层。姓名、手机号、邮箱、订单号、访问令牌和内部域名在离开本机前应替换为稳定的占位符。脱敏不是把几个字段删掉就结束，还要检查上下文是否能通过组合信息重新识别对象。

第三，把网关作为不受信任的外部处理者。默认不要发送源码、生产日志、客户工单、内部架构图和未公开产品计划。即使服务承诺“不保存”，调用方仍然应当按最坏情况设计，因为承诺、实现和可审计证据是三件不同的事。

第四，为客户端设置出口限制。只允许测试程序访问明确的域名，记录 DNS、TLS 证书、HTTP 状态和请求量变化。不要为了方便关闭证书校验，不要在代理配置里把所有系统流量都改走一个未经验证的中转站。

## 失败边界：哪些信号足以停止接入

以下情况不一定证明服务恶意，但足以让它不适合生产使用：模型列表、价格或免费期没有可追溯的正式说明；服务要求上传长期密钥；接口返回的模型身份与请求不一致且无法解释；错误响应包含内部堆栈、其他用户信息或后端凭证线索；请求在没有明确授权的情况下被自动转发到多个供应商；计费、限速和数据保留政策无法获得；检测报告只有单次截图，且没有测试范围与时间说明；账号撤销、退款和数据删除没有可执行路径。

遇到错误时也不要反复重试敏感请求。先记录请求时间、状态码、响应头中非敏感的诊断字段和客户端版本，再使用新的无敏感样例复现。若怀疑凭证泄露，优先撤销 Key、检查账户活动并更换测试环境，而不是继续“验证一下”。

## 一个适合团队评审的接入清单

可以把评审结论分为四档，而不是简单地标记“可用”或“不可用”。

**观察**：只确认站点存在，社区讨论或活动页面提供了线索，尚未完成接口验证。此阶段不能发送任何敏感内容。

**实验**：基本协议可以验证，测试账号、短期凭证和固定无敏感样例已经准备好，但数据处理和计费边界仍未确认。只能用于临时开发和协议联调。

**受限使用**：完成错误路径、限额、撤销和数据脱敏测试，明确禁止生产数据、客户数据和无人值守调用。所有请求经过本地审计代理，并设置预算与速率限制。

**生产使用**：除技术可用性外，还必须有可核验的服务条款、数据处理说明、密钥生命周期、故障响应和供应商责任边界。没有这些证据，即使价格很低、模型很多、检测评分很高，也不应进入关键业务链路。

## 结论：免费降低的是试用门槛，不是信任成本

BT-API 样本真正值得讨论的，不是“几十个模型免费用”是否划算，而是一个兼容网关如何把复杂的供应链隐藏在统一入口之后。S5 的社区帖子可以作为选题雷达和问题样本，S6 能确认站点自我定位为 API 网关，S7 则提醒我们：一次检测报告不是安全认证。三者放在一起，恰好说明了证据链的分层关系。

对个人开发者，最稳妥的做法是把未知中转当成短期实验工具：使用无敏感数据、独立凭证和小额度，验证协议后及时撤销。对团队，应该把网关视为外部供应商，要求数据边界、计费规则和凭证管理先于模型数量进入评审。所谓“免费”，最多证明试用成本暂时较低；它从来不能证明数据处理成本、故障成本和信任成本不存在。
