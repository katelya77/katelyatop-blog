## 一行变更，为什么值得单独审查

llama.cpp 的 b12198 是一个标记为 Pre-release 的版本。材料中唯一明确列出的变更是：`server : downgrade per-request proxy logs to trace (#31859)`。这不是“新增一个日志功能”，而是改变既有运行时信息的默认可见性。这里首先要划清证据边界：官方发布说明证明了该变更存在，也证明它针对 server 的 per-request proxy logs；材料没有说明具体日志框架、默认日志级别、配置参数名称、输出格式、性能收益或兼容性承诺。因此，后文不会把这些未披露内容包装成项目事实，而是把它们作为部署时需要验证的工程问题。

日志降级也不等于删除日志。按照日志系统通常的语义，trace 比 info 或 debug 更细，意味着消息仍可能被生成，但只有运行时阈值允许时才会输出。这个解释是工程上的一般模型，不是 b12198 发布说明对实现细节的确认。真正需要关心的是：当默认阈值不再显示每个请求的代理细节时，服务是否仍保留足以判断请求成功、失败、延迟和上游错误的信号。

这也是它和“把日志关小一点”之间的差别。代理层通常处于客户端、推理服务和可能的上游模型之间，单次请求可能经历路由、转发、重试、流式响应和错误归因。每请求日志很容易形成高基数输出：请求 ID、路径、模型名、状态码、耗时以及分段事件都可能重复出现。默认输出过多，会增加磁盘、采集、索引和检索成本；但如果降级时连关联 ID 或失败原因一起消失，问题又会从“日志太多”变成“事故不可解释”。

## 先把三类信号分开

验证这类变更，不能只比较日志行数。可以把服务输出拆成三层。

第一层是业务结果信号。它回答请求有没有完成，例如成功、客户端取消、上游拒绝、内部错误和超时。它应当足够稳定，不能因为代理明细被降级就无法统计。第二层是请求关联信号，包括请求标识、模型或路由标识、状态码、总耗时和错误类别。它用于把一次外部请求和一次内部处理联系起来，但不必记录每个转发细节。第三层才是逐请求代理轨迹，例如每一次转发、连接和中间状态变化。这一层最可能具有高频、调试性和高基数特征，适合放在 trace。

b12198 的公开说明只告诉我们第三类信号发生了级别变化，并没有保证前两类信号的行为。因此升级验收的核心不是“trace 是否存在”，而是确认降级没有误伤请求结果和故障归因。若一个系统只能依靠逐请求代理日志判断请求失败，那么原本的可观测性设计就已经把关键事实放错了层级。

还要注意日志与指标的替代关系并不对称。指标可以告诉你错误率上升，却通常不能告诉你某个请求经过了哪条路由；trace 日志可以提供细节，却不适合直接承担稳定的总量统计。合理的设计是让低成本的计数和延迟信号承担趋势监控，让受控的关联日志承担单请求定位，再把最细粒度的代理轨迹留给按需开启的诊断窗口。

## 不依赖特定参数的验证流程

由于材料没有给出 b12198 的具体配置键，不能凭空写出一个“官方开关”。可以先用不依赖实现细节的方式建立基线。下面的命令只检查版本、日志内容和发布证据，不假设服务支持某个特殊 API：

```bash
# 记录待测二进制和源码版本
./llama-server --version 2>&1 | tee version.txt

git -C llama.cpp rev-parse HEAD
git -C llama.cpp describe --tags --always

# 在固定请求集下保存服务日志
./llama-server ... 2>&1 | tee run.log

# 区分明显的级别标记，并统计代理相关行
awk 'BEGIN{IGNORECASE=1} /trace|debug|info|warn|error/ {count[$1]++} END{for (k in count) print k, count[k]}' run.log
grep -iE 'proxy|request|upstream|timeout|error' run.log | head -n 100
```

固定请求集应至少包含：一次正常短请求、一次流式请求、一次客户端主动中断、一次非法输入、一次上游不可用或明确超时的场景。如果服务部署在 systemd 下，可把 `journalctl -u <service> --since ...` 的结果保存为同样的测试产物；如果由容器运行，则同时保存容器标准错误和采集器转发后的日志。这样做的重点不是命令本身，而是确保比较的是同一请求、同一模型、同一并发和同一采集链路。

每个场景至少记录四个结果：客户端看到的 HTTP 或协议结果、服务是否产生错误信号、是否还能通过关联字段定位请求、trace 级代理细节在开启与关闭时是否符合预期。若没有公开的日志格式契约，就不要把某个字段名称写进自动化断言；可以断言“存在可关联的请求标识”或“失败请求能被检索”，把字段名作为部署环境的适配层。

## 用差分而不是感觉判断回归

最有价值的比较是同一版本在两个日志阈值下的差分，而不是升级前后随手翻几页日志。对每个固定场景生成两份输出：默认配置和显式开启细粒度日志的配置。后者的具体配置方式必须以项目文档或二进制帮助为准；若帮助没有披露，就记录“无法验证可控开启”，不要自行猜测环境变量。

差分检查可以分为三步。第一步比较结果：状态码、流是否正常结束、错误类别和超时行为不能因日志阈值变化而改变。第二步比较关联性：默认输出中仍应保留足以定位失败请求的最低信息，或者由指标、访问日志和外部追踪系统提供等价能力。第三步比较细节：只有在诊断阈值下，才期待出现每请求代理轨迹。若两种阈值下输出完全相同，可能是默认级别没有变化，也可能是采集器在服务外部重新放大了日志；若默认输出完全没有失败信息，则不能直接接受“日志变少了”作为成功标准。

可以把验证结果做成一张机器可读的矩阵：场景、客户端结果、默认日志中的关联信号、诊断日志中的代理细节、采集后是否保留、是否允许进入长期索引。矩阵比肉眼查看日志更可靠，因为它迫使团队明确“必须保留什么”和“可以丢弃什么”。

## 失败边界：trace 降级不解决所有噪声

第一种边界是采集链路覆盖不到 trace。应用即使正确输出 trace，容器运行时、日志代理或集中式系统也可能只采集 info 及以上。此时“需要时打开诊断日志”在理论上成立，在运维现场却不可用。上线前应确认采集器的级别过滤、保留时间和临时提升权限，并为恢复默认级别设置明确的回退动作。

第二种边界是日志隐私。代理日志可能包含路径、参数、模型标识、错误上下文甚至用户输入片段。把它降级为 trace 只能减少默认暴露，不能自动完成脱敏。开启诊断窗口前仍要检查采集范围、访问权限和保存周期；尤其不能为了排查请求链路而把完整提示词长期写入集中日志。

第三种边界是高并发下的关联成本。即使逐请求轨迹被降级，访问日志、指标和外部追踪仍可能产生高基数标签。不要把请求 ID、完整 URL 或用户可控字段无条件作为指标标签。请求级数据适合日志或追踪，聚合指标应使用有限的枚举维度。

第四种边界是预发布版本本身。b12198 的官方页面标记为 Pre-release，不能据此推导生产兼容性。材料中的 Codex `0.169.0-alpha.3` 同样明确标记为 Pre-release，且提供的摘录没有列出可用于本次日志主题的行为细节。这个对照提醒我们：版本号和发布页面可以证明“有一个候选版本”，不能替代目标功能的行为验证。升级前应锁定构建来源、保留旧版本回退路径，并把日志差分结果作为候选版本的验收证据。

## 工程取舍：默认安静，诊断可逆

这次变更最值得借鉴的不是某个具体级别名称，而是默认路径与诊断路径的分工。生产默认日志应优先保证低成本、可检索和不泄漏敏感内容；诊断路径则应能够在有限时间内提高细节，但必须有权限控制、明确的开始与结束时间，以及自动恢复默认配置的机制。

因此，验收标准不应写成“代理日志减少了多少百分比”。更可靠的标准是：正常请求的结果不变；失败请求仍可被关联和分类；高细节轨迹可以按文档方式开启；采集系统不会悄悄丢弃所需级别；诊断结束后能恢复；发布失败时可以回滚到已知版本。只有这几项同时成立，日志降级才是可治理的观测性调整，而不是把噪声从屏幕上移走。

从公开证据能得出的结论很有限，但也足够明确：llama.cpp b12198 改变了 per-request proxy logs 的日志级别，且版本仍处于预发布状态。真正的工程工作不在于复述这一行 changelog，而在于证明默认输出减少后，服务仍然可解释、可定位、可回退。对任何推理服务而言，少打日志不是目标；在不牺牲关键事实的前提下，把昂贵的细节放到需要它的时刻，才是值得验收的结果。
