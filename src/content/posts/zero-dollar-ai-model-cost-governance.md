## 先把“免费”拆成三个不同命题

“限时免费使用 0 美元的图像和视频模型”是一个很有吸引力的入口，但它首先只是社区雷达发现，不等于平台的长期承诺。S16 的描述提到，部分模型可能以 0 美元使用，也可能需要约 0.1 美元的验证；这类信息的证据等级是社区发现，适合用来提出问题，不适合直接当作稳定产品能力。

更可靠的事实来自 PPQ 的公开定价页。S17 将服务描述为按量计费、无订阅，并明确指出一次查询的成本与整个聊天上下文的输入 Token 数量以及输出 Token 数量有关。页面还列出了模型 ID、上下文上限、输入价格、输出价格、缓存读取价格和中位成本。由此可以把“免费”拆成三个命题：

1. **价格为零**：某个模型或某个时间窗口显示为 0 美元，但不一定代表所有请求都免费。
2. **额度为零**：账户获得免费余额或促销额度，额度消耗后仍可能进入正常计费。
3. **边际成本很低**：模型价格很低，但长上下文、长输出和重试仍会累计成本。

这三个命题的工程处理方式完全不同。价格为零需要验证适用范围和有效期；免费额度需要监控余额和扣费事件；低边际成本则需要控制上下文、输出和重试。把它们混成一个“免费 API”，最终会让预算、账单和故障定位都失去依据。

## 按量计费的核心：请求不是一个固定价格单位

PPQ 的定价结构说明，一次查询不是简单的“调用一次扣一次钱”。可以先用一个近似模型表达单次请求成本：

```text
请求成本 ≈ 输入 Token / 1,000,000 × 输入单价
         + 输出 Token / 1,000,000 × 输出单价
         + 缓存读取 Token / 1,000,000 × 缓存读取单价
```

这不是对平台内部结算实现的臆测，而是将公开页面中的计费维度转化为工程核算模型。实际账单还应以平台返回的用量记录为准，尤其要注意页面同时展示了平均查询成本、中位成本和“Prompts / $1”等辅助指标，这些数字不能替代自己的请求级账单。

S17 中的模型价格差异也说明，模型选择不仅是能力问题。页面列出的模型包含不同的上下文上限、输入和输出价格。例如，同一个提供商下，较强模型的输出单价可能显著高于轻量模型；某些模型有缓存读取价格，而另一些模型没有展示缓存价格。若应用把完整历史会话、系统提示词、工具结果和检索文档全部拼进每次请求，输入 Token 会随会话增长，即使用户只问了一句短问题，也可能触发较高的输入成本。

因此，网关不能只记录 `model` 和 HTTP 状态码，至少还要记录以下字段：

```json
{
  "request_id": "内部唯一 ID",
  "model": "模型 ID",
  "input_tokens": 0,
  "output_tokens": 0,
  "cache_read_tokens": 0,
  "estimated_cost_usd": 0,
  "retry_count": 0,
  "status": "success"
}
```

其中 `estimated_cost_usd` 只能作为实时预算控制依据，不能伪装成最终账单。模型价格会变化，页面也可能增加或移除模型，因此价格表应当带有抓取时间、来源和版本，而不是硬编码在业务代码深处。

## 从“免费入口”到可验证流水线

面对社区里发现的 0 美元入口，比较稳妥的做法不是立即把生产流量切过去，而是建立四阶段验证。

### 第一阶段：确认入口身份

先确认链接最终指向的域名、登录页面和服务主体。不要把社区帖子里的跳转链接、临时激活链接或带有账户操作含义的 URL 直接放进自动化脚本。S16 只证明社区有人发现了一个限时优惠信息，并未证明优惠范围、持续时间、API 权限或退款规则。

可以先做不涉及敏感凭据的基础检查：

```bash
url='https://example.invalid'
curl -sS -L -o /dev/null \
  -w 'status=%{http_code}\nfinal=%{url_effective}\n' "$url"
```

这个命令只能确认 HTTP 跳转结果，不能证明模型可用，更不能证明请求免费。正式验证时，应使用专门的测试账户、最小权限密钥和独立预算，不要在命令行历史中直接写入真实 Token。

### 第二阶段：确认计费语义

把平台页面或 API 返回的价格信息保存为结构化快照，至少包括模型 ID、价格单位、生效时间、上下文上限和适用产品。对于 S17 这类页面，可以人工核对网页中的输入价格、输出价格和缓存读取价格，再将结果录入内部配置。

配置不应只写一个 `free: true`：

```yaml
models:
  trial-model:
    provider: ppq
    billing_mode: promotional
    input_price_per_million: 0
    output_price_per_million: 0
    requires_verification: true
    expires_at: "2026-10-31T23:59:59Z"
    max_request_usd: 0.05
```

这里的字段是应用侧治理配置，不是对 PPQ 内部 API 的声明。`expires_at` 和 `max_request_usd` 的价值在于，即使促销失效或价格配置过期，系统也不会静默地把生产请求升级成无限预算请求。

### 第三阶段：只做最小请求

验证顺序应从短输入、短输出、无工具调用开始，再逐步增加上下文。每一步都保存请求时间、模型 ID、用量和账单变化。不要用一次长文档问答来判断“免费”，因为那会同时混入上下文计费、输出计费、截断和重试等变量。

可以用一个本地计算器复核网关的估算逻辑：

```bash
python3 - <<'PY'
from decimal import Decimal

input_tokens = Decimal("1200")
output_tokens = Decimal("300")
input_rate = Decimal("0.38")
output_rate = Decimal("1.88")

cost = (input_tokens / Decimal("1000000")) * input_rate
cost += (output_tokens / Decimal("1000000")) * output_rate
print(f"estimated_cost_usd={cost:.8f}")
PY
```

示例中的价格只是演示计算方法，不能替代当前价格页。生产系统应该从经过审核的价格配置读取费率，并在价格缺失时阻断高成本请求，而不是默认按零成本处理。

### 第四阶段：验证失败路径

真正容易失控的不是成功请求，而是超时、空响应、部分流式输出和客户端重试。需要分别验证：上游返回 429 时是否退避；连接在收到部分内容后断开时是否重复扣费；网关超时后客户端是否再次发送同一个请求；模型不可用时是否自动切换到价格更高的模型；促销模型到期后是否仍被路由。

每次重试都应拥有独立的请求 ID，并与原始请求建立关联。预算判断要放在重试之前，而不是只在第一次请求前判断。否则一次用户操作可能被扩展成多次上游调用，最终账单远高于前端显示的单次估算。

## 失败边界：免费模型也可能是高风险组件

第一类边界是**促销范围不清**。社区消息可能只对应网页端，不对应 API；可能只覆盖特定模型，不覆盖自动路由；也可能需要小额验证，却没有说明验证款是否退回。没有一手条款时，文章和系统都不应把它写成“永久免费”。

第二类边界是**模型名与模型 ID 不一致**。S17 同时列出展示名称和模型 ID，例如模型可能有面向用户的名称，也有供 API 使用的字符串。工程配置必须使用平台明确给出的模型 ID，并在启动时检查模型是否仍存在。只保存展示名称，会让路由层在名称变化后出现静默降级或请求失败。

第三类边界是**上下文上限不等于可用上下文**。页面列出的最大上下文长度是模型或平台标称能力，不代表应用应该把这么多内容全部发送。长上下文会增加延迟、输入成本和隐私暴露面；当系统还附带工具结果、检索片段和历史消息时，实际请求可能在到达模型前就被网关拒绝或截断。

第四类边界是**空响应仍可能有成本**。S2 的社区案例虽然不是 PPQ 的官方证据，但它揭示了中转服务常见的治理风险：用户可能遇到错误、空回复或额度变化，却无法从公开后台确认真实用量。这个案例不能证明任何特定平台存在同样问题，但足以说明接入第三方网关时必须保存自己的请求日志、响应摘要和预算快照，不能只相信前端显示的“成功”。

第五类边界是**自动降级改变了成本契约**。当低价或促销模型不可用时，系统如果自动切到更昂贵模型，用户体验可能变好，但成本也会改变。正确做法是为降级策略设置明确的价格上限，并在响应元数据中返回实际模型，而不是继续展示用户原先选择的模型。

## 一份可落地的接入检查清单

在把“0 美元”模型接入开发或生产环境前，可以按以下顺序检查：

- 入口是否来自可核验的一手页面，社区帖子是否只被当作线索？
- 促销适用的是网页、API、某个账户，还是某个具体模型？
- 是否存在验证扣款、最低充值、有效期或地区限制？
- 模型展示名称、模型 ID、上下文上限和费率是否分别记录？
- 输入、输出、缓存读取 Token 是否能在请求级别落日志？
- 价格未知、价格过期或账单字段缺失时，系统是否默认阻断？
- 单次请求、单用户、单日和全局预算是否都有上限？
- 重试、超时、流式中断和自动降级是否会产生重复调用？
- 是否能通过账单或用量接口核对本地估算，而不是只看 HTTP 200？
- 测试密钥、生产密钥和个人账户是否完全隔离？

其中最关键的是最后一项验证闭环：本地估算只能回答“按当前费率应该花多少”，平台账单才能回答“实际扣了多少”。两者出现差异时，应优先保留请求 ID、时间窗口、模型 ID 和用量记录，避免用平均成本倒推单次扣费。

## 原创结论：把免费当成一种需要过期的配置

AI 服务里的“免费”不应该被建模成布尔值，而应被建模成带证据、范围、有效期和预算上限的策略对象。社区发现可以帮助我们找到入口，但不能替代官方价格页；官方价格页可以说明计费维度，但不能替代自己的请求级验证；请求级日志可以解释本地估算，但不能替代最终账单核对。

因此，最小可靠架构不是“找一个免费模型然后改环境变量”，而是“证据分级、价格快照、请求计量、预算闸门、失败回放”五件事同时存在。只要其中任何一环缺失，所谓零美元就可能只是页面上的一个瞬间状态。

对个人开发者而言，这套方法能避免因为长上下文和自动重试产生意外支出；对团队而言，它还能把模型切换从临时运气变成可审计的发布变更。真正值得追求的不是永远免费的入口，而是在免费结束、价格变化或上游故障时，系统仍然知道自己为什么调用、调用了多少，以及何时应该停止。
