## 先区分两种事实：项目能力与社区描述

NodeLoc 上的帖子把 WkBdy2api 描述为一个把 WorkBuddy 接成 API 的项目，并列出了 OpenAI Chat Completions、Responses、Anthropic Messages、流式输出、推理内容、工具调用和图片等关键词。这些信息可以作为选题雷达，也能说明社区最关心的使用方式，但它属于社区发布信息，不能自动等同于正式兼容性承诺。本文把这部分标记为“社区证据”，只用来解释问题背景。

更可靠的边界来自项目自己的 GitHub 仓库。官方 README 将它定义为一个“loopback-only gateway”，通过 OpenAI-compatible 和 Anthropic-compatible HTTP APIs 暴露 WorkBuddy AI。仓库同时给出了 Node.js 20 或更新版本、pnpm、类型检查和测试命令。由此可以确认两件事：第一，它的目标是协议适配，而不是重新实现一个模型服务；第二，它默认把服务放在本机回环网络上，而不是默认暴露到互联网。

这一区分很重要。一个项目“能够接收某种格式的请求”，不代表所有字段、错误码、工具调用和流式事件都与上游厂商完全一致。兼容性首先是入口协议的工程约定，其次才是模型能力的映射。

## 它解决的不是模型问题，而是入口协议问题

可以把 WkBdy2api 抽象成三层：客户端协议层、本地适配层和 WorkBuddy 会话层。

客户端协议层面对的是调用方。调用方可能按照 OpenAI 风格构造请求，也可能按照 Anthropic 风格构造请求。它们虽然都表达“给模型一组消息并获得回答”，但消息字段、系统提示的位置、流式事件格式和工具调用表达方式并不相同。网关的任务不是简单把 URL 改名，而是把一种请求语义翻译成另一侧能够理解的内部调用。

本地适配层是风险和复杂度集中的地方。它需要处理模型列表、消息体、流式响应以及错误传播。官方 README 至少明确列出了 `GET /v1/models` 和以 `/v1` 开头的接口入口；这说明项目把模型发现与推理请求都放在兼容 API 的命名空间里。至于某个字段是否被完整支持，不能仅凭“兼容”二字推断，应该以仓库当前实现和测试为准。

最底层是 WorkBuddy 会话层。官方仓库把服务描述为通过 WorkBuddy AI 提供能力，因此网关并不等于一个独立模型运行时。它更像一个本地协议转换器：上游客户端使用熟悉的 API 形状，本地服务再把请求交给 WorkBuddy。这个架构的直接收益是降低客户端改造成本，代价则是增加了一条状态、认证和错误语义的转换链。

从工程角度看，最值得警惕的是“接口看起来统一，语义实际上分叉”。例如客户端可能发送了工具定义，但底层会话未必能以同样的方式执行；客户端可能期待标准 SSE 事件，但适配器输出的事件边界、终止原因或推理字段可能不同。验证兼容性时，不能只测试 HTTP 状态码为 200，而要检查完整响应结构。

## 最小可复现流程：先验证本地闭环

官方 README 给出的开发路径很短，适合先建立一个可控的验证闭环。环境要求是 Node.js 20 或更新版本，并使用 pnpm：

```bash
node --version
pnpm --version
pnpm install
pnpm dev
```

启动后，不要立即把端口映射到公网。第一步只检查本机模型发现接口：

```bash
curl -i http://127.0.0.1:<port>/v1/models
```

这里的 `<port>` 应以项目当前配置或启动输出为准，不应把示例端口当成固定事实。验证重点有三个：连接是否只发生在本机；响应是否是客户端预期的 JSON 结构；服务在 WorkBuddy 不可用时是否返回明确错误，而不是返回一个伪成功的空结果。

随后再使用你实际采用的兼容协议发送最小请求。不要一开始就加入工具、图片、长上下文和流式选项。建议按以下顺序递增：

```text
第一步：单条用户消息，关闭流式输出
第二步：加入 system 消息，检查角色映射
第三步：打开流式输出，检查事件顺序和结束标记
第四步：加入工具定义，确认调用与错误是否可区分
第五步：加入图片或较复杂内容，观察请求体和响应体边界
```

每一步都保留原始请求和原始响应的摘要，至少记录 HTTP 状态码、响应类型、事件数量、结束原因和错误字段。不要把完整提示词、令牌或敏感会话内容写入公共日志。

官方仓库还提供了两类验证命令：

```bash
pnpm typecheck
pnpm test
```

`typecheck` 只能说明 TypeScript 类型约束没有被破坏，不能证明真实客户端完全兼容；`test` 能覆盖仓库作者已经写下的行为，但也不能替代你自己的协议回归样例。两者应当一起运行，再补充 curl 或 SDK 级别的黑盒检查。

## loopback-only 是安全边界，不是部署建议里的小字

“loopback-only”决定了这个项目的默认信任模型。回环地址通常意味着服务只接受本机发起的连接；调用它的客户端、脚本或本机 Agent 与网关处于同一台机器上。这个边界有一个明显优点：服务不需要直接成为互联网入口，扫描器、随机请求和公网滥用流量不会天然到达它。

但它不等于自动安全。只要本机上存在恶意程序、被入侵的浏览器扩展、权限过大的自动化 Agent，或者另一个能够访问本机回环地址的应用，网关就可能被当成内部工具调用。尤其是当网关能够代替用户访问 WorkBuddy 时，攻击者未必需要拿到独立 API 密钥，只要能构造本地 HTTP 请求，就可能尝试复用现有会话。

因此，验证监听范围是上线前的必做项：

```bash
ss -lntp
```

检查监听地址是否为回环地址，而不是 `0.0.0.0` 或公网网卡地址。也可以从另一台机器发起一次连接测试，确认它不会因为容器、端口转发或反向代理配置而意外暴露。仓库包含 Dockerfile 和 docker-compose.yml，只能说明项目提供了容器相关文件，不能据此推断容器部署后仍然保持同样的网络边界；容器端口发布规则必须单独检查。

如果确实需要让局域网内其他客户端访问，正确做法不是直接把监听地址改成公网可达，而是先明确访问者、认证方式、限流策略和日志脱敏规则，再通过受控反向代理或专用网络发布。这样做会改变项目原本的信任边界，应当被当作一次架构变更，而不是启动参数微调。

## 兼容 API 的失败边界在哪里

第一类失败是协议字段被“接受”但没有等价执行。网关可能能够解析请求，却无法把所有语义传递给 WorkBuddy。例如工具参数、推理内容或多模态数据在两个协议之间没有一一对应关系。工程上应区分“请求格式合法”和“模型能力已实现”，不要用一个 200 响应覆盖两者。

第二类失败是流式响应的中途断开。流式接口不是把最终文本拆成几段普通 JSON，而是一个有顺序、有结束条件的事件序列。客户端需要知道连接异常、模型主动结束和网关转换失败之间的区别。验证时应人为中断连接、发送空响应场景，并确认客户端不会把半截答案误认为完整结果。

第三类失败是上游错误被错误包装。WorkBuddy 会话失败、认证失效、模型不存在和请求字段非法，应尽量保持可区分的错误类别。否则调用方只能看到“代理报错”，无法判断是重试、换模型还是修正请求。对于自动化 Agent，这种模糊错误尤其危险，因为它可能触发无意义重试或重复执行工具。

第四类失败是能力列表与真实能力不一致。`/v1/models` 的存在方便客户端发现模型，但发现结果只是目录，不是对每个模型、每种协议特性和每个上下文限制的完整保证。上线前应把模型列表与实际请求结果做交叉验证，并为不支持的能力保留明确失败路径。

## 一份不依赖宣传语的上线检查清单

可以把检查分为四组。

**协议检查。** OpenAI 风格和 Anthropic 风格请求分别测试；非流式、流式、system 消息、工具定义和异常请求分别记录；确认 JSON 的 Content-Type、结束事件和错误字段符合调用方预期。

**网络检查。** 用 `ss -lntp` 确认监听地址；检查 Docker 或反向代理是否改变端口暴露范围；从非本机位置验证不可达性；若必须开放访问，补充认证、限流、来源控制和审计日志。

**行为检查。** 先运行 `pnpm typecheck` 与 `pnpm test`，再用固定的最小请求做回归；保存脱敏后的响应结构，而不是只保存“成功”字符串；测试 WorkBuddy 不可用、模型不存在、连接中断和上游超时。

**维护检查。** 锁定 Node.js 主版本和 pnpm 安装结果；升级依赖后重新执行类型检查、测试和黑盒请求；不要因为社区帖子列出了某项能力，就把它写进自己的稳定性承诺，除非仓库文档或测试能够证明。

## 原创结论：它适合做本地协议适配器，不应被误读成公共 API 平台

WkBdy2api 的价值在于把 WorkBuddy 的使用方式接入已有的 API 客户端生态。对于本机脚本、编辑器插件或受控 Agent，这种 loopback-only 设计可以减少公网暴露面，也能让验证过程集中在协议转换本身。

它的边界同样清楚：网关增加了协议便利性，却没有凭空创造新的模型权限、稳定性或安全保证。越多协议能力被宣称“兼容”，越应该把验证拆成请求映射、流式事件、工具调用、错误传播和网络暴露五个独立问题。真正可维护的做法不是追求一张漂亮的兼容性清单，而是为每项能力保留可复现样例、明确失败结果和可撤销的访问边界。

因此，部署判断可以简化成一句话：如果需求是“让本机工具按熟悉的 API 形状调用 WorkBuddy”，它是一个值得验证的适配器；如果需求是“把它变成任何人都能访问的稳定公共 API”，那就已经超出了官方所强调的 loopback-only 默认场景，必须重新设计认证、隔离、限流、审计和故障语义。
