## 先把“缓存命中 100%”拆成四个不同命题

NodeLoc 上有一条关于 AxAI 的分享：帖子给出了 `https://axai.dpdns.org/v1` 这一 API 地址，指定了一个模型 ID，并声称“缓存命中能达到 100%”。这是一条社区体验描述，不是厂商文档、性能报告或可审计的监控截图，因此证据等级只能标为“社区观察”。它可以作为值得验证的线索，却不能直接升级成平台能力结论。

“缓存命中”这个词本身也不够精确。至少要拆成四个命题：第一，域名和 `/v1` 入口当前可访问；第二，入口接受某种 API 请求并返回协议层响应；第三，相同请求被网关或上游缓存直接复用；第四，复用行为不会把一个用户的结果、权限或计费状态错误地暴露给另一个用户。前两个命题属于连通性和协议兼容，后两个命题才涉及缓存架构与安全边界。

AxAI 入口当前公开返回的内容是 `{"message":"AXAI API Gateway is running","status":true}`。这足以说明该 URL 存在一个运行中的网关响应，但不足以证明它支持哪一种具体模型、是否支持流式响应、是否存在响应缓存，也不足以证明请求会被转发到哪个上游。另一个公开页面只显示 `new-api-Max`，同样不能替代 API 文档。材料没有提供缓存 TTL、缓存键组成、命中响应头、计费规则或数据隔离说明，文章因此不会把这些未知项写成事实。

## 第一步：只验证入口，不提前推断架构

验证公共入口时，先把目标限定为“它是否响应”，不要一上来发送真实提示词或敏感内容。最小检查可以使用：

```bash
curl -i --max-time 15 https://axai.dpdns.org/v1
```

需要记录的是 HTTP 状态码、响应时间、响应体和 `Date`、`Server`、`Via`、`Age`、`ETag`、`Cache-Control` 等实际出现的头部。没有这些头部，不能据此判断“没有缓存”；有 `Age` 也不能单独证明内容来自共享缓存，因为反向代理、CDN 和应用自身都可能生成类似信号。检查结果应保存为带时间戳的文本，而不是只截取一张成功页面。

```bash
curl -sS -D /tmp/axai.headers \
  -o /tmp/axai.body \
  --max-time 15 \
  -w 'code=%{http_code} time=%{time_total} size=%{size_download}\n' \
  https://axai.dpdns.org/v1

cat /tmp/axai.headers
cat /tmp/axai.body
```

这一步的工程意义是建立基线：域名解析、TLS、HTTP 路由和响应体分别处于什么状态。如果入口返回网关运行信息，只能把它标记为“控制面或健康检查响应”。不要把健康检查的稳定返回误当成模型调用成功，更不要把一次低延迟误当成缓存命中。

还要注意时间因素。社区帖子中的状态、模型列表和额度规则可能随时变化；本次材料没有给出官方版本号、发布记录或 SLA。验证报告应写明执行时间、请求 URL 和状态码，而不是使用“长期稳定”“永久免费”等无法由现有证据支撑的词。

## 第二步：用请求矩阵验证“缓存”而不是验证“重复字符串”

如果平台提供了正式 API 文档和测试账户，才可以进入请求层验证。材料没有给出认证方式，因此不能假设某个 `Authorization` 格式，也不能把下面命令当成对该站点已经验证通过的调用。它是一份通用的实验模板，执行前必须根据平台官方接口补齐模型、鉴权和请求字段。

核心不是连续发送两次完全相同的请求，而是设计对照组。至少需要四组样本：

1. 同一账户、同一模型、同一输入，连续发送两次。
2. 同一账户、同一模型，只改变输入末尾的一个字符。
3. 同一输入，改变随机性参数；如果接口支持，应分别测试固定和不同的随机种子。
4. 同一输入、同一模型，换用另一账户或另一独立凭证。

每次请求都记录请求摘要、响应摘要、HTTP 状态码、响应头、首字节时间、总耗时、Token 用量、计费变化和错误信息。提示词本身可能包含隐私，不应直接写入公共日志；可以保存规范化请求的哈希，并在受控环境里保留原文。

伪代码式的检查框架如下：

```bash
request='{"model":"MODEL_ID","messages":[{"role":"user","content":"cache-probe-001"}]}'

curl -sS --max-time 60 \
  -H 'Content-Type: application/json' \
  -H "Authorization: Bearer $API_KEY" \
  -d "$request" \
  -D response.headers \
  -o response.body \
  -w 'code=%{http_code} first=%{time_starttransfer} total=%{time_total}\n' \
  https://example.invalid/v1/chat/completions
```

这里使用 `example.invalid` 是为了强调：材料没有确认 AxAI 的具体调用路径、认证方式和响应协议，不能编造一个看似可用的命令。真正的验证应以平台公开文档或服务方给出的接口契约为准。若平台只给出一个网关首页而没有 API 说明，那么最稳妥的结论只能停留在“入口可达，调用协议待核验”。

判断缓存时，响应文本相同只是必要条件之一，不是充分条件。模型本来就可能在相同参数下返回相同结果；客户端也可能重复展示本地历史结果；上游模型可能拥有自己的提示词缓存。更有价值的证据包括明确的命中头部、网关控制台中的命中计数、Token 计费差异、服务端返回的请求 ID 规律，以及在改变缓存键相关字段后命中状态发生可重复变化。单次请求耗时下降也不能独立证明缓存，因为网络路径和上游负载都在变化。

## 第三步：缓存键决定了它是优化还是数据泄漏

一个可接受的缓存实现，至少要回答“以什么作为键”和“谁可以复用”。常见候选字段包括模型、消息内容、系统提示词、工具定义、温度、种子、响应格式、租户、账户和权限范围。材料没有说明 AxAI 使用哪种策略，因此只能把这些列为核查清单，不能断言其架构。

如果缓存键只包含模型和文本，却没有纳入账户或租户标识，就可能出现跨用户复用。对于公共 AI 网关，这不是抽象风险：用户输入可能包含源代码、内部 URL、个人资料或业务数据；若响应缓存没有正确隔离，后一个请求就可能得到前一个请求的结果。反过来，如果缓存键包含账户、完整鉴权上下文和大量请求参数，安全性更容易控制，但命中率会下降，缓存占用也会增加。

工程上还存在一个取舍：缓存越激进，成本和延迟可能越低，但结果新鲜度、个性化能力和撤销能力越弱；缓存越保守，隔离和可解释性越好，但重复请求仍会消耗上游资源。需要明确 TTL、主动失效、错误响应是否缓存、流式响应如何处理、工具调用是否禁用缓存，以及管理员能否查询和清理缓存。没有这些信息，就不能把“100% 命中”翻译成“所有请求都不会消耗额度”或“可以放心发送敏感数据”。

还有一个容易被忽略的边界：缓存命中与计费是两条链路。即使返回内容来自缓存，平台仍可能按请求次数、输入 Token、输出 Token 或固定单价计费；也可能为了统计而保留一次调用记录。只有同时观察账单、额度和请求日志，才能判断缓存是否改变了成本。材料中的其他社区帖子提到一些站点会赠送额度或允许有限透支，但这些现象不能外推到 AxAI，也不能作为缓存计费规则的证据。

## 失败边界：什么结果应该被判为“无法证明”

验证公共网关时，最有价值的结论往往不是“命中”或“未命中”，而是明确哪些证据缺失。出现以下情况时，应停止扩大测试并把结论写成“无法证明”：

- 只有健康检查页面，没有正式 API 文档、认证说明和模型契约。
- 请求返回相同文本，但没有命中头部、请求 ID、用量或计费证据。
- 只测试了同一账户和同一输入，没有跨输入、跨参数的对照组。
- 只观察到一次低延迟，无法排除网络抖动、上游负载变化或客户端缓存。
- 平台没有说明数据保留、日志访问、缓存清理和租户隔离策略。
- 社区帖子给出个人体验，但没有可复核的时间、版本、完整响应和失败样本。

尤其不能用“缓存命中 100%”推导出“服务可靠”“上游稳定”“隐私安全”或“永久免费”。这些是不同维度的工程命题，需要分别验证。社区材料适合帮助我们发现问题和构造测试样本；一手来源才适合证明接口、发布和架构事实。本批材料中的 AxAI 官方入口只能证明当前有网关响应，`new-api-Max` 页面只能证明页面自称使用这一名称，二者都没有提供缓存实现细节。

## 给使用者和运营者的最小检查清单

对使用者来说，第一次接入未知 AI 网关时，建议先用无敏感、可撤销的探针文本，设置短超时和低频率，确认协议和错误格式后再接入编辑器或 Agent。不要把生产密钥、客户数据、内部代码和长期凭证直接交给一个只有社区推荐、没有隐私与计费说明的入口。若必须测试，应为测试用途单独创建凭证，并记录请求时间、模型、状态码和额度变化。

对运营者来说，想让“缓存命中率”成为可信指标，至少需要公开指标定义：分母是请求数还是可缓存请求数，命中是网关命中还是上游命中，流式请求是否计入，错误和取消请求如何处理，统计窗口多长，是否按租户分组。同时应提供不会泄露提示词的请求 ID、命中状态、Token 用量和计费解释，并明确缓存 TTL、隔离维度和清理接口。

最终结论应保持克制：社区关于 AxAI“缓存命中 100%”的说法值得作为实验线索，但现有材料不足以证明其缓存机制、命中率口径、安全隔离或费用影响。对公共 AI 网关而言，真正可复用的能力不是一个漂亮百分比，而是一条能被第三方重复执行的证据链：入口可达，协议明确，请求可对照，命中可观测，账单可核对，失败边界可解释。
