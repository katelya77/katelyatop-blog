## 先把“8GB 显存可运行”拆成一个工程问题

FreeVideo 的吸引力不只是“开源视频生成”这五个字，而是它把一个原本容易被云端 GPU 绑架的任务，明确指向了已有个人电脑：官方 GitHub 仓库的项目说明称，FreeVideo 用于在用户已有的电脑上生成视频，运行 MiniMax H3 时最低可使用约 8GB 显存和 16GB 系统内存，并会根据硬件调整加速路径。社区帖子也转述了相近的硬件条件，并提到可以在 ComfyUI 中使用文字提示、关键帧、视频和音频参考。

这里有一个必须先澄清的证据等级：硬件下限和项目定位来自项目仓库，属于一手来源；“免费”“自动适应硬件”“可以在 ComfyUI 中运行”等使用场景由社区材料补充，但社区帖子不能替代官方运行文档。材料没有提供完整安装命令、模型下载地址、具体显卡兼容矩阵、每段视频的生成耗时，也没有证明“8GB 显存”在所有分辨率、帧数和输入组合下都能稳定完成任务。因此，更准确的表述是：8GB 显存是项目宣称的可运行下限，不是对任意工作流、任意视频长度和任意速度的保证。

这一区别决定了部署思路。不要先问“我的显卡能不能跑”，而要把问题拆成四层：推理引擎能否启动，模型能否装入可用显存，工作流是否能完成，输出是否满足质量和时延要求。只有四层都通过，才算真正可用。

## 从仓库目录看，它不是一个单文件脚本

官方仓库列出的目录包含 `freevideo_engine`、`constraints`、`docs`、`example_workflows`、`web` 和 `scripts` 等部分。仅从这一结构可以看出，FreeVideo 的工程形态更接近“推理引擎 + 约束定义 + 示例工作流 + Web 入口”的组合，而不是复制一个 Python 文件后直接执行。

`freevideo_engine` 可以视为核心推理层；`constraints` 暗示项目需要对显存、内存或硬件能力做约束管理；`example_workflows` 则承担把模型能力组织成可重复流程的作用；`web` 说明项目可能提供面向交互的界面；`scripts` 和 `docs` 分别对应自动化操作与使用说明。这里不能把目录名扩写成未经证明的具体实现，例如不能据此断言它使用了某一种量化格式、某个特定注意力优化库，或一定支持 CPU fallback。工程上应该把这些内容当成待核验接口。

一个更稳妥的本地架构可以按以下链路理解：

```text
用户输入
  ├─ 文本提示
  ├─ 关键帧
  ├─ 参考视频
  └─ 音频参考
        ↓
工作流编排层 / ComfyUI
        ↓
FreeVideo 推理引擎
        ↓
硬件约束与加速路径选择
        ↓
显存、系统内存、磁盘共同参与的生成过程
        ↓
视频输出与结果校验
```

这个架构的关键不是“界面是否漂亮”，而是把输入类型、推理资源和输出验证分开。文本生成失败，可能是模型或提示问题；参考视频失败，可能是输入编码或显存峰值问题；同一工作流在另一张卡上速度不同，则可能是加速路径选择差异。分层后，排错不必把所有问题都归咎于模型。

## 先做环境盘点，再决定工作流规模

由于材料没有给出一条经过官方确认的安装命令，不能凭空编写 `pip install`、Docker 镜像或模型下载脚本。正确的第一步是获取代码并检查项目自身提供的文档和示例：

```bash
git clone https://github.com/FlashML-org/FreeVideo.git
cd FreeVideo

git rev-parse --show-toplevel
git log -1 --oneline
find . -maxdepth 2 -type f | sort | sed -n '1,160p'

grep -RniE 'install|setup|download|model|ComfyUI|VRAM|RAM|workflow' \
  README* docs example_workflows 2>/dev/null | sed -n '1,220p'
```

这些命令不假设项目的安装方式，只确认当前代码版本、文档入口、示例工作流以及依赖说明。部署时应以仓库中的 README、`docs` 和示例文件为准；如果项目的当前分支与文章依据的版本发生变化，先记录提交哈希，再进行后续比较。

硬件检查也应该留下可复核的输出。Linux 上可以使用：

```bash
nvidia-smi --query-gpu=name,memory.total,driver_version \
  --format=csv,noheader
free -h
df -h .
```

如果机器没有 NVIDIA 工具，不要因此直接得出“无法运行”的结论，因为官方材料只说明项目会根据硬件调整加速路径，没有给出完整后端清单。此时应检查项目文档是否声明了其他后端，以及当前工作流是否依赖特定 GPU。这里需要记录三类容量：显存总量、系统可用内存和模型及输出所在磁盘空间。8GB 显存与 16GB 内存是项目宣称的下限，但系统本身、桌面环境、浏览器和其他进程都会占用资源，实际可供推理使用的容量通常低于标称值。

建议第一次只运行最小示例：单一文本提示、较短输出、无额外参考输入，并关闭不必要的本地程序。通过后再逐步加入关键帧、参考视频和音频，而不是一次性把所有能力叠加到同一个工作流中。

## ComfyUI 工作流的价值：把变量变成可比较的实验

社区材料提到 FreeVideo 可在 ComfyUI 中运行。即使具体节点名称和导入方式需要以项目文档为准，工作流思维仍然适合本地视频生成：把提示词、输入素材、采样参数、输出设置和执行结果固定下来，每次只改变一个变量。

可以建立一个最小验证表：

| 阶段 | 固定内容 | 只改变的变量 | 通过标准 |
| --- | --- | --- | --- |
| A | 文本提示、输出尺寸、帧数 | 是否能启动 | 工作流完成且产生文件 |
| B | A 的全部条件 | 输出帧数 | 显存不溢出，文件可播放 |
| C | B 的全部条件 | 关键帧输入 | 输入被正确读取，主体不明显丢失 |
| D | C 的全部条件 | 参考视频或音频 | 失败时能定位到新增输入链路 |
| E | 选定工作流 | 硬件或加速路径 | 质量、速度和资源占用可接受 |

每次运行至少保存工作流文件、项目提交哈希、输入素材摘要、输出文件大小和错误日志。不要只保存一张最终视频截图，因为截图无法证明生成过程是否完整，也不能帮助判断一次成功是不是偶然。

输出验证可以先做廉价检查：

```bash
find . -type f -mmin -30 -printf '%TY-%Tm-%Td %TH:%TM:%TS %s %p\n' \
  | sort -r | head -20

file path/to/output-file
sha256sum path/to/output-file
```

如果项目文档明确提供了输出格式和播放器要求，再按其说明检查时长、帧率和编码。材料没有证明 FreeVideo 固定输出哪一种容器或编码，因此不应把某个具体扩展名写成项目保证。验证的核心是：文件确实由本次任务产生，大小不是零，能够被目标播放器或后续处理工具正常读取，并且工作流没有在中途静默失败。

## 失败边界比最低配置更值得关注

第一类边界是显存峰值。视频生成通常不是“模型大小小于显存”这么简单，输入参考、输出帧数和中间张量都可能改变峰值。FreeVideo 宣称会适配硬件，但材料没有说明适配是降低分辨率、减少帧数、切换算子，还是采用其他策略。因此，遇到显存不足时，优先按官方示例降低单次任务规模，并逐项关闭参考输入；不要擅自断言某个环境变量一定有效。

第二类边界是系统内存和交换空间。16GB 内存可以作为项目宣称的参考下限，却不是桌面系统下的安全余量。即使显存足够，内存压力也可能造成系统卡顿、进程被终止或生成时间失去可预测性。部署机器最好专门留出内存和磁盘预算，把浏览器、视频编辑器和推理任务分开运行。

第三类边界是输入复杂度。文本提示、关键帧、参考视频和音频参考并非同一个成本等级。输入越多，越难判断失败来自模型、格式、节点连接还是资源峰值。工程上应该先验证最短路径，再扩展输入；对于生产任务，还要保留原始素材和工作流版本，避免无法复现。

第四类边界是“本地运行”与“本地完成”的区别。模型权重、依赖包、浏览器界面或更新流程可能仍需要网络；当前材料只支持 FreeVideo 的本地视频生成定位，不能进一步声称它完全离线、无需账号或不向外部服务发送任何数据。涉及敏感素材时，必须审查代码、依赖和工作流，而不能仅凭“在自己的电脑上运行”就完成隐私判断。

## 工程取舍：免费不是零成本

本地运行的直接收益是把计算控制权放回用户设备，素材不必默认上传到第三方 GPU 服务，也可以反复调整工作流而不按云端调用次数计费。但成本会转移到硬件折旧、显卡功耗、磁盘空间、安装维护和失败重试上。

云端更适合短期验证、突发高并发或需要稳定吞吐的团队；本地 FreeVideo 更适合已有合适设备、素材不希望离开内网、愿意维护运行环境的个人和小团队。若任务是批量生成，不能只比较“每次调用价格”，还应比较队列等待时间、设备占用、失败重跑比例和人工排障成本。

一个可操作的选择规则是：先用本地最小工作流验证质量，再测量连续任务中的平均耗时、峰值显存、系统内存和失败率。如果本地生成质量合格但吞吐不足，可以考虑把本地作为创作和隐私链路，把云端作为可替换的批处理链路；如果连最小工作流都无法稳定完成，就不要通过增加输入复杂度来掩盖基础环境问题。

## 结论：把硬件下限改写成可验证的预算

FreeVideo 最值得关注的不是“8GB 显存能不能生成视频”这一句宣传，而是它试图把 MiniMax H3 视频生成放进不同个人硬件的现实约束中，并通过推理引擎、约束目录、示例工作流和交互入口组成一个可继续验证的工程项目。官方仓库给出了项目定位和硬件下限，社区材料提供了 ComfyUI 与多种输入类型的使用线索；但完整安装步骤、后端覆盖、性能曲线和具体质量边界仍应回到项目版本与文档逐项核验。

因此，部署成功的定义不应是“程序启动了”，而应是：记录了代码版本，确认了显存、内存和磁盘预算，完成了最小工作流，逐步验证了参考输入，保存了可复现的配置，并能解释失败发生在哪一层。只有这样，本地视频生成才不是一次偶然跑通的演示，而是一条可维护、可迁移、可审计的生产链路。
