AI 编程代理的风险，往往不在它能不能生成代码，而在它准备执行动作时，系统是否有机会把动作停下来。一个代理可能调用网络、运行 Shell、触发云端任务、读取组织策略，还可能把账号信息带出当前环境。只要其中任意一步缺少明确的阻断点，后续再补审计日志，通常已经晚了。

Claude Code v2.1.317 的官方 Release 将多个变化放在同一批发布中：当 Web 或 Shell 工具调用会把账号邮箱发送到网络时进行询问；Agent SDK 的 Hook 回调支持 `onFailure: "block"`；远程托管设置未加载时在桌面端提示；自动模式无法判断子代理工具调用时显示通知；同时向 OTel 指标、事件和 Span 增加计划、席位类型、提供商和自定义网关地址等字段。它们共同指向一个工程问题：把代理的“是否允许执行”从隐式行为变成可验证的状态机。

需要先说明证据等级：本文关于版本行为的判断只采用 Claude Code 官方 Release；关于仓库是否受到保护、如何在安全评估中呈现，采用 GitHub 官方 Changelog。材料没有提供某个具体配置文件、命令行开关或 API 响应样例，因此下文的命令主要用于建立验收记录和检查本地证据，不把未披露的开关写成产品事实。

## 一、把代理安全拆成三个时刻

第一时刻是执行前。代理准备调用 Web 或 Shell 工具时，系统需要判断动作是否会把账号邮箱发送到网络。这里的关键不是“邮箱是不是高危秘密”，而是数据流是否跨越了原本的信任边界。账号邮箱可能用于身份关联、社工或组织画像；更重要的是，用户必须在动作发生前看到风险，而不是在日志里事后发现。

第二时刻是策略判定失败。Agent SDK 的 Hook 回调新增 `onFailure: "block"`，意味着回调失败可以阻止动作继续执行。这个选择把失败语义从“回调坏了但主流程照常运行”改成“无法完成安全判定就不放行”。它适合权限检查、敏感数据扫描、命令审查这类默认拒绝场景，但会带来可用性成本：网络抖动、依赖服务故障或规则误报，都可能使任务中断。

第三时刻是执行后。OTel 增加的 `anthropic.plan`、`anthropic.seat_type`、`anthropic.provider` 和 `anthropic.custom_base_url` 字段，让团队可以把一次调用放回更完整的上下文中：它属于什么计划、哪个席位、通过哪个提供商、是否经过自定义网关。这里的价值不是多几个标签，而是让安全事件、成本事件和路由事件能够关联起来。

这三个时刻不能互相替代。执行前确认解决的是“现在要不要放行”；失败即阻断解决的是“判定系统失效时怎么办”；遥测解决的是“放行之后能不能复盘”。只做其中一项，闭环仍然是不完整的。

## 二、为什么失败即阻断比失败即放行更难

失败即放行的系统通常更顺滑：Hook 超时了，任务继续；策略服务不可用，工具照常调用；远程设置没加载，本地默认配置接管。问题在于，这些默认值会把一次明确的异常悄悄转换成一次成功动作。对于代理来说，调用链越长，用户越难意识到某个安全检查实际上没有执行。

失败即阻断则相反。它把系统故障暴露给用户，也把“是否执行”变成显式结果。工程上至少要区分三种失败：

1. 规则明确拒绝，例如命令或请求命中禁用条件；
2. 检查器自身失败，例如依赖服务超时、解析错误或回调崩溃；
3. 检查结果未知，例如自动模式无法判断子代理工具调用。

第一类应该给出可读的拒绝原因；第二类应该阻断并记录故障上下文；第三类不应伪装成允许，至少需要在主界面或调用结果中明确通知。Claude Code v2.1.317 的发布说明分别提到 `onFailure: "block"` 与自动模式无答案时的提示，这说明产品正在把“未知”从静默状态提升为用户可见状态，但材料并未说明所有工具调用都统一采用同一策略，不能据此推断完整的全局默认行为。

实际取舍是：高风险动作采用失败即阻断，低风险动作可以采用降级，但降级必须有边界。比如只读本地分析可以在遥测不可用时继续，而发送网络请求、执行破坏性命令、修改远程资源则应要求策略检查成功。不要把“体验更流畅”当作统一原则，应该按动作的不可逆程度分级。

## 三、用可复现检查记录发布是否真的生效

由于 Release 没有给出统一的 CLI 参数，验收不能依赖“升级成功”这一代理指标。可以把下面的清单放入版本升级工单或 CI 记录中，逐项保存结果、时间和日志位置。

### 1. 版本与变更来源

```sh
claude --version
printf '%s\n' 'record: official release v2.1.317'
```

检查项：

- 输出版本是否与目标版本一致；
- 升级来源是否能追溯到官方 Release，而非第三方打包说明；
- 发布记录是否注明这是正式版本还是预发布版本；
- 变更验证是否覆盖了本组织实际启用的 Web、Shell、Hook 和远程策略路径。

### 2. 网络发送确认

准备一个不会造成真实外发的测试动作，观察代理在调用 Web 或 Shell 工具、且动作可能发送账号邮箱时是否出现确认。验收记录至少包含：触发条件、用户看到的提示、选择拒绝后的结果、选择允许后的审计信息。不要只截取允许场景，因为安全控制最容易在拒绝路径上失效。

检查项：

- 提示是否发生在网络动作之前；
- 提示是否说明被发送的数据类别，而不是只显示工具名称；
- 拒绝后是否没有继续调用目标网络；
- 同一会话中的重复动作是否出现不可解释的静默放行；
- 日志是否能关联到具体会话和工具调用。

### 3. Hook 失败路径

构造一个可控的 Hook 失败，例如让测试回调返回错误或暂时不可用，但不要在生产目录执行。记录三种结果：回调成功、回调明确拒绝、回调失败。只有在第三种情况下确认动作被阻断，才能认为 `onFailure: "block"` 的语义在当前集成中真正被验证。

```text
PASS: callback success -> action follows policy
PASS: callback deny -> action is not executed
PASS: callback failure -> action is blocked and failure is visible
```

如果第三行变成“action continues”，不要用重试次数、日志数量或人工承诺弥补，它说明当前路径仍然是失败即放行。还要记录阻断是否可恢复：用户修复策略服务后能否重新提交，而不是被迫重启整个代理会话。

### 4. 远程设置加载

在测试环境中分别模拟远程托管设置成功、延迟和未加载。检查桌面端或主界面是否明确提示当前会话的策略状态。重点不是提示文案是否漂亮，而是用户能否在执行高风险动作前知道组织设置尚未生效。

```text
policy_loaded=true  -> record policy source and load time
policy_loaded=false -> show visible notice; do not imply managed policy is active
```

材料只确认官方发布说明提到未加载和加载完成通知，并没有规定所有未加载场景都自动阻断。因此，组织应自行规定：在策略未加载时，哪些动作必须禁止，哪些只允许本地只读操作，并把规则写入内部运行手册。

## 四、把 OTel 字段变成可查询的证据链

增加遥测字段后，最常见的误区是“字段出现了，所以已经可观测”。真正有用的验证应检查字段是否在指标、事件和 Span 中保持一致，是否能与一次具体的工具调用、策略决策和结果关联。

可以先做字段完整性检查：

```sh
# 仅检查脱敏后的导出样本，不把真实账号信息写入终端
jq -e 'has("anthropic.plan") and has("anthropic.seat_type") and has("anthropic.provider")' otel-sample.json
jq -e 'has("anthropic.custom_base_url")' otel-sample.json
```

这不是产品官方命令，而是对脱敏导出样本的结构检查。它只能证明样本中存在字段，不能证明字段值正确，更不能证明所有调用都携带字段。进一步的验收应建立最小关联表：调用时间、会话标识、计划、席位类型、提供商、自定义网关地址、工具类型、策略结果、最终动作。对于自定义网关地址，应把它视为路由和数据边界信息，限制访问权限，避免把完整 URL 中可能存在的敏感查询参数直接暴露给普通观察者。

查询时要重点看异常组合：策略拒绝但没有对应事件、工具执行成功却没有策略判定、提供商或自定义网关突然变化、同一席位出现不符合预期的路由。可观测性不是为了堆报表，而是为了证明“谁在什么策略上下文中，放行了什么动作”。

## 五、GitHub 安全评估为何要看仓库保护状态

GitHub 在 2026 年 11 月 2 日的官方更新中说明，代码安全风险评估和秘密风险评估现在会显示发现所在仓库是受保护还是未受保护。这一变化的重要性在于：同一个漏洞或秘密发现，处在不同保护状态的仓库里，治理优先级并不相同。

“有发现”只回答问题的一半；“发现所在仓库是否已有保护”回答的是覆盖率问题。一个组织可能拥有大量扫描结果，却仍然把关键仓库放在未保护的配置里。把仓库保护状态纳入评估，可以把安全工作从单条告警推进到控制面盘点：哪些仓库没有保护，哪些保护已覆盖但仍有高风险发现，哪些项目应该优先补齐策略。

这和代理安全是同一个闭环的不同层次。代理调用代码、提交变更或访问仓库时，动作层需要确认和阻断；组织层需要知道目标仓库是否处于受保护状态。没有仓库保护状态，代理的风险评估容易只看行为日志；没有代理动作记录，仓库保护也无法解释某次变更是如何产生的。

## 六、工程取舍：阻断不是越多越安全

默认阻断会降低误操作概率，但也会把策略服务的可靠性变成开发效率的一部分。最稳妥的做法不是所有动作统一拒绝，而是建立动作分级：本地只读、可逆文件修改、网络发送、远程写入、破坏性命令分别设定不同的策略强度。

同时，阻断必须可诊断。用户至少需要知道动作被谁阻断、阻断原因属于拒绝还是检查失败、修复后如何重试。没有这些信息，团队会倾向于关闭 Hook 或绕过确认，最终让安全控制失去实际效果。

我的结论是：AI 代理的安全成熟度，不应以“默认开启了多少策略”衡量，而应以三个问题衡量。第一，风险动作发生前是否有明确的决策点；第二，决策系统失败时是否安全停机；第三，执行结果能否通过策略上下文和遥测字段复盘。Claude Code v2.1.317 的这些变化，以及 GitHub 将仓库保护状态纳入风险评估的更新，共同说明安全能力正在从单点提示走向分层证据链。

当团队下一次升级代理工具时，最值得验收的不是新增了几个命令，而是失败时它是否真的停下来、停下来的原因是否可见，以及事后能否证明它当时为什么放行或拒绝。
