## 先把“能选”与“能用”分开

AI 工具中的模型选择器很容易制造一种错觉：只要某个模型出现在列表里，组织就已经完成了接入。实际上，至少有三件事必须分别确认：模型是否对当前账户可见，组织策略是否允许使用，以及请求经过的服务商和数据处理路径是否满足要求。

GitHub 在 2026 年 11 月发布的 Copilot 更新说明提供了一个典型案例：Claude Fable 5.2 已进入 GitHub Copilot 的多个产品入口，包括 Visual Studio Code、Copilot CLI、coding agent、Copilot app，以及部分 IDE。可是，企业和组织管理员仍需显式开启对应策略；该策略默认关闭。更重要的是，Fable 5.2 默认需要数据留存，以运行 Anthropic 的安全分类器。这里的“可选”只说明产品层面已经提供入口，并没有自动推出“适合所有代码和组织”的结论。

因此，模型治理不能只记录模型名称和价格。至少应把以下字段视为同等重要的配置对象：

- 可见范围：哪些计划、团队、用户或产品入口可以选择；
- 管理开关：谁能启用，默认状态是什么；
- 数据策略：提示词和输出是否会被保留，保留的目的是什么；
- 例外期限：例外是否有明确的截止日期；
- 运行路径：请求是否存在区域选择、速度档位或自动降级；
- 证明方式：如何证明实际使用的是批准的模型和策略。

这套拆分的价值在于，它把“功能发布”还原成一组可审计的控制面，而不是一个 UI 标签。

## 数据留存不是抽象的隐私声明

在 Fable 5.2 的官方说明中，数据留存有明确的操作目的：用于运行安全分类器，检测有害使用；留存数据不用于训练 Anthropic 的模型。这两个事实必须同时记录，不能把后半句简化成“所以没有留存”，也不能把前半句扩大成“所有请求都会被用于训练”。工程上应将不同目的拆开管理：安全检测、运行日志、计费记录、调试数据和模型训练并不是同一个数据类别。

官方说明还指出，其他 Claude 模型通常继续按零数据留存运行，但 Fable、Fable 5.1 和 Fable 5.2 是例外。对于企业管理员而言，这意味着“Claude”这个供应商名称不足以作为策略键。策略至少要下沉到具体模型系列，必要时还要下沉到版本。

更容易被忽略的是，零数据留存并非对所有用户都立即可用。符合条件的企业客户可以在一个有时间限制的豁免期内使用部分 Fable 模型的零数据留存选项；官方说明同时表明，后续使用可能需要 Enterprise Frontier Safeguards。这个设计告诉我们：合规例外不是永久能力，而是带有期限和前置条件的状态。

所以，企业策略不应写成“允许 Claude，禁止有留存模型”这样模糊的规则，而应形成可计算的决策：

```text
if model in restricted_models:
    require explicit_admin_policy
    require approved_data_classification
    require retention_exception_if_applicable
    require expiry_review_date
else:
    apply_provider_and_plan_specific_policy
```

这段伪配置不是某个产品的真实 API，而是审计时应具备的决策结构。真正落地时，策略名称、模型 ID 和权限入口必须以产品当前文档为准，不能凭模型显示名称猜测。

## 速度开关也会改变运行路径

数据留存是明显的治理边界，路由降级则是性能和可重复性的边界。Claude Code v2.1.322 的官方 Release 说明提到，Vertex 的快速模式已在 global、us 和 eu 区域提供；当 Vertex 拒绝快速模式时，会回退到标准速度。

这个行为的工程含义不是“快一点或慢一点”这么简单。它至少引入了三个可观测变量：请求所在区域、请求选择的速度档位，以及服务商拒绝后是否发生了自动回退。若团队只记录模型名称，而不记录区域和模式，那么同一条任务在不同时间得到不同延迟，甚至出现不同服务行为时，调查会缺少关键上下文。

自动回退通常是合理的可用性设计，但它会削弱实验的可重复性。性能测试若没有固定区域和模式，结果只能代表混合路径；SLA 若只按理想快速模式估算，也可能把服务商拒绝时的标准路径漏算进去。另一方面，彻底关闭回退可能让短暂的服务商限制直接变成失败。这里不存在对所有团队都正确的单一选择，关键是把选择显式化：生产任务优先保证完成，基准测试优先保证路径稳定，故障演练则应覆盖回退路径。

可以把一次 AI 请求的最小运行记录设计为：

```json
{
  "model": "approved-model-id",
  "provider": "approved-provider",
  "region": "global-or-explicit-region",
  "mode": "fast-or-standard",
  "fallback": "allowed-or-denied",
  "policy_revision": "policy-version",
  "timestamp": "request-time"
}
```

这同样是记录格式示例，不是上述产品声明提供的固定接口。它的作用是提醒工程团队：没有路径信息，就无法解释延迟变化，也无法证明请求符合批准策略。

## 一套可执行的接入检查清单

### 1. 发布证据检查

先确认来源等级。模型能力、数据处理方式和默认策略应优先采用厂商 changelog、官方 release 或正式文档。社区帖子可以帮助发现问题，但不能证明某项能力已正式开放。对预览、逐步 rollout 或时间限制豁免，必须在内部记录证据日期和失效条件。

再确认版本范围。Fable 5.2 的说明明确列出了可用产品入口，但还提示 rollout 会逐步进行。因此，管理员看到“已发布”并不等于每个组织、每个界面已经立即可用。验证时应把“官方宣布可用”和“当前租户实际可见”作为两个独立结果。

### 2. 管理策略检查

在启用前回答四个问题：策略默认是否关闭；启用动作由谁执行；哪些计划或用户受影响；关闭策略后，模型是否从选择器中消失。不要只截一张模型列表截图，因为截图无法证明组织级策略、用户级覆盖和默认状态。

对于需要数据留存的模型，应建立数据分类门禁。源代码、生产凭据、客户内容和内部设计文档不应因为“模型已获批准”就自动进入同一条路径。批准的模型范围、允许的数据等级和例外审批应分别记录。

### 3. 运行路径检查

若产品存在快速模式、区域选择或自动回退，应在测试任务中故意覆盖至少两种结果：快速路径成功，以及服务商拒绝快速路径后的标准路径。验证重点不是追求某个固定延迟，而是确认回退是否发生、是否有日志或状态可识别、最终请求是否仍符合数据策略。

对于区域相关能力，不能只在一个区域验证后推断所有区域一致。官方说明明确列出 global、us 和 eu，这些名称本身就是应纳入测试矩阵的维度。若组织有数据驻留要求，还应进一步确认产品关于区域的定义是否等同于数据处理地点；没有官方依据时，不应自行作出等同判断。

### 4. 期限与回退检查

所有例外都要有到期时间。时间限制豁免不能依赖个人记忆，也不能把“到期后继续可用”当成默认假设。自动任务应在到期前提醒管理员复核，复核结果只有三类：继续满足条件、切换到批准模型、阻断请求。

回退策略也应明确。若快速模式被拒绝，标准模式是否允许继续执行；若模型策略被关闭，调用方是选择其他已批准模型，还是直接失败；若审计字段缺失，是否阻断高敏感任务。对高风险工作负载，失败通常比静默切换更容易审计，但对低风险交互，受控降级可能更符合可用性目标。

## 如何验证，而不是只看配置页面

验证应覆盖控制面、执行面和证据面三个层次。

控制面验证确认管理员策略真实生效：模型是否按预期可见，默认关闭项是否确实关闭，普通成员是否无法自行绕过组织策略。执行面验证使用固定任务和固定输入，分别测试允许路径、被拒绝路径和回退路径。证据面验证检查日志、请求元数据或账单记录中是否能看到模型、区域、模式和策略版本。

三层中缺一不可。控制面显示“已关闭”，不代表旧会话或其他产品入口已经停止；执行面返回成功，不代表请求使用了批准的区域；日志存在，也不代表日志字段足以证明数据留存策略。验收结论应写成条件句，例如“在指定计划、产品入口和策略版本下，模型不可见；在策略开启后，固定测试任务可执行；快速模式被拒绝时，系统记录并进入标准模式”。

不要把一次成功请求当成全面证明。逐步 rollout、计划差异、区域差异和供应商拒绝都会造成局部结果。更可靠的验收材料是一个小型矩阵：行是产品入口，列是组织计划、策略状态、区域和模式；每个单元格附带时间、结果和证据位置。

## 原创结论：把模型接入当成策略发布

这两份官方材料放在一起，能得到一个比“新模型上线”更有用的结论：AI 产品的风险通常不藏在模型名称里，而藏在模型名称之外的默认值、例外状态和自动路径中。

Fable 5.2 说明了模型能力与数据留存策略可以同时变化；Vertex 快速模式则说明性能档位与区域回退也会改变请求路径。前者要求数据治理，后者要求可重复性和可观测性。它们共同指向一种工程方法：模型接入应像发布一条新策略，而不是给选择器增加一个选项。

一条合格的策略发布至少要有四个版本化对象：允许谁使用、允许处理什么数据、请求可以经过哪些路径、出现异常时如何降级。只有当这四项都能被配置、验证和回滚时，“模型可用”才接近“模型可运营”。否则，产品页面上的绿色按钮只是入口，不是治理完成的证明。
