## 通知的难点不止是送达

常见的通知设计把重点放在发送动作：事件发生后，调用接口、投递消息，再确认有没有成功。但只检查这条链路，仍然回答不了几个更关键的问题：用户为什么会收到通知？取消订阅后，哪些动作会让订阅恢复？收件人是否符合当前计划限制？管理界面展示的通知原因，能不能代表全部触发原因？

GitHub 于 2026 年 11 月 24 日公布的 GitHub.com 通知调整，和 Cloudflare 同日公布的 Workers Email Sending 免费计划能力，分别触及这条链路的两端。前者重新划分订阅状态与通知原因，后者把收件资格、发送限制和事件分析明确连接起来。它们不是同一套产品，也不能互相证明对方的行为；但放在一起看，可以得到一个实用的工程结论：通知系统至少要分别治理意图、资格、投递和观测，不能用一个“已发送”状态概括整条链路。

## 订阅是有来源的状态，不是一个布尔值

把用户状态建模成 `subscribed = true/false` 很容易，却会丢失“为什么订阅”的来源。用户可能手动订阅，也可能因为创建内容、评论、被指派、被提及或收到审查请求而进入通知范围。同一个讨论串上，这些来源还可能同时存在。只保存布尔值，系统就难以正确处理其中一个来源消失、另一个来源仍然有效的情况。

GitHub 公布的调整体现了这种区分：用户手动取消订阅后，普通参与动作不再自动让其重新订阅；被提及、被指派或收到拉取请求审查请求，仍会使其重新订阅。团队提及也与当前成员关系相连：移除提及或离开团队后，未来基于该团队提及的通知会停止；后来加入团队，则可收到该线程未来的活动。与此同时，如果评论、被指派等其他原因仍然成立，移除提及不会抹去这些独立来源带来的通知。

可借鉴的建模方式，是把来源作为状态的一部分，而不是把所有触发压成单一开关。例如，一个通知对象可以分别记录手动订阅、作者关系、评论参与、指派、提及和审查请求等来源。取消其中一种来源，只更新对应关系；重新订阅也应由明确的用户操作或明确要求关注的事件触发。这里是从已公布行为推导出的工程模型，并不表示 GitHub 公布了内部数据结构。

## 展示原因也需要确定性规则

当多个原因同时成立时，界面究竟显示哪一个？如果每次都展示最近发生的活动，通知原因会随着后续操作来回变化；自动化规则若依赖这个字段，也可能因此改变判断结果。

GitHub 表示，收件箱和邮件页脚展示的原因会按固定优先级决定，而不是简单选择最近活动。一般顺序为提及、团队提及、指派、请求审查、评论、手动订阅、作者、状态变化和已订阅；Issue 的指派优先级最高。邮件头则会包含所有适用的通知原因。由此要区分两个概念：一个是用户看到的主要原因，另一个是完整的原因集合。前者适合压缩呈现，后者更适合解释和自动化。

接入通知筛选或自动化时，可以先把依赖字段的地方列出来，检查规则究竟需要主要原因，还是需要完整的原因集合。若只读取展示用的主原因，不要把它误当成所有触发关系的清单。规则设计还应明确：原因优先级改变时，是要改变通知分流，还是只改变界面文案？这两种需求不应隐式绑定。

另一个容易忽视的界面边界是管理入口。GitHub 表示，Subscriptions 页面将只列出用户明确手动订阅的线程；作者、评论者、被指派、被提及或被要求审查而收到的通知，需要到通知收件箱管理，也可以在那里批量取消订阅。因此，页面上“看不到订阅”不能直接推出“不会收到通知”。产品文案和支持流程都应区分手动订阅列表与所有通知来源。

## 收件资格是发送链路的一道门

Cloudflare 的公告给出了另一类常见边界：Workers Free 计划可以向账户中已验证的目的地址发送邮件；面向任意收件人的发送需要升级到 Workers Paid。已验证收件人的发送在各计划中免费，也不计入月度配额或每日发送限制。换句话说，发送接口可用，不代表每个目标都具备发送资格。

公告示例展示了在发送时识别 `E_RECIPIENT_PLAN_RESTRICTED` 并返回 403 的做法。下面的片段保留这个处理逻辑，但把发件人和收件人留作运行环境中的配置值，避免把真实联系方式写进代码：

```js
export default {
  async fetch(request, env) {
    try {
      await env.EMAIL.send({
        from: env.SENDER_ADDRESS,
        to: env.VERIFIED_DESTINATION,
        subject: "Notification test",
        text: "This is a test notification."
      });
    } catch (error) {
      if (error.code === "E_RECIPIENT_PLAN_RESTRICTED") {
        return new Response("Recipient is not verified for this plan", {
          status: 403
        });
      }
      throw error;
    }
    return new Response("Notification accepted");
  }
};
```

这段处理只对明确的收件人计划限制做出响应，其他错误继续抛出，避免把网络故障或服务异常伪装成权限限制。实际项目还需要按其使用的 Workers binding、REST API 或 SMTP 接入方式配置发送能力；公告没有给出完整项目配置，因此不能仅凭这段示例推定具体部署命令或配置文件格式。

## 让验证覆盖状态、限制与观测

可以用以下检查清单验收通知行为，而不是只确认接口返回成功：

1. **订阅来源**：手动取消订阅后，再评论或改变线程状态，检查是否仍保持取消；分别验证被提及、被指派和收到审查请求的行为。
2. **来源独立性**：同时具备提及和评论等多个来源时，移除提及后，检查其他仍成立的来源是否继续产生通知。
3. **团队成员关系**：覆盖离开团队、移除团队提及和后来加入团队的情况，确认未来活动与既有通知不会被混为一谈。
4. **原因展示**：在多个原因并存时检查主原因排序；再检查邮件头是否保留全部适用原因。Issue 的指派应单独验证其优先级。
5. **管理入口**：比较手动订阅列表和通知收件箱，确认用户知道在哪里管理主动订阅，以及在哪里批量取消其他来源的通知。
6. **收件资格**：使用已验证目的地址和不符合当前计划限制的目的地址分别测试；对计划限制确认返回明确错误，其他错误应继续暴露，而不是成功返回。
7. **分析归属**：在 Cloudflare 中核对已验证收件人的发送是否出现在 Email Sending 活动日志和分析中，并检查事件订阅与 GraphQL 分析所需的 `isVerifiedRecipient` 字段。

Cloudflare 还说明，这类已验证目的地址的消息会计入 Email Sending 流量，不再出现在 Email Routing 分析中；相关发送事件可通过事件订阅观察。若团队仍从旧的分析位置寻找记录，就可能把“没有看到”误判成“没有发送”。因此验证应同时检查发送结果、事件流和分析数据集，而不是只看请求响应。

## 灰度期与失败边界

GitHub 通知调整计划从 2026 年 12 月 1 日开始，在一周内逐步迁移；迁移期间，不同用户可能看到不同表现，而且这项调整不适用于 GitHub Enterprise Server。因而，在迁移窗口内观察到行为差异时，首先应确认产品范围和迁移状态，不宜马上把单个账户的现象推广为全量规则。自动化若依赖通知原因，也需要按新优先级检查规则，而不能假定旧值含义不变。

Cloudflare 一侧则有另一种边界：开发与测试可以免费发送到已验证目的地址，不等于生产环境面向任意收件人的发送也免费开放。免费能力适合验证模板、接收测试通知和团队内部场景；若业务目标是任意收件人，公告明确要求升级到 Workers Paid。不能把测试环境中成功的投递结果当作生产资格证明。

## 工程结论：把通知拆成可解释的决策

通知系统的可靠性，不只是“消息到了没有”，还包括系统能否解释为什么发送、为什么没发送、由哪个来源决定展示原因，以及结果会出现在哪个分析面板。GitHub 的调整说明订阅来源和原因优先级会影响用户预期及自动化；Cloudflare 的能力说明收件资格会影响请求结果，而产品迁移还可能改变流量归属和分析位置。

对工程团队而言，最稳妥的抽象不是一个发送函数，而是一组可分别验证的决策：事件是否产生通知意图、该意图是否仍有效、目标是否有资格接收、哪个原因应该展示、投递与结果应从哪里观测。把这几步拆开，才能在规则变化、计划限制或分析迁移时定位问题；否则，一条看似成功的发送记录，可能掩盖订阅状态错误、资格拒绝或观测入口变化。
