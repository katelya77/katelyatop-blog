## 从一条 Release 标题开始

llama.cpp 的 b12629 Release 只用一句话宣布了一个具体变化：为 Adreno 850 增加基于 coopmat 的 GEMM 支持，涉及的量化格式包括 Q4_0、Q5_0、Q8_0、Q4_K、Q5_K 等。

这是一条足够具体的代码变更线索，却不足以直接得出“手机端推理已经全面加速”的结论。Release 标题说明的是一个后端实现分支的存在，不能自动替代设备兼容性、模型覆盖、运行时行为、吞吐量和稳定性的验收。尤其是移动端推理同时受到显存带宽、OpenCL 驱动、调度策略、上下文长度、预填充与解码阶段的影响，一个内核变快未必意味着整个请求链路变快。

因此，合适的阅读方式不是把这条标题当作性能公告，而是把它当作一个待验证假设：llama.cpp 在特定设备与特定量化格式下，可以选择一条新的 coopmat GEMM 路径；只有形成可重复的对照数据，才能判断这条假设是否成立。

本文不会把代码支持等同于通用加速，也不会把一次 benchmark 结果外推到所有机型和模型。它将这一变化拆成可核验的问题：tag 是否正确、提交是否包含预期修改、当前设备是否实际走入新内核、该内核是否改善目标指标，以及失败或异常时应如何回退。

## 什么是这次变更的结构

GEMM 是模型推理中广泛存在的矩阵乘法。量化权重和激活张量经过计算后，生成用于下一层或下一阶段的结果。在 llama.cpp 等推理实现中，同一种量化格式可能有不同的算子实现；设备可选的后端和指令集也决定了实际执行哪个版本。

coopmat 可以理解为面向协作矩阵运算的专用抽象。它的价值是让计算能表达为设备更擅长执行的矩阵块操作，而不是仅依赖更通用的逐元素或标量式分解。但它是否能带来收益，取决于具体硬件是否提供相应能力、驱动是否正确暴露该能力、矩阵形状是否适合分块，以及数据搬运和同步是否抵消计算收益。

b12629 的标题同时列出了多个量化格式。这意味着它强调的是一组格式与设备组合，而不是所有模型权重自动获得相同提升。Q4_0、Q5_0、Q8_0 和 K 系列格式的块结构、精度与访存模式并不相同；相同的 GEMM 内核不一定适用于相同形状；内核是否真正支持某种格式，还应从构建产物、运行日志和源码分支共同确认。

因此，合理的架构理解应是：

1. llama.cpp 根据设备和量化格式选择后端与算子。
2. 新版本为 Adreno 850 增加了一条 coopmat GEMM 选择。
3. 实际运行时，OpenCL 驱动、设备能力和矩阵形状共同决定是否进入该路径。
4. 内核通过后，仍需通过端到端指标判断是否形成工程收益。

这里的关键不是“支持”一词，而是“选择”一词。选择发生于运行时，验收必须观察选择结果，而不能只观察编译成功。

## Release 证据与可复现的版本检查

b12629 是带有发布标签的官方 llama.cpp Release。材料中已经明确标识了 commit `1fb8a26`，并显示该 tag 对应一个已验证的签名提交。它不只是一段社区转发，也不应由社区帖中描述的效果替代。

可以先确认本地 Git 仓库是否拿到了准确 tag：

```bash
git fetch --tags --force
git rev-parse b12629
git rev-parse b12629^{commit}
git ls-remote --tags origin refs/tags/b12629
```

第一个命令应为维护者目标仓库的标签解析。最后一个命令可验证上游 tag 与本地 tag 是否指向相同提交。若本地存在同名标签，或者克隆源不是官方仓库，这一步就可能暴露错源问题。

随后检查源码中是否存在对应实现线索：

```bash
git checkout --detach b12629
git grep -n -E 'Adreno|coopmat|Q4_0|Q5_0|Q8_0|Q4_K|Q5_K' -- \
  | sed -n '1,120p'
```

这不是证明端到端性能的测试，而是证明：目标提交确实包含相关符号或实现分支；构建产物是否意外丢失该路径；本地复制是否与发布 tag 一致。

如果仓库中没有对应关键字，不应直接认定版本不支持。可能是实现拆分在生成代码、宏展开、分支或构建脚本中。此时应继续阅读 tag 对应提交的变更，而不是只凭单次 grep 下结论：

```bash
git show --stat --oneline --decorate b12629
git diff b12629^ b12629 --stat
git diff b12629^ b12629 -- '*.c' '*.cpp' '*.h' '*.cl' '*.cmake' 'CMakeLists.txt'
```

最重要的是保存输出，至少记录：仓库远程地址、tag、commit、构建时间、设备型号、驱动版本和本地修改状态。没有这些字段，所谓“在某台手机上快了”就无法成为可复现结论。

## 编译前先做的检查清单

移动端复现最容易遗漏的变量，是构建配置和运行环境。即使使用相同源码，不同构建选项也可能生成完全不同的 OpenCL 后端。

建议按以下清单准备：

- 固定官方仓库、官方 tag 和完整 commit。
- 确认目标芯片确实是 Adreno 850，而不是以同品牌 GPU 名称代表近似产品。
- 记录 Android 系统版本、OpenCL 驱动版本、内核版本和设备温度状态。
- 确认 b12629 构建产物确实启用 OpenCL 后端。
- 检查构建目录中是否残留旧配置。CMake 构建应使用干净目录。
- 固定模型文件、模型大小、量化格式、上下文长度和线程数。
- 固定提示词长度、生成长度、批处理参数和采样参数。
- 暂时关闭或记录省电模式、后台负载和设备温控策略。
- 保存基准版本和目标版本的完整日志与配置。

构建配置的原则是先确保可用，再追求性能。一个最小但可审计的流程可以是：

```bash
rm -rf build-b12629
cmake -S . -B build-b12629 -DCMAKE_BUILD_TYPE=Release
git status --porcelain
cmake --build build-b12629 --parallel
```

这里故意未假设目标平台一定会通过某个固定选项启用 OpenCL。移动端、桌面端和交叉编译的 CMake 参数可能不同。应以本地源码的 CMake 帮助和目标平台文档确认后端开关，然后记录最终 CMake 缓存：

```bash
cmake -LA -N build-b12629 | sed -n '1,200p'
```

构建成功只能证明产物可编译，不能证明该产物包含或激活 coopmat GEMM。下一步必须验证设备能力和运行时选择。

## 对照测试要回答什么

一项合格的验收至少应区分三个指标：

- 预填充吞吐量：处理固定提示词所需时间或每秒 token 数。
- 解码吞吐量：生成固定数量 token 的速度。
- 稳定性与异常：错误率、崩溃率、超时、热切换和退化情况。

预填充与解码不应混为“推理速度”。很多优化主要改善解码阶段的矩阵乘法，也可能改变批处理行为；如果只记录一次端到端秒数，无法说明具体瓶颈。

建议至少建立基线版本和目标版本的配对：

```text
硬件：Adreno 850，同一台设备
系统：相同，未重启或重启后保持一致
驱动：相同版本
模型：相同文件和校验值
量化：逐格式对比，不混合结果
上下文：相同长度
提示词：相同 token 序列
生成长度：相同
预热：固定轮数并记录预热外的测试轮次
重复：至少多轮，每轮收集原始数据
```

每轮应保存原始日志，而不是只保存平均值。由于移动设备存在温控，平均值可能掩盖首轮极快、后续变慢或触发降频的情况。更好的做法是记录每轮耗时、设备温度变化、能耗或功耗代理指标，并对相邻轮次做对比。

测试时还应分别覆盖：

- 新格式和旧格式。
- 短上下文与长上下文。
- 小批量与目标实际批量。
- 单次生成与连续请求。
- 低负载与正常后台负载。

只有同时出现“路径被使用”和“指标改善”，才能建立从实现到收益的证据链。只有指标改善而没有确认路径被使用，可能只是设备状态或测试噪声；只有路径被使用而指标没有改善，则只能说明兼容分支存在，不能证明用户体验提升。

## 一个实用的验收脚本框架

下面不是固定版本的完整命令，而是对原始结果进行收集的框架。具体 benchmark 可执行文件和参数应以本地构建产物的帮助信息为准：

```bash
set -eu

BIN=./build-b12629/bin/llama-bench
MODEL=/absolute/path/to/model.gguf

"$BIN" --help > run-help.txt
sha256sum "$MODEL" > model.sha256

for format in Q4_0 Q5_0 Q8_0 Q4_K Q5_K; do
  : # 仅当对应模型实际存在时替换为该模型的执行参数
  echo "testing $format"
done
```

占位脚本刻意提醒：不能把格式名直接当作可运行模型文件名。只有使用真实存在的目标量化模型时，才会形成有效对照。正式脚本应包含：固定模型路径、固定工作负载、预热轮数、正式轮数、每轮时间戳、版本信息和退出状态。

可为每轮生成唯一目录：

```bash
mkdir -p results/b12629/$(date -u +%Y%m%dT%H%M%SZ)
cp -f model.sha256 results/b12629/*/ 2>/dev/null || true
```

不过设备上通常不应依赖当前 shell 的绝对路径和 UTC 时间直接做产品配置；这里的价值是确保数据不会被覆盖。更可靠的方案是在 CI 或有线测试中固定输出目录，再自动附加设备与驱动信息。

验收输出至少包括：

- 目标量化格式。
- 基线版本与 b12629 版本。
- 预填充结果和解码结果的原始值。
- 每轮失败原因。
- 有效运行轮数与剔除轮数。
- 剔除规则，不能事后随意删除异常值。
- 是否确认进入 coopmat 路径。
- 是否存在崩溃、计算差异或超时。

验证数量时，应同时看中位数、最差情况和尾部抖动。只看平均值容易把偶发降频结果算成稳定收益。

## 回归判断的止损线

一次性能测试不能只问“是否变快”，还要问“可接受的失败边界是什么”。对于移动端推理，建议预先定义以下停止条件：

- 目标格式结果没有覆盖到：不能宣布格式支持已验证。
- 特定提示词或上下文长度下路径被绕过：结论限定在该工作负载。
- 同一配置的重复结果高度分散：暂不采用，继续检查温控和负载。
- 输出校验失败或数值差异超出既定容差：不得上线该内核路径。
- 崩溃、超时或设备重置：立即禁用该组合并保留日志。
- 端到端延迟不改善，但某一算子微基准改善：结论只针对算子，不能推广。
- 电量消耗明显增加：即使速度提升，也需纳入工程取舍。

回退条件应在测试前定义，而不是在失败后临时设置。例如，若目标版本在解码吞吐量提高不足、稳定性下降或电量消耗上升，就继续使用上一版本。回退不需要删除构建产物，只需让运行时配置明确选择已验证的后端；同时保留新版本用于后续特定工作负载的测试。

此外，不应把单次 benchmark 的失败视为所有设备都失败，也不应把一次成功外推为平台普遍可用。结论应写成：“在 Adreno 850、相同模型、相同量化和驱动下，某个工作负载得到相应结果”，而不是“Adreno 850 都会加速”。

## 工程取舍：支持矩阵不能替代性能承诺

这次 Release 的工程价值在于扩展了实现层的选择空间，而不在于直接承诺用户体验。它让维护者可以测试一条新的量化 GEMM 路径，也让硬件和量化格式的组合逐渐具备可观测性。

产品方则需要区分三个层级：

第一层是编译与源码支持：版本包含新实现，构建产物可用。

第二层是运行时可达性：目标设备加载该后端，目标格式进入 coopmat 路径，且没有触发回退。

第三层是端到端收益：吞吐量、延迟、稳定性、功耗和输出一致性达到预设标准。

前两层可以由工程日志证实，第三层必须由实际工作负载证实。即便前两层通过，也不能自动证明第三层通过。相反，如果第三层通过，仍应保留长期测试，防止驱动更新、温控策略或其他运行时变化使收益消失。

## 最终结论

llama.cpp b12629 为 Adreno 850 增加了多种量化格式的 coopmat GEMM 路径。它是一个明确的源码与发布变更，不是传闻，也不是官方宣称的全局性能提升。证据等级应定为“官方 Release 明示代码变化”，而不是“官方验证了具体吞吐量和功耗”。

最需要避免的是把一条 Release 标题转换成强性能承诺。合适的结论是：新版本提供了一个值得验证的设备—量化—算子组合，是否实际可用取决于构建、运行时和工作负载。只有固定版本、固定设备、固定模型、固定参数并保存原始日志，才能判断它是否值得进入生产。

这类移动端优化最可靠的评估方式，不是一次 benchmark，而是一条完整证据链：tag 与 commit 一致、源码实现可定位、目标后端被运行时选中、特定格式和工作负载通过对照、回归指标没有恶化、失败组合能够明确回退。缺少其中任何一环，都只能称为“可能支持”，不能称为“已经加速”。
