## 搜索入口不是答案接口

网站内容对人可见，不代表自动化 Agent 知道该从哪里找。传统集成往往要求调用方先知道站点用什么搜索产品、如何鉴权、请求参数是什么，再把这些约定写进工具或提示词。站点一旦更换搜索实现，Agent 侧的配置也可能需要跟着调整。这里真正需要解决的，不只是“能不能搜”，还包括入口如何被发现、结果如何交给后续推理。

Cloudflare 在 2026 年 11 月 25 日的官方变更日志中介绍了 Search for Agents：在域名 Overview 页的 Quick Actions 中启用后，Cloudflare 会创建一个 AI Search 实例、开始索引内容，并在该域名下提供搜索端点。端点路径为 `/.well-known/search`。官方示例使用 `q` 参数提交自然语言问题，端点返回相关内容的 Markdown，而不是 AI 生成的答案。

这几个环节值得分开看：页面或 Markdown 响应中的发现元数据负责告诉 Agent 搜索入口在哪里；搜索端点负责返回相关内容；Agent 自己的模型再负责综合材料、生成回答。搜索服务与答案生成分离，意味着搜索结果可以作为可检查的证据材料，而不是把检索和生成混成一个无法区分的黑箱。反过来说，端点返回了内容，不等于内容一定完整、正确，也不等于 Agent 最终回答就可靠。

## 从页面发现到 Markdown 检索

官方说明提到，Search for Agents 会向 HTML 页面添加发现元数据；如果启用了 Markdown for Agents，也会把元数据加入 Markdown 响应。Agent 可以据此发现端点，再使用关键词或自然语言查询。这个设计让接入路径从“为每个 Agent 手动配置搜索集成”转向“站点发布可发现的搜索能力”。

它不是把整站内容直接塞进提示词，也不是要求每个 Agent 各自爬一遍页面。根据官方描述，启用过程会创建 AI Search 实例并开始索引站点内容，查询时由域名端点返回相关 Markdown。工程上可以把它理解为一种站点侧的内容检索入口：网站控制内容与搜索实例，Agent 通过标准化位置发起查询，再决定如何使用结果。这是对公开流程的架构归纳；具体索引管线、排名算法、更新时延和结果格式细节，材料没有给出，不应据此推断。

可发现性也不意味着调用方无需验证。页面元数据是否出现在预期响应中、Markdown for Agents 是否开启、Agent 是否遵循发现信息，都会影响实际链路。即使发现成功，查询结果仍取决于被索引的内容以及搜索系统对相关性的判断。不要把“网站有一个 well-known 路径”泛化成任何 Agent 都会自动调用；不同客户端如何读取元数据，仍是接入侧需要确认的部分。

## 用一个查询建立最小验收

官方变更日志给出的 GET 调用形式可以直接作为连通性检查。把 `example.com` 换成已启用功能的域名：

```bash
curl --get 'https://example.com/.well-known/search' \
  --data-urlencode 'q=How do I verify webhook signatures?'
```

`--get` 会把参数放入 URL 查询串，`--data-urlencode` 则负责编码问题中的空格等字符。示例使用英文问题；若站点内容主要是中文，验收时应另外使用中文关键词和自然语言问题，观察返回内容是否与预期页面相关。官方说明端点支持 GET 和 HTTP QUERY；上述命令只演示文档明确展示的 GET，不猜测 QUERY 方法的请求体或客户端兼容方式。

一次请求成功只能证明最基本的路径可用。可以按以下顺序分层检查：

1. **入口检查**：在启用功能的域名上请求 well-known 路径，记录响应状态、响应头和响应正文。若失败，先确认域名、功能启用状态及请求 URL，而不是先改 Agent 的提示词。
2. **内容检查**：用站点中确实存在的标题、术语或问题查询，确认返回 Markdown 是否包含相关内容。再用一个不应命中的问题作对照，检查是否出现明显无关材料。不要仅凭“有正文”判定检索质量。
3. **发现检查**：分别查看代表性的 HTML 页面，以及启用了 Markdown for Agents 时的 Markdown 响应，确认实际响应中是否出现发现元数据。官方材料没有规定元数据的具体格式，因此应以真实响应和对应文档为准，不要预设标签名称或解析规则。
4. **Agent 检查**：在目标 Agent 上观察它是否识别站点提供的入口、是否确实发起查询，以及回答能否回溯到返回内容。搜索端点返回 Markdown，不代表 Agent 自动引用或正确理解这些内容。

涉及生产验收时，最好保存查询词、请求时间、响应状态和返回正文的样例，并选取几类页面做重复检查。这样可以区分“端点暂时不可用”“没有发现入口”“索引内容不符合预期”和“Agent 没有使用结果”等不同问题，而不是把所有失败都归为搜索质量。

## 结果边界比端点路径更重要

官方变更日志称该功能适用于所有计划，但使用仍受 AI Search 定价和计划限制约束；创建的 AI Search 实例也可以调整可配置设置。因而“所有计划可用”不能解读为“无限量免费”，也不能推导出具体配额、价格或索引上限。上线前应查看当前账户对应的 AI Search 价格和计划限制，并核对新建实例的设置。

同样，现有材料没有说明索引覆盖率、内容刷新周期、语言支持边界、每次查询的结果数量、排序规则、缓存、鉴权或限流行为。对这些问题，正确做法是通过当前产品文档、控制台配置和实际响应确认，而不是把常见搜索系统的默认行为当作 Cloudflare 的承诺。若站点包含不希望被公开检索的页面，还应先确认索引范围与站点访问策略；不能仅凭“搜索由 Agent 使用”就假设内容访问控制会自动满足业务要求。

对内容发布者而言，检索入口提高了内容被 Agent 找到的机会，但也使内容质量问题更容易沿着自动化链路传播。标题含糊、版本信息缺失、过期操作步骤与新内容并列，都会让“相关结果”不等于“适合回答”。因此，应把文档维护、明确的适用版本和可验证步骤纳入搜索验收，而不是只关注请求是否返回 200。这里是通用工程建议，不是对该产品内部索引机制的描述。

## 取舍：集中接入，分开验收

Search for Agents 的价值在于降低站点搜索能力的发现成本：站点侧提供可发现入口，Agent 侧不必为每个站点预先硬编码同一套搜索集成；Markdown 结果则让后续模型可以继续处理内容。它适合希望把公开网站内容暴露为 Agent 可检索材料的场景。若业务需要细粒度授权、稳定的结果契约、专用过滤条件或严格的版本快照，仅凭这份功能介绍不足以确认它能满足要求，应先做针对性验证，必要时保留自有搜索 API。

落地时最重要的不是把 well-known 路径加入配置清单，而是分别证明三件事：Agent 能找到入口，查询能返回预期内容，Agent 最终回答能依据这些内容。第一项是发现，第二项是检索，第三项是应用；任何一项失败，都会让整条链路看起来“接上了”却没有实际价值。

因此，评估这类能力可以从最小闭环开始：启用后用 curl 验证端点；检查 HTML 与可选 Markdown 响应中的发现信息；用真实问题和负向对照评估结果；最后观察目标 Agent 是否使用返回内容。这个顺序能把平台提供的能力与调用方的行为分开，也能避免把“支持 Agent 搜索”误读成“Agent 已经可靠地理解了整个网站”。
