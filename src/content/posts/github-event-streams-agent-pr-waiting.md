## 一、为什么 PR 等待问题值得重新设计

很多自动化流程并不是在提交 Pull Request 后立刻结束，而是要等待审查完成、检查套件结束、分支状态变化或合并冲突消失。常见实现会把这部分需求写成循环：调用一次 GitHub API，休眠一段时间，再调用一次；直到成功、超时或达到最大重试次数。

这种模式看起来简单，却把两个不同问题混在了一起：一个是“在外部状态发生变化时通知调用方”，另一个是“调用方反复主动读取外部状态”。前者适合事件流，后者才是轮询。

轮询至少有四个成本：不必要的请求、固定间隔带来的平均等待延迟、脚本对限额或速率限制的敏感性，以及无法区分“暂时没有变化”和“请求已经失败”。当循环还被包进 AI Agent 时，这些问题会进一步放大。Agent 可能把“没有收到状态”理解为任务失败，也可能把可恢复错误重复解释为需要继续执行；每一次错误分支都可能生成新的工具调用和令牌成本。

GitHub 在 2026 年 11 月 18 日宣布：`gh` v2.105.0 支持 GitHub Event Streams。`gh event listen` 可以订阅一个 Pull Request，并把审查提交、PR 状态、Head 变化、合并冲突和检查套件完成等事件作为 JSON 行输出。这不是对轮询循环的语法糖，而是把等待语义提升为一等操作。

当前证据等级是公开预览。GitHub 明确说明该能力正在预览，功能可能变化；Event Streams 本身也处于预览阶段，需要加入 waitlist 获得访问权限。因此，本文讨论的是可验证的公开能力与边界，不把其描述为已经普遍开放的稳定服务。

## 二、事件流的核心抽象

### 从主动读取到被动接收

`gh event listen` 的基本模型是建立订阅、打开事件流、逐行打印事件。默认情况下只等待第一个事件，适合脚本和短生命周期 Agent 循环。它还提供 `--count` 等待多个事件，`--follow` 持续监听，以及 `--timeout` 限制等待时间。

因此，最小心智模型可以写成：

1. 选定一个稳定的 Pull Request URL。
2. 明确本次要等待多少个目标事件。
3. 建立订阅并保持一个有边界的监听过程。
4. 收到 JSON 行后解析字段并决定下一步。
5. 超时、网络中断或订阅失效时走失败分支。

这个模型中的关键不是“第一个事件一定代表任务成功”。审查提交、Head 变化、合并冲突和检查套件完成是不同语义。比如，一个检查套件完成可能是成功，也可能是失败；审查提交可能是批准、请求修改或评论。必须读取事件中的具体字段，再进入后续判断，不应把所有事件等同于通过。

### 生命周期仍然需要显式管理

公开材料提到可以通过以下命令直接管理订阅：

```text
gh event subscription create
gh event subscription list
gh event subscription view
gh event subscription delete
```

这里的设计意味着监听并不一定等于一次性脚本的一部分。订阅可能需要审计、清理和生命周期管理。若长时间运行的 Agent 被终止，订阅是否会继续存在、何时自动失效以及服务端是否保留错过的事件，都必须以正式文档和实际环境为准。现有材料没有提供这些细节，不能在本文中补写成事实。

一个稳妥的工程原则是：只把事件流当作状态变化通知源，不把订阅本身当作任务的事实存储。任务结果仍应由 Pull Request、提交状态、检查套件和审查记录等业务对象重新确认。

## 三、可复现的最小检查流程

下面的流程不假设已经获得 Event Streams 权限；它用于在升级后确认 CLI、帮助入口、登录状态和监听行为。

### 升级并确认版本

```bash
gh --version
gh extension list
gh event --help
```

至少确认使用的 `gh` 为 v2.105.0 或更高版本。仅看到二进制版本高于要求并不能证明已获得服务端访问权；下一步应确认命令是否能真正建立订阅。

### 创建一次有边界的监听

```bash
PR_URL="https://github.com/OWNER/REPO/pull/123"

gh event listen "$PR_URL" \
  --count 1 \
  --timeout 10m
```

这里使用公开材料明确提到的参数：等待第一个或多个事件、限制超时，以及输出 JSON 行。实际的超时时长单位应以本机 `gh event listen --help` 为准，不能仅凭本文示例推断其他版本支持相同格式。

若只需要筛选字段，可以尝试使用官方参数入口：

```bash
gh event listen "$PR_URL" --count 1 --timeout 10m --jq '.'
```

`--jq` 只有在本地实际可用时才应加入流水线。表达式应基于监听到的真实 JSON 字段编写，而不是基于猜测中的字段名。模板输出同理：先做一次未筛选监听观察结构，再决定是否固定化字段。

### 管理和清理订阅

```bash
gh event subscription list
gh event subscription view
gh event subscription delete
```

具体参数应从本机帮助文本读取。验证清理时应记录清理前后列表差异，并确认目标订阅确实不再出现在列表中。不要只检查命令是否返回零退出码；命令成功不等于订阅已按预期删除。

## 四、把监听接入 Agent 循环

GitHub CLI 的公开命令已经直接面向 Agent 场景：`gh pr create`、`gh pr view`、`gh run view`、`gh run watch` 和 `gh api` 会建议在适用处改用 `gh event listen`，而不是继续轮询。

这带来一个可设计的 Agent 工作流：

```text
创建或发现 PR
  -> 输出目标 URL 和期望结果
  -> 调用 gh event listen
  -> 解析单行或多个事件
  -> 查询 PR、审查或检查详情
  -> 人工/自动规则判定成功或失败
  -> 超时则保留证据并退出
```

第一个改进是让等待成为显式步骤，而不是把循环藏在工具内部。第二个改进是把“收到事件”与“任务完成”分层。收到审查提交后，仍需确认是否是批准；收到检查套件完成后，仍需确认检查结论；收到 Head 变化后，可能需要重新等待后续检查而不是直接继续合并。

建议 Agent 在下一步执行前保存以下证据：

- 监听起止时间
- 使用的 PR URL
- 命令退出状态
- 收到的事件数量
- 原始或脱敏后的事件 JSON
- 最终确认的审查、状态和检查结果
- 超时或中断时保留的订阅查询结果

脱敏时至少不要把令牌、私有仓库地址和用户敏感字段原样写入日志。公开事件行也可能包含与仓库、提交、用户或组织有关的信息，应按仓库策略决定保留范围。

## 五、失败边界与可观测性

预览能力最大的失败风险，不是参数写错，而是把“无事件”和“执行失败”混为一谈。

### 超时不是事件

`--timeout` 到期时，Agent 不能自动把它解释为目标状态未满足，也不能继续无限循环。超时只表示监听窗口结束。下一次行动可以是重新监听、查询一次权威状态、升级人工处理，或者直接结束任务并报告等待未完成。

为了区分状态，应至少建立四类结果：

- 目标事件已收到，并经权威对象确认
- 收到了无关事件，需要继续监听
- 超时或监听窗口结束，状态未知或未满足
- 命令、权限、订阅或网络错误，需要人工或自动恢复

混合这些状态会使自动化无法解释失败。尤其是无关事件，命令可能已经收到数据，却不代表任务完成；它只表示状态发生了变化。

### 权限和可用性不是同一件事

即使二进制支持 `gh event`，不同账号、组织或仓库仍可能没有 Event Streams 权限。公开材料明确要求加入 waitlist，因此在 CI 环境中不能把访问作为默认假设。

应当在运行前做能力检查：

```bash
gh event --help >/dev/null 2>&1
gh event subscription list
```

第一个命令确认本地版本是否暴露事件命令，第二个命令能发现本地凭据和服务端访问是否可建立有效订阅。只有两个检查都成功，才能进入监听流程。即使它们失败，也应保留两者的退出状态，不要用同一个错误文案覆盖所有原因。

### Hook 失败不应默认为继续成功

Claude Code v2.1.328 的 Release Notes 提供了一个与 Agent 控制面相邻的示例：`onFailure: "block"` 可以让 MCP 工具 Hook 在失败时阻止后续动作。这个信息说明运行 Agent 时需要区分“Hook 未执行”和“Hook 执行后失败”。但它不能证明 Claude Code 已经与 GitHub Event Streams 联动，也不能证明所有工具和 Hook 都使用相同语义。

原始材料适合建立以下设计规则：对 PR 监听而言，若确认或清理订阅失败，就应阻止可能造成副作用的合并和发布动作；而单纯超时不应被误写成合并成功。

## 六、工程取舍：何时仍应轮询

事件流并不自动优于轮询。以下场景可能更适合保留轮询或一次性查询：

- 只需要一个精确快照，不需要等待变化。
- 平台尚未开放 Event Streams，但任务又需要短期兼容性。
- 每个任务只执行一次状态查询，不值得建立订阅生命周期。
- 查询对象、权限或网络环境不稳定，订阅失败概率高于轮询失败概率。
- 必须保留一个明确的最终状态快照，而不是依赖流式通知。

反过来，以下场景更适合事件等待：

- 同一个 Agent 会长时间等待审查或检查。
- 固定频率轮询会产生明显重复请求。
- 状态变化发生后需要尽快触发下一步。
- 流程能清楚区分目标事件、无关事件和失败事件。

一次可维护的迁移也不必从第一天就删除所有轮询。更稳健的方式是保留轮询作为降级读取，不把降级读取伪装成事件流：事件监听负责等待，权威状态查询负责确认，轮询只负责兼容和兜底。

## 七、验收清单

上线或纳入正式脚本前，至少应逐项确认：

- 本机 `gh` 是否为 v2.105.0 或更高版本。
- `gh event --help` 是否可用。
- Event Streams 和目标仓库是否具有可用访问权限。
- 监听目标是否是预期的 Pull Request URL。
- 是否明确使用 `--count` 或 `--follow`。
- `--timeout` 是否有覆盖短超时、正常完成和无事件三种场景。
- 是否区分审查提交、Head 变化、合并冲突和检查套件完成。
- 收到事件后是否再次查询权威对象确认最终状态。
- 订阅是否能被列出、查看和删除。
- 失败时是否阻止合并、发布等不可逆动作。
- 日志是否避免写入令牌、敏感字段和过量私有信息。
- 预览能力不可用时是否存在不产生误报的降级路径。

## 原创结论

GitHub Event Streams 的真正价值不在于它省略了一个 `sleep` 调用，而在于把 Agent 循环从固定频率探测改成了有生命周期、有事件语义、有超时边界的等待模型。

但事件流提供的是通知，不是结论。工程上必须保留两个阶段：先等待可信事件，再用 Pull Request、审查和检查状态做权威确认。只要这个分层建立起来，事件流才能减少轮询成本；如果把“收到任何一条 JSON”直接当成成功，它只会把轮询中的误报换成更隐蔽的自动化误判。

由于该能力和相关服务目前仍是公开预览，不应把命令兼容性、订阅持久性或组织可用性写成通用承诺。最可靠的结论是：先在受控仓库中验证版本、权限、事件语义和清理能力，再决定是否把它纳入生产 Agent 的默认等待机制。
