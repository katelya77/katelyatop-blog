## 先把“模型名”从代码里拿出来

很多 AI 应用把模型名称直接写在业务代码中：请求体里的 `model` 指向某个具体模型，部署配置里再补充 API 地址、密钥和超时。这样做在单一供应商、单一模型、低变更频率的阶段很直观，但它把一个本应属于基础设施的决策，固化成了应用版本的一部分。

Cloudflare AI Gateway 在 2026 年 11 月 4 日的更新中引入了 model aliases。别名不是模型的新名字，而是一个由网关维护的模型池入口。应用只调用一个名称，例如 `custom/support-fast`；网关可以按照预先设置的顺序尝试多个模型，也可以使用智能路由为每次请求选择模型。应用侧不需要因为后端模型替换或路由算法变化而重新部署。

这个变化的核心不是“少写几个字符”，而是把模型选择从数据面请求中抽离出来，放进一个可以单独变更的控制面。应用关心的是服务契约，网关关心的是候选模型、顺序、故障转移与路由策略。两者之间通过别名建立稳定边界。

不过，别名只改变决策位置，并不会自动解决所有模型接入问题。模型协议、输入格式、上下文限制、工具调用能力、输出结构和计费方式仍然可能不同。因此，别名更准确的定位是“路由抽象”，而不是“兼容性抽象”。

## 别名背后的两条路由路径

从行为上看，模型别名至少包含两种不同的路由模式。

第一种是有序回退。网关按照配置顺序请求模型 A；如果请求失败，再尝试模型 B，依次向后。这适合候选模型具有相近接口和能力的场景，也适合把主模型与备用模型组成一个明确的可用性链路。它的优点是行为容易解释：排在前面的模型承担正常流量，后面的模型只在失败时接管。

但“请求失败”必须被定义清楚。连接失败、超时、服务端错误，通常可以作为回退信号；鉴权失败、请求参数不合法、输入超过上下文上限，则未必适合继续尝试。若所有错误都触发回退，一个配置错误可能被掩盖，最终变成一个看似成功、实际语义不同的响应。材料只确认网关会在请求失败时尝试下一个模型，并未给出所有错误类别的详细判定，因此生产配置不应假设每一种失败都具有相同的回退语义。

第二种是智能路由。网关根据路由算法为每次请求选择模型。它可能适用于在延迟、可用性、能力或成本之间做动态平衡的场景，但动态选择会降低单次请求的可解释性。相同输入不一定命中相同后端，排查问题时不能只记录别名，还必须知道实际选择了哪个模型、为何选择以及是否发生过回退。

因此，顺序回退与智能路由不是简单的“两个开关”。前者更像显式的故障切换链，后者更像策略驱动的选择器。前者优先可预测性，后者优先策略空间。若业务需要稳定输出、严格审计或模型能力高度不对称，应该先从有序回退开始，而不是直接把所有决策交给智能路由。

## 最小调用链：先验证作用域，再验证请求

官方更新给出的 REST API 调用形式是向 `/accounts/{account_id}/ai/run` 发送请求，并把别名放入 `model` 字段，同时通过 `cf-aig-gateway-id` 请求头选择创建了该别名的网关。一个最小化的检查请求可以写成：

```bash
export ACCOUNT_ID='你的账户 ID'
export GATEWAY_ID='已创建别名的网关 ID'
export API_TOKEN='具备相应权限的令牌'

curl --fail-with-body --silent --show-error \\
  "https://api.cloudflare.com/client/v4/accounts/${ACCOUNT_ID}/ai/run" \\
  -H "Authorization: Bearer ${API_TOKEN}" \\
  -H "Content-Type: application/json" \\
  -H "cf-aig-gateway-id: ${GATEWAY_ID}" \\
  --data '{
    "model": "custom/support-fast",
    "input": {
      "messages": [
        {"role": "user", "content": "Reply with a short greeting."}
      ]
    }
  }'
```

这条命令验证的是调用链是否完整，不等于验证了路由策略。至少要分成四步检查。

第一步，确认别名确实创建在目标网关，而不是另一个网关。官方说明别名按单个网关作用域隔离；同一个名称在不同网关中不能被视为同一个全局资源。请求头缺失或指向错误网关时，问题可能表现为别名不存在，而不是模型不可用。

第二步，确认应用请求使用的是别名，而不是某个后端模型名。否则即使请求成功，也没有经过别名控制面，无法证明应用已经脱离具体模型耦合。

第三步，使用一个确定性较高、内容很短的请求做基线。短输入可以减少上下文限制、长响应超时等变量，把问题集中到身份、网关作用域和模型解析。

第四步，保存请求时间、别名、网关标识、HTTP 状态、响应错误字段和请求追踪信息。一次成功响应只能证明路径可用，不能证明候选池中的每个模型都可用，也不能证明发生故障时回退行为符合预期。

## 别名迁移真正改变的是发布流程

没有别名时，切换模型通常需要修改环境变量或代码，重新构建、发布，然后观察新版本是否稳定。使用别名后，应用可以继续提交同一个 `model` 值，网关侧单独调整候选模型或路由算法。这样，模型切换从应用发布流程中分离出来，能够缩短变更路径，也减少业务代码与模型供应商之间的耦合。

但“无需重新部署”不等于“无需发布治理”。别名配置本身仍然是生产变更，应当具备版本记录、审批边界和回滚方案。至少要记录以下内容：别名名称、所属网关、候选模型及顺序、路由模式、变更时间、变更人和验证结果。若平台提供配置历史，应将其纳入审计；若没有，则需要在自己的配置仓库或变更系统中保留等价记录。

一个稳妥的切换流程可以是：先创建新别名或更新候选池，再用固定请求验证；随后对低风险流量观察错误率、延迟和响应结构；确认结果后才扩大使用范围。由于材料没有给出具体的灰度能力、指标字段或告警接口，不能把灰度、自动回滚等能力当作 AI Gateway 别名已经提供的功能。工程上可以在调用方或外围流量层实现这些机制，但必须明确它们属于额外控制层。

还要特别注意别名的可见范围。一个面向客服的别名和一个面向代码生成的别名，即使背后暂时使用同一个模型，也不应该随意合并。别名名称本身应表达业务契约，而不是暴露供应商内部版本，例如 `custom/support-fast` 比 `custom/provider-x-v3` 更适合作为长期接口。前者描述用途，后者把实现细节泄漏到了应用层。

## 回退不是兼容：失败边界要提前写清楚

模型回退最容易被误解成“只要有备用模型，服务就不会坏”。实际上，备用模型可能在多个维度上不兼容。

第一是请求兼容性。不同模型可能接受不同的消息字段、工具参数或多模态内容。主模型能处理的请求，备用模型不一定能处理。若错误发生在请求校验阶段，继续回退可能只是重复提交一个永远无效的请求。

第二是能力兼容性。备用模型可能不支持工具调用、结构化输出、长上下文或特定推理模式。即使它返回 HTTP 成功，业务代码也可能在后续解析时失败。因此，验收不能只检查状态码，还要检查响应是否满足业务契约。

第三是语义兼容性。相同提示词交给不同模型，答案风格、事实可靠性、拒答边界和结构稳定性都可能变化。对聊天场景，这可能只是质量波动；对自动执行、数据抽取或代码修改场景，则可能形成更大的业务风险。

第四是成本兼容性。回退链可能使一次用户操作产生多次上游请求。材料确认网关支持失败后尝试下一个模型，但没有提供计费细节，因此不能推断回退请求一定按某种方式计费。生产系统应从供应商账单、网关日志或调用方计数中核对实际请求次数，而不是只按用户请求数估算成本。

第五是重试边界。一个请求在上游已经被接受、但响应在网络中丢失时，网关是否会把它视为失败并请求下一个模型，可能导致重复处理。对于非幂等工具调用或会产生外部副作用的 Agent 请求，不能只依赖模型别名的回退机制。需要在业务层增加幂等键、工具执行去重或明确的“仅生成、不执行”阶段。

这些边界说明了一个原则：回退只能保证候选路径存在，不能保证候选模型具有相同的业务语义。别名的验收标准应该是“可接受的契约集合”，而不是“任意模型都能返回文本”。

## 一份可执行的验收清单

可以把上线前检查拆成控制面、数据面和故障面三组。

控制面检查：

- 别名是否创建在预期网关，名称是否符合业务用途；
- 应用配置中是否只保留别名，而没有绕过网关直连具体模型；
- 候选模型顺序或智能路由策略是否有明确的变更记录；
- 是否存在回滚到上一组候选模型的操作路径；
- 不同环境是否使用不同网关或明确隔离的别名，避免测试变更影响生产。

数据面检查：

- 正常请求是否把别名放在 `model` 字段；
- 是否携带选择目标网关所需的 `cf-aig-gateway-id`；
- 短输入、长输入、工具调用和错误参数是否分别验证；
- 响应状态码、错误结构、正文格式和业务字段是否都被检查；
- 监控是否能区分别名、实际模型、失败类型与回退次数。

故障面检查：

- 主模型连接失败时，是否确实尝试备用模型；
- 主模型返回业务不可接受的内容时，系统是否有能力识别，而不是把它当作成功；
- 备用模型不支持某种请求时，是否能明确失败；
- 连续回退时，超时是否受到总预算限制；
- 带副作用的请求是否具备幂等与去重保护；
- 网关不可用时，应用是否有明确的降级提示，而不是无限重试。

最后一项尤其重要：要区分“路由成功”和“业务成功”。网关把请求交给某个模型并返回结果，只说明路由链路工作；只有结果通过业务校验，才说明这次调用真正完成。

## 结论：把别名当作策略接口，而不是模型目录

模型别名最有价值的地方，是给应用提供了一个相对稳定的策略接口。应用不再需要知道每次请求应该选择哪个具体模型，基础设施团队也可以在不改业务代码的情况下调整候选池和路由方式。这对快速迭代的模型服务尤其有用。

但别名不会自动提供统一能力、统一成本、统一质量或统一安全边界。它把模型选择集中起来，也把错误集中到了路由策略和验收流程上。若没有作用域隔离、变更记录、响应契约、故障注入和成本核对，别名只会把“代码里散落的耦合”变成“网关里隐藏的耦合”。

因此，一个更可靠的判断标准不是“应用是否已经改成调用别名”，而是：当后端模型替换、主路径失败、备用模型能力不足或路由策略改变时，团队能否回答请求去了哪里、为什么去那里、失败后发生了什么，以及结果是否仍满足业务契约。能回答这些问题，别名才是控制面；否则，它只是一个更容易被误解的字符串。
