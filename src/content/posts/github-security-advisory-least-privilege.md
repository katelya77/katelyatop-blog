## 权限拆分之后，漏洞治理能否继续依赖“管理员角色”？

GitHub 已经把安全建议权限拆成一组可以分配给自定义仓库角色的能力。对安全团队来说，这意味着仓库级漏洞协作不再必须绑定仓库管理员或组织级 Security Manager；对维护者来说，则意味着私有漏洞报告、临时私有 Fork 和最终公开披露可以用更细的授权边界来管理。

这不是一次界面整理，而是治理模型的变化。过去只要能完整处理安全建议，往往只能授予较强的仓库管理权限；现在，组织可以依据工作职责，只在需要的仓库中授予相应能力。但细粒度并不自动等于最小权限：只有把“查看、创建和编辑、接受报告、发布与申请 CVE、合并修复”拆成不同的生命周期阶段，才能判断某个角色是否真的过度授权。

证据等级方面，这项能力已由 GitHub 在 2026 年 11 月 20 日作为正式可用能力发布，而不是社区猜测或预览功能。本文讨论的是公开发布能力及其公开声明的工程边界，不推断未披露的后台实现，也不假设所有组织账号均能使用；该能力用于支持自定义仓库角色的平台和计划范围，仍需以组织实际配置能力为准。

组织身份登录也会影响这种治理。公开发布的 Claude Code v2.1.330 说明，企业组织登录可以在登录后应用组织配置并选择云服务商或网关。虽然这不是 GitHub 安全建议权限本身，但它提供了一个可比的治理模式：身份登录、组织策略和仓库动作应属于不同控制面。同样地，GitHub 中的安全建议权限不能只用一个“安全人员”角色覆盖，必须把组织身份、仓库成员身份和安全建议生命周期区分开。

## 权限矩阵：先按工作流，而不是按职位命名角色

GitHub 将安全建议相关权限公开划分为四组。理解它们时，最稳妥的方法不是逐项翻译，而是把每项能力放进一个具体工作流中。

### View security advisories

该权限允许查看草稿安全建议、状态和评论。它适合只需要了解风险状态、参与信息收效或准备沟通材料的角色。

该角色应有能力阅读私有上下文，但不应默认获得创建、编辑或管理协作的能力。如果安全建议中包含供应链坐标、受影响版本和临时修复信息，查看权限本身仍可能暴露敏感内容，因此仓库范围和成员范围都不能省略。

### Create、Edit 和 Manage security advisories

这是一组组合能力：在拥有 View 能力的基础上，能够创建、编辑安全建议、发表评论、管理协作者，并创建临时私有 Fork。

这适合负责安全建议草稿、协调修复分支和跟进私有漏洞报告的维护人员。但公开资料明确指出，合并临时私有 Fork 的改动仍需仓库管理员或安全管理员；该组权限本身不等于合并权限。拥有这项权限的人也不能删除临时私有 Fork。

另一个边界是保密评论。只有同时拥有 Create、Edit 和 Manage，并且具备仓库写权限的人才能使用保密评论。因此，角色名称和实际仓库写权限不能混为一谈。评审时应同时检查角色赋予的权限和仓库成员已有的写权限。

### Accept private vulnerability reports and close or reopen security advisories

这项能力允许接受私有漏洞报告，以及关闭或重新打开安全建议。公开材料要求角色至少具有 View 或 Create、Edit 和 Manage 中的一项。

这种权限适合接收和分流报告的安全 triage 角色，但不应自动等同于发布权限。一个能够接受报告的人可能负责确认报告、联系上报者或安排修复，却不一定有权公开披露。关闭和重新打开能力也应视为状态变更权，而不是普通查看权。

### Publish security advisories and request CVEs

这项能力允许发布安全建议并申请 CVE。公开材料同样要求角色至少具有 View 或 Create、Edit 和 Manage 中的一项。

申请 CVE 或公开披露的结果比一般编辑更具外部影响，应当是更少人拥有的权限。角色范围之外的成员可能参与修复或评论，但不能因为能提交修复就推导出具有披露权限。

## 配置清单：从组织到仓库逐层收敛

GitHub 官方说明指出，这些权限适用于仓库安全建议和私有漏洞报告，并可分别分配给组织内选定的仓库。以下配置过程不依赖任何不可验证的后台接口，适合在组织设置页面中逐项核对。

```text
1. 确认组织支持自定义仓库角色，并确认操作者已获得创建角色所需的组织管理权限。
2. 打开组织设置中的自定义仓库角色配置页面。
3. 新建角色时选择 Security 权限组。
4. 逐项启用上述四类安全建议权限，不要一次性创建一个“大安全角色”。
5. 为角色选择单个仓库或明确的仓库范围。
6. 将角色分配给用户或团队，而不是组织范围的通用账号。
7. 保存后分别用接收者和管理员账号登录进行验证。
8. 检查临时私有 Fork 是否能创建、不能删除以及合并是否仍受额外限制。
9. 对保密评论执行有写权限和无写权限两组测试。
10. 完成验证后记录角色、仓库、成员团队及生效日期。
```

推荐的初始角色组合如下：

| 角色用途 | 建议权限组合 | 明确排除 |
|---|---|---|
| 风险观察者 | View | 创建、接受、关闭、发布、申请 CVE |
| 漏洞接收与分流 | View；接受或关闭/重新打开报告 | 发布、申请 CVE、合并修复 |
| 修复协调者 | Create、Edit 和 Manage；接受报告 | 发布、申请 CVE |
|披露负责人 | View；发布并申请 CVE | 不替代仓库管理员合并权限 |

这里必须注意：权限组合不是孤立的。修复协调者可能同时拥有仓库写权限，披露负责人则不一定需要这样；角色范围比角色名称更重要。建议使用项目团队映射角色，不要把个人账号长期绑定到组织级角色。

## 真实验收矩阵：至少覆盖这六种状态

配置完成不等于功能可用。验收应围绕私有漏洞报告和安全建议的完整生命周期，并区分功能是否存在、权限是否正确、仓库范围是否收敛。

```text
测试一：无权限成员
预期：无法查看草稿安全建议、无法读取保密评论，也无法创建临时私有 Fork。

测试二：仅 View 权限
预期：可以查看授权范围内的安全建议状态和评论，不能创建或编辑内容。

测试三：Create、Edit 和 Manage 权限
预期：可以创建安全建议、管理协作者并创建临时私有 Fork。
额外检查：不能删除该临时私有 Fork；合并仍需仓库管理员或安全管理员。

测试四：保密评论
使用相同角色分别测试具备和不具备仓库写权限的成员。
预期：只有拥有该管理权限且具备仓库写权限的成员能使用保密评论。

测试五：接受报告与状态变更
预期：只有具备接受权限、关闭或重新打开权限的角色可以执行相应操作。

测试六：发布与申请 CVE
预期：只有发布权限角色能够执行公开披露和 CVE 请求。
不应：因成员具有修复提交权限，就推断他们拥有披露权限。
```

如果测试账号在无权限仓库中仍能看到建议，不应继续扩大合并测试；应先确认角色是否误分配到组织范围、仓库范围是否设置错误、以及成员是否已经通过其他角色获得权限。此处的核心是找出实际权限来源，而不是把现象归结为某个角色无效。

## 验证方式：同时检查正向能力和失败边界

不能只验证“能不能创建安全建议”。一套完整验收至少需要正向与反向两组操作。

正向验证应回答：授权成员是否能完成其职责；例如接收报告的成员能否接受报告、修复协调者能否创建临时私有 Fork、披露负责人能否打开公开披露流程。

反向验证应回答：未授权能力是否确实不可执行。尤其要测试以下五个容易混淆的动作：删除临时私有 Fork、合并临时私有 Fork、发表评论但不具备仓库写权限、在未授权仓库查看建议、申请 CVE 或发布安全建议。

可以使用一个权限变更日志表记录每次角色变更：

```text
role_name:
repositories:
assigned_team_or_user:
view_advisories:
create_edit_manage:
accept_close_reopen:
publish_request_cve:
existing_repo_write_access:
validated_on:
validator:
rollback_owner:
```

这个记录的作用不是证明某次操作绝对安全，而是提供可追溯证据。未来出现异常时，可以结合仓库范围、角色变化和成员已有权限定位。单项配置成功只能说明该能力存在，不能证明整个组织治理成立；只有正向操作、反向拒绝、仓库隔离和合并边界同时通过，才算完成验收。

## 工程取舍：为什么不建议一个安全万能角色

最小权限的直接成本是角色数量和维护工作量。一个万能角色通常只需要一次配置，却会让所有安全成员同时拥有接受报告、创建临时分支、发表评论、关闭建议、申请 CVE 和合并修复的潜在能力；当成员离岗或仓库转移时，风险面会迅速扩大。

细分角色的成本则是配置复杂度、培训成本以及角色组合冲突。组织不一定需要创建四个独立角色，可以先围绕两个核心职责建立：漏洞接收与修复协调、披露与发布；但每个组合都应明确排除不需要的权限。

还要区分仓库角色和组织安全职责。仓库管理员拥有强大的仓库级管理能力，可能已具备合并临时私有 Fork 的能力，但这不意味着应让他自动获得安全建议的全部生命周期权限。反过来，安全负责人的安全建议权限也不自动意味着可以合并仓库修改。权限之间需要清楚的职责分离，而不是互相包含。

对长期维护的组织而言，建议采用以下回退原则：

- 新权限默认只覆盖一个仓库或一个仓库集。
- 新权限先由维护团队演练，再扩展到其他仓库。
- 发布、申请 CVE 等外部影响能力保留给最少成员。
- 临时私有 Fork 的合并始终保持额外审批边界。
- 保密评论是否可用要同时验证角色权限和仓库写权限。
- 当角色来源不明确时先撤销组织范围分配，再逐仓库重新核对。

## 失败边界与原始结论

GitHub 的公开说明没有提供所有平台和计划的可用性保证，只有支持自定义仓库角色的组织、且采用受支持计划时才会应用。这意味着界面中的选项、组织策略和成员实际操作能力可能因账号类型、平台或计划而不同，不能把一份配置截图作为跨组织结论。

此外，公开材料没有说明私有 Fork 的合并者如何与仓库管理员、安全管理员进行审计接管，也没有披露底层角色继承的实现细节。我们只能验证公开声明的外部行为：能力是否出现在自定义角色中，仓库范围是否有效，以及合并、删除和保密评论是否遵循公开限制。

这项能力的原创工程结论是：安全建议治理不能只问“谁是安全人员”，而要问“这个成员在这个仓库、当前处于安全建议生命周期的哪个阶段，能否执行一个不可逆动作”。如果角色模型只回答身份问题，而不回答仓库范围、生命周期阶段和不可逆边界，最小权限就只剩下文字上的承诺。

对 GitHub Organization 来说，真正可落地的最小权限不是把管理员从列表中移除，而是把查看、接收、修复、披露和合并拆开；再用仓库级分配、正反向验收和可追溯变更日志证明这些边界确实存在。
