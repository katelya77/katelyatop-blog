安全扫描工具升级，最容易被误解成一次普通的依赖更新：把版本号改掉，等待流水线重新跑完，再看告警数量有没有变化。但静态分析的输出并不是单纯的布尔值。一次升级可能改变查询的识别范围、误报率、CWE 标签、日志输出位置，甚至改变扫描规则包在打包和发布阶段能读取哪些文件。若只比较“告警总数”，就很难知道变化来自真实风险、查询修正，还是元数据和运行环境的改变。

GitHub 发布的 CodeQL 2.27.4 提供了一个很典型的观察窗口：Java/Kotlin 查询增加了对多类框架清理函数和保护条件的识别；Rust 查询减少了若干误报；C/C++ 查询不再把特定的有意指针运算和 `[[maybe_unused]]` 变量当成问题；CLI 则把 JVM 警告与初始化错误移到标准错误，并在打包或发布 pack 时检查符号链接解析后是否仍位于 pack 根目录内。它们看起来分属规则、元数据和 CLI 三个层面，实际上共同指向同一个工程问题：扫描结果必须能被解释、被复现、被安全地消费。

## 一次升级其实改变了三条链路

第一条是“代码到查询结果”的语义链路。查询并不是简单地寻找字符串，而是根据数据流、清理函数、保护条件和语言语义判断一段代码是否构成风险。以 Java/Kotlin 为例，日志注入查询开始识别更多来自 JDK、Apache Commons、Guava、OWASP Java Encoder 和 Spring Framework 的清理器及保护条件。这意味着旧版本曾经可能把某些已经完成处理的输入继续报告为风险，新版本则可能减少这类误报。

第二条是“查询结果到治理标签”的元数据链路。CWE 标签经常被用于看板分类、合规报表、风险优先级和自动化门禁。CodeQL 2.27.4 移除了若干正则表达式相关查询上的 CWE-730 标签。这里不能简单理解为“风险消失了”，更准确的说法是：查询与该 CWE 的关联元数据发生了修正。若组织把 CWE 标签直接当作风险类型、指标维度或告警路由条件，那么升级后统计口径可能变化，即使代码本身没有任何修改。

第三条是“CLI 输出到自动化系统”的接口链路。机器可读输出一旦混入 JVM 警告或初始化错误，JSON、SARIF 或其他结构化结果就可能无法被下游解析。把这类信息转移到标准错误，是对命令行接口边界的修正，而不是一个无关紧要的日志调整。流水线应当明确区分标准输出和标准错误：前者保存结构化结果，后者进入诊断日志，并在失败时保留完整上下文。

## 不要用告警总数验收查询升级

升级前后的告警数量只能作为入口指标，不能作为结论。一个更可靠的验收样本至少要分成三组。

第一组是“已知真实问题”。选择仓库中已经人工确认的缺陷，记录查询 ID、文件路径、行号、告警消息和当前处置状态。升级后确认这些问题仍然能被发现，或者明确记录查询语义改变的原因。真实问题样本用来检查召回能力，不能因为总告警减少就直接视为成功。

第二组是“已知安全清理路径”。针对 Java/Kotlin、Rust 等受影响语言，挑选项目实际使用的清理器、编码器或保护条件，制作最小化样例。样例需要同时包含安全路径和不安全路径，避免只测试一条“应该不报”的代码。升级后的目标不是让告警越少越好，而是让安全路径不再被无意义地阻塞，同时让绕过清理器的路径仍然可见。

第三组是“元数据依赖样本”。从已有报告中抽取使用 CWE 标签进行统计或分派的记录，比较查询 ID、CWE、严重度、路径和消息，而不是只比较数量。如果发现某个看板的趋势线突然下降，应先判断是代码变安全了，还是查询标签被调整了。对于合规报告，最好同时保存扫描器版本和查询包版本，避免把不同版本的统计直接拼接成一条时间序列。

可以先用如下方式建立结果快照，命令本身不依赖具体项目语言，重点是保留可比较的字段：

```bash
mkdir -p artifacts/codeql-before artifacts/codeql-after
codeql version 2>artifacts/codeql-after/version.stderr \
  | tee artifacts/codeql-after/version.stdout
jq -S '{runs: [.runs[] | {
  tool: .tool.driver.name,
  rules: [.tool.driver.rules[]?.id],
  results: [.results[]? | {
    ruleId, level, message: .message.text,
    locations: [.locations[]?.physicalLocation?.artifactLocation?.uri]
  }]
}]}' scan.sarif > artifacts/codeql-after/normalized.json
```

如果当前流水线使用的不是 SARIF，而是其他机器可读格式，应保留等价字段。关键不是强行统一工具输出，而是固定比较维度：扫描器版本、查询 ID、规则元数据、结果级别、文件位置和消息。对标准输出与标准错误也要分开保存，不能把两者通过无条件的 `2>&1` 合并后再交给 JSON 解析器。

## 符号链接把“扫描输入”变成了边界问题

CodeQL 2.27.4 对 pack 的打包或发布增加了符号链接边界检查：解析链接后，如果文件位于 pack 根目录之外，CLI 会跳过该文件并显示警告。这项行为的工程意义不在于“某个特殊文件终于被处理”，而在于它明确了安全工具处理文件系统时的信任边界。

一个 pack 目录里可能存在普通文件、目录链接、文件链接，甚至由构建脚本临时生成的链接。目录树表面上看起来位于 pack 根目录内，真实路径却可能指向工作区、缓存目录或构建机上的其他位置。如果发布流程把解析后的外部文件纳入资产，就会产生两个问题：其一，发布内容不再由 pack 目录完整决定，复现性下降；其二，打包过程可能意外携带不应发布的源码、凭据文件或构建机信息。

升级验收时，应该把链接作为单独的测试维度，而不是等待生产流水线偶然触发。可以在临时目录中构造一个根内文件和一个指向根外文件的链接，然后检查打包日志是否出现警告、最终包内是否包含外部文件。验证重点有三项：

1. 根内普通文件正常进入包，避免把所有链接都误判为非法。
2. 指向根外的链接不进入包，并且留下可定位的警告。
3. 流水线不会把警告吞掉后仍然输出“发布成功”的无条件状态。

示例检查可以先做文件系统层面的预检：

```bash
pack_root="path/to/pack"
find "$pack_root" -type l -print0 |
while IFS= read -r -d '' link; do
  resolved="$(realpath -m "$link")"
  case "$resolved" in
    "$PWD/$pack_root"/*) echo "inside: $link -> $resolved" ;;
    *) echo "outside: $link -> $resolved" >&2; exit 1 ;;
  esac
done
```

这段检查不能替代 CodeQL CLI 的正式打包逻辑，因为它只负责提前暴露链接边界；真正的验收仍应以实际使用的打包命令、警告和产物清单为准。它的价值是把“发布时才发现的问题”提前变成一个可测试的流水线条件。

## 让 CI 能区分规则变化与环境变化

静态分析升级通常同时发生在多个层面：运行时镜像、查询包、编译数据库、依赖缓存和 CI 执行器都可能变化。若把这些改动放在同一个提交中，失败后很难知道根因。更稳妥的做法是先固定代码和构建环境，只替换 CodeQL 版本；完成结果快照后，再单独更新查询包或运行时镜像。

流水线至少应该记录以下信息：扫描器版本、查询包版本或提交标识、目标语言、构建命令、数据库创建结果、分析命令的退出码、标准错误日志摘要，以及最终报告的哈希。这里的“记录”不是为了增加日志数量，而是为了让一次告警变化可以回溯到具体输入。特别是 CLI 将 JVM 警告移至标准错误后，日志采集器必须确认错误流仍会被保留；否则输出虽然更适合机器解析，诊断信息却可能消失。

对于门禁策略，建议把“新告警”“历史告警”“元数据变化”和“工具执行失败”分开处理。新告警可以阻断合并；历史告警可以按照既有基线管理；CWE 标签变化应触发报告审阅，而不是自动关闭问题；工具执行失败必须被视为失败，不能因为没有生成告警就当成安全。尤其不能用“结果文件存在”替代“分析成功”，因为一个空文件也可能来自前置步骤异常。

预发布版本的 CI 改动也能说明同一原则：当集成测试、锁粒度、缓存复用或测试分片发生变化时，验证对象不只是单个测试是否通过，还包括运行状态是否被错误共享、失败是否能稳定复现、并行化是否改变了结果。静态分析流水线同样如此，不能只看绿色徽章，还要验证输入边界、输出协议和失败信号。

## 一份可执行的升级验收清单

在合并升级前，可以按下面顺序执行：

1. 保存旧版本的版本信息、查询清单、报告摘要和失败日志。
2. 选取真实缺陷、安全清理路径和元数据依赖各一组样本。
3. 只替换扫描器版本，重新生成数据库和报告。
4. 比较查询 ID、规则级别、文件位置、消息和 CWE，而不是只比较总数。
5. 验证标准输出仍是可解析的机器格式，标准错误包含 JVM 警告和初始化诊断。
6. 为 pack 中的普通文件、根内链接和根外链接分别构造测试。
7. 检查外部链接被跳过时，流水线是否保留警告并根据策略决定是否失败。
8. 更新看板或合规报表的基线说明，标注工具版本和元数据变化。
9. 在合并门禁中区分分析失败、规则新增告警和历史告警。
10. 将升级后的快照保存为后续回归样本，而不是只保留最终绿色状态。

## 原创结论：静态分析的升级对象是“证据链”

CodeQL 2.27.4 的价值不应被概括为“误报减少了”或“新增了安全检查”。更重要的是，它让三个经常被忽略的边界变得可见：查询语义会影响召回与误报，元数据会影响治理统计，CLI 输出和文件系统解析会影响自动化系统是否可信。

因此，静态分析升级的验收单位不应该是版本号，也不应该是告警总数，而应是一条完整证据链：同一份代码经过明确版本的工具处理，产生可解析且可复现的结果；结果中的规则和元数据能解释统计变化；打包产物不越过目录信任边界；任何执行失败都能以失败信号进入流水线。只有达到这个层次，扫描工具的升级才真正从“换依赖”变成了安全工程能力的升级。
