## 先判断问题：模型名相同，不代表请求相同

AI 网关排障最容易陷入一个误区：只要客户端请求的是 `/v1/chat/completions`，模型字段也写成同一个名称，服务端就应该得到同样的结果。OpenAI 兼容接口解决的只是表面上的数据交换格式，并不意味着上游会忽略客户端身份、请求头、工具定义或路由路径。

NodeLoc 上的一篇社区记录提供了一个很具体的样本：作者比较了旧的 `opencode2api` 方案与 `zen-proxy` 方案，认为后者之所以能得到真实上游响应，并不是简单更换模型名或 IP，而是同时匹配了 Bun runtime、OpenCode 2.1.4 的 User-Agent、完整的 OpenCode harness system prompt、真实 tool manifest，以及若干会话和链路追踪请求头。该记录还提到上游路径从旧路径改为 `https://opencode.ai/inference/openai/v1`。

这些内容的证据等级需要明确：它们来自社区复现记录，而不是 OpenCode 官方发布说明；材料中没有提供上游协议的正式兼容性文档，也没有证明这些条件在所有账户、地区或时间段都成立。因此，合理的工程结论不是“照抄参数即可绕过限制”，而是：当一个代理表现异常时，必须把请求拆成可比较的协议特征，并在有授权的环境中逐项验证。

## 网关真正适配的是一组协议特征

可以把一次 AI 请求抽象成五层，而不是一个 URL 加一个模型名。

第一层是传输层，包括 HTTPS、连接复用、超时、流式响应和运行时行为。社区记录特别提到 Bun runtime，但材料不足以证明运行时本身是决定因素。它更像是一个需要纳入对照实验的变量：如果切换运行时后结果变化，应继续比较实际发出的 TLS、连接和 HTTP 行为，而不能直接把结论归因于 Bun。

第二层是身份层。User-Agent、授权方式、客户端版本和请求头可能参与上游路由或兼容性判断。记录中出现了“真实 OpenCode 2.1.4 User-Agent”，这意味着代理如果随意伪造一个通用客户端标识，可能无法还原原客户端的请求形态。但工程上不应把“伪造身份”当作默认方案；更稳妥的做法是使用官方支持的客户端和凭据，或者在自有服务中明确记录并验证客户端版本。

第三层是上下文层。system prompt 不只是提示词内容，也可能决定工具调用格式、角色顺序、消息字段和模型行为。OpenCode harness system prompt 与普通聊天提示词并不等价。若代理只转发用户消息，丢失系统层上下文，即使 HTTP 返回 200，也可能出现工具不可用、输出格式变化或模型行为不一致。

第四层是工具层。工具名称、参数 JSON Schema、调用结果消息和工具选择策略共同构成 tool manifest。一个“兼容聊天接口”若没有完整转发这些字段，实际上只兼容了文本对话，而没有兼容 Agent 工作流。调试时不能只比较 `messages`，还要比较 `tools`、`tool_choice`、工具调用 ID，以及后续工具结果如何回注。

第五层是会话与链路层。案例中提到 `x-opencode-session`、`x-opencode-project` 和 `b3/traceparent`。这些字段可能用于会话关联、项目隔离或追踪，而材料没有证明每个字段的具体语义。工程上应把它们视为“需要保留和观察的协议字段”，而不是未经证实就写死业务含义。

## 在自有环境中建立最小可复现对照

验证兼容性时，先建立一个只服务于排障的旁路实例。社区记录给出的实例监听地址是 `127.0.0.1:8789`，并报告了 `GET /health` 返回 `{"ok":true}`，以及通过 `/v1/chat/completions` 获得上游响应。这里的地址和结果只能作为该社区案例的记录，不能视为通用默认配置。

可以先用最小检查确认本地代理是否启动：

```bash
curl -i http://127.0.0.1:8789/health
```

再用一个不涉及敏感凭据的短请求确认基本转发链路。凭据应从环境变量读取，不要写入 shell 历史、仓库或日志：

```bash
curl -N http://127.0.0.1:8789/v1/chat/completions \
  -H 'Content-Type: application/json' \
  -H "Authorization: Bearer ${UPSTREAM_TOKEN}" \
  -H 'x-opencode-session: diagnostic-session' \
  -H 'x-opencode-project: diagnostic-project' \
  -d '{
    "model": "MODEL_ID",
    "messages": [{"role":"user","content":"respond with one word"}],
    "stream": true
  }'
```

这条命令只验证“请求能否经过本地代理并返回响应”，不能证明模型可用、工具兼容或配额状态正常。下一步应保存一份脱敏后的请求摘要，至少包括：方法、路径、状态码、响应时间、是否流式、模型字段、消息角色序列、工具数量、关键非敏感请求头名称，以及上游错误类型。不要记录完整 Authorization、完整 system prompt 或用户数据。

对照实验要一次只改变一个变量。例如先固定运行时、模型、提示词和 token，比较是否保留完整工具清单；再比较是否保留会话头；最后比较上游路径。每轮都记录成功率、首字节时间、完整响应时间、错误码和响应体结构。只有当其他变量保持不变时，才能把结果差异归因于某个字段。

## 不要被 429 和 200 误导

社区记录提到旧方案返回 `Free usage limit reached`，而新方案返回真实上游响应；它还声称本地健康检查成功。这里至少存在两个不同层次的状态：本地代理健康，不等于上游授权成功；HTTP 请求成功，不等于 Agent 协议完整兼容。

因此，验证应分成三道门。第一道门是进程与网络：端口可连接、健康检查稳定、DNS 和 TLS 正常。第二道门是协议：响应 `Content-Type` 正确，流式 chunk 能被客户端解析，错误对象结构稳定，工具调用字段能够往返。第三道门是业务授权：凭据有效、模型确实被允许访问、配额和限流符合服务条款。

尤其要把 429 分类处理。它可能表示并发上限、速率限制、账户配额、模型不可用，或某个服务特有的策略。不能仅凭状态码推断原因，更不能把重试当成万能修复。客户端应读取错误体和 `Retry-After`，设置有上限的指数退避，并区分可重试的瞬时错误与需要人工处理的授权错误。如果服务明确禁止绕过限制，代理也不应通过伪造客户端指纹、轮换账户或隐藏真实请求来规避控制。

## 工程取舍：透明代理还是协议适配器

透明代理的优点是实现简单，消息和响应尽量原样转发，适合排查网络、认证和基础格式问题；缺点是它无法自动修复 OpenCode 特有的系统提示词、工具定义或会话关联。

协议适配器则会主动补齐字段、转换工具 schema、维护会话元数据，能更好地接入 Agent 客户端，但也更容易产生隐性差异：代理注入的提示词可能改变上下文，工具转换可能丢失约束，重试可能造成重复调用，日志则可能扩大敏感数据暴露面。适配器必须提供可关闭的注入项、结构化审计日志和请求回放摘要，而不是只在 README 中宣称“兼容”。

一个可执行的发布清单应包括：固定并记录客户端版本；对比真实请求与代理请求；验证普通文本、流式输出和工具调用三种路径；测试无效 token、未知模型、超时和 429；确认日志脱敏；确认重试不会重复执行有副作用的工具；确认所有上游路径和域名都来自可信配置；最后在服务条款允许的范围内进行小规模灰度。

## 结论：兼容性是可观测的协议契约

这个案例最有价值的地方，不是某个旁路实例是否在特定日期有效，而是它提醒我们重新定义“API 兼容”。兼容性不是返回一个 JSON，也不是模型名相同，而是传输、身份、上下文、工具、会话和错误语义能够共同满足客户端契约。

对社区发现应保持证据边界：材料只证明一篇帖子记录了特定方案、特定版本和特定结果；S3 仅能确认一个名为“追梦云AI”的 AI API Gateway 页面存在，不能替代 OpenCode 官方协议文档，也不能证明该方案长期稳定。真正可迁移的工程资产，应是脱敏请求样本、逐变量对照表、错误分类规则和可重复的验收清单。

当下次遇到“同样的 OpenAI 接口，为什么一个客户端能用、另一个不能用”时，优先问的不是“换哪个模型名”，而是：请求到底差了哪些字段？哪一层契约没有被代理保留？这个差异能否在授权环境中被单变量实验验证？这三问，比任何一次临时成功都更接近可维护的网关工程。
