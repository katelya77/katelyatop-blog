## Preview 的核心问题不是功能少，而是边界未定

Qwen Code 1.0 Preview 的发布说明给出了一个很容易被忽略的信号：它不仅增加了若干功能，还明确提醒接口、配置选项和行为可能发生变化。这个提醒决定了我们应该如何理解它。Preview 不是“功能完整但稳定性稍差”的正式版替代品，而是一组正在收敛的产品契约。

发布说明列出的能力包括：将 Qoder 与 Qwen Code 的 Agent 能力结合，用于代码理解、实现、调试和测试；支持 Qwen、Qoder 账号、多种模型提供商以及自定义兼容端点；为 macOS、Linux 和 Windows 提供不需要额外安装 Node.js 的原生包；支持会话恢复和非交互执行。

这些能力放在一起，意味着它已经不只是一个交互式聊天程序。它同时具备三种角色：面向开发者的终端工作台、可以嵌入脚本的自动化组件，以及连接多个模型和身份系统的控制面。角色越多，验证重点就越不能停留在“能不能启动”。

最近的 AI CLI 发布中也能看到类似现象：一个 Release 页面可能同时包含预览标签、平台资产、接口变化和行为变化。因而，版本号、下载成功、命令返回 0，只能证明不同层级的事实，不能合并成“适合生产使用”的结论。

## 把 CLI Agent 拆成四层契约

第一层是分发契约。Qwen Code 1.0 Preview 提供面向 macOS、Linux、Windows 的原生包，并强调无需单独安装 Node.js。这解决的是运行时前置条件，不等于解决了所有环境兼容性问题。操作系统和 CPU 架构仍然需要与资产匹配，企业代理、证书、文件权限、沙箱策略也可能影响启动和联网。

第二层是身份与模型契约。发布说明提到 Qwen、Qoder 账号、多模型提供商和自定义兼容端点。这里至少包含四个需要分别确认的问题：身份是否能完成登录或令牌配置；模型提供商是否能被正确选择；兼容端点是否符合客户端预期；不同提供商的错误、限流和上下文限制是否会以一致方式呈现。所谓“兼容”只能说明接口形状接近，不能推导出能力、计费、数据处理或工具调用行为完全相同。

第三层是执行契约。交互模式通常允许用户在每一步观察、修改或拒绝操作；非交互执行则会把 Agent 放入脚本、任务调度器或 CI。两者最重要的区别不是有没有终端，而是决策确认点是否被移除。一个适合人工辅助的流程，不能直接因为增加了一个非交互入口，就被视为适合无人值守。

第四层是状态契约。会话恢复意味着执行过程不再只存在于一次进程生命周期中。状态可能影响后续上下文、工具选择、工作目录理解和输出结果。因此，“恢复成功”至少要拆成三件事：是否找到了目标会话，是否恢复了预期上下文，恢复后是否仍然执行了正确的任务。只检查会话列表或进程退出码是不够的。

## 一套不依赖内部实现的验收流程

Preview 工具最适合采用分层验收，而不是直接接入真实仓库。下面的流程只依赖操作系统提供的检查能力和产品发布页明确列出的能力，适合在隔离目录中执行。

### 1. 固化资产与运行时证据

下载对应操作系统和架构的官方资产后，先记录文件名、大小和哈希：

```bash
sha256sum ./qwen-code-* 2>/dev/null
file ./qwen-code-* 2>/dev/null
uname -a
```

如果资产是压缩包，应记录解压后的目录清单；如果是可执行文件，应检查其格式和执行权限。不要把“下载页面出现了文件”当成“本机运行条件满足”。资产、架构和权限必须分别留下证据。

### 2. 验证启动与帮助信息

在临时目录中启动程序，先读取版本和帮助信息：

```bash
tmpdir="$(mktemp -d)"
cd "$tmpdir"
/path/to/qwen-code --version
/path/to/qwen-code --help
```

这里的目标不是背下参数，而是确认三个事实：版本标识是否与计划验证的 Preview 版本一致；程序是否能在无项目文件的目录启动；帮助信息是否明确暴露交互、非交互或会话相关入口。若帮助信息与发布说明不一致，应优先以当前资产的帮助输出为准，并暂停自动化接入。

### 3. 用无副作用任务验证模型链路

第一条任务应当是只读、短小、可重复的任务，例如要求 Agent 解释一个临时目录中的固定文本文件。不要一开始就让它修改真实项目、运行迁移或访问生产凭据。验证时同时保存标准输出、标准错误和退出码：

```bash
/path/to/qwen-code --help >help.txt 2>help.err
status=$?
printf 'exit=%s\n' "$status"
```

实际的非交互参数应以该版本帮助信息或官方文档为准，不应从其他 Agent CLI 的习惯中猜测。能够输出答案，只能证明一次调用链路可用；还需要检查异常输入、网络失败和模型端错误是否被明确报告。

### 4. 单独验证会话恢复

会话恢复不能用“第二次命令仍然成功”代替验证。应先创建一个包含唯一标记的短任务，再在新的进程中恢复，要求工具复述该标记并完成一个不同但相关的只读任务。验收记录至少包括：原始会话标识、恢复命令、恢复前后的工作目录、输出中的唯一标记、最终退出码。

如果恢复后只能重新开始，而不是读取原有上下文，就不能把它称为状态恢复。反过来，即使上下文恢复成功，也不能推断历史中的工具授权、文件锁或网络连接仍然有效；这些资源往往属于进程或环境，而不是会话文本本身。

## 非交互执行的风险边界

非交互执行最容易制造一种危险错觉：脚本返回成功，于是流水线就可以继续。实际上，至少有四类失败可能被掩盖。

第一类是语义失败。模型完成了一个与任务相近、但并不满足验收条件的动作。退出码只能描述程序流程，不会自动判断代码是否正确。工程上应要求 Agent 输出结构化结果，随后由确定性的检查器验证文件差异、测试结果或格式约束。

第二类是权限失败。非交互模式可能没有人工确认，Agent 也可能面对不同的工作目录、令牌和文件权限。应将它放在最小权限账户和临时工作区中，明确允许访问的路径，并把敏感环境变量从默认继承范围中移除。不能因为客户端支持自定义端点，就把所有网络访问都开放给它。

第三类是状态失败。恢复会话可能恢复了旧目标、旧分支或旧上下文。自动化任务应在开始时打印并核对工作目录、提交标识和目标文件清单；不一致时直接失败，而不是让模型自行猜测当前环境。

第四类是供应链失败。Preview 资产可能在后续版本中改变配置格式、命令行为或输出结构。脚本如果依赖未声明的日志文本、临时参数或内部目录，就会在升级后产生静默错误。自动化接口应尽量只依赖帮助信息或正式文档明确承诺的入口，并对版本做显式门禁。

## 从人工试用到工程采用的三阶段策略

第一阶段是观察。只允许在隔离目录中使用，任务限定为阅读、解释和生成补丁，不直接写入重要仓库。保存输入、输出、版本、环境和失败日志，目标是识别行为边界，而不是追求自动化比例。

第二阶段是受控自动化。将工具接入非关键仓库或临时分支，要求所有变更经过确定性测试、静态检查和人工审阅。会话恢复只用于可重放任务，网络和凭据采用最小权限。此阶段重点观察失败是否可识别、重试是否会产生重复副作用，以及不同模型提供商是否导致结果差异。

第三阶段才是有限生产化。即使进入这一阶段，也应保留版本锁定、回滚资产、任务超时、输出大小限制和人工接管路径。对于发布说明明确标记为 Preview 的版本，最稳妥的定位仍然是受控试验，而不是替代现有交付流程。

## 原创结论：Agent CLI 的稳定性是组合属性

Qwen Code 1.0 Preview 的价值不只在于把更多 Agent 能力放进一个终端程序，而在于它把分发、身份、模型、执行和状态放在了同一条链路上。链路中任何一层发生变化，最终行为都可能变化。

因此，CLI Agent 的“稳定”不能由一个版本号代表，也不能由一次成功运行代表。更可靠的判断方式是建立证据矩阵：资产是否正确、运行时是否满足、模型链路是否可用、非交互入口是否可重放、会话是否恢复了正确上下文、失败是否显式、变更是否经过确定性检查。只有这些证据同时成立，工具才适合进入更高风险的自动化层级。

Preview 的正确用法不是拒绝尝试，而是把尝试限制在可回滚、可观察、可验证的边界内。对 AI Agent 来说，真正可复用的工程能力不是“让它一直运行”，而是知道它何时不应继续运行。
