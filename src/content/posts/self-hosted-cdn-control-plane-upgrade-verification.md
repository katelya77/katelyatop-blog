## 先把问题从“部署一个 CDN”改写成“管理一组边缘节点”

社区里看到一个自托管 CDN 项目时，最容易被功能列表吸引：缓存规则、预热刷新、图片格式转换、HTTPS、HTTP/2、HTTP/3、压缩、WAF、四层转发和 DNS 调度。这些能力当然重要，但它们并不能回答一个更基础的问题：谁有权让某个节点接入控制面，节点运行的版本是否与控制面兼容，升级后出现故障时能否确认问题来自镜像、协议还是数据面？

Edgeweir 的公开仓库和发布说明提供了一个适合观察的样本。它把控制台和边缘节点拆成两个项目：控制面负责集群、配置、证书、策略、审计和 API；节点侧由 Go agent 与 OpenResty 数据面组成，并通过 mTLS 接入控制台。这样的结构意味着，CDN 不再是一个“启动容器、改几条 Nginx 配置”的单体服务，而是一个持续管理远端执行单元的控制系统。

因此，评估这类项目时，功能数量应该放在第二层。第一层应当是四个问题：初始化凭据如何产生，节点如何建立身份，控制面如何识别节点能力，发布如何证明升级对象确实是已经验收过的产物。只有这四层闭合，缓存命中率和节点数量才有工程意义。

## 控制面初始化：一次性令牌解决的是权限交接，不是登录体验

Edgeweir 20261110-e8637a1 的发布说明新增了通用安装器初始化模式。安装器从私密文件读取一次性令牌，在同一事务中创建内部运营身份、默认集群和专用 AccessKey。这个设计的关键不是“少输入一次密码”，而是把首次初始化从交互式账户登录改成了一个有边界的授权事件。

传统做法往往是：部署脚本要求管理员提供账户密码，脚本用这组长期凭据调用 API，再把密码写入环境变量、命令历史或 CI 日志。问题在于，初始化任务和日常管理任务共享了同一把钥匙。一旦脚本、日志或临时主机暴露，攻击者得到的就不只是一次安装权限。

一次性令牌和专用 AccessKey 则把权限拆成两个阶段：令牌只负责创建初始资源，后续自动化使用单独的集成密钥。已有实例还可以由部署所有者通过本地 CLI 显式授权集成并轮换旧密钥，不需要把账户密码、MFA 或通行密钥交给集成程序。发布说明同时强调，初始化和授权结果使用主密钥加密，并允许在 24 小时内恢复；确认需要持有本次签发的凭据，确认后删除恢复结果。

这类流程的工程重点是“恢复窗口也必须是状态机”。初始化结果不是永久可读的备份，也不是任何拿到接口响应的人都能再次确认的对象。相关接口拒绝普通幂等缓存并记录审计，说明它们不应被当成普通 GET 请求处理，也不能简单套用通用缓存层。

一个不依赖具体平台的部署检查可以这样写：

```bash
# 私密文件应由部署系统单独挂载，而不是写入镜像或仓库
install -m 0600 /secure/edgeweir-bootstrap-token /run/secrets/edgeweir-bootstrap-token
export EDGEWEIR_BOOTSTRAP_TOKEN_FILE=/run/secrets/edgeweir-bootstrap-token

# 初始化后立即检查：令牌文件权限、初始化日志、审计记录和专用密钥状态
stat -c '%a %n' "$EDGEWEIR_BOOTSTRAP_TOKEN_FILE"
# 不要把令牌内容打印到终端、CI 日志或诊断压缩包
```

命令本身不能证明初始化成功。至少还要核对四项结果：内部运营身份是否只创建了一份，默认集群是否存在，专用 AccessKey 是否已签发，审计日志是否记录了初始化和后续确认。若只看到容器返回 0，却没有这四项证据，初始化仍然不能算完成。

## 节点信任：mTLS 解决“是谁”，能力协商解决“能做什么”

控制面与节点分离后，节点身份和节点能力是两个不同问题。mTLS 可以帮助控制面验证连接对端的身份，但它不能自动证明节点支持某个扩展监听器、某个协议版本或某种数据面行为。Edgeweir 的节点仓库描述了 Go agent、OpenResty 数据面、mTLS 接入控制台和签名发布；控制台发布说明则明确指出，功能按节点上报的能力判断。

这意味着控制面不能仅根据节点名称、IP 地址或版本字符串下发配置。正确的决策路径应当类似：节点先以受信身份接入，再上报能力集合；控制面根据能力集合决定哪些功能可以启用；当节点不具备某项能力时，控制面应拒绝该配置、降级到兼容路径，或把节点排除在目标范围之外。

发布说明提供了一个具体边界：节点作用范围的扩展监听器需要 `extensions-node-v1`，已发布的 edgeweir-node v1.7.0 不具备该能力，因此本次控制台发布没有另发节点版本。这里有一个容易被忽略的结论：控制面版本更新不等于节点功能更新。即使控制台已经包含了新配置入口，旧节点仍然可能无法执行对应能力。

可以把上线前的兼容检查写成一张矩阵，而不是只比较两个版本号：

| 检查项 | 控制面 | 节点 | 结论 |
| --- | --- | --- | --- |
| 控制台镜像摘要 | 已固定 | 不适用 | 记录发布对象 |
| 节点版本 | 不适用 | v1.7.0 | 对照支持范围 |
| 协议版本 | proto/v1.10.0 | 需兼容 | 先做兼容检查 |
| 扩展监听器 | 可配置 | 不具备 `extensions-node-v1` | 不启用 |
| mTLS 身份 | 验证端 | 提供端 | 允许接入 |

这张表的价值在于阻止“界面可见”被误判为“运行时可用”。一个功能出现在控制台，只说明控制面知道它；只有节点能力、协议兼容性和数据面行为都通过验证，才能把它纳入生产配置。

## 发布与升级：固定标签只是选择，摘要和来源才是证据

Edgeweir 的该次发布同时给出了稳定标签、日期版本镜像和提交信息，并说明发布流程会直接提升已经通过完整验收的双架构候选镜像，保留原始摘要、SBOM 和构建来源证明，发布时不再重新构建。这种流程解决的是供应链中的“发布对象漂移”：如果构建一次、发布时再构建一次，即使源码提交相同，依赖、基础镜像或构建环境变化也可能让最终镜像不同。

对于运维人员来说，`stable` 标签适合简化部署，但不适合成为唯一的回滚依据。日期版本可以让变更窗口与目标对象对应起来；镜像摘要则进一步把“我想运行哪个版本”落实为不可含糊的内容地址。实际变更单至少应保存：控制台镜像标签、镜像摘要、节点版本、协议版本、提交 SHA、SBOM 或构建来源证明的位置。

升级顺序也不能省略。该版本说明要求先升级控制台，再升级节点；相较上一 stable 版本没有新增数据库迁移或协议变更，但从更早版本升级仍需留意已有迁移 0092。这种说明反映出升级风险至少有三个维度：数据库状态、控制面协议、节点能力。只看“是否有新迁移”不足以判断是否安全。

官方给出的更新路径包括执行 `./deploy.sh update`，或固定到日期版本镜像后拉取并重建。一个更稳妥的执行清单如下：

1. 记录当前镜像摘要、控制台版本、节点版本和协议版本。
2. 备份数据库，并确认备份可以被独立读取；只生成备份文件不等于具备恢复能力。
3. 在候选环境验证控制台启动、数据库迁移、API 健康状态和现有节点连接。
4. 先更新控制台，再按批次更新节点，保留至少一组旧节点作为回退观察对象。
5. 验证节点能力上报、缓存读写、刷新预热、证书续期和 WAF 配置加载。
6. 记录升级后的镜像摘要与审计事件，确认运行对象和变更单一致。

## 验证闭环：不要把 CI 绿色等同于边缘网络正常

该发布记录列出了 `pnpm lint`、29 项 CI Python 测试、proto 生成一致性与兼容检查、`pnpm typecheck`、`pnpm test`、双架构候选构建，以及 certd 的 `go vet ./...` 和 `go test -race`。这些证据覆盖了代码、类型、协议、构建和并发检查，但它们仍然不能替代部署后的运行时验证。

原因很简单：CI 能证明候选代码在预设测试中满足条件，却不能证明真实节点拥有正确证书、正确 DNS、可达的上游、足够的 MTU，也不能证明某条缓存规则在业务流量下不会把私有响应缓存给错误用户。因此验收应分成三层。

第一层是发布对象验证。确认运行中的镜像摘要与批准的候选摘要一致，架构与目标主机匹配，节点版本和协议版本在兼容矩阵内。第二层是控制面验证。检查登录、审计、节点状态、能力上报、证书状态和配置下发。第三层是数据面验证。用无敏感内容的测试域名验证缓存命中与回源、主动刷新、压缩、HTTPS、WAF 规则和节点故障切换。

每个测试都应记录请求入口、节点、响应状态、关键响应头、配置版本和时间窗口。尤其要区分“控制面显示健康”和“用户请求成功”：前者证明心跳或管理链路存在，后者才证明 DNS、网络、TLS、OpenResty 路由与上游服务共同工作。

## 失败边界：自托管带来的不是免费基础设施，而是责任转移

Edgeweir 的仓库和发布资料足以说明其架构、版本和验收信息，但不能据此推导出未提供的性能指标、抗攻击容量、全球网络质量或生产可用性。社区帖子中的功能描述也只能作为选题雷达；正式版本、协议和升级事实应以仓库与 Release 为准。对于 CDN 这类系统，尤其不能把“支持 HTTP/3”直接写成“在所有网络和客户端上都能稳定使用”，也不能把“支持 WAF”写成“自动阻断所有攻击”。

工程取舍也很明确：自托管控制面可以减少对外部厂商回连和遥测的依赖，获得配置、日志、密钥和节点生命周期的自主权；代价是证书、DNS、数据库备份、节点安全、漏洞响应和容量规划都回到了运营者手里。单镜像部署降低了初始复杂度，却不意味着升级、回退和灾难恢复可以省略。

因此，判断一个自托管 CDN 是否值得采用，不应从“功能表有多长”开始，而应从“失败时能否定位并回退”开始。一次性初始化令牌控制第一次信任，mTLS 和能力协商控制持续接入，镜像摘要与构建证明控制发布对象，分层验收控制真实流量风险。四者连起来，才形成了比“容器启动成功”更可靠的交付证据链。

这也是自托管边缘系统最重要的设计结论：控制面不是配置页面，节点也不是普通服务器。前者负责声明意图、权限和兼容边界，后者负责在网络不稳定和能力不一致的环境中执行意图。只有把身份、能力、版本和运行结果分别验证，CDN 才不会从一个方便的反向代理，变成一个难以审计的分布式故障源。
