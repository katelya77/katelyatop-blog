## 先把问题从“谁在登录”改成“谁在运行”

许多 AI Agent 最初都以交互式工具形态出现：开发者登录账号，工具继承当前用户的权限，再替用户调用模型或代码服务。这种模式适合本地试用，却不适合长期运行的机器人、CI 任务和组织级自动化。服务一旦离开人的终端，登录态就会变成脆弱的依赖：它可能过期，可能绑定个人离职风险，也很难回答“这次调用究竟应该算在哪个主体名下”。

GitHub 在 2026 年 10 月 27 日公布的 Copilot 服务到服务认证，选择了另一条路径：由安装在组织中的 GitHub App 作为工作负载身份，服务通过短期的 installation access token 调用 Copilot SDK。这里的关键变化不是增加了一种登录方式，而是把身份主体从“当前操作的人”切换为“被组织授权运行的应用”。该功能仍是 public preview，不能把预览能力直接当作稳定承诺，但它已经足够说明 AI Agent 服务化接入的架构方向。

这类设计的核心模型可以写成：

```text
自动化服务
    │ 持有或申请短期 installation access token
    ▼
GitHub App（组织安装实例）
    │ 具备组织授予的 Copilot Requests 只读权限
    ▼
Copilot SDK
    │
    ▼
Copilot 服务
```

服务本身不需要保存某个开发者的长期登录凭据。组织授权的是一个可识别、可撤销、可审计的应用安装实例，调用产生的使用量也归属于安装该应用的组织。

## 令牌只是入口，组织策略才是控制面

容易被忽略的一点是：短期令牌并不等于完整治理。材料明确给出的控制链至少包含四层。

第一层是安装范围。GitHub App 必须安装到组织，应用才能以组织拥有的身份工作。第二层是权限范围，组织可以授予 GitHub App `read-only Copilot Requests` 权限，而不是让它自动继承所有用户能力。第三层是调用令牌，服务把短期 installation access token 传给 Copilot SDK。第四层是组织控制面：模型策略、预算和支出控制仍然作用于这类调用。

因此，正确的问题不是“这个 token 能不能请求成功”，而是以下几项是否同时成立：

- 应用安装在正确的组织，而不是个人账户或错误的测试组织；
- 只授予完成任务所需的 Copilot Requests 权限；
- 令牌由服务运行时获取和轮换，不写入仓库、镜像层或日志；
- 组织的模型政策、预算和支出限制已经覆盖自动化调用；
- 业务侧能将应用调用与人工调用区分开，避免异常用量无法定位。

这解释了为什么“把个人 token 放进 CI”通常不是服务化方案。个人 token 解决的是认证动作，不能自动解决主体归属、离职影响、组织预算和统一撤销。工作负载身份的价值，正是把这些问题放回组织控制面。

## 用量归属决定了成本治理能否闭环

服务化 AI Agent 最大的工程风险之一，是功能调用成功了，但账单和责任无法解释。GitHub 的方案将使用量归因到拥有该安装的组织，并在 AI usage CSV reports 中通过 `app_client_id` 识别应用产生的使用量。这提供了一个比“看某个用户的消费记录”更适合自动化系统的审计维度。

落地时可以把一次调用拆成四个需要保留的字段：

```text
organization_id
app_client_id
job_id
requested_at
```

其中组织和应用标识负责回答“谁拥有这次调用”，任务编号负责回答“哪个流水线或业务任务触发了调用”，时间字段则用于和令牌生命周期、部署记录、预算告警对齐。应用日志不应记录完整 access token，但可以记录令牌获取是否成功、调用开始结束时间、请求的内部任务编号和返回状态。

验证成本闭环时，不要只检查 SDK 返回 200。至少要完成一次低额度测试，并在组织侧核对：该调用是否出现在预期的应用归因记录中；模型策略是否生效；预算或支出控制是否能够影响调用；同一组织中不同应用的用量是否可区分。若只能看到“某个用户用了多少”，而看不到 `app_client_id` 对应的应用记录，说明审计链还没有闭合。

## 从人工登录迁移时，最容易踩到的边界

第一，public preview 不是正式稳定接口。S4 明确将服务到服务认证标为公开预览，因此生产系统需要把认证适配层隔离出来，避免业务代码到处依赖预览字段或固定行为。出现接口变化时，应只替换令牌获取和 SDK 初始化部分，而不是重写业务任务。

第二，组织授权不等于无限权限。GitHub App 只读的 Copilot Requests 权限仍然需要与任务实际需求匹配。若 Agent 同时操作代码仓库、部署平台或外部系统，应为这些系统分别建立权限边界，不能因为它已经获得 Copilot 调用权限，就把所有外部凭据集中到同一个进程。

第三，撤销路径必须在上线前验证。材料给出的组织侧动作包括暂停或卸载应用。工程上应把它们视为正式的故障演练：暂停应用后，新调用是否被拒绝；已有任务如何结束；服务是否会无限重试；告警是否能指向具体的 `app_client_id`。没有撤销演练的自动化身份，只是把人工凭据换了一个名字。

第四，身份修复不等于上下文安全。另一个近期的 Claude Code v2.1.312 发布记录显示，Claude apps gateway 增加了 `oidc.user_id_claim`，可用 id_token 中非 `sub` 的声明识别用户，例如 Microsoft Entra ID 的 `oid`；同一版本还修复了 VS Code 扩展登录后托管设置和组织策略未持续获取的问题。这类变化说明，企业 AI 工具同时面对“应用是谁”和“应用代表哪个人或组织上下文”两个问题。工作负载身份适合无人值守服务，但需要模拟用户审计时，仍必须明确用户声明、组织策略和应用身份的对应关系，不能把它们混成一个字段。

## 一份可执行的接入检查清单

### 身份与权限

1. 为自动化服务创建专用 GitHub App，并确认安装目标是正确组织。
2. 仅申请材料明确支持的 Copilot Requests 只读组织权限。
3. 将短期 installation access token 放在运行时凭据管理中，禁止进入 Git、构建产物和普通业务日志。
4. 设计令牌获取失败、过期和权限被撤销时的明确错误路径，不用静默降级到个人登录。

### 归因与预算

1. 为每次任务生成稳定的内部 `job_id`。
2. 在应用日志中保存组织、应用客户端标识和任务编号，不保存完整令牌。
3. 用组织 AI usage CSV reports 检查 `app_client_id` 是否能识别自动化用量。
4. 用小规模调用验证模型政策、预算和支出控制确实作用于应用。

### 撤销与回滚

1. 在测试组织暂停应用，确认新请求被阻断。
2. 卸载应用后检查服务是否仍持有可继续使用的旧凭据。
3. 为重试设置上限，避免权限撤销后形成高频失败请求。
4. 保留回滚开关，但不要把回滚设计成恢复个人长期 token。

## 原创结论：AI Agent 的“无用户运行”不是无责任运行

服务到服务认证真正改变的是责任的归属方式。个人登录把责任隐含在某个账号里，工作负载身份则要求组织明确承认：这是一个由应用代表组织执行的自动化主体。它带来更稳定的运行方式，也让错误调用、预算超支和权限撤销变得更可定位。

但这条路径不能被简化成“申请一个 GitHub App，再传一个 token”。完整的工程闭环至少包括主体建模、最小权限、短期凭据、用量归因、组织策略和可验证撤销。由于当前能力仍处于 public preview，合理的上线策略应是把它当作隔离的认证适配层，先用低风险任务验证归因和撤销，再逐步扩大自动化范围。

当 AI Agent 从聊天窗口进入定时任务、流水线和组织服务，最值得优先建设的不是更长的上下文，而是一个能回答“谁授权、谁付费、谁能撤销、谁负责”的身份系统。
