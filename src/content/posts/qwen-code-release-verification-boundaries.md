## 发布说明不是功能清单，而是一组待证明的命题

AI 编程工具的升级公告通常很短，但每一条描述背后都可能包含多个不同层次的承诺。比如“支持有界 SQL 历史查询”，至少要继续追问：查询对象是什么，是否支持分页，能不能查到事务记录，精确操作或命令是否可定位；“默认启用 Generated UI”，则涉及默认配置、交互输出、上下文生命周期和旧用法兼容性。

Qwen Code v0.26.5 的官方 Release 同时列出了多类变更：Managed local H2 与 Hosted MySQL 增加有界 SQL 历史查询；Generated UI 默认启用，并允许将带有交互卡片值的内容作为可移除上下文附加在输入框上；Web Shell 增加 Session Overview 和 Split View 的键盘快捷键；Goal card 与 Goals dialog 增加俄语本地化，并对未翻译字符串回退到英文；一键守护进程更新扩展到 pnpm、yarn、bun 以及带 sudo 前缀的 npm 安装，并在自动更新不可用时展示手动步骤。

这些内容不应被直接改写成“体验全面升级”。更稳妥的做法，是把每条 Release note 转换为可观察的验收命题，再分别验证默认行为、输入边界、持久化结果和失败提示。发布说明负责提出事实，测试负责证明事实在当前环境中成立。

## 第一层：把 SQL 历史查询当成边界问题

“有界”是这条变更中最值得注意的词。它意味着历史查询不是无条件导出全部记录，而是存在查询范围或结果规模的控制。官方说明明确提到三类能力：分页的近期消息、journal transactions，以及精确的 operation 或 command 查找。材料没有提供具体 SQL 语法、默认页大小或保留周期，因此不能据此推导数据库结构，也不能声称它解决了完整审计需求。

工程上可以把验证拆成四个问题。

第一，查询范围是否真的受控。准备一组连续会话和足够多的历史消息，分别请求第一页、第二页，并记录是否出现重复、遗漏或顺序漂移。第二，近期消息与 journal transactions 是否是两个不同视图，是否能从返回结果中区分消息记录和事务记录。第三，精确 operation 或 command 查找是否要求完整匹配，空字符串、大小写变化和不存在的值如何处理。第四，结果为空时，界面或 API 是否返回明确的空结果，而不是把错误伪装成“没有历史”。

如果要把这套检查放进 CI，可以先固定一份最小数据集，再保存查询请求与响应摘要。例如：

```bash
# 查看当前发布说明，确认测试目标来自指定版本
 gh release view v0.26.5 --repo QwenLM/qwen-code

# 为每次验证保存版本和运行环境
 node --version
 pnpm --version
 git rev-parse --short HEAD
```

上面的命令只能确认版本与环境，不能证明 SQL 功能已经可用。真正的验收记录还应包含：数据集规模、分页参数、返回记录标识、事务或操作查询条件，以及错误响应。尤其不要用“页面能打开”替代“结果边界正确”。

## 第二层：Generated UI 改变的是输入状态机

Generated UI 默认启用，表面上像是一个开关变化，实际上会影响对话输入的状态模型。官方说明指出，用户可以继续聊天，并把交互卡片中的值作为可移除上下文附加在 composer 上。由此至少存在三个状态：普通文本输入、携带卡片值的输入、移除上下文后的输入。

验证时应避免只测试一次成功路径。首先确认升级后新用户是否确实进入默认启用状态；其次通过交互卡片产生一个值，观察该值是否以可识别的上下文形式附加到输入区；再次移除该上下文，确认后续消息不再携带旧值。还要测试连续选择多个值、重复移除、刷新页面和重新进入会话等情况。

这里有一个容易被忽略的取舍：交互卡片提高了结构化输入的效率，但也让“用户看见的文本”和“实际提交的上下文”不再完全等价。对于 AI 编程代理，这种差异会直接影响复现性。验收日志最好同时保存界面上显示的内容和最终提交的结构化字段；如果系统没有提供导出能力，就至少记录选择顺序、移除动作和提交时间。

失败边界同样重要。卡片值失效、值为空、上下文过长或与当前会话不匹配时，系统应明确提示，不能静默退化成普通文本。材料没有说明这些异常的具体处理方式，因此本文只把它们列为验收项，而不把任何一种行为写成 Qwen Code 已经保证的能力。

## 第三层：Web Shell 的快捷键不是小修饰

Session Overview 与 Split View 的键盘快捷键属于典型的交互变更。它们看似简单，却可能与终端输入、浏览器快捷键、操作系统快捷键和文本编辑行为发生冲突。测试重点不是“快捷键存在”，而是快捷键在不同焦点状态下是否作用于正确对象。

可以建立一张最小检查清单：焦点位于命令输入框时，快捷键是否仍能切换视图；焦点位于日志、对话或可编辑区域时，是否会误插入字符；切换到 Split View 后，两个面板的滚动位置是否保持可理解；窄屏窗口下是否有不可见面板；刷新页面后当前布局是否被错误恢复。若快捷键不可用，界面是否仍提供鼠标或菜单入口。

这类功能不应通过自动化脚本只检查 DOM 元素是否存在。更有价值的断言是：发送一个会改变状态的键盘事件，读取当前视图标识，再确认原输入内容未被破坏。对于终端型产品，还要把浏览器环境和真实终端环境分开记录，避免把浏览器事件模型的结果误认为所有运行环境都一致。

## 第四层：本地化与自动更新共享同一个原则

俄语本地化并不等于“所有文字都已翻译”。Release note 明确说明，Goal card 和 Goals dialog 增加俄语，同时对未翻译字符串使用英文回退。这实际上是一个可验证的本地化策略：已覆盖的键使用俄语，缺失的键保持可读，并且不会出现空白、原始键名或破坏布局的长文本。

因此测试不应只截图比较语言，而应准备覆盖和未覆盖两类字符串，检查回退是否稳定。还要确认切换语言后已经打开的对话框是否重新渲染，以及混合语言是否仍能完成操作。英文回退不是失败本身，无法理解当前状态才是失败。

守护进程一键更新则更接近运维流程。此次变更涉及 pnpm、yarn、bun 和带 sudo 前缀的 npm 安装，并在自动更新不可用时显示手动步骤。这里至少有两个独立命题：识别安装方式是否准确，以及失败后是否给出可执行的替代路径。不能因为界面出现“更新成功”就认为二进制、包管理器和服务状态都已一致。

验收时应为每种包管理器建立独立样本，记录当前版本、识别结果、升级前后版本和退出状态；对无权限、网络失败、命令不存在和版本已是最新等情况分别测试。带 sudo 的路径尤其需要确认提示是否清楚，避免把需要人工授权的步骤包装成无需干预的自动化。

## 证据等级决定文章和发布决策的语气

本批材料中，Qwen Code v0.26.5 是正式 Release 页面，能够支持对其发布说明的直接引用。但 OpenAI Codex 的 rust-v0.167.0-alpha.1 页面只明确显示了 alpha 版本、提交标识和 Release 状态，材料没有提供足够的变更内容。它可以证明该版本以 alpha 形式存在，却不能支持对具体功能、稳定性或生产适用性的推断。

这一区分对 AI 工具尤其重要。正式 Release 的“Added”可以作为功能存在的证据，但不自动等价于所有平台都可用、默认路径都成功或性能达到预期。alpha 标签则进一步降低结论强度：可以讨论版本身份和预发布属性，不能把它写成稳定发布，更不能用一个版本页面推导兼容性承诺。

建议在升级评审中把证据分成三层：发布页确认“官方宣称了什么”；运行验证确认“当前环境实际发生了什么”；回归测试确认“旧行为是否仍然成立”。三层证据缺一不可。只有发布页而没有运行验证，最多能决定是否进入试用；只有运行验证而没有版本锁定，则难以复现；只有新功能测试而没有旧功能回归，则无法判断升级风险。

## 我的结论：把升级拆成可撤回的行为变化

Qwen Code v0.26.5 的价值不在于一次加入了多少功能，而在于它展示了 AI 编程工具正在同时改变数据查询、对话输入、工作台导航、本地化和运维更新。它们分别属于数据边界、状态机、交互焦点、语言回退和失败恢复问题，不能用同一条“启动成功”标准验收。

更可靠的升级方式，是先锁定版本，再把 Release note 改写成行为断言；为每个断言准备成功、空值、重复、无权限和不可用等边界样本；保存请求、响应、界面状态和版本信息；最后给自动更新保留人工回退路径。这样做的结果不是让发布变慢，而是让“升级成功”从一句感觉，变成可以复查、可以回滚、也可以解释的工程结论。
