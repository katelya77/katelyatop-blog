## 先把“上线”拆成三个不同问题

社区材料里有一种很容易被忽略的叙事：项目作者说“网站也做好了”，随后给出多个域名，并表示“马上可以开始”。这句话对于产品宣传已经足够，对于工程判断却远远不够。一个 AI 网关是否真正上线，至少要拆成三个层次：网页是否能访问，API 是否能完成协议交互，以及服务是否具备可持续、可审计、可控的运营边界。

公开材料 S5 是社区帖中的项目说明，提到作者反复在 Go、Node 和 Rust 之间切换，后来参考 sub2api，并为 cliproxyapi 编写插件，同时列出了一个面向美国直连的域名、一个面向香港直连的域名，以及一个 API 域名。这些信息可以证明项目正在尝试把前端、反代和插件整合成服务，但不能证明它已经稳定提供某个模型，也不能证明它支持某种具体的 OpenAI 兼容接口，更不能证明免费额度、限流、日志保留和数据处理规则。

S6、S7、S8 是三个站点的首页材料，页面标题都显示“乐子AI”。这属于 primary 来源，但它们目前只足以确认页面存在和品牌名称一致。它们不能替代 API 文档、健康检查响应、模型列表、服务条款或隐私政策。也就是说，证据等级应当这样标记：社区帖子是项目意图和实现过程的线索，站点首页是域名可达与品牌一致性的直接证据，协议能力和运营承诺仍然属于未核验事项。

这种拆分很重要。否则，用户看到一个能打开的首页，就会顺手把“能访问”推导成“能调用”，再把“能调用”推导成“值得放入生产环境”。AI 网关的风险恰好集中在这些未经验证的跳跃上。

## 多域名不是三个入口，而是三条可能不同的链路

材料中的域名设计至少包含三种角色：一个美国直连入口、一个香港直连入口和一个 API 入口。表面上看，这是地理分流；从系统角度看，它更像是三条需要分别验证的请求路径。

第一条路径是浏览器到站点首页，主要验证 DNS、TLS、CDN 或反代是否正确。第二条路径是客户端到 API 域名，验证请求是否被转发到应用层，以及鉴权、路径重写和错误响应是否符合预期。第三种情况是用户从某个地区入口访问网页，再让浏览器或前端代码调用另一个 API 域名，此时还会引入 CORS、Cookie 域、Origin 校验和跨域预检等问题。三个域名即使展示同一个品牌，也不代表它们共享同一套配置。

最小检查可以从 DNS 和 TLS 开始。以下命令只是验证方法，不代表对材料中的站点已经执行过：

```bash
for host in ai.lezi-ai.bond ai.lezi-chat.bond api.lezi-ai.bond; do
  echo "== $host =="
  dig +short "$host"
  curl -I --max-time 10 "https://$host/"
done
```

如果没有 `dig`，可以使用：

```bash
getent ahosts ai.lezi-ai.bond
curl -sS -D - -o /dev/null --max-time 10 https://api.lezi-ai.bond/
```

这里至少要记录四类结果：是否解析到地址，证书是否覆盖当前主机名，响应状态码是否稳定，以及 `server`、`location`、缓存和安全相关响应头是否出现异常。不要只看浏览器能否显示页面，因为浏览器可能隐藏重定向、混合内容和证书链问题。

如果 API 域名确实承担 OpenAI 兼容入口，下一步应当优先检查文档声明的路径，而不是猜测。常见路径如 `/v1/models`、`/v1/chat/completions` 只能作为待验证候选，不能因为行业习惯就把它们写成该服务已经支持的事实。对于需要密钥的接口，应使用专门的测试凭证，并避免把真实 Token 放进 Shell 历史、截图或 CI 日志：

```bash
export BASE_URL="https://api.example.invalid/v1"
export API_KEY="replace-with-test-key"
curl -sS --fail-with-body \
  -H "Authorization: Bearer ${API_KEY}" \
  -H "Content-Type: application/json" \
  "${BASE_URL}/models"
```

测试完成后应立即清理环境变量，并检查终端历史是否记录了带密钥的命令。若服务没有公开文档，或者只返回网页而不是结构化 JSON，正确结论应是“协议能力尚未核验”，而不是“接口不可用”或“接口兼容”。

## 反代和插件层，决定“看起来统一”是否真的统一

S5 提到作者先后尝试不同语言和实现方式，后来参考 sub2api，并编写 cliproxyapi 插件。这个过程透露出一个常见架构：入口层负责接收用户请求，适配层把请求转换为某个上游或多个上游所接受的格式，管理层则处理账号、额度、模型展示和访问控制。它也暴露出最容易出问题的地方：每一层都可能把“兼容”理解成不同的范围。

协议兼容至少包含路径、请求字段、流式响应、错误格式、鉴权方式和模型标识六个维度。一个网关可以成功返回普通 JSON，却在 SSE 流式响应中丢失分隔符；也可以接受 `messages`，却无法正确处理工具调用、视觉输入或停止条件。因此，“能通过一次聊天测试”不能代表客户端生态兼容。

工程上更稳妥的做法，是为每一层保留可观测的边界：入口记录请求 ID，适配层记录规范化后的模型名和请求类型，上游调用记录耗时、状态码和重试次数，最终向用户返回不泄露上游凭证的错误信息。日志不能默认保存完整 Prompt、Authorization 或模型响应，因为网关天然处在用户输入与上游服务之间，日志系统本身会成为高价值数据汇聚点。

插件也不应被当作“把任意上游变成统一 API”的魔法。插件真正需要明确的是输入输出契约：哪些字段被保留，哪些字段被重写，流式事件如何映射，超时和取消如何传播，失败时是否可能重复扣费或重复执行。若这些规则没有文档或测试覆盖，接入方就只能依赖黑盒试错，最终把不确定性转移给用户。

## 上线前检查清单：从可达性走到可负责性

第一组检查是网络层。确认每个域名都有明确用途，DNS 记录没有指向陌生或过期目标，证书覆盖实际访问名，HTTP 到 HTTPS 的跳转没有循环，地区入口不会把敏感参数暴露在重定向地址中。

第二组检查是应用层。用无效 Token、缺少 Token、错误路径、空请求体和超大请求体分别测试，确认服务返回清晰的 4xx，而不是把所有失败都包装成 200。再用一个最小、非敏感的请求验证普通响应和流式响应是否分别成立。若服务声称支持模型列表，应记录模型名称、响应时间和错误结构，但不能把一次返回当成长期可用性证明。

第三组检查是跨域和浏览器层。若网页与 API 使用不同域名，应检查预检请求、允许的 Origin、允许的请求头和凭证策略。`Access-Control-Allow-Origin: *` 与携带凭证不能随意组合；更不能为了让前端“先跑起来”而把所有来源、方法和请求头全部放开。浏览器能发出请求，不等于服务端已经正确完成鉴权。

第四组检查是资源和运营层。明确免费额度从哪里来，限流按用户、密钥、IP 还是上游账号计算，余额耗尽后返回什么错误，异常流量如何封禁，管理员能否撤销凭证。公益项目尤其需要说明可用性预期：免费不等于无限，测试入口不等于生产 SLA，项目尚在准备阶段也不应让用户把它当作关键业务依赖。

第五组检查是数据边界。至少要回答 Prompt 是否进入持久化日志，响应是否用于调试，管理员是否能查看请求内容，数据保存多久，删除请求如何处理。如果这些问题没有公开答案，使用者应把该网关当作不适合发送密钥、个人信息、企业源代码和未公开材料的实验入口。

## 失败边界比成功截图更有价值

一个值得信任的网关，不是永远返回成功，而是在失败时保持边界清楚。上游超时应该与客户端取消区分；模型不存在应该与余额不足区分；网关自身过载应该与上游拒绝区分。错误码、响应体和请求 ID 共同决定了调用方能否重试。如果所有错误都变成“服务异常”，客户端可能无限重试，进一步放大故障；如果所有错误都变成 200，监控也会失去意义。

多地域入口同样不能只比较首页加载速度。真正需要比较的是 API 往返延迟、DNS 命中、TLS 建连、首字节时间、流式事件间隔和失败率。地区入口可能改善用户到边缘节点的网络距离，却把请求转发到同一个遥远上游；也可能因为不同反代配置而出现一边支持流式、一边缓冲完整响应的差异。没有分路径数据，就不能把“美国直连”和“香港直连”写成确定的性能结论。

因此，当前材料支持的最稳妥判断是：乐子 AI 已公开多个同品牌入口，社区作者描述了反代、前后端和插件整合过程，首页材料证明这些域名至少有可访问的品牌页面；但 API 协议、模型范围、免费规则、安全策略和稳定性仍需通过文档与实际响应进一步核验。这个结论看似保守，却比把准备上线误写成正式服务更有工程价值。

## 结论：网关的核心产品不是“模型数量”，而是证据链

AI 网关最容易被营销成一个入口、一个 Base URL 或一组免费模型，但真正决定它能否进入工作流的，是证据链是否闭合：谁维护入口，入口如何分流，请求怎样适配，上游失败如何返回，凭证如何撤销，日志保存什么，用户如何知道服务发生了变化。

对于材料中的项目，下一步最值得补齐的不是再增加一个域名，而是建立公开的最小契约：API 基础地址与路径、鉴权方式、支持的请求类型、限流和额度规则、数据处理说明、状态页或变更记录。每条声明都应能对应到页面、文档、仓库、测试响应或 Release，而不是只存在于社区帖的一句“马上开始”。

这也是使用者的判断顺序：先确认服务是谁，再确认请求去了哪里；先确认失败如何处理，再决定是否发送真实数据；先确认能力有证据，再把它接入自动化。所谓“公益”可以降低价格，却不能替代身份、协议和数据边界。一个 AI 网关真正成熟的标志，不是首页更漂亮，而是用户在成功与失败两种情况下，都能知道发生了什么。
