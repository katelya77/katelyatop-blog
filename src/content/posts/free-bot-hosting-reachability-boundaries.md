## 免费托管真正提供的是什么

社区里常见的“免费 Discord 机器人托管”通常会被描述成一个很简单的命题：创建服务、上传代码、让机器人保持在线。但公开方案的实际边界并不是“给你一台免费的 VPS”。HYEHOST 的免费 Bot Hosting 页面明确列出了一组受限资源：128 MB RAM、512 MB 持久化存储、1 个 NAT 端口、专用 IPv6 地址和 10 Mbps 网络速度，并要求每 30 天手动续订。社区帖子则补充了一个常被忽略的事实：这类服务可能只有 Shell 控制台，没有 root 权限。

因此，免费托管提供的更像是一个受约束的工作负载执行环境，而不是完整的网络基础设施。你可以运行一个轻量进程，但不能默认拥有端口管理权、完整的入站路径、内核级排障能力，也不能把控制台中“服务正在运行”直接等同于用户或 Discord 能够访问它。

工程上应把它拆成四层：进程是否存活，应用是否监听，网络是否能到达，第三方平台是否接受这个地址。任何一层失败，最终表现都可能只是“机器人没反应”。

## NAT 端口与专用 IPv6 不是同一条路径

NAT 端口解决的是地址转换后的某一条入站映射。它通常意味着：外部访问一个宿主机或边缘入口的端口，再由平台转发到你的服务端口。这个端口可能是动态分配的，也可能只允许 TCP；材料没有证明具体协议和映射规则，因此不能把它假设成通用的 HTTP 入口。

专用 IPv6 则是另一种地址族路径。它可能让服务拥有可路由地址，但“可路由”不等于“可从所有网络访问”。客户端所在网络可能没有 IPv6，云防火墙可能仍然阻断入站连接，应用也可能只绑定在 127.0.0.1 或 IPv4 地址上。反过来，若应用只监听 IPv6，拥有 NAT IPv4 端口也无法自动把请求送进正确的监听器。

部署前应明确回答四个问题：

1. 应用监听的是 IPv4、IPv6，还是双栈地址。
2. 平台分配的 NAT 端口是否支持应用需要的协议。
3. Webhook 发送方访问的是域名、IPv4、IPv6 还是平台生成的 URL。
4. 回调失败时，能否区分 DNS、路由、端口、TLS 和应用层错误。

不要用一次成功的本机 curl 替代公网验证。本机访问 127.0.0.1 只证明进程存在；通过服务器自身访问公网地址，也可能绕过真实的外部路径。

## 先验证进程和监听，再验证公网路径

在没有 root 权限的环境中，仍可以完成一组低侵入检查。假设应用端口是 3000，服务域名是 `bot.example.com`：

```bash
ps -ef | grep '[n]ode'
curl -fsS http://127.0.0.1:3000/health
ss -lnt
getent ahosts bot.example.com
curl -4 -v --connect-timeout 5 http://bot.example.com/health
curl -6 -v --connect-timeout 5 http://bot.example.com/health
```

这组命令的判断顺序很重要。`ps` 只能说明进程存在，不能说明它没有死循环或已经卡住；健康检查能证明应用层响应，但不能证明外部可达；`ss -lnt` 用来确认监听地址，重点观察是否为 `127.0.0.1:3000`、`0.0.0.0:3000`、`[::]:3000` 或其他地址；`getent ahosts` 则确认域名到底返回了哪些地址族。

如果平台提供了 NAT 端口，例如外部端口为 18080、内部端口为 3000，应把两者写进部署清单，而不是只记录内部端口。外部测试可以使用：

```bash
curl -v --connect-timeout 5 http://PUBLIC_HOST:18080/health
nc -vz -w 5 PUBLIC_HOST 18080
```

`nc` 成功只表示 TCP 建连成功，不代表 HTTP 路由正确；HTTP 返回 404 也不一定是网络失败，可能只是健康检查路径不存在。验证结果应至少记录 DNS 地址、连接地址族、TCP 结果、HTTP 状态码和响应时间。

如果使用 IPv6，还应在一个确认具备 IPv6 的外部网络执行：

```bash
curl -6 -v --connect-timeout 5 https://[2001:db8::10]/health
```

示例地址仅用于说明格式，实际部署必须替换为平台分配的地址。若域名同时存在 AAAA 和 A 记录，客户端可能优先选择 IPv6；于是“IPv4 测试成功、用户仍然失败”并不矛盾。

## Webhook 的失败边界比长连接更复杂

Discord 或其他第三方 Bot 平台通常会从外部发起请求。对这类请求而言，服务端的关键不是“机器人代码能启动”，而是第三方能否在规定时间内完成 DNS 解析、建立连接、完成 TLS 握手并收到符合要求的响应。

免费托管环境中常见的失败边界有四种。

第一，应用只监听回环地址。控制台内访问正常，外部永远连接不上。第二，NAT 端口存在，但应用把端口写死为 3000，平台实际入口却是另一端口。第三，域名同时返回 IPv4 与 IPv6，其中一条路径未开放，导致部分客户端失败。第四，服务休眠、续订过期或容器重启后端口映射改变，旧的 Webhook URL 仍被第三方使用。

因此，Webhook 端点应具备一个不依赖业务逻辑的健康检查，并把启动日志中的监听地址、外部入口、应用版本和启动时间输出到可保存的位置。健康检查只返回最小状态，不要把 Bot Token、环境变量或内部错误堆栈放进响应体。

一个简单的检查清单如下：

```text
[ ] 进程在无 root 权限下能够启动
[ ] 应用监听地址不是意外的 127.0.0.1
[ ] 平台内部端口与外部 NAT 端口已明确记录
[ ] A/AAAA 记录与实际可用地址一致
[ ] IPv4 和 IPv6 分别从外部网络测试
[ ] TLS 证书覆盖实际访问的域名
[ ] 健康检查不泄露密钥和内部路径
[ ] 续订日期、重启行为和端口变化有记录
[ ] Webhook 超时、重试和重复事件可以安全处理
```

## 私有源站改变的是暴露模型，不是可达性定律

Cloudflare 官方博客宣布其 private origins 服务正式可用，这类能力的核心方向是：让源站不必直接暴露为传统公网入口，而由受控边缘服务承担访问与回源关系。它解决的是源站暴露和访问路径治理问题，但不能替代应用自身的监听、认证和健康检查。

把这个思路放回免费 Bot 托管环境，可以得到一个重要区分：入口隐藏不等于应用安全，代理接入也不等于源站健康。如果源站进程已经退出，边缘层只能返回失败；如果源站端口配置错误，代理只会把错误稳定地转发出去；如果健康检查没有认证，公开入口仍可能被扫描或滥用。

更合理的分层是：边缘层负责域名、TLS、访问策略和回源控制；托管平台负责进程、端口映射和资源限制；应用负责身份校验、请求幂等和错误响应。每层都应有独立的验证证据，不能只看某个控制台上的绿色状态。

在资源极低的 Bot 环境中，最小化暴露面尤其重要。不要因为平台提供一个 NAT 端口，就把管理面板、调试接口和业务 Webhook 放在同一个入口。若必须共用端口，应使用明确的路径路由和鉴权，并禁止把 Shell 控制台、环境变量读取接口或任意代理能力暴露到公网。

## 续订与资源回收是运行时状态机

“免费”方案要求每 30 天手动续订，这意味着服务可用性不是静态属性，而是一个状态机：已创建、运行中、待续订、暂停、回收、重新创建。每个状态都可能影响 DNS、端口、存储和 Webhook。

工程上至少要保存三类信息：资源标识与区域、外部入口与地址记录、续订截止时间。续订前后分别执行健康检查，并比较公网地址是否变化。若平台重建服务会改变 NAT 端口或 IPv6 地址，就不能只做“进程启动”检查，还要同步更新 DNS 和第三方回调配置。

可以用一个定时任务做外部探测，但探测系统必须在托管环境之外。探测内容包括 DNS 解析、TCP 建连、TLS 验证和健康接口状态；告警消息只包含资源标识和失败阶段，不包含访问令牌。对于 Bot 事件，还应把事件 ID 或等价唯一键持久化，避免服务短暂中断后因重复投递造成重复操作。

## 结论：可用性是路径证据的交集

免费 Bot 托管的最大误区，是把资源领取当成部署完成。真正的上线条件是四个集合的交集：进程能持续运行，应用在正确地址监听，公网路径能够到达，第三方平台能够稳定完成协议交互。

NAT 端口适合轻量入口，但需要精确记录外部和内部端口；专用 IPv6 提供了不同的可达路径，却不能替代双栈测试和防火墙检查；私有源站或边缘代理可以减少源站暴露，却不能修复进程、端口和应用层错误。对低成本服务而言，最有价值的不是再找一个“更快的免费节点”，而是把每条访问路径做成可重复验证的证据链。

最终应以外部测试结果而不是宣传页或控制台状态决定是否可用：谁能解析、谁能连上、连到哪个地址、拿到什么响应、失败后如何恢复。只有这些问题都有明确答案，免费托管才从一个临时运行环境，变成可以被治理的 Bot 服务。
