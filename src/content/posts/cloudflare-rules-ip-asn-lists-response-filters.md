## 名单复用扩大了，策略边界没有消失

网络规则中经常出现一类重复劳动：同一组合作方网段、办公出口或自治系统，需要分别写进防火墙、缓存、重定向和响应头策略。规则分散后，名单一旦更新，各处都要同步；漏改一处，就会让不同处理阶段对同一来源作出不同判断。

Cloudflare 在 2026 年 11 月 27 日的更新中，扩大了自定义 IP 与 ASN 列表的引用范围：除请求侧已有用途外，列表现在也能用于响应侧过滤器，更新明确举例包括 Response Header Transform Rules，以及速率限制中的 response-counting expressions；同时，支持范围延伸到客户自有 CDN 规则过滤器，包括 WAF custom rules、Cache Rules、Redirect Rules 和 Request Header Transform Rules。可以把它理解为“更多地方能引用已有网络组”，而不是“所有规则都改成同一个执行阶段”或“名单自动控制所有流量”。

这一区分很重要。名单是可复用的匹配输入，规则则决定匹配发生在哪里、匹配后执行什么动作。列表扩大可见范围，有机会减少复制；它本身不会替团队统一策略，也不会替规则决定缓存、重定向或响应头的正确行为。上线评估应同时检查输入是否一致、规则是否在预期阶段执行、动作是否符合目标，而不能只看表达式是否被接受。

## 请求侧与响应侧：复用的是匹配条件，不是执行语义

可以把 CDN 规则粗略拆成两个观察点：请求抵达时的决策，以及生成或处理响应时的决策。不同产品的规则表达式可能共享网络属性，但执行时机和动作仍由各自的产品规则决定。更新所说的“响应侧”，不能简单推导成“读取响应正文里的客户端地址”；官方示例仍以 `ip.src` 和 `ip.src.asnum` 表示源地址及其 ASN 条件。这里应把它理解为：列表可在新增的响应侧规则语境中被引用，而不是这些规则的对象或动作彼此等价。

更新给出的表达式示例如下：

```text
ip.src.asnum in $partner_networks
ip.src in $office_network
```

第一条把 `partner_networks` 这个 ASN 列表用于 ASN 匹配，第二条把 `office_network` 这个 IP 列表用于源 IP 匹配。示例说明的是列表引用方式，不是完整规则，也没有说明任何匹配之后应该采取什么动作。实际部署时，应把表达式放回目标产品的规则编辑器中，并分别确认规则作用范围、优先顺序、动作和已有例外条件；不要只把示例复制到生产规则里，就认为策略已经完整。

一个稳妥的设计方法，是先把网络分组的含义写清楚，再让规则引用它。例如，名称应表达名单代表的业务对象，而不是临时的用途或某条策略：`partner_networks` 可作为合作网络的标识，`office_network` 可作为办公网络的标识。名称只是组织方式，不是访问控制本身；名单内容、维护责任和各规则的处置动作仍需单独治理。若同一列表同时被请求侧与响应侧规则使用，变更影响面也会随之扩大，名单调整不应被当作某个局部规则的私有改动。

## 先盘点范围，再做迁移

迁移前先建立一张规则清单，至少记录产品、规则名称、当前名单来源、引用表达式、执行阶段、动作、例外条件和负责人。把需要复用的网络条件与具体动作分开：名单回答“哪些来源属于这个组”，规则回答“在这个产品和阶段遇到该组时做什么”。如果原有策略把名单内容直接写进多个表达式，迁移目标可以是收敛名单引用；但若这些表达式原本包含不同例外，就不能为了减少重复而把差异一并抹掉。

随后按目标用途逐条检查可用性。更新明确提到的范围包括 WAF custom rules、Cache Rules、Redirect Rules、Request Header Transform Rules，以及响应侧的 Response Header Transform Rules 和 rate-limit response-counting expressions。名单可复用的范围增加，并不意味着每一种规则中的每一种字段、动作或表达式能力都发生了变化。尤其应把 response-counting expressions 当作更新点名的具体范围，不要自行扩展成所有速率限制规则行为都改变。

还要在变更前记录当前策略基线：规则原有条件、动作、顺序及已知例外。如果平台或团队流程提供变更前后的表达式差异记录，应保存它；没有专门工具时，也可以在变更单中逐项列出旧表达式和新表达式。关键是让评审者能够判断名单引用替换是否只改变了数据来源，还是连规则匹配范围、动作或条件也发生了变化。后者需要作为策略变更单独审查。

## 可复现的验收清单

可以把下面的清单用于变更评审和上线验收。它不是某个产品专有的命令行工具，而是对每条受影响规则都能重复执行的检查步骤：

1. **确认名单类型与名称。** 核对表达式中的列表确实是 IP 列表还是 ASN 列表，并检查拼写、维护责任和预期业务含义。更新中的示例分别使用 `$office_network` 和 `$partner_networks`；不要仅凭名称推断其中实际包含哪些网段或 ASN。
2. **确认目标产品和阶段。** 将规则归入请求侧或响应侧，再对照更新明确列出的规则产品检查引用场景。若产品或规则类型不在已核实的范围内，先不要推定支持；应以相应产品的官方文档或实际规则编辑界面确认。
3. **确认资格与限制。** Cloudflare 明确说明此次更新不改变计划可用性和配额；ASN 列表仍为 Enterprise-only，hostname lists 仍保留各产品自身的限制。先检查账户计划、现有配额及 hostname 列表的产品约束，避免把“过滤器支持列表”误读为“账户必然有权限或额度”。
4. **比较新旧条件。** 对比改动前后的表达式，确认预期只是将散落的网络条件改为引用名单，而没有意外删掉其他条件、排除项或动作。若表达式还包含其他业务逻辑，应逐项核对，不能用名单名称代替对完整条件的审查。
5. **用受控样例验证。** 在可安全评估的规则环境中，为属于名单和不属于名单的样例分别检查表达式结果，再验证目标规则实际执行的动作。响应头规则应检查预期响应头变化；缓存或重定向规则应检查对应行为；WAF 规则则应确认其处置结果。具体如何构造样例及记录结果，取决于团队可用的环境和平台能力，不能据此假定所有产品都有相同的模拟功能。
6. **检查负向与边界情况。** 验证名单更新后，未匹配来源仍按预期处理；检查空名单、名单维护延迟或错误归组时的风险，并确认规则是否会因此意外扩大或缩小匹配范围。这里关注的是策略安全边界，不代表更新改变了名单的同步机制或失效行为。
7. **保留回退信息。** 保存原表达式、名单引用变更和验收结果。若出现误匹配，回退应能恢复变更前的明确策略，而不是临时猜测名单内容或再叠加一条未经验证的补丁规则。

这套检查把“能保存表达式”与“策略结果正确”分开。前者确认语法及平台接受度，后者确认名单内容和规则动作在目标场景中产生预期结果。只有两类证据都满足，变更才算完成；没有可用于目标场景的测试条件时，应明确记录验证缺口，而不是把规则编辑成功写成策略已验收。

## 主要失败边界与工程取舍

第一种常见误判，是把能力扩展等同于计划或额度升级。此次更新明确不改变计划可用性和配额，ASN 列表仍要求 Enterprise 计划。迁移工作即使表达式设计正确，也可能被账户权限或既有配额挡住；这类问题需要先核对资格，而非反复改写表达式。

第二种误判，是把规则类型之间的限制抹平。hostname lists 仍有产品特定限制；类似地，某项列表可以出现在一个过滤器中，不代表所有过滤器都支持同一种字段、动作或使用方式。应只依据目标产品对应的官方资料判断边界，不从一条支持声明推出全产品通用能力。

第三种误判，是以为统一名单就能统一策略。一个来源组在缓存规则中可能用于选择缓存行为，在 WAF 规则中可能用于安全处置，在响应头规则中可能影响输出头；相同的名单条件并不意味着这些动作应相同。过度复用会降低维护成本，但也会扩大名单变更的影响范围。更合适的取舍是复用稳定、含义清楚的网络分组，同时保留各产品规则独立的动作、例外和验收记录。

最后要避免把一次更新描述为性能或安全效果承诺。现有材料说明了列表支持范围和不变的计划、配额限制，没有提供规则评估开销、响应时间变化或安全事件减少等数据。可以合理讨论维护负担和一致性风险，但不能据此声称上线后必然更快、更安全，或已经消除不同规则之间的偏差。

## 工程结论：共享输入，分别验收

这次变化的工程价值，不在于把 CDN 规则变成一套统一策略，而在于同一网络组有机会跨更多规则过滤器复用。它减少的是条件重复的空间，不是规则评审、账户资格检查和行为验证的责任。

因此，采用时可以坚持三条边界：名单负责表达可复用的网络分组；规则负责在具体产品和阶段定义动作；验收负责证明目标场景下的结果符合预期。更新明确覆盖的产品可以作为迁移清单的起点，未明确的能力应继续查官方产品文档，而不是从相邻规则类推。把复用范围和验证边界同时写进变更流程，才可能在减少重复维护的同时，不让共享名单成为难以追踪的全局开关。
