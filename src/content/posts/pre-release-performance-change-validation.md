## 性能变化先问：省掉了哪一步

推理优化的标题往往很醒目，真正决定它是否适合某个部署环境的，却是改动作用在哪条执行路径、需要什么前提，以及在什么条件下会失效。llama.cpp 的 b12816 是一个适合拆解的例子：发布说明称，这是一项计算图层面的变更，目标是减少状态复制步骤；在可能的情况下，内核直接从缓存读取循环状态，而不再先经由 `ggml_get_rows` 复制一份。说明还将 token 输出变快描述为“多数情况和后端”的结果，而不是所有模型、设备与工作负载的统一保证。

这里的关键不是“缓存更快”这样宽泛的直觉，而是减少数据搬运。若原路径需要先复制状态，再让后续算子读取，移除中间步骤有机会降低开销。但要让这种路径正确，读取与写入的时序必须保持一致：被读取的旧状态不能在消费前就被覆盖。发布说明特别指出，RWKV6/7 的改动会在覆盖之前先读取旧状态。也就是说，优化对象虽是计算图和数据访问路径，正确性仍然取决于状态生命周期。

这类改变不应被简化成“少一次复制，所以一定更快”。它影响的是一条特定的执行路径；当状态布局、图复用方式、后端调度或工作负载不同，收益也可能不同。发布说明中的“多数情况”是项目给出的方向性描述，不是某台机器的基准测试，也没有提供可直接套用到所有环境的加速比例。

## 原地读取并不意味着不再需要图检查

直接从缓存读取状态，可能改变计算图对状态数据的访问方式。b12816 的发布说明同时提到增加了图复用检查，用于跟踪状态是否采用原地读取。这一细节很重要：图复用并非只看“上次已经构建过图”，还要确保当前图所采用的状态访问方式，与可以安全复用的条件相符。

说明还记录了一个具体边界：在 `GGML_SCHED_NO_REALLOC` 条件下，Vulkan 和 Metal 曾出现失败；随后相关处理调整为，不论状态是原地读取还是移动，计算图都保持相同形状。对工程实践的启发是，性能路径的优化与图结构稳定性、后端约束可能紧密相关。一个改动即使在常见配置下通过，也不能据此推断在特殊内存分配策略或所有后端上都通过。

在现有材料范围内，可以确认的是这些已披露的机制与问题，不应进一步推断失败的完整根因、所有受影响设备，或修复后的覆盖范围。遇到类似预发布说明，最稳妥的阅读方式是把“优化做了什么”“正确性如何维持”“哪些条件曾出问题”分开记录。它们回答的是不同问题：前者解释收益来源，第二项涉及语义正确性，第三项提示验证边界。

## 把版本、构建和模型固定下来

验收时，先把候选版本与基线版本分开，避免将模型、编译选项或机器状态的变化误认为代码收益。b12816 的发布页将其标记为预发布版本，因此用于评估时应把它当作候选，而不是默认可替换稳定版本。以下命令展示固定候选版本的基本做法；构建前应查看项目针对当前平台的官方说明，并保存实际使用的编译选项：

```sh
git clone https://github.com/ggml-org/llama.cpp.git
cd llama.cpp
git checkout b12816
cmake -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build --config Release -j
```

然后先检查当前构建提供的基准工具选项，再针对同一个模型和固定参数运行：

```sh
./build/bin/llama-bench --help
./build/bin/llama-bench -m /path/to/model.gguf -p 512 -n 128 -r 5
```

这只是一个可执行的起点，不是对所有平台都适用的完整验收方案。应记录仓库提交或 tag、构建类型、编译器与后端、设备、模型文件校验值、量化版本、提示词长度、生成长度和重复次数。尤其要保证基线与候选使用同一份模型文件和同一组参数；只在命令行上看起来相似，不足以证明输入条件相同。

对于有不同后端的项目，应分别构建和运行对应后端，不要拿 CPU 上的结果替代 Vulkan 或 Metal 的结论。若部署启用了特殊调度或分配选项，应把它们作为独立测试维度；b12816 的说明明确提到了 `GGML_SCHED_NO_REALLOC` 下的 Vulkan 与 Metal 问题，因此忽略这一配置，会漏掉发布说明本身已经提示的风险边界。

## 用正确性和性能两道门验收

第一道门是正确性。对固定输入，检查生成是否稳定、是否出现异常退出或数值问题，并覆盖能够触发循环状态更新的实际工作负载。对于使用 RWKV6/7 的情形，尤其应把连续生成纳入测试，因为改动涉及旧状态读取和覆盖时序。测试应有基线结果作对照，而不是只确认候选版本能够启动。

第二道门才是性能。至少重复运行多轮，并同时看整体趋势和离散程度；如果只有单次运行更快，或不同轮次波动大到淹没差异，就不应把它包装成稳定收益。测试期间尽量维持相同设备状态，避免并发负载、热降频或后台任务成为混杂变量。`llama-bench` 可以帮助固定模型与基准参数，但它不能替代贴近实际业务的请求形态测试：真实请求的上下文长度、批处理和并发情况，都可能改变瓶颈。

还要检查生成速度以外的代价。计算图变化可能影响初始化、图复用、内存占用或其他阶段；如果业务关注首 token 延迟、长上下文吞吐或并发容量，就应分别测量相应指标，而不是用单一的 token 输出速度代表全部体验。发布说明所说的是 token 输出在多数情况和后端有所加快，材料没有给出对这些其他指标的普遍保证。

可以把最小验收表写成四项：基线与候选是否使用同一模型和参数；目标后端与关键配置是否都覆盖；正确性检查是否通过；性能差异是否在多轮和真实负载中持续出现。任一项缺失，都应把结果标为“未验证”或“仅在指定条件下观察到”，而不是笼统地写“性能已提升”。

## 发布标签不是部署结论

证据等级同样影响如何表达结论。b12816 的页面明确标记为预发布；这可以支持“项目发布了该候选版本”和“发布说明列出了这些改动”，却不能单凭标签证明它已适合所有生产环境。类似地，Qwen Code 的 TypeScript SDK 发布说明会标出该 SDK 所捆绑的 CLI 版本，说明消费 SDK 的人还需要核对实际包含的运行时，而不能只看外层包的版本号。版本标签、包版本和运行时版本是不同的识别对象。

因此，性能结论最好带上条件：在哪个提交、什么后端、什么模型、什么参数下，观察到什么变化；哪些路径没有测试；是否覆盖预发布版本提到的特殊配置。条件不是给结论“打折”，而是让别人能复现并判断结果是否适用于自己的环境。

## 工程取舍：先缩小承诺，再扩大覆盖

b12816 展示的工程取舍很典型：为了减少状态复制，改变读取路径；为了保持状态语义，调整读取与覆盖顺序；为了兼容图复用和后端约束，再增加检查并保持图形状稳定。性能优化不是孤立的一行快路径，而是一组必须一起成立的正确性条件。

团队评估此类改动时，可以先在受控环境里验证最小假设，再按实际使用的后端和配置逐步扩大覆盖。若目标环境启用特殊调度策略，就优先覆盖它；若模型并不使用相关循环状态路径，基准结果也不能证明优化对该模型有意义。出现回归时，应保留旧版本作为可比较基线，并根据证据决定是否升级，而不要让“预发布写了提速”替代风险判断。

最终结论应比发布标题更窄、比一次跑分更可复现：指出改动机制，限定适用条件，给出正确性和性能验证结果，并明确尚未覆盖的边界。只有这样，“可能更快”才会变成一项可审查、可复测、可撤回的工程决策。
