## 这不是“给数据库加一个向量接口”

Cloudflare 在 2026 年 11 月 12 日的更新中宣布，AI Search 可以把 D1 数据库作为数据源。当前材料明确标注为 Beta：系统执行用户提供的只读查询，并把查询返回的每一行建立为一个独立文档；随后通过计划同步，让索引随着行的新增、修改和删除保持更新。

这个描述里真正重要的不是“D1”三个字，而是数据边界发生了变化。传统 RAG 往往先把数据库内容导出，再交给切分、嵌入和索引流水线。D1 数据源则把“哪些行可以进入检索系统”前移到 SQL，把查询结果当成索引输入。数据库查询因此不只是取数逻辑，也成为检索系统的内容授权边界、字段投影边界和更新入口。

这类能力最容易被误解成“AI 可以直接读数据库”。更准确的说法是：AI Search 读取一个受配置约束的只读查询结果，并把结果转换成检索文档。它不是任意 SQL 控制台，也不是让模型获得 D1 的写权限。这个区分决定了后续的权限设计、数据建模和验收方式。

## 一行数据为什么会成为一个文档

官方示例使用如下查询形态：

```sql
SELECT
  article_id AS id,
  title,
  content,
  category AS meta_category
FROM articles
WHERE published = 1
```

这里至少有四个工程信号。

第一，查询应该显式投影字段，而不是依赖 `SELECT *`。检索系统需要稳定的字段集合，标题和正文用于形成可检索内容，分类则作为元数据参与过滤或展示。显式列名可以避免表结构增加字段后，索引内容在没有评审的情况下悄然变化。

第二，`article_id AS id` 不是装饰。它把业务实体的稳定标识带入索引输入。没有稳定 ID，更新和删除就难以准确对应到已经建立的文档。即使材料没有进一步承诺内部实现细节，工程上也应把 ID 视为数据契约的一部分：它必须非空、稳定，并且在业务生命周期内不被复用。

第三，`WHERE published = 1` 把发布状态放在源查询中，而不是只依赖前端隐藏结果。未发布内容如果进入索引，就可能在用户查询时被召回；仅在展示阶段过滤，无法替代索引入口处的内容门禁。状态条件应与业务发布规则一起评审。

第四，元数据需要有明确命名。示例把 `category` 映射为 `meta_category`，说明分类不是普通正文的一部分，而是需要被识别为元数据的字段。实际项目中，应把可过滤字段、展示字段和全文字段分别列出，避免把内部备注、排序权重或管理字段误送进检索语料。

因此，数据库表不应直接等同于知识库。适合作为数据源的查询，应该像一个面向检索的只读视图：字段少而明确，身份稳定，内容已完成发布过滤，并且能够解释每一列为什么需要进入索引。

## 同步机制改变的是“新鲜度责任”

AI Search 的 D1 数据源支持计划同步，官方描述覆盖新增、修改和删除三类行变化。它解决的是索引维护中的重复劳动，但不等于实时一致性，也不应被表述为数据库写入后立即可搜。

应用设计需要先区分三种时间：数据库提交时间、索引同步时间和用户查询时间。用户看到的结果取决于第三个时间点之前，前两个阶段是否都已完成。若文章刚刚发布，数据库里的 `published` 已经变为 `1`，但同步尚未完成，检索结果暂时不可见是合理的 Beta 系统边界，而不是 SQL 查询失败。

删除同样需要单独验收。很多系统只测试“新增后能搜到”，却不验证取消发布或删除后是否从结果中消失。官方材料明确提到索引会随行的删除保持更新，因此验收必须覆盖删除路径，而不是只检查新增与修改。对有缓存的应用，还要区分索引已经移除和页面仍然展示旧缓存这两个不同问题。

同步设计还会带来内容版本问题。假设一条记录在短时间内连续修改，系统最终需要让索引收敛到某个较新的版本；但材料没有承诺同步延迟、排序规则或冲突处理细节，不能把这些行为写成确定能力。工程上更稳妥的做法是：把可接受的新鲜度写成业务目标，在测试环境用可观测的时间戳记录“数据库变更—可检索”的间隔，并把超时视为需要调查的同步故障，而不是由模型自行补偿。

## 三种创建入口，核心仍是同一个数据契约

官方更新列出三种创建 D1-backed 实例的入口：控制台、REST API 和 Workers binding。入口不同，验证重点不应不同。无论通过哪种方式创建，都应该最终核对实例 ID、数据源数据库、服务令牌标识、查询文本和同步状态。

REST API 示例可以作为配置审查的起点：

```bash
curl -X POST \
  "https://api.cloudflare.com/client/v4/accounts/<ACCOUNT_ID>/ai-search/namespaces/default/instances" \
  -H "Authorization: Bearer <API_TOKEN>" \
  -H "Content-Type: application/json" \
  --data '{
    "id": "help-center",
    "type": "d1",
    "source": "<D1_DATABASE_ID>",
    "token_id": "<SERVICE_TOKEN_ID>",
    "source_params": {
      "d1": {
        "query": "SELECT article_id AS id, title, content, category AS meta_category FROM articles WHERE published = 1"
      }
    }
  }'
```

这段命令展示了几个配置对象之间的关系：实例有自己的业务标识，`source` 指向 D1 数据库，`token_id` 指向服务令牌，查询则位于 D1 专用的 `source_params` 中。它没有把真实账号、数据库或令牌写死在命令里，这种占位符形式也更适合进入部署脚本模板。

配置时应特别避免把拥有过宽权限的长期令牌直接塞进自动化环境。材料明确要求的是服务令牌标识，但没有给出令牌权限清单，因此不能擅自宣称某个权限集合就是官方要求。可以做的是建立最小权限原则：令牌只应满足该数据源读取所需范围；令牌生命周期、轮换流程和失败告警则由项目自己的凭据治理负责。

如果团队使用 Workers binding，仍然需要把查询和数据库 ID 当成可审查配置，而不是把它们隐藏在代码生成结果中。控制台适合探索和初始配置，REST API 适合纳入流水线，binding 适合应用侧统一管理。三者是操作入口的差异，不是数据正确性的替代品。

## 一套可复现的验收顺序

验收不要从“问一个自然语言问题”开始。自然语言召回结果包含模型、分词和排序等变量，无法单独证明数据源配置正确。更可靠的顺序是从源数据一路向上检查。

**第一步：验证查询集合。** 在 D1 中准备至少三条记录：一条已发布、一条未发布、一条随后会被删除或取消发布。直接执行与 AI Search 配置相同的只读查询，确认返回的列名、ID、正文和元数据符合契约。未发布记录不能出现在结果中。

**第二步：验证标识唯一性。** 检查 `id` 是否非空、是否重复、是否会因业务迁移而变化。若同一个业务实体可能产生多个版本，应先决定是覆盖旧文档还是把版本当成独立文档；不能把这个决定留给同步系统猜测。

**第三步：验证创建配置。** 通过选定入口创建实例后，逐项核对实例 ID、类型是否为 D1、源数据库是否正确、服务令牌是否为预期标识，以及查询是否是经过评审的版本。测试环境尤其要防止把生产数据库 ID 误填进去。

**第四步：验证首次可见性。** 用一个具有唯一标题或唯一短语的已发布记录作为探针。记录数据库中写入完成的时间，再等待索引同步，使用检索接口或产品提供的查询方式寻找该短语。这里验证的是“数据最终进入索引”，不是模型是否能回答复杂问题。

**第五步：验证修改。** 修改同一条记录的标题和正文，加入新的唯一短语。确认新的短语最终可检索，并检查旧内容是否仍然被召回。若新旧内容同时出现，应进一步判断是索引收敛窗口、缓存，还是 ID 设计造成了重复文档。

**第六步：验证删除与取消发布。** 将记录删除，或把发布条件改为不满足，再执行相同的查询验证。删除路径必须单独记录结果，因为“新增和修改正常”不能推出“删除正常”。

**第七步：验证权限失败。** 使用无权访问目标数据库的测试令牌，确认实例创建或同步会明确失败，而不是返回一个看似成功但永远为空的索引。错误信息、状态和告警都应保留在运行记录中。

## 失败边界决定它适合什么内容

D1-backed AI Search 最适合结构化程度较高、发布状态明确、可以用稳定主键表示的内容，例如帮助中心文章、产品目录或经过审核的知识条目。它尤其适合已经把内容维护在 D1 中的应用，因为查询本身可以复用业务的发布条件，并减少额外导出管道。

它不天然适合所有数据。需要复杂跨表拼接、强实时一致性、细粒度用户权限过滤或大量临时计算的数据，都应先评估查询结果是否能稳定地表达访问边界。材料只说明“每个查询返回行成为一个文档”，并没有说明 AI Search 会替应用自动完成每个用户的行级授权。因此，不能因为索引来自数据库，就推断查询者自动继承了业务系统的全部权限。

另一个边界是内容粒度。一行成为一个文档意味着表中一行过大时，检索质量、更新成本和结果可读性都可能受影响；一行过小时，上下文又可能被拆散。官方材料没有给出长度限制或切分算法，工程上不应编造具体阈值。应通过代表性数据集评估：用户问题能否命中正确行，返回的标题是否足以解释结果，正文是否包含回答所需上下文，以及修改一列是否会导致整行文档重新处理。

“Beta”还意味着生产承诺需要更谨慎。Beta 能力可以用于受控试点，但上线前应明确回退方案：保留原有检索源、允许关闭该实例、保留可重建的查询配置，并为同步延迟、权限失败和索引内容异常设置人工处理路径。不要把一个新数据源直接绑定到不可回退的高风险回答流程。

## 原创结论：SQL 是检索系统的第一道治理层

D1 接入 AI Search 的价值，不只是少写一个数据导出脚本。更重要的是，它把“什么内容有资格被检索”变成可以评审、版本化和复现的 SQL。查询里的字段投影决定内容形状，发布条件决定纳入范围，稳定 ID 决定更新与删除的可追踪性；计划同步则把数据库变化传递给索引，但不会替工程师定义一致性目标。

因此，最小可行方案不是“创建实例，然后问模型一个问题”，而是四件事同时成立：源查询可读且可审查，结果行具有稳定身份，新增修改删除都能验证，权限和回退路径都被明确记录。只有当这四件事形成闭环，数据库才真正成为可治理的检索源，而不是一个隐藏在 AI 功能背后的数据出口。

对团队而言，最值得保存的资产也不是某次控制台点击，而是那份经过评审的查询契约、测试数据、同步延迟记录和失败样本。未来无论更换模型、调整检索策略，还是把同一数据迁移到另一种索引系统，这些证据仍然能回答最关键的问题：索引里究竟有什么，它为什么在那里，以及当源数据改变后，系统多久、以什么方式恢复一致。
