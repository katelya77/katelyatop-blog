## 一个测试选择器，为什么值得单独写一篇文章

vLLM 的 `v0.33.0rc1` 发布记录中，唯一明确列出的变更是“修复 DGX Spark 上过时的 NVFP4 decode 测试选择器”。它不是一个醒目的新 API，也没有承诺吞吐提升，却直接触及推理框架发布中最容易被忽略的一层：测试系统到底有没有找到应该运行的测试。

测试选择器通常负责把测试名称、硬件条件、后端能力和 CI 标记组合起来。选择器过时，可能出现两种相反结果：本来应该执行的测试被排除，或者旧名称仍然被筛选器引用，导致 CI 报告“没有匹配测试”。前者会制造假绿，后者会制造假红。两者都不是单纯的测试脚本问题，而是发布证据链断裂。

这也是为什么预发布版本不能只看 `rc1`、提交时间或变更数量。OpenAI Codex 的 `0.166.0-alpha.6` 发布页明确标注为 Pre-release，并显示该版本由自动化流程发布；vLLM 的记录同样是候选版本。它们能证明“某个候选构建存在”，却不能单独证明目标硬件上的完整推理路径已经稳定。

## 从测试选择到硬件路径：要验证的到底是什么

NVFP4 decode 测试至少涉及四个层次。第一层是测试是否被发现：名称、标签和筛选表达式必须匹配当前代码。第二层是硬件是否满足前置条件：目标设备、驱动、运行时和编译产物需要处在可支持范围内。第三层是路径是否真的走到了 NVFP4 decode，而不是因为能力探测失败后退回普通精度或另一条内核路径。第四层才是结果是否正确、性能是否符合预期。

这四层不能用一个“测试通过”替代。一个测试被选择并启动，只能说明发现阶段成功；进程返回 0，通常也只能说明该测试认为自己完成了。若测试因为能力检测失败而跳过，CI 仍可能显示整体成功；若输入规模太小，功能正确也不代表实际服务负载可用。

因此，针对候选版本的验证应先建立路径矩阵，而不是直接执行一条模糊的全量命令：

| 层次 | 要回答的问题 | 最小证据 |
| --- | --- | --- |
| 发现 | 目标测试是否被选择器找到 | 选择器输出、收集列表、测试数量 |
| 环境 | 当前机器是否具备前置条件 | GPU、驱动、运行时、构建信息 |
| 执行 | 是否真的走 NVFP4 decode 路径 | 后端日志、内核或算子标识、跳过原因 |
| 结果 | 输出与性能是否满足目标 | 正确性断言、延迟、吞吐、错误率 |

vLLM 这条发布记录至少提醒我们：第一层发生变化时，后面三层的结论都需要重新确认。测试代码没有改，不代表测试集合仍然有效。

## 一套可复现的候选版本检查流程

下面的流程不假设某个特定安装方式，也不把社区帖子或搜索摘要当作兼容性证明。命令中的测试名称和筛选参数应以目标提交的仓库文档、测试目录与 CI 配置为准；如果仓库没有公开对应入口，就不能自行声称已经完成验证。

### 1. 固定候选版本和环境指纹

先记录源码版本、Python 版本、GPU 识别结果和驱动信息。重点不是把信息贴到日志里，而是让后续失败可以归因到同一环境：

```bash
git rev-parse HEAD
python --version
python -m pip show vllm
nvidia-smi --query-gpu=name,driver_version,memory.total --format=csv
```

如果使用容器，还要额外保存镜像摘要、容器启动参数和 GPU 透传配置。候选版本验证不应使用“当前目录代码大概就是这个版本”这样的隐含前提。`rc1` 是发布标签，不等于你的工作树、已安装包和正在运行的服务一定来自同一个提交。

### 2. 先收集测试，再执行测试

对于任何依赖选择器的测试框架，先运行收集模式或等价命令，确认目标测试实际出现。一个通用的 pytest 形式如下，具体路径必须按项目仓库调整：

```bash
pytest --collect-only -q path/to/nvfp4_tests
pytest --collect-only -q -k 'decode and nvfp4'
```

需要保存三类输出：收集到的测试数量、目标关键字是否命中、未命中时框架给出的原因。若结果为零，不能直接把它解释为“当前硬件不支持”；也可能是测试重命名、标签迁移、路径变化或选择器仍引用旧标识。vLLM 的发布记录把“stale selector”单独列为修复对象，正说明测试发现本身必须被当成发布接口维护。

### 3. 区分跳过、失败和未执行

验证脚本应把三种状态分开记录：

- **未收集到**：选择器没有找到目标测试，属于发现链问题。
- **已收集但跳过**：测试被发现，但前置条件不满足，需要保存跳过原因。
- **已执行但失败**：代码路径启动后出现断言、运行时或资源错误。

不要用“没有报错”替代状态判断。对于量化和硬件后端，跳过往往比失败更难观察，因为它可能让整体 CI 看起来正常。工程上可以要求目标测试数量必须大于零，并对允许跳过的条件建立白名单；不在白名单中的跳过直接阻断候选版本验收。

### 4. 记录路径证据，而非只记录最终数字

如果测试宣称覆盖 NVFP4 decode，应保存能证明路径选择的日志。日志至少包含：设备识别结果、量化配置、后端选择、是否发生 fallback、测试输入形状和最终状态。只保存“延迟 8 ms”没有复查价值，因为同一数字可能来自不同实现路径。

性能数据也必须带上上下文。固定模型、输入长度、输出长度、并发度和预热次数；分别记录首 token 延迟、后续 token 延迟与总吞吐。若这些条件没有在材料或项目文档中定义，就只能把结果称为一次局部观测，不能外推为版本级性能结论。

## 失败边界：哪些结论不能从 rc1 推出来

第一，不能从测试选择器修复推出 NVFP4 在所有 GPU 上都可用。发布记录只明确提到 DGX Spark 上的选择器问题，证据范围不能扩展到其他设备、驱动或云实例。

第二，不能从候选版本标签推出生产稳定性。`rc1` 的含义是发布候选，不是长期支持承诺。Alpha 版本更不能被当作正式发布；Codex `0.166.0-alpha.6` 的页面明确显示 Pre-release，这类证据适合用于说明版本状态，不适合证明 API、性能或兼容性已经稳定。

第三，不能从选择器修复推出内核正确性。选择器只解决“应该运行什么”的问题，不能替代数值正确性、边界形状、长上下文、并发和故障恢复测试。

第四，不能把 CI 通过等同于服务可用。CI 可能使用较小样本、单卡、固定输入和理想资源；线上还会遇到显存碎片、请求排队、模型加载失败、驱动差异以及动态批处理。候选版本应先通过功能门槛，再进入受控流量验证，而不是直接替换生产镜像。

## 把修复变成发布门禁

一个可执行的发布门禁可以分成三道：

**发现门禁**：目标测试必须被收集，收集数量与基线相比出现异常时阻断发布；测试重命名必须同步更新选择器、文档和 CI 配置。

**路径门禁**：测试日志必须证明目标硬件和目标量化路径被启用。发生 fallback、能力探测失败或静默跳过时，状态应为“不确定”，而不是成功。

**结果门禁**：正确性测试与性能测试分离。正确性先验证输出、边界输入和错误处理；性能再在固定环境中比较延迟、吞吐和显存。没有可比基线时，不发布“更快”结论。

这三道门禁的价值在于把“测试有没有跑”从隐含假设变成显式数据。未来即使测试名称再次变化，流水线也能通过收集数量、跳过原因和路径日志发现异常，而不是等到用户报告某个硬件后端失效。

## 原创结论：预发布推理软件的最小可信单元不是版本，而是证据闭环

vLLM 的 NVFP4 选择器修复看起来很小，实际暴露的是发布工程的核心事实：推理框架的行为由源码、测试选择器、硬件探测、后端实现和运行参数共同决定。版本号只标记了一个时间点，不能替代这些对象之间的对应关系。

因此，判断一个候选版本是否值得继续，不应只问“它发布了吗”，而应问四个问题：目标测试是否被找到，目标路径是否被执行，失败或跳过是否可解释，结果是否能在同一环境中复现。四个问题全部有证据，才形成最小可信闭环；缺一项，结论就应该降级为“待验证”。

这套方法也适用于其他 AI 工具链。面对 Alpha、RC 或快速迭代的推理运行时，最可靠的升级策略不是追逐最新标签，而是把测试选择器、环境指纹和路径日志纳入版本验收。软件真正可用的边界，往往不在发布说明里最显眼的功能，而在那些看似琐碎、却决定测试是否真的运行的连接处。
