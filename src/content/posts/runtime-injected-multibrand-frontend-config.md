## 先把问题从“页面显示错误”改写成配置时序问题

社区里出现过 WorkBuddy 补偿积分的领取入口，材料指向的是登录后的个人中心页面，而不是一个公开的产品介绍页。这个差异很重要：登录后页面的品牌、区域、用户状态和可用功能，往往要等运行环境、请求域名以及用户会话都确定之后才能计算。把这些信息提前写死在静态 HTML 中，看起来有利于首屏和搜索引擎，实际上可能把“默认值”误当成“真实配置”。

材料 S8 直接暴露了这类页面的实现线索：页面由 `usercenter-inject-common-html` 在运行时注入，bootstrap 会根据 `brand(hostname) × region(IS_INTERNATIONAL_EDITION)` 作出判断；个人中心不再提供静态 SEO 出口，因为静态注入拿不到 hostname，可能写错品牌；`lang="zh-CN"` 只是运行时覆盖前的安全默认值，国际版再改成 `en-US`。这不是某个文案字段的修补，而是配置计算时机的调整。

可以把问题抽象成一个函数：

```text
页面配置 = f(hostname, region, runtime environment, product features, user session)
```

如果其中任意输入只能在浏览器启动、边缘代理转发或用户登录后获得，那么构建阶段生成的静态结果就只能是候选值，而不能是最终值。多品牌系统最常见的错误，并不是“没有配置”，而是配置存在于错误的生命周期。

## 运行时注入到底解决了哪些架构矛盾

### 1. hostname 是路由事实，不是构建常量

同一套前端产物可能服务多个域名。域名既可能决定品牌，也可能影响 API 前缀、Cookie 范围、帮助中心地址和埋点归属。构建时无法可靠知道用户最终通过哪个 hostname 进入页面，尤其是前置 CDN、反向代理或多区域入口存在时。

因此，品牌判断至少应该放在请求或浏览器运行时，而不是把某个品牌写进 bundle。材料中强调判定逻辑必须和 `src/utils/brand.ts` 的 `getBrand()` 保持一致，这揭示了第二个关键点：运行时注入不是随意插入一段脚本，而是要复用唯一的品牌判定规则。否则服务端、注入插件和客户端各自判断一次，最终会出现页面标题是 A 品牌、接口地址是 B 品牌、埋点又归到 C 品牌的分裂状态。

### 2. region 不等于浏览器语言

`IS_INTERNATIONAL_EDITION` 是区域或版本判定，`lang` 是界面语言。二者经常相关，但不是同一个概念。材料明确说明中文只是安全默认值，国际版由 bootstrap 改写为英文，这种设计至少保留了一个确定的启动状态，同时允许运行时配置覆盖。

工程上应避免把浏览器 `Accept-Language` 直接当作产品区域。语言可以由用户偏好决定，区域可能由访问域名、部署环境、合规策略或产品开关决定。将它们混为一谈，会让用户切换语言时意外切换 API、价格、功能甚至数据区域。

### 3. 环境变量需要分层，而不是全部暴露

S8 列出了由插件注入的 `APP_EDITION`、`RUN_ENV`、`PRODUCT_FEATURES`、`IS_INTERNATIONAL_EDITION`、`__toCdnUrl` 和 `qcStat`。这类字段至少可分成三组：

- 产品决策：版本、区域、功能开关；
- 运行地址：CDN 或静态资源转换函数；
- 观测能力：统计或质量采集入口。

它们都在浏览器侧可见，因此不能放入密钥、签名材料或权限判断依据。前端功能开关只能控制展示和交互，不能替代服务端授权。一个按钮在国际版隐藏，不代表对应 API 在服务端不可调用；真正的权限仍应由后端会话和接口策略决定。

## 用命令把“注入是否正确”变成可验证检查

这类问题不能只靠肉眼打开页面。即使没有完整部署环境，也可以围绕 HTML、脚本和运行时状态建立最小检查流程。下面的命令只读地检查响应头、HTML 中的注入痕迹以及关键字段，不依赖修改线上数据：

```bash
curl -sS -D /tmp/workbuddy.headers \
  -o /tmp/workbuddy.html \
  'https://www.workbuddy.cn/profile/plans-usage'

sed -n '1,40p' /tmp/workbuddy.headers

grep -nE 'usercenter-inject-common-html|APP_EDITION|RUN_ENV|PRODUCT_FEATURES|IS_INTERNATIONAL_EDITION|__toCdnUrl|qcStat' \
  /tmp/workbuddy.html
```

如果页面必须登录，未认证响应不应被误判为最终页面。检查清单可以分成四层：

1. **入口层**：不同 hostname 是否进入预期品牌；重定向后是否保留正确的区域和协议。
2. **注入层**：bootstrap 是否在业务脚本之前完成；字段是否存在、类型是否符合约定；默认值是否只承担安全兜底作用。
3. **消费层**：`getBrand()`、语言初始化、CDN 地址生成和功能开关是否读取同一个配置源；是否存在旧的静态常量覆盖运行时值。
4. **服务层**：前端隐藏功能后，未授权请求是否仍被服务端拒绝；切换 hostname 或区域是否造成跨品牌 Cookie 和缓存污染。

对静态资源，还应检查缓存键。若 HTML 或注入脚本的结果依赖 hostname，却被 CDN 仅按路径缓存，那么第一个访问者的品牌配置可能被复用给后续访问者。可以用响应头和内容摘要做简单比对：

```bash
for host in www.workbuddy.cn intl.workbuddy.cn; do
  curl -sS -H "Host: $host" \
    -D "/tmp/${host}.headers" \
    -o "/tmp/${host}.html" \
    'https://www.workbuddy.cn/profile/plans-usage'
  sha256sum "/tmp/${host}.html"
done
```

这条命令不等于完整的 CDN 验证，但能快速发现“不同入口返回完全相同 HTML”是否值得进一步调查。实际检查时还要记录 `Cache-Control`、`Vary`、`ETag` 和代理层的缓存命中头，不能只看摘要是否不同。

## 失败边界：运行时注入不是天然更安全

运行时方案把错误从构建阶段推迟到了启动阶段，因此必须明确失败策略。

### 注入脚本加载失败

如果公共注入插件不可用，页面不能静默地继续使用一组看似完整的旧配置。建议保留最小安全默认值，例如基础语言和只读错误页；对于 API 地址、品牌归属和支付相关功能，应显式阻断或降级，并在质量采集系统记录失败原因。默认值的作用是让错误可解释，而不是伪装成成功。

### 字段缺失或类型错误

`PRODUCT_FEATURES` 如果从字符串、JSON 和布尔值之间无约束转换，前端很容易把空字符串、`"false"` 或 `undefined` 当成真值。启动阶段应做 schema 校验，失败时输出字段名、版本和请求入口，但不要把可能含用户信息的完整会话内容写进日志。

### 品牌判定不一致

材料要求插件逻辑与 `getBrand()` 保持一致，说明重复实现本身就是风险。更稳妥的做法是让判定逻辑只有一个实现，服务端注入和客户端消费都围绕同一份可测试模块构建；如果技术边界迫使两端各自实现，也应建立表驱动测试，覆盖主域名、国际域名、未知域名、端口和反向代理头。

### 预渲染与搜索需求冲突

放弃个人中心的静态 SEO 出口，并不等于所有页面都不能预渲染。公开文档、产品介绍和帮助页可以使用静态或服务端渲染；登录后的用户中心则应优先保证身份、品牌和区域一致性。关键是按数据敏感性和配置时序划分页面，而不是给整个站点套用同一种渲染策略。

## 一套更可维护的配置契约

一个可落地的运行时配置对象，至少应包含版本号、品牌、区域、语言默认值、环境、功能集合和资源地址，但不要把它设计成任意键值字典。推荐将它视为有版本的契约：

```json
{
  "schemaVersion": 1,
  "brand": "resolved-at-runtime",
  "region": "resolved-at-runtime",
  "locale": "zh-CN",
  "runEnv": "production",
  "features": {},
  "cdn": {}
}
```

这里的结构只是契约示意，不是对材料中线上值的补充断言。真正重要的是三条边界：第一，构建产物不保存依赖 hostname 的最终品牌；第二，运行时配置只负责产品呈现和资源选择，不能充当授权系统；第三，配置需要可观测，至少能回答“来自哪个入口、采用了哪个版本、在哪一步失败”。

验证应覆盖正常和异常两条路径：正常路径确认中文入口、国际入口和已登录用户得到各自一致的品牌与语言；异常路径人为阻断注入脚本、删除字段、传入未知 hostname，并确认页面不会把错误配置当成成功状态。每次发布还应保留 HTML 与 bootstrap 的版本关联，便于把“页面显示错了”定位到构建、注入、缓存还是消费端。

## 原创结论：多品牌前端的核心不是配置中心，而是配置时序

从这份材料能得到的最有价值结论，不是某个页面用了哪一个插件，而是多品牌系统必须回答三个先后顺序问题：谁先知道 hostname，谁负责决定区域，谁最终有权覆盖默认值。答案如果不清晰，静态 HTML、客户端 bootstrap、业务模块和服务端授权就会互相覆盖；即使每一段代码单独看都合理，组合起来仍会产生品牌串线、语言闪烁、缓存污染和权限错觉。

因此，工程评审不应只问“有没有运行时配置”，而应要求一张配置时序图：构建阶段生成什么，入口层注入什么，浏览器启动时校验什么，服务端最终裁决什么，异常时显示什么。对于公开页面，可以为性能保留预渲染；对于登录后的个人中心，应优先选择可验证的一致性。把默认值限制在安全范围，把最终决策放到拥有真实上下文的生命周期，才是运行时注入真正的工程价值。
