## 一个容易被名字误导的功能

Ollama v0.40.17 最值得关注的变化之一，是 `ollama launch claude` 增加了对 Claude Code 延迟工具加载的支持。发布说明没有把它描述成“更智能”，而是明确写成：MCP 工具会在需要时才加载，而不是一次性全部载入。

这个描述很容易被理解成性能优化，也容易被理解成上下文窗口可以无限使用。但对工程而言，它同时涉及三个边界：工具发现何时发生、调用前是否已经完成校验，以及失效的工具是属于启动配置问题还是运行时问题。

Claude Code v2.1.330 的发布说明也值得放在同一组证据里。它新增了组织登录支持、内置图表能力和 MCP 指标展示入口，并补充了自托管 runner 的启动目录与插件加载行为。也就是说，所谓“Agent 可以使用工具”，已经不是一个单一开关，而是由登录身份、运行目录、插件发现、MCP 注册和指标反馈共同组成的状态链。

本文的证据等级是明确的：上述结论来自 Ollama 与 Anthropic 的公开 GitHub Release，属于项目发布事实，不是社区传闻。真正的本地运行效果仍需以具体机器、模型和 MCP 配置验证，不能仅凭 Release 说明推导。

## 延迟加载解决的不是模型能力，而是装载成本

传统的 MCP 接入方式，通常会在会话启动时向模型提供较完整的工具目录：名称、参数、说明和可调用约束。工具数量少时，这很直接；工具数量多时，描述会占用上下文、增加提示词处理成本，并让模型在无关工具之间做选择。

延迟加载的直观变化是：会话不再预先把所有工具的完整定义都交给模型，而是在任务确实需要工具时再发现或加载。它保护的并不只是上下文长度，还包括启动阶段的工具依赖：一个暂时不可用的工具，理论上不应该立刻把整个会话判定为失败。

不过，延迟加载并不会消除工具调用本身需要的代价。模型仍然需要知道如何发现工具、选择工具以及形成参数；工具服务器仍然需要启动、响应或读取状态；失败仍然可能发生，只是发生位置从会话初始化阶段移到了任务执行阶段。

因此更准确的技术模型是：

1. Agent 先建立模型与会话的运行上下文。
2. MCP 只暴露必要的发现入口或已加载工具集合。
3. 模型在任务需要时请求工具发现或工具能力。
4. 工具进程、网关或远程服务完成解析与调用。
5. 返回结果进入模型上下文，再决定下一步。

这个状态链里没有哪一步天然可靠。工具目录可能过时，参数可能不兼容，MCP 服务可能启动失败，模型也可能在加载工具前就生成了错误调用。因此，“延迟加载”应被视为一种加载策略，而不是自动获得可靠性的机制。

## 一个可复现的起点

公开 Release 给出的明确命令是：

```bash
ollama launch claude
ollama run inkling-2-mini
```

第一条用于启动 Claude Code，并使用 Ollama 的集成方式；第二条用于直接运行 `inkling-2-mini`。根据 Ollama v0.40.17 的说明，`inkling-2-mini` 在该版本中支持 Apple silicon，并会在未来提供 PC 支持。因此，第二条命令不应被扩展成当前所有平台都可运行的通用示例。

一个保守的本地验证流程可以这样组织：

```bash
# 1. 检查 Ollama 与目标模型是否可用
ollama --version
ollama list

# 2. 先验证模型可以直接加载
ollama run inkling-2-mini

# 3. 再进入 Claude 与 Ollama 的集成启动入口
ollama launch claude
```

退出模型交互后，在 Claude Code 会话里用自然任务触发工具，而不是先下结论：

```text
列出当前工作区中可发现的 MCP 工具。
只读取一个与当前任务直接相关的工具描述，不要加载其他工具。
执行只读检查并报告工具名称、参数、状态和错误。
```

这是一组验收提示，不是产品承诺。它的目的，是区分三件事：Claude 是否能进入会话、MCP 是否能被发现，以及工具是否能在调用时成功完成。

Claude Code v2.1.330 还提供了 `/config` 用来关闭自动图表。发布说明中提到 `easel` 在 MCP 指标结果上可用，并根据账户版本与系统平台提供。验证时不要把图表作为工具加载成功的证据，它只能说明某个展示能力可用，不代表底层 MCP 调用链通过。

## 验证要按阶段建立证据

延迟加载最常见的错误，是只看最终答案是否合理。合理答案可能由模型缓存、模型知识或无工具执行得到，无法证明 MCP 调用成功。

建议至少记录以下证据：

- 启动方式：是直接运行 `ollama run`，还是使用 `ollama launch claude`。
- 平台与架构：特别是 Release 明确标注了 Apple silicon 限制的模型。
- 会话初始工具数量：只记录本次会话实际暴露的工具摘要。
- 首次调用时刻：工具是在第几轮任务或什么时候被发现。
- 工具名称与参数：确认模型选择的是预期工具，而非相似名称。
- 返回状态：区分成功、超时、协议错误、权限拒绝和服务未启动。
- MCP 指标：若平台与版本支持，记录加载次数、调用次数或错误指标。
- 最终结果来源：明确区分工具返回内容与模型推理补全。

一个简单的验收清单是：

```text
□ 会话能稳定启动
□ 模型与目标模型版本一致
□ 工作区目录和启动目录符合预期
□ MCP 配置可被发现
□ 第一个只读工具可以加载并返回
□ 后续工具不会在无关任务中提前加载
□ 工具失败不会污染同一会话的其他只读操作
□ 重启后状态或缓存不会被误认为持久正确性
```

检查清单的价值在于将“能回答问题”和“工具链可工作”拆开。如果某一步失败，就应停止向下验收，而不是从最终文本推断工具执行成功。

## 失败边界比功能范围更重要

Release 提供的是版本承诺，不是失败保证。至少有以下边界需要单独处理。

### 平台边界

Ollama 对 `inkling-2-mini` 明确标注 Apple silicon 支持，PC 支持在该版本中尚未提供。如果在其他平台测试，不应声称功能不存在，只能把结果标记为该平台未被 Release 支持。

对 Claude Code 自托管运行而言，v2.1.330 新增了 `--start-dir` 和 `SELF_HOSTED_RUNNER_START_DIR`，用于控制启动目录。目录错误可能表现为配置找不到、插件无法加载或相对路径失效，但这不等于 MCP 协议本身失败。

### 工具发现边界

延迟加载意味着工具目录可能分为发现状态和加载状态。发现到某个工具不代表它已经连接成功；只暴露工具名称也不代表参数模型兼容。验收必须包含最小只读调用，而不能只检查工具列表。

### 权限边界

工具调用可能成功地完成发现，但仍因身份、写权限或仓库范围失败。为了减少不可逆风险，首轮验收应只使用只读操作。只有只读链路稳定后，再考虑创建、修改或发布类能力。

组织登录时，Claude Code 会应用组织设置并使用组织配置的云服务或网关。它的含义是组织策略会进入运行时，而不是本地模型配置自动继承组织能力。企业策略、团队策略和本地配置之间仍需逐项核验。

### 缓存与重启边界

一次成功的工具发现不能证明重启后仍然可用。工具进程可能在重启后不存在，配置可能被环境变量覆盖，模型也可能加载不同版本的工具目录。每次验收都应记录会话版本、工作目录和启动参数，而不能将前一次运行保存在内存中的结果当作持久状态。

### 指标边界

MCP 指标是否可用，取决于 Claude Code 版本、账户类型、平台和集成状态。即使展示了指标，也只能证明指标采集与展示链路存在，不应直接推断模型质量、工具准确性或安全性。指标应与调用日志和最终结果一起使用。

## 工程取舍：延迟加载不是多工具的万能解法

延迟加载适合工具数量多、调用频率低、启动速度敏感的场景。它能降低会话初始化时一次性暴露全部工具的成本，也能让不相关的工具暂时不进入模型上下文。

但它不适合以下取舍：

- 工具调用频繁且延迟敏感：每次发现都可能增加往返成本。
- 参数约束复杂：延迟加载后，模型可能仍需要额外轮次理解参数结构。
- 工具集本身变化频繁：缓存目录过期会造成不可见的不一致。
- 强审计场景：每次工具调用必须有稳定的请求、身份和返回记录。
- 离线工作流：工具发现和调用都可能依赖本地或远程服务可用性。

更稳妥的架构是按任务域建立工具集合，而不是追求单个会话中加载所有 MCP 工具。工作区可以只暴露只读工具，发布、迁移或写入工具放在独立会话中，由人工确认触发。这样不仅减少上下文，也能让权限和审计边界直接映射到工具组。

## 原创结论：加载机制和治理机制必须分开验收

MCP 延迟加载解决的是“何时把工具交给模型”的问题，不是“谁能调用工具、工具能否可靠执行、结果是否可审计”的问题。一次会话可能正确加载工具并失败在权限上，也可能成功执行工具却将错误数据带入最终结论。因此，工具发现、参数校验、权限控制、执行结果和人工验收应作为独立证据阶段。

对于工程团队，一个可落地的结论是：不要把“支持延迟加载”作为上线标准，而应把“在指定目录、指定平台、指定身份下完成只读发现、只读调用、失败回收和重启复验”作为上线标准。只有每个阶段都有可保存的证据，才能区分版本能力、运行时可用性和任务执行质量。

本次材料足以支持功能趋势和版本事实，却不足以证明任意配置下的性能提升、参数准确率或全平台兼容性。没有部署日志、指标基线和复现实验之前，更严谨的结论仍是：延迟加载是可验证的新能力入口，而不是已经完成全局加速的结论。
