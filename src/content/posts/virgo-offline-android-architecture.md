## 先把问题从“计时器”改写成“本地状态系统”

NodeLoc 上关于 Virgo 的介绍很简短：这是一个开源的原生 Android 三阶魔方计时器，支持打乱生成和解法历史，项目仍处于较早阶段。社区帖子只能证明项目被公开介绍过，不能单独承担架构、权限和实现细节的证据。因此，本文把 GitHub 仓库作为主要依据，把社区帖子当作选题雷达，而不是把帖子中的宣传语直接当成技术结论。

从仓库 README 可以确认，Virgo 使用 Kotlin 和 Jetpack Compose 编写，是 fully native 的 Android 应用，不使用 WebView；项目定位为离线运行，不请求 INTERNET 权限；打乱和计时逻辑参考并重新实现了 csTimer 的相关逻辑，许可证标注为 GPLv3。它的价值不在于“功能很多”，而在于把一个看似适合接入统计服务、账号系统或广告 SDK 的小工具，收敛成一个本地状态系统。

这个改写非常重要。若把需求写成“做一个计时器”，工程师很容易只关注按钮和秒表；若把需求写成“在没有网络、没有账号、没有远端依赖的条件下，可靠地产生一次打乱、完成一次计时，并保留可回看的解法历史”，核心就变成了状态转移、数据生命周期和失败边界。界面只是状态的投影，不是系统本身。

## Virgo 的最小架构：输入、状态与历史记录

一个离线计时器至少有三条逻辑链。

第一条是打乱链。应用需要生成或展示一次魔方打乱，用户根据打乱开始还原。打乱不是装饰文本，而是本次成绩的上下文。没有打乱，历史记录只能回答“用了多少时间”，无法回答“在什么题目上用了多少时间”。因此，一次有效记录应该至少把打乱文本与计时结果绑定在同一个本地状态中。

第二条是计时链。计时器通常会经历 idle、准备、运行、停止或取消等阶段。真正容易出错的地方不是显示数字，而是边界：用户按下开始后立刻按停止怎么办？应用进入后台怎么办？旋转屏幕或 Compose 重新组合时，计时是否被重复启动？系统进程被回收后，当前未完成的计时应不应该伪装成一条成绩？

第三条是历史链。Virgo README 明确列出 solve history，这意味着应用不仅要显示当前成绩，还要保存一组过去的解法。历史记录最好被视为不可随意改写的事件集合：每条记录对应一次完成的解法，包含时间、打乱和必要的元数据。这样做的好处是，统计功能可以在后续从历史记录派生，而不必把“当前界面上的数字”当成唯一真相。

Jetpack Compose 适合表达这类状态驱动界面，但 Compose 本身并不会自动解决持久化问题。一个清晰的分层方式是：界面层只负责展示状态和发送用户意图；计时状态由单一的状态持有者管理；历史记录通过明确的数据接口读写；打乱生成器作为可替换的纯逻辑模块存在。这里不需要为了一个小工具引入复杂的远程架构，也不应把每个按钮的副作用直接散落在 Composable 函数中。

这种设计有一个朴素的判定标准：同样的状态输入，不应因为界面重组而产生不同的业务结果。若屏幕重绘会重新生成打乱，或者重组会把计时任务启动两次，那么问题不是 UI 样式，而是状态所有权没有被定义清楚。

## “无网络权限”不是一句隐私口号，而是可检查的边界

仓库 README 给出的重要事实是：应用完全离线运行，并且不请求 INTERNET 权限。这个声明可以转化成一组工程检查，而不是停留在宣传层面。

首先检查 Manifest。可以在源码目录执行：

```bash
git clone https://github.com/mukunjin/virgo.git
cd virgo
rg -n "INTERNET|ACCESS_NETWORK_STATE|WebView|http://|https://" app
```

这个命令不能替代 Android 构建系统的最终合并结果，但可以快速发现显式网络权限、WebView 和常见网络地址。进一步检查构建后的 APK：

```bash
./gradlew assembleDebug
apkanalyzer manifest permissions app/build/outputs/apk/debug/app-debug.apk
```

如果本地环境没有 `apkanalyzer`，也应该使用 Android SDK 中等价的 APK 检查工具，目标是确认最终 APK，而不只是确认某个源码文件。源码没有写网络调用，不等于依赖库、Manifest 合并或构建变体不会引入权限；最终产物才是用户安装的对象。

其次检查依赖。项目根目录包含 Gradle 构建文件和 Gradle Wrapper，依赖应从构建配置中逐项核对。对于一个定位为离线工具的应用，重点不是“依赖越少越好”这种口号，而是每个依赖是否改变了信任边界：是否引入统计 SDK，是否在初始化阶段发起请求，是否包含远程配置，是否需要账号或设备标识。即使这些库没有直接暴露在界面上，也会影响离线承诺。

再次检查运行时行为。关闭设备网络后打开应用，验证打乱生成、计时和历史读取是否仍能完成；之后开启飞行模式，重复冷启动和页面切换；最后观察应用是否在首次启动时要求与核心功能无关的权限。这里的验证目标不是证明“任何情况下都不会联网”，而是验证项目声明的核心边界：核心功能不依赖网络，也不以网络可用作为成功条件。

## 算法复用的难点：能运行不等于能正确

Virgo README 说明，打乱和计时逻辑参考并重新实现了 csTimer，并明确标注 GPLv3。这一事实同时带来算法和许可证两类工程问题。

算法层面，打乱生成器的输出不能只凭“看起来像一串字母”判断正确。需要区分几种验证：语法是否可解析，转动符号是否符合预期，连续输出是否出现异常重复，应用能否稳定展示，历史记录能否原样保存。若项目将来加入更复杂的统计，还应验证打乱与成绩的关联没有错位，例如用户完成第二次计时时，第一条记录不能意外绑定第二次打乱。

可以建立一个不依赖 UI 的检查清单：固定随机种子时，生成器是否得到可重复结果；不同随机种子时，输出是否发生变化；生成 N 条打乱后，是否每条都能被应用接受；空字符串、超长字符串或非法符号进入展示层时，是否会造成崩溃。这里不应该把某个样例输出硬编码成“正确答案”，除非仓库明确提供了测试向量。更可靠的做法是验证不变量，并把已知样例作为回归测试。

许可证层面，参考并重新实现代码并不意味着可以忽略上游项目的授权条件。仓库 README 已经标注 GPLv3，贡献者在继续扩展算法或复制实现时，应保留许可证与版权信息，并确认新增代码、分发方式和依赖关系符合项目原有许可证要求。对于一个小型工具来说，许可证文件和 README 往往比复杂的合规系统更容易被忽略，但这恰恰是开源项目可持续维护的一部分。

还有一个常被低估的取舍：完全离线意味着不能把算法错误、统计异常或用户反馈自动上传。它换来的不是“绝对安全”，而是更小的数据暴露面和更明确的故障模型。维护者需要通过版本发布、Issue、可复现样例和本地导出等方式补足可观测性，而不是偷偷加入遥测来解决维护便利性。

## 失败边界：离线优先并不等于功能没有代价

离线架构最直接的失败边界是数据丢失。若历史只保存在进程内存中，应用被系统回收后记录就会消失；若只依赖一个本地文件，又需要考虑写入中断、格式升级和损坏恢复。Virgo 的公开材料确认了历史记录功能，但没有提供完整的数据存储格式和迁移策略，因此不能把某一种存储方案写成项目已经采用的事实。工程上应把“历史是否持久化、如何迁移、能否导出”作为需要继续从源码核验的问题，而不是自行补全。

第二个边界是系统生命周期。计时过程中切到后台、锁屏、旋转屏幕或发生配置变化，都可能改变进程和界面状态。一个可靠的实现需要定义：后台期间是否继续计时，恢复后显示什么，未完成记录是否丢弃，是否允许从恢复状态继续。对计时工具来说，错误地把一次中断显示成有效成绩，比直接提示“本次未完成”更糟，因为它会污染个人历史和后续统计。

第三个边界是时间来源。用户看到的是经过时间，不应简单等同于墙上时钟的差值。设备时间被手动调整、时区变化或系统休眠，都可能影响结果。具体采用哪种 Android 时钟 API，需要以项目源码和目标平台为准；在设计层面则应先写清楚计时语义：测量的是用户操作期间的持续时间，还是设备时间戳之间的差值。没有这个定义，精度争论没有意义。

第四个边界是“无网络”承诺的范围。它可以覆盖核心计时功能，却不自动覆盖应用商店更新、外部链接、未来新增的排行榜或云同步。每次增加功能，都应该重新做权限、依赖和数据流审查。一个项目今天没有网络权限，不代表所有未来版本都天然保持同样的边界。

## 从源码到 APK 的验证清单

如果要审阅或维护类似 Virgo 的项目，可以按以下顺序执行，而不是先看截图判断质量。

1. **确认项目入口。** 检查 `settings.gradle.kts`、根目录构建文件、`app` 模块和 Gradle Wrapper，确认构建结构是否与 README 描述一致。
2. **确认平台边界。** 搜索 Manifest、网络权限、WebView、网络客户端和远程配置；同时检查依赖树，避免只审查业务源码。
3. **确认状态模型。** 沿着“生成打乱—开始—停止—保存历史—展示历史”的路径阅读调用关系，标出每次状态写入的位置。
4. **确认重组安全。** 检查计时任务、随机数生成和持久化操作是否绑定在正确的生命周期范围内，避免界面重组触发业务副作用。
5. **确认异常输入。** 测试空历史、损坏记录、快速重复点击、屏幕旋转、后台恢复和进程重启；每个场景都要有明确结果，而不是依靠不确定的默认值。
6. **确认构建产物。** 执行 `./gradlew assembleDebug`，再检查 APK 的 Manifest 和权限。仅仅“Gradle 构建成功”只能证明能打包，不能证明离线边界和业务正确性。
7. **确认许可证。** 核对仓库 LICENSE、README 中的上游来源说明以及新增代码的授权，尤其关注参考或重新实现的算法模块。

这套清单的重点是把“项目宣称了什么”与“产物实际具备什么”分开。README 是一手项目说明，APK 是可验证对象，测试结果则是两者之间的证据链。

## 原创结论：小工具最值得做的是减少不可见状态

Virgo 这个案例给出的结论，不是每个 Android 应用都应该拒绝网络，也不是离线应用一定比在线应用高级。真正值得借鉴的是它把产品边界收窄了：不使用 WebView，不请求 INTERNET 权限，把打乱、计时和历史记录留在本地，并用原生 Kotlin 与 Compose 表达交互。

边界收窄后，工程复杂度并没有消失，而是从“如何接入更多服务”转移到“如何保证本地状态可信”。计时是否只启动一次，记录是否与打乱正确绑定，应用被系统回收后是否诚实地告诉用户发生了什么，算法复用是否符合许可证，这些问题不会出现在功能宣传图里，却决定了工具能不能长期使用。

因此，评价一个小型开源应用时，不应只看功能数量、界面是否漂亮或仓库是否有很多提交。更有信息量的判断是：它是否明确说明数据去哪儿、权限为什么存在、离线时哪些功能仍然成立、失败后用户会看到什么，以及维护者能否用源码和构建产物证明这些承诺。对一个魔方计时器如此，对更复杂的个人效率工具同样如此。
