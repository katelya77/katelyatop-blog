## 先把“免费代理 API”还原成一个工程问题

NodeLoc 上出现了“制作了一个免费 socks5 代理获取 api”的真实需求样本，指向的项目是 GitHub 上的 `runoneall/free-socks5-proxy-api`。社区帖子只能说明有人在寻找这种能力，不能证明代理长期可用、匿名性达标、出口稳定，也不能证明它适合生产流量。更稳妥的选题方式，是把“免费”从卖点降级为约束：数据来源不稳定、代理生命周期短、带宽和地址质量不可控，调用方必须自己承担验证和降级。

仓库页面显示这是一个公开的 Go 项目，包含 `main.go`、`datamgr.go`、`helper.go`、`limiter.go`、`go.mod`，并配置了 `.github/workflows` 与 `data` 目录；仓库说明还标注了 MIT license。README 的公开摘要只确认项目目标是“免费 socks5 代理获取 api”，没有在材料中给出一个足以据此断言的完整接口契约。因此本文不虚构路径、参数、响应字段或代理来源，而是讨论如何从源码和运行结果确认这些事实。

这类项目的核心不是“找到几个 IP”，而是把一个不断变化的候选集合，变成调用方能够理解的状态集合：候选地址从哪里来，什么时候被采集，是否通过 SOCKS5 握手，最近一次检查何时成功，失败后多久移除，以及 API 返回的数据是否已经过期。没有这些状态，所谓 API 只是一个未经验证的文本列表。

## 从仓库结构推断控制面与数据面

`data` 目录通常意味着项目需要持久化或发布采集结果；`.github/workflows` 则说明自动化运行是项目设计的一部分。仓库页面列出了 `last_run_time.txt`，这至少表明项目需要留下最近一次运行时间的可见痕迹。它的价值不在于证明数据新鲜，而在于让维护者和使用者知道：数据生成不是一次性静态文件，而是周期任务的产物。

可以把系统拆成四个边界，而不是把所有逻辑塞进一个“获取代理”函数。

第一是采集边界。采集器负责获得候选地址，候选地址可能来自公开页面、文件或其他来源。这个阶段只回答“看到了什么”，不回答“能不能用”。采集器应保留原始候选与抓取时间，避免把解析错误误判为网络故障。

第二是验证边界。SOCKS5 代理至少需要完成协议协商，并且在规定超时内建立目标连接。一个地址能响应 TCP，并不等于它能完成 SOCKS5 握手；能够握手，也不等于能访问指定目标。验证结果应该包含阶段信息，例如解析失败、连接超时、协商失败、目标连接失败，而不是只有一个布尔值。

第三是数据管理边界。`datamgr.go` 这一命名暗示项目存在独立的数据管理职责。数据管理应负责规范化地址、去重、合并新旧结果、淘汰过期记录，并决定发布格式。它不应偷偷把验证逻辑和 HTTP 输出逻辑混在一起，否则很难解释“列表变短”究竟是采集减少、验证失败，还是发布阶段过滤。

第四是服务边界。API 返回的是一个时间点上的快照，不是对每个地址可用性的保证。调用方应当把响应看作候选池，再进行自己的最终验证。`limiter.go` 的存在也提醒我们：无论限流保护的是上游采集、验证目标还是对外 API，都必须明确对象，否则“有限流”这个词没有可检查的含义。

## 用源码检查代替猜接口

材料中没有完整 README 内容时，最可靠的做法不是猜一个 URL，而是先固定仓库版本，再让源码告诉我们入口。下面的检查流程只依赖公开仓库和本地 Go 工具链，适合在评估第三方代理项目时复用：

```bash
git clone https://github.com/runoneall/free-socks5-proxy-api.git
cd free-socks5-proxy-api

git log --oneline -n 5
grep -RInE 'ListenAndServe|HandleFunc|http\.Handle|SOCKS|socks5|limiter|last_run' \
  --include='*.go' --include='*.md' .

go mod download
go test ./...
```

这里有三个容易被忽略的验证点。第一，`git log` 用于记录你检查的提交，而不是把“当前 main 分支”当作不可变版本。第二，搜索 HTTP 注册点和 SOCKS5 相关代码，可以区分“提供代理列表的 API”与“本身作为代理转发流量的服务”。第三，`go test ./...` 的通过只代表已有测试通过，不代表公网代理质量通过；如果仓库没有测试，命令失败或没有测试文件也不能被包装成质量证明。

进一步检查构建入口和自动化配置：

```bash
find . -maxdepth 3 -type f | sort
sed -n '1,220p' go.mod
sed -n '1,260p' main.go
sed -n '1,260p' datamgr.go
sed -n '1,260p' limiter.go
find .github/workflows -type f -maxdepth 2 -print -exec sed -n '1,240p' {} \;
```

这组命令的目的不是把文件内容复制进文章，而是建立一条可审计链：依赖版本来自 `go.mod`，进程入口来自 `main.go`，数据变化来自数据管理模块，运行周期来自 workflow。只有当这些证据彼此对上，才能描述系统的真实架构。仓库页面显示有 19 次提交、公开 issue 与 pull request 数量为 0，但这些页面指标不能替代代码审查，更不能推导出 SLA 或安全保证。

## “代理可用”必须拆成多层检查

代理池最常见的误判，是把一次成功连接写成永久健康。验证应该至少分层，并给每层设置独立超时。

第一层是地址层：检查 host 与 port 是否能解析，端口是否可以建立 TCP 连接。它只能说明网络路径存在。

第二层是协议层：通过 SOCKS5 协商，确认服务端确实按预期响应。若项目支持认证，还应分别记录无需认证、用户名密码认证或认证失败；不能把认证失败记录成“地址失效”，因为它可能只是调用配置不匹配。

第三层是目标层：通过代理连接一个由调用方控制、响应简单且不会泄露敏感信息的测试目标。目标应固定或可配置，并记录状态码、耗时和错误阶段。不要用登录页面、内部地址或带个人信息的站点做探针。

第四层是持续性层：同一个地址在不同时间、不同目标上的结果可能完全不同。可以采用滑动窗口，例如保存最近若干次检查的成功率、最近成功时间和连续失败次数，再制定发布规则。具体阈值应由使用场景决定，不能因为一次成功就标注为稳定代理。

一个本地检查脚本可以先验证 API 返回内容是否符合预期，但在没有确认项目实际端点和响应格式前，不应写死示例 URL。正确顺序是从源码确认接口，再用 `curl` 保存原始响应：

```bash
curl --fail-with-body --max-time 15 \
  -H 'Accept: application/json' \
  'http://127.0.0.1:确认后的端口/确认后的路径' \
  -o response.json

wc -c response.json
head -c 500 response.json
```

如果返回的是 JSON，再使用项目实际字段做结构校验；如果返回的是文本列表，就逐行规范化并检查 `host:port` 格式。不要因为 HTTP 返回 200 就认为里面的代理可用，更不要把空数组包装成“服务正常”。空池是一个需要被监控和告警的业务状态。

## GitHub Actions 带来的新鲜度与限额取舍

仓库包含 `.github/workflows`，说明自动化任务是重要运行面。周期任务的优点是可以定期刷新结果、减少人工维护，并把生成结果留在公开仓库或其发布渠道中；代价是任务运行频率、执行时长、网络出口和上游站点变化都会影响结果。社区帖子提到“每 3 小时自动更新”，但这属于社区材料中的项目介绍，证据等级低于仓库代码与 workflow 文件；在未读取具体 workflow 前，不能把它当作永久承诺。

评估 workflow 时，应检查以下项目：触发方式是定时、手动还是代码变更；任务是否有明确超时；失败时是否仍会提交空结果；生成文件是否原子替换；提交身份和权限是否最小化；依赖是否固定；日志中是否可能暴露代理、令牌或上游返回内容。尤其要关注“任务失败但旧数据被覆盖成空文件”这一灾难性边界。更安全的策略是：生成到临时文件，完成格式检查和最小数量检查后再替换正式文件；失败则保留上一份数据，并让 workflow 明确失败。

新鲜度也不是越高越好。频繁采集会增加上游压力，触发来源封禁，也会让低质量地址快速进出，增加调用方抖动。低频任务可能得到更稳定的快照，却延长失效地址存活时间。工程上应把“采集频率”“验证频率”和“发布频率”分开思考：候选采集可以低频，健康检查可以按需，发布可以只在结果满足质量门槛时发生。

## 免费代理的安全边界不能省略

免费代理不是免费网络出口。使用第三方 SOCKS5 节点时，调用方应假设流量可能被观察、篡改或记录。密码、Cookie、访问令牌、内部服务地址和管理接口都不应通过不受信任的代理发送。即便业务使用 HTTPS，也要确认证书校验没有被关闭，避免把“代理不可见”误认为“连接安全”。

还要防止 SSRF。若程序接受用户提供的目标 URL，再把请求交给代理池，它可能成为访问内网、云平台元数据或本机管理端口的跳板。应限制目标协议、解析结果和地址范围，拒绝回环、链路本地、私有网段及其他不属于业务的地址；重定向也必须重新检查。这里的规则应放在调用方业务边界，而不是期待公共代理项目替你完成。

代理本身也可能是恶意或被接管的。不要执行代理返回的脚本，不要下载并运行未知内容，不要把代理响应直接写入可执行目录。对下载任务，应限制大小、类型和重定向次数，并保存必要的审计信息。对爬取场景，还需要确认目标站点的条款与法律边界；“公开列表”不等于“可以绕过访问控制”。

## 失败边界与工程取舍

这个项目形态最适合低风险、可重试、允许失败的任务，例如公开页面的可用性探测、测试环境的网络路径实验或临时数据抓取。它不适合支付、登录、管理后台、生产数据库访问、稳定出口要求高的业务，也不适合把 IP 白名单当作唯一身份认证。

当代理池为空时，系统应有明确降级：直连、切换到自有出口、延迟重试或终止任务，不能无限重试。重试要有总时限和退避，避免一个失效地址拖垮整个 worker。并发也要受控：对外 API 的限流保护服务，对目标站点的并发保护业务，对单个代理的并发保护代理本身，这三种限制不是同一件事。

监控指标建议围绕结果而非请求数建立：候选数量、通过协议验证的数量、通过目标验证的数量、最近成功时间、连续失败数、池中地址年龄、API 错误率和空池持续时间。日志中记录错误阶段与耗时即可，避免记录完整 URL、认证信息和敏感响应。若项目只提供静态列表而没有这些指标，调用方就应在自己的适配层补齐，而不是假定上游已经治理。

## 一个可复用的验收清单

在把任何免费代理 API 接入工具链前，可以按下面顺序验收：

1. 固定仓库提交，确认许可证、依赖和启动入口；
2. 从源码确认 API 路径、返回格式、更新方式和失败响应；
3. 检查 workflow 的定时策略、权限、超时和空结果处理；
4. 对返回数据做格式校验、去重和时间戳校验；
5. 在隔离环境完成 SOCKS5 协议验证与目标连通性验证；
6. 用无敏感信息的测试目标测量延迟、连续成功率和失败阶段；
7. 为空池、旧数据、全部超时、认证失败和目标拒绝设计降级；
8. 明确禁止承载的流量类型，并在代码中限制内网目标与危险重定向；
9. 观察一段时间后再决定是否接入，不能用一次成功替代持续性证据。

原创结论是：免费代理项目真正提供的不是“一个能用的 IP”，而是一条需要被调用方重新验证的候选数据管道。仓库中的数据管理、限流和自动化任务，解决的是供给侧的基本秩序；代理质量、隐私风险、目标安全和业务降级，仍然属于使用侧责任。把二者混为一谈，才是这类 API 最危险的工程误读。
