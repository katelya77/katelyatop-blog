## 先把它定义准确：日志扫描是新增入口，不是新增保险箱

GitHub 在 2026 年 11 月 9 日发布了一项公开预览能力：Secret Scanning 除了检查代码、Issues、Wiki、Discussions 和 Pull Request 外，也会检查 GitHub Actions 的工作流日志。这个变化的关键，不是又增加了一个“扫描开关”，而是把构建系统产生的输出正式纳入密钥治理范围。

工作流日志与代码仓库有一个重要差异：它往往是运行时数据的混合物。命令回显、依赖安装信息、调试输出、测试失败上下文，以及脚本意外打印的环境变量，都可能进入日志。开发者没有把凭据提交到 Git，但凭据仍可能在一次构建中离开进程边界，成为可被后续查看、复制或下载的文本。

因此，日志扫描解决的是“密钥已经进入运行产物后，能否被发现”的问题，而不是“密钥为什么会被打印”的问题。它不能替代最小权限、环境变量保护、日志脱敏和代码审查。更准确的架构表达是：日志扫描位于运行时泄漏之后、人工响应之前，是一层事后检测与定位机制。

## 它实际扫描什么，又明确不扫描什么

官方说明给出了几个必须同时记住的条件。

第一，扫描发生在工作流运行完成之后。也就是说，它不是每输出一行日志就同步拦截，也不等同于一个实时阻断器。一个正在运行的任务，即使已经产生了疑似密钥，在运行完成前也不应被当作已经完成检测。

第二，检测基于提供商模式。发现结果会出现在仓库的 Secret Scanning alert 列表中，并链接回对应的 Actions 工作流日志。对于支持的密钥类型，GitHub 还会进行有效性检查。这意味着告警不只是“看起来像一串字符串”，部分结果还可能带有当前凭据是否有效的判断依据。

第三，日志被删除并不意味着告警自动消失。官方说明指出，相关告警在日志删除后仍可保留。这一点改变了传统“删掉构建产物就算清理”的直觉：日志删除可以减少继续暴露的载体，但不能代替凭据撤销、轮换和事件记录。

边界同样重要。公开预览阶段不检测通用模式、自定义模式、AI 检测出的密钥，也不检测已经被 Actions 掩码处理的密钥。换言之，团队不能把“没有告警”解释成“日志里没有任何敏感信息”。它只能说明当前能力没有识别出支持范围内的提供商模式，或者该运行尚未满足扫描条件。

这也是为什么验证时不能只做一个布尔判断：告警为零不代表风险为零；告警存在也不代表泄漏来源已经被修复。扫描结果是证据链中的一环，不是最终结论。

## 启用前先检查四个门槛

这项能力并非所有仓库默认可用。官方信息显示，Actions 工作流日志扫描处于公开预览阶段，面向 GitHub Enterprise Cloud，并要求企业具备 Secret Protection 或 GitHub Advanced Security。企业所有者需要在企业设置中进入 Policies，再进入 Advanced Security，在 All repositories 下将 Secret scanning 设为 Enabled。仓库本身还必须已经启用对应许可范围内的 Secret Scanning。

可以把启用过程拆成四个可核对的门槛：

1. **平台门槛**：确认组织所在环境是 GitHub Enterprise Cloud，而不是把公共仓库中的普通 Secret Scanning 页面误认为具备日志扫描能力。
2. **许可门槛**：确认企业拥有 Secret Protection 或 GitHub Advanced Security。仅仅能打开某个安全页面，不等于此预览功能对当前组织生效。
3. **策略门槛**：由企业所有者检查 Advanced Security 策略中的 All repositories 设置。策略默认关闭，不能用单个仓库的局部设置替代企业策略。
4. **仓库门槛**：确认目标仓库已经启用 Secret Scanning。否则企业级策略即使打开，也不能推导出该仓库已经开始检查日志。

在变更前，建议把这四项记录在变更单中，而不是只截一张设置页面。至少保存目标企业、目标仓库、操作者、启用时间和预期验证运行编号。这样在后续查询告警时，能够区分“没有发现”和“从未成功启用”。

## 用无敏感数据的方式验证链路

验证目标不是制造一个真实泄漏，而是确认策略、运行完成、结果呈现和告警留存四段链路确实连通。可以先使用一个不包含凭据的最小工作流作为探针：

```yaml
name: log-scan-probe
on:
  workflow_dispatch:

jobs:
  probe:
    runs-on: ubuntu-latest
    steps:
      - name: Emit non-secret marker
        run: |
          echo "LOG_SCAN_PROBE_RUN=${GITHUB_RUN_ID}"
          echo "No credential is intentionally emitted"
```

触发后，用 GitHub CLI 查看运行状态和日志：

```bash
gh run list --workflow log-scan-probe.yml --limit 5
gh run view <run-id> --log
```

这两条命令只能证明工作流运行并产生了可查看日志，不能证明扫描能力已经识别某种密钥。真正的验收应回到仓库的 Secret Scanning alerts 页面，检查是否能看到与工作流日志相关的入口，并记录页面显示的策略状态。由于官方说明只有启用功能后完成的运行才会被扫描，验证运行必须发生在启用之后；不能拿启用前的历史运行作为反例。

在正式环境中，不建议为了“测试告警”而把真实服务令牌、网上流传的测试令牌或可被第三方识别的凭据写进日志。更稳妥的做法是先确认组织的演练流程：由安全团队提供专门的、可立即撤销的测试材料，明确其生命周期、权限和销毁步骤；如果没有这样的流程，就只验证配置和结果页面，不人为制造泄漏。

验收记录最好至少包含：启用前后时间点、测试运行编号、运行是否完成、日志是否可访问、告警列表是否出现日志来源、告警是否链接到运行日志、日志删除后告警是否仍保留，以及负责响应的团队。这样做的价值在于把“产品开关已打开”与“运营链路可用”分开。

## 失败边界：哪些结论不能从告警页面推出来

最常见的误判有五种。

第一，把预览能力当作正式、完整的覆盖范围。当前功能明确属于 public preview，检测范围受提供商模式限制，不能直接承诺所有自定义密钥、内部令牌或新型凭据都能被发现。

第二，把扫描当作实时阻断。扫描在工作流完成后进行，所以它不保证泄漏发生的瞬间就停止任务。对高风险工作流，仍应在脚本层避免打印环境变量，并在权限层限制令牌可以访问的资源。

第三，把历史日志当作自动回溯对象。官方说明指出，只有启用后完成的工作流运行会被扫描，既有日志不会回填。启用策略之前发生过的泄漏，必须依靠既有审计、人工检索或其他检测机制处理。

第四，把没有通知理解成没有事件。预览期间，来自 Actions 工作流日志的告警不会产生通知，需要直接检查仓库的 Secret Scanning alert 列表。如果团队只依赖邮件、聊天机器人或默认通知渠道，可能会在能力已经发现问题时仍然毫无感知。

第五，把掩码当作扫描结果。已经被 Actions 掩码的密钥不会被该能力检测。掩码降低了日志读取者直接看到明文的概率，但它不能说明凭据没有被使用、复制或传递到其他输出中。掩码策略与泄漏响应必须分别验收。

## 从“发现”走向可执行响应

日志告警真正产生价值，要看它能否触发一套不依赖个人记忆的响应流程。建议将处理分成三个阶段。

**隔离阶段**：先判断令牌是否仍然有效、具有什么权限、是否被其他任务或环境复用。对高权限令牌，应优先暂停相关发布或撤销凭据，而不是先花时间清理日志文本。

**定位阶段**：沿着告警链接回到具体工作流、运行编号、作业和步骤，确认是脚本显式打印、工具调试输出，还是第三方动作间接输出。定位时要保留最小必要证据，避免把疑似密钥复制到新的工单、聊天记录或附件中。

**修复阶段**：修改输出行为和权限边界，轮换或撤销受影响凭据，再重新运行安全检查。若只删除日志而不改变工作流，下一次运行仍可能重复泄漏；若只轮换凭据而不修复输出路径，事件会变成持续重复的噪声。

我的工程结论是：Actions 日志扫描最适合被当作“运行产物的安全索引”，而不是最后一道防火墙。它补上了代码扫描看不到的运行时盲区，但预览状态、完成后扫描、无回填、无通知和有限模式覆盖，决定了它必须与日志最小化、令牌短生命周期、权限隔离和人工响应结合使用。只有当团队能回答“谁检查告警、多久响应、如何撤销、怎样证明修复”时，打开这个开关才真正完成了安全建设。
