## 这次升级改变的是运行时假设

vLLM 0.34.0 的信息密度，集中在一个容易被忽略的事实：它不是一次普通的补丁升级。官方 Release 将 Model Runner V1 移除、Model Runner V2 成为唯一 GPU runner、可扩展 KV cache 默认启用，以及若干依赖和镜像变化放在同一次发布中。换句话说，升级对象不只是 Python 包或容器标签，而是推理服务启动方式、显存预算模型和底层执行路径。

这类升级最危险的地方，不是程序一定启动失败，而是服务可能仍然能启动，却改变了吞吐、首 token 延迟、显存占用或请求排队行为。一个只检查 HTTP 200 的验收流程，无法证明新版本仍满足原有服务目标。

本文只讨论官方 Release 已明确给出的变化。性能数字属于项目发布说明中的硬件与模型案例，不应直接外推为所有 GPU、模型和 batch 配置的普遍结果。文章中的命令是通用检查模板，用于建立升级前后的可比证据，不代表某个具体环境已经执行过。

## 从 V1 移除理解兼容性边界

Model Runner 可以看作 GPU 推理请求进入执行层前的一道调度与运行时边界。vLLM 0.34.0 明确说明 Model Runner V1 已移除，Model Runner V2 成为唯一 GPU runner。官方给出的直接迁移要求是删除 `VLLM_USE_V2_MODEL_RUNNER=0`；继续保留该设置会在启动时失败。这个变化说明旧变量不再是一个可选开关，而变成了失效配置。

工程上应把它当作配置契约变化，而不是简单的环境变量清理。很多部署系统不会把变量写在启动脚本里，而是藏在 Helm values、Compose 文件、CI secret、systemd drop-in 或平台的环境变量界面中。只改 Dockerfile 而不检查最终进程环境，容易让旧配置在发布后重新出现。

升级前可以先对部署材料做静态检查：

```bash
grep -R --line-number --fixed-strings 'VLLM_USE_V2_MODEL_RUNNER' .
```

如果服务由容器运行，还应检查最终镜像和容器配置，而不是只看仓库文件：

```bash
docker inspect <container> --format '{{range .Config.Env}}{{println .}}{{end}}' | grep VLLM
```

升级后的第一道验证是故意保留一份启动日志，确认服务没有因为旧开关而失败；第二道验证是确认服务确实由 V2 路径运行。若项目自身没有提供稳定的运行器标识，就不要凭日志中的偶然文本推断内部路径，应以启动成功、请求成功、指标可采集和性能对比共同构成证据。

## KV cache 默认行为变化，意味着预算需要重算

Release 说明中另一个关键变化是：可扩展 KV cache 默认启用。vLLM 会根据预热后实际可用的显存来确定 KV cache 大小，因此官方判断多数模型可以获得更大的 cache 和更高吞吐。这里的重点不是“默认更大”四个字，而是 cache 预算的计算时机发生了变化：它不再只依赖静态配置或启动前的粗略估算，还受到预热后实际显存状态影响。

KV cache 保存注意力计算过程中与历史 token 相关的中间状态。缓存越充分，长上下文请求或连续请求越有机会减少重复计算；但缓存占用显存，也会与权重、临时工作区、通信缓冲和其他运行时分配竞争。因此，缓存扩大可能提高吞吐，也可能压缩突发请求的安全余量。不能把官方给出的“多数模型更大 cache”理解为每个业务都能无条件提速。

升级前后至少应固定以下变量：模型版本、量化方式、GPU 型号与数量、上下文长度、并发度、请求分布和预热方式。测试脚本不需要复杂，关键是输入和观察窗口一致。例如可以记录服务启动信息、GPU 显存和请求统计：

```bash
nvidia-smi --query-gpu=name,memory.used,memory.total,utilization.gpu --format=csv
curl -sS http://127.0.0.1:8000/metrics > metrics-after.txt
```

如果服务地址或指标端点不同，应以部署实际配置替换。比较时不要只看平均吞吐，还要观察首 token 延迟、生成阶段速度、排队时间、显存峰值、请求失败率和长上下文请求的尾延迟。至少准备短输入、长输入、低并发和目标并发四组样本。这样才能判断性能变化来自 cache、调度、输入长度还是测试噪声。

## 默认 block size 变化不是小参数

官方升级提示还指出，默认 block size 现在是 64。block size 参与 KV cache 的分块管理，因此它不仅是一个配置文件里的整数，也会影响缓存碎片、分配粒度和可用容量的表现。即使业务没有显式设置该参数，默认值变化也可能让同一套请求在显存边界附近呈现不同结果。

这类变化最容易在“正常流量”下被掩盖：短请求和低并发测试可能全部成功，但长上下文与突发并发会触发更早的排队、拒绝或显存不足。升级验收应覆盖最接近业务上限的组合，而不是只选一个容易通过的冒烟请求。

一个实用的检查清单如下：

1. 记录旧版本实际生效的 block size，不只记录配置文件中的候选值。
2. 用相同模型和相同上下文长度比较显存峰值与可接受并发。
3. 增加接近上下文上限的请求，观察是否出现持续排队或请求失败。
4. 在服务重启和连续运行两个阶段分别采样，区分启动期分配与运行期碎片。
5. 将 block size 与 cache 相关配置纳入发布差异，而不是只比较镜像 digest。

若旧版本使用了显式 block size，不能因为新版本有默认值就直接删除配置。更稳妥的做法是先保留业务已验证的显式设置，在独立灰度中验证默认行为，再决定是否接受新默认值。这样可以把“版本升级”和“参数策略迁移”拆成两个可定位的变化。

## 依赖与硬件镜像必须单独验收

vLLM 0.34.0 的官方说明还列出两个环境层面的升级信号：要求 `huggingface_hub >= 2.0.0`，并且 ROCm 7.2 镜像已经移除。前者属于 Python 依赖约束，后者属于容器与硬件软件栈约束。它们不能用同一条测试代替。

依赖检查可以在目标环境中执行：

```bash
python -m pip show vllm huggingface-hub
python -c 'import vllm, huggingface_hub; print(vllm.__version__); print(huggingface_hub.__version__)'
```

镜像检查则要确认实际使用的 tag、基础运行时和 GPU 后端，而不是只看仓库里的默认值：

```bash
docker image inspect <image:tag> --format '{{json .RepoTags}}'
```

如果原有部署依赖 ROCm 7.2 镜像，不能把镜像 tag 改成相近名称后直接上线。应先确认替代镜像是否存在、是否包含目标 GPU 所需运行时，并用真实模型完成启动和请求验证。材料只证明 ROCm 7.2 镜像在该版本中被移除，并没有证明任意替代 tag 的兼容性，因此替代方案必须由具体环境重新提供证据。

## 把升级验收分成四个闸门

第一道是配置闸门：扫描已移除的 V1 开关，检查 block size、模型路径、并发和显存相关配置，确认没有隐式覆盖。第二道是启动闸门：在隔离环境启动服务，保存完整日志，验证依赖、模型加载、GPU 初始化和指标接口均正常。第三道是行为闸门：使用固定请求集，对比成功率、首 token 延迟、生成速度、排队时间和显存峰值。第四道是压力闸门：将并发和上下文长度逐步推向业务上限，记录失败类型和恢复行为。

每道闸门都应有明确的失败动作。配置闸门失败，停止发布；启动闸门失败，回到旧镜像或修正环境；行为闸门出现不可接受的尾延迟，先固定显式 cache 与 block size 再复测；压力闸门出现显存不足或持续排队，则不能用降低测试规模来“证明通过”，而应重新评估容量和限流策略。

回退也需要提前验证。旧镜像、旧依赖和旧启动参数应能在同一发布系统中重新生成，不能把回退寄托在某台机器上残留的本地缓存。尤其当新版本改变了镜像来源或依赖上限时，应在发布前确认旧版本制品仍可拉取、模型缓存仍可读、监控和流量切换仍然可用。

## 结论：升级的最小单位是运行时契约

vLLM 0.34.0 给出的真正工程信号，不是某个单独性能数字，而是推理服务的兼容性边界正在从“接口能否调用”扩展到“运行器、缓存、分块、依赖和硬件镜像是否共同满足契约”。V1 移除要求清理旧开关；KV cache 默认变化要求重做显存与吞吐基线；block size 变化要求覆盖边界流量；依赖和 ROCm 镜像变化要求验证整个交付环境。

因此，最小可接受的升级证据不应只是新容器返回 200，而应是一组可追溯记录：最终环境配置、启动日志、固定请求集结果、资源峰值、压力失败边界以及可执行的回退路径。只有当这些证据都与业务目标对齐，版本号变化才真正转化成了可控的工程变更。
