## 论坛的重量，往往不在功能列表里

论坛看起来是一个典型的 CRUD 应用：用户注册登录，创建主题，回复楼层，点赞收藏，再加一个后台管理页面。但当这些功能真正组合起来，系统通常会迅速膨胀：前端需要状态管理和构建工具，后端需要路由、ORM、会话、CSRF 防护，数据库还要承担列表分页、计数、关系查询和后台统计。

NodeLoc 上有人分享了一个直接运行在 Cloudflare Workers + D1 上的轻量论坛项目 cf-bbs · Nexus。它的价值不只是“可以免费部署”，而是提供了一种反方向的架构样本：把页面生成、路由和安全控制收拢到一个 Worker，把结构化数据交给 D1，尽量不引入第三方运行时依赖，客户端只负责渐进增强。

根据项目仓库和项目说明，这个实现约有 5k 行 TypeScript，使用服务端直出 HTML，首屏不依赖 JavaScript；CSS 和 JavaScript 由 Workers Static Assets 返回。它还将分页、计数和关系数据放到索引友好的 SQL 查询中，并在写操作中使用 `DB.batch()` 保证一组变更的一致性。这里的重点不是行数本身，而是边界收敛：少一层运行时，就少一组版本、构建和部署问题；但更多的业务约束也必须由应用代码明确承担。

## 一次请求如何穿过边缘应用

这类系统可以抽象成四层。

第一层是 Worker 入口。请求进入后，入口负责运行时上下文、安全响应头、CSRF 检查、限流和错误处理。第二层是极简路由，根据 HTTP 方法和路径参数把请求交给具体处理函数。第三层是业务逻辑，包括认证、主题、回复、通知、搜索和管理操作。第四层是 D1 数据库及静态资源。

这种划分与传统 Node.js 服务并没有本质冲突，但执行环境不同。Worker 不是一台长期运行、可以随意保存进程状态的服务器。内存限流只能覆盖当前运行实例的短期请求，不能被当作跨实例的全局计数器；需要持久化的状态必须进入 D1 或其他明确的数据服务。项目说明中的“登录/注册、发帖、API 三档内存限流”也应理解为应用层的基础保护，而不是完整的分布式反滥用方案。

服务端渲染则改变了前端的默认职责。首页、主题详情、管理页面都可以由 Worker 直接生成 HTML，点赞、收藏和回复预览再通过渐进增强提供更顺滑的体验；即使没有 JavaScript，项目也保留表单回退路径。这个选择降低了首屏对前端资源加载的依赖，也让搜索引擎可直接获得页面内容，但代价是模板、表单状态和错误反馈都必须在服务端设计清楚。

因此，SSR 并不等于“前端更简单”。它只是把复杂度从浏览器状态管理转移到了请求处理、模板数据和安全校验。对于以文本内容为主、交互节奏不高的论坛，这种转移通常值得；对于高度实时、重交互的编辑器或协作应用，则需要重新评估。

## D1 查询设计决定轻量架构能否成立

轻量架构最容易被低估的部分是数据库访问。一个主题列表看似只需要查询主题，但页面通常还需要作者信息、回复数、最后回复时间、当前用户是否点赞或收藏，以及置顶和加精状态。如果每一项都单独查询，服务端渲染很快会变成 N+1 查询集合。

项目说明给出的方向是：页面级 SQL 尽量走索引，列表分页、计数和关系数据一次查询完成。工程上可以把它转化为几条检查规则：

1. 列表分页优先使用明确的排序字段和索引，避免把全表读入 Worker 后再切片。
2. 主题详情需要的作者、版块和互动状态，应在 SQL 层或受控的批量查询中合并获取。
3. 计数逻辑要明确是实时计算、冗余字段还是聚合查询，不能因为页面需要一个数字就重复扫描大量回复。
4. 写操作涉及主题、回复、通知或统计更新时，检查是否需要放进同一个 `DB.batch()`。
5. 搜索、通知和举报队列要单独检查索引与分页，不能只验证首页列表。

可以先用下面的命令建立本地数据库并执行项目提供的迁移、种子数据：

```bash
npm install
npx wrangler d1 create cf-bbs
npm run db:migrate
npm run db:seed
npm run dev
```

本地启动后，项目说明中的默认行为是首次访问进入 `/setup`，创建第一个管理员账号，并同时生成一篇欢迎主题。验证时不应只看首页是否打开，而应依次检查：首次初始化是否只能创建预期的管理员；未登录用户能否浏览公开内容；登录后是否能创建主题和回复；点赞、收藏、通知和举报是否产生正确的关联记录；后台操作是否受到角色限制。

如果需要验证分页，不要只创建少量数据。至少应检查第一页、最后一页、空结果和排序边界。尤其要观察删除主题、锁定主题或删除回复后，计数和最后回复信息是否仍然一致。这些才是“轻量数据库层”是否可靠的实际证据。

## 认证与 OAuth：少依赖不等于少安全工作

项目说明列出了较完整的安全设计。会话使用 HMAC-SHA256 签名令牌，并配合 `HttpOnly`、`SameSite=Lax` 和 `Secure` 属性；密码使用 PBKDF2-SHA256，默认迭代次数为 10 万；CSRF 使用双提交 Cookie 加表单隐藏字段或 `X-CSRF-Token`，比较时使用常量时间比较；Markdown 则先整体转义，再生成允许的标签，链接只允许 `http(s)` 和站内路径。

这些机制分别对应不同风险，不能互相替代。HttpOnly 主要降低脚本直接读取会话 Cookie 的机会，不能阻止服务端错误地执行恶意请求；CSRF 防护不能代替输出编码；Markdown 过滤也不能替代权限检查。一个安全检查清单至少应覆盖：

- 登录、注册、修改密码和绑定账号是否有独立的速率限制。
- 所有改变状态的请求是否校验 CSRF，而不是只保护登录表单。
- 普通成员是否无法通过参数修改他人内容或调用管理动作。
- 退出登录和全端下线是否能让旧令牌失效。
- 用户提交的链接、图片和 Markdown 是否经过统一处理。
- 响应是否包含项目声明的 CSP、`X-Frame-Options`、`nosniff`、`Referrer-Policy`、HSTS 和 `Permissions-Policy` 等安全头。

OAuth 的实现也不是把按钮放到登录页那么简单。项目内置 GitHub、Google、GitLab、Gitee、Discord 和通用 OIDC 登录方式，未配置对应环境变量时，入口会隐藏。通用 OIDC 可以对接提供 `.well-known/openid-configuration` 的服务，回调地址则必须与正式域名一致。

部署前可以按下面的方式写入密钥：

```bash
npx wrangler secret put SESSION_SECRET
npx wrangler secret put GITHUB_CLIENT_ID
npx wrangler secret put GITHUB_CLIENT_SECRET
```

`SESSION_SECRET` 是必需项，项目说明要求使用 32 位以上随机串。验证 OAuth 时，应分别测试首次登录、已有邮箱账号的合并、已绑定账号登录、解绑后的行为和回调地址错误。特别要确认“邮箱自动合并”是否符合站点的账户政策：便利性提高了，但身份关联一旦判断错误，影响会比普通登录失败更大。

## 部署流程与失败边界

线上初始化与本地初始化不是同一件事。根据项目提供的部署步骤，可以按以下顺序操作：

```bash
npx wrangler d1 create cf-bbs
npx wrangler d1 migrations apply cf-bbs --remote
npx wrangler d1 execute cf-bbs --remote --file=./seed.sql
npx wrangler secret put SESSION_SECRET
npm run deploy
```

数据库标识需要写入 `wrangler.toml`，站点名称、站点标语和是否允许注册可以放在 `[vars]` 中调整。发布后，还需要在 Workers 的 Domains & Routes 中绑定自定义域名，再把 OAuth 回调地址改为正式域名。验证发布是否完成，应从外部访问正式域名，而不是只看部署命令是否返回成功：检查 DNS、HTTPS、首页、登录回调、静态资源、数据库读写和管理入口。

这个方案也有明确失败边界。

第一，免费版 Workers 的单次请求 CPU 上限较低。项目说明特别指出，PBKDF2 默认 10 万次迭代可能触顶，建议使用付费计划，或将 `PASSWORD_ITERATIONS` 调整为 50000。降低迭代次数会减弱密码哈希的计算成本优势，因此这不是“调小参数就完成优化”，而是套餐、登录耗时和密码安全之间的取舍。调整后必须重新验证登录、注册、修改密码和高并发失败行为。

第二，内存限流不能承担全局风控。多个 Worker 实例之间不共享同一内存，攻击者也可能通过分布式请求绕过单实例计数。正式站点如果需要更强保护，应在边缘 WAF、平台能力或持久化限流层补足，而不能把 README 中的三档内存限流理解成完整防护。

第三，D1 适合结构化论坛数据，但并不意味着任何数据库工作负载都适合边缘化。大量全文检索、复杂报表、持续实时推送或高频写入，都可能要求额外的索引、异步任务或独立服务。轻量的核心不是“所有东西都塞进 Worker”，而是只把与请求路径直接相关的职责放在那里。

## 一份可复用的上线检查表

在真正发布前，可以把检查分成四组。

**功能组：**注册、登录、退出、密码修改、主题、回复、点赞、收藏、通知、举报、搜索和后台角色逐项验证；同时检查移动端页面、暗色模式、语言切换和 RSS、sitemap、robots、OG 标签及 canonical 是否按预期输出。

**数据组：**迁移能否重复执行而不破坏数据；种子数据是否只用于初始化；分页、计数和最后回复是否一致；删除、锁定、置顶和加精是否产生正确状态；批量写操作失败时是否留下半完成记录。

**安全组：**检查 Cookie 属性、CSRF、密码哈希参数、会话失效、XSS、开放重定向、权限边界、OAuth 回调和安全响应头。对每个状态改变接口，记录“未登录、普通成员、版主、管理员”四种结果，而不是只测试成功路径。

**运行组：**检查 Worker CPU 耗时、登录请求是否触及套餐限制、D1 错误是否能被识别、静态资源是否正常返回、域名和 HTTPS 是否生效，以及部署后旧版本配置是否仍会影响回调或密钥读取。

## 原创结论：边缘论坛的核心不是省服务器费

Workers + D1 论坛最值得借鉴的地方，不是“把 VPS 换成免费套餐”，而是重新定义了应用的最小运行单元：请求进入边缘，页面由服务端生成，数据访问受索引和批量写约束，安全能力在入口统一处理，浏览器只承担渐进增强。

这种设计适合内容型社区、内部知识库、项目讨论区和低频管理系统。它的优势是部署面小、首屏路径短、基础设施责任清晰；它的限制也同样清楚：没有长期进程状态，内存限流不是全局治理，密码计算受 CPU 套餐约束，数据库查询设计必须先于页面开发。

所以，判断一个论坛是否适合边缘运行时，不应先问“免费额度够不够”，而应先问四个问题：请求是否可以无状态处理，核心查询能否稳定索引化，写操作能否明确划分一致性边界，安全与观测是否有平台之外的补强路径。如果四个答案都清楚，轻量架构才不是删掉依赖后的偶然成功，而是一套可验证、可迁移、也知道何时应该停止扩张的工程方案。
