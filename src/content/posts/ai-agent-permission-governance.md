## 先区分两件事：Agent 能做什么，和什么时候可以做

AI Agent 的能力边界，通常由工具集合决定：它可能运行命令、读取文件、访问路径或打开 URL。但真正影响安全性的，不只是工具是否存在，而是每次调用是否需要人工确认、谁可以改变确认规则，以及系统如何处理无法明确判断的请求。

这两个问题经常被混在一起。把所有工具都关闭，确实可以降低误操作概率，却也让 Agent 退化成只能输出建议的聊天窗口；把所有工具都设置为自动批准，则把一次自然语言请求直接连接到了本地文件系统、命令执行环境和外部网络。更稳妥的设计，是把“能力授权”和“调用决策”分成两层：第一层规定 Agent 可以接触哪些资源，第二层对具体请求进行风险判断。

GitHub 在 2026 年 10 月 26 日宣布，Copilot assisted permissions 在 Copilot CLI、Copilot app 和 Visual Studio Code 中正式可用。其基本机制是：当 Copilot 请求运行命令、访问文件系统路径或打开 URL 时，由语言模型评估请求；被判断为明确安全的请求可以自动继续，其他请求仍需要用户批准。这不是“自动批准全部操作”，而是将人工确认从每一步操作，调整为对不明确风险的操作保留人工闸门。

Qwen Code 的 v0.26.2-preview.1 则提供了另一组值得观察的信号：该预览版本加入了会话权限规则和自动批准，增加了实验性的共享 Agent Loop，并支持在该循环上以 headless 方式运行；同时还修复了 serve token 解析可能受到项目环境注入影响的问题。这里必须标注证据等级：这是官方仓库的预发布版本说明，不等同于稳定版承诺，也不能据此推断所有实现细节已经固定。

## 权限系统可以看成三段式管线

一个可治理的 Agent 权限系统，至少可以抽象为“请求生成、风险判定、策略执行”三段。

第一段是请求生成。Agent 根据任务决定要运行某条命令、读取某个路径、打开某个 URL，或者调用其他工具。此时请求应当携带足够的上下文：目标资源是什么、请求来自哪一轮会话、操作是读取还是写入、是否会产生外部副作用。没有上下文的权限判断，只能依赖字符串猜测，容易把看似相同的操作误判为同一风险。

第二段是风险判定。Copilot assisted permissions 的公开描述明确了两种结果：明确安全的请求自动继续，其他请求需要批准。这意味着判定器并不需要证明请求“绝对安全”，而是先识别能否归入低风险集合。剩余请求进入人工决策。这种设计的关键不是让模型拥有最终权限，而是让模型负责降低低风险操作的确认噪声。

第三段是策略执行。判定结果必须受到更高层级策略约束。GitHub 的企业控制允许管理员阻止 Allow All，同时保留 Assisted；也可以单独禁用 Assisted，并为新会话设置默认权限模式。如果默认模式不可用或被策略禁止，会话将以人工批准启动。由此可以看出，权限模式不是单纯的个人偏好，而是存在组织级上限和回退路径。

Qwen Code 的会话权限规则和自动批准，说明另一条工程路线：把规则显式绑定到会话或托管工作区，再由 Agent Loop 反复执行。它更接近“策略驱动的自动化”，但由于该版本仍是 preview，使用时应把规则格式、继承关系和默认行为视为需要持续验证的接口，而不是稳定契约。

## 为什么“自动批准”不等于“无人值守安全”

自动批准最容易被误解成效率开关。实际上，它改变的是控制点的位置：原本由人逐条点击确认，现在由规则或模型在请求发生时决定是否放行。只要请求边界没有被准确描述，自动化就会扩大错误的影响面。

第一类失败边界是路径语义。读取项目目录中的源代码，与读取用户目录中的凭据文件，都是“读取文件”，但风险完全不同。仅按操作类型放行是不够的，还需要对路径范围、符号链接、生成文件和工作目录变化进行约束。

第二类失败边界是命令组合。单个低风险命令可能在管道、重定向、命令替换或脚本加载后产生不同效果。权限判定如果只检查命令开头，而不解析完整执行链，就可能出现“看起来安全，组合后危险”的情况。因此，工程上不能把模型对命令文本的判断当成操作系统级沙箱。

第三类失败边界是 URL 和外部副作用。打开文档页面与向外部服务提交数据，可能都表现为访问 URL。真正需要审查的不是域名字符串本身，而是请求方法、参数、身份凭据、数据来源以及是否会触发写操作。

第四类失败边界是环境注入。Qwen Code 该预览版本专门修复了 serve token 解析受到项目环境注入影响的问题。这个变更提醒我们：权限控制不仅存在于最终工具调用，也存在于 Agent 启动、服务端口、令牌解析和项目配置加载这些“前置阶段”。如果令牌或策略来源可以被项目目录中的环境变量悄悄改变，那么后面的审批逻辑再严谨，也可能建立在错误的身份和上下文之上。

## 可复现的最小验证流程

如果要在团队中评估 assisted 或自动批准模式，不应从“能不能少弹几个确认框”开始，而应建立一组可重复的行为检查。

首先，记录基线。新建一个最小项目，准备只读文件、可修改文件和项目外文件三类资源；再准备无副作用命令、会写入磁盘的命令，以及包含外部 URL 的请求。测试前明确当前权限模式，避免把上一次会话的状态当成实验变量。

其次，按官方入口选择模式。在 Copilot CLI 中运行：

```text
/permissions
```

然后选择 `assisted`。官方说明中，明确安全的请求应自动继续，其他请求应进入批准流程。验证时不要只观察“是否弹窗”，还应记录请求类别、判定结果、是否出现人工批准、实际影响范围和失败后的会话状态。

再次，分别测试边界：

```text
只读项目文件
写入项目内的临时文件
访问项目目录之外的文件
运行带重定向的命令
打开外部 URL
使用项目环境变量启动服务
```

这些不是预设的官方结果，而是测试样例。材料并没有给出每一类请求的固定判定，因此不能提前声称哪些一定会自动放行。正确做法是把结果记录为策略行为，并在版本升级后重新执行。

最后，验证组织级回退。若企业策略禁止 Assisted 或 Allow All，检查新会话是否回到人工批准模式；若默认模式不可用，也应验证会话是否仍能启动，并确认用户不会在没有提示的情况下获得更宽权限。对于 Qwen Code 的 preview 能力，则应额外记录版本号、会话规则来源、自动批准范围以及 headless 运行时是否仍遵循同一套策略。因为预发布版本可能改变配置格式或执行语义，测试报告必须包含版本和提交标识，而不能只写“Qwen Agent 可用”。

## 规则、模型与沙箱：三种控制手段如何取舍

规则的优点是可审计、可复现。团队可以明确写出哪些路径、命令或域名属于允许范围，并在代码审查中讨论变更。缺点是维护成本高，规则很快会遇到脚本封装、软链接、跨平台命令差异和新工具加入等问题。

模型判定的优点是能够利用自然语言上下文，减少低风险操作的人工确认。缺点是判定具有概率性，且模型看到的上下文可能不完整。它适合做“低风险筛选器”，不适合成为唯一的安全边界。官方对 Assisted 的描述本身也保留了人工批准路径，这正是这种取舍的体现。

沙箱的优点是即使 Agent 做出错误决策，文件系统、网络或进程权限仍可被物理隔离。缺点是环境搭建复杂，调试和工具兼容性成本更高。对于一次性的本地辅助任务，Assisted 加人工审批可能已经足够；对于无人值守、托管工作区或 headless Agent，沙箱、最小凭据和审计日志的重要性会显著上升。

更现实的组合不是三选一，而是分层使用：组织策略限制最高权限，规则限定资源范围，模型处理低风险请求，沙箱承接不可避免的错误。任何一层都不应被描述成“完全安全”。

## 面向团队的权限上线清单

上线前至少确认以下问题：

1. 是否明确区分个人默认设置与企业强制策略，且高风险模式可以被组织禁用？
2. 自动批准的对象是操作类型、资源范围，还是完整请求上下文？
3. 项目目录之外的文件、凭据文件、环境变量和令牌是否有单独规则？
4. 命令中的管道、重定向、脚本加载和子进程是否会改变风险判断？
5. 外部 URL 是否区分读取、上传、认证和写入行为？
6. headless 运行是否继承交互式会话的权限策略，还是拥有另一套默认行为？
7. 每次放行和拒绝是否能关联到会话、版本、策略来源和实际资源？
8. 升级到预览版本后，是否重新执行了拒绝、回退和环境注入测试？

## 原创结论：权限体验的终点不是“少确认”，而是“可解释地确认”

Agent 权限系统的成熟指标，不是自动批准比例，也不是完全无人干预，而是用户能否回答三个问题：这次请求要影响什么、为什么被自动放行或要求批准、如果策略改变会回退到哪里。

GitHub assisted permissions 的正式可用，表明业界正在把“模型参与权限判断”做成产品级能力，但其安全前提仍是企业策略和人工回退。Qwen Code 预览版把会话规则、自动批准、共享循环和 headless 执行放在同一批变更中，则把问题推进到了更难的阶段：当 Agent 不再只是交互式助手，而是持续运行的执行循环时，权限必须成为会话生命周期的一部分。

因此，团队不应把自动批准当作效率按钮，也不应把 preview release 当作稳定接口。更可靠的路线是：先限定资源，再引入低风险自动放行；先保留人工回退，再逐步扩大规则覆盖；每次升级都用可重复的边界测试验证行为。只有当权限决策可解释、可回退、可审计，Agent 才真正具备进入工程工作流的基础。
