## 一句话结论

llama.cpp b12651 官方 Release 中宣布了“WebGPU add ROLL support”，同时说明测试应保持在不同后端之间可移植。这一证据只能证明：某个提交在源码或测试层面为 ROLL 增加了支持，并以跨后端便携性作为改动目标；它不能证明所有模型都因此更快，也不能证明 CPU、Vulkan、CUDA、ROCm、WebGPU 等后端都会得到同等正确性、性能和兼容性。

本文不把一条 Release Notes 当成吞吐量承诺，也不把一次单元测试当成端到端推理结论。更合理的工程观点是：先区分“算子已实现”“测试已覆盖”“发布产物可运行”和“目标工作负载可验收”四个证据层，然后逐层收窄结论。

## 证据等级与适用范围

当前材料中，b12651 的直接证据来自 ggml-org/llama.cpp 的官方 GitHub Release。该页面明确列出提交版本、签名状态、主要改动和预编译产物范围，属于项目发布证据。它仍然是 Pre-release，不属于已标识为稳定正式版的证据。

作为对照，OpenAI Codex 的 0.173.0-alpha.4 页面说明了另一个常见现象：一份发布页面可以提供标签、提交、资产数量等交付信息，但并不自动证明发布说明中的所有能力已经覆盖所有平台。两份 Release 都处于预发布或演进阶段，因此最重要的是把标签视为可追溯入口，而不是将标签描述直接升级为生产承诺。

本文只讨论 ROLL 这一变更可验证的边界。材料没有提供 ROLL 的数值语义、适用模型、性能数据或各后端基准，因此不会猜测算子含义，也不会声称某个硬件获得了具体加速。

## ROLL 增加了什么，而没有增加什么

Release 中的核心改动被概括为“WebGPU : add ROLL support”，并补充了“tests : keep ROLL cases portable across backends”。这至少涉及两个工程对象：

第一，WebGPU 后端需要识别并执行 ROLL 对应的计算；第二，测试用例需要避免依赖只存在于某个后端的行为、设备差异或数值约定。

只有后端能力描述，没有必要意味着端到端可用。一个算子可能通过某些形状的测试，却不支持特定维度组合；可能在模型加载阶段可识别，却在实际推理图中走到另一条实现；也可能测试通过但速度低于现有实现。反过来，测试可移植也不代表现有模型一定触发该算子，更不代表吞吐量由算子决定。

因此，“添加支持”应被理解为实现分支扩展，而不是系统级性能提升。工程中真正需要确认的是：目标图是否实际调用 ROLL、目标后端是否成功落地、结果是否在容差内一致，以及最终工作负载是否满足延迟和吞吐要求。

## 为什么便携测试比参数表更重要

跨后端测试的价值，是使验收标准不绑定单一 GPU 厂商或单一运行环境。若测试只针对一块设备，一个通过结果可能同时受到驱动版本、共享内存配置、编译选项和硬件实现差异影响。将测试保持便携，并不能消除这些差异，却可以减少测试用例自身的后端假设。

工程上的便携性主要有三层：

1. 形状便携：测试不应假设某个固定维度必然存在。
2. 精度便携：判定应使用相应精度可表达的容差，而不是强求位级完全一致。
3. 执行便携：用例应能在不同后端中读取相同输入并得到可比较输出，而不依赖后端私有设备行为。

如果没有这三层，测试通过只能证明某个驱动上的某次运行可通过，无法迁移到新机器。相反，即使测试保持便携，性能仍需另行测量，因为正确性和效率是不同验收维度。

## 可复现的源码核验

下面的检查适合在隔离工作区中核对 b12651 对应提交，不会依赖图形环境：

```bash
# 使用官方仓库中的精确提交入口
git clone https://github.com/ggml-org/llama.cpp.git
cd llama.cpp
git fetch --tags
git checkout f5e6915

# 核对版本、提交与当前工作区
git show -s --decorate --oneline HEAD
git status --short

# 定位 ROLL 的实现、声明和测试入口
git grep -n -E 'ROLL|roll' -- src ggml test tests 2>/dev/null | head -n 120
```

这组命令只能回答“提交中是否存在 ROLL 字符串、实现或测试”。它不能回答“某台机器是否具备可用加速”。核验时应记录完整提交、操作系统、编译器、后端、驱动和硬件型号；只记录版本号会丢失大量验证背景。

还可以通过原始标签核对发布入口，而不是依赖自动部署脚本自行拼接版本：

```bash
# 确认发布标签指向精确提交
git rev-parse b12651^{commit}
git ls-remote --tags origin refs/tags/b12651
```

若本地提交与发布标签不一致，应停止验收，不再把本地代码的成功或失败归因于 b12651。

## 分层验收矩阵

建议把验收拆成表格之外的执行顺序，而不是一次性跑出一个综合结论。

### 第一层：源码与编译

确认提交为 f5e6915，发布标签可解析到该提交，并能在目标编译器和后端配置下完成构建。构建失败时，要区分缺少依赖、工具链版本不受支持、后端未启用和源码本身不兼容。

此阶段至少记录：提交 SHA、构建配置、编译器版本、后端标识、产物是否来自官方 Release 资产或自行构建。自行构建与官方产物不是同一证明，不能互相替代。

### 第二层：算子测试

使用仓库中现有的 ROLL 测试入口，优先在至少两个后端上运行相同形状和容差配置。测试应覆盖正常形状、边界形状和目标模型实际可能触发的形状；若仓库没有公开的便携入口，不应自行发明测试名称后声称已通过。

一个合格的输出至少包含：测试名称、输入形状、数值精度、容差、后端、通过或失败状态，以及失败时的最小复现输入。

### 第三层：模型级推理

算子测试通过后，再验证目标模型能加载、执行推理并产出可比较结果。模型级验收应使用固定提示、固定解码参数、固定随机种子或明确说明随机性来源，并至少覆盖首次运行和后续运行。

同一个模型在同一设备上重复执行时，如果结果不稳定，不能把首次结果当成性能基线。应分别记录冷启动、预热后、连续请求以及显存不足时的行为。

### 第四层：工作负载验收

最后才进入生产指标：每秒生成 token 数、首 token 延迟、显存峰值、连续负载下的稳定性和失败恢复能力。这里应使用目标业务的输入长度、并发量和部署形态，而不是只采用一个短提示。

性能提升应该由多个重复样本比较，且至少报告中位数和尾延迟。只看平均值可能掩盖偶发的首次编译、驱动抖动或显存回收问题。

## 最小检查清单

- [ ] 确认是官方 b12651 标签还是其他相近构建。
- [ ] 确认本地 SHA 与 Release 页面对应提交一致。
- [ ] 区分官方产物、自行构建和社区第三方包。
- [ ] 记录目标后端是否处于启用状态。
- [ ] 确认 ROLL 测试确实被执行，而不是只构建了测试二进制。
- [ ] 至少跑相同测试在两个可用后端上做差异比较。
- [ ] 使用目标模型，而非只用合成张量。
- [ ] 固定输入、精度、容差和解码参数。
- [ ] 记录冷启动、预热、并发和尾延迟数据。
- [ ] 保存失败最小复现及完整环境信息。

## 失败边界与回退条件

以下任何一项成立，都不应继续扩大结论：

首先，源码和发布标签无法对应时，不能把测试结果归因于 b12651。其次，只有合成张量通过时，不能推断目标模型可用。第三，只在 CPU 或单一 GPU 后端通过时，不能推断 WebGPU 或其他后端支持一致。第四，只验证了编译成功时，不能推断运行正确。第五，只验证了一次短模型推理时，不能推断并发吞吐和长时间稳定性。

回退条件应在升级前定义，例如任一目标模型在固定容差下出现数值偏差、目标设备发生崩溃或资源耗尽、首 token 延迟超过既定上限、连续负载出现不可恢复错误，就恢复到已验证的旧版本或旧后端。

回退不仅是替换二进制，还应包括配置、模型缓存、运行时依赖和系统服务状态。只回退应用版本而保留不兼容的缓存或驱动组合，可能再次触发相同问题。

## 工程取舍：何时值得升级

对于研究环境，可以优先把 b12651 当作可回滚的预发布候选：验证源码可追溯、基本算子测试通过，再观察目标模型是否使用该实现。对生产环境，应提高证据门槛：至少要求目标后端、目标模型、目标并发和目标错误恢复都完成验收。

该取舍不是保守主义，而是证据分层。预发布版本的价值，在于尽早暴露兼容性问题；它的风险，也正来自发布成熟度尚未通过所有模型、设备和负载的完整验证。

另一个取舍是构建速度与覆盖率。只跑一次小型模型、单一形状和一个后端，成本低但结论窄；覆盖多个形状、精度和平台，成本高但能发现实现假设。工程团队应基于风险选择覆盖深度，而不是用一个“全绿”测试集合掩盖未覆盖区域。

## 原创结论

b12651 的关键贡献不是让 llama.cpp 突然获得“全局加速”，而是让 ROLL 在源码与便携测试层面迈出了一步。真正的验收单位不是发布版本号，而是“提交—后端—形状—模型—负载—设备”这一条完整证据链。

因此，最稳妥的技术描述是：b12651 宣布了 WebGPU 对 ROLL 的支持，并要求测试保持跨后端便携性，但官方材料没有提供性能提升、全模型兼容性或全后端通过结论。把这句话作为边界，升级决策才能同时保留可验证性和工程审慎。
