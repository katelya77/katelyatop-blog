## Agent 会话不是一段对话，而是一组待完成的工作

一次 Agent 运行通常不只包含模型生成文本：它可能等待工具审批、等待用户补充信息，也可能已经启动一个尚未结束的后台任务。把这些阶段都看成“聊天记录”，就容易忽略一个关键问题：进程退出以后，哪些工作仍然有效，哪些动作已经发生，恢复时应该从哪里继续？

Qwen Code v0.28.6 的发布说明给出了一组值得放在一起观察的变化：托管会话可以在等待工具审批、问题回答或后台工作时挂起，并在 Harness 崩溃后通过冷恢复继续；Headless 会话和 Ink TUI 默认使用 event-bus kernel；发送新消息不再停止正在运行的 shell 命令，而是将其移至后台，并把命令 ID、输出位置和状态提供给模型；Web Shell 为提示提交使用幂等键，并对瞬时失败静默重试两次。这些是该版本发布说明明确列出的能力，不等于对所有 Agent 产品或部署方式的普遍保证。

它们共同指向一个工程主题：运行中的 Agent 应被建模为可恢复的工作流，而非依赖单个进程内存的长函数。这里的“工作流”是对这些功能关系的架构解读，并非发布说明披露了内部存储格式或完整实现细节。

## 从等待、执行到恢复：状态必须有归属

可以把会话抽象为几个逻辑状态：正在处理、等待外部输入、等待工具审批、工具仍在运行、已完成，以及可恢复的中断状态。重点不在状态名称，而在每次转换是否有明确的所有者和可观察依据。

例如，等待审批时，模型不能把“工具已获准”当作事实；任务应该停在等待边界，直到审批结果成为可用事件。shell 命令被移入后台后，会话也不能只记住“已启动”这一事实：后续需要能关联对应命令，并区分仍在运行、已有输出、失败或结束。发布说明提到命令 ID、输出位置和状态会提供给模型，这至少表明这些信息在该交互路径中具有后续用途；但它没有说明状态如何持久化、输出保留多久，或跨机器恢复时使用什么存储。

冷恢复的价值正在于把“进程活着”从工作继续的必要条件中移除。要做到这一点，系统至少需要某种足以重新识别未完成工作的状态记录，并能在恢复后重新接上等待点。至于是否采用事件日志、快照或其他机制，材料没有说明，不能把某一种实现方式写成 Qwen Code 的既定架构。

event-bus kernel 则可以从另一个角度理解：会话各阶段以事件推进，比多个界面各自维护一套隐式控制流更容易定义等待、取消和继续的边界。这里同样只能把它作为设计推论；发布说明只确认 Headless 会话和 Ink TUI 默认使用该内核，并称取消的运行会在 10 秒内完成收敛。这个指标不应外推为任何负载、任何工具或所有运行环境下的取消时延上限。

## 重试不等于“再发一次”：幂等性要落在副作用之前

网络请求失败时，客户端往往无法确定服务器究竟有没有处理请求。若 Web Shell 将同一个提示重复提交，可能产生重复任务或重复副作用。幂等键的核心用途，是让系统能够识别“这是同一次提交的再次尝试”，而不是把重试当作一条新意图。Qwen Code v0.28.6 的发布说明确认 Web Shell 提交提示时使用幂等键、对瞬时失败静默重试两次，并显示消息级别的重新发送提示；没有披露键的生成方式、服务端去重期限或覆盖哪些错误类型。

工程上应把重试分成三层验收。第一层是提交身份：同一用户动作的网络重试应沿用同一幂等身份。第二层是副作用：服务端不能因为传输重放而启动多份等价工作。第三层是用户可见性：自动重试耗尽后，界面要能表达失败并给出可控的再次发送入口。仅仅看到客户端发出两次请求，并不能证明幂等有效；必须检查服务端工作记录或等价的可观测结果。

可以用一个与产品无关的检查脚本校验结构化事件日志。下面假设测试环境能导出 JSONL，且测试埋点包含 `request_id`、`idempotency_key`、`attempt` 和 `job_id`；这只是建议的验收数据契约，不是 Qwen Code 已公开的日志格式：

```bash
jq -s '
  group_by(.idempotency_key)[] |
  {key: .[0].idempotency_key,
   attempts: map(.attempt) | unique,
   jobs: map(.job_id) | unique}
' events.jsonl
```

对同一逻辑提交，检查重试记录是否关联相同键，并验证产生的业务任务数量符合预期。若日志没有稳定的提交身份和任务身份，测试就无法区分“请求重试”与“重复创建任务”；这时应先补齐可观测性，而不是把脚本的输出当成可靠性结论。

## 用故障注入验证恢复，而不是只验证正常路径

可以在隔离测试环境构造一组最小场景：会话等待审批时终止 Harness；命令仍在后台执行时断开前端；提示提交后模拟瞬时网络失败；运行中请求取消并记录完成时间。每个场景都要保存恢复前后的会话标识、待处理工作、工具任务状态和用户可见结果。故障注入应限定在专用测试环境，不要对真实用户任务或生产工具执行随意终止。

验收时，先验证身份连续性：恢复后是否接回原有会话和待处理事项，而不是悄悄创建新的任务。再验证动作边界：等待审批的工具是否仍需审批，已经运行的命令是否被重复启动，已完成的工作是否被误报为待执行。最后验证可见性：用户能否判断当前是在恢复、等待、运行还是失败。对于取消路径，可以把发布说明中的“10 秒内收敛”作为该版本所述行为的核对点，但需要明确测量起止事件、重复次数和测试环境；不能只用一次本地计时就把它提升成通用服务等级承诺。

测试记录可以用简单的命令保留，而不依赖某个产品专属接口：

```bash
printf '%s\n' \
  'scenario=approval_wait crash=forced' \
  'scenario=background_command disconnect=forced' \
  'scenario=prompt_submit transient_failure=forced' \
  'scenario=active_run cancel=observed'
```

真正的测试还需要由运行环境采集每个场景的开始、故障注入、恢复和最终状态，并把预期结果写成断言。例如，审批等待应继续保持等待，除非出现有效审批结果；后台命令应能被识别，而不是因为前端刷新就被当作新命令；重试应关联原提交；取消要有明确终态。上面的命令只是生成场景清单，不会自动触发故障，也不能替代断言和运行记录。

## 失败边界：恢复成功不代表所有工作都能续上

“冷恢复”容易让人联想到断点续跑，但工具本身可能已经产生不可逆的外部副作用。比如外部系统已收到写操作，而 Agent 进程在收到响应前崩溃；恢复后如果盲目重放，就可能重复写入。会话恢复机制只能恢复系统能够识别的状态，不能自动替工具提供事务语义。对有副作用的工具，仍需定义调用身份、重复请求处理方式，以及结果不确定时是查询、等待还是人工介入。

同样，后台命令继续运行并不意味着它适合无限期运行；发布说明没有提供资源限制、超时策略或输出清理规则。幂等重试也不等于所有失败都能自动修复：材料只称瞬时失败重试两次，没有说明错误分类细节。若系统把永久错误误判为瞬时错误，静默重试只会延迟暴露问题；若所有失败都展示重新发送入口，也可能诱导用户重复触发有副作用的操作。

最后要区分版本证据等级。Qwen Code v0.28.6 的条目是正式的项目 Release，但它仍然只是发布说明，不足以证明每种故障下的行为或性能。作为对照，OpenAI Codex 的 0.174.0-alpha.7 页面明确标记为 Pre-release；该标记说明它是预发布版本，不能仅凭标签推断其功能成熟度或生产适用性。写升级结论时，应记录具体版本、发布渠道、场景和观察结果，而不是把不同阶段的版本名称当作稳定性证据。

## 工程取舍：状态越可靠，状态治理越重要

可恢复会话通常意味着更多状态需要被命名、关联和清理：用户请求、审批结果、工具任务、输出位置、重试身份，都可能拥有不同的生命周期。把它们统一塞进“对话历史”里看似简单，却会模糊会话恢复与工具重放的区别；拆分太细又会增加一致性和排障成本。合理的边界不是追求最复杂的事件系统，而是确保每个未完成动作都能回答三个问题：它现在由谁负责？重复执行是否安全？如何判断它已经完成或失败？

对使用 Agent 的团队，升级验收应至少覆盖：正式版还是预发布版；受影响的会话类型和界面；等待审批、后台命令、网络重试和取消路径；任务是否重复创建；恢复失败时如何呈现；以及状态和输出如何清理。当前材料能支持的结论是，v0.28.6 将挂起恢复、事件驱动执行、后台命令和幂等提交放进了同一轮更新；它不能替团队回答具体部署的持久化、权限、保留期限或副作用控制问题。

因此，Agent 可靠性的验收单位不该只是“对话恢复了”，而应是“未完成工作以可识别、可继续、不会无声重复的方式到达明确终态”。这条标准比追问实现用了哪种内部机制更实用，也能避免把一次成功续跑误当成端到端可靠性的证明。
