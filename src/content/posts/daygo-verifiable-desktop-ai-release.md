# 把开源桌面 AI 工具变成可验证产品：从 Daygo 的证据链看发布工程

桌面 AI 工具最容易陷入一种叙事：打开下载页，看到“本地优先”“隐私可控”“支持自定义模型”，用户就默认数据不会离开电脑，默认安装包与源代码一致，也默认所谓的 AI 处理边界足够清晰。

但这些词本身不是证据。它们只有被拆成可检查的对象，才具有工程意义：什么数据被采集，何时采集，保存在哪里；哪些内容会送往模型；密钥由谁管理；安装包与源码之间如何建立对应关系；当用户选择云端模型时，隐私承诺是否仍然成立。

Daygo 是一个适合观察这条链路的开源桌面项目。官网将它描述为面向 macOS 与 Windows 的工作记录和复盘工具，按照间隔捕获屏幕画面，再使用用户选择的 AI 整理为时间线、每日回顾和每周总结。公开仓库则提供源代码、构建相关目录、文档、许可证和提交历史。本文的重点不是判断它“好不好用”，而是讨论：一个桌面 AI 产品怎样把宣传语转化为可以复核的工程承诺。

## 一、先把“本地优先”拆成四个不同问题

“本地优先”不是一个二元开关。至少要拆成四层。

第一层是采集位置。Daygo 官网明确写出“每 10 秒捕获一帧，而不是视频”，这说明它的记录模型是离散截图，而不是持续录制的视频流。两者在存储量、检索方式和用户感知上都不同，但“每 10 秒一帧”仍然不等于“没有敏感数据”：一张静态画面同样可能包含密码管理器、私聊、代码仓库或客户资料。

第二层是原始数据保存位置。官网宣称截图和数据留在当前电脑上，并把“本地存储”列为产品特性。这是一个明确的产品承诺，但用户仍应区分“默认保存位置”“缓存位置”“导出位置”和“模型请求中的临时副本”。如果文档没有分别说明，工程上就不应把四者合并为“数据都在本地”。

第三层是模型处理位置。Daygo 支持用户选择 OpenAI、Anthropic 和本地模型。这里存在一个关键分支：选择本地模型时，推理路径可以在设备内完成；选择云端模型时，屏幕内容或经过整理的文本可能进入第三方服务。官网还强调“由你选择模型”，这意味着控制权交给用户，但不意味着所有配置下的网络边界相同。

第四层是凭据位置。官网写明密钥保存在系统 Keychain，并且通过界面只能写入、不能读出。这个设计把“应用需要调用模型”和“应用可以随时读取完整密钥”区分开来，是比单纯把密钥放进配置文件更清晰的边界。不过，Keychain 只能解决凭据存放问题，不能自动解决第三方模型的数据保留、日志记录或账号权限问题。

因此，阅读这类产品时，最有用的问题不是“它是否隐私”，而是：“在本地模型、云端模型、敏感应用和普通应用四种组合下，分别有哪些数据会发生什么变化？”

## 二、敏感应用占位符，是采集系统里的减压阀

Daygo 官网提供了“Blocked apps”能力：敏感应用离开后只留下占位符。这个设计的价值不在于它听起来安全，而在于它改变了数据生命周期。

如果系统只提供全局暂停，用户必须在工作开始前记得操作，并且要在重新工作时恢复；如果系统只提供事后删除，敏感画面已经进入存储或模型处理链路。按应用进行阻断，则把隐私控制点放在采集入口附近，减少了“先收集、后补救”的风险。

但这个边界也有明显失败面。应用识别可能依赖进程名、窗口标题或系统权限；同一应用可能有多个窗口；敏感内容也可能出现在普通应用中，例如浏览器打开后台管理页面。占位符还需要明确几个语义：它是完全不生成图像，还是生成一张无内容的记录卡；该事件是否仍然包含时间、应用名称和分类；后续摘要是否会根据上下文推断被阻断内容。

这些问题不应靠猜测回答。验证时可以先将一个明确包含敏感内容的应用加入阻断列表，再观察三个结果：磁盘中是否出现对应截图，时间线中是否出现内容缩略图，模型输入中是否仍有可识别文本。若产品只公开了功能名称，没有公开这些行为的文档或测试，则应把它标记为“有隐私控制入口”，而不是“已经证明不会采集”。

这个差别很重要。工程上，隐私功能不是一个按钮，而是一组可观察的不变量：被阻断的应用不能产生可还原画面，不能通过摘要恢复敏感文本，也不能因为后台任务重试而绕过阻断规则。

## 三、从官网到仓库：建立发布证据链

桌面软件还有一个经常被忽略的问题：官网展示的产品，是否就是用户下载的产品；用户下载的产品，是否对应公开仓库中的代码。

Daygo 的公开仓库提供了几个有价值的信号：仓库包含 `cmd`、`internal`、`frontend`、`native`、`web`、`docs` 等目录，也包含 Go 模块文件、构建工作流目录和 MIT 许可证。它至少说明项目不是只有一个展示页面，而是存在可供检查的应用源码、文档和自动化构建入口。

不过，目录存在不等于发布链路已经可复现。用户可以先把“看见开源”转换成一组低成本检查：

```bash
git clone https://github.com/Jwz-git/Daygo.git
git -C Daygo log -1 --oneline
git -C Daygo status --short
find Daygo -maxdepth 2 -type f | sort | sed -n '1,120p'
sha256sum Daygo/go.mod Daygo/LICENSE Daygo/README.md
```

这组命令不会证明安装包安全，也不会自动完成构建；它们的作用是固定检查起点。第一步确认仓库来源，第二步记录当前提交，第三步发现工作树是否干净，第四步查看源码、文档和构建入口，最后为关键文本建立本地摘要。若项目提供正式 Release，还应把下载文件的校验值与对应提交、构建工作流和版本说明关联起来，而不是只保存一个“最新下载地址”。

更完整的证据链至少包含四个对象：源码提交、构建配置、发布产物、用户可读的隐私文档。四者任何一个缺失，用户都只能验证局部事实。例如，能读到源代码，不代表下载包由这份代码构建；能下载安装包，不代表能够知道它使用了哪次提交；写了隐私说明，也不代表实际实现覆盖了说明中的全部分支。

## 四、模型选择会重新定义产品边界

Daygo 支持 OpenAI、Anthropic 和本地模型，这使它看起来比固定接入某个云模型的工具更灵活，但灵活性也让验证工作变复杂。

本地模型的主要优势是减少数据离开设备的路径，代价是用户需要承担模型文件、推理速度、内存占用和兼容性问题。云端模型通常更容易获得稳定的推理能力，却会引入网络可用性、服务商数据政策、账号权限和计费等外部依赖。两条路径都不是绝对正确，关键在于应用是否把差异显式呈现给用户。

一个可靠的配置界面至少应让用户知道：当前使用的模型名称和提供方；发送的是原始截图、压缩图还是抽取后的文本；请求失败时是否会重试；离线时是暂停、排队还是降级；切换模型后，历史数据是否会重新处理。尤其是重试机制，它可能把一次用户没有注意到的网络请求扩展成多次请求，也可能导致同一敏感内容进入不同服务。

验证模型边界时，不要只观察最终生成的日报。最终文本已经经过多次处理，无法反推出原始请求。更好的检查方式是选择一张包含唯一测试字符串的截图，分别在本地模型与云端模型配置下观察网络连接、应用日志和生成结果，并记录失败时的行为。测试字符串不应包含真实密码或客户资料，验证目标是请求路径，而不是拿真实敏感数据做实验。

## 五、给桌面 AI 工具的最小验收清单

如果要把类似 Daygo 的产品纳入团队工作流，可以用下面的顺序做验收。

1. **采集验收**：确认采集频率、暂停方式、后台运行状态，以及退出应用后是否仍有任务。
2. **存储验收**：定位原始截图、索引、摘要和缓存的实际位置，确认删除操作是否覆盖全部副本。
3. **阻断验收**：配置一个敏感应用，检查它是否只产生占位符，且摘要不能还原被阻断内容。
4. **模型验收**：分别验证本地模型和云端模型，记录网络请求、失败重试和离线行为。
5. **凭据验收**：确认密钥不出现在普通配置文件、日志和导出数据中，并测试界面是否允许读取完整密钥。
6. **发布验收**：记录下载地址、版本、平台架构、源码提交和校验值，保留安装包来源。
7. **撤销验收**：删除历史数据、移除模型凭据、关闭采集后，重新检查磁盘和网络活动。

这份清单的核心不是增加流程，而是把“隐私”“本地”“开源”这类宽泛词语转换成可观察结果。不能验证的承诺，应当降低可信等级；只在文档中出现、没有实现或测试证据的能力，应标记为待确认。

## 六、原创结论：开源不是终点，证据链才是产品的一部分

Daygo 公开页面和仓库已经提供了相对清晰的起点：离散截图而非视频、本地保存、自选 AI、敏感应用占位符、系统密钥链，以及 macOS 和 Windows 的发布目标。它的工程价值不只是“把 AI 放在桌面上”，而是展示了一个事实：桌面 AI 工具的真正产品面，包含采集器、存储层、模型适配器、凭据管理、发布流水线和用户可理解的隐私控制。

但这些能力必须被分层验证。官网负责提出承诺，仓库负责提供实现线索，构建和发布记录负责连接源码与安装包，用户测试负责确认运行时行为。缺少其中一环，结论就只能停留在“看起来合理”。

对使用者而言，最稳妥的做法不是盲信“本地优先”，也不是因为存在云端模型就全盘否定，而是先画出数据流，再为每条路径定义可验证的不变量。对开发者而言，隐私开关、模型切换、Keychain 凭据和构建产物都不应被当作附加卖点，它们本来就是发布工程的一部分。

当一个开源桌面 AI 工具能够让用户回答“采集了什么、发送了什么、保存在哪里、如何删除、下载包对应哪次代码提交”，它才真正从功能演示走向可验证产品。
