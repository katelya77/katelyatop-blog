## 先把问题说清楚：访问者变了，策略对象也变了

传统网站通常把访问者粗略分成两类：真人浏览器与自动化爬虫。这个分类在搜索引擎、监控程序和恶意扫描器占主导时还算有效，但个人 AI 代理带来了第三种更容易被误判的对象：它不是单纯为了建立索引，也不是必然执行攻击，而是代表某个人去获取信息、浏览页面，甚至比较产品。

Cloudflare 在 2026 年 11 月 4 日的官方 Changelog 中，把原先的“Configure AI bot policies”设置更名为“AI Crawler and Agent access policies”，并增加了对主要 Personal Agents 分别设置动作的能力。这里最值得注意的不是菜单名称，而是策略模型发生了变化：站点不再只能对一类“AI 流量”做整体判断，而是可以把个人代理作为单独的治理对象。

这意味着“允许 AI 访问”不应被理解成一个全站开关。真正需要回答的问题是：哪些代理可以访问，访问行为允许到什么程度，策略是否继承，发生误判时如何定位，以及网站是否有能力证明一次访问确实符合预期。

本文只使用官方变更材料与 Cloudflare 官方文档仓库作为依据。关于 Cloudflare 对 Personal Agents 的具体识别算法、完整动作枚举、套餐限制和日志字段，材料没有给出，以下不作推断。文章中的架构拆解和检查清单，是基于已公开策略描述提出的工程方法，而不是对未公开实现的声称。

## 从总开关到分对象策略：控制面发生了什么变化

官方描述给出了三个关键事实。

第一，Personal Agents 的行为定义是“代表个人获取信息，或响应请求进行浏览”。这使它们与传统内容抓取器存在目标差异：同一个页面，可能被代理即时读取，而不是为了长期建立搜索索引。站点如果一律阻止，可能损失一部分由用户主动发起的内容发现；如果一律放行，又可能把所有自动化访问混成一个信任等级。

第二，新的策略允许对主要 Personal Agents individually 设置 actions。这里的工程含义是策略键至少包含“代理类别或代理身份”这一维度，而不是只有网站、域名或请求来源。即使官方材料没有公布底层匹配字段，也可以据此设计运维流程：变更记录中必须写明目标代理、动作、作用范围和生效时间，而不能只记录“AI 爬虫已允许”。

第三，Personal Agents 默认继承现有的 Agents policy。继承是便利，也是风险来源。它减少了首次配置时的重复操作，却可能让一个面向传统自动化流量的旧策略意外影响个人代理。官方推荐对 Personal Agents 使用 Allow（不阻止），但这是一项产品建议，不等于每个站点都应无条件执行。付费内容、隐私页面、管理入口和高成本接口仍然需要独立的访问边界。

可以把策略决策抽象成一条控制链：

```text
请求进入
  -> 是否被识别为 Personal Agent
  -> 是否存在针对该代理的专门策略
  -> 若不存在，继承 Agents policy
  -> 执行动作
  -> 观察结果并决定是否调整
```

这条链条解释了为什么“我已经允许 AI”不是完整配置。至少要验证识别、匹配、继承和结果四个环节，而不是只看控制台里某个开关的状态。

## 可复现的配置流程：先记录基线，再改变策略

按照官方 Changelog 给出的路径，入口位于 Cloudflare 控制台的 **Security > Settings > AI Crawler and Agent access policies**。为了让变更可复查，可以按下面的顺序执行。

### 1. 记录变更前状态

先把当前的 Agents policy 记录下来，至少包含：站点、当前动作、是否存在例外、变更人和时间。不要直接进入新设置后凭印象修改，因为 Personal Agents 默认会继承既有 Agents policy，基线是判断后续差异的必要条件。

可以用以下表格作为最小变更单：

| 字段 | 示例填写方式 |
| --- | --- |
| 站点 | example.com |
| 原 Agents policy | 阻止 / 挑战 / 允许，以控制台实际显示为准 |
| 目标 Personal Agent | 控制台列出的具体对象 |
| 新动作 | 允许或其他可选动作，以控制台实际提供为准 |
| 作用范围 | 全站或现有策略范围 |
| 回滚动作 | 恢复原策略并记录时间 |
| 验证证据 | 页面访问、日志或业务指标 |

### 2. 明确“允许谁”而不是“允许一切

在新页面中，先确认设置名称已经是 AI Crawler and Agent access policies，再寻找 Personal Agents 的单独控制项。对需要开放的代理逐项设置动作，不要把“主要 Personal Agents”理解为所有可能出现的自动化客户端。官方材料只说明了对 top Personal Agents 的粒度控制，未说明未知代理的处理方式，因此未知对象仍应按站点既有策略验证。

### 3. 将继承关系写进变更说明

如果没有专门配置某个 Personal Agent，它会继承现有 Agents policy。变更单中应明确写出这一点，并列出受继承影响的页面类别。尤其要检查：公开文章、搜索结果、用户资料、付费内容、后台路径是否共用同一站点级策略。若所有内容都共享一个策略，允许个人代理访问公开页面，并不自动意味着应允许访问私有或高成本页面。

### 4. 设置后立即做最小验证

不要用“控制台保存成功”作为验证结论。至少要验证三件事：公开页面是否仍可正常访问；被允许的个人代理是否没有被旧 Agents policy 意外拦截；不在允许范围内的自动化请求是否仍保持原有保护。材料没有提供模拟 Personal Agent 的官方命令，因此不应伪造一个 User-Agent 就宣称完成了等价验证。更稳妥的做法是使用站点已有的真实访问日志、Cloudflare 提供的请求可观测性以及业务侧页面可达性进行关联检查。

## 验证闭环：把“允许”拆成四个可检查结果

### 识别结果

首先确认请求是否被归入 Personal Agent。不要只看访问量变化，因为流量上升或下降无法证明识别正确。需要在 Cloudflare 可见的请求记录中寻找与该策略相关的分类或动作结果；如果当前日志没有足够字段，应把“无法直接证明识别结果”记录为验证限制，而不是用猜测补齐证据。

### 策略结果

其次确认命中的策略是专门策略还是继承策略。两者对后续排障完全不同：专门策略的问题通常是对象选择或动作配置，继承策略的问题则可能来自已有 Agents policy。排障记录要保存站点、时间、请求路径和最终动作，避免只截图一个总开关。

### 内容结果

再次验证内容层面。允许访问不等于页面一定适合被代理读取。检查页面是否依赖登录、短期令牌、客户端脚本或地域条件；这些属于应用本身的可访问性边界。Cloudflare 的策略动作解决的是访问控制，不会替代应用对敏感数据的授权判断。

### 业务结果

最后观察业务影响。个人代理的价值在于帮助用户发现和比较内容，因此不能只用“拦截率下降”衡量成功。至少应关注公开页面可达性、异常请求变化、缓存或源站负载、敏感路径是否出现非预期访问。若材料中没有足够数据，就把结论限制为“策略已保存且请求动作符合预期”，不要扩大成“代理生态获得增长”或“安全风险已经消除”。

## 失败边界：哪些问题不能靠这项设置解决

第一，身份识别不等于用户授权。即使请求被识别为 Personal Agent，也不能证明请求者有权读取站点中的所有内容。个人代理代表用户行动这一描述，说明了使用场景，不是对站点业务权限的替代。

第二，允许不等于低风险。代理可以在合法场景下高频读取公开内容，也可能造成源站压力、内容再分发或业务规则失效。策略放行后仍需保留接口限流、登录授权、敏感路径隔离和异常监控等应用层措施。

第三，继承不等于一致。旧 Agents policy 可能是为另一类自动化访问设计的。继承降低了配置成本，却会把历史决策带入新的代理场景。任何“默认允许”或“默认阻止”的结论，都必须追溯到实际继承链。

第四，单一厂商策略不等于全网策略。Cloudflare 控制的是经过其站点防护链路的请求。站点还可能存在直连源站、其他 CDN、对象存储和第三方 API。若这些入口的规则不同，用户看到的结果就可能不一致。

第五，当前材料不足以支持完整的代理名单或动作矩阵。官方 Changelog 只明确了主要 Personal Agents 的单独动作、默认继承和 Allow 建议，并没有在材料中列出所有代理、动作语义、识别条件或计费差异。工程文档应保留这些未知项，等待官方文档进一步明确，而不是把控制台当前可见内容外推成稳定 API。

## 工程取舍：开放内容发现，但把边界留在应用层

对大多数内容站点，较合理的设计不是在“全部阻止”和“全部允许”之间二选一，而是分层处理：公开内容可以评估是否允许主要 Personal Agents 访问；账户、支付、管理和个性化数据则继续依赖应用授权；对无法确认身份或不符合既有策略的自动化请求保持原保护。

这里有一个重要取舍：越细的策略，治理成本越高。为每个代理建立独立例外，能够减少误伤，却也需要持续维护对象、动作和回滚记录；使用继承策略更简单，但更容易把旧规则带入新场景。站点规模较小时，先保持清晰的默认策略，再对确有业务价值的 Personal Agents 建立例外，通常比一开始建立复杂矩阵更容易审计。

我的结论是：Cloudflare 这次变化的核心，不是“AI 流量应该放行”，而是网站终于可以把代理访问从一个模糊类别，提升为可以单独记录、单独验证、单独回滚的策略对象。真正成熟的配置应满足三个条件：能解释为什么允许某个代理，能证明它没有意外继承错误规则，也能在业务或安全信号恶化时快速恢复原策略。做到这三点，AI 代理访问才从一次控制台操作，变成可治理的生产能力。
