## 先把问题说准确：切分不是简单分片

模型权重切分，最容易被误解成“把一个大文件平均切成几个小文件”。如果只是传输或存储问题，按字节划分确实足够；但推理后端面对的不是一串字节，而是一组带有类型、布局、依赖关系和执行约束的张量。文件能够被打开，只能说明容器层面可读，并不能说明每个后端都能按照自己的能力边界消费它。

llama.cpp b12383 的发布说明给出了一个非常具体的变化：`ggml-backend` 会在一个没有输入的切分中，遇到不兼容权重时开始新的切分。这里有三个值得注意的词。

第一是“后端”。权重是否兼容，不再只是模型格式解析器的问题，而与实际承载计算的 backend 有关。同一份模型，在 CPU、Vulkan、CUDA、ROCm 或其他构建目标上，能够接受的权重类型和布局可能并不相同。第二是“切分”。切分边界不是任意的文件边界，而是运行时需要理解的结构边界。第三是“没有输入”。这意味着某些切分并不是从一个完整的输入张量开始，而可能是由权重装载、后端分配或图初始化过程触发。对这类路径来说，不能把“当前没有用户输入”误认为“没有约束”。

因此，b12383 的改动不应被概括为“修复了大模型加载”。材料只证明了一个更窄、也更有价值的事实：项目针对无输入切分中的不兼容权重，调整了后端开始新切分的行为。工程上真正需要验证的，是这个边界是否让后端选择更可解释、加载失败更早暴露，以及不同构建产物是否保持一致。

## 从发布证据看：这仍然是预发布能力

S8 明确将 b12383 标记为 `Pre-release`。发布页还显示该提交由 GitHub verified signature 标记，并列出了多个平台与后端构建产物，包括 CPU、Vulkan、CUDA、ROCm、OpenVINO 和 SYCL 等类别。它们说明项目提供了较宽的构建覆盖面，但不等于每一个产物都已经在所有模型和切分组合上获得同样的稳定性保证。

这一区分很重要。一个预发布版本可以包含高价值的兼容性修复，也可以提供签名提交和丰富的二进制资产；这些是发布证据，却不是生产可用性的完整证明。S6 中的 Codex `0.171.0-alpha.5` 同样被标记为 `Pre-release`，说明“版本号已经出现”与“能力已经稳定”本来就是两个维度。不能因为下载链接存在，就把行为当成正式契约；也不能因为它是预发布，就完全忽略其中有明确边界的工程改动。

对 b12383，推荐把证据拆成四层：

1. **来源证据**：标签、提交哈希、预发布标记和 verified signature，回答“拿到的东西来自哪里”。
2. **构建证据**：目标平台、后端名称和构建产物，回答“准备运行什么”。
3. **行为证据**：不兼容权重是否触发新的切分边界，回答“运行时做了什么”。
4. **结果证据**：模型是否完成装载、图是否成功执行、输出是否达到可接受标准，回答“最终是否可用”。

前两层不能替代后两层。尤其不能用“Release 页面有 CUDA 资产”推导出“我的 CUDA 环境能够正确装载这份切分权重”。

## 一套可复现的验收流程

### 1. 固定版本与来源

先把版本、提交和下载文件记录成机器可读的清单。不要只保存一个短标签：

```bash
set -eu
version=b12383
mkdir -p evidence/$version
printf 'version=%s\n' "$version" > evidence/$version/release.env

git ls-remote --tags https://github.com/ggml-org/llama.cpp.git "$version" \
  | tee evidence/$version/tag.txt
sha256sum path/to/downloaded-artifact \
  | tee evidence/$version/artifact.sha256
```

如果是从源码构建，还应保存实际提交、编译器版本、目标架构和启用的后端。重点不是把环境写得越长越好，而是让下一次失败能够回答“是否运行了同一个东西”。在预发布版本中，标签和本地文件名尤其不应作为唯一身份标识。

### 2. 把权重清单当成输入契约

为每个切分文件建立清单，至少记录文件名、大小、哈希和生成时间。若格式工具能够列出张量元数据，再记录张量名、数据类型、形状和所在切分；若工具不能提供这些信息，就不要自行推断。

```bash
find model-dir -maxdepth 1 -type f -print0 \
  | sort -z \
  | xargs -0 sha256sum \
  | tee evidence/$version/weights.sha256

find model-dir -maxdepth 1 -type f -printf '%f\t%s bytes\n' \
  | sort \
  | tee evidence/$version/weights.size.tsv
```

这一步的价值在于区分三种失败：文件缺失或损坏，是传输问题；清单完整但后端拒绝某个权重，是兼容性问题；权重装载成功但执行失败，则更可能是运行时图、内存或后端实现问题。没有清单时，所有失败都会被压缩成一句含糊的“模型跑不起来”。

### 3. 用最小场景验证切分边界

不要一开始就使用长上下文、并发请求和复杂采样参数。先准备一个最小输入，并把日志完整保存。验证目标也不要写成“输出看起来不错”，而要拆成可判定的状态：文件是否全部打开、后端是否完成初始化、切分是否完成、执行是否返回、是否出现不兼容权重或内存分配错误。

```bash
mkdir -p evidence/$version/run-001
cat > evidence/$version/run-001/input.txt <<'EOF'
请只输出一个短句，说明这次测试已完成。
EOF

# 将实际推理命令替换为项目当前构建提供的入口，并固定其参数
./your-inference-entrypoint \
  --model-dir model-dir \
  --input evidence/$version/run-001/input.txt \
  > evidence/$version/run-001/stdout.log \
  2> evidence/$version/run-001/stderr.log

wc -c evidence/$version/run-001/stdout.log \
  evidence/$version/run-001/stderr.log
```

这里故意没有给出一个未经材料证明的固定 CLI 参数表。不同构建入口可能不同，验收方法应依赖实际生成的帮助信息和项目文档，而不是把某个版本的命令行接口当成永久 API。命令的骨架可以固定，具体入口和参数必须随构建产物记录。

### 4. 做后端矩阵，而不是只测默认路径

至少把“后端构建”和“权重切分”作为两个独立维度。一个简单矩阵可以包含：同一组权重在 CPU 构建上的装载、同一组权重在目标加速后端上的装载，以及一个已知会触发兼容性边界的切分样本。每一格都记录版本、后端、退出码、首个错误和是否生成有效输出。

```text
version | backend | split-set | load | execute | exit_code | first_error
b12383  | CPU     | A         | pass | pass    | 0          | -
b12383  | Vulkan  | A         | ?    | ?       | ?          | pending
```

不要把不同后端的结果合并成一个“模型支持”字段。CPU 成功只证明 CPU 路径通过；加速后端失败也不能直接说明模型文件损坏。只有当失败能够在多个后端、多个切分组合中稳定复现，才适合进一步归因。

## 哪些结果不能被误读

**能列出文件，不等于能装载权重。** 文件系统和哈希检查只能证明输入完整，不能证明后端接受其中的数据类型或布局。

**能装载权重，不等于能执行计算。** 初始化、图构建和实际执行可能处在不同阶段。特别是“没有输入”的切分路径，不能用一次普通请求覆盖所有初始化行为。

**能生成文本，不等于切分边界正确。** 输出存在只能说明某条路径完成了；它不自动证明所有权重都由预期后端处理，也不证明没有发生隐式回退。应保存初始化日志、后端标识和退出状态，而不是只截取最终文本。

**某个后端失败，不等于修复无效。** b12383 的说明针对的是不兼容权重与切分边界。若失败来自驱动、设备内存、构建依赖或输入文件损坏，就不能归因于这一改动。验收报告必须保留首个错误，而不是只记录最后一行报错。

**预发布通过，不等于可以无条件升级。** 预发布版本适合用来验证特定问题是否改善，但生产升级仍需要固定版本、保留回退版本、保存模型清单，并在目标硬件上执行同一矩阵。尤其当发布页同时提供多个后端资产时，“下载成功”与“目标环境可运行”之间的距离更长。

## 工程取舍：让切分更聪明，也让观测更重要

自动在不兼容权重处开始新切分，优点是把后端能力边界纳入装载过程，减少了“按文件平均切分”造成的隐性错误。它也可能带来新的取舍：切分数量增加后，内存规划、装载顺序、跨设备传输和错误定位都可能变得更复杂。材料没有给出 b12383 的性能收益、额外开销或所有边界条件，因此不能把这次改动宣传成普遍加速，也不能推断它覆盖所有后端组合。

更稳妥的做法，是把“自动切分”当成运行时策略，而不是输入文件的永久属性。输入侧保存原始清单，运行侧记录实际切分结果，发布侧保存版本与后端矩阵。这样即使下一版改变切分策略，也能判断变化来自代码、构建资产还是模型本身。

我的结论是：权重切分的核心问题不是“能否把大文件拆开”，而是“拆开的边界是否与后端可执行边界一致，并且能被验证”。b12383 值得关注的地方，正是它把一个容易被隐藏的兼容性判断前移到了 `ggml-backend` 的切分过程。但对于预发布版本，正确的使用方式不是追逐标签，而是围绕一个窄问题建立证据闭环：固定来源，清点输入，记录后端，观察切分，验证执行，保留失败。只有这样，发布说明中的一句边界修复，才会变成可审计、可回退、可复现的工程结论。
