## 先区分产品事实与架构推断

这批材料里，Parlz 的信息密度高，不是因为它宣称“有 200 多项功能”，而是因为公开页面同时暴露了聊天、身份、在线状态、内容装扮、商业化和客户端入口。社区帖子把它描述为“全平台 app”，并展示了较长的功能页面；官方站点则直接列出私聊、群组、通讯录、在线状态、正在输入、自绘 SVG 表情、头像框、挂件、消息字体、VIP 和站内商店等能力。官方页面还明确写出：付款由第三方 Creem 处理，Parlz 不保存银行卡信息。

因此，本文把证据分成两层。官方站点可直接支持产品当前页面呈现的功能与支付说明；社区帖子只作为发现线索，不能单独证明性能、客户端覆盖范围、后端技术栈或“200+ 功能”的真实性。下文涉及 WebSocket、事件总线、数据库表结构等内容时，都是根据公开交互面反推的工程模型，不把它们写成 Parlz 已公开确认的内部实现。

这一区分很重要。一个聊天页面能显示“在线”，不等于它已经解决了多端一致性；一个支付页跳转到 Creem，也不等于订阅状态已经可靠地回写到用户账户。真正值得拆解的，是如何把这些可见承诺变成一条可验证的状态链。

## 聊天核心不是消息表，而是状态流

最小聊天产品通常先想到一张 messages 表：发送者、接收者、正文和时间。但 Parlz 页面同时出现私聊、群组、通讯录、在线状态和正在输入，这意味着系统至少存在三类不同生命周期的数据。

第一类是持久状态，例如用户、会话成员、消息、已读位置和商店订单。这些数据需要可恢复、可查询，并且应该有明确的幂等键。客户端重试发送时，服务端不能因为网络抖动产生两条相同消息；支付回调重复到达时，也不能重复发放 VIP。

第二类是短期事件，例如“正在输入”和在线心跳。它们不适合像普通消息一样永久累积。在线状态更接近租约：客户端周期性续租，服务端在超时后将其标记为离线。正在输入则是带过期时间的瞬时提示，用户停止输入、切换会话或网络断开后都应该自动失效。把这类事件误写进永久消息流，会让存储、同步和隐私管理变得复杂。

第三类是派生视图，例如通讯录里的未读数、会话排序、在线列表和 VIP 标识。它们可以由持久状态与短期事件计算得到，但客户端仍需要处理乱序、重复和断线重连。一个更稳妥的事件模型可以抽象成：

```text
conversation.message.created
conversation.message.read
presence.updated
typing.started
typing.expired
entitlement.changed
```

事件名只是示例，不代表 Parlz 已公开采用这些名称。工程上的关键是给每个事件定义版本、产生时间、会话 ID、发送者和幂等标识。客户端收到旧事件时不能覆盖新状态；重新连接后也不能只依赖本地内存，而要从服务端补齐持久事件，再重新订阅实时流。

对于小团队，未必需要一开始就部署独立消息队列。更实际的取舍是：持久消息使用关系数据库，实时层使用一个带过期能力的共享存储或托管实时服务，应用层只维护清晰的事件契约。等到连接数、群组规模和离线补偿真正成为瓶颈，再把广播、持久化和搜索拆开。架构的“小”不应等于把所有状态混在一个接口里。

## 从登录到聊天：先验收状态转移

官方页面显示了用户名密码登录、邮箱验证码注册、忘记密码、二维码确认登录等入口。入口多并不等于体验一定好，反而意味着账户状态机更容易出现分叉。至少应区分“未注册”“待验证”“已注册未登录”“已登录”“密码重置中”和“二维码待确认”，而不是用一个布尔字段覆盖所有情况。

二维码登录尤其需要短生命周期和单次消费。二维码被展示后，服务端应生成随机挑战值；手机端确认时绑定当前已登录会话、挑战值和过期时间；网页端轮询或保持连接，只接受一次成功结果。任何一个条件不满足，都应该回到明确的失败状态，而不是静默刷新登录页。二维码图片本身不是凭证，真正的凭证是服务端可撤销、不可重复使用的挑战记录。

可以用浏览器和命令行做一套不依赖内部 API 的黑盒验收。以下命令不会证明系统内部实现，但能帮助检查页面是否稳定暴露关键入口：

```bash
curl -I https://chat.parlz.com/
curl -L --max-time 15 -sS https://chat.parlz.com/ | head -c 1000
```

如果页面依赖 JavaScript，HTML 中没有完整应用内容并不自动代表故障；此时应在浏览器开发者工具中检查脚本是否成功加载、登录失败是否有明确提示、刷新后会话是否保持，以及断网重连后当前会话是否重复创建。验收重点不是“页面能打开”，而是每个状态转移都有可观察结果：注册验证码过期、重复提交、密码错误、二维码失效、主动退出和异地登录都应能被区分。

聊天消息还要单独验证四件事：发送后刷新是否仍存在，重复点击是否只生成一条，接收方离线后重新进入是否能补齐，消息排序是否以服务端序列为准。若产品支持群组，则还要测试成员被移除后是否还能发送、历史消息是否继续可见，以及新成员能看到哪一段历史。这些都属于产品契约，不应留给前端自行猜测。

## “不保存银行卡”不等于支付链路没有风险

Parlz 官方页面声明付款由 Creem 处理，站点不保存银行卡信息。这是一个有价值的边界声明，但它只覆盖卡号存储这一层，不能自动推出订单、订阅和权益都可靠。

一个可治理的支付链至少包含四个对象：本地订单、第三方支付会话、回调事件和用户权益。用户点击购买时，本地先创建不可重复的订单号，再生成第三方结算会话；支付成功后，服务端通过经过签名校验的回调或主动查询确认结果；确认成功才写入权益表。前端跳转成功页只能作为展示，不应直接赋予 VIP，因为用户可能关闭页面、重复访问成功 URL，或者支付状态尚未最终确定。

回调处理必须幂等。可以把第三方事件 ID 设为唯一键，并记录原始状态、处理时间和处理结果。状态从 pending 到 paid 后，不应因为重复回调倒退；退款、拒付和订阅到期则应通过明确的反向事件撤销或冻结权益。若产品提供装扮、头像框、挂件和消息字体等数字商品，库存不一定是问题，但重复发放、越权使用和退款后的继续使用仍然是问题。

隐私边界也应写得比“我们不保存银行卡”更具体：保存哪些账户字段，聊天内容保存多久，管理员能否读取，日志是否包含邮箱或消息正文，第三方支付方会接触哪些订单信息，删除账户后哪些数据仍因合规或备份要求保留。官方页面还提供服务条款、支付与退款条款、隐私政策入口，这些文档应与实际数据流保持一致，而不能只作为页脚链接。

## 装扮功能的取舍：表达力与安全面同时增长

自绘 SVG 表情、头像框、挂件和消息字体，让聊天产品的差异化从“能发消息”转向“能表达身份”。但可定制内容越自由，渲染和安全边界越重要。

SVG 不应被当作普通图片直接注入页面。服务端应限制尺寸、文件大小、元素类型和引用资源，剥离脚本、外部链接和危险事件属性；客户端则应在隔离上下文中渲染，避免用户内容获得页面权限。消息字体也不应允许任意远程字体地址，否则会引入隐私泄露、加载阻塞和供应链风险。更简单的方案是只提供服务端审核过的字体集合，用商品 ID 引用资源，而不是让消息携带任意 CSS。

装扮商品还涉及版本兼容。用户购买的是“商品权益”，客户端展示的是“资源版本”。如果资源下架、客户端旧版本不认识新字段，服务端应返回可降级的默认样式，而不是让整条消息渲染失败。这里的工程原则是：内容可以丰富，协议必须保守；未知装扮字段应被忽略，核心消息仍然可读。

## 失败边界清单：小产品也要有可观测性

可以把 Parlz 这类产品的发布验收压缩成一张清单：

1. **身份**：验证码过期、重复使用、密码重置和二维码确认是否都有明确状态；退出后旧令牌是否立即失效。
2. **实时性**：断网、切后台、刷新和多标签页后，在线状态、正在输入和消息是否会自动恢复或过期；重复事件是否不会制造重复消息。
3. **一致性**：消息发送成功但客户端超时重试时是否幂等；群成员变化与消息权限是否按服务端结果执行。
4. **支付**：成功页、回调、主动查询和退款是否区分；重复回调是否只产生一次权益变更；支付失败是否不会留下可用 VIP。
5. **内容安全**：SVG、头像、字体和昵称是否经过大小、类型、脚本及外链限制；恶意内容是否只能影响自己的渲染区域。
6. **隐私**：日志、错误追踪和客服工具是否会采集消息正文、邮箱或支付标识；账户删除和数据导出是否覆盖主要对象。
7. **运维**：实时连接数、消息投递失败、回调积压、验证码发送量和异常登录是否有指标与告警。

验证这些项目时，不应只测“正常流程”。至少要人为制造一次超时、重复提交、断线重连和回调重复，并记录服务端日志、客户端提示与最终数据状态是否一致。没有可观察的失败，所谓稳定往往只是没有被测到。

## 原创结论：小而美的核心是边界少而清晰

Parlz 公开呈现出的价值，不在于功能数量本身，而在于它把多个高耦合问题放在了一个产品里：实时消息要求低延迟，账户系统要求可撤销，装扮系统要求内容隔离，支付系统要求第三方信任边界，隐私政策又要求把数据流说清楚。任何一项做成“页面看起来能用”，都会在其他环节留下隐性债务。

对类似产品而言，最值得复用的不是某个框架或某家支付服务，而是三条原则：先把持久状态、短期事件和派生视图分开；再把支付成功、权益生效和页面跳转分开；最后把“公开承诺”与“内部推断”分开。这样，即使产品仍然很小，也能用黑盒验收、事件幂等和清晰的失败状态建立可信度。

真正的小而美，不是功能少，而是每增加一个功能，都能说明它依赖什么状态、如何验证成功、失败后如何恢复，以及用户的数据边界在哪里。
