# 自建 AI 访问链路：从 VPS 代理到 API 端点路由的工程实践

在 AI 工具日益普及的当下，依赖第三方中转站已成为许多开发者的常态。然而，社区反馈中关于“注水”、“垃圾上游”以及服务不稳定的抱怨屡见不鲜 [S11]。为了摆脱对不可控中转站的依赖，并追求更纯净的 IP 环境与可控的成本模型，基于 VPS 的自建访问链路逐渐成为一种高性价比的工程实践。本文将基于社区提供的实践指南与平台架构 [S10][S11]，拆解这一链路的设计原理、配置步骤与工程取舍。

## 一、 基础设施选型：Incus NAT VPS 与纯净家宽

自建链路的第一步是构建一个稳定且具备独立 IP 的网络出口。传统的中转站往往共享 IP 池，极易触发风控或遭遇运营商降速。而自建 VPS 则能提供“纯净家宽”般的体验。

### 1.1 平台架构与节点选择

根据纳泰云（NateCloud）的官方介绍，该平台基于 Incus 容器技术提供低价 NAT VPS 服务 [S10]。Incus 作为轻量级容器虚拟化技术，相比传统的 KVM 或 OpenVZ，提供了更好的资源隔离性与性能表现。NAT VPS 虽然共享公网 IP，但通过合理的路由配置，可以模拟独立的网络环境。

在社区实践中，香港节点因其低延迟与相对宽松的网络环境，成为了自建代理的首选 [S11]。虽然材料 [S9] 提到了“免费小鸡”的福利，但在追求稳定性的自建方案中，付费的高性能节点（如酷鸭 HK 机器）是更优的工程选择。

### 1.2 网络拓扑设计

自建链路的核心在于将 VPS 打造成一个“本地网关”。其基本拓扑如下：

*   **本地设备**：运行 ChatGPT 客户端或 API 调用脚本。
*   **VPS (HK)**：作为中转节点，运行代理服务。
*   **上游服务**：OpenAI Plus 订阅或 AI 中转站。

通过这种方式，本地设备不再直接暴露在公网，而是通过 VPS 的代理隧道与上游服务通信，从而获得纯净的出口 IP。

## 二、 协议转换：3xui + AIMILIVPN 隧道部署

拥有了 VPS 只是第一步，如何将 VPS 的网络能力转化为 AI 工具可用的代理服务是关键。社区实践 [S11] 提出了一套基于 3xui 和 AIMILIVPN 的组合方案。

### 2.1 3xui 面板配置

3xui 是一个功能强大的多协议代理管理面板。在 VPS 上安装 3xui 后，核心任务是创建入站协议。根据实践指南，建议配置 **SOCKS5 协议** 并设置密码认证 [S11]。SOCKS5 协议相比 HTTP 代理，对 TCP/UDP 流量的支持更完善，且在 AI 工具的流式传输场景下表现更稳定。

### 2.2 AIMILIVPN 与家宽模拟

AIMILIVPN 是一个用于模拟纯净家宽的工具。在 3xui 面板配置完成后，通过 AIMILIVPN 对 VPS 的网络环境进行优化，可以进一步降低被识别为代理节点的风险，从而提升与 OpenAI 服务器的握手成功率。

**配置检查清单**：
1.  确认 VPS 系统为 Debian 11/12 或 Ubuntu 22.04 LTS [S11]。
2.  安装并启动 3xui 面板。
3.  创建 SOCKS5 入站，设置强密码。
4.  部署 AIMILIVPN，确保路由规则生效。

## 三、 协议转换层：sub2api 的 API 端点映射

VPS 上的代理服务（SOCKS5）无法直接被 ChatGPT 客户端识别。此时，sub2api 工具起到了关键的“协议转换”作用。

### 3.1 sub2api 的工作原理

sub2api 是一个将订阅链接转换为 API 端点的工具。它监听本地端口，接收 HTTP 请求，并将其转发至上游订阅地址。对于自建方案，其作用是将本地的代理服务封装成 OpenAI 兼容的 API 格式。

### 3.2 端点配置与路由修改

在配置 sub2api 时，最关键的步骤是 API 端点的修改。社区实践指出，在 CCS（或其他客户端）中手动修改 API 端点并增加 `/v1` 后缀 [S11]。例如，将端点设置为 `https://www.nodeloc.com/v1`。这一步确保了请求符合 OpenAI API 的标准路径规范，使得客户端能够正确识别并转发请求。

**验证方式**：
在配置完成后，可以通过 curl 命令测试本地 API 端点是否响应：
```bash
curl http://localhost:8080/v1/models -H "Authorization: Bearer YOUR_API_KEY"
```
若返回 JSON 格式的模型列表，说明端点映射成功。

## 四、 混合路由策略与工程取舍

自建链路并非完全抛弃中转站，而是构建一个“混合使用”的优先级调度系统。根据社区经验，这种策略在成本与稳定性之间取得了最佳平衡 [S11]。

### 4.1 优先级调度机制

在配置中，通常将自建的 Plus 账号设为**优先级最高**，而将中转站设为备用。当本地 Plus 的额度（如 5 小时或周额度）耗尽后，系统自动切换至中转站。这种设计利用了自建链路的稳定性优势，同时保留了中转站的低成本优势。

### 4.2 成本模型分析

从工程成本角度看，自建方案的固定开支主要由两部分组成：
1.  **Plus 订阅**：约 $20/月 [S11]。
2.  **VPS 服务器**：如酷鸭 HK 机器，年费约 $27（199元）[S11]。

相比之下，长期依赖中转站可能面临单价波动、额度不稳定以及潜在的封号风险。自建方案虽然初期投入较高，但通过混合使用，实际上降低了单次调用的边际成本，并消除了服务中断的风险。

### 4.3 失败边界与维护成本

尽管自建方案优势明显，但其维护成本不容忽视。VPS 需要定期维护，包括系统更新、代理服务监控以及 AIMILIVPN 的配置调整。此外，如果 VPS 所在的机房出现网络波动，整个链路将失效。因此，该方案更适合对稳定性有较高要求、具备一定运维能力的开发者。

## 五、 结论

从“注水”的中转站转向自建链路，本质上是将 AI 访问的控制权从第三方平台收回到本地基础设施。通过 Incus NAT VPS 提供纯净出口，利用 3xui 与 AIMILIVPN 构建隧道，再借助 sub2api 完成协议转换，开发者可以构建出一套既稳定又经济的 AI 访问方案。

这一过程不仅是技术配置的堆叠，更是对成本模型与风险边界的重新评估。对于追求长期稳定输出的开发者而言，自建链路虽然门槛略高，但其带来的“纯净家宽”与“完全掌控权”是任何免费中转站都无法提供的核心价值。
