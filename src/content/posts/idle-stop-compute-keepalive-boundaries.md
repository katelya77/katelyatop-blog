## 先把“免费主机”还原成一个状态机

在 NodeLoc 的一则分享中，instabox.sh 被描述为提供 4 核 8 GB 主机，但实例在空闲 30 分钟后会自动停止；帖子进一步建议使用 Cloudflare 的定时任务，并配置 `INSTABOX_API_KEY` 与 `INSTABOX_MACHINE_ID`。这是一条有用的真实问题样本，但它的证据等级需要先说清楚：关于“4 核 8 GB”“30 分钟空闲停止”以及保活方式的具体描述，来自社区帖子 S5；官方入口 S6 目前只显示需要 JavaScript，材料中没有公开展示完整 API 文档、计费规则、实例状态枚举或 SLA。因此，本文把这些内容当作待验证的行为，不把它们写成厂商正式承诺。

从工程角度看，所谓“主机在线”至少包含四个不同状态：实例存在、实例处于运行态、网络端口可达、业务进程能够正常响应。空闲回收通常只改变其中的运行态，不一定删除磁盘，也不一定撤销实例标识；但如果平台的控制面在停止后释放 IP、重建磁盘或要求重新启动，那么保活策略就不能只判断一个布尔值。

可以先用下面的状态模型描述问题：

```text
PROVISIONED -> RUNNING -> IDLE
                     |       |
                     |       v
                     +---- STOPPED

STOPPED -> STARTING -> RUNNING
```

这里最关键的不是“每隔几分钟调用一次接口”，而是确认平台到底允许哪些迁移：停止后的实例是否能通过同一个机器 ID 启动，启动是否异步，重复启动是否幂等，失败后是否存在 `ERROR` 或 `UNKNOWN` 状态。材料没有给出这些官方契约，所以在自动化前必须先观察真实返回值，而不是凭字段名称猜测。

## 保活的本质是控制面调度，不是业务流量

很多人会把一个 HTTP 请求打到自己的服务端口，认为这样就能避免空闲。这种方法最多证明业务进程收到了请求，却不能证明平台把请求计入“活跃使用”。如果回收判定发生在宿主机、虚拟机监控器或平台控制面，应用层访问可能完全不起作用。反过来，调用启动或续期接口虽然更接近根因，却需要凭据、机器标识和明确的权限边界。

因此，保活系统应拆成两个相互独立的探针：

1. **控制面探针**：询问实例当前状态，必要时发起启动动作；
2. **数据面探针**：在实例声称运行后，验证 SSH、HTTP 或实际业务端口是否可用。

一个安全的执行顺序应当是“查状态，再决定动作”，而不是固定频率地无条件启动：

```text
读取实例状态
  ├─ RUNNING：记录状态，执行数据面检查
  ├─ STOPPED：确认是否允许启动，再提交启动请求
  ├─ STARTING：等待并轮询，禁止重复提交
  └─ UNKNOWN/ERROR：告警并停止自动重试
```

这套流程的价值在于减少两类隐性风险。第一类是重复启动：如果启动接口是非幂等的，多个定时任务可能制造重复操作、竞态或额外资源。第二类是错误掩盖：把所有非 200 响应都当成“稍后再试”，会让权限失效、配额耗尽和实例被删除看起来像普通网络抖动。

材料只证明社区有人建议配置 `INSTABOX_API_KEY` 和 `INSTABOX_MACHINE_ID`，并没有证明变量的生命周期、权限范围或接口路径。因此，真实接入时应该把 API Key 放在 Worker Secret 或等价的机密存储中，不能写入前端脚本、公开仓库、日志和 URL 查询参数。`MACHINE_ID` 即使不一定属于秘密，也不应与密钥一起硬编码在可公开访问的页面中。

## 一份不依赖猜测的验证流程

在正式设置定时任务前，先做一次“契约发现”。目标不是马上让实例永久运行，而是回答几个可以被观测的问题：

- 官方页面或浏览器网络请求是否暴露状态查询接口；
- 状态响应是否包含稳定的实例标识、当前状态和错误信息；
- 启动动作是否返回任务 ID，还是直接等待到运行完成；
- 同一个请求重复发送时，平台是否返回相同结果；
- 停止、启动和状态查询分别需要什么权限；
- 空闲计时是从实例启动开始，还是从最后一次有效使用开始。

如果接口是标准 HTTPS JSON，可以先用不带真实密钥的方式检查公开页面和文档线索：

```bash
curl -I https://instabox.sh/
curl -sS https://instabox.sh/ | head -c 2000
```

这两条命令只能验证入口是否可访问，不能推导 API 契约。拿到官方文档或浏览器开发者工具中明确出现的请求后，再用环境变量测试，避免把秘密放进 shell 历史：

```bash
export INSTABOX_API_KEY='只在当前会话使用的临时凭据'
export INSTABOX_MACHINE_ID='待验证的实例标识'

curl --fail-with-body --silent --show-error \
  -H "Authorization: Bearer $INSTABOX_API_KEY" \
  "https://example.invalid/api/machines/$INSTABOX_MACHINE_ID"
```

上面的域名和路径只是命令形状示例，不是材料确认的 instabox API 地址。不能因为社区帖子提到变量名，就推断认证头、路径或响应格式。验证时应保存响应的字段结构、HTTP 状态码、请求时间和平台返回的错误码，但要对日志中的令牌、Cookie、完整授权头做脱敏。

当控制面契约确认后，才适合把逻辑放进定时任务。Worker 的伪代码应当保持保守：

```text
scheduled:
  state = get_machine_state()
  if state == RUNNING:
      emit_control_result("running")
      return
  if state == STARTING:
      emit_control_result("already-starting")
      return
  if state == STOPPED:
      result = start_machine()
      record_request_id(result)
      return
  raise_alert("unexpected machine state")
```

不要把 `start_machine()` 的失败改写成成功响应，也不要在异常时无限重试。定时器只能负责发起有限次数的控制动作；它不能替代告警、人工确认和供应商支持。

## 如何证明“保活有效”而不是“任务运行过”

验证保活至少需要三条时间线：调度时间线、控制面时间线和数据面时间线。仅看到 Cron 或 Worker 执行成功，只能说明调度器运行过；仅看到启动接口返回成功，也不能说明实例已经可以接收业务请求。

建议记录以下字段：

| 时间线 | 最小记录 | 用途 |
|---|---|---|
| 调度 | 触发时间、执行耗时、任务结果 | 判断定时器是否漏跑或重叠 |
| 控制面 | 查询状态、动作类型、HTTP 状态、请求 ID | 判断平台是否接受操作 |
| 数据面 | 端口探测、业务健康检查、响应延迟 | 判断实例是否真的可用 |
| 生命周期 | 最近启动、最近停止、最后一次有效请求 | 判断空闲回收规则 |

验证窗口不能只覆盖一次任务。至少要覆盖“启动完成”“接近空闲阈值”“超过空闲阈值”“发生网络失败”和“重复触发”几个场景。由于材料只提到约 30 分钟的社区描述，不能把 30 分钟当成精确计时器；实际测试应在阈值前后设置多个观察点，并记录平台显示时间与本地 UTC 时间。

数据面检查也应尽量贴近真实工作负载。例如，HTTP 200 可能只是反向代理的静态响应，不能证明应用、数据库和磁盘都健康。可以把检查拆成轻量级的 `/healthz`、关键依赖检查和一次只读业务请求，但不要通过高频请求制造虚假流量，更不要为了阻止回收而持续运行无意义任务。那会把“节省资源的自动停止”变成资源浪费，也可能违反平台使用政策。

## 失败边界与工程取舍

第一种失败是定时器本身失效。Cloudflare Worker、外部 Cron 或本地计划任务都有可能遇到暂停、配额、网络错误或时区配置问题。解决办法不是把频率调到极高，而是设置任务重叠检测、最大执行时长和告警渠道，并为短暂失败保留少量带退避的重试。

第二种失败是凭据失效。API Key 过期、权限被收回或账号状态变化时，自动化应明确报告认证失败，而不是继续伪装成“实例空闲”。密钥轮换也应有双凭据过渡期，至少要能在不修改业务代码的情况下替换 Secret。

第三种失败是启动动作成功但数据面不可用。可能的原因包括启动异步、网络地址变化、服务进程未拉起或健康检查依赖尚未恢复。此时要区分“控制面已接受”和“业务已就绪”，使用请求 ID 或状态轮询把两者串起来。

第四种失败是平台策略变化。官方入口 S6 的当前页面内容不足以证明长期稳定的 API 或服务承诺；如果平台调整认证方式、空闲规则或前端流程，社区帖子中的做法可能立即失效。因此，保活脚本应把接口版本、响应字段和最后成功时间纳入监控，并在连续失败后停止动作，避免错误请求扩大影响。

第五种失败是把临时资源误当成生产资源。自动停止、共享基础设施、未知 SLA 和可能变化的网络地址，都意味着它更适合短任务、实验环境、构建缓存或可丢失服务，而不适合唯一数据库、长期公网入口和需要持续连接的业务。真正需要稳定在线时，购买明确的实例服务往往比维护一套脆弱保活链更便宜，因为后者还要承担监控、凭据治理、数据备份和故障恢复成本。

## 原创结论：先验证“可恢复”，再讨论“可保活”

这类临时算力最值得验证的指标，不是“能否让它一直运行”，而是“停止后能否可预测地恢复”。如果实例停止后磁盘仍在、标识稳定、启动接口有明确幂等语义、网络地址变化可发现、业务可以自动重新连接，那么自动停止就是一种可治理的成本策略。相反，如果只能靠不断制造请求维持在线，却不知道停止是否丢数据、启动是否收费、地址是否变化，那么保活只是把未知风险推迟。

因此，选择这类服务时可以使用一个简单的门槛清单：

- 能否从官方页面或正式接口确认生命周期语义；
- 是否存在可撤销、最小权限的控制面凭据；
- 停止和启动是否可观察、可重试、可回滚；
- 数据是否有独立备份，实例丢失后能否重建；
- 是否能用真实业务探针证明恢复完成；
- 失败时是否有明确告警，而不是静默继续运行；
- 业务是否真的需要持续在线，而不是只需要按需计算。

基于现有材料，instabox 的空闲停止和社区保活方案可以作为一个很好的问题入口，但还不能据此证明完整的官方 API、性能、费用或可靠性。工程上最稳妥的做法，是把社区经验当作待验证假设，把官方入口当作契约发现起点，先建立状态、凭据和恢复能力的证据链，再决定是否值得自动化。
