## 先把变化说清楚：评估位置发生了迁移

Feature Flag 最容易被误解成一个简单的键值查询：代码传入 flag 名称，系统返回 true 或 false。但真正影响开发体验的不是返回值，而是“这次评估由谁完成”。如果开发服务器每次都访问远程应用，那么本地调试依赖网络、远程权限和线上配置；一次开关实验还可能误触生产状态。Cloudflare 在 2026 年 11 月 2 日发布的 Flagship 更新，改变了这一边界：Flagship bindings 在本地开发时可以针对本地 flag store 进行评估，而不是调用远程应用。

官方更新明确覆盖四类本地开发入口：`wrangler dev`、Cloudflare Vite 插件、Vitest 集成和 `cf dev`。这意味着本地 store 不是某个单独调试命令的旁路，而是绑定运行时的一种开发模式。它的价值也不只是“断网时还能用”：本地评估把开关试验从共享远程状态中隔离出来，开发者可以在不影响生产的情况下测试 flag 变化。

这里需要先区分证据等级。本文使用的是 Cloudflare 官方 Changelog 和官方文档仓库信息，属于一手资料；讨论限于该更新明确说明的本地评估、版本要求、命令入口和 `remote: true` 行为，不把社区体验或尚未公布的能力推断成产品承诺。

## 本地 flag store 不是远程环境的复制品

本地 store 的第一个关键语义是：它初始为空。官方说明指出，空 store 中的评估会返回代码传入的默认值。这一设计非常重要，因为它把“没有本地配置”和“flag 明确关闭”区分开了：前者由调用点的默认值决定，后者需要通过本地 flag 管理命令或 Local Explorer 写入。

因此，下面两种结果不能混为一谈：

```text
本地 store 没有 checkout-redesign
→ 返回代码指定的 default value

本地 store 已存在 checkout-redesign，且被设置为 false
→ 返回本地 store 中的 false
```

这也是本地模式最容易制造假象的地方。页面正常渲染，不代表 flag 已经从远程应用同步；测试通过，也不代表测试覆盖了远程环境中的开关组合。开发者如果没有先确认本地 store 的状态，很可能只是验证了业务代码的默认分支。

从架构角度看，本地 flag store 更接近开发期的配置层，而不是生产配置数据库。绑定调用仍然存在，但评估请求的目标由本地开发模式决定。远程应用、生产 flag、权限体系和发布流程并不会因为本地 store 出现而自动消失。它解决的是开发时的隔离与可重复性，不是跨环境配置治理。

## 三条操作路径：命令行、Local Explorer 与 cf CLI

官方更新给出了三种管理本地 flag 的方式，分别适合自动化、交互式调试和 Cloudflare CLI 用户。

### 1. Wrangler 命令行

Wrangler 的 Flagship flags 命令支持 `--local`。创建、更新和评估都应明确带上本地标记，例如：

```bash
npx wrangler flagship flags create --local
npx wrangler flagship flags update --local
npx wrangler flagship flags evaluate --local
```

这些命令的重点不是具体参数，而是目标环境。命令中没有 `--local` 时，不能仅凭“我现在运行在开发机上”推断它一定操作本地 store。验证脚本应把目标环境写进命令本身，避免开发者切换上下文后误操作远程应用。

如果需要把远程应用中的全部 flag 复制到本地，官方提供了：

```bash
npx wrangler flagship flags pull <APP_ID>
```

“复制”并不等于“持续同步”。一次 pull 之后，本地 store 与远程状态可能再次分叉；本地修改也不应被当作远程发布。工程上更稳妥的做法，是把 pull 作为明确的初始化或复现步骤，而不是把它隐藏在每次启动脚本里。否则本地手工构造的测试状态可能在启动时被覆盖，测试结果也就失去了可重复性。

### 2. Local Explorer

Local Explorer 适合观察开发服务器运行期间的开关变化。官方说明支持在其中创建、编辑、切换和评估 flags。它的优势是可视化：开发者不必先写命令，就能快速构造某个状态并观察页面行为。

但交互式工具也有记录不足的问题。一个通过点击产生的状态，如果没有同步记录 flag 名称、初始值和变更步骤，其他人就很难复现。因此，Local Explorer 适合探索和演示；进入自动化测试或缺陷复现阶段后，最好把关键状态转换成命令或测试夹具。

### 3. cf CLI

使用 Cloudflare CLI 的项目可以在 `cf flagship` 命令上添加 `--local`。它与 Wrangler 路径体现的是同一个原则：本地目标必须显式表达，而不是依赖当前 shell、当前账号或开发者记忆。

## 版本门槛决定“本地”是否真的存在

这项能力不是任意旧版本 Wrangler 或插件都具备。官方给出的本地 flag store 要求是 Wrangler v4.135.0 或更高版本，或者 `@cloudflare/vite-plugin` v1.56.0 或更高版本。

如果使用 Local Explorer，还需要更高的版本门槛：Wrangler v4.148.0 或更高版本，或者 `@cloudflare/vite-plugin` v1.63.0 或更高版本。两个门槛不能合并成一个模糊的“升级到最新版”：基础本地 store 和 Local Explorer 的支持范围不同。

可以把检查拆成两层：

```text
第一层：当前项目是否满足本地 flag store 的最低版本？
第二层：如果要用 Local Explorer，是否满足 Explorer 的更高版本要求？
```

版本检查应放在环境验收清单中，而不是等到运行时看到行为异常再排查。特别是团队同时使用 Wrangler、Vite 插件和 Vitest 时，不能只检查其中一个包。实际采用哪条入口，就检查哪条入口对应的版本；如果工具链由锁文件管理，还应确认 CI 安装到的版本与开发机一致。

## 远程评估仍然存在：`remote: true` 是显式回退

本地模式并不意味着远程评估被删除。官方提供 `remote: true`，让绑定继续针对远程应用进行评估。这是一个重要的工程取舍：本地 store 带来隔离、离线能力和可重复修改；远程评估保留了接近真实环境的配置读取路径。

两者分别适合不同目标：

| 目标 | 更适合的评估方式 | 主要风险 |
| --- | --- | --- |
| 验证默认分支和本地开关组合 | 本地 flag store | 可能与远程配置不一致 |
| 调试断网或避免影响共享环境 | 本地 flag store | 空 store 会回到默认值 |
| 检查远程应用中的真实 flag 状态 | `remote: true` | 依赖网络、权限和远程状态 |
| 复现一次已知远程配置 | 先 pull 到本地再评估 | pull 后仍可能发生状态漂移 |

这里没有绝对更好的模式。把所有本地开发都强制改成本地，可能掩盖远程权限、配置同步或真实数据差异；把所有开发都保留为远程，又会让普通页面调试依赖外部服务。更可靠的做法是按测试目的选择，并在日志、脚本或文档中显式标记评估来源。

## 一套可复现的验收清单

### 第一步：确认入口与版本

先明确项目使用的是 Wrangler、Cloudflare Vite 插件、Vitest 集成还是 `cf dev`。然后依据入口检查最低版本；需要 Local Explorer 时，额外检查 Explorer 对应的更高门槛。不要把“命令可以启动”当作能力已启用，因为旧版本也可能具备部分开发流程，却不支持本地 store。

### 第二步：验证空状态

选择一个不会影响真实业务的 flag 名称，保持本地 store 为空，调用代码中的评估逻辑，并记录默认值。预期应是返回调用点传入的默认值。这个步骤确认的是空 store 语义，而不是某个具体业务分支。

### 第三步：验证本地写入

使用带 `--local` 的 create 或 update 命令写入 flag，再使用带 `--local` 的 evaluate 命令检查。随后刷新或重新运行开发入口，确认业务代码观察到的值发生变化。写入、评估和应用运行三者都要指向同一环境，否则很容易出现“命令显示成功、页面没有变化”的错觉。

### 第四步：验证远程隔离

在本地修改一个与远程应用不同的值，然后确认本地评估得到本地值；再用 `remote: true` 的绑定进行对照。对照的目的不是证明某一边永远正确，而是确认项目确实能够区分两个状态源。若两边始终返回相同结果，应进一步检查是否真的写入了本地 store，或者测试值恰好与远程值一致。

### 第五步：验证复制边界

运行 `npx wrangler flagship flags pull <APP_ID>` 后，记录本地 flag 数量或关键名称，再修改其中一个值。下一次重复 pull 时，应明确预期是覆盖、更新还是重新初始化，并把该行为纳入团队流程。官方资料确认了 pull 入口，但没有在材料中给出所有冲突处理细节，因此不能把它描述成双向同步或无冲突合并。

## 失败边界：哪些结论不能从本地成功推出

第一，本地页面成功加载，不能证明生产 flag 已配置。空 store 会返回默认值，默认分支本来就可能让页面正常运行。

第二，本地 flag 切换成功，不能证明 CI、预览环境和生产环境使用同一份状态。不同入口、不同版本和不同绑定配置，都可能改变评估目标。

第三，pull 成功，不能证明之后会自动保持同步。它是官方提供的复制命令，但材料没有支持持续同步、冲突解决或发布回推的结论。

第四，启用 `remote: true`，不能证明远程评估一定稳定。远程路径仍然受网络、权限和远程应用状态影响；它只是显式选择远程目标，不是可用性保证。

第五，满足版本门槛，不能证明项目已经正确接入。版本解决的是能力存在性，仍需验证绑定配置、flag 名称、默认值和实际评估路径。

## 原创结论：把 flag 来源纳入测试结果

Feature Flag 的测试结果至少应包含两个维度：业务输出是什么，以及这个输出来自哪个状态源。只记录“页面显示新版”是不完整的；更可审计的记录应说明是空本地 store 的默认值、本地手工设置、从远程 pull 的快照，还是 `remote: true` 的远程评估。

Cloudflare 这次更新的真正价值，不是增加一个更方便的开关面板，而是把状态源选择暴露为开发架构的一部分。团队可以用本地 store 构造稳定、隔离、可离线复现的测试状态，再用远程评估做一次独立的环境对照。两条路径并行存在，才有机会同时发现业务默认值错误、本地配置遗漏和远程环境偏差。

最终的验收标准不应是“本地 flag 能不能切换”，而应是：项目能否明确回答当前评估来自哪里、空状态会返回什么、所用工具是否满足对应版本门槛、远程与本地如何对照，以及一次配置复制之后如何保持可复现。做到这些，本地开发能力才真正从便利功能变成了可靠的工程边界。
