升级 AI 工具时，最容易被忽略的不是版本号，而是证据边界：一个发布说明可能同时包含诊断能力、身份配置、传输兼容性和底层性能优化，但这些变化的可验证方式完全不同。把它们统一理解成“模型更快了”或“CLI 更稳定了”，往往会让排障方向一开始就错位。

本文选择两个不同层次的发布材料作为样本。Claude Code v2.1.331 是正式发布版本，说明中列出了 `claude doctor` 的 API 连通性诊断、OIDC 群组映射、响应压缩开关等变化；Ollama v0.40.18-rc0 则是候选预发布版本，说明涉及仅面向特定 GPU 代际和尺寸类别的 Metal 内核，以及保留 stock graph 回退路径。前者适合讨论“问题能否被定位”，后者适合讨论“优化是否真的适用”。两者共同说明：升级验收必须先拆分能力，再定义证据。

## 一、先区分三种升级证据

第一种证据是功能存在性。发布说明明确写出某个命令、配置项或能力，意味着可以把它纳入验证清单。例如 v2.1.331 增加了 `claude doctor` 的 API connectivity section，它能够报告 API 是否可达、HTTP 状态或错误，也可能说明为什么没有执行测试。这是一个诊断入口的存在性证据，不等于所有网络问题都能被自动修复。

第二种证据是行为变化。即使版本说明提到一个环境变量，也还需要验证它在目标环境下是否改变了实际行为。`CLAUDE_CODE_DISABLE_RESPONSE_COMPRESSION` 被用于请求未压缩的模型响应，材料同时明确提示该能力尚不建议用于自托管 runner 或 Remote C。这里至少包含两个边界：它是面向代理兼容性的尝试性开关，不是普遍的性能优化；它有明确的适用风险，不能因为“能设置”就默认纳入生产环境。

第三种证据是性能收益。Ollama 的 v0.40.18-rc0 发布说明提到 inkling2 的 Metal decode、prefill 和 draft rounds 优化，并列出短 BF16 product、NVFP4/MXFP8 expert gathers、融合 SwiGLU 等内核路径。但这只是实现和门控逻辑的发布证据，不是某台机器上固定倍数的加速证明。材料还说明这些内核按 GPU generation 和 size class 进行门控，并保留 stock-graph fallback。因此，正确结论应是“新增了条件化优化路径”，而不是“所有 Metal 用户都会变快”。

这三类证据不能互相替代。功能存在不等于行为生效，行为生效不等于性能提升，性能提升也不等于可靠性改善。升级报告最好把它们拆成独立字段：能力、触发条件、观测输出、回退路径和结论等级。

## 二、Claude Code 的变化：把网络故障变成可判别事件

API 连接问题通常被粗略归类为“模型不可用”，但实际故障可能发生在多个阶段：客户端没有发起检查、DNS 或代理无法连接、服务端返回错误、响应在中间代理处被截断，或者组织身份信息没有正确映射。v2.1.331 增加的 API connectivity section，价值不在于替代完整监控，而在于把“不可用”拆成更接近事实的结果。

一个最小化的升级检查可以这样设计：

```bash
claude --version
claude doctor 2>&1 | tee claude-doctor.txt
```

检查结果时，不要只搜索一个代表成功的字符串，而应记录以下字段：

```text
版本：是否为目标版本
API 检查：执行、跳过，还是失败
HTTP 状态：若有，记录原始状态码
错误信息：保留网络或代理错误
环境：是否处于代理、自托管 runner 或远程执行环境
```

如果输出显示没有执行 API 测试，不能把它解读为“API 正常”；如果显示 HTTP 错误，也不能直接把责任归因于模型服务。`claude doctor` 的结果应被当作诊断证据的一部分，继续结合代理日志、DNS 解析结果和服务端状态进行判断。

响应压缩是另一个容易被误用的变化。材料提到，`CLAUDE_CODE_DISABLE_RESPONSE_COMPRESSION` 可用于请求未压缩的模型响应，目标场景是某些代理会截断压缩响应；同时发布说明明确表示，目前不建议用于自托管 runner 或 Remote C。这个配置更像一个故障隔离开关，而不是日常默认值。

可以把验证拆成两组对照，而不是直接改生产环境：

```bash
unset CLAUDE_CODE_DISABLE_RESPONSE_COMPRESSION
claude doctor 2>&1 | tee compressed-check.txt

export CLAUDE_CODE_DISABLE_RESPONSE_COMPRESSION=1
claude doctor 2>&1 | tee uncompressed-check.txt
```

这里的关键不是比较两次命令是否都退出成功，而是比较错误是否从“响应被截断”变成“能够完整返回”，以及延迟、响应大小和代理日志是否发生变化。如果未压缩模式只能绕过代理问题，却让链路成本、响应时间或资源压力明显增加，就不应把它当作永久修复。更稳妥的工程做法是保留开关、记录触发条件，并在代理修复后重新验证默认压缩路径。

## 三、OIDC 群组映射：新增配置不等于完成授权治理

v2.1.331 还增加了 `oidc.groups_jsonpath`，用于从匹配列表对象的条目中读取群组，并采用 RFC 9535 的一小部分 JSONPath。这个变化解决的是身份声明结构与应用授权输入之间的映射问题，但不能自动证明授权策略正确。

验证时至少要准备三类身份样本：

```json
{"groups": [{"name": "engineering"}, {"name": "reviewers"}]}
```

```json
{"groups": [{"name": "engineering"}]}
```

```json
{"groups": []}
```

测试目标不是确认“能读到一个值”，而是确认四个边界：多个群组是否都能被正确识别；缺少目标群组时是否按预期拒绝或降级；空列表是否与字段缺失区分；嵌套对象或异常类型是否不会被错误当成授权成功。由于材料只说明这是一个受限 JSONPath 子集，工程上不能把完整 JSONPath 语法假设为可用。配置上线前，应只使用文档明确支持的表达式，并用真实身份声明的脱敏样本进行回归。

还需要把身份映射和网络诊断分开。API 可达只能说明连接链路某一阶段正常，不能证明 OIDC 群组被正确解析；群组映射成功也不代表目标 API 一定可访问。两者分别记录日志和验收结果，才能避免“登录成功所以权限正确”这种错误推断。

## 四、Ollama RC 的性能路径：门控和回退比宣传数字更重要

Ollama v0.40.18-rc0 的证据等级与正式版不同。它是 release candidate，发布说明描述了 inkling2 的 Metal 优化，包括 decode、prefill 和 draft rounds，并指出使用针对特定场景的 Metal kernels，同时保留 stock-graph fallback。这里至少有三个工程含义。

第一，优化不是全局路径。它按 GPU generation 和 size class 进行门控，说明同一个版本在不同硬件、模型尺寸或算子形态下可能走不同实现。不能拿一台符合条件的设备的结果，推导所有 Apple Silicon 或所有 Metal 后端都获得同样收益。

第二，回退路径是性能优化的可靠性保险。新内核即便没有达到预期，也不必然导致功能失败，因为不满足条件时可以使用 stock graph。但这并不意味着回退完全没有成本：它可能带来更低吞吐、更高延迟或不同的显存行为。因此验收时应记录实际走的是优化路径还是回退路径，而不是只记录“请求成功”。

第三，RC 版本不能直接当作稳定承诺。候选版本适合实验室或隔离环境验证，不应仅凭 release note 就替换稳定版本。尤其是涉及 BF16、NVFP4、MXFP8、专家路由和融合算子的变化，测试集合必须覆盖目标模型实际使用的算子组合。

一个不依赖具体性能数字的验证矩阵如下：

| 维度 | 至少记录的内容 |
| --- | --- |
| 版本 | Ollama 版本、是否为 RC |
| 硬件 | GPU 型号、代际、内存配置 |
| 模型 | 精确模型标识、量化或数据类型 |
| 阶段 | prefill、decode、draft rounds 分开观察 |
| 路径 | 优化 kernel 或 stock-graph fallback |
| 指标 | 首 token 延迟、持续生成速度、错误率、资源占用 |
| 稳定性 | 多轮重复、长上下文、并发变化后的结果 |

比较时要固定输入和输出约束，避免把采样差异、上下文长度变化或后台负载误判为内核收益。对候选版本尤其要保留稳定版本的对照结果，并规定回退条件：出现错误率上升、输出异常、资源峰值超预算，或优化只在极少数样本上生效时，就先回到稳定路径。

## 五、把发布说明转化为可执行验收单

一份可复用的升级验收单可以分为五层。

**版本层。**确认目标版本、发布类型和证据来源。正式发布、预发布和社区讨论必须分开标注。本文中 Claude Code v2.1.331 的能力描述来自项目 Release，属于正式发布材料；Ollama v0.40.18-rc0 明确是候选版本，关于性能的结论只能写成“发布说明声称新增了条件化优化路径”，不能写成稳定版本承诺。

**配置层。**列出新增命令、环境变量和身份字段，并确认默认值没有被无意改变。对压缩开关这类诊断配置，应记录启用原因和撤销条件；对 OIDC JSONPath，应保存经过脱敏的输入样本及预期结果。

**链路层。**把连接、认证、授权、模型请求和响应传输分开检查。`claude doctor` 可以提供 API 连通性的直接线索，但不能代替身份系统、代理和服务端日志。任何“检查通过”的表述，都应该带上检查范围。

**性能层。**只在输入、硬件、模型和负载可比时比较结果。对 GPU 优化，必须记录路径是否命中门控条件；否则所谓提升可能只是测试环境变化。对于 RC，性能结论应加上版本性质和回退策略。

**回退层。**每个新能力都要有明确的禁用或降级方式。Claude 的未压缩响应开关可以用于隔离代理截断问题，但不应默认永久开启；Ollama 的 stock graph fallback 则是新内核不适用时的安全路径。没有回退证据的优化，只能算实验结果，不能算完成交付。

## 六、结论：升级验收的最小单位是“可解释差异”

AI 工具的版本升级越来越像多个系统同时变化：客户端命令改变，组织身份声明改变，代理传输行为改变，底层 GPU 图和算子也可能改变。真正可靠的验收，不是把所有变化压缩成一个“升级成功”，而是为每项变化建立可解释差异：之前是什么，之后是什么，什么条件触发，如何观测，失败时如何回退。

Claude Code v2.1.331 展示了诊断能力如何把网络问题从黑盒变成可记录事件，也提醒我们配置开关存在适用边界。Ollama v0.40.18-rc0 则展示了硬件条件化优化的另一面：实现已经发布，不代表所有设备都命中，更不代表 RC 已经形成稳定性能承诺。

因此，面对 AI 运行时升级，最值得优先建设的不是一张“支持版本”表，而是一套证据表：功能存在性、行为生效、性能收益、适用条件和回退结果分别记录。只有当这些字段能够被独立复核，版本升级才不再是一次盲目的替换，而是一个可以解释、可以回滚、可以继续迭代的工程决策。
