## 先把“免费云主机”拆成五个不同命题

在社区里看到“开通 AWS 服务器免费 6 个月”时，最容易犯的错误，是把一句营销式描述当成一个完整事实。材料 S10 的原文同时提到让 Muse 代为注册 AWS、用户负责设置密码和绑定卡、搭建节点、每月使用 200G（并注明免费 100G），还提到抢甲骨文云免费实例的脚本。这里至少混合了五个命题：是否成功创建了云厂商账户，是否真的创建了计算实例，实例是否能持续运行，流量或其他额度是否属于免费层，以及超出免费范围后由谁承担费用。

这五件事不能互相证明。注册成功不等于实例存在；实例存在不等于账单为零；账单暂时为零不等于没有产生可结算用量；当前没有扣款也不等于绑定的支付方式不会承担未来费用。尤其当注册动作由第三方 Agent 执行时，账号控制权、恢复邮箱、双因素认证、API 密钥和支付方式会被拆散到不同参与者手中，风险不再只是“机器能不能用”。

因此，本文把 S10 视为社区发现，不视为云厂商的正式承诺。材料没有提供 AWS 官方免费套餐页面、具体区域、实例类型、账单截图或账户条款，也没有证明 Muse 具备官方授权。能写入工程结论的，不是“确实免费六个月”，而是：这类说法必须经过账户、资源、账单和责任链的分层验证。

## 证据等级：社区截图只能证明有人这样描述

一条云资源线索至少需要三层证据。

第一层是入口证据，证明某个页面、机器人或 Agent 确实存在。S10 是 NodeLoc 社区帖子，属于二手材料，只能证明发帖者发布了相关描述。S6 是 instabox.sh 的官方入口，但其页面内容只有“需要 JavaScript”，并没有给出 AWS、Oracle、免费期限或流量政策。因此，不能把 S6 当作 S10 所述权益的官方背书；它最多提醒我们，动态页面本身也可能无法从静态抓取结果中提供完整事实。

第二层是账户与资源证据，应该来自实际控制台或官方 API。证据至少要包含账户标识的脱敏信息、资源所在区域、资源类型、创建时间、生命周期状态和权限主体。只展示 SSH 登录窗口、面板首页或一张实例截图都不够，因为截图可能来自临时实例，也无法说明实例由谁控制、是否已经产生费用。

第三层是结算与政策证据，应该来自云厂商账单、用量明细和对应的官方条款。免费额度往往按服务、区域、资源类型、账户资格和时间窗口分别计算。一个“免费”标签不能替代这些条件。没有官方条款和账单明细时，最稳妥的表达应是“社区声称存在某项优惠”，而不是“该服务免费”。

证据还有一个常被忽略的维度：可撤销性。即使资源真的创建成功，如果恢复邮箱、根账号或支付方式不在自己手里，用户也不能独立撤销密钥、删除实例或关闭账户，那么这不是完整的可用资源，而是借用他人控制面的临时入口。

## 先检查控制权，再检查机器

面对第三方代注册或 AI 代办，第一步不应是登录服务器，而是确认账号控制面是否已经回到本人手中。可以使用下面的清单逐项核对：

- 注册邮箱是否是自己的长期邮箱，且能够独立收取安全通知；
- 根账号或主账号密码是否由自己生成，而不是从聊天记录中接收；
- 多因素认证是否绑定自己的设备，备用恢复方式是否可用；
- 是否存在未知的 IAM 用户、访问密钥、SSH 公钥、OAuth 授权或组织成员；
- 账单通知、预算告警和付款方式是否都能由自己查看与撤销；
- 代办方是否仍然保留登录权限、浏览器会话或脚本中的令牌。

如果使用 AWS CLI，命令本身只能证明当前凭据可以调用接口，不能证明账号免费。可以先做身份确认：

```bash
aws sts get-caller-identity
```

输出中的账号和 ARN 应与预期主体对应。随后查看当前区域的实例，而不是只看默认区域：

```bash
for region in $(aws ec2 describe-regions \
  --query 'Regions[].RegionName' --output text); do
  aws ec2 describe-instances --region "$region" \
    --query 'Reservations[].Instances[].{Id:InstanceId,State:State.Name,Type:InstanceType,Launch:LaunchTime}' \
    --output table
 done
```

这个检查仍然不是账单证明。它只能回答“当前凭据能看到哪些 EC2 实例”。如果命令返回空结果，可能是确实没有实例，也可能是区域、权限或账号不对；如果返回实例，也不能推导出该实例属于免费层。工程上应把身份、资源和费用结果分别保存，不能用一个成功状态覆盖全部检查。

对于不确定的第三方工具，不要把访问密钥直接交给它。优先使用官方支持的临时授权、最小权限角色或一次性工作区；若必须审查脚本，先在隔离环境中阅读它访问的域名、读取的环境变量和上传的数据。所谓“只负责设密码、绑卡，其他交给 Agent”恰恰把最关键的控制权交给了不可见过程，便利性和可审计性是冲突的。

## 账单为零不是“没有成本”的证明

云平台的成本验证要回答三个问题：已经产生了什么用量，当前适用什么抵扣，未来超额后谁会收到账单。最低限度的检查清单包括：实例小时数、磁盘容量与类型、公网 IPv4、快照、出口流量、负载均衡、托管数据库以及其他随账号启用的服务。

在控制台中，应分别查看账单摘要、按服务拆分的用量、按区域拆分的用量和预算告警。对于自动创建资源的 Agent，还要检查它是否顺手启用了不在免费范围内的附加服务。一个实例页面只展示计算资源，不代表磁盘、地址和流量没有单独计费。

可以把验证结果设计成明确的状态机：

```text
unknown       -> identity_verified
identity_verified -> resource_verified
resource_verified -> billing_observed
billing_observed -> policy_matched
policy_matched -> budget_guarded
```

任意一步失败，都不应输出“免费云主机已开通”。例如，身份已确认但账单尚未出现，应标记为 `resource_verified`，而不是 `free_confirmed`；账单当前为零但政策条件无法匹配，应标记为 `billing_observed`，因为零账单可能只是延迟、抵扣、试用余额或尚未结算。

预算与告警也必须先于生产使用。不要等待余额接近零或账单出现异常后再处理。若平台支持预算阈值、邮件通知或服务配额告警，应使用自己的通知地址，并测试通知是否能真正送达。没有告警、没有自动停机策略、没有删除清单的“免费实例”，本质上是把未知成本留给未来。

## 自动化脚本的收益与失败边界

S10 提到用于抢实例的脚本。这类自动化可以降低重复点击成本，却不能解决供应稀缺、地区配额、账户资格和风控拦截。脚本成功提交请求，最多说明请求被接受；只有在后续读取资源状态、网络连通性、账户权限和账单信息后，才能判断任务完成。

一个可靠的自动化流程至少要具备幂等性。每次运行前先查询已有资源，使用稳定标签记录创建者和用途，避免失败重试导致重复实例；收到限流或配额错误时采用退避，而不是高频重试；创建成功后保存资源 ID、区域和时间戳；超过预期生命周期时主动清理。脚本日志不得输出访问密钥、完整邮箱、支付信息或私钥。

失败也要分类记录：

- `auth_failed`：凭据无效、过期或权限不足；
- `quota_failed`：区域或资源配额不足；
- `policy_unknown`：无法确认免费资格；
- `resource_pending`：请求已提交但资源尚未稳定；
- `billing_unknown`：无法读取或匹配账单；
- `cleanup_failed`：实例或附属资源未能删除。

这比一个布尔值 `success=true` 更接近真实运维。特别是账号注册和绑卡流程，自动化不应绕过验证码、身份验证或厂商风控，也不应把支付凭据放入脚本配置。社区中“能跑起来”的经验，不能替代账户所有权和服务条款的验证。

## 工程结论：把“免费”改写成可撤销的资源合同

这批材料最有价值的地方，不是证明某个云服务一定能免费使用，而是暴露了一个普遍的产品陷阱：入口、实例、额度和责任经常被一句话压缩。S10 的信息密度很高，但证据等级仍停留在社区线索；S6 则显示，一个需要 JavaScript 的官方入口并不会自动提供可引用的服务事实。两者共同说明，检索到页面和获得可治理资源之间，还隔着一条完整的证据链。

更可靠的内部定义应该是：免费资源必须具备可确认的账户控制权、可读取的资源状态、可匹配的官方政策、可观察的账单、可执行的预算保护，以及由本人完成的撤销和清理。缺少其中任一项，就把状态写成“待核验”或“试用中”，不要写成“免费已确认”。

对个人开发者而言，最小安全路径不是拒绝所有社区线索，而是把线索当作待验证输入：先确认谁控制账号，再确认创建了什么，接着确认哪些成本会产生，最后确认如何停止。对 AI Agent 而言，真正值得自动化的也不是“代绑卡、代注册”，而是可审计的资源发现、状态轮询、预算告警和清理流程。

“免费”只有在成本边界、时间边界和责任边界都能被复核时，才是一个工程属性；否则，它只是一个尚未完成验证的标题。
