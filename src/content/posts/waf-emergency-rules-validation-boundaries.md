## 先区分事实、判断与操作建议

这次更新的直接事实来自 Cloudflare 官方 Changelog：Cloudflare Managed Ruleset 针对 Java4Shell（CVE-2026-114938）新增了 6 个 malformed base64 检测，覆盖 Header、Query Value、Body Value、Path Segment、Malformed Base64url JWT Component 和 WebAuthn Value；这些规则的默认动作是 Log，而不是直接拦截，且官方说明可以在需要时覆盖默认动作。Cloudflare 同日的官方博客则将这批规则放在 Java4Shell 防护背景下说明。

因此，本文讨论的是一组已经由厂商发布的 WAF 检测规则，不是社区传闻，也不是对漏洞利用细节的推测。材料没有提供 Java4Shell 的完整攻击链、受影响产品清单、规则匹配表达式或误报统计，下面不会补写这些未经材料证明的事实。能够得到的工程问题是：当规则覆盖了多个请求输入面，并且厂商选择默认记录时，运营团队应该如何理解这个信号，怎样验证它，再决定是否改变动作。

“规则已发布”与“攻击已被阻断”是两个不同结论。前者只说明控制面出现了检测能力；后者还需要确认规则已在目标流量路径生效、事件确实被记录、请求经过预期策略，并且动作切换不会破坏正常业务。

## 六个输入面，意味着六条验证路径

这次更新最值得注意的不是“增加了 6 条规则”这个数量，而是它们分布在不同的 HTTP 输入位置。Header、Query、Body、Path、JWT 组件和 WebAuthn Value 并不是同一种业务数据。它们的编码方式、解析时机、业务用途和可接受字符范围都可能不同。把这些规则当成一个总开关，容易让验证结果失真。

可以先建立一张最小覆盖矩阵：

| 输入面 | 验证重点 | 不能直接推出的结论 |
| --- | --- | --- |
| Header | 请求头是否被边缘代理完整接收并纳入 WAF 事件 | 不代表应用一定读取了该字段 |
| Query Value | 查询参数在 URL 编码和解码后的表现 | 不代表所有参数都存在同样风险 |
| Body Value | 请求体类型、大小和解析方式 | 不代表 JSON、表单、上传内容行为一致 |
| Path Segment | 路径规范化、编码和路由匹配顺序 | 不代表源站路由一定收到相同字符串 |
| JWT Component | Base64url 组件与认证中间件的交互 | 不代表令牌已经通过身份校验 |
| WebAuthn Value | 与认证流程有关的字段是否被正确观察 | 不代表整个 WebAuthn 流程被判定为攻击 |

这个矩阵的作用不是猜测规则内部实现，而是避免只构造一种请求就宣称“防护已验证”。官方公告明确列出了六类位置，因此验证也应至少按照这六类位置分别记录结果。若某个业务完全不使用其中一类输入面，应该记录为“不适用”，而不是把它混入“通过”。

## 为什么默认 Log 不是防护失效

WAF 规则的动作至少可以分成两个层次：观察和阻断。Log 模式的价值在于先获得生产流量中的命中样本，再判断规则信号与业务请求之间的关系。Cloudflare 官方公告给出的理由是这些新检测默认采用 Log，以降低误报风险；这并不等于规则没有检测能力，也不等于所有命中都应被忽略。

对于编码异常类规则，误报风险尤其需要单独评估。现实系统可能存在签名、令牌、兼容性字段或经过多层代理转换的数据。即使某个值看起来“不规范”，也不能仅凭 WAF 命中就得出“这是恶意请求”的结论。反过来，Log 也不是最终安全动作：如果命中事件没有被告警、分流和复核，记录本身不会改变风险。

更准确的判断链应该是：

1. 规则是否处于目标域名、目标路径和目标请求类型的实际流量路径上。
2. 命中事件是否包含足够上下文，例如规则 ID、请求位置、时间、主机和动作。
3. 命中是否集中在少量异常来源，还是由正常客户端、SDK 或内部服务持续产生。
4. 业务是否能够在不依赖该字段的情况下处理请求，或是否存在明确的兼容性例外。
5. 在限定范围内切换为拦截后，错误率、认证失败率和关键接口成功率是否出现变化。

只有当这些问题有可追溯答案，才适合从 Log 进入更强动作。动作切换应是基于证据的决策，而不是看到新规则后立即全局开启 Block。

## 可复现的验证方法：先构造，再观察

验证应在隔离的测试域名、候选路径或明确的低风险业务范围内进行。不要把下列请求直接发送到不属于自己的站点，也不要用真实令牌、真实用户资料或生产凭据构造测试数据。

第一步是保存一份规则基线。至少记录更新日期、规则集名称、6 个规则 ID、当前动作、作用范围和例外配置。官方 Changelog 给出的规则 ID 包括：`4d718bf4`、`2337b51d`、`e5e5836c`、`6fd6f152`、`5a25d991` 和 `67d74ebb`。这些 ID 应作为事件检索和变更审计的主键，而不是只依赖规则显示名称。

第二步是在本地生成测试输入。下面的命令只生成一个包含非法 Base64 字符的样例，不包含任何真实敏感数据：

```bash
printf '%s' 'not-base64-%%-sample' > malformed.txt
cat malformed.txt
```

然后针对自有测试端点，分别把样例放入不同位置。端点应由测试团队控制，并且请求结果要能在 WAF 事件中对应起来：

```bash
curl -i 'https://test.example.invalid/check?sample=not-base64-%%-sample'
curl -i -H 'X-Test-Value: not-base64-%%-sample' \
  'https://test.example.invalid/check'
curl -i -H 'Content-Type: application/json' \
  --data '{"sample":"not-base64-%%-sample"}' \
  'https://test.example.invalid/check'
curl -i 'https://test.example.invalid/check/not-base64-%%-sample'
```

这些命令只能验证请求是否发出以及测试端点如何响应，不能单独证明 Cloudflare 规则是否命中。真正的验证结果应来自 WAF 事件：检查对应规则 ID 是否出现、请求位置是否与测试设计一致、动作是否仍为 Log，以及事件时间是否和请求时间匹配。JWT 和 WebAuthn 两类输入不应使用随手拼接的生产令牌验证；如果业务有专用测试流程，应由测试系统生成无真实身份价值的样本，并单独标注测试流量。

第三步是做负向验证。准备合法业务样本，确认正常请求不会因为字段位置变化、代理重写或客户端版本变化而大量命中。正向样本只能证明“某些异常输入被观察到”，负向样本才有助于发现规则与业务协议之间的冲突。两组样本都要保留请求时间、请求标识和预期结果，避免事后凭记忆判断。

## 从 Log 到 Block 的分阶段切换

最稳妥的切换方式不是一次性改全局动作，而是分阶段收敛范围。可以采用以下顺序：

### 阶段一：确认可见性

维持官方默认的 Log 动作，验证六类输入面是否都能在事件中被区分。若某类测试请求没有事件，先检查流量是否经过相应站点、WAF 策略是否覆盖该路径、请求是否被前置代理终止，以及事件检索条件是否使用了正确的规则 ID。不要把“事件搜索不到”直接解释为“规则没有命中”。

### 阶段二：按业务边界统计

按主机、路径、请求方法、客户端类型和规则 ID 聚合命中。这里的目标不是追求一个漂亮的总命中数，而是找到稳定模式：某条规则是否只命中测试样本，是否集中在一个接口，是否由某类合法客户端产生。统计时应保留原始事件样本，敏感字段只保存经过脱敏或哈希处理的标识。

### 阶段三：限定范围拦截

对于命中来源和业务行为已经明确的规则，可以先在测试域名、低风险路径或小范围条件中启用更强动作。切换前应定义回退条件，例如关键接口错误率上升、认证成功率下降、特定客户端大量失败或支持工单异常增加。回退不应依赖临时手工记忆，而应写入变更单和操作手册。

### 阶段四：持续复核例外

官方公告允许在需要时覆盖默认动作，但“可以覆盖”不等于“应该永久放宽”。任何例外都应包含规则 ID、适用范围、业务理由、负责人、创建时间和失效时间。没有失效时间的例外会逐渐变成不可见的安全债务；全局关闭则会掩盖后续规则更新带来的变化。

## 失败边界：哪些结论不能从一次命中得到

第一，命中不等于漏洞利用成功。WAF 只观察到符合检测条件的请求特征，不能据此证明源站执行了危险操作。要确认影响，需要结合应用日志、认证日志和业务结果；本文材料没有提供 Java4Shell 的完整利用验证方法，因此不应把 WAF 事件包装成漏洞复现报告。

第二，未命中不等于安全。规则只覆盖官方公告列出的六类 malformed base64 位置，且材料没有说明它是完整防护方案。没有命中可能意味着输入没有落在这些位置、请求没有经过该策略、日志检索不完整，或者样本不符合规则条件。它不能替代补丁、应用层修复、访问控制和源站审计。

第三，Log 不等于没有动作。记录会影响告警、工单、审计和事件响应流程；如果日志进入了高噪声管道，真正的异常可能被淹没。切换前应验证事件保留时间、字段脱敏和检索权限，而不是只看控制台上是否出现一条记录。

第四，规则 ID 不等于永久稳定的业务语义。规则可能被更新、替换或调整动作。工程上应同时保存发布日期、显示名称和规则 ID，并在规则变更后重新运行最小正负样本集。

## 原创结论：安全动作的最小单位是“规则—输入面—业务范围”

这次应急更新给出的启示，不是“WAF 新规则应该默认拦截”，也不是“默认 Log 就不值得关注”。更可操作的结论是：安全动作的最小治理单位应当是“规则—输入面—业务范围”三元组。

同一规则在 Header 与 Body 中的误报来源可能不同；同一输入面在登录接口与公开搜索接口中的业务容忍度也不同。因此，按整个规则集全局切换动作，往往丢失了最有价值的上下文。将规则 ID、请求位置和业务范围绑定起来，才能做到既保留厂商快速发布检测能力的速度，又避免把未知误报直接转化为全站故障。

最终验收也应写成可复核的句子：六类规则是否都能被定位；正向样本是否进入预期事件；合法样本是否保持低噪声；当前动作是否符合变更目标；拦截后的回退条件是否可执行。只有这些证据闭环，才能把“厂商发布了应急规则”推进为“组织已经完成了可验证的防护变更”。
