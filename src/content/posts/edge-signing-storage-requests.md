私有对象存储的访问签名，常常卡在一个看似很小的环节：请求发出时，认证头里的日期和签名必须与实际请求一致。把这件事交给每个调用方处理，意味着多个客户端都要实现签名逻辑；把它移到请求经过的边缘规则，则能让调用方少承担一段认证代码，但也把规范化、凭据管理和验收责任集中到了规则配置上。

Cloudflare 在 2026 年 11 月 27 日的更新中，为 Rules 语言增加了 HMAC、SigV4 签名密钥派生和 UTC 日期格式化函数，目标场景是通过 Request Header Transform Rules 认证对私有 Amazon S3 和 Google Cloud Storage bucket 的读取。关键不是“边缘替你完成了一切”，而是签名计算能力进入了规则表达式；规范请求和待签名字符串仍由规则作者负责构造。

## 签名计算被拆成了哪些部分

可以把这条链路看成三个相互依赖的阶段。

第一阶段是时间输入。请求日期既可以作为存储服务要求的日期头，也可能参与凭据作用域或签名材料。更新提供 `format_date()`，可以从请求时间戳生成 UTC 日期文本。官方示例为：

```text
format_date(http.request.timestamp.sec, "%Y%m%dT%H%M%SZ")
```

这一步减少了调用方提供日期头的需要，但它只解决日期文本的生成，不会替你判断某个请求是否应该被允许签名，也不保证其他参与签名的字段已经规范化。

第二阶段是摘要与密钥处理。规则语言提供 `hmac_md5()`、`hmac_sha1()`、`hmac_sha256()` 和 `hmac_sha512()`，计算原始 keyed digest；`encode_hex()` 可以把原始摘要编码为小写十六进制文本。另有 `sign_sigv4_hmac_sha256()`，将 SigV4 的签名密钥派生和签名计算合并为一次调用，并返回小写十六进制签名。它们是表达式里的计算能力，不等同于自动发现存储凭据、选择 bucket、授权对象路径或替应用决定访问策略。

第三阶段是请求头改写。规则可用请求时间戳构造 `x-amz-date` 或 `x-goog-date`，也可以把 Authorization 头拼接起来。实际签名还取决于规则作者构造的规范请求和 string to sign。边缘计算接手的是“按给定输入执行函数”，而不是替代协议实现者对输入内容负责。

## 把规则当作受约束的签名入口

更稳妥的设计，是先定义哪些请求可以进入签名流程，再生成认证头。规则匹配条件应尽量收窄到预期的主机、路径范围和请求类型；不要把“能计算签名”作为开放代理的理由。尤其要检查客户端是否可任意指定目标对象、查询参数或会改变签名语义的请求头。签名规则若覆盖了不该开放的路径，计算本身正确也仍会产生过宽的访问能力。

在表达式层面，先单独验证日期文本，再验证签名输入，再接入最终头部，能把排错范围拆小。可以把以下内容作为上线前清单：

- 确认账号计划满足 HMAC 与 SigV4 函数的使用条件；这组签名函数面向 Pro、Business 和 Enterprise 计划。
- 用更新中给出的日期表达式确认生成值采用目标服务需要的 UTC 格式；`format_date()` 本身在所有计划可用。
- 明确规则覆盖的请求范围，以及规范请求和 string to sign 如何与目标存储协议保持一致。
- 确认 Authorization 头中每一段文本的拼接、大小写和编码都与待签名输入一致；不要只检查最终表达式是否能保存。
- 将 S3 与 GCS 作为不同的目标配置分别验证。更新列出两种存储场景，但不应据此假设所有头部、凭据或错误行为完全相同。
- 使用不含敏感对象的测试路径验证规则，再逐步扩大覆盖面；确保失配时不会把受保护对象内容返回给调用方。

这里有意不提供一条看起来完整、却未经目标配置验证的 Authorization 表达式。官方更新列出了函数能力，但没有在变更摘要中给出适用于所有 bucket、凭据和请求形式的通用规则。签名串的组成与部署上下文有关；复制一段未经核对的字符串模板，比明确标注边界更容易造成“配置成功、请求仍失败”或错误放行。

## 用正向与反向请求验收

验证应覆盖“该成功的成功”和“该失败的失败”，而不是只看规则编辑器接受表达式。对于已经设置好边缘规则的测试域名，调用方可以用普通 GET 发起请求：

```bash
curl --include --request GET 'https://<测试域名>/<测试对象路径>'
```

正向用例检查返回内容是否对应预期对象，而不只是响应看起来成功。若使用不存在的对象或权限不足的对象，记录目标服务实际返回的行为；某些服务可能以不同状态码表达拒绝或不存在，因此验收重点应是受保护内容没有泄露，而不是把单个状态码当成跨服务标准。

随后做反向测试：在隔离环境里修改一个会影响签名的输入，例如请求路径或规则中的测试密钥，观察原本可读的测试对象是否仍能被错误地读取。还应测试规则不匹配的路径，确认其不会意外附加签名头或获得同等访问能力。对每一组测试，记录请求条件、实际响应和目标 bucket 的对应行为；如果边缘响应与预期不符，应分开检查规则是否命中、日期值是否符合格式、规范请求是否与真实请求一致，以及目标凭据是否具备该对象的读取权限。

需要谨慎解释验证结果：一次成功读取只能说明这组请求和配置能够工作，不能证明所有路径、方法、查询参数都正确；一次 403 也不能单独说明签名算法出错，因为权限、对象存在性和规则匹配都可能影响结果。将规则命中情况、请求输入和目标侧响应放在一起看，才更有助于定位问题。

## 日期自动化不会消除时间与规范化边界

自动生成 UTC 日期，解决的是日期值与请求时间来源的一致性问题，不是所有时间相关故障。请求时间戳如何进入表达式、日期字符串如何参与作用域，以及其余签名输入如何从同一请求构造，都应保持一致。若日期头来自请求时间戳，而签名串却拼接了另一套静态日期，结果仍可能不匹配。

同样，HMAC 函数只会对提供的字节输入计算摘要。路径编码、查询参数顺序、头部文本和请求方法如果在实际请求与规范请求之间不一致，签名就可能对“另一份请求”有效。这里的工程重点不是再增加一层复杂抽象，而是让签名所依据的输入可检查、可复现，并在测试中有意改变单个输入观察结果。

还有一个重要的计划边界：HMAC 与 SigV4 签名函数并非所有计划都能使用，而 `format_date()` 在所有计划上可用。规则语言函数也有适用位置限制：`format_date()` 可用于 URI、请求头和响应头改写表达式，不能用于规则过滤器。也就是说，日期表达式可以生成头部值，却不能直接被当成过滤条件来决定规则是否匹配。部署前要分别核对“函数是否可用”和“表达式放置位置是否支持”，不要把两者混成一个检查项。

## 选择边缘签名，还是由应用签名

将签名放在边缘侧的优势是认证头可以在统一的请求处理位置生成，调用方无需各自重复实现同一段签名逻辑；日期也能从请求时间戳动态格式化。代价则是规则配置成为关键运行代码：任何输入构造错误都可能影响一组请求，表达式的可读性和变更审核也变得重要。若应用端需要更细的对象级授权、不同用户对应不同凭据，或者请求签名材料高度依赖业务上下文，就不能只因为边缘有 HMAC 函数而把决策全部迁过去。

工程上可按请求稳定性做取舍：若签名所需信息都能从已验证的请求上下文中安全确定，边缘改写可以减少客户端重复工作；若授权逻辑依赖调用者身份、动态业务规则或复杂的逐对象策略，应用层通常更适合作为授权决策者，边缘只做范围清晰的转发或头部处理。无论哪种方案，都要避免把“签名成功”误认为“访问授权设计正确”。

这次更新带来的实际变化，是 Rules 语言能执行更多签名计算，不是私有存储访问从此无需协议知识。最值得优先验收的并非函数名单，而是三条边界：规则是否只覆盖预期请求，签名串是否忠实对应实际请求，以及错误输入是否会被安全拒绝。只要这三条仍由工程团队显式负责，边缘签名才是可管理的实现选择，而不是一段看似自动化的隐藏授权逻辑。
