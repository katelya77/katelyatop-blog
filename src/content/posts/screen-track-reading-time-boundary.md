## 先把“阅读时长”从一个数字拆成一条链路

论坛中的阅读时长，表面上像一个简单的累计器：页面打开了，时间就应该增加。但从材料中披露的浏览器观察结果看，它更接近一条由客户端采样、浏览器状态判断、批量上报和服务端约束共同组成的链路。

可以把它抽象成：

```text
帖子进入视口
    ↓
客户端按秒产生 tick
    ↓
本地按 post_id 累积毫秒数
    ↓
约每 60 秒批量 POST /topics/timings
    ↓
服务端校验、限流、取整与封顶
    ↓
社区等级系统读取 time read 等字段
```

这条链路与普通的“打开标签页计时”有本质区别。它计量的不是浏览器进程存在了多久，而是某个帖子在满足若干条件时，被客户端认为处于可阅读状态的时间。帖子通常以 `article[data-post-id]` 作为独立对象，主楼和每一条回复都可能分别进入计时范围。

因此，阅读时长首先是一个**帖子级指标**，随后才可能被汇总为账号级指标。这个顺序很重要：当一个帖子达到服务端或客户端设置的上限后，继续停留并不会线性增加账号收益；当页面失去焦点或帖子离开视口时，计时也不应被理解为仍在持续。

## 客户端计时：视口、焦点和滚动共同决定是否“有效”

材料中的 DevTools 观察给出了几个关键边界。客户端大约每秒为当前视口内的帖子增加一个 tick，先在本地累积，随后再批量发送。计时并不是对整个主题页统一加秒，而是重新判断当前屏幕中有哪些帖子。

用伪代码表达，大致可以理解为：

```js
for (const post of visiblePosts()) {
  if (document.visibilityState === "visible" && document.hasFocus()) {
    post.elapsedMs += 1000;
  }
}
```

这段代码不是论坛源码，而是根据材料还原出的机制模型。它解释了三个常见现象：

第一，切换标签页、最小化窗口或让浏览器失去焦点后，tick 会停止。`document.visibilityState` 只能说明页面是否处于可见状态，`document.hasFocus()` 则进一步限制了窗口是否拥有焦点。两者同时参与判断，意味着“页面还开着”并不足以证明阅读时长仍在增长。

第二，滚动会改变正在计时的帖子集合。一个很长的主题可能同时包含主楼和许多回复，用户滚动一次，计时对象就可能从上一组 `post_id` 切换到下一组。由此产生的时长更接近“多个帖子的可见时间之和”，而不是一个主题从打开到关闭的墙上时钟。

第三，连续一段时间没有滚动后，子系统会自动暂停。材料给出的观察值约为 300 秒。这个规则体现了一个典型的工程取舍：系统不要求判断用户是否真的读懂内容，但可以用滚动、焦点和视口等低成本信号，降低无人操作页面长期累积时间的概率。

读者可以在自己的浏览器中做非侵入式核验。打开一个主题页，使用开发者工具的 Network 面板过滤 `timings`，只观察请求时间、请求方法和请求体结构；再在 Elements 面板确认帖子是否以独立的 `article[data-post-id]` 呈现。验证过程不需要修改请求、不需要重放请求，也不应该尝试伪造计时数据。

## 上报不是结算：POST 请求只代表客户端提交了观察结果

材料显示，客户端约每 60 秒向 `/topics/timings` 发送一次批量数据，形式可以概括为：

```json
{
  "post_id": 180000
}
```

实际请求可能包含多个帖子及其他字段，这里只展示结构化思路。关键点在于：请求中的毫秒数是客户端积累并提交的观测值，不等于服务器无条件接受后的最终值。

服务端至少可能承担三类职责。

其一是**频率控制**。材料提到连续请求可能触发 `429` 限流。这样做可以避免客户端通过高频请求放大计时，也能降低异常流量对站点的压力。对普通用户而言，最合理的客户端行为是保持页面自然运行，不主动缩短上报间隔。

其二是**单帖封顶**。材料给出的观察值是单帖最多计入约 6 分钟，即 360000 毫秒。这个上限改变了“停留越久越有效”的直觉：如果仍在同一帖子上停留，超过封顶之后，客户端或服务端都可能不再产生有效增量。这个设计既限制了单个页面的异常贡献，也迫使指标更接近多帖阅读，而不是单帖挂机。

其三是**取整与窗口统计**。社区材料对 `time read` 是否为累计值存在冲突：一份材料把它描述为 100 天滑动窗口，另一份帖子则认为是累计模式。这个矛盾不能靠经验推断解决。较稳妥的结论是：客户端 tick、可见性门控和单帖封顶属于较具体的机制观察；账号等级字段如何聚合、是否按窗口回落，则必须以站点当前公告和账号进度页为准。

这也是工程系统中“采集值”和“业务值”的区别。客户端提交的是原始事件，服务端可能进行校验、去重、封顶、窗口化和延迟更新。看到 Network 面板里某个请求成功，并不能直接推出等级页面会立即增加相同数量。

## 为什么“挂着网页”不是可靠策略

如果只看界面，最容易产生的误解是：只要标签页没有关闭，时间就会持续累积。但上述链路至少有四道边界会打破这个假设：

```text
页面存在 ≠ 页面可见
页面可见 ≠ 窗口有焦点
窗口有焦点 ≠ 帖子仍在视口
帖子在视口 ≠ 尚未达到单帖上限
```

再加上连续无滚动暂停和服务端频率控制，长期无人操作页面很难稳定地产生有效时长。即使某次观察中出现了增长，也不能据此推导出可重复、可持续的自动化收益。

更重要的是，社区材料明确将刷在线时长或刷回复视为违规风险。这里不讨论脚本实现，也不提供修改 `visibilityState`、模拟焦点、重放 `/topics/timings` 或构造请求的教程。原因不仅是规则层面的风险，还因为这种做法会同时面对客户端状态检查、服务端限流、单帖封顶以及账号侧异常行为判断，收益和风险并不对称。

从系统设计角度看，反自动化并不需要做到“完美识别人类”。它只要让低成本挂机方案的收益下降，让伪造请求需要承担更高的不确定性，就已经完成了主要目标。这是一种常见的防滥用策略：不追求绝对证明，而是提高自动化的边际成本。

## 一份不越界的复核清单

如果目的是理解机制，而不是操纵指标，可以按下面的顺序检查：

1. **确认页面结构**：在 Elements 中查找 `article[data-post-id]`，确认主楼和回复是否具有独立标识。
2. **确认请求节奏**：在 Network 中过滤 `timings`，记录自然浏览时请求的大致间隔，不修改请求内容。
3. **确认焦点影响**：在相同主题页中，分别保持窗口聚焦、切换到其他标签页，观察请求和页面状态是否变化。
4. **确认视口影响**：让某条回复进入和离开当前视口，比较相关帖子是否继续出现在本地计时对象中。
5. **确认长时间静止行为**：在不滚动的前提下观察约数分钟，记录计时是否暂停；不要为了验证而批量刷新或并发访问。
6. **区分事实层级**：把“浏览器中看到的请求”“社区作者的机制推断”“站点官方公告中的等级条件”分开记录。
7. **以账号页面为最终结果**：如果社区公告、社区讨论和个人进度显示不一致，以当前站点公开页面和最新规则为准。

还可以在控制台做只读观察，例如：

```js
({
  visibility: document.visibilityState,
  focused: document.hasFocus(),
  posts: [...document.querySelectorAll("article[data-post-id]")]
    .map(el => el.dataset.postId)
})
```

这段检查只读取页面状态和帖子标识，不改变计时逻辑，也不发送额外请求。它适合帮助读者理解“页面上有哪些计时对象”，但不能证明服务端最终接受了哪些数据。

## 证据等级比“看起来合理”更重要

本批材料主要来自 NodeLoc 社区帖子，其中一份材料较完整地记录了 DevTools 观察过程，另一份则提供了面向普通用户的机制总结。这些内容可以支持“客户端存在帖子级 tick、可见性与焦点会影响计时、存在上报和单帖封顶”等方向性的判断，但仍属于社区实测和二次整理，不应直接包装成 Discourse 或 NodeLoc 的正式源码说明。

材料中另有一个官方页面访问结果显示环境异常，无法提供可核验正文。因此，涉及阈值、等级窗口、掉级条件等业务规则时，不能因为社区帖子引用了“官方公告”就自动把所有数字提升为已核验的一手事实。尤其是材料内部已经出现了“滑动窗口”和“累计模式”的冲突，更应该把不确定性写出来，而不是挑选一个更符合直觉的版本。

这给技术写作和工程排障都提供了一个通用方法：先把观察到的现象、推断出的机制和官方确认的规则分层，再讨论结论。浏览器 Network 面板能证明请求发生过，却不能单独证明业务结算；社区经验能帮助定位问题，却不能代替版本化文档；页面显示的数字能代表当前状态，却不一定解释历史聚合方式。

## 结论：真正被计量的不是“在线”，而是可验证的阅读信号

这套机制的核心并不是把用户阅读精确到每一秒，而是把“可见、聚焦、处于视口、持续产生交互”的信号组合起来，形成一个成本可控的近似指标。客户端负责低成本采样，服务端负责限流、封顶和业务聚合，社区等级系统再把聚合结果转化为权限或等级。

因此，理解阅读时长最有价值的结论不是“每个帖子看几分钟最划算”，而是：**不要把客户端计时请求当成最终业务事实，也不要把页面打开当成有效阅读证明。** 对使用者来说，合规且可靠的路径是按正常节奏浏览、持续参与并以站点当前进度页面为准；对开发者来说，关键则是明确采集层、结算层和规则层的边界，并为每一层提供可独立验证的证据。

当一个看似简单的“时长数字”背后同时存在视口检测、焦点门控、批量上报、限流、封顶和时间窗口时，它已经不是一个计时器，而是一套小型的反滥用系统。
