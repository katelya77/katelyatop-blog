## 代码审查的变化：从一次调用变成一组可治理状态

过去讨论 AI 代码审查，常见问题是“能不能发起审查”“模型发现了多少问题”“评论是否足够准确”。这些问题仍然重要，但当审查进入团队流水线后，真正难管理的往往不是一次调用，而是这次调用处在什么政策环境中：企业是否允许使用、组织是否启用、仓库采用哪种审查投入程度、是否允许自定义指令和 MCP 工具、最终评论是否确实来自 Copilot，以及某些文件为什么没有被审查。

GitHub 在 2026 年 11 月 6 日的 Changelog 中宣布，Copilot code review 的设置可以通过 REST 和 GraphQL API 管理，范围从企业策略延伸到组织和单个仓库；同时，审查和评论可以通过明确的归属字段识别，审查还可能返回使用的 effort，以及 Copilot 报告的技能、MCP server 和自定义指令来源。这个变化的核心，不是多了几个接口，而是把原本藏在网页操作和评论文本里的状态，变成了能够读取、比较和审计的控制面数据。

因此，工程团队不应只把 API 当作“批量改配置”的脚本入口。更稳妥的理解是：AI 审查由执行面、策略面和证据面组成。执行面负责请求审查并获取结果；策略面决定谁能启用、默认投入程度和运行器配置；证据面回答这条评论由谁产生、使用了哪些上下文、哪些文件被跳过，以及配置是否被上级策略锁定。

## 先画清层级：企业策略不是仓库默认值

材料明确给出的层级至少包括企业、组织和仓库。企业管理员可以为所有组织启用或禁用代码审查，也可以把选择权交给组织管理员。组织管理员可以管理启用状态、默认 review effort 和 runner 配置。仓库管理员则可以管理审查 effort，以及是否使用自定义指令和 MCP 工具。一个关键约束是：企业管理的设置不能被下级覆盖。

这意味着配置模型不能简单地理解为“最后一次写入获胜”。更接近真实情况的模型是带有来源和锁定状态的策略合并：

```text
企业策略
  └── 组织策略
        └── 仓库策略
              └── 单次审查请求
```

仓库管理员看到的值，可能只是当前有效值，不一定代表仓库拥有修改权。若脚本只读取仓库配置，然后直接写入期望值，就可能把“未授权修改”“上级锁定”和“目标值已经一致”混为一谈。批量治理前，至少应保存以下字段：目标层级、当前值、期望值、是否由上级管理、执行身份、修改时间和 API 响应。

可以先建立一个只读检查流程。伪代码如下：

```bash
# 伪命令：实际路径以 GitHub API 文档中的 endpoint 为准
get_enterprise_review_policy "$ENTERPRISE" > enterprise.json
get_org_review_policy "$ORG" > org.json
get_repo_review_policy "$OWNER/$REPO" > repo.json

jq '{enabled, effort, runner, managed_by}' enterprise.json
jq '{enabled, default_effort, runner, managed_by}' org.json
jq '{effort, custom_instructions, mcp, managed_by}' repo.json
```

这里的重点不是命令名称，而是先读后写、保留来源、逐层判断。若企业策略已经管理某项配置，仓库级自动化应将其标记为“不可覆盖”，而不是继续重试。这样既避免无意义的 API 调用，也避免把权限边界误报成系统故障。

## 权限边界：同一个 API 不代表同一种凭据

S2 特别指出，企业和组织设置 endpoint，包括组织 runner endpoint，不支持 GitHub Apps 或 fine-grained personal access tokens。仓库设置 endpoint 则支持这两类身份，并分别需要 Administration: read 或 Administration: write 权限；classic personal access token 需要仓库管理员访问权限。

这条限制会直接影响自动化设计。一个常见但危险的假设是：只要某个机器人能够调用仓库 API，就可以顺手读取企业和组织设置。实际上，设置范围不同，支持的认证方式也不同。把同一个 token 复制到所有层级，既可能在较高层级失败，也可能诱使团队为了“让脚本跑通”而扩大凭据权限。

更可靠的做法是按管理边界拆分凭据和任务：

1. 企业策略检查由企业管理员上下文执行，并且只授予读取所需能力。
2. 组织配置检查和修改由组织管理员流程执行，组织 runner 配置单独记录失败原因。
3. 仓库级配置由仓库管理员或具备明确 Administration 权限的自动化身份执行。
4. 只读审计和变更操作使用不同的工作流，避免一个任务同时拥有不必要的写权限。

每次调用都应记录 HTTP 状态、请求目标层级、身份类型和返回的有效配置。不要把“API 返回 403”统一解释为 token 过期：它也可能表示认证方式不被该 endpoint 支持、权限级别不足，或者目标设置受上级策略管理。错误分类越粗，后续越容易通过扩大权限掩盖真正的策略问题。

## 归属元数据：评论内容之外还要验证评论来源

AI 代码审查的结果通常以 review 或 comment 的形式出现。只看评论正文，很难可靠判断它是 Copilot 生成的、人工补充的，还是其他自动化程序写入的。此次更新提供了明确的 attribution 字段，能够识别 Copilot 的审查和评论；在元数据可用时，还可以看到审查使用的 effort，以及 Copilot 报告的 skills、MCP servers 和 custom instructions 来源。

这让审查结果可以从“文本意见”升级为“带上下文的事件”。一个可审计的结果记录至少应包括：提交或拉取请求标识、审查请求标识、评论归属、审查 effort、是否使用自定义指令、是否使用 MCP、被报告的来源列表、审查时间和未审查文件列表。

工程上可以把这些字段用于三类校验。第一类是身份校验：流水线只统计明确标记为 Copilot 的结果，避免把普通机器人评论混入 AI 审查指标。第二类是策略校验：如果仓库要求关闭 MCP 或固定 effort，结果元数据与配置不一致时，应进入人工复核，而不是直接计入质量指标。第三类是可追溯校验：当审查结论受到争议时，能够回看它使用了哪些技能、工具和指令，而不是只保留一句评论。

需要注意的是，“能看到来源”不等于“来源天然可信”。元数据是审计证据的一部分，仍要结合请求身份、仓库配置和时间顺序判断。比如一条评论可能来自合法的 Copilot 审查，但对应的仓库配置已经在审查之后发生变化；如果不保存时间和请求关联，就无法准确解释它使用的策略。

## 文件未审查不是空白，而是结果的一部分

新的 review overview 会把 skipped files 和 content-excluded files 放入统一的“Files not reviewed”区域，并列出文件名和排除原因；空章节会被省略，过长列表则显示溢出数量。这个界面变化看似只是展示优化，实际上改变了验收重点：一次审查是否“完成”，不能只看有没有发现问题，还要看哪些文件根本没有进入审查范围。

在自动化验收中，建议把文件覆盖作为独立状态，而不是从评论数量推断。至少检查以下项目：

```text
[ ] 审查请求确实关联目标提交或目标变更
[ ] 结果中存在明确的 Copilot attribution
[ ] 使用的 effort 符合仓库或组织策略
[ ] Files not reviewed 已读取并保存
[ ] 排除原因符合预期，而不是未知或异常
[ ] 关键目录没有因规则、大小或内容限制而被静默遗漏
[ ] 失败、超时和空结果与“无问题”明确区分
```

这里最重要的边界是：没有发现问题，不等于所有文件都通过审查；没有评论，也不等于审查成功。若结果只包含压缩后的概览，系统仍应保留原始 API 响应或最少的结构化摘要，确保后续可以区分“没有发现问题”“没有审查文件”和“请求没有生成有效结果”。

## 从配置 API 到治理闭环

把这些能力放进流水线时，可以采用四阶段闭环。第一阶段是基线读取：在变更前读取企业、组织和仓库的有效设置，建立当前状态快照。第二阶段是策略评估：根据管理来源判断哪些值可改、哪些值只能报告，明确所需身份和权限。第三阶段是执行与采集：发起审查，采集归属、effort、来源和未审查文件信息。第四阶段是验收与留痕：把配置快照、请求结果和异常分类关联到同一个审查记录。

一个简单的状态机可以表示为：

```text
未检查
  -> 配置已读取
  -> 权限与继承关系已确认
  -> 审查已请求
  -> 结果已返回
  -> 归属与覆盖已验证
  -> 允许进入后续流程
```

任一步骤失败，都不应伪装成“审查通过”。例如，读取仓库设置成功但审查结果缺少 attribution，只能说明 API 可访问，不能说明结果可审计；审查评论存在但 Files not reviewed 包含关键目录，也不能直接作为合并门禁的充分依据。

这套闭环还需要接受一个现实取舍：更强的审查证据会增加存储、解析和维护成本，也可能让流水线变慢。并非所有仓库都需要把所有元数据变成硬门禁。可以把检查分成三档：核心仓库将归属、策略和文件覆盖作为阻断条件；普通仓库将其作为告警；实验性仓库只保存证据，观察稳定性后再升级门禁。关键是分档要显式配置，而不是让不同脚本在失败时各自决定。

## 结论：AI 审查的产品化终点是可解释的控制面

Copilot code review API 更新真正带来的价值，不是把网页上的几个开关搬到了 REST 和 GraphQL，而是让 AI 审查具备了控制面特征：策略有层级，权限有边界，结果有归属，运行上下文可以被记录，未覆盖范围可以被展示。

因此，团队评价 AI 审查时不应只问“发现了多少问题”，还应追问四件事：谁允许它运行、它按照哪条策略运行、这条评论是否确实由目标系统产生、哪些变更没有被覆盖。只有当这些问题能够由配置和结果证据共同回答时，AI 审查才从一个自动评论机器人，变成可以纳入工程治理的系统能力。

本文的原创结论是：代码审查自动化最容易被低估的不是模型能力，而是状态可解释性。模型输出再好，如果无法证明它在什么权限、什么配置、什么覆盖范围下产生，组织就很难把它接入高责任级别的交付流程。API 化只是起点，真正的工程工作是把策略、证据和失败边界连成一条可复查的链。
