## 先区分“存在”，再讨论“可用”

AI 网关的宣传语很容易把几个完全不同的概念压缩成一句话：有一个网页，网页上写着 Free AI Model Gateway；有人在社区发布了一个接口地址；接口返回了 JSON；某个客户端能够发出一次回复。这些现象分别证明了不同层次的事实，不能相互替代。

本批材料里，WusRouter 的一手页面只明确显示了产品名称“Free AI Model Gateway”。NodeLoc 的帖子则进一步声称该项目提供 Claude 免费额度、OpenRouter 兼容接入、Google 账号池、社区共享以及 NodeLoc OAuth 登录等能力。由于这些细节来自社区发帖，而不是项目文档、代码仓库或正式 API 说明，证据等级应标为“社区描述，待项目侧核验”，不能直接写成稳定的产品契约。

另一条社区材料给出了两个看起来像 OpenAI 风格的入口：一个使用 HTTP，一个使用 HTTPS，并带有 `/v1` 路径。帖子还提到代理池误开后产生了大量账号，并以点赞作为查看密钥的条件。这里至少包含两个工程信号：入口可能被大量陌生客户端同时探测，凭据可能处于公开传播或半公开传播状态。它并不能证明接口当前可用，也不能证明提供方授权任何第三方长期调用。

因此，免费网关的第一原则不是“找到一个能调用的 key”，而是建立证据链：入口是谁发布的，协议是什么，身份如何绑定，额度如何扣减，异常如何撤销，服务方是否提供变更和停用机制。只有这些问题能够分别得到答案，调用结果才有工程意义。

## `/v1` 只是路径，不是协议契约

很多客户端把 URL 拼成 `https://example.com/v1`，再填入一个 token，就默认后端是 OpenAI 兼容接口。这个假设经常导致错误定位：请求可能被网关接收，却不支持目标路径；也可能返回统一错误页；还可能只兼容聊天接口，不兼容模型列表、嵌入或流式响应。

验证协议时，应当先使用低风险、无凭据的请求观察边界，不要把真实生产密钥直接塞进第三方页面或诊断脚本。下面的命令只用于检查响应头和状态码，不能据此判断服务已经获得授权：

```bash
BASE_URL='https://example.example/v1'
curl --silent --show-error --include --max-time 10 \\
  "$BASE_URL/models" \\
  -o /tmp/ai-gateway-models.out

sed -n '1,25p' /tmp/ai-gateway-models.out
```

检查时至少记录四类信息：HTTP 状态码、`Content-Type`、是否发生跳转、响应体是结构化 JSON 还是 HTML。`401` 只能说明该路径要求身份认证，不能说明密钥格式正确；`404` 可能代表路径不对，也可能代表服务刻意隐藏模型列表；`429` 既可能是限流，也可能是共享额度耗尽；`5xx` 则要结合时间窗口和请求体大小继续判断。

若服务方明确提供了兼容接口，再使用一个非敏感、低成本的探针。请求体应该固定模型名、短提示词和较低输出上限，并显式关闭流式，以便首先确认普通 JSON 响应：

```bash
BASE_URL='https://example.example/v1'
API_KEY="$AI_GATEWAY_KEY"

curl --silent --show-error --max-time 20 \\
  "$BASE_URL/chat/completions" \\
  -H 'Content-Type: application/json' \\
  -H "Authorization: Bearer $API_KEY" \\
  --data '{
    "model": "replace-with-documented-model",
    "messages": [{"role": "user", "content": "Reply with OK."}],
    "max_tokens": 8,
    "stream": false
  }'
```

这里的 `replace-with-documented-model` 故意不是猜出来的模型名。社区帖子中出现的模型名称、账号数量或免费额度，都不应自动变成接口契约。只有服务方公开列出的模型、计费和限制，才适合进入应用配置。探针成功也只证明“在某一时刻、某一凭据、某一请求下获得响应”，不证明延迟、配额、数据保留和可用性承诺。

## 共享资源最容易缺少的是隔离层

“免费”通常意味着成本由某个集中资源承担，而不是请求没有成本。WusRouter 的社区介绍提到账号池、额度刷新和社区共享，这类设计的核心风险不是功能数量，而是资源与身份之间的映射是否可审计。

一个可治理的网关至少要把四种主体分开：登录主体、调用主体、上游账号和计费主体。用户登录账号不应直接等同于某个上游 Google 账号，也不应把一个共享 token 当成所有用户的永久身份。网关需要能够回答：某次请求由谁发起，使用了哪个上游，消耗了哪一类额度，发生了什么错误，是否可以只撤销这一条映射。

最小数据模型可以从以下关系开始：

```text
user ──< credential ──< request ──> upstream_account
  │                         │
  └──── quota_ledger <──────┘
```

`credential` 只保存哈希、状态、创建时间和撤销时间，不保存可逆明文；`request` 保存请求摘要、模型、状态码、延迟区间和成本估计，正文与完整提示词应按隐私策略单独处理；`quota_ledger` 采用追加记录而不是直接覆盖余额，便于解释额度为何变化。上游账号池需要有健康状态、冷却时间和失败计数，但不能让“自动换号”成为掩盖封禁或超限的手段。

额度控制也不能只放在前端按钮上。至少要有三层：用户级速率限制、凭据级并发限制、全局上游预算。每一层都应有明确的失败响应和重试策略。比如用户级限制可以返回 `429` 并带 `Retry-After`；上游返回认证错误时，凭据应进入隔离状态，而不是立即无限轮换其他账号；全局预算触顶时，应停止新请求并保留可查询的账本记录。

NodeLoc 材料中“代理池忘记关闭后出现大量账号”的描述，恰好说明自动化注册或批量入口一旦失去边界，资源池会从内部运维工具变成公共攻击面。无论这个描述是否完整属实，工程上都应把注册、登录、密钥签发和模型调用分开限速，并设置紧急开关：可以停止新注册，可以冻结单个凭据，可以切断某个上游，而不必关闭整个网关。

## 验证链要覆盖正常、异常和撤销

一个网关的验收不能只写“curl 返回 200”。更可靠的检查清单应当包含以下路径。

第一是身份链。新建一个测试账号，确认未登录请求不会意外获得调用能力；签发凭据后，检查凭据是否只显示一次、是否能单独撤销；撤销后重复请求，预期应得到明确的认证失败，而不是继续消耗上游额度。

第二是协议链。分别测试模型不存在、请求体缺字段、输出上限过大、流式开启和普通 JSON 五种情况。记录错误是否稳定地使用 JSON 格式，是否包含可定位的错误类型，是否把上游密钥、账号标识和内部 URL 泄露到响应中。兼容 OpenAI 不代表所有 OpenAI 客户端行为都能工作，尤其要验证流式事件格式、终止标记和代理层的超时设置。

第三是配额链。用极短请求确认正常扣减，再发送一个预计会触发限制的请求，检查限制发生在用户、凭据还是全局层。需要验证并发请求下不会出现负余额、重复扣减或“请求失败但额度已扣、日志却不存在”的不一致。账本应能区分预扣、成功结算、失败释放和人工调整。

第四是故障链。主动模拟上游超时、认证失败、响应格式错误和网关重启。客户端只允许对可重试错误进行有限次数、带退避的重试；认证失败、参数错误和配额耗尽不能盲目重试。对于流式响应，网关还要定义“已经输出部分内容但连接中断”是否计费，以及客户端重新发送是否可能造成重复执行。

第五是观测链。至少收集请求总量、状态码分布、P50/P95 延迟、上游失败率、活跃凭据数和额度异常。日志字段应使用请求 ID 关联各层，不要默认记录完整提示词和 `Authorization` 头。外部探针只能验证可达性与表面协议，不能替代网关内部的额度账本和上游审计。

## 失败边界决定它能不能进入生产

免费入口最常见的误判，是把短期可用性当成长期依赖性。共享资源可能被撤回，社区帖子可能被编辑或删除，入口可能因为滥用而更换域名，账号池可能因上游策略变化而失效。材料中没有提供 WusRouter 的正式 SLA、版本记录、API 文档、数据保留政策或稳定性承诺，因此不应为它推导出生产级保证。

工程上更稳妥的做法是把这类网关放在可替换适配层后面。应用只依赖内部统一接口，网关适配器负责模型名映射、错误分类、超时和指标；配置中保留至少一个经过正式授权的备用提供方。切换条件不应只有“请求失败”，还可以包括连续认证错误、P95 延迟超过阈值、额度余额低于安全线或证据链发生变化。

对于公开传播的接口地址，更要把凭据当作可能已经暴露处理。不要在浏览器扩展、代码仓库、截图或共享配置中保存真实密钥；不要因为帖子要求点赞、私信或进入群组就把它当成安全证明；不要把第三方账号池接入涉及个人资料、商业机密或不可恢复操作的工作流。若必须评估，使用最小权限、最小额度、最短有效期和可撤销凭据，并在验证结束后立即回收。

## 结论：网关的价值在于可撤销，而不是免费

从公开材料能够确认的是：社区正在讨论共享模型资源和 API 入口，WusRouter 对外呈现为一个免费 AI 模型网关；但材料不足以证明全部功能、稳定性或授权范围。真正值得借鉴的，不是复制某个地址，而是把“发现入口”改造成一条可重复的验证流程。

这条流程可以压缩成六个问题：入口的发布者是谁？协议是否有一手说明？凭据能否独立撤销？请求和额度能否对账？异常是否有明确边界？服务失效时能否无损切换？只要其中两个问题没有答案，就应把它视为临时实验入口，而不是基础设施。

免费降低的是第一次调用的门槛，不会自动降低身份泄露、额度漂移、隐私暴露和供应商退出的风险。一个成熟的 AI 网关最终要交付的不是“能返回文本”，而是可观测、可限流、可审计、可撤销、可替换的接入契约。
