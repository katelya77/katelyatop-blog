## 先别急着复制配置：真正的问题是“谁来拼路径”

在 AI 客户端接入第三方网关时，最容易被忽略的不是 API Key，而是 Base URL 的语义。用户看到的往往只有一个域名，但客户端内部还会根据协议拼接路径。例如，一个客户端可能在配置的地址后面追加 `/v1/chat/completions`，另一个客户端则会追加自己的消息接口路径。如果把已经带有 `/v1` 的地址再次交给会自动追加版本路径的客户端，最终请求就可能变成重复路径；反过来，缺少版本前缀也可能让服务端路由无法命中。

AXAI 的公开接入页面明确把 Codex 和 Claude Code 分成两种地址：Codex 使用 `https://axai.dpdns.org/v1`，Claude Code 使用 `https://axai.dpdns.org/`，后者不带 `/v1` 且以斜杠结尾。页面还说明，Codex 的 `wire_api` 需要根据后端能力选择，默认建议先使用 `chat`，而不是直接假设所有模型都支持 Responses 接口。这说明“API 地址”并不是一个脱离客户端的常量，而是客户端协议、路径规则和网关兼容层共同决定的配置。

这里可以建立一个简单模型：

`最终请求地址 = 客户端 Base URL + 客户端协议路径 + 版本或资源路径`

当用户填写 Base URL 时，至少要回答三个问题：

1. 客户端会不会自动追加 `/v1`？
2. 客户端使用的是 Chat Completions、Responses，还是另一套消息协议？
3. 网关是否只是转发路径，还是会把一种协议转换成另一种协议？

如果这三个问题没有答案，继续换模型名、反复生成密钥，通常都不会解决 404 或流式响应错误。问题可能还没有到认证层，甚至请求都没有进入正确的路由。

## 从公开页面可以确认的架构：入口、凭证和模型权限是三层

AXAI 的公开页面把接入流程拆成了几个相互独立的部分：兑换码换取 API Key、查询用量、获取可用模型、为客户端写入环境变量或配置文件。页面还特别说明，用量查询和模型列表读取不会发起对话请求，也不会消耗额度或次数。仅从这些公开信息，就可以推导出一个较清晰的网关分层，而不需要把社区帖子中的营销描述当成技术事实。

第一层是入口层。`https://axai.dpdns.org/v1` 的公开探测结果返回 `AXAI API Gateway is running` 和 `status: true`，这只能证明该入口在该次访问时有网关响应，不能证明所有模型、所有请求方法或所有账号都可用。入口存活、路由正确、上游模型可用，是三个不同的状态。

第二层是凭证层。页面描述的流程是先通过兑换码获得一把专属 API Key，再使用这把 Key 查询权益和调用记录。页面要求用户立即保存密钥，并提示密钥不会被保存于身份系统中，关闭页面后需要凭同一兑换码再次找回。这种设计意味着凭证找回机制本身就是高价值边界：兑换码不能放在截图、浏览器同步笔记或公开工单中，API Key 也不应直接写入 Git 仓库。

第三层是权限层。页面称“可用模型与连通性”会按当前密钥的实际权限返回模型列表，模型列表按需获取。因此，模型名不是一个可以随意猜测的字符串，而是凭证权限、网关配置和上游能力共同决定的结果。一个请求返回 404，不一定代表整个服务不可用，也可能是模型名不存在、模型未对当前 Key 开放，或者请求路径对应的协议不被该入口支持。

这三层带来一个重要的工程判断：不要把“域名能打开”“密钥能查询余额”“模型能完成对话”当作同一个健康指标。它们分别对应入口、凭证和端到端调用，应该分开记录和验证。

## Chat Completions 与 Responses：不要把协议名当成模型能力

AXAI 页面建议 Codex 配置中的 `wire_api` 先选择 `chat`，并说明只有部分模型支持 `responses`。这条说明的价值在于，它把“模型名称”和“线协议”区分开了。

模型支持某个厂商的能力，并不等于第三方网关已经把该能力完整映射到目标客户端。网关可能只实现了 Chat Completions 的字段转换，却没有覆盖 Responses 的事件流、工具调用、状态字段或错误格式。此时，模型本身即使能够生成文本，使用另一种协议仍可能在请求校验或流式解析阶段失败。

因此，配置时应该先选择最小、最常见、最容易观察的协议路径：

```toml
# ~/.codex/config.toml
model = "从可用模型列表中复制的名称"
wire_api = "chat"

[model_providers.axai]
name = "AXAI"
base_url = "https://axai.dpdns.org/v1"
env_key = "AXAI_API_KEY"
```

上面只表达配置关系，不代表页面之外的完整 Codex 配置格式。真正接入时，应以客户端当前版本的配置 schema 为准；关键点是 `wire_api`、Base URL 与环境变量名必须互相匹配。

环境变量可以这样设置：

```bash
export AXAI_API_KEY='替换为你自己的密钥'
```

随后再启动客户端，而不是在客户端已经运行后才修改环境变量。AXAI 页面明确提醒 Codex 只在启动时读取配置，因此修改配置文件或 shell 环境后需要重新打开终端或重启进程。

Claude Code 的配置边界不同。公开页面要求其地址使用不带 `/v1`、结尾带斜杠的形式，并使用 `ANTHROPIC_AUTH_TOKEN`，而不是 `ANTHROPIC_API_KEY`。这不是变量名偏好的问题，而是客户端读取哪个变量、向哪个协议入口发送请求的问题。把 Codex 的地址和变量名原样搬到 Claude Code，失败是预期结果。

```json
{
  "env": {
    "ANTHROPIC_AUTH_TOKEN": "替换为你自己的密钥",
    "ANTHROPIC_BASE_URL": "https://axai.dpdns.org/",
    "ANTHROPIC_MODEL": "从可用模型列表中复制的名称"
  }
}
```

页面还提到 `API_TIMEOUT_MS` 可用于调整超时，并给出了普通对话与长文档场景的示例值。超时值只能改变客户端愿意等待多久，不能修复错误的 Base URL、错误的模型名或上游不支持的协议。把超时时间无限调大，反而会让故障被隐藏在更长的等待中。

## 一套可复现的验证顺序：从便宜检查到端到端请求

验证第三方网关时，建议按照成本从低到高执行，而不是一上来就把服务接入编辑器或 Coding Agent。

### 第一步：验证入口是否响应

```bash
curl -i --max-time 10 https://axai.dpdns.org/v1
```

材料中给出的入口响应是 JSON，包含网关运行状态字段。这里主要看三件事：DNS 是否解析、TLS 是否成功、HTTP 是否返回。即使返回 200，也只能说明入口响应，不等于认证和模型调用已经通过。

### 第二步：验证模型发现能力

AXAI 页面提供了获取可用模型的入口，并强调模型列表按当前密钥的实际权限返回。若客户端兼容 OpenAI 风格模型列表，可以先尝试：

```bash
curl -sS --fail-with-body \
  -H "Authorization: Bearer $AXAI_API_KEY" \
  https://axai.dpdns.org/v1/models
```

如果这里失败，应先记录 HTTP 状态码和响应体，再判断是变量为空、密钥无效、路径不正确，还是服务端没有提供这个兼容端点。不要跳过模型发现，直接把社区帖子里的模型名写进配置。社区材料中关于模型、注册条件、价格和并发的描述属于社区信息，不能替代当前密钥权限返回的模型列表；MODELOC 页面也明确提醒，其报告只描述某次凭证在某一时刻的检测结果，不是安全认证。

### 第三步：验证最小文本请求

在客户端接入前，可以用一个最小请求确认协议与模型名是否匹配。请求体的具体字段必须以网关公开文档和目标协议为准，不应把某个客户端的扩展字段直接复制到另一个客户端。对于 Chat Completions 兼容入口，检查重点通常是：地址是否带正确版本前缀、Authorization 是否生效、模型名是否来自权限列表、响应是否能被完整解析。

### 第四步：验证流式响应和长请求

AXAI 页面把“流式响应报错”列为常见问题，并建议先将 `wire_api` 改为 `chat`。因此，普通非流式文本成功后，还要单独验证流式输出。需要观察首字节延迟、是否持续收到事件、结束标记是否完整，以及客户端是否把事件解析为一条最终消息。

长文档或代码任务还应单独验证超时边界。一次短文本成功，并不能证明长上下文、工具调用、长时间生成都可用。若只是把 `API_TIMEOUT_MS` 调大而没有记录服务端是否继续输出，可能得到一个“客户端一直等待”的假成功。

## 常见失败边界：哪些现象不能互相推断

**打开首页成功，不代表 API 可用。** 首页可能只是前端或状态页，API 还需要不同路径、请求头和认证方式。AXAI 的 `/v1` 入口返回运行状态，只能作为连通性起点。

**余额查询成功，不代表模型调用成功。** 页面将查询权益、调用记录和实际对话区分开，并说明查询不消耗额度。凭证层通过时，模型权限仍可能为空，或者客户端协议与网关转换能力不匹配。

**模型列表存在，不代表每种协议都支持。** 模型列表回答的是“当前 Key 可见哪些模型”，不是“这些模型能在 Codex、Claude Code 的所有模式下工作”。特别是 Chat Completions 与 Responses 的字段和流式事件不同，必须按客户端分别验证。

**一次检测结果不代表长期安全。** MODELOC 的页面明确声明报告不是安全认证，且检测只描述某次凭证在某个时刻的结果。即使报告显示某次测试评级，也不能推导出网关会长期稳定、不会记录请求、不会更换上游，或者所有账号都具有相同权限。

**社区贴中的价格与并发不是服务承诺。** NodeLoc 材料中出现了注册赠送额度、请求价格、低并发和号池调整等说法，但这些内容来自社区帖子，且帖子本身描述了仍在变更中的状态。它们可以作为选题雷达和待核验线索，不能作为客户端配置、费用结算或可用性保证。

## 使用第三方 AI 网关的最小信任边界

这类服务的最大风险不是“配置多写一个斜杠”，而是用户很容易把开发环境中的全部数据直接交给一个无法完全验证的中间层。即使协议转换正常，也应把数据和权限分层。

第一，使用专门的低权限密钥，不要把个人主账号、生产系统密钥或长期有效凭证交给测试网关。若服务支持按套餐或按模型授权，应先用最小权限验证，再决定是否扩大使用范围。

第二，把敏感项目与普通试验分开。不要把生产源码、客户数据、访问令牌、内部日志和私钥交给只用于验证兼容性的服务。测试提示词应使用脱敏样本，尤其不要因为“免费额度”而降低数据分类标准。

第三，保留可观测记录。至少记录使用的 Base URL、协议类型、模型名、Key 创建时间、错误状态码和撤销时间。这样出现异常扣费、响应内容异常或模型权限变化时，才能判断问题发生在客户端、网关还是上游。

第四，准备退出路径。AXAI 页面支持通过页面查询用量和查看调用记录；这类功能只能帮助观察当前状态，不能替代本地审计。项目应能快速切换回官方 API 或其他已审核提供商，配置文件中不要把网关地址散落在脚本、CI 变量和多个编辑器插件里。

## 原创结论：中转网关的“兼容”应当拆成四个可验证命题

判断一个 AI 网关是否值得进入工程环境，不应只问“能不能返回一句话”，而应把兼容性拆成四个命题：

1. **入口兼容**：DNS、TLS、HTTP 路径和版本前缀是否稳定，客户端是否能命中正确路由。
2. **认证兼容**：客户端使用的变量名、Authorization 形式和密钥生命周期是否匹配。
3. **协议兼容**：Chat、Responses、消息流和工具调用的字段与事件是否能被目标客户端正确解析。
4. **运营可验证**：模型权限、用量、错误记录和撤销路径是否可观察，服务变化时是否能安全退出。

四项中只满足第一项，叫“站点能访问”；满足前两项，叫“接口可能可用”；只有把协议行为和运营边界也验证清楚，才接近“可以承担某类工程任务”。这也是为什么一个看似简单的 `/v1` 差异，背后实际牵涉到客户端架构、网关转换、凭证权限和数据治理。

对于临时试用，最稳妥的做法不是追求更多模型和更大赠送额度，而是先建立一条最小验证链：无敏感数据、低权限密钥、明确协议、固定模型、可查询用量、可随时撤销。验证链跑通之后，再根据任务类型决定是否扩大范围；如果其中任何一层只能依赖社区口述、一次性检测或无法复现的状态，就应把它当作实验入口，而不是生产基础设施。
