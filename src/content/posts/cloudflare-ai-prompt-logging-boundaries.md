## 先看变化：记录目标由规则决定

Cloudflare 在 2026 年 11 月 24 日更新了 AI Security for Apps 的提示词日志说明。官方变更记录给出的新流程是：配置 payload logging，并创建引用 `cf.llm.prompt` 前缀字段的 WAF 自定义规则；规则匹配时，payload logging 保存提取出的提示词。如果没有提取到提示词，分析会回退到完整请求体，此时保存的也可能是完整请求体。这一流程取代了此前的 AI Security Log Mode Ruleset 配置步骤。[S6]

这不是简单地把一个字段加入日志。关键在于日志记录有条件：规则是否匹配，决定了是否进入记录路径；字段提取是否成功，又决定了保存的是提示词还是完整请求体。把它理解成一条“提示词专用日志”容易忽略回退分支，也容易让人误判实际采集范围。

本文只依据官方变更记录描述这些行为。材料没有提供规则表达式示例、具体字段列表、仪表板操作步骤或 API 请求格式，因此下面不会补写看似可复制、实际未经证实的配置语法。Cloudflare 的文档仓库是官方文档的代码来源之一，但仓库首页本身并不证明某个字段或配置细节；实施时应以对应产品文档和账户中可用能力为准。[S7]

## 把采集路径拆成三个判断点

可以把这项能力抽象为三个连续判断，而不是一条日志开关。

第一步是请求分析。AI Security for Apps 对请求进行分析，系统可能提取出提示词，也可能无法提取。变更记录明确描述了这两种结果，但没有给出提取失败的全部原因。工程上应把它当作一个可能出现的分支，而不是假定所有请求都能得到结构化提示词。

第二步是 WAF 规则匹配。新流程要求自定义规则引用 `cf.llm.prompt` 前缀字段。规则的匹配结果承担采集门控的作用：匹配后才进入 payload logging 的记录行为。因而规则范围不仅影响拦截或告警逻辑，也影响哪些请求内容会留下审计数据。规则写得过宽，可能扩大日志覆盖；写得过窄，则可能漏掉希望观察的请求。由于材料未给出字段的完整语义和表达式语法，这里不能进一步推定空值、类型转换或组合条件的具体处理方式。

第三步是 payload logging。匹配规则后，保存内容取决于提示词提取结果：提取成功时保存提取出的提示词；没有提取到提示词而分析回退到完整请求体时，保存内容也可能扩展为完整请求体。这个差异是设计中最重要的隐私边界：同一条规则并不意味着每条日志都具有相同粒度。

因此，完整的数据流可以概括为：请求分析产生提示词提取结果，WAF 自定义规则决定记录门控，payload logging 保存对应内容。任何只检查规则命中、却不检查最终记录载荷的验收，都没有覆盖整个链路。

## 配置前先做范围清单

缺少经核验的命令和规则语法时，最可靠的可复现做法不是编造配置片段，而是让配置意图、变更对象和验收结果可重复。可以在变更单或配置审查中逐项填写以下清单：

| 检查项 | 需要明确的内容 | 为什么重要 |
| --- | --- | --- |
| 目标应用 | 哪些应用或流量范围需要提示词日志 | 避免把观察范围默认扩大到所有请求 |
| 规则意图 | 哪类请求应匹配，规则引用了什么 `cf.llm.prompt` 前缀字段 | 让规则匹配范围可审查；具体字段语义需查当前产品文档 |
| 日志能力 | payload logging 是否按目标配置 | 规则命中本身不等于已保存载荷 |
| 数据预期 | 提取成功时保存提示词；未提取时关注完整请求体回退 | 防止把日志误当作只含提示词的安全数据 |
| 可访问范围 | 谁能查看记录、如何用于排障或审计 | 日志的风险取决于内容和访问者，不只取决于存储位置 |
| 保留与后续处理 | 依据适用策略核实保留期限、导出和删除流程 | 当前材料没有说明这些产品参数，不能从功能描述推断 |
| 旧配置处置 | 识别旧的 AI Security Log Mode Ruleset 流程是否仍在使用 | 新流程取代旧配置步骤，迁移时需要避免两套规则各自运行或形成盲区 |

这里有意把产品事实和运营要求分开。官方记录确认的是新流程、匹配后记录、提取失败时完整请求体回退，以及对旧流程的替代关系；访问控制、保留期限和脱敏策略则是部署方必须另行核实的治理事项，不能因为启用了 payload logging 就假定这些方面自动得到处理。

## 验证要覆盖成功路径和回退路径

验收不应止于规则保存成功。建议在受控环境中建立一组测试请求，并分别检查规则命中结果与最终日志内容。测试数据应使用合成提示词和无敏感信息的请求体，避免为了验证日志而制造新的真实数据暴露。

| 场景 | 验证重点 | 通过标准 |
| --- | --- | --- |
| 可提取提示词且规则匹配 | 规则命中后是否有对应记录，记录内容是否为提取出的提示词 | 与变更记录描述的成功路径一致 |
| 未提取提示词且分析回退 | 最终记录是否可能包含完整请求体 | 团队明确识别并接受或限制这一内容范围 |
| 规则不匹配 | 是否没有由该规则触发的记录 | 证明采集门控符合预期，而不是仅凭启用状态判断 |
| 不同应用或策略范围 | 目标内外请求是否分别落入预期范围 | 避免配置意外覆盖其他流量 |
| 更新前后对照 | 新流程是否覆盖原先依赖旧 Ruleset 的使用场景 | 在移除旧配置前确认所需观察能力没有中断 |

对每个用例，保留规则版本、测试场景、观察到的匹配结果和日志内容摘要，才能在后续调整后重复比较。若测试结果与预期不同，不要立即推断是产品缺陷：先确认规则是否匹配、payload logging 是否配置，以及请求是否走到了提示词提取或完整请求体回退分支。具体诊断字段和界面入口应查当时的官方产品文档；现有材料不足以指定某个按钮、API 或响应码。

## 失败边界与隐私取舍

最容易被忽略的失败边界是“未提取”不等于“没有日志”。官方描述恰好指出了相反的情况：分析回退到完整请求体时，日志保存的内容可能比预期更广。请求体可能带有上下文、用户输入或其他业务数据，因此把这项能力用于故障排查或安全分析之前，需要按完整请求体的最坏合理范围做数据评估，而非只按提示词字段做评估。

第二个边界是规则门控的含义。规则匹配是记录流程的一部分，不等于对内容进行脱敏，也不等于确认记录符合组织的隐私要求。即使规则只针对某类 AI 请求，也应检查该类请求实际包含什么数据，以及日志的查看、导出和保留安排是否与用途一致。材料没有说明 Cloudflare 在该流程中自动执行了哪些脱敏或保留控制，因此不能把这类控制当作既有保证。

第三个边界是迁移。新流程替代了旧的 AI Security Log Mode Ruleset 配置步骤，意味着维护文档和变更流程需要同步更新。不能仅凭“新旧名称不同”就删掉旧配置，也不能长期并行运行而不确认它们是否重复采集。应先列出旧流程承担的用途，再用新流程逐项验证覆盖；若某项用途无法从现有资料确认，就应先查官方文档或通过受控测试补足证据。

这里存在明确的工程取舍：更窄的规则范围通常有助于缩小采集面，但可能降低观察覆盖；更宽的范围可能增加排障可见性，同时也扩大敏感内容进入日志的机会。合理目标不是追求“日志越多越好”，而是在每项记录都有明确用途、匹配条件可审查、回退内容已知的前提下，保留足以回答安全问题的数据。

## 可操作的变更门禁

将这一能力纳入常规变更时，可以用四道门禁收束风险。第一，文档门禁：确认目标产品文档与当前账户能力，尤其核实规则字段和 payload logging 的配置方式。第二，范围门禁：由规则审查人确认覆盖对象和采集目的，不把未说明的流量范围当成默认值。第三，内容门禁：在合成数据用例中分别验证提取成功与回退场景，检查日志究竟保存了什么。第四，治理门禁：确认日志访问者、保留、导出和删除等政策，并记录这些设置的责任归属。

上线后的检查也应关注规则变化和日志内容变化，而不仅仅关注规则是否仍处于启用状态。字段或匹配逻辑调整可能改变进入记录路径的请求集合；提取行为变化也可能改变实际保存内容。定期抽查时使用经过批准的样本和最小必要访问，并把发现的问题反馈到规则范围、测试用例和数据治理策略中。

## 结论：审计对象是内容路径，不是开关状态

这次更新值得关注的不是配置入口换了名字，而是它把记录行为明确组织为“字段规则匹配 + payload logging”，并保留了提示词提取失败后可能记录完整请求体的回退路径。工程验收应同时证明三件事：哪些请求会进入记录路径、匹配后实际保存什么、提取失败时数据范围如何变化。

当一项 AI 安全日志能力同时服务于检测与排障时，最可靠的默认做法是先把规则范围收窄，再用合成请求验证两条内容路径，最后确认访问与保留策略。日志可见性是安全能力的一部分，但可见性本身也会创造新的数据责任。把这两个方向放进同一份验收证据里，才算真正理解了提示词日志的边界。
