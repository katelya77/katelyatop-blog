AI 编程工具的升级，表面上通常只是执行一次安装命令，真正改变的却可能是身份映射、组织策略、配置加载路径、文件编辑方式以及 SDK 与 CLI 的绑定关系。仅看版本号或“新增功能”列表，很难判断升级是否安全。

近期的官方发布材料提供了两个很有代表性的样本。Claude Code v2.1.312 的发布说明同时涉及 OIDC 用户标识、组织策略获取、超大规则文件编辑、目录级技能发现和终端会话恢复；Qwen Code 的 TypeScript SDK v0.1.25 则明确记录了其绑定的 CLI 版本。它们说明一个事实：AI 编程代理已经不是单一的命令行二进制，而是由身份、策略、运行时、插件和 SDK 共同组成的系统。

下文不把这些发布说明当成新闻摘要，而是把它们转化为升级前后的验证框架。Claude Code 的事实来自官方 v2.1.312 Release，Qwen Code 的事实来自官方 SDK TypeScript v0.1.25 Release；后者只说明发布页列出的绑定关系，不足以推导所有 SDK 行为。

## 先把“升级”拆成五条变化链

第一条是身份链。Claude Code v2.1.312 增加了 `oidc.user_id_claim`，允许 Claude 应用网关使用 id_token 中 `sub` 之外的声明来识别用户，发布说明举例提到 Microsoft Entra ID 的 `oid`。这不是普通的登录体验优化，而是身份主键选择发生了变化。`sub`、`oid` 或其他 claim 的稳定性、租户范围和唯一性可能不同，配置错误时，用户可能被错误合并，也可能被识别成新用户。

第二条是策略链。同一版本修复了从 VS Code 扩展登录后，托管设置与组织策略在剩余会话中不再获取的问题。这个描述说明策略不是只在进程启动时存在的静态文件，而可能受到登录入口和会话生命周期影响。对于企业工作流，最危险的不是明显报错，而是界面看起来正常、实际策略没有生效。

第三条是上下文链。发布说明提到，Claude 在只看到超大 `CLAUDE.md`、规则文件或被 `@` 引用文件开头内容后，曾覆盖文件；现在写入操作会要求完整读取或原地编辑。这暴露了上下文截断与写入动作之间的耦合：模型看到的是局部内容，但工具执行的是完整文件修改。

第四条是发现链。发布说明还修复了在 Git 仓库中执行更深层 `Bash cd` 后，目录级和路径级 skills 无法发现的问题。技能发现依赖当前工作目录、仓库边界和路径匹配，因而不能只在仓库根目录验证一次。

第五条是供应链链。Qwen Code SDK TypeScript v0.1.25 的发布页列出了 bundled CLI version，并显示该 SDK 发布与 CLI 版本存在绑定关系。对 SDK 用户而言，升级 SDK 不等于只升级类型定义；实际执行的 CLI 版本也属于运行时组成部分。若锁定策略只记录 npm 包版本，就可能遗漏真正发生变化的 CLI。

## 身份 claim 变化必须先验证“唯一性”

OIDC 配置最先要验证的不是登录是否成功，而是身份映射是否符合预期。可以先保存令牌的非敏感元数据，避免把完整令牌写入日志：

```bash
jq -r 'keys | sort[]' id-token.json
jq -r '.sub, .oid, .iss, .aud, .tid' id-token.json
```

这组命令只适用于已经经过授权、且存放在受控环境中的测试令牌。生产环境不要把完整 id_token 提交到仓库，也不要在 CI 输出原文。检查重点包括：

1. 目标 claim 是否存在，是否为空。
2. 同一用户在不同登录入口、不同租户或不同客户端下是否保持预期稳定。
3. `iss`、`aud` 和用户 claim 是否被作为同一信任域的一部分校验，而不是只读取一个字符串。
4. 迁移旧 claim 时，历史账号是否需要映射，而不是直接生成第二个身份。

可以用一组脱敏后的样本做回归测试：

```bash
jq '{iss, aud, tid, sub_present: (.sub != null), oid_present: (.oid != null)}' id-token.json
```

验证通过的标准应当是“同一身份在预期边界内稳定、不同租户不会意外合并”，而不是“页面显示登录成功”。如果组织策略依赖用户标识，claim 迁移还应与权限回归一起执行：读取策略、执行受限操作、确认拒绝路径，最后检查审计记录中的主体是否仍然可追踪。

## 配置与策略要做会话级验证

托管设置和组织策略的问题，不能只检查磁盘上的配置文件。应当把登录入口和会话状态纳入测试矩阵。至少准备三种场景：从终端直接登录、从编辑器扩展登录、恢复已有会话。每种场景都检查以下项目：

```text
启动前配置：组织策略文件、托管设置、项目规则
登录入口：terminal / editor extension
会话动作：新建、切换目录、恢复
验证结果：策略是否加载、限制是否生效、日志主体是否正确
```

如果工具提供诊断输出，可将配置加载结果导出为经过脱敏的快照；如果没有，则用行为测试代替。比如，为测试账号设置一个明确可观察的限制，让代理尝试执行受限动作，再检查是否被拒绝。不要把“配置文件存在”当作“配置已生效”，也不要把“旧会话还能继续对话”当作“新策略已刷新”。

失败边界也要写进清单：网络中断时策略是否保持上一次状态、重新登录后旧策略是否残留、从 VS Code 扩展进入后是否使用了不同的缓存目录。材料只证明官方修复了特定的策略获取问题，并不能推导所有客户端、所有身份提供商都已覆盖，因此验证范围必须明确记录。

## 大文件编辑要验证完整性，而不是只看模型回复

超大规则文件的风险在于，模型上下文看到的内容可能不完整，但写入工具面对的是完整文件。升级后应准备一个包含文件头、中部和尾部哨兵文本的测试文件：

```bash
printf 'HEADER\n' > CLAUDE.md
for i in $(seq 1 20000); do printf 'RULE-%05d\n' "$i"; done >> CLAUDE.md
printf 'FOOTER\n' >> CLAUDE.md
sha256sum CLAUDE.md
```

随后要求代理只修改一个明确的小段，验证四件事：文件头仍在、文件尾仍在、中间未授权内容未被重写、目标修改确实存在。可以用命令检查边界：

```bash
grep -n -E '^(HEADER|RULE-10000|FOOTER)$' CLAUDE.md
sha256sum CLAUDE.md
```

哈希值在合法修改后当然会变化，因此它不能单独证明安全；更可靠的做法是保存修改前副本，对差异进行审阅：

```bash
cp CLAUDE.md CLAUDE.md.before
git diff --no-index -- CLAUDE.md.before CLAUDE.md || true
```

验证标准应是差异范围符合请求，而不是文件能够被打开。对于规则文件、权限文件和部署配置，原地小范围编辑通常比让模型重写整个文件更可控。即使发布说明已经修复了特定覆盖问题，也不应取消人工审阅和版本控制，因为工具修复不能替代变更授权。

## 技能发现要从仓库根目录和深层目录分别测试

目录级 skills 的问题具有路径相关性。一个只在仓库根目录通过的测试没有代表性，至少要覆盖：仓库根目录、一级子目录、深层子目录、通过 Bash `cd` 进入的目录，以及从编辑器启动的工作目录。

可以先记录测试矩阵：

```bash
pwd
find .. -maxdepth 4 -type f \( -name 'SKILL.md' -o -path '*/skills/*' \) -print
 git rev-parse --show-toplevel
```

然后在每个目标目录执行同一个、无副作用的技能发现任务，记录当前目录、发现到的技能名称和实际调用结果。重点不是技能数量，而是路径规则是否一致：深层目录是否仍能继承仓库级技能，路径级技能是否只在允许的范围内出现，离开仓库后是否错误泄漏。

这类测试还要注意工作目录的来源。终端直接启动、编辑器集成启动和代理内部执行 `cd`，可能经过不同的初始化流程。官方材料只确认了一个特定发现问题的修复，不能把它扩展成“所有技能加载问题都已解决”。因此应把版本、启动入口、初始目录和最终目录一并记录，形成可复现的故障样本。

## SDK 与 CLI 必须作为一个版本单元管理

Qwen Code SDK v0.1.25 的官方发布页明确给出了 bundled CLI version，这类信息应进入依赖清单，而不是只停留在发布页面。升级时建议同时记录：SDK 包版本、绑定的 CLI 版本、Node.js 运行时、配置文件哈希和启动参数。

```bash
npm ls --depth=0
node --version
npm view @qwen-code/sdk version
```

最后一条命令只能查看注册表中的当前信息，不能替代锁文件或官方 Release 的核对。实际项目应以锁文件、发布标签和 CI 安装结果为准。若 SDK 通过内部封装启动 CLI，还要在测试中确认：参数是否完整传递、退出码是否保留、标准错误是否可观测、CLI 版本是否与预期一致。

更稳妥的升级流程是先固定旧版本基线，再升级 SDK；分别运行单元测试、最小真实调用和失败场景；最后把 SDK 与 CLI 的版本组合写入构建产物元数据。这样出现问题时，团队能回答“是哪一个运行时单元变化了”，而不是只知道“昨天升级过依赖”。

## 一套可落地的发布验收清单

上线前可以把验证压缩成以下顺序：

1. **证据确认**：区分正式 Release、预发布版本和社区发现。本文使用的 Claude Code 与 Qwen Code 材料均为官方 GitHub Release；若测试其他材料中的预发布版本，应单独标注其证据等级。
2. **身份回归**：验证 claim 存在性、租户边界、历史账号映射和审计主体。
3. **策略回归**：覆盖终端登录、编辑器扩展登录、新建会话和恢复会话。
4. **文件安全**：使用带头尾哨兵的大文件，审阅最小差异，确认没有隐式重写。
5. **路径发现**：从根目录、深层目录和 Bash `cd` 后分别验证 skills。
6. **运行时锁定**：同时记录 SDK、CLI、运行时和锁文件，不把包版本当成完整版本信息。
7. **失败演练**：至少测试令牌缺少目标 claim、策略无法刷新、文件写入被拒绝、技能不存在和 CLI 返回非零退出码。

## 结论：发布说明是测试设计的输入，不是升级批准书

AI 编程代理的版本变化越来越像一次小型平台迁移。身份声明影响账号治理，策略加载影响组织控制，文件编辑影响变更安全，技能发现影响工具权限，SDK 与 CLI 绑定影响运行时可重复性。它们都可能在“命令成功退出”的情况下悄悄改变。

更可靠的判断方式，是把 Release notes 中每一条行为变化翻译成一个可观察断言：哪个主体被识别、哪个策略实际生效、哪些字节发生变化、哪个目录能发现能力、哪个 CLI 真正被调用。只有这些断言在新旧版本之间完成对照，升级才具备工程意义。版本号负责定位变化，验证链才负责决定变化是否值得接受。
