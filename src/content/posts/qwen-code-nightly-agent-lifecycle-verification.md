## 先把证据等级说清楚：这是 nightly，不是稳定承诺

Qwen Code 的 `v0.26.9-nightly.20261106.80fd7c3353` 发布页明确标注为 Pre-release，发布时间为 2026 年 11 月 7 日，发布提交为 `b4ff899`。因此，这批变化可以作为项目当前实现方向和测试重点的公开证据，却不能直接写成“已经稳定支持”或“所有用户都能获得”。这一区分很重要：nightly 的价值不只是提前获得功能，也包括让工程团队提前识别状态机、并发和兼容性风险。

这次发布说明没有提供一套完整的产品规格，而是列出了多个看似分散的变更：前台 Shell 改为轮询 frame，托管 Agent 的生命周期集成测试调整并重试快照锁竞争，dispatcher 处理标题竞争，Hook 增加 `FileChanged` 通知，Web Shell 展示可读的 Skill 完成细节，Flaky Patrol 的 rerun 和 no-action 决策变得可见，托管 Agent 的基础工具与 daemon 对齐，以及覆盖 `workspace_runtime_stop` 启动时组合条件的测试。

把它们放在一起看，主题并不是“又加了几个工具”，而是 Agent 工作台正在处理同一个核心问题：一个动作经过多个运行时、事件通道和后台组件之后，如何仍然保持可解释、可恢复、可验证。

## 从快照到 frame：前台 Shell 的状态不能靠一次读取

“轮询 foreground-shell frame，而不是对它做快照”，至少说明前台 Shell 的输出或生命周期状态可能在观察期间继续变化。快照适合读取静态对象：调用一次，得到一个结果；frame 更接近连续状态：命令仍在运行、输出仍在追加，或者运行时正处于切换过程。

这会改变客户端的验证方式。一次读取成功，只能证明某个时刻拿到了状态，不能证明命令已经结束，也不能证明最后一段输出已经到达。轮询则需要明确三个问题：什么字段代表当前 frame，什么条件表示完成，以及状态长时间不变化时如何区分“命令空闲”和“观察失效”。发布说明只确认了测试策略发生变化，没有给出完整协议，因此不能臆测具体字段或时间间隔。

在没有依赖内部 API 的情况下，可以先用版本和提交做静态复核：

```bash
git clone https://github.com/QwenLM/qwen-code.git
cd qwen-code
git fetch --tags origin

git show --stat --oneline b4ff899
git show --format=fuller --no-ext-diff b4ff899 --
```

如果要把这类变更纳入自己的验收，应记录一条最小状态链，而不是只截取最终输出：启动时间、首次可见 frame、连续 frame 数量、完成信号、退出码、最终文本和超时原因。测试结果至少要能回答“没有输出”“输出延迟”“输出分段到达”“进程已退出但 frame 未更新”这几类边界，而不是只检查一条字符串是否出现。

## 托管 Agent 的真正难点是所有权，而不是工具数量

发布说明同时出现了三类托管 Agent 相关修复：生命周期集成测试被重新定位，快照声明竞争需要重试，dispatcher 需要处理“标题先被另一个组件声明”的情况，基础工具还要与 daemon 对齐。这些词汇共同指向一个问题：多个组件可能同时认为自己拥有同一个 Agent 或同一个生命周期对象。

“dispatcher claimed first”并不等于简单的排序问题。它至少意味着标题、任务或运行时对象存在竞争性声明；如果后来者覆盖先到者，用户界面可能显示错误的任务名称；如果后来者直接失败，又可能留下已创建但无法管理的对象。工程上应把所有权分配设计成显式状态转移，例如 `unclaimed -> claimed -> running -> completed`，并为重复声明定义幂等结果。这里的状态名只是通用建模，不是对 Qwen Code 内部协议的断言。

“重试快照锁竞争”也不应被理解为“测试偶尔失败，所以多跑几次”。重试只能降低偶发竞争对测试结果的干扰，不能证明锁设计正确。更有价值的检查是区分：

- 竞争发生在快照读取、声明还是生命周期结束阶段；
- 重试后得到的是同一个对象，还是被另一个对象替换；
- 失败是否留下后台进程、未释放锁或半完成状态；
- 并发测试中是否仍能保持标题、任务结果和退出状态的一致性。

因此，托管 Agent 的验收应同时看三份记录：控制器日志、运行时状态和用户可见事件。只看最后一条成功消息，无法发现“后台已结束但界面仍显示运行中”这类问题。

## FileChanged 与 Skill 结果：事件可见性要能追溯

这次 nightly 为本地会话增加了 `FileChanged` 通知，并让 Web Shell 展示更易读的 Skill 完成细节。两项改动都属于可观测性，而非模型能力本身。它们解决的是“系统做了什么，用户能否知道”的问题。

文件变化通知的价值在于把隐式副作用变成显式事件。一个 Agent 可能通过工具修改文件，随后触发构建、刷新索引或更新界面。如果只有最终回答，用户无法判断修改发生在哪个阶段，也无法区分 Agent 主动写入和外部进程造成的变化。合理的事件至少应包含路径、时间、来源会话和关联任务；但当前材料没有确认 Qwen Code 的具体字段，不能把这些字段写成既定 API。

Skill 完成细节则对应另一个边界：任务成功不一定等于用户理解了结果。可读信息应帮助用户判断调用了什么、是否产生副作用、是否部分完成以及失败发生在哪一步。这里仍然要避免把“readable details”扩展成未经证实的完整审计日志能力。发布说明只支持一个较窄的结论：界面呈现被改善，验证时应关注信息是否足以解释完成状态。

可以用下面的检查清单验收事件通道：

1. 同一文件连续修改时，事件是否按发生顺序可识别；
2. 修改后立即结束会话时，最后一个事件是否丢失；
3. Skill 部分成功时，界面是否把成功、跳过和失败混成一个结果；
4. 事件重复到达时，消费者是否会重复执行刷新或索引；
5. 事件与具体会话、任务或运行时之间是否存在可追踪关联。

这些检查不要求猜测内部实现，却能覆盖 Agent 产品最容易被忽视的“做完之后发生什么”。

## Flaky Patrol 的可见性：自动化决策也必须可审计

发布说明提到，Flaky Patrol 的 rerun 和 no-action 决策变得可见。这是一个容易被低估的变化。自动重跑和自动不处理都会改变 CI 的事实面：前者可能把暂时性失败隐藏在第二次成功后，后者可能让失败继续积累。如果决策不可见，团队看到的只有一个最终绿灯或红灯，却不知道系统中间做过什么。

验证这类能力时，不能只检查“页面上是否出现文字”。应构造至少三种结果：第一次失败、重跑后成功；连续失败且决定不再处理；判断条件不足而保持未决。每种结果都应能关联到原始运行、决策时间和采取的动作。若只记录最终状态，之后无法回答“这次绿色是首次成功还是自动重跑成功”。

这也说明了为什么 nightly 变更不应按功能列表逐项打勾。Shell frame、文件事件、Skill 结果和 Flaky Patrol 看似属于不同模块，实际都在增强同一条证据链：状态产生、状态传播、状态呈现、状态决策。任何一环缺少关联标识，用户看到的就只是零散提示，而不是可复查的过程。

## 发布升级的最小验证流程

对于带有 `nightly` 和 `Pre-release` 标记的版本，建议把升级分成四层，避免“能启动”被误认为“可采用”。

第一层是来源核对。固定仓库、标签、提交和发布时间，保存发布页中的变更原文；不要只保存一个版本字符串。第二层是静态变更核对，检查提交统计、测试文件和运行时模块是否确实涉及发布说明中的关键词，例如 `foreground-shell`、`FileChanged`、`managed-agent` 和 `workspace_runtime_stop`。关键词命中只能帮助定位，不代表功能已经验证。

第三层是行为测试。对前台 Shell 使用分段输出和延迟退出，对托管 Agent 使用重复声明和并发结束，对文件通知使用快速连续修改，对 Flaky Patrol 分别模拟重跑成功和持续失败。测试中同时保留原始日志、事件顺序和最终界面结果。

第四层是回退判断。只要出现状态无法收敛、事件无法关联、自动决策不可解释，或者 daemon 与托管 Agent 的工具行为不一致，就不应因为单个功能可用而直接扩大 nightly 的使用范围。nightly 的证据可以支持“值得进入隔离验证”，不能单独支持“适合生产升级”。

## 结论：Agent 可靠性首先是状态证据问题

Qwen Code 这次 nightly 的信息密度，正来自它没有只展示一个醒目的新功能，而是同时触及观察、声明、通知、工具对齐和自动决策。它提醒我们：Agent 系统的可靠性不是把更多工具接进来，而是让每个动作拥有明确的状态归属、可重复的转移规则和可追溯的用户证据。

对使用者而言，最稳妥的结论是把该版本视为预发布验证样本。可以研究它如何处理 frame、生命周期竞争和事件可见性，也可以据此设计自己的验收矩阵；但在没有更完整官方文档和稳定版本承诺前，不应把发布说明中的测试修复直接等同于生产级保证。真正值得迁移的不是某一个 nightly 标签，而是这套判断方法：先确认状态从哪里来，再确认谁拥有它，最后确认失败和自动决策是否能被复查。
