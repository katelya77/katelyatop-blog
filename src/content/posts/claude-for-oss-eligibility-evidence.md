## 先把它定义清楚：这是定向计划，不是公开兑换码

NodeLoc 上出现的帖子把 Claude Code 六个月 Max 会员描述成一种可以直接领取的福利，并建议发布开源项目后提交申请。这类信息可以作为选题雷达和真实问题样本，但不能直接当作资格规则。官方页面把项目命名为 Claude for Open Source，明确说明它面向开源生态贡献者，提供 6 个月的 Claude Max 20x；页面同时要求申请人说明自己维护的项目或贡献情况，并保留审核判断空间。

这一区分非常重要。公开活动通常强调兑换入口、截止时间和名额；而该项目的核心信息是申请资格与项目影响力。换句话说，问题不是有没有一个链接，而是申请材料能否证明你属于目标人群。一个刚创建、没有外部使用者的个人仓库，和一个被大量项目依赖、持续接受外部贡献的库，在申请逻辑上不是同一类证据。

官方页面列出的典型人群包括：维护被其他项目依赖的软件包；在公认基金会或语言项目中担任列名提交者或维护者；过去 12 个月向非自己所有的仓库合并了至少 100 个 Pull Request；拥有一个过去 12 个月有至少 20 名不同外部贡献者提交并合并 Pull Request 的仓库；以及维护 OpenSSF criticality score 达到 0.4 或更高的项目。官方还写明，如果维护的项目属于生态系统中被默默依赖的关键组件、但不完全符合列出的门槛，也可以申请并解释情况。

因此，正确的工程化理解是：这是一个需要提交事实材料的项目型申请，而不是注册账号后自动获得的兑换权益。

## 五类资格，分别对应五种证据结构

### 1. 维护者资格：证明别人真的依赖你的发布物

如果走维护者或库作者路线，单独展示 GitHub 星标并不够。官方页面给出的量化门槛是：至少有 500 个依赖仓库、100 个依赖软件包，或在任意注册表中达到每月 200,000 次合计下载。这里的关键词是依赖和下载，而不是项目作者自报的用户数量。

准备材料时，应把证据拆成三层：项目主页说明维护关系；包管理平台或注册表页面显示包名、版本和下载统计；依赖图或平台统计显示外部使用情况。不同生态的统计口径可能不同，申请材料中要明确平台名称、统计周期和指标含义，避免把一次性下载总量误写成月度下载量。

### 2. 核心贡献者：证明身份和项目归属

如果你是 CPython、Rust、Node.js TSC、Apache PMC、CNCF、Kubernetes、Linux kernel、Django、Rails 等项目的列名提交者或维护者，重点不是罗列提交次数，而是证明你的身份能在项目的正式贡献者名录、维护者文件、委员会页面或仓库权限中被核验。

这条路线的优势是证据结构相对清楚，风险是容易把普通贡献者误写成维护者。拥有一个已合并的 Pull Request，不能自动推出你属于项目维护团队。申请文本应使用项目本身对角色的称呼，不要自行拔高头衔。

### 3. 活跃贡献者：把 100 个合并 PR 变成可审计记录

官方条件是过去 12 个月内，向自己不拥有的仓库贡献并合并至少 100 个 Pull Request。它同时包含时间范围、目标仓库归属、合并状态三个约束。仅仅打开 100 个 PR、向个人仓库提交 100 次，或者把旧 PR 在统计期外合并，都不能等价替代。

可以用 GitHub CLI 先构造自己的工作清单：

```bash
gh pr list --author @me --state merged --limit 100 --json repository,number,title,mergedAt,url
```

这条命令适合初筛，但它不自动替你判断仓库是否由你拥有，也不保证所有组织权限和历史记录都以同一口径返回。拿到结果后，应导出仓库名、PR 编号、合并时间和链接，再按月份去重核对。申请材料不必堆上百条链接，但要保留完整清单，至少准备若干代表性 PR 供审核者抽查。

### 4. 社区建设者：证明外部贡献者不是自己邀请的重复账号

官方门槛是过去 12 个月内，你的某个仓库有至少 20 名不同外部贡献者提交并合并 Pull Request。这里有三个容易被忽略的边界：贡献者必须是不同的人；PR 必须合并；时间范围是最近 12 个月。

仓库的贡献者图、合并记录和 PR 作者列表可以组成证据包。不要只截取 Contributors 页面，因为它可能混合提交、Issue 活跃度和历史贡献，未必直接对应已合并 PR。更稳妥的做法是建立一张表：作者账号、PR 链接、合并时间、是否属于仓库维护团队，并保留原始页面链接。

### 5. 关键基础设施：使用 OpenSSF criticality score 作为外部指标

官方还接受项目 OpenSSF criticality score 达到 0.4 或更高这一条件。它的价值在于引入了外部评估指标，申请人不需要只靠主观描述项目的重要性。但分数对应的是具体项目和具体时间点，不能把组织整体、个人影响力或某个相邻仓库的分数混用。

申请时应记录项目地址、分数页面、抓取日期和仓库是否完全匹配。若分数发生变化，至少要能解释提交时使用的时间点。对于没有达到 0.4 的项目，也不要用星标、下载量或公司背书替换这条官方指标；应改走其他资格路线，或者使用官方允许的开放式说明渠道。

## 一套可复现的申请前检查清单

申请前可以把材料整理成一个不依赖记忆的证据目录：

```text
claude-oss-evidence/
├── profile.md          # 个人身份、角色和联系方式
├── project.md          # 项目地址、发布物和维护关系
├── dependencies.csv    # 依赖仓库、依赖包或下载统计
├── merged-prs.csv      # 过去12个月的合并PR清单
├── external-contributors.csv
└── criticality.txt     # 项目地址、分数和核验日期
```

`merged-prs.csv` 至少应包含 `repository,number,merged_at,author,url` 五列。检查时逐行确认：仓库是否不是自己拥有；PR 状态是否确实为 merged；合并时间是否在过去 12 个月；作者是否与申请人身份一致。对依赖和下载数据，则要标记数据来源、统计周期和单位。

如果你使用脚本整理记录，脚本的作用应限于去重、筛选时间和生成索引，不应把模糊的数据自动转换成符合资格的结论。例如，下载量抓取失败时应显示缺失，而不是写成 0；仓库归属无法判断时应进入人工复核，而不是默认属于外部仓库。申请材料最忌讳的不是数字少，而是数字口径不明。

提交前还应做三轮核对：第一轮核对身份，确保 GitHub 用户名、项目维护者账号和申请表中的姓名一致；第二轮核对时间，所有数量都对应官方要求的过去 12 个月；第三轮核对来源，每一个关键数字都能由公开页面、注册表统计或项目正式文件回溯。

## 到期和付费边界：六个月之后才是容易误解的地方

官方页面明确说明，免费期结束后，赠送订阅会终止。Anthropic 会在结束前发送邮件提醒；如果此前使用的是付费计划，订阅会恢复到之前的计划和费率，除非用户取消；如果此前没有付费计划，账号会回到免费计划。

这意味着申请成功不等于获得永久权益，也不等于可以把账号转让给别人。团队在使用时应把它当作个人账户上的限时授权，提前记录结束日期和通知邮箱。若组织把 Claude Code 接入自动化流程，更不能把这项资格当成稳定的生产依赖，因为官方页面只说明了订阅周期和计划恢复方式，并没有在该页面承诺固定的 API 配额、团队共享、服务等级或永久价格。

工程上最稳妥的做法是把六个月当作试用窗口：用它验证代码审查、Issue 分析、文档生成和本地 Agent 工作流是否真的节省时间；同时保留模型替换、人工审批和成本上限。不要在免费期内把关键发布流程改造成只能依赖某个个人账号的单点系统。

## 失败边界：社区帖能提示方向，但不能替你完成核验

这批信息中，社区帖子提供了一个真实需求：开源作者希望降低 Claude Code 的使用成本，并寻找官方申请入口。但社区帖属于二手传播，可能省略资格条件、审核结果和计划到期规则。即使帖子中的申请人已经提交，也不能据此推断所有申请都会通过；即使有人获得资格，也不能推断普通新仓库自动满足条件。

官方页面还有一个值得注意的弹性边界：它表示不完全符合列举条件、但维护着生态系统默默依赖的项目，也可以申请并说明情况。这不是放宽为人人可得，而是允许申请人提交上下文。最好的做法不是包装数字，而是描述项目被哪些系统使用、你承担什么维护责任、如果项目停止维护会产生什么影响，并附上可验证链接。

我的结论是：这类开发者福利的核心竞争力不是发现更快，而是证据组织得更可靠。把活动看成一次可审计的项目申请，你就会自然地区分资格、证明、审核和到期四个阶段；把它看成一个免费兑换码，则很容易在资格不符、数据口径错误或自动续费边界上做出错误承诺。对开源维护者而言，最值得长期建设的不是某一次六个月权益，而是能持续证明项目影响力、维护责任和外部贡献的公开记录。
