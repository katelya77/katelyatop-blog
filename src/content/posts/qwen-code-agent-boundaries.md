## 先看变化：Agent 能力正在从“本地工具”变成“受控会话”

很多 AI CLI 的介绍仍然停留在“能不能读文件、能不能执行命令、能不能调用模型”。但当 Agent 具备托管会话、网页终端、消息推送和持久记忆后，真正需要回答的问题已经变成：它在哪个工作区运行？谁授予了访问权？危险操作如何被确认？执行结果是否会离开原来的控制面？记忆导入能否撤销和重试？

Qwen Code v0.27.4 的官方 Release Notes 给出了一个很有代表性的答案。该版本把 Managed Agent sessions、Managed Web Terminal、Auto Mode 的风险授权、Web Shell Goals、飞书与企业微信输出，以及 Codex memory imports 放在同一份发布说明中。这些变化表面上属于不同功能，底层却共同指向一个主题：Agent 不再只是一次性的命令行进程，而是一个拥有身份、工作区、外部通道和持久状态的执行主体。

这里的证据等级是“官方仓库 Release”。它足以证明发布说明中列出的能力属于该版本的发布内容，但不能据此推导所有部署形态、默认配置、服务端 SLA 或具体权限策略。工程验收也应当遵循同样的边界：先验证发布说明明确承诺的行为，再把环境差异单独记录。

## 工作区访问不是路径参数，而是授权关系

Release Notes 提到，Managed Agent sessions 可以访问被授予的本地目录，并打开交互式 Managed Web Terminal，同时不持久化凭据或路径。这里至少包含三层设计意图。

第一层是资源范围。Agent 不是天然拥有整台机器的文件系统权限，而是只能访问被授予的目录。目录授权因此成为会话创建时的输入，而不是 Agent 运行过程中自行发现的结果。第二层是会话入口。Web Terminal 让用户可以进入一个交互式环境，但终端入口并不等于获得额外目录权限；入口和资源授权必须保持分离。第三层是敏感信息生命周期。发布说明明确强调凭据或路径不被持久化，这意味着“本次会话能访问”与“系统长期保存访问材料”是两个不同问题。

可以把一次会话抽象为：

```text
Session = Identity + GrantedWorkspaces + RuntimeChannel + ApprovalPolicy
```

其中 `GrantedWorkspaces` 决定文件边界，`RuntimeChannel` 决定用户如何观察和交互，`ApprovalPolicy` 决定高风险操作是否需要额外授权。若把这三者压缩成一个“Full Access”开关，系统会变得容易使用，却很难审计。

升级后首先应检查的是边界，而不是功能演示。一个最小检查清单如下：

```text
[ ] 会话是否只能看到明确授予的目录
[ ] 未授权目录是否被拒绝，而不是返回空目录
[ ] Web Terminal 的交互权限是否与文件授权分离
[ ] 凭据、绝对路径和临时授权是否不会写入持久配置
[ ] 会话结束后，临时访问材料是否仍可被复用
[ ] 审计记录能否区分创建会话、授予目录和执行操作
```

如果产品没有提供完整的审计接口，至少应在外围保留会话 ID、授权目录摘要、授权时间、操作者和撤销状态。不要把目录内容或令牌原文写入日志；验证授权链并不需要复制敏感数据。

## Auto Mode 的关键不是自动，而是危险动作的闸门

v0.27.4 的发布说明还提到，Auto Mode 现在要求对危险操作进行明确授权，会复核分类器超时，避免把 HTTP(S) URL 当作文件系统查找，并且会明显标记 Full Access。

这四项变化可以组成一个相对完整的风险控制模型。

“明确授权”解决的是意图问题。用户允许 Agent 自动完成任务，不等于允许它执行所有具有副作用的动作。删除文件、修改权限、发送外部消息或改变工作区状态，都应当与普通读取和分析区分开来。

“复核分类器超时”解决的是失败默认值问题。风险分类器没有及时给出结果时，系统不能简单把超时当作低风险，否则网络抖动就会变成权限提升路径。更稳妥的策略是进入待确认状态，或者拒绝执行并要求重新提交。

“避免 HTTP(S) URL 文件系统查找”解决的是输入语义混淆。一个 URL 是网络资源标识，不应因为某个接口接受字符串，就被隐式解释为本地路径。路径、URL 和命令参数应在解析阶段使用不同的数据类型或明确的前缀规则。

“明显标记 Full Access”解决的是用户认知问题。权限已经扩大时，界面必须让用户在执行前看见，而不是只在设置页里埋一个选项。可见性不是装饰，它直接影响授权是否有效。

可以用以下伪配置表达推荐的决策顺序：

```yaml
operation:
  input_kind: path | url | command
  risk: read | write | external_side_effect
  classifier_timeout: deny_or_confirm
  full_access: visible_before_run
  approval: required_for_high_risk
```

这不是 Qwen Code 的配置格式，而是用于审查实现的模型。实际检查时，应准备三组输入：一个明确的本地路径、一个 HTTP(S) URL、一个会改变状态的操作。分别确认解析结果、授权提示和失败行为。测试目标不是证明 Agent“会做事”，而是证明它不会把不同语义和不同风险等级混在一起。

## 外部消息投递：输出通道必须有边界

该版本支持把输出发送到飞书和企业微信 Webhook，并将较长的托管频道回复按有序片段发送，而不是直接截断。这看似只是消息适配器，实际涉及两个可靠性问题。

其一是内容完整性。长回复被拆分后，接收端必须能够按顺序重组；如果片段顺序不稳定，代码块、命令和结构化结果都会失去意义。其二是通道副作用。发送到外部 Webhook 意味着内容跨越了本地会话边界，因此输出策略应当独立于模型生成策略，至少要考虑敏感内容过滤、目标频道确认、失败重试和重复投递。

建议把投递过程拆成四个状态：

```text
Generated -> PolicyChecked -> Segmented -> Delivered
```

只有经过策略检查的内容才能进入分片；只有分片完成并带有序号，才能进入投递。任何一步失败，都应保留明确状态，而不是返回一个看起来成功的“已发送”。

可复现的验收样例不需要真实生产 Webhook。可以使用本地 HTTP 服务记录请求，发送一段超过通道限制的文本，然后检查：

```bash
python -m http.server 8080
curl -X POST http://127.0.0.1:8080/webhook \
  -H 'content-type: application/json' \
  -d '{"text":"long test message"}'
```

上面的命令只用于验证本地请求是否抵达，不能证明飞书或企业微信的真实接口行为。真正的集成测试还需要检查片段顺序、重复请求、网络超时和 Webhook 撤销后的错误处理。尤其不要把 Webhook 地址、令牌或完整业务内容写进公开日志。

## 记忆导入必须像数据迁移，而不是一次性开关

v0.27.4 恢复了 CLI 的 `/memory` 控制，并提供持久化工作区设置以及带类型的 SDK API，用于预览、提交、检查、取消和重试 Codex memory imports。

这组操作最值得注意的地方是“预览”和“提交”被分开。记忆导入不是简单复制文本，而是把旧状态引入新的工作区或新的 Agent 生命周期。若没有预览阶段，用户很难知道哪些内容会被写入；若没有检查、取消和重试，导入失败后只能重新执行整个过程，容易产生重复数据或部分成功。

一个安全的导入状态机应当接近这样：

```text
Draft -> Previewed -> Submitted -> Inspecting
                         |             |
                      Cancelled      Retryable
```

需要特别区分“取消尚未提交的导入”和“删除已经写入的记忆”。发布说明确认了取消和重试等 API 能力，但没有说明删除语义、冲突合并规则或跨工作区隔离策略，因此这些部分不能被假设为已解决。接入 SDK 时，应该把未确认的行为列为待验证项，而不是在业务层默默补上成功提示。

验收时至少保留四类结果：预览内容摘要、提交返回的导入标识、检查接口的最终状态、失败后的重试关联关系。重试必须能回答“这是同一次导入的再次执行，还是创建了一个新的导入任务”。否则运营数据和故障排查都会失真。

## 从 Release Notes 到升级验收：一份可执行方法

面对 AI CLI 的快速迭代，最有效的升级方式不是逐条阅读宣传语，而是把发布说明转换为行为契约。

第一步，给每条变化标注对象：会话、工作区、授权、外部通道、持久状态或用户界面。第二步，给对象标注副作用：只读、写入、外发、长期保存。第三步，为每个副作用设计一个允许路径和一个拒绝路径。第四步，记录证据类型：版本标签、Release Notes、命令输出、审计记录或人工确认。最后，把“未在发布说明中说明”的部分列为未知，不用推测填补。

对于 v0.27.4，最小验收矩阵可以这样组织：

| 能力 | 正向验证 | 失败边界 | 需要保留的证据 |
| --- | --- | --- | --- |
| 托管会话 | 进入被授予的工作区 | 访问未授权目录 | 会话与授权记录 |
| Web Terminal | 能建立交互式终端 | 授权撤销或路径不可用 | 终端状态与错误 |
| Auto Mode | 普通操作自动执行 | 高风险操作需要授权 | 操作分类与确认记录 |
| URL 输入 | 按 URL 语义处理 | 不应当查找为本地文件 | 解析结果与拒绝日志 |
| 外部投递 | 长消息按序发送 | 超时、重复和撤销 | 片段编号与投递状态 |
| 记忆导入 | 预览后提交 | 取消、检查和重试 | 导入 ID 与状态流转 |

## 结论：能力越多，越要把“可执行”拆成多个状态

Qwen Code v0.27.4 的价值不只在于增加了托管终端、消息通道或记忆 API，而在于它把 Agent 的生命周期拆得更细：访问工作区需要授予，危险动作需要授权，外部输出需要经过投递边界，持久记忆需要预览和状态管理。

这也给 AI 工具升级提供了一个可迁移的判断标准：不要问“这个版本能不能自动完成任务”，而要问“它能否在正确的身份、正确的资源范围、正确的风险等级和正确的失败状态下完成任务”。

对于 Alpha、RC 或快速发布的 CLI，这个标准尤其重要。另一个官方 Release 可能只提供版本标签和少量变更摘要，不能因此推断其行为契约已经完整。发布标签证明“有一个版本”，详细说明和可重复检查才逐步证明“这个版本在什么边界内可靠”。
