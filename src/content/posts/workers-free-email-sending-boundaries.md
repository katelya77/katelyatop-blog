Cloudflare 在 2026 年 11 月 24 日公布，Workers Free 计划可以通过 Email Sending 向账户中已验证的目的地址发送邮件。开发和测试阶段可以免费发送到这些地址；要发送给任意收件人，则需要升级到 Workers Paid 计划。已验证收件人的发送在所有计划中免费，并且不计入月度配额和每日发送限制。[S8]

这项变化很容易被简化成“Workers 可以免费发邮件了”，但工程上更有用的理解是：发送通道开放了一个受收件人资格限制的使用范围，同时把相关邮件纳入 Email Sending 的活动、分析和事件体系。它适合为开发、测试和团队内部通知减少接入门槛，却不是可以不经检查直接用于任意收件人的免费群发服务。

## 先把发送资格和发送能力分开

一个邮件发送请求能否成立，至少要分清三件事：调用方式、发件域与收件人资格。Cloudflare 的公告列出 Workers binding、REST API 和 SMTP 三种发送入口，并说明可以先接入发送域，再向已验证的目的地址发送。三种入口是同一项服务的不同调用路径，不应误认为选择 SMTP 就能绕过计划限制；公告明确把任意收件人发送与 Workers Paid 计划关联。[S8]

因此，判断一次发送是否符合当前计划，不能只看 Worker 是否拿到了 Email binding，也不能只看发件域是否完成接入。开发和测试时还要确认目标地址已经在账户中验证。计划限制应被视为发送链路的一部分，而不是上线时才补上的账单问题。

可以把资格判断拆成一个简单矩阵：

| 场景 | 需要确认的条件 | 处理方向 |
| --- | --- | --- |
| 开发或测试通知 | 目的地址已验证，发送域已接入 | 使用 Free 计划测试 |
| 团队内告警 | 每个收件目的地址符合验证要求 | 逐个验证并记录用途 |
| 面向任意收件人的生产发送 | 当前计划允许该发送范围 | 按要求升级计划并复核限制 |

矩阵描述的是公告给出的范围，不是对所有账户配置或所有产品限制的穷举。Cloudflare 的计划与产品规则可能分别说明不同层次的费用和能力，实际部署前应核对对应产品的最新限制，不要仅凭“Free”或“Paid”标签推导出未写明的发送额度。[S8][S10]

## 最小 Worker 骨架：把限制错误变成明确结果

公告给出的 Workers 示例通过 `env.EMAIL.send()` 发送，并用错误码 `E_RECIPIENT_PLAN_RESTRICTED` 识别收件人不符合计划条件的情况。示例返回 403，并将其他错误继续抛出。这种处理方式的价值不只是让请求有返回值，而是避免把资格错误误报成已发送成功。[S8]

下面保留这一结构，但把地址作为部署配置提供，不在代码中写入真实地址：

```js
export default {
  async fetch(request, env) {
    try {
      await env.EMAIL.send({
        from: env.SENDER_ADDRESS,
        to: env.DESTINATION_ADDRESS,
        subject: "Worker test notification",
        text: "This is a test message.",
      });
    } catch (error) {
      if (error?.code === "E_RECIPIENT_PLAN_RESTRICTED") {
        return new Response("Destination is not permitted by the current plan", {
          status: 403,
        });
      }
      throw error;
    }

    return new Response("Send request completed");
  },
};
```

`SENDER_ADDRESS` 和 `DESTINATION_ADDRESS` 是示意性的运行时配置名称，须按项目采用的 Worker 配置方式提供有效值；其中目的地址必须满足当前计划的验证条件。代码没有把其他异常统统转换为 403：域配置、调用链或服务端的其他失败不应伪装成收件人限制。公告只明确展示了这个特定错误码的处理，不应据此假设所有错误都具有相同结构或都适合重试。

生产代码也不应把“请求函数没有抛出异常”直接等同于“收件人已经收到邮件”。发送请求、服务端事件与最终业务确认是不同层次；至少要保留后续事件的核对路径。若业务动作必须由用户确认，邮件发送本身不能替代确认状态。

## 配额免计不等于所有限制消失

公告的措辞很具体：向已验证目的地址的发送不计入月度配额或每日发送限制，而且在所有计划中免费。[S8] 这说明免计针对的是所列出的统计口径。它不能自动推出任何发送频率都能被接受、所有账户限制都不存在、任意收件人也免费，或邮件一定成功送达。

工程上应把“费用范围”和“发送资格”分别记录。前者回答哪些发送会计入哪些额度；后者回答目标地址能否在当前计划下发送。两者有关联，却不是同一个判断。尤其在代码审查中，看到免费发送路径后，仍应检查目的地址来源、验证状态和异常处理，而不能以“不会计费”为由省去这些控制。

还要避免把测试配置原样带入生产。开发阶段可以将已验证的团队目的地址作为固定测试目标；生产阶段若收件人由用户输入或业务数据动态生成，就必须先核对计划允许的范围，再决定是否升级及如何控制发送。没有证据表明“开发能发”意味着“生产目标集合也能发”。

## 可复现的验收清单

可以用以下步骤检查集成是否覆盖了关键边界，而不需要假定某个特定账户的配置已完成：

1. **确认发送域。** 检查 Email Sending 使用的发送域是否已按账户要求接入。若域尚未配置，先解决域配置，不要把失败归因于收件人资格。
2. **确认目的地址验证。** 在账户中确认测试目的地址已验证。测试用地址应由团队控制，避免把个人或未经授权的收件地址写入示例、日志或仓库。
3. **执行允许范围内的请求。** 通过选定的 binding、REST API 或 SMTP 路径发送一封可识别的测试消息，记录调用时间、使用的路径和返回结果，但避免记录不必要的完整地址或邮件正文。
4. **执行资格失败检查。** 在受控环境中使用不符合验证条件的目的地址，确认应用能识别 `E_RECIPIENT_PLAN_RESTRICTED` 并向调用方返回明确结果。不要为了通过测试而吞掉错误或返回成功状态。
5. **检查发送侧记录。** 在 Email Sending 的 Activity log 和 analytics 中查找测试发送。Cloudflare 公告说明，这类已验证目的地址的消息现在计入 Email Sending 流量，不再出现在 Email Routing analytics 中。[S8]
6. **检查事件与分析。** 如果系统订阅邮件事件，检查相关 Email Sending 事件；若使用 GraphQL Analytics API，公告指出可通过新增的 `isVerifiedRecipient` 字段筛选数据集。确认查询使用的是 Email Sending 数据，而不是旧的 Email Routing 视图。[S8]
7. **核对目标计划。** 若目标超出已验证目的地址范围，先核实计划是否允许发送，再进行生产验收。不要把测试账户中的成功结果当作其他账户或计划的证明。[S8][S10]

这份清单把“代码能调用”拆成配置、资格、错误响应和观测四类证据。每一项回答的问题不同：返回正常说明调用路径没有报告已知错误；活动记录回答服务侧是否能观察到流量；事件与分析帮助追踪后续状态；它们都不能被单独当成完整的业务交付证明。

## 从 Email Routing 迁移观测口径

对已有 Cloudflare 邮件工作流的团队而言，容易遗漏的变化是数据归属。公告说明，向已验证目的地址发送的消息此前作为 Email Routing 流量记录；现在转为 Email Sending 流量。因此，Email Sending 的 Activity log 和 analytics 能看到这些消息，而 Email Routing analytics 不再显示它们。相关事件通过 Email Sending 的事件订阅发布，例如 `message.delivered` 和 `message.bounced`；GraphQL 分析则可以用 `isVerifiedRecipient` 字段筛选。[S8]

这不是单纯换一个菜单名称。如果告警、日报或人工排查仍然只看 Email Routing 的统计，就可能把流量迁移误判为发送量下降。迁移检查应逐项确认：仪表盘指向哪个产品数据集，事件订阅监听哪个事件源，GraphQL 查询是否使用新的字段，历史报表的时间范围是否跨越了口径变更日期。对于跨越变更点的趋势比较，也应在报表中标出数据口径变化，避免把统计归属迁移解释成用户行为变化。

## 失败边界与工程取舍

第一类边界是收件人范围。若收件人不符合计划要求，服务可能以 `E_RECIPIENT_PLAN_RESTRICTED` 表示限制；应用应向调用方返回可解释的失败，而不是无限重试。重试不会让一个未经验证的目的地址变成符合资格的地址。

第二类边界是发送与观测的差异。一次 API 或 binding 调用的结果，不能代替 Activity log、事件订阅或业务端状态核对。若消息用于运维告警，应设计独立的发送失败监控；若消息用于用户流程，则应通过业务状态确认用户后续动作，而不是把“发出请求”写成“用户已知悉”。公告列出可用事件和分析入口，但没有承诺某种事件到达时间、投递成功率或端到端时延，因此不应据此设定未经验证的服务等级目标。[S8]

第三类边界是测试代表性。验证目的地址的成功路径适合检查集成和内部通知，却不能覆盖任意目的地址下的计划资格，也不能证明生产域名、真实业务流量和其他计划配置一致。上线验收要针对目标账户、目标计划和目标地址集合复核；如果只在个人开发环境通过，结论应限定在该环境。

是否采用 Workers Email Sending，取决于发送对象和观测需求。对于受控目的地址的开发测试、团队通知，它提供了较低门槛的接入方式；对任意收件人发送，计划升级是明确的前置条件。若系统依赖邮件事件、分析或既有 Email Routing 报表，还要把数据口径迁移纳入实施工作，而不能只改发送代码。

这次开放真正值得关注的不是“免费”本身，而是资格边界与可观测链路同时变得清晰：先验证接收范围，再调用发送能力，最后用 Email Sending 的记录和事件检查结果。把这三步分开，既能减少测试环境里对计划限制的误判，也能避免把免费额度误读成无限制发送承诺。
