## 背景：状态字段终于要进入 Agent 工作流

长期以来，Issue 中的“打开”和“关闭”只能回答任务是否存在，无法准确表达任务位于哪里。一个 Issue 可能已经分配负责人、正在编写代码、等待评审，也可能已经重新开放。为了让人和 Agent 使用同一套上下文，GitHub 在 2026 年 11 月 23 日发布了 Issue 状态与仓库看板的公共预览能力。

这次更新的核心不是增加几个炫酷的按钮，而是把工作状态变成可读、可写、可筛选、可同步的结构化数据。状态可以直接展示在 Issue 标题区、Issues 页面、仪表板和仓库看板中；Issue 状态筛选器、看板分组以及拖拽操作会围绕同一套状态值工作。

这里需要先区分证据等级：上述能力来自 GitHub 官方 Changelog，属于官方公开预览说明，不是社区传闻，也不是正式版承诺。公共预览意味着可以开始评估，但不应在生产流程中将其视为长期冻结的兼容契约。迁移脚本、治理策略和自动化都应保留回退能力。

## 状态模型：从孤立字段到协作协议

GitHub 提供的默认状态包括 Backlog、Todo、In progress、In review、Done 和 Not planned、Duplicate。它们的价值在于把不同阶段的语义从自由文本变成可枚举值：人不再需要猜测“进行中”指的是编码、评审还是等待外部服务，Agent也不再需要从标题、标签和评论中推断工作阶段。

官方预览还包含一组自动状态更新规则。Issue 关联草稿 Pull Request 时进入 In progress；草稿 Pull Request 变为 Ready for review 时进入 In review；Issue 关联已打开的 Pull Request 时进入 In review；Issue 被分配后进入 Todo；Agent 被分配后进入 In progress。这些规则的本质，是用可观察的代码交付事件更新工作状态，而不是依赖用户手工维护。

状态与 GitHub Project 同名状态值之间还会保持联动。改变任一端的状态，另一端也会更新。这意味着仓库看板、Issue 页面和 Project 可能形成一个状态共享平面，但并不等于所有状态都来自同一个权威源。仓库视图负责局部展示，Issue 状态负责实体语义，Project 负责更高层的规划配置。三者需要在同一状态集合上保持一致，才能避免“双写冲突”。

对于 Agent 接入而言，Issue 状态也可能成为任务调度的一部分。官方说明明确提到 GraphQL、REST API 和 MCP 服务都可以读取或设置状态，并选择创建 Issue 时的初始状态。状态变化还能触发 Copilot 自动化。这不是简单的 UI 功能，而是让 Agent 的计划、执行和人工审核拥有统一的状态接口。

但 Agent 不应把状态变化本身等同于任务完成。In review 只说明进入评审阶段，不能证明评审已通过；Done 只是在组织流程中表示完成，不能证明构建、部署或回归测试已经成功。状态是流程证据之一，不是交付证据的全部。

## 仓库看板：把可见性放到默认入口

仓库保存的视图现在支持 Board 布局。用户可以在视图选项中切换布局，并按状态分组；拖拽 Issue 到另一列即可更新状态。看板还支持泳道、可见字段、排序和列配置。

这样的设计适合中小型仓库直接获得工作可见性，但看板不是万能的项目管理数据库。字段过多会造成高密度界面，状态列过多会形成无意义的任务站点，自动化规则过细又可能让状态漂移。工程上更重要的是先确定状态集合，再决定看板如何呈现。

例如，一个三人维护的个人博客仓库可以只使用 Backlog、Todo、In progress、In review 和 Done。一个内容与工程混合的团队也许需要在评论和标签中记录发布渠道，但不应该为了不同角色再复制一套互不联通的状态值。状态列越接近实际决策节点，就越容易成为真正的工作协议。

仓库看板还把自动化状态从后台事件搬到了更容易观察的位置。维护者可以看到哪些 Issue 处于 In progress，哪些卡在 In review，哪些正在被 Agent 修改。可见性本身不产生效率，只有团队同时保留状态变更责任时才有价值。

## 可复现的检查清单

以下检查适合在公共预览环境中逐项验证，不要求任何机器私有信息。

第一步，选取一个非关键测试仓库，创建三到五个临时 Issue，不要直接使用生产工作流。确保至少覆盖新建、分配、关联草稿 PR、草稿 PR 转为 Ready for review、关联开放 PR 等场景。

第二步，在 Issue 创建或标题区设置状态。确认状态图标能够出现在 Issue 页面、Issues 仓库列表和仪表板中。需要特别检查状态筛选语法：官方说明中可以使用 status: 过滤；检查是否能组合搜索目标状态与责任人、标签或时间条件。

第三步，打开仓库保存视图，在 View options 中切换为 Board 布局。按 Status 分组，拖动 Issue 到不同列，并回到 Issue 详情页确认状态是否同步。这个操作验证的是用户界面与实体状态的一致性，而不是仅看页面是否渲染成功。

第四步，如果仓库已连接 GitHub Project，为一个状态值建立相同名称的 Project 状态。从 Issue 修改状态，再检查 Project 是否同步；反向修改 Project 后，再检查 Issue 是否同步。只验证单向联动是不够的，双向联动、并发修改和网络失败都属于验收范围。

第五步，验证 Agent 接入。读取一个已知状态、尝试设置一个允许状态，并创建一个带初始状态的测试 Issue。若使用 MCP 或 API，记录请求是否成功、状态是否出现在 Issue 详情中、状态变更是否触发预期的自动化。不要只看工具调用返回成功：必须核对仓库中的最终状态。

第六步，验证 Agent 的运行状态与网络状态之间的边界。例如 Claude Code v2.1.331 在官方 Release 中加入了 claude doctor 的 API 连通性检查。可以运行相应客户端的 claude doctor，并确认其只把“可访问 API”报告为独立证据。模型未响应、网关认证失败、代理压缩异常或状态写入失败，都可能同时发生；状态能力正常不能覆盖诊断能力异常，反之亦然。

## 验证方式：从点击到证据链

最基本的验证是人工核对：修改状态后刷新多个入口，确认图标、筛选和看板列一致。下一层是自动化验证：保存一份固定测试矩阵，在预览环境中重复创建、分配和转换 Pull Request；每一步都检查状态最终值及是否触发预期自动化。

验证 MCP 和 API 时，应记录至少四类证据：请求参数、操作版本、服务响应和仓库最终状态。只保存响应无法证明状态已写入；只保存最终状态无法证明写入来自哪条 Agent 调用。完整证据链至少需要把调用与结果关联起来。

还需要区分状态机和可观测性。状态机证明状态之间允许怎样转换，可观测性证明转换是否发生。应当检查非法转换是否被拒绝、重复触发是否幂等、部分失败是否留下中间状态，以及状态回滚后是否触发了额外副作用。

公共预览阶段还要固定产品版本或更新时间。不建议在脚本注释里写“目前支持”而不保存测试日期；当自动化依赖预览能力时，能力可用性本身就是需要监控的配置项。

## 失败边界：状态正确不代表交付完成

Issue 状态不是分布式事务。它可以表达工作阶段，但不能替代锁、幂等键、审计日志或回滚机制。Agent 两次更新 Done，最终状态可能仍然正确，但系统可能重复触发一次通知或一次部署。如果自动化没有幂等处理，同一状态值的重复写入会产生额外副作用。

同时，自动状态规则可能与人工操作冲突。Issue 已关联开放 PR 是进入 In review 的规则，但 PR 的环境检查、人工评审和合并状态仍可能不同。若维护者把状态手动改回 In progress，而自动化再次识别开放 PR，就可能形成规则反复覆盖。

公共预览能力还存在兼容风险。状态名称、筛选语法、MCP 参数、自动化触发行为可能在正式版中调整。生产脚本若在解码 API 响应时假设固定枚举值，可能在新增状态或行为变化时失败。更稳妥的做法是拒绝未知状态、记录未知值并暂停自动决策，而不是静默地把未知状态映射到当前集合。

网络故障也会制造虚假结论。MCP 或 REST 调用超时不一定意味着状态没有写入；可能请求已送达但响应丢失。重试若没有幂等约束，也可能重复触发后续动作。因此每次状态写入都应先查询最终状态，再决定是否重试。

## 工程取舍：统一命名还是允许本地语言

状态越标准化，跨仓库和跨 Agent 的协作成本越低；状态越自由，团队越容易表达领域差异。GitHub 默认状态适合大多数软件交付流程，但并不适合每一种工作形态。新闻选题、课程排期、视觉设计和运维事故的有效状态集合可能完全不同。

当组织需要本地语义时，可以保留 GitHub 状态作为外部协议，同时在标签或字段中存放领域状态。例如内部流程使用“等待素材”“已出稿”“等待发布”，但仍将交付实体映射到 Todo、In progress、In review 或 Done。这样可以兼顾局部表达和跨仓库统一。

反过来，若直接把所有领域状态都塞进默认枚举，状态列会失去真实语义；若为每个仓库建立完全独立状态，Agent 就必须维护大量映射关系。较好的折中是统一少量跨组织状态，允许非核心字段描述局部过程。

还有一个治理问题：谁可以设置哪个状态？如果所有 Agent 都能直接把 Issue 改成 Done，状态字段会失去人工验收含义。更合理的权限模型是 Agent 设置 In progress 或 In review，人工或专门的发布流程设置 Done；状态变更应进入审计日志，至少记录操作主体和关联证据。

## 原始结论

GitHub 的公共预览不是只在界面上增加了一个状态下拉框，而是在给 Issue 工作流提供一个可共享的状态协议。仓库看板负责可见性，Issue 状态负责语义，Project 负责规划联动，API 与 MCP负责机器可读写，自动化负责按事件推进。

真正的工程价值来自这条链路是否可验证：状态能否显示、筛选、同步、触发和回滚；Agent 能否读取和写入；网络、认证或部分服务故障时能否避免重复修改；状态变成 Done 后是否还有独立证据证明交付完成。

在公共预览阶段，最稳妥的策略不是立即替换所有看板，而是用一个测试仓库建立状态模型、接入规则、审计字段和失败边界。只有状态能够成为交付证据链的一部分，而不是替代证据链，这种自动化才值得扩展到生产。
