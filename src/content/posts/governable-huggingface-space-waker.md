社区里把 Hugging Face Space “保持在线”说得很简单：定时访问接口，发现休眠就重启。但这类脚本一旦进入长期运行，就不再是一个定时 HTTP 请求，而是一个小型控制平面：它要读取远端状态，决定是否执行有副作用的操作，管理多个身份，保存审计记录，还要在失败时告诉操作者究竟是 Space 休眠、接口失败、凭据错误，还是 Worker 自己没有按计划执行。

本文选择 CF-HF-Waker 作为工程样本。它的公开仓库描述了从 GitHub Actions 迁移到 Cloudflare Workers 的实现，并提供状态检测、定时触发、多账号多 Space、KV 历史记录和 Telegram 通知等能力。需要先划清证据等级：Cloudflare Workers 的无服务器、隔离执行和 Cron Triggers 是平台能力；Hugging Face Spaces 是模型与应用展示、运行的平台产品；而“查询 runtime.stage 后按状态唤醒”属于这个具体项目的实现方式，不应被表述成 Hugging Face 官方推荐的保活方案。

## 一、真正要解决的是状态机，不是定时器

最容易写出的版本是“每隔几分钟调用一次重启接口”。它的问题在于把所有状态都当成同一种状态：正在运行的 Space 被重复重启，构建中的 Space 被打断，接口短暂超时也可能被误判为需要恢复。这样做不仅增加远端请求，还会让故障从“服务冷启动”扩大成“服务持续被人为打断”。

CF-HF-Waker 的核心思路是先读取 Space 的运行阶段，再决定动作。可以把这个流程抽象成四个状态：

1. `RUNNING`：目标已经正常运行，巡检记录“跳过”，不执行重启。
2. `SLEEPING` 或 `PAUSED`：目标处于休眠或暂停，进入唤醒路径。
3. 构建中或其他过渡状态：不应简单地视为失败，需要记录状态并等待下一轮。
4. 查询失败或返回异常：这是控制面故障，不能伪装成“已唤醒”。

这个模型的关键不是状态名称本身，而是把“读取状态”和“改变状态”分开。读取是幂等的，改变是有副作用的；只有在读取结果明确落入允许唤醒的集合时，才进入第二步。工程上可以用如下伪代码表达：

```js
const stage = await readSpaceStage(repo, token)

if (stage === "RUNNING") {
  return { action: "skip", stage }
}

if (stage === "SLEEPING" || stage === "PAUSED") {
  await wakeSpace(repo, token)
  return { action: "wake", stage }
}

return { action: "observe", stage, error: "unexpected-stage" }
```

这里的 `observe` 很重要。未知状态不应该自动升级为强制重启，因为未知往往意味着 API 返回结构变化、权限不足或项目尚未覆盖某个生命周期阶段。宁可让通知系统报告“需要人工确认”，也不要把不确定性包装成成功。

## 二、为什么 Worker 适合做轻量控制平面

Cloudflare 官方将 Workers 描述为运行在全球边缘的无服务器函数平台，采用轻量级 isolates 架构，按 CPU 执行时间计费，并提供 Cron Triggers、Queues 和 Workflows 等用于后台任务的能力。对于 Space 巡检来说，Worker 的价值不是“离用户更近”这么简单，而是把一个需要长期运行的控制循环从常驻服务器中拆出来。

传统方案通常需要一台机器持续运行定时器、脚本和日志服务。它要处理进程保活、系统升级、磁盘轮转和网络出口；Worker 方案则把触发器、请求处理和少量状态存储交给平台。CF-HF-Waker 的实现还加入了 Web 控制台，使手动唤醒和定时巡检使用同一套状态判断逻辑，减少“网页按钮一套逻辑、定时任务另一套逻辑”的分叉。

不过，Worker 并不等于无限可靠。它适合短时的状态查询与控制请求，不适合把大量构建日志、长时间轮询或大文件处理塞进一次执行。若远端唤醒动作本身是异步的，Worker 的职责应当是提交动作并记录提交结果，而不是同步等待 Space 完成构建。下一轮巡检再读取状态，才能避免单次执行时间被远端冷启动拖长。

一个合理的架构分层如下：

```text
Cron Trigger / 手动请求
          |
          v
  认证与参数校验
          |
          v
  按账号分组的 Space 清单
          |
          v
  查询 runtime.stage
    |              |
 RUNNING       SLEEPING/PAUSED
    |              |
  记录跳过       提交唤醒
          \      /
           v    v
       KV 审计记录
             |
       Telegram 汇总通知
```

其中 KV 不是业务数据库，而是轻量审计存储。公开项目说明中，它用于保存最近的巡检与手动唤醒历史。这个边界应保持清晰：KV 可以帮助回答“最近发生了什么”，不能替代完整指标系统，也不能保证保存所有远端运行日志。

## 三、部署时最容易忽略的是凭据边界

项目公开说明给出了几类环境变量：Space 列表、Hugging Face Token、控制台访问密码、Telegram Bot Token 和 Chat ID。部署时最重要的不是照抄变量名，而是先决定身份和资源之间的绑定关系。

最小单账号配置可以类似这样：

```text
HF_TOKEN=hf_xxxxxxxxxxxxxxxxxxxx
SPACE_REPO_ID=alice/space-one,alice/space-two
SECRET_KEY=change-this-console-password
```

如果需要管理多个账号，项目支持把 Token 与 Space 列表绑定在同一配置中，例如：

```text
SPACE_REPO_ID=hf_token_A:alice/space-one,alice/space-two;hf_token_B:bob/space-three
```

这类配置方便，但也带来明显风险：只要控制台配置泄露，多个身份和资源就会同时暴露。因此更稳妥的做法是把 Token、控制台密码和 Telegram Token 都放在 Cloudflare 的 Secret 类型变量中，而不是写进源码、截图、公开 README 或前端代码。Space 标识可以是普通配置，访问凭据不应混在可公开复制的 Worker 源码里。

还要注意权限最小化。公开项目说明要求用于唤醒的 Hugging Face Token 具备相应的写权限，但“能写”不代表应该给它整个账号的最大权限。实际部署前应检查 Token 是否只服务于预期账号和 Space；若平台提供更细粒度的资源范围，应优先使用范围更窄的凭据。多账号功能的价值是隔离责任，不是鼓励把大量账号批量塞进一个 Worker。

控制台也必须被视为管理面，而不是普通展示页。`SECRET_KEY` 保护的是手动唤醒与 `/wake` 一类操作入口，不能只给页面加一个隐藏按钮就算完成。检查清单至少包括：

- 管理接口是否要求独立认证，而不是只依赖前端状态。
- 错误响应是否避免回显完整 Token、请求头和远端响应原文。
- 日志是否只记录账号别名、Space 标识和结果，不记录凭据。
- 多个账号失败时，是否能定位到具体账号，而不是只返回一个总失败。
- 是否关闭不需要的公开路由，避免把手动唤醒接口暴露给全网。

## 四、把“部署成功”拆成四层验证

复制代码并点击 Deploy，只能证明 Worker 有一个版本，不能证明巡检系统可用。更可靠的验收应分成四层。

第一层是配置验证。确认 Worker 的 Cron Trigger 已绑定，Secret 名称与代码读取的名称一致，Space 标识格式合法，KV 绑定存在。若项目支持网页控制台，先访问根路径确认页面可加载，但不要把“页面能打开”当作凭据有效。

第二层是只读状态验证。选择一个明确可访问的 Space，先执行一次手动巡检，观察结果是否能够区分 `RUNNING`、休眠状态和查询失败。运行中的目标应该得到“跳过”结果，而不是无条件产生重启记录。这样可以验证状态机的第一条安全线。

第三层是副作用验证。只对自己拥有或明确获授权管理的 Space 执行唤醒，确认记录中同时包含目标、原始状态、动作、时间和结果。不要用反复强制重启来验证“按钮有效”，因为这会把测试成本转嫁给远端构建资源。项目公开说明也建议日常任务使用智能模式，避免频繁使用 `force=true`。

第四层是通知与审计验证。故意制造一个可控的配置错误，例如临时使用无效 Token，确认系统报告的是认证或查询失败，而不是“唤醒成功”。随后恢复配置，再检查 KV 历史是否保留了两次不同结果。通知的意义不是制造消息数量，而是让运行者知道哪些 Space 被跳过、哪些被唤醒、哪些失败。

可以把验收结果整理成一张小表：

| 场景 | 预期动作 | 不应出现的结果 |
| --- | --- | --- |
| Space 正在运行 | 记录并跳过 | 无条件重启 |
| Space 处于休眠或暂停 | 提交唤醒并记录 | 只显示“检查成功”但没有动作结果 |
| Token 无效 | 报告认证失败 | 伪装成 Space 故障 |
| 远端接口超时 | 标记查询失败，等待下一轮 | 立即连续重试或强制重启 |
| KV 未绑定 | 明确提示审计不可用 | 页面显示“已记录” |

## 五、失败边界决定它是不是运维系统

最常见的失败是把“唤醒”误解成“保证在线”。Space 仍可能因为资源不足、构建失败、应用自身异常或平台策略再次进入暂停；一次成功的唤醒请求只证明控制面提交了动作，不证明应用已经通过健康检查。除非另有应用层探针，否则系统应使用“已提交”“等待确认”这样的结果词，而不是“服务已恢复”。

第二个边界是频率。社区项目说明提到，免费 Space 可能在长时间无交互后进入休眠，并建议把 Cron 设置为每天数次，而不是每分钟轮询。这里的工程原则比某个具体间隔更重要：巡检周期必须低于业务可接受的冷启动容忍度，但不能为了追求“永不休眠”而制造高频控制流量。周期应该根据应用价值、构建时间、资源限制和平台政策共同决定。

第三个边界是通知风暴。若远端持续失败，每次 Cron 都发送一条 Telegram 消息，几小时后通知渠道就失去价值。更好的策略是按目标聚合结果，在正常运行且全部跳过时启用静默模式；只有状态变化、连续失败或从失败恢复时才提高通知等级。项目已提供“全部正常时不打扰”的配置方向，但连续失败退避和恢复通知仍应结合自身需求补齐。

第四个边界是多账号并发。`Promise.all` 可以让多个目标并发处理，但并发不是越大越好。账号数量、远端 API 限制、Worker 执行时间和通知长度都会形成约束。并发任务应有清晰的单目标结果，不能因为其中一个失败就吞掉其他目标的成功；也不能因为追求毫秒级完成，把所有账号配置成无法审计的批量操作。

## 六、原创结论：保活工具应升级为“最小控制平面”

从这个项目可以抽象出一个比“自动唤醒脚本”更稳健的设计公式：只读探测优先，状态驱动动作，凭据按资源隔离，副作用可审计，失败结果可区分。

它也说明了一个常被忽略的取舍：如果你的 Space 只是偶尔演示，冷启动本身可能比维护一套长期巡检更便宜；如果 Space 承载个人 API、团队 Demo 或定时任务，才有必要引入 Cron、KV 和通知。但一旦引入，就不要只追求“每天都在线”，而应把目标改成“在可接受成本内，知道它为什么不在线”。

因此，验收标准不应是“Worker 部署完成”或“按钮能点击”，而应是：运行中的目标不会被无意义重启；休眠目标能提交一次可追踪的唤醒；凭据不会进入源码和日志；失败能区分查询、认证与远端运行问题；审计记录能支持下一次排障。做到这些，Cloudflare Worker 才不是一个定时器，而是一个边界清楚、动作克制、结果可验证的轻量运维控制平面。
