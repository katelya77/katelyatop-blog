AI 工具的发布说明，往往把“支持了什么”放在最显眼的位置：某个后端新增了优化，某项扫描能力可以批量启动，某个版本已经发布。但工程上真正困难的问题不是功能是否存在，而是它在什么输入、什么范围、什么生命周期和什么失败条件下成立。

GitHub Changelog 在 2026 年 11 月 16 日宣布，AI Scan for repositories 支持一次启动最多 20 个仓库的扫描；该能力仍处于 public preview。llama.cpp 的 b12441 则修复了 WebGPU flash attention mask 对 head 维度处理不正确的问题，并调整了相关参数缓冲区与共享内存估算。两者看似分属代码安全与推理运行时，实际上揭示了同一条工程规律：能力扩展必须和验证边界一起交付。

## 两种升级：治理面的扩展与运行时的修正

AI Scan 的升级发生在控制面。根据 GitHub 的一手说明，它会扫描仓库默认分支，覆盖 CodeQL 尚未支持的语言，也会在 CodeQL 已分析的语言中寻找额外问题；扫描结果会出现在与 CodeQL 告警并列的 code scanning backlog 中。批量启动最多 20 个仓库，减少了逐仓库点击的操作成本，但它没有把“扫描已启动”变成“所有风险已发现”。

这里至少有四个不同状态：组织设置允许启动、目标仓库被选中、扫描任务真正开始、结果进入告警队列。任意一个状态成立，都不能替代其余状态。尤其需要注意的是，材料只确认了默认分支扫描，并没有证明它会覆盖任意分支、历史提交、未选中的仓库或所有语言中的同等问题。

llama.cpp b12441 的升级发生在运行时正确性。发布说明指出，WebGPU flash attention shader 原先没有正确使用 mask 的 head 维度，当 `ne[2] > 1` 时可能产生错误结果。修复包括让 mask offset 和向量块状态携带 head 信息，并按 `head % mask->ne[2]` 进行广播。这不是单纯的性能优化，而是输入形状变化后，计算结果是否仍可信的问题。

同一版本还调整了参数缓冲区大小，使其能够容纳新增的 mask 字段，并修正 K、V 读取路径与共享内存估算之间的不一致。由此可见，内核修复的验证对象也不止是“能否启动”：需要同时检查输入维度、输出正确性、资源估算和设备限制。

## 先把证据等级写进验收单

这两项能力的证据等级不同。AI Scan 的批量启动明确标注为 public preview，说明功能已经公开可用，但产品行为、限制和界面仍可能变化。它适合进入受控试用，不适合直接推导出长期稳定的组织安全基线。

b12441 的发布页则标注为 pre-release。它可以作为具体修复存在的直接证据，但不能自动等价于稳定版推荐，也不能证明所有 WebGPU 设备、模型和输入都已覆盖。工程记录中应保留“事实”和“推论”的区别：

- 事实：某个版本包含某项修复或能力。
- 条件：该能力只在材料明确的范围内成立，例如默认分支、最多 20 个仓库或特定 mask 维度。
- 未知：没有材料支持的稳定性、覆盖率、性能提升和跨设备兼容性。
- 结论：需要通过自己的输入矩阵、仓库清单和结果核验得到，而不是从发布标题推断。

最小的证据归档可以这样做：

```bash
mkdir -p evidence
curl -L --fail \
  https://github.blog/changelog/2026-11-16-bulk-start-ai-scan-for-repositories \
  -o evidence/github-ai-scan.html

curl -L --fail \
  https://github.com/ggml-org/llama.cpp/releases/tag/b12441 \
  -o evidence/llama-b12441.html

sha256sum evidence/*.html
```

这段命令只负责保存发布页面和校验文件完整性，不应被误认为已经验证了扫描结果或推理输出。发布页面是“版本事实”的证据，运行日志和结果对比才是“行为事实”的证据。

## AI Scan 批量启动的可复现检查清单

在组织内试用批量扫描时，建议把操作拆成四个阶段，而不是直接记录“点击成功”。

第一阶段是范围盘点。建立目标仓库清单，至少记录仓库名称、默认分支、是否有代码扫描配置、是否属于当前试验范围。材料确认 AI Scan 面向默认分支，因此清单不能只统计组织仓库总数，还要明确哪些仓库的默认分支确实承载生产代码。

第二阶段是能力开关。根据发布说明，批量启动可以在启用组织级设置时选择多个仓库，也可以从代码扫描组织告警页面启动；单个仓库还可以从自己的告警页面启动。验收时应记录入口、操作者、时间和选中的仓库数量，确保“最多 20 个”被当作一次操作上限，而不是组织级覆盖上限。

第三阶段是结果确认。对每个选中的仓库检查：是否出现扫描任务、是否有新的 backlog 项、结果是否归属于预期仓库和默认分支。没有发现告警不等于扫描未发现问题，更不等于仓库无漏洞；必须区分“任务未完成”“任务完成且无结果”“结果尚未进入队列”和“确实没有告警”。

第四阶段是失败处理。预览功能应当允许单仓库重试和人工回退。若 20 个仓库中只有部分出现结果，不能用批量操作成功来覆盖缺失项。应把未完成仓库重新列为待处理项，并保留原始批次记录，避免重试后丢失覆盖率证据。

可以用一个简单的表格或脚本维护状态：

```text
repository,default_branch,selected,started,result_visible,verified
service-a,main,yes,unknown,unknown,no
service-b,main,yes,yes,yes,yes
service-c,develop,no,n/a,n/a,no
```

其中 `selected`、`started`、`result_visible` 和 `verified` 必须是不同字段。把它们压缩成一个布尔值，正是批量安全能力最常见的审计盲区。

## WebGPU 修复不能只验证“没有崩溃”

对 b12441 这类内核修复，测试重点应放在触发条件上。材料明确指出问题出现在 mask 的 head 维度大于 1 时，因此测试矩阵至少要包含 head 维度为 1 和大于 1 的两组输入，并比较修复前后的结果。若只运行默认示例，恰好使用单 head mask，就可能得到“测试通过”的假象。

验证时可以把问题拆成三层：

1. **形状层**：确认输入 mask 的维度确实包含多个 head，并记录实际的 `ne[2]` 或等价维度信息。
2. **结果层**：使用同一输入、同一模型和同一采样配置，对比 WebGPU 输出与可信参考后端的结果；不能只比较进程退出码。
3. **资源层**：关注参数缓冲区和工作组共享内存是否触及设备限制，尤其是 K、V 只有一侧直接读取以及两侧都直接读取的组合。

一个通用的检查框架可以先固定环境变量和输入，再保存输出摘要：

```bash
set -eu
export MODEL_PATH=/path/to/model
export PROMPT='fixed verification prompt'

# 使用项目现有的 WebGPU 启动方式运行，保存完整日志
./your-webgpu-runner --model "$MODEL_PATH" --prompt "$PROMPT" \
  2>&1 | tee evidence/webgpu-run.log

# 至少保存版本、设备和输入摘要
./your-webgpu-runner --version
sha256sum evidence/webgpu-run.log
```

这里没有假设 llama.cpp 的具体构建参数或启动器名称，因为材料只证明了发布内容，没有提供统一命令行接口。真正的验收应以项目当前构建方式为准，并将设备、驱动、模型量化格式和输入形状纳入记录。否则，即使输出看起来正常，也无法判断到底验证了修复，还是绕开了触发路径。

## 性能、正确性与覆盖率不能互相替代

工程团队常把三种指标混在一起：更快、没有报错、覆盖更多。它们对应完全不同的风险。

对 WebGPU 内核而言，减少共享内存估算可能帮助某些 K/V 组合满足工作组存储限制，但这不代表所有设备都更快；参数缓冲区扩大也不代表吞吐量提升。首要问题应是结果正确，其次才是资源边界和性能变化。

对 AI Scan 而言，一次选择 20 个仓库主要改善治理效率，不等于扫描质量提高。扫描结果进入 Code Scanning backlog，意味着它可以被纳入现有告警工作流，但不代表与 CodeQL 具有相同检测范围，也不代表能够覆盖所有语言和所有类型的安全问题。

因此，报告中应分别记录：

- **正确性**：输出或告警是否符合预期。
- **覆盖率**：哪些仓库、分支、语言和输入被验证。
- **完整性**：任务是否都完成，结果是否都可追溯。
- **性能**：耗时、资源和吞吐是否变化。
- **稳定性**：预览版或预发布版在重复运行时是否出现不一致。

如果只给出“扫描成功”或“推理更快”，报告就无法回答真正的上线问题。

## 我的结论：把“能力”改写成可失败的契约

AI 功能发布最有价值的部分，不是新增名词，而是它允许工程团队重新划定自动化边界。GitHub AI Scan 的批量启动适合减少组织级安全检查的手工成本，但必须以仓库清单、默认分支、任务状态和结果可见性作为配套证据；llama.cpp 的 WebGPU 修复适合修正特定输入形状下的运行时错误，但必须用多 head mask、参考后端和设备资源限制验证，而不是只看启动成功。

更可靠的发布契约应写成可失败的形式：当输入满足哪些条件时，系统承诺什么；哪些范围没有覆盖；失败时在哪里观察；如何重试；何时回退。预览版和预发布版尤其如此。

真正可交付的不是“某功能已经发布”，而是一个能被复现、能暴露缺口、能保留证据的验证闭环。
